# 清单项层级编码：状态位后加独立层级位 + 一次性迁移

## 状态

accepted

## 背景与决策

清单存在 Thing 的 `content` 字符串里，每个真实项是 `SIGNAL + <状态位> + <文本>`（状态位
`0`=未完成、`1`=已完成，控制标记 `2/3/4`）。为支持最多三级的多级清单项，需要给每项再带一个
层级（1/2/3）。决定在**状态位之后加一个独立的层级位**：真实项变为
`SIGNAL + <状态位> + <层级位> + <文本>`，`item[0]` 仍是纯状态位、`item[1]` 是层级位、文本变为
`substring(2)`；控制标记 `2/3/4` 保持单字符不变。旧数据没有层级位，通过**一次性数据库迁移**
（新版本号，扫描所有 `isCheckListStr` 的 Thing，给每个真实项插入层级位 `1`）补齐。

## 考量过的方案

- **方案 B（采纳）·独立层级位**：状态与层级正交。现有散落各处的 `state == '0'/'1'` 判断**零改动**
  （状态位语义不变），只需把取文本的 `substring(1)` 改成 `substring(2)`、在读层级处多读一位，
  并在 `toContentStr` 导出时一并跳过层级位。代价是需要一次性迁移旧数据。
- **方案 E（否决）·状态与层级打包进单个数字**（如 `5/6`=二级未完成/已完成、`7/8`=三级）：完全
  向后兼容、零迁移，但每一处状态读取点都得改成“先解码再判断完成与否”，把风险摊到每个读取点，
  漏改一处即 bug。

## 取舍理由

项目已有成熟的版本化数据库迁移框架（已到第 20 版），把风险集中在一次可单测的纯字符串迁移上，
优于把风险分散到代码各处的状态判断点。独立层级位也让“层级与状态正交”这一领域模型在存储层得到
直接体现。

## 后果

- 需要新增一个数据库版本与对应的迁移；迁移是纯字符串变换，应配单元测试覆盖含已完成项、含控制
  标记等情形。
- `toContentStr` 等所有解析/导出路径需把层级位纳入处理（导出纯文本时跳过它）。
- 取文本从 `substring(1)` 改为 `substring(2)` 是一处需要全量排查的机械改动。
- 层级位是输出无关的存储细节；通知/分享的 Markdown 任务列表是另一条纯输出格式路径，二者独立。
