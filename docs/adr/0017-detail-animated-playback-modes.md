# 详情页动态内容按四档模式播放（Detail animated playback is user-selectable among four modes）

记事详情附件网格里的动态内容（**Animated Image**、**Motion Photo**、视频）由一个新的四档设置 **Detail Autoplay** 统一管控：**关闭自动播放 / 逐一播放 / 同时播放一次 / 同时循环播放**，默认**同时循环播放**。四档全部**按滚动视口生效**——只有当前可见的附件参与播放与排队。视频在详情页首次接入 **Thing Card Video Preview**（复用卡片那份 720px 派生 GIF），不再永远停在单帧。

**全屏预览不受此设置管控**，但普通视频在那里补上与 **Motion Photo** 同族的行为：翻到该页自动播**真视频**（从 **Thing Card Video Frame** 起 3 秒、有声、带触感）→ 回静帧；长按从视频开头播、松手回静帧、再长按续播。

这修订三条既有结论：ADR-0007「详情附件列表（默认与定制模式）播放」现受设置管控；ADR-0012「详情附件列表与全屏预览不受开关影响、照旧无条件播放」作废；ADR-0014「全屏只有 Motion Photo 播真视频」扩展到普通视频。

## 为什么

**为什么是独立的第二个设置、而不是把 Cover Autoplay 升级成四档：** 「逐一播放」在会滚动、会回收、条目数不定的 Thing Card 列表里没有可定义的语义（第几个算"一"？回收后重播吗？），强行统一会污染卡片端已经稳定的行为，还要迁移一个已投产的布尔 key。详情附件网格恰好相反——它是一次性全量布局的**有界集合**，四档在那里才成立。两个设置互不依赖："列表安静、详情热闹"是合法组合，此时详情端照常触发派生 GIF 生成。

**为什么默认必须是"同时循环播放"：** 沿用 ADR-0012 给 Cover Autoplay 定"默认开"的同一条理由——详情页的 GIF 与 Motion Photo 此前是**无条件无限循环**的，任何其它默认值都等于替用户把已有行为降级。选此默认后 GIF 与 Motion Photo 行为零变化，视频从静帧升级为派生 GIF 循环，即用户诉求开箱即得。代价是默认档也是最重的一档。

**为什么全部档位都必须按视口生效：** 详情附件 `RecyclerView` 的 `isNestedScrollingEnabled = false` 且高度按总行数写死（`AttachmentHelper.setImageRecyclerViewHeight`），**所有附件项一次性全部布局并 attach**——Glide 依赖 View 可见性的屏外自动暂停在这里**完全失效**，滚出屏幕的 GIF 照样在解码。这一个事实同时决定了三件事：不加视口判定，「同时循环」会烧掉屏幕外的 GIF；「逐一」会在用户看不见的地方空转，长记事里体验直接崩坏；而视口判定又天然成了派生 GIF 生成请求的限流器（"你看到哪个才生成哪个"）。附件区是滚动容器顶部一个连续块，按 `scrollY` 与行高算可见行即可，不需要逐 view 求交。

**为什么"一次"绑定在"进入视口"而不是"打开详情"：** 前者无状态——不维护"已播过"集合，附件增删、旋转、Activity 重建都不用同步；且用户主动滚回来正是他想看的时刻，此时给一张死图违反直觉。「一次」的诉求是"别一直循环晃眼"，不是"这辈子只播一次"。代价是必须配可见性滞回，否则手指停在边界会反复重播。

**为什么详情页复用卡片那份 720px 派生 GIF：** GIF 的画质短板是 256 色色带而非分辨率，在 3 秒循环的动态画面上放大 1.5–2 倍带来的软化远不如静止图明显；而分辨率翻倍的代价是实打实的——生成瓶颈在取帧（约 90ms/帧 × 75 帧）、存储要新开一套 key 维度、1GB LRU 周转加快。把统一长边提到 1080 则会外溢到已调优过的卡片滚动路径。

**为什么全屏用真视频而不是派生 GIF：** 这正是 ADR-0012「GIF 画质差主要是全屏/大渐变才明显」与 ADR-0014「全屏是单界面、画质要紧，值得用真视频而非降质 GIF」两条结论的直接推论。720px + 256 色抖动铺到 1080/1440 宽的全屏上会现原形。组件也是现成的——Motion Photo 那套 `MediaPlayer` + `TextureView`（矩阵对齐、生命周期、触感）直接复用，普通视频比 Motion Photo 更简单，不需要 offset/length。

**为什么全屏的自动播是 3 秒、长按却从头播完整视频：** 自动那一遍是**勾子**——与卡片、详情看到的是同一段内容（Thing Card Video Frame 起 3 秒），只是原画质；长按是**正片**，不受 3 秒窗口限制。两者时间线独立，播放头在长按之间保留，翻页或退出重置。

**为什么详情页保留长按播放、且长按是"触发后可松手"：** 「关闭自动播放」档需要一个手动入口，否则设置名与行为不符。但详情附件的长按已被 `ItemTouchHelper` 拖拽排序占用，而 `ItemTouchHelper` 在长按瞬间就把项目"浮起来"跟手——若播放要求一直按住，手指微动就可能把附件挪位，而附件顺序会被自动保存写回记事。改成"长按触发、松手继续播完"后，拖拽刚起来就随松手结束，位置几乎不可能被挪动；这个手感还与四档里"播放一次 = 完整一轮"的定义天然对齐。

## 影响

- **范围**：仅详情附件网格（`ImageAttachmentAdapter`，只被 `DetailActivity` 使用）受四档管控；Thing Card 各面仍归 Cover Autoplay；桌面 widget（RemoteViews）无法播放、永远静态。
- **"一次"的时长**：忠实播完一轮，不封顶——视频与 Motion Photo 的派生 GIF 固定 3 秒，真 GIF 播自身一轮。长 GIF 可能阻塞「逐一」队列，属已知取舍（候选封顶值 12 秒，实测后再定）。
- **播完停在静态代表帧**：GIF 回首帧；视频回 Thing Card Video Frame（零成本，派生 GIF 第 0 帧即是它）；Motion Photo 回**高画质静态主图**（其派生 GIF 首帧来自内嵌视频起点，不是主图）。与「关闭自动播放」档看到的画面完全一致。
- **生成**：详情页主动触发但只为视口内附件；与卡片端共用 `VideoCoverPreviewManager.requestPreview`，同 key 由 `enqueueUniqueWork(KEEP)` 去重；未就绪时**不阻塞**「逐一」队列，跳过后按"刚进入视口"处理。设置为「关闭」时不请求生成。
- **性能**：手机竖屏详情附件是 2 列方形网格、每项边长 = 屏宽一半，一屏典型可见 6–8 项；最坏情况 8 路 540×540 GIF 软解并发（无硬件解码）。**暂不设并发上限**，按项目惯例发 debug 真机实测帧率后再定（候选上限 6）。
- **音频**：全屏视频**不静音**，与 Motion Photo 现状一致；顺带补齐两处都缺的音频焦点（`AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`），并对翻页做防抖（停稳约 300–400ms 才起播），避免快速滑动产生声音碎片。
- **标识去留规则**：操作入口播放时隐藏（全屏中央 `iv_video_signal` 绑了点击监听），身份标识播放时保留（详情页 `ivVideoSignal` 无监听，与 Motion Photo「实况」徽标同规则）。
- **HDR**：详情页本就走 SDR 路径，派生 GIF 为 SDR，无回归；全屏静图态照常提亮（ADR-0006 不变）。
