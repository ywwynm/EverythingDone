# Thing 私密用标题前缀编码，有效私密靠集中解析在展示层强制

## 状态

accepted

## 背景与决策

EverythingDone 有两种私密：Private Thing 与 Private Thing Folder。二者存储编码**不对称**：Thing 私密编码在**标题前缀**（`title` 以 `PRIVATE_THING_PREFIX` 开头即私密，`getTitleToDisplay()` 去前缀显示），而 ThingFolder 私密是**真实布尔列** `isPrivate`。文件夹私密采用容器模型（见 `docs/features/private-content/decisions.md` 2026-06-28）：设私密只改文件夹自身，后代记事**不加前缀**，仅在展示层靠"有效私密（自身私密 OR 任一祖先文件夹私密）"保护。

决定：**暂不**把 Thing 私密迁移为独立布尔列、也不去掉前缀；而是把"展示用有效私密解析"集中为**唯一入口**（泛化自列表小部件现有的 `protectThingIfNeeded`），要求所有展示/通知界面拿到记事后都先经此入口再决定是否遮蔽。前缀继续作为"自身私密"的内部存储。

## 考量过的方案

- **方案 A（采纳）· 保留前缀编码 + 集中化有效私密强制**：不动存储与迁移，把分散在各界面的"是否有效私密"判断收敛成一条路径，新界面无法绕过。成本低、无迁移风险，立即消除已知泄露。
- **方案 C（推迟）· Thing 私密改真实布尔列 + 现算有效私密 + 去掉前缀**：与文件夹对称、模型最干净，前缀不再污染标题字段；但需 DB 版本迁移（扫描所有前缀标题→置列、去前缀、回填历史数据），风险面大。作为独立架构债推迟（见 `followups.md`）。

## 取舍理由

前缀编码的真正危害是"是否私密"与"标题内容"耦合，且"有效私密"要各界面各自现算，谁忘了谁泄露——单一记事小部件、系统通知已确认会明文泄露"处于私密文件夹内、自身无前缀"的记事。该危害的根因是"分散判断"，而非"前缀存储本身"。先用集中化（A）以最小风险消除分散判断即可堵住全部已知泄露；是否进一步迁移为列（C）是干净度问题，可单独评估，不必与本轮安全修复耦合。

## 后果

- 所有展示/通知界面（列表、单一/列表小部件、系统通知、NoticeableNotification、DoingActivity 等）必须统一经由集中入口取"展示安全"的记事；需一次性审计现有界面，漏接即泄露。
- 前缀仍存在于 `title` 字段：任何直接读 `title`（而非 `getTitleToDisplay()`）的新代码仍可能显示前缀垃圾或误判，是保留的隐患。
- 若日后采纳 C，本 ADR 由后续 ADR 取代；集中入口可平滑改为基于新列的实现，调用方无需再改。
