# 应用界面交互互斥方案

## 用户补充与已确认代码

用户强调问题不限于弹窗：设置页同时触摸“计时数字风格”和“粒子动画设置”，前者打开弹窗，后者打开二级界面，也会同时执行。用户希望统一覆盖其它界面的同类问题，继续保持先分析、不改代码。

`SettingsActivity.kt` 当前两处实现：

- 1068～1071 行：点击后新建 `DoingDigitStyleDialogFragment` 并调用 `show()`。
- 1085～1086 行：点击后直接 `startActivity(Intent(this, ParticleTuningActivity::class.java))`。

两处都是独立监听器，没有共同的请求受理状态。即使只给 `BaseDialogFragment.show()` 增加互斥，第二条 Activity 路径仍不受约束。

## 统一规则

规则覆盖整个应用，但状态按来源页面／窗口管理，不使用进程级全局点击锁。

1. 同一触摸序列默认归属一个普通交互目标，避免不同手指同时激活两个按钮／设置项。
2. 同一来源界面同一时刻只接受一个改变当前交互界面的请求。弹窗、菜单、页内模态面板、Activity 跳转和系统界面请求使用同一状态控制。
3. 请求在创建目标、修改页面字段或启动跳转之前同步登记。后续竞争请求拒绝，不排队。释放依据真实生命周期及输入交接，不依据固定点击间隔。
4. 目标界面有自己的交互状态；正常“父弹窗打开子弹窗”“弹窗替换”“弹窗内启动 Activity”属于显式顺序流程，不能按重复操作拒绝。

## 第一层：普通控件的触摸分发策略

优先利用 Android 的 `ViewGroup.setMotionEventSplittingEnabled(false)` 约束不同子控件并发接收手指输入。其语义是该 ViewGroup 只向一个子 View 分发本次触摸；同一子 View 内部仍可接收完整多指事件，因此图片缩放等手势不应被统一删掉。

依据：[ViewGroup 官方 API](https://developer.android.com/reference/android/view/ViewGroup#setMotionEventSplittingEnabled(boolean))。

实际接入需要覆盖嵌套容器、Toolbar 菜单容器、RecyclerView 动态条目、Dialog 内容及 PopupWindow 内容；只设置 Activity 最外层不能保证内部 ViewGroup 不再次拆分。应采用公共的创建／附着策略，不通过覆盖组件已有的层级监听器破坏 RecyclerView 等内部行为，也不在每次触摸时遍历整棵 View 树。

这一层处理“两个普通控件同时被触摸”，也适用于只切换设置值而不跳页面的控件。它不能独自处理先后两个完整点击、已经投递的点击回调、键盘／无障碍操作或异步代码重复请求。

## 第二层：统一的界面切换状态

候选公共组件可命名为 `UiTransitionCoordinator`，其职责是记录来源界面是否可发起新的切换及当前请求的身份。

- 弹窗的 `show`、应用的页面启动入口、菜单／模态面板入口共享同一组件。ActivityResult、旧 `startActivityForResult`、外部选择器及权限流程也要核对，不能只包最常见的 `startActivity` 重载。
- 先同步受理，再执行操作；不得等待 `onPause`、`onStart` 或新窗口获焦点后才登记。两个回调即使在同一主线程消息周期到达，后一个也必须看到前一个已经被受理。
- 页面跳转期间，来源页面不再接受其它界面切换。新页面进入后按自己的状态正常操作；来源页返回可交互状态后恢复，不在全进程维持锁。
- 弹窗打开期间，下层页面保持不可交互；当前最上层弹窗可发起合法子流程。弹窗内启动 Activity 与 Activity 根页面的残留点击必须能够区分。
- 动画隐藏真实 Window 时，输入保护仍由这套状态控制。关闭动画期间不能仅凭真实 `onDismiss` 提前释放；完成替换时可将操作权直接交给新界面，无须等待旧动画结束后再创建新界面。
- 取消进行中的旧手势并处理其剩余事件。已经排队的展示／导航回调还须经过第二层校验，不能只拦截新触摸。
- 失败和取消要按请求身份撤销登记；旧异步回调不能清除新流程状态。旋转、恢复、外部 Activity 返回和权限结果要按实际流程恢复，不能在每次 `onResume`／焦点变化时无条件清空状态。

初始化含副作用的入口必须在受理之后执行，例如颜色编辑器在 `show()` 前设置 `mBgEditorSheet`、`mColorEditorBgFrom`。单纯覆写所有 `show`／`startActivity` 而完全不审查调用前代码，仍可能留下状态覆盖问题。

## 集中接入与边界

应用主要 Activity 经 `EverythingDoneBaseActivity` → `ParticleDialogContentActivity`，透明弹窗宿主另经 `ParticleDialogHostActivity`；`ShortcutActivity` 直接继承 AppCompatActivity，属于外部入口转发，需要单独确认归属。窗口输入保护应覆盖这些实际入口，避免宣称改一个基类就覆盖所有 Activity。

29 个普通弹窗经 `BaseDialogFragment` 集中接入；`PopupPicker` 与页内模态面板需要各自的公共接入点。正常父子、替换和带前置副作用的入口需少量显式调整，不能把这一方案描述成“无需审查任何调用点”。

不对所有普通点击加入固定冷却期。普通点击完成且界面没有切换时，应允许下一次合法操作。保存、导出和后台任务的重复执行仍由相应任务状态负责；这里统一处理触摸竞争和界面切换竞争。

## 验收矩阵

| 场景 | 预期 |
| --- | --- |
| 两个按钮打开相同／不同 dialog | 最多接受一个竞争请求 |
| 计时数字风格 + 粒子动画设置 | 最多打开 dialog 或 Activity 之一 |
| 两个二级页面入口 | 最多启动一个目标页面 |
| PopupWindow／页内面板 + dialog／Activity | 共用来源界面互斥 |
| 同时触摸两个普通设置开关 | 本次手势不并行激活两个控件 |
| 快速连续的独立点击 | 界面切换期间仍受约束，不靠多指策略代替 |
| 图片缩放、裁剪、滚动 | 正常多指／拖动／取消语义保留 |
| dialog 内打开子 dialog 或 Activity | 显式顺序流程正常完成 |
| 失败、旋转、后台恢复、返回、权限结果 | 不遗留阻塞，不执行失效来源的请求 |

实施时先验证公共状态组件的竞争请求与释放条件，再在获得设备授权后合并验证真实多指和窗口切换。本轮没有运行或新增应用测试。
