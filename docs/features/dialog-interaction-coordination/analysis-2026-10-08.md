# 重复弹窗与多指打开不同弹窗的静态分析

> 后续用户补充了“弹窗与 Activity 同时打开”的反例。本文保留初次源码证据；最新实施范围以 [统一界面交互方案](ui-transition-plan-2026-10-08.md) 为准，不能按仅修改 DialogFragment 的方案执行。

## 证据范围

本轮只阅读 EverythingDone 的 Kotlin 实现、相关功能记录与 Android 官方资料。没有连接设备，也没有复现实测；源码中已确认的控制缺口与对用户设备表现的推断分别记录。用户明确要求先分析，因此不执行 diagnose 技能中的设备复现、加探针、修复与回归阶段。

## 已确认的应用实现

1. `DetailActivity.onOptionsItemSelected` 每次收到添加附件菜单事件，都会执行 `AddAttachmentDialogFragment.newInstance().show(...)`。
2. `BaseDialogFragment.show(FragmentManager, String?)` 仅检查当前对象的 `!isAdded`。新建对象总能通过此检查；公共入口没有同宿主互斥，也没有等待提交期间的登记。
3. 改变颜色入口会新建 `ThingBackgroundEditorBottomSheet`，并在调用 `show()` 之前写入 `mBgEditorSheet`、`mColorEditorBgFrom`。如果以后仅在最末端拒绝 `show()`，这些前置状态仍可能被错误覆盖，需要在准入成功后再执行初始化。
4. 工具栏的 `BackgroundUtil.applyToolbarIconRipples` 只替换背景／前景 Drawable；`GradientRippleDrawable.onStateChange` 根据 pressed 状态启动绘制动画，没有调用业务点击。
5. 粒子出现经 `startCondense` 调用 `appearContent(..., hideWindow = true)`，将 `window.attributes.alpha` 设为 0，完成后恢复。`DialogDimLayer`、`ParticleDismissOverlay`、`ParticleWindowSurface` 均不承担点击拦截。
6. `ParticleDialogStack` 在 `onStart` 登记，用于粒子窗口层级选择；它不是弹窗请求的准入控制，不能覆盖 `show()` 到 `onStart` 的间隔。

## 已确认的正常多弹窗流程

- 改变颜色 → 从世界取色：保留下层颜色编辑器，再打开相机取色弹窗。
- 开始做事 → 选择做事时长：父子弹窗。
- 添加附件 → 录音：`showRecordAudioDialog()` 先调用新弹窗的 `show()`，随后关闭附件弹窗，属于替换流程。

因此不能直接套用“一个 Activity 只要存在任意 Dialog 就拒绝所有新 Dialog”的规则。

## 平台依据

- [Fragment 事务](https://developer.android.com/guide/fragments/transactions)：`commit()` 异步执行。仅查 `isAdded` 或 `findFragmentByTag` 无法覆盖尚未执行的展示请求。
- [ViewGroup 多指分发](https://developer.android.com/reference/android/view/ViewGroup#setMotionEventSplittingEnabled(boolean))：启用事件拆分时，多根手指可以分发给不同子 View。因此两个按钮分别收到点击并不需要 ripple 重复派发。

## 粒子动画与输入可见性

核对 AOSP 的 `android16-release` 分支：

1. [WindowStateAnimator](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/services/core/java/com/android/server/wm/WindowStateAnimator.java) 创建 BLAST 窗口图层并更新其整体 alpha；[InputMonitor](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/services/core/java/com/android/server/wm/InputMonitor.java) 将输入信息设置在 `w.mWinAnimator.mSurfaceControl` 上。
2. [LayerSnapshot.canReceiveInput](https://android.googlesource.com/platform/frameworks/native/+/refs/heads/android16-release/services/surfaceflinger/FrontEnd/LayerSnapshot.cpp) 要求窗口不被隐藏，且“没有缓冲／sideband，或整体 alpha 大于 0”。对于已经提交缓冲的普通窗口，alpha 为 0 会使此条件失败。
3. [LayerSnapshotBuilder](https://android.googlesource.com/platform/frameworks/native/+/refs/heads/android16-release/services/surfaceflinger/FrontEnd/LayerSnapshotBuilder.cpp) 据此设置 `NOT_VISIBLE` 输入标志；[InputDispatcher.windowAcceptsTouchAt](https://android.googlesource.com/platform/frameworks/native/+/refs/heads/android16-release/services/inputflinger/dispatcher/InputDispatcher.cpp) 跳过此类窗口。

因此，不能把“Dialog 对象仍然 isShowing”当作“该窗口始终拦截输入”。当前出现动画隐藏的是整个 Window，而非仅隐藏一个普通 View；粒子与暗层又均不可点击，存在下层 Activity／父弹窗重新收到触摸的明确平台路径。这与用户描述的动画开启后更容易重复打开一致，但具体设备与每次异常是否走此路径仍需实测，不能标记为已复现。

消失也有边界：`GestureAnchoredDialog` 的 `ParticleDismissStartGate` 在粒子已经起播、覆盖层已经显示时执行真实 dismiss，并不等整场动画结束。因此仅在 `onDismiss` 释放输入保护，会过早暴露下层界面。

## 推荐方案：统一展示状态与输入保护

这是待实施建议，不是已经接受的产品决策。

### 展示请求先受理，再创建与初始化

- 按 Activity 管理状态，区分页面、当前弹窗与父子关系；不使用进程级布尔锁。
- 请求在主线程同步登记，然后才创建实例、修改业务引用并提交 Fragment 事务。登记必须早于 `show()` 的异步提交；不能等到 `onStart`。
- 同一来源层级已有未结束的打开／替换请求时，后续竞争请求直接拒绝，不排队；包括相同 tag 与不同 tag。
- 登记覆盖待提交、出现、可交互、关闭／交接状态。普通重新打开须等旧实例和相应输入保护结束，不能按固定毫秒数自动放行。
- `BaseDialogFragment` 统一接入；当前源码有 29 个直接子类。所有公开展示重载需纳入约束，防止将来通过 `showNow` 或事务重载绕过。
- 对先写 Activity 字段再 `show()` 的入口，使用接受请求后才执行的初始化函数，或先取得许可再写字段。颜色编辑器已确认存在这种前置副作用。

### 输入按窗口所属层级控制

- 从受理展示请求起，阻止原页面继续向控件分发触摸；新弹窗交互就绪后，由它接受输入，下层仍被阻止。
- 动画覆盖层与真实窗口的输入职责明确分开，不能依赖 `window.alpha = 0` 的窗口继续模态拦截。可在公共 Activity／Dialog 的窗口分发入口使用同一状态控制；父弹窗也必须接入。
- 对已经开始的手势发送取消并处理剩余事件，直到下一次新的 DOWN，避免动画结束后旧 UP 落到按钮上；已经投递的点击与非触摸打开请求仍须通过展示入口校验。
- 关闭中的控件不再接受新的业务操作；真实 dismiss 早于粒子完成时，输入保护不能随 `onDismiss` 提前结束。
- 通过对应请求的标识释放状态，覆盖显示失败、动画失败／取消、返回、旋转重建、页面销毁；旧回调不能释放新请求。恢复的 Fragment 应重新登记，不能因内存状态重建而失去约束。

### 正常父子与替换显式表达

候选接口语义为“从页面打开”“从当前弹窗打开子弹窗”“用新弹窗替换当前弹窗”。普通入口走默认规则，只有确有父子／替换关系的流程需要明确标注。

| 流程 | 行为 |
| --- | --- |
| 连点添加附件 | 只接受第一个 |
| 同时点添加附件与改变颜色 | 同一页面只接受先到达的一个 |
| 颜色编辑器 → 从世界取色 | 允许子弹窗，暂停父弹窗交互 |
| 添加附件 → 录音 | 接受一次替换，连续交接状态，不在两个窗口之间恢复页面输入 |
| loading → 结果／错误 | 按明确的替换或子流程展示；不能把必要业务结果当成误触静默丢弃 |

异步权限返回也须绑定发起流程：父窗口失效或页面已退出时，不能继续弹出过期窗口。

## 不宜单独作为完整修复的办法

| 办法 | 局限 |
| --- | --- |
| 每个按钮限制 300／500 ms | 不覆盖不同按钮；动画准备、慢设备和时长缩放可能超过时间限制 |
| 全局限制点击时间 | 会吞正常连续操作，无法表达父子弹窗与替换关系 |
| 只查同 tag 或 `isAdded` | tag 查询看不到待执行事务；同类／异类竞争需要共同来源层级的控制 |
| 全部改成 `showNow` | 同步提交不提供互斥，也不能阻止透明窗口期间的新触摸 |
| 只设 `splitMotionEvents=false` | 只控制该 ViewGroup 的事件拆分；仍允许跨手势连点，也不能阻止代码／无障碍发起的重复展示 |
| 整个应用禁止多指 | 影响图片缩放等正常手势，仍未解决非触摸重复请求 |
| 只修改 Window 的 alpha 或动画速度 | 无法消除无动画时的同层竞争，也可能影响 Surface 内容与快照交接 |

## 覆盖范围

公共基类能集中覆盖现有应用 DialogFragment。`PopupPicker` 使用 `PopupWindow`，首页部分外观面板是页内 View，需要在各自的公共展示入口接入同一规则后才能计入覆盖。系统权限框和外部文件选择器由系统管理，本方案约束的是应用侧发起请求。

如果将需求扩大到重复保存、导出、网络请求或 Activity 跳转，还需要按相应操作的真实生命周期定义执行中状态／幂等条件。弹窗控制不能被描述成对所有点击业务的无条件保证。

## 后续验收建议

1. 主线程连续两次请求：同种弹窗、不同弹窗均只能接受一次，特别覆盖 Fragment 事务尚未执行时。
2. 单页面真实点击：粒子关闭／仅出现／仅消失／双向开启，连续快速点击与两个按钮多指操作。
3. 在出现准备、动画播放、关闭动画期间持续触摸；检查既没有新弹窗，也没有下层业务副作用，动画结束后旧手势不会补触发。
4. 颜色编辑器 → 取色、开始做事 → 时长、添加附件 → 录音、loading → 结果，以及权限返回和页面退出。
5. 显示失败、取消、旋转、后台恢复后状态正常；错误拒绝不能覆盖现有 `mBgEditorSheet` 和撤销起点。

先在可独立验证的状态控制层补回归，再在得到设备授权后合并验证真实输入。只有静态证据的本轮不宣称已消除故障。
