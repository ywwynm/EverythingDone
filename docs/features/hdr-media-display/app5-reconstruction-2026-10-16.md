# APP5 真实增益与重建曲线调查

## 本轮结论

已找到比“存在附加图”更具体的原生实现证据，但尚未确定可以取代参考曲线的完整厂商公式。现阶段保留已接近图库的实验显示，不将未验证的浮点字段或内核常量写入重建算法。

可确认：旧格式有独立合成内核；其参数表与新 Vivid 内核明显不同；公开 CUVA 参数传递分支也不使用通用增益参数。可推断但未证明：旧格式可能使用固定解码曲线，部分私有元数据用于其他阶段。未解决：真实曲线、32 字节块剩余字段的含义，以及华为图库显示阶段的亮度映射。

## 当前证据与边界

用户反馈实验版 `202610160756` 的模式 6 显示 APP5 照片时，观感已与华为图库接近，希望进一步根据元数据精确还原。用户随后确认使用“自动”（当前按 4 倍处理），4 倍与 8 倍主观差异不明显。此反馈是视觉证据，尚不能证明当前 `selectedHeadroom^(Y'/255)` 参考曲线等于厂商算法，也不能证明两档输出数值相同。

研究只读取本地原图、公开源码与离线 SDK 文件，不连接或启动设备，不上传照片，不将厂商二进制加入 APK。应用中未知私有字段继续只记录、不参与重建。

## 本地 SDK 的新线索

在已安装的 HarmonyOS 7.0.0.107／API 26 手机 x86 SDK 的 `sys_prod.img` 中，找到 `etc/VideoProcessingEngine/hdr_compose.bin`（345,563 字节）与 `hdr_decompose.bin`（562,126 字节）。离线解包至隔离工作树的临时目录，保留原始 SDK 不变。

`hdr_compose.bin` 包含 `CLCC`／`MBSX` 容器、编译后的内核及内核参数表，未发现标准 LLVM bitcode、SPIR-V 或 ELF 标识。内核名同时包括 `kernelHDRComposeVividCase1`、`kernelHDRComposeVividLinear`、`kernelHDRComposeOldCase1` 与 `kernelHDRComposeOld`。

- Vivid 内核参数表包含逐通道 gamma、gainMapMax、gainMapMin、SDR/HDR offset、maxContentLightLevel、systemGamma 等字段。
- Old 内核的 27 项参数主要为 SDR／附加图／HDR 缓冲、`srgbEOTF`、尺寸、步长、像素格式、SDR 色彩空间与 `useHLG`。其中没有对应的逐图 gamma、增益上下限或私有参数块入口。
- **推断**：旧合成内核可能使用固定的附加图解码规则，而不是将八个私有字段直接映射为 ISO Gainmap 参数。但尚未确认 APP5 实际选用该内核，也未确定 `srgbEOTF` 缓冲的内容和构造方式，不能只根据内核名与参数表宣布公式已知。

公开 OpenHarmony 的 CUVA 分支不向通用 VPE 接口传入增益元数据，这与上述推断相容；它本身仍不能证明华为图库所有版本的实际处理路径。

## 数值核对与原生实现检查

### 自动、4 倍与 8 倍的数值差异

将两张附加图按当前适配器的半尺寸、RGB 到 Y' 整数系数读取，再代入现有参考公式，可得以下重建乘数。此为离线数值计算，不代表屏幕实测亮度：

| 样本／像素分位 | 4 倍选项的实际乘数 | 8 倍选项的实际乘数 | 后者相对前者 |
| --- | ---: | ---: | ---: |
| 照片 1，中位数 | 1.401 | 1.658 | +18.4% |
| 照片 1，第 99 百分位 | 1.770 | 2.354 | +33.0% |
| 照片 2，中位数 | 1.439 | 1.727 | +20.0% |
| 照片 2，第 99 百分位 | 2.348 | 3.598 | +53.2% |

选项中的 4／8 是参考曲线在附加图值 255 时的上限，并非整张照片统一乘以 4／8。因而切换两档不会让整图亮度直接翻倍。屏幕余量、系统色调映射和视觉适应也可能缩小可见差异，现有证据不能确认是哪一项造成。

### 原生实现进一步核对

从华为官方 CDN 的旧版 5.0.1.120 SDK ZIP 中，按 HTTP Range 获取所需分区并校验 ZIP CRC。其 `hdr_compose.bin` 也保留 Old 与 Vivid 两类内核。`libaihdr_engine.so` 实际导出 AIHDR 图像增强接口，不能仅凭名称将其视为旧 APP5 的合成实现；x86 系统分区未找到 VPE 实际算法库。

另行检查同版本官方 ARM64 系统分区，同样未找到 VPE 合成算法库。当前 7.0 的公开接口库通过动态扩展加载算法，但该 SDK 镜像中未找到相应扩展。不能把 SDK 中保留的 GPU 内核文件等同于已获得可调用的华为图库重建器。

5.0 的 Old／Vivid 参数数为 23／43；7.0 对应为 27／51。Old 新增的四项为 UV 奇数宽高偏移，仍未发现逐图 gamma、增益上下限入口。这里只分析编译产物的接口，尚未排除查找表、图像预处理或后续显示阶段使用其他参数的可能。

Old 内核常量区包含 `0.5325000286`，新旧 SDK 均存在；7.0 版本还包含 `1.8778599501`。这些常量在 Vivid 内核相同位置未出现，但尚未跟踪其运算用途，**不能直接将它们解释为 gamma 或指数系数**。以 Mesa Valhall 指令定义尝试匹配该 GPU 代码，大部分指令及开头指令均无法合理匹配，因此不沿用不兼容的反汇编结果。

继续定位原生合成实现对旧内核的选择、查找表构造与常量，优先获得可重复的数值依据。若只能取得外观相近的结果，保留“参考曲线未校准”标识，不因主观相近而将当前参数升级为正式标准。

## 下一步的有效验证

最有区分力的依据是同一原图经华为原生解码／合成后导出的 HDR 像素，附上输出格式、色彩空间和传递函数。先比较恢复后的线性像素，才能把重建误差与图库后续的屏幕适配分开。

可在独立副本中固定主图与附加图，仅改变一个私有参数字段，再比较原生输出；或固定参数，输入受控的附加图灰阶，拟合实际传递关系并用另一张照片验证。此为待执行实验，本轮未改写照片或实施设备操作。仅用常规 SDR 截图无法提供这套 HDR 数值基准。
