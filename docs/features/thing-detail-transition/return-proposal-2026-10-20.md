# 详情返回列表的连续动画方案

状态：本文件保留 2026-10-20 方案分析时的建议。用户随后批准实施，现已完成三机回归，最新结果见 [实施与验证](return-execution-2026-10-20.md)。

## 核心建议

**由接收返回的列表页主持动画：先提交本次应显示的列表，再把当前详情画面收回到该列表中实际存在的卡片。一次动画只使用一个固定的列表展示版本。**

动画只需要知道“当前有无可用目标”，不需要知道变化是由编辑、同步、排序、其他记事更新还是列表刷新引起的。

- 有目标：收回到目标的当前位置、尺寸和内容。
- 无目标：短淡出，显露正确的当前列表。
- 动画开始后新发生的更新：业务照常执行，列表呈现合并到动画结束后。

固定的是短时间内的列表呈现，不是数据库，不阻塞接收、提醒或保存。不等待整个系统停止变化，也不重放从打开详情起发生的每一个事件。

## 已核实的工程事实

1. `DetailActivity.returnToThingsActivity()` 先校验提醒、处理确认、保存，再结束页面。完成、删除、恢复、置顶等还有其他提交出口；不能只在顶部返回按钮加动画，也不能把任意 `onPause()` 当成返回。
2. 未修改记事时可以只调用 `setResult(RESULT_NO_UPDATE)`，没有结果 Intent。首页当前 `onActivityResult()` 仅在 `data != null` 时调用 `updateMainUi()`，因此返回动画不能依赖非空结果数据。
3. `ThingsActivity.onResume()`、普通编辑结果、置顶结果及碰一碰接收结果中，存在约 540～560 ms 的延迟发布。置顶路径还会在移动动画后再次重绑。直接找到卡片就开始收缩，会遇到动画中或动画后再次移动、变高、换内容的问题。
4. 现有碰一碰更新已经实现离开时的列表快照、按稳定 ID 计算差异、成批发布。其快照在 `onPause()` 获取，因为搜索键盘可能推迟 `onStop()`。这一能力值得复用，但不能原样视为通用返回事务。
5. `ThingsAdapterWrapper.tryToNotify()` 只执行队列的最后一项，`notifyItemMoved()` 又不受等待开关保护。单独打开 `setShouldWaitNotify(true)` 不能保证一批更新完整，也不能保证列表停止变化。
6. `snapshotContentUpdateEntries()` 会复制记事和嵌套缩略项，但文件夹对象仍有共享引用，部分外观还会查询实时 Manager。仅复制 List 容器不等于持有稳定的展示数据。
7. 文件夹缩略记事是嵌套的预览 View，不是外层 RecyclerView 的独立 ViewHolder；当前普通卡片的稳定 ID 标记和隐藏接口不能直接覆盖这些预览。
8. 状态更新结果中同时处理撤销信息、习惯庆祝、计数等。不能用“一律重新加载并通知全表”替代业务结果处理。10 月 16 日的定向更新修复也明确保留普通更新的单卡动画，见[相关记录](../thing-transfer-update/home-item-update-2026-10-16.md)。

## 一次返回的顺序

### 1. 完成原有返回业务

继续使用现有校验、确认、保存和结果计算。用户取消确认、提醒时间不合法、只是收起键盘或退出裁剪／清单移动模式时，不创建返回动画。

真正决定离开后，捕获此刻实际可见的详情内容及必要元素。保存只执行一次；抓图失败或动画失败不能造成重复写入，也不能阻止已经完成的正常返回。

打开详情时只保留轻量的返回来源描述：记事 ID、接收页面身份及来源展示位置的身份信息。不要为返回长期保留打开时的整屏图片、旧坐标或强引用 View。现有展开令牌在详情接收时已被消费，需要独立的轻量来源描述。

### 2. 列表先承接画面，再提交结果

在列表页第一次可见绘制之前安装当前详情画面，随后放行本次结果处理与列表提交。两个 Activity 之间仍关闭系统窗口动画，实际运动在 `ThingsActivity` 的绘制层中完成。

接入需覆盖无修改返回、结果回调及恢复可见等路径，不假设只有一种生命周期回调顺序。不能先放行 `onStart()` 的通知，再补装覆盖层。

本次提交继续使用当前页面的真实文件夹、搜索、筛选及排序规则，合并截至提交时已经发生的更新；刷新计数、空状态和相关页面外观。保留正常滚动锚点，不为了找记事主动滚屏、切换筛选或进入其他文件夹。

原有的结果处理继续负责业务语义。撤销记录不能丢，提示条和庆祝等可见反馈安排在返回交接后显示，避免被覆盖层遮住并提前消耗显示时间。

### 3. 提交完成后确定目标

本次列表提交在详情画面覆盖期间直接形成最终布局，不再叠加该批次的卡片移动、换内容或入场动画。先结束已有相关 ItemAnimator，再对这一批提交临时抑制项目动画；其他普通更新继续保留原有动画。

在实际布局完成、该批 adapter 更新已经反映到布局后，通过统一的卡片目标接口查找记事：

- 普通列表卡与文件夹缩略记事都提供记事 ID、展示位置身份、当前 View 和有效可见裁剪。
- 优先匹配原来的展示位置身份；该展示位置不存在时，只接受当前接收页面内唯一可确定的同 ID 可见卡片。无法消除歧义时视为无目标，不随意取某个旧 View。
- 必须检查当前绑定身份、授权、挂载状态、几何及实际可见区域；位置索引只用于查找，不能作为身份。
- 只有一部分可见时按真实裁剪收回；完全离屏、过滤掉、删除、移出当前页面或不允许显示时，不制造目标。

找到目标后记录它在这次布局中的几何和实际外观。这是当前目标，不是打开详情时的来源截图。

不等待网络、不等待全部图片解码，也不要求所有动态内容停止活动；匹配不到某个元素只降低该元素的过渡精度。准备阶段按实际就绪推进，不新增固定的 540～560 ms 等待。目标准备应有上限，超时退出自绘动画准备并交回正常页面恢复，不能把超时当作“布局已完成”的证据；实际预算在实施时分别测量和确定。

### 4. 动画期间保持这版列表呈现稳定

从选择列表展示版本到最后一帧交接，列表位置和目标卡片外观必须对应同一版本：

- 后来的业务结果照常处理，待呈现状态按最新版本合并；不重放每一条过期的 `notifyItem…(旧位置)`。
- 维持 adapter 的展示条目与已经发布的数量、顺序一致；不能数据源已变、只是不发通知。复用现有展示快照能力时，补齐涉及的可变字段及外观依赖。
- 会改变布局的媒体回调、重绑和页面外观刷新也经过同一呈现控制；目标动态封面保持本次捕获的显示状态，到交接后恢复播放。无需暂停后台解码或传输。
- 按目标展示身份暂时隐藏真实目标的绘制，保留布局占位，避免与运动中的卡片重复出现。结束时校验绑定身份再恢复，不能恢复一个已经被回收给其他记事的 View。
- 期间限制列表点击、长按和滚动，避免用户操作与暂缓呈现的数据版本错位。

窗口尺寸变化、页面销毁、进入后台等统一终止这次动画，恢复正常页面状态。认证失效必须立即丢弃受保护的画面并执行原有遮蔽，不能作为普通刷新延后。

这不是给每一种更新加条件，而是规定所有列表呈现共享一个时间边界。`suppressLayout()` 可辅助控制布局，但不能代替展示数据管理或停止已有动画。

### 5. 同一帧交接，再发布后续更新

动画末帧精确等于所选卡片的可见外观，在同一次绘制交接中恢复真实目标、撤下覆盖层。随后解除呈现控制，如果期间有新变化，以当前展示版本和最新数据计算一批差异，恢复正常列表更新。

先交接到动画承诺的那一版列表，再显示后来发生的更新，避免末帧直接换成另一位置的目标。新的更新可以表现为正常的单卡变化或移动；这是发生在返回过程中的新变化，不是重复播放返回前已完成的那一批变化。

正常结束、超时、取消和异常共用幂等清理：释放图片、恢复目标可见性及项目动画策略、解除输入保护、撤销旧回调。返回会话只消费一次，过期回调不能再次刷新旧位置。

## 两种视觉结果

### 有可用卡片：当前详情 → 当前卡片

建议先以约 300 ms 调试返回，比现有 360 ms 展开稍快，保留相同的容器和元素语言；具体时长是设计建议，不是已经验证的指标。

- 容器从当前全屏内容收至真实卡片，圆角、背景和可见裁剪连续变化。
- 两端都实际可见的标题、正文及同源封面沿用现有匹配能力。换行、省略号、清单结构和封面裁剪差异采用局部渐变。
- 内容或封面被替换时，从当前详情外观过渡到最新卡片外观，不需要单独的“内容是否改变”业务分支，也不把不同附件强行当作共享元素。
- 详情工具栏、底栏和卡片没有的内容在前段淡出。详情已经滚到下方时，以当前视口开始，不能先滚回顶部；未共同可见的元素自然淡化，容器仍可收回。
- 系统栏图标由系统绘制，随覆盖范围切换样式；键盘与应用内容分开处理，不能把输入法截图一起压进卡片。窗口几何未稳定时降低到正常返回。

### 没有可用卡片：短淡出 → 当前列表

建议约 140～180 ms，不朝旧坐标、屏幕中心或其他记事缩小，不自动寻找离屏卡片。删除和移出筛选等情况因此不需要专用飞行方向。

来源丢失、抓图失败或系统关闭动画时，直接正常返回；这属于动画能力不可用，不是第三套业务动画。私密授权失效时直接遵从遮蔽规则，不能为完成淡出继续展示已失效的私密快照。

## 各类变化如何归入同一规则

| 情况 | 呈现结果 |
| --- | --- |
| 没有修改 | 提交当前列表状态，收回到当前卡片；不依赖结果 Intent。 |
| 标题、清单、背景、附件或卡片大小变化 | 收回到重新绑定后的实际卡片，元素差异局部渐变。 |
| 其他记事更新，挤动本记事的位置 | 在新布局中找目标，收回到新位置。 |
| 置顶、取消置顶、排序变化 | 新位置仍可见则收回；不在当前视口则淡出。 |
| 变更类型、搜索匹配或所属文件夹 | 当前页面仍有合法可见目标则收回，否则淡出。 |
| 从文件夹缩略记事打开 | 使用同一目标接口定位当前缩略卡；预览名额或模式变化使它消失则淡出。 |
| 完成、删除或清空导致删除 | 仍在当前列表中可见则收回，否则淡出；原有撤销语义保留。 |
| 多条后台更新、列表重载、接收更新及撤销重做 | 提交截止点的最终本地展示状态，不逐事件设计动画。 |
| 动画中继续更新同一或其他记事 | 完成本次固定版本的交接，再合并发布新变化。 |
| 旋转、窗口尺寸变化、宿主重建 | 旧几何失效，结束会话，交还正常页面恢复。 |
| 来源 Activity 已消失、通知／组件直接打开详情 | 无来源会话，使用原有正常返回路径。 |

## 代码改动的合理范围

建议划分三个小职责，名称在实施时确定：

1. **返回会话**：在原有返回业务成功后创建，承接当前详情画面，管理一次性消费和退出清理。与正向转场共享捕获、元素和绘制基础，分别负责各自接收窗口。
2. **列表呈现提交**：集中处理“立即提交这版列表／动画期间合并待呈现更新／结束后发布”。复用当前列表加载、差异和展示快照能力，保留业务结果处理；收口此次涉及的延迟刷新及重绑入口。
3. **卡片目标接口**：普通卡片和嵌套预览提供统一身份、可见几何与临时隐藏恢复能力。动画不理解卡片在哪个 adapter position，也不理解更新来自哪个业务。

主要工作是第二项。只在现有返回路径上增加一个缩小动画会留下时序竞争；另建一套保存或全局数据状态系统又超出需要。应只整理返回接收方的呈现调度，并让普通路径继续使用相同的结果语义。

不把 `notifyDataSetChanged()` 作为所有返回的默认实现。可靠时继续精准 Diff；确有现有全量刷新原因时保留兜底。自绘返回期间抑制的是该批次额外的项目运动，不能全局关闭碰一碰等普通单卡更新动画。

新建记事没有本方案的原卡片返回来源，继续使用现有粒子、涟漪和边框光效。第一版先做“返回已提交后的动画”；可取消的跟手返回另行设计，不能在用户尚可取消手势时提前执行不可撤销的保存、删除等业务。

## 验证重点

后续实施继续使用三台已授权设备。原有记事只读打开和返回，所有编辑、排序、删除、接收及私密状态模拟只使用专用测试记事，前后审计原有数据。

除正常返回和表中各类变化，还应控制更新分别发生在列表提交前、布局后、收缩中途和末帧之前。验收不只看最终截图：

- 首帧不得闪出旧列表；动画终点与当时实际可见目标一致。
- 末帧不得再次换高度、换位置或闪回旧内容；后续新更新只发布一次。
- 无修改返回、缩略卡、部分可见卡、详情滚动后返回均有正确路径。
- 提示、撤销、计数和保存次数正确；输入保护、目标隐藏及会话资源均能恢复。
- 兼顾媒体晚到、目标回收、快速连续返回、旋转、后台及认证失效。
- 回归普通碰一碰更新动画和新建三档，不能以自绘返回通过替代这些已有行为。

分别测量“返回业务完成至第一次运动”和“动画持续时间”。不能把 540～560 ms 的固定等待藏在承接画面后，也不能只通过缩短返回动画宣称响应优化。

## 官方资料核对

- [`RecyclerView` API](https://developer.android.com/reference/androidx/recyclerview/widget/RecyclerView)：按稳定 ID 查找只覆盖已经布局的子项；更新未落实到布局时不能据旧几何选目标；`suppressLayout()` 不会自动停止已经运行的 ItemAnimator。这些 API 能辅助实现就绪判断，不能替代应用的提交顺序。
- [`ViewTreeObserver.registerFrameCommitCallback()`](https://developer.android.com/reference/android/view/ViewTreeObserver#registerFrameCommitCallback(java.lang.Runnable))：仅适用于硬件渲染且自 API 29 提供，提交帧不等于屏幕已经显示。首尾交接仍需真实绘制与设备回归，不能仅凭该回调宣称无缝。
