## 已核实

- 返回动画接在原有确认和保存出口之后，普通新建仍走原流程；已有记录测试继续只读退出，修改场景仅使用专用模拟记录。
- 打开捕获使用的底层硬件快照有超时清理；详情准备和返回捕获也分别有超时，不依赖无限等待。
- 返回快照仅固定展示数据，不把旧记事写回数据库；目标按记事身份和当前展示条目查找，不依赖打开时的位置。

## 已复现的问题

### 返回取消路径可能发布尚未保存的旧内容

`ThingsActivity.finishDetailReturnPresentation()` 只有正常结束会等待 `afterPendingWrites`；超时、切后台等取消路径立即执行待处理结果并重载数据库。若原保存尚未完成，就会用旧数据库行替换 Manager 中已经编辑过的记录，并清掉刷新结果。

三星隔离模拟确认：阻塞专用测试记录的保存队列，分别触发 1500 ms 准备超时和切后台取消；放开队列后数据库是新内容，Manager 仍是旧内容，输入已恢复，再次点击也读到旧正文。原有记录全行散列和累计数量不变。完整复现为 `tmp/thing-detail-review/R5CW20BLNKL/review-save-red3/result.json`，共四个失败断言对应两种取消原因下的列表值和再次打开值。初版探针未等待列表项目动画结束便点击，现已修正该测试时序。

### 完成通知与后来写入交错时，正常返回也可能读旧值

原 `afterPendingWrites` 只在串行队列排入一次标记，再向主线程发送通知。通知排队后、主线程执行前到来的更新也会被本次结果合并消费，但其数据库写入可能尚未执行；最终再次等待保存时，结果已消费，不再触发重载。

三星可控队列顺序复现：动画正常结束，数据库最终保存新正文，Manager 仍保留旧正文。证据为 `review-save-races-red/result.json` 的 `review-interleaved-current-content`，退出原因是 `finished`。

### 另一入口的新建结果可能重复通知插入

`RESULT_CREATE_THING_DONE` 原来仍使用独立的 300+300 ms 回调。若它在当前详情返回时一起处理，新记录先被最终列表差异插入，稍后旧回调又发出一次插入通知，导致通知数量与实际条目变化不一致。

三星 `review-create-red` 已复现这条延迟通知。探针在首次展示之后临时截留后续通知，既确认存在多余插入，又避免把已知错误交给 RecyclerView 造成测试进程崩溃；所有操作仍限定本次模拟记录。

## 修正

- 所有返回退出原因统一在保存完成后合并展示并释放输入。动画超时或取消仍立即撤去动画层，不跳过数据完成顺序。
- Manager 的十处异步写入统一经过 `SerialWriteQueue`。读取回调真正执行前检查写入版本，有后来写入就继续等待；不再用一次已排队通知推断当前写入全部完成。
- 认证失效仍立即重绑当前展示并遮蔽私密内容，不与保存等待绑定；目标捕获期间的认证失效也使用明确的失效退出原因。
- 新建结果的两段回调也纳入统一结果调度。若与返回合并，只完成原有创建及界面更新语义，由最终差异发布一次；普通新建仍保留原 300+300 ms 揭示路径。
- 新增 JVM 顺序测试和真机复现探针；三机原有返回场景及新竞态用例均已通过。
- 1719 项 JVM 检查中 3 项既有跳过，0 失败。三星、魅族的新竞态及私密等待用例已通过；私密断言遵循现有“标题可见，正文／附件遮蔽”的产品约定。
- OPPO 中途曾 ADB 离线，恢复连接后已补齐同样的回归。
