# 详情转场等待优化（2026-10-20）

## 边界和基线

- 用户要求优化魅族首次约 0.7 秒的准备等待，保留双 Activity 架构及现有效果。
- 基线为已发布 `202610200628`；已有三机性能记录在本地 `tmp/thing-detail-transition/`，上一轮结果保留不覆盖。
- 新一轮设备数据备份、测量和审计单独保存在 `tmp/thing-detail-transition-latency/`。现有记事只读，私密认证用模拟场景，测试记录按本轮身份清理。
- 当前指标中的系统触摸用时包含注入同步等待，不能全部归因于应用；运动帧间隔是 View 绘制回调指标，不等同于屏幕丢帧率。
- 原版准备策略以 250 ms 为上限，未超时则要求焦点、媒体、布局连续两帧就绪。本轮发现超时分支会绕过焦点和布局条件，已改为仅对媒体使用 250 ms 上限，详见下文。

## 诊断计划

- 先分析已有主线程采样及生命周期时间，提出有排序的假设。
- 对点击处理、快照、Activity 初始化和首帧等待加入低开销分段测量，通过同一探针进行前后对照。
- 根据实际主要开销修改，再合并完成三机性能、视觉、兼容性及数据完整性回归。

## 第一轮证据

- 三机已建立新的只读备份。带分段探针的基线未改变转场行为；魅族首次运动 705 ms，来源点击 24.7 ms、快照完成 63.4 ms、详情创建开始 122.7 ms、初始化完成 393.4 ms、匹配准备完成 676.1 ms。
- 主线程采样另起一轮，采样有明显额外开销，只用于调用栈归因，不把其时长当作性能基线。
- 采样发现 `include_bottom_bar_detail.xml` 的 CheckBox 在构造期间解析系统 AnimatedStateListDrawable 和 AnimatedVectorDrawable；随后 `findViews()` 的 `BackgroundUtil.applyCheckboxAccent()` 无条件替换成应用自绘复选框。先单独取消 XML 的初始系统 button/buttonCompat，保留原应用绘制与状态逻辑。
- 其余待验证开销包括详情内容布局、碰一碰硬件查询以及首帧之后才创建的菜单。尚未通过删除焦点等待或缩短动画改变体验。

## 当前修正和测量校正

- 单次 Instrumentation 首次测量出现 0.7～1.3 秒的较大波动；不能把不同轮次总耗时差异直接归因于某个修正。新增仅 debug、需 DUMP 权限显式启用的普通应用进程旁观计时器，使用真实卡片边界及系统触摸，并限制现有记录只读。
- 普通进程的一条现有清单首次为 531 ms；与短正文模拟不是同一内容，此数仅确认普通进程也存在等待，不作为修正前后的对照。
- 无媒体覆盖顶部按钮时，省去本来不参与底色选择的字形栅格化；媒体进入按钮区域时再取样，保持原采样顺序和参数，整数下标不再装箱。
- 详情普通提示条改为首次显示时创建，关闭时只处理已经存在的实例。
- 列表展开期间，碰一碰接收控制器和 NFC 能力查询延至交接结束。只补齐溢出菜单状态，不重建可见工具栏；无转场入口仍立即准备，异常退出沿用清理机制。
- 动画仍为 360 ms、原曲线、原元素与配色交接；未改快照、焦点等待及绘制轨迹。

## 第二阶段：空布局预创建

- 第一阶段三机短正文回归功能均通过，但魅族首次仍为 769 ms（点击受理计时），未达到稳定降低首次总等待的目标。继续保留这一不利结果。
- 普通进程冷启动对照也出现 1.4～1.8 秒等待；同轮原数据全表一致。它与已有进程中的首次详情打开不同，不能和最初 705 ms 直接相减。
- 针对首次原生控件／资源创建，增加单份空布局异步准备。使用 [AndroidX 官方的 AppCompat 异步工厂](https://developer.android.com/jetpack/androidx/releases/asynclayoutinflater)，不自行在工作线程复刻布局解析。
- 真实 Activity 仍执行原业务绑定，空布局不包含任何记事文本、附件或认证状态；配置变化和内存回收可降级。接下来检查实际命中、后台创建是否回退主线程、三机输入／保存及视觉一致性。

- 魅族首轮预创建性能检查六次均命中，未发现 AsyncLayoutInflater 回退主线程的警告；首次初始化从旧版约 271 ms 降到 164 ms，但该次整体首次运动仍为 661 ms，不能宣称已经显著解决所有首次等待。
- 同一原有短正文、普通应用进程三次冷启动真实点击：旧版 1758／1640／1404 ms；预创建版 936／1061／1009 ms。三次中位数下降约 38.5%。这组结果包含进程首次打开详情，区别于已有进程里的六次模拟测量。
- 慢帧另暴露旧的准备判定问题：250 ms 到期即使没有焦点或仍请求布局也开始 ValueAnimator，首次可见运动可能已经接近动画末端。修正为媒体最多等待 250 ms，但焦点和连续两帧布局就绪仍是必要条件；整个准备保留 1500 ms 兜底，开始运动后移除准备超时，不消耗 360 ms 的运动时长。

## 最终实现与初步回归

- 预创建内容包括详情根布局、固定编辑区和快捷提醒选择器的空 View。只保留一份，首页恢复后异步创建；切入详情时把 MutableContextWrapper 指向真实 Activity。窗口尺寸、inset、焦点、输入法、状态恢复和业务绑定仍由真实 Activity 处理。
- 缓存尚未就绪或 Configuration 不同，立即执行原同步路径。首页停止、内存压力时清理缓存；已经提交的后台任务通过代次失效，等回调结束才允许新任务，避免连续进出时堆积。
- `preparation-verified` 三机各 14 项检查通过：实际缓存命中、编辑框 Context 指向当前 Activity、提醒选择器打开和关闭、真实输入、缓存缺失及配置失配降级、碰一碰菜单恢复、提示条懒创建，以及原记录和累计数量不变。
- 预创建与同步布局的整根软件像素对照在三机均为最大差值 0、不同像素 0。该对照用于布局／主题一致性，不等同于屏幕合成帧验证。
- 新增选择器检查最初因探针反射只查本类字段、漏查 PopupPicker 父类字段而失败；修正测试后补跑通过，不是生产代码崩溃。

## 普通进程复测与结论边界

- 最终版普通进程、同一原有短正文的两次有效冷启动点击到运动为 1165.6、1371.9 ms；旧版三次为 1757.8、1640.3、1404.4 ms。该场景仍可有超过一秒的等待，不能用中间版本 38.5% 的结果代表最终版本。
- 第三次原流程的点击未打开详情：封面加载使瀑布流重新排布，旁观计时器先前输出的坐标落入卡片间隙。应用仍停留首页，无本轮新增崩溃。用系统 UI 层级与目标内容核对最新卡片边界后补测成功，为 294.1 ms。
- 补测增加了 UI 层级确认和等待，启动条件与前两次不完全相同，故单独记录，不混入冷启动对照中位数。测试位置过期不作为应用转场失败或零耗时样本。
- 这次修正减少了初始化工作，并改善多次打开的响应；同方法首次总等待仅下降约 7%，窗口添加、初次绘制、焦点和布局就绪仍占较大部分。不同进程／系统负载下波动显著，未承诺每次都低于 632 ms。
- 当前缓存不包含真实记事或认证数据；真实指纹、卓易通本体和 API 26～28 仍未实机验证。保留双 Activity、360 ms 动画和既有元素／媒体／系统栏效果。
