# 必要的小组件刷新与快速返回

## 复现与验证边界

- 上轮 Find X9 Ultra 的主线程采样已证实 `BaseThingWidget.onUpdate` 同步调用视频取帧，阻塞转场截图回调；无修改返回已跳过多余刷新，本轮继续处理实际修改后的必要刷新。
- `finishCommittedReturn` 在入场动画仍运行时直接 `finish()`，因此快速返回退回系统动画。将增加早、中、晚三个进度的自动回归，确认从当前画面连续收回。
- 小组件测试使用独立测试记事与测试宿主分配的小组件 ID；不重新绑定或删除用户桌面上的小组件。不修改原记录，不备份整库。
- 用户随后改用一加 15T，并明确允许添加小组件。已确认 `3B1629006YC00000` 的制造商为 `OnePlus`、型号为 `PLZ110`；下文较早阶段记录中的“OPPO”指这台测试设备。Find X9 Ultra 与 OPPO 平板本轮不再操作。

## 待验证的原因（按优先级）

1. 小组件静态视频封面取帧占用主线程：后台渲染应消除返回截图等待期间的这类堆栈。
2. 小组件读取与异步保存竞争：延迟保存及连续编辑后，最终小组件必须显示最新提交。
3. 入场状态被直接丢弃：保留当前画面和几何后，应持续走自定义返回，并保持第一帧位置不变。

## 已取得的证据

- OPPO 测试手机在展开进度 0、0.3、0.8 附近，通过工具栏回调和系统返回各测一次；六次均没有自定义返回帧，落入系统退出。专用记事已清理，114 条原有记录的摘要及统计缓存一致。
- 小组件测试宿主可以独立分配并绑定真实小组件；首轮未收到预期显示内容，正在补充宿主侧诊断，不能把“没有崩溃”当作更新正确。

## 实现约束

- 小组件使用现有 WorkManager 依赖持久化刷新工作，按小组件 ID 替换旧请求；后台等待保存完成后从数据库读取独立对象，后台渲染与串行提交。广播只等待入队完成，避免批量视频取帧超过广播时限。依据：[Android 小组件更新指南](https://developer.android.com/develop/ui/views/appwidgets/advanced)。
- 返回转场冻结正在展开的当前画面，使用当前容器位置、裁剪及圆角作为关闭起点；首页仍按稳定 ID 寻找当前目标，不使用旧位置直接结束。

## 阶段验证

- 同一份“新的测试君”视频与外观引用只复制到测试 NOTE。OPPO 的旧同步小组件版本六次实际修改返回中位数 501.8 ms；后台刷新版本六次中位数 181.1 ms，所有新标题均由独立 `AppWidgetHost` 收到。原记录摘要未变。
- 三机的连续修改、故意延迟保存、已保存清单读取、私密清单隐藏、尺寸调整验证已覆盖。测试清单最初误用了转纯文本方法 `toContentStr`，已改为真实持久化格式 `toCheckListStr` 后复测通过。
- OPPO Android 17 拒绝对尚未完成配置确认的测试小组件转换集合，平台日志为 `Skipping legacy list conversion, pending config activity`。主线程直接更新同样被跳过，不能归因于后台渲染。宿主测试必须调用 `startAppWidgetConfigureActivityForResult`，让配置 Activity 真实返回 `RESULT_OK`；不修改生产行为绕过平台配置规则。
- 宿主使用应用 Context 创建 `AppWidgetHostView`，避免 AppCompat Activity 的 inflater 把远程控件替换成不支持 RemoteViews 方法的 AppCompat 控件。

## 最终核对进展

- 完整小组件回归：一加 15T 31 项、三星 22 项、魅族 22 项全部通过；分别包含 6／3／3 次真实编辑与返回，随后确认宿主显示新标题。起播中位数分别为 165.3／166.9／188.0 ms。
- 以上回归还验证了延迟保存、连续更新覆盖、清单读取已保存数据、私密清单隐藏、尺寸变化、列表投影与标题更新、渲染期间删除。原有小组件配置及绑定均未改变。
- 三机原记录数分别为 114／374／181；前后摘要一致，专用记事与小组件已由各次测试清理，统计缓存恢复原值。没有导出整库备份。
- 自查补充：快速返回的当前帧须保留到详情窗口真正分离，不能在 `onPause` 时移除覆盖层；窗口分离后释放位图和来源引用。新增真实生命周期断言，检查暂停后保留、窗口移除后清理。
- 小组件提供者使用系统实际绑定的组件，校验单记事／列表家族；不依赖旧尺寸字段反推提供者。
- 补测发现魅族每次进程首次横屏、在展开准备阶段立刻返回时，虽然自定义交接正确，首个样本仍等待约 0.61～0.76 秒。主要空档在来源画面已承接、首页请求目标布局之前；后续五次约 0.17～0.25 秒。已单独采样定位，不能将其记为小组件后台刷新完全消除了所有等待。

## 回归结论与剩余边界

- 一加竖屏、三机横屏的最终快速返回检查均通过，每组六次：展开准备期、展开中期、展开后期分别使用系统返回与真实工具栏触摸。自定义返回、当前几何承接、暂停后保留当前帧、分离后释放画面与输入均正确。一加最终六组末帧逐像素一致，中间帧已人工核对。
- 三星旋转与窗口尺寸回归 26 项、魅族通知／突出通知／正在做／嵌套详情／其他页面回归 22 项通过；小组件提供者校验调整后三机各追加 16 项回归通过。
- JVM 共 1719 项，0 失败、0 错误、3 项既有跳过。生产修改构建通过，测试探针只在 debug 源集中。
- 魅族额外采样确认首次横屏返回的主要应用内开销是 `publishDetailReturnList → justNotifyAll → ThingManager.loadThings → Thing(Cursor)` 重复解析列表外观 JSON；100 个区间样本中 43 个位于卡片、详情附件或背景外观解析，没有小组件视频解码堆栈。该项属于完整列表读取的首次成本，后续应单独评估不可变外观缓存或后台准备，不能通过跳过当前列表刷新破坏返回正确性。它仍是性能边界，本次两项功能修复不承诺所有设备所有场景零等待。
- 本地证据位于 `tmp/thing-detail-widget-quick-return/validation-summary.json`、各 `wqr-*/result.json`、`visual-check.json`；历史 `wqr-oppo-*` 名称保留以对应原始日志，设备实际是一加 15T。
