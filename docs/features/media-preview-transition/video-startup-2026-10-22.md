# 大视频起播黑屏诊断

## 反馈与复现

- 用户反馈卓易通打开较大视频时，先出现预览图，中间全黑一次，然后才显示视频画面。
- 继续使用本会话授权的三星、一加、魅族，只读真实记事与原视频；卓易通宿主无法直接通过当前 ADB 连接，慢画面测试用于复现相同交接条件，不代表已在宿主完成实测。
- 在真实查看器新增 debug 首帧探针：记录预览图、等待期间、播放后的系统合成画面，以及播放器准备、首帧通知、目标纹理更新、视频层揭示时刻。仅在测试时将真实播放器暂时输出到隔离 Surface，900 毫秒后接回目标 Surface，并可丢弃首帧通知；不修改原视频或生产计时。
- 三星真实视频首次回归失败：准备 138 ms，视频层 344 ms 已揭示，目标纹理 1296 ms 才更新。等待截图的媒体区非黑像素比例为 0，前后分别约 82.3%／82.0%，确认是交接空白。
- 一加真实记事“新的测试君”的 168,695,573 字节、3840×2160 视频在不加延迟时也失败：准备 68 ms，揭示 256 ms，首帧通知 364 ms，目标纹理更新 372 ms，提前约 116 ms 揭示。加 900 ms 输出延迟时同样复现，等待期间画面接近全黑。

## 排序后的候选原因

1. 旧 180 ms 兜底无条件揭示：如果成立，延迟画面到达时会先露出空视频层，改成等待实际纹理更新后应保持预览图。
2. 播放器首帧通知早于目标纹理更新：如果成立，即使去掉定时兜底，提前投递通知仍会造成空白；只以实际纹理更新交接才能通过。
3. 源视频首帧本身黑色：如果成立，黑色会存在于实际更新后的纹理，而不是仅发生于纹理更新前；不能按像素明暗作为播放就绪条件。

## 修复及阶段验证

- 原生真实大视频已证实第一项：180 ms 兜底无条件切走预览图。删除固定时间揭示，播放器首帧通知只请求刷新，最终交接由目标 TextureView 的实际纹理更新时间戳变化触发，排除空纹理和沿用旧帧。
- 每页监听目标 Surface 的更新与销毁；停止时撤销等待，销毁当前输出时停止播放器。保留黑底与视频同步显示、停止同步恢复的细边修复，保留视频变换与原解码路径。
- 一加同一真实大视频、900 ms 输出延迟、缺失首帧通知：修复后等待期间仍为封面，994 ms 纹理更新、1010 ms 揭示，22 项通过。实际纹理在 alpha 为 0 时仍正常更新，不需要把空层提前显示，也不按像素亮度筛选合法黑帧。

## 平台约束

- [MediaPlayer 首帧通知](https://developer.android.com/reference/android/media/MediaPlayer#MEDIA_INFO_VIDEO_RENDERING_START) 表示播放器已推送第一帧用于渲染。
- [TextureView 更新通知](https://developer.android.com/reference/android/view/TextureView.SurfaceTextureListener#onSurfaceTextureUpdated(android.graphics.SurfaceTexture)) 对应纹理经过 `updateTexImage()` 更新；可直接验证目标输出，不依赖固定等待时间或画面亮度。
