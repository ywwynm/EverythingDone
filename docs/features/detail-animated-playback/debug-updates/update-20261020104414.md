## GIF 独立播放的三机性能复核与首页大 GIF 内存修复

用户担心首帧重播崩溃修复采用独立解码后，会增加内存并影响大 GIF 和首页滚动，授权三台
设备测试且不得影响现有记事。本轮使用独立包运行真实首页和详情，完成共享／独立 A/B，
覆盖 25 张混合卡片、12 个详情 GIF、反复返回首页，以及首页四个约 35 MB GIF。

确认独立解码有真实代价：同源六消费者从一个 decoder 变为六个，缓冲及首帧多占约
17～23 MiB。继续只在详情需要从头播放的模式隔离，首页和默认循环仍共享。三机普通手指
滑动对照接近，但多个高复杂度 GIF 并发仍有既有吞吐瓶颈，魅族惯性呈现异常另保留边界。

大文件首页测试另复现整文件输入流解码的 OOM：约 35 MB GIF 导致 64 MiB 临时数组分配
失败，关闭隔离也会出现。新增 LocalAnimatedImageModel，BaseThingsAdapter 的缩略图和
媒体背景在播放／静态首帧入口均将存在的本地 GIF／WebP 转为 File，使用文件映射；原
裁切、尺寸、播放与缓存预算保持。视频、普通照片、URI 和缺失文件仍使用原加载模型。

修复后六轮三机 A/B 的首页 GIF 输入全部为 direct，无崩溃、OOM 或回收异常，全部页面
关闭后所追踪的播放 loader 为 0。同一压力场景首页 Java 堆峰值由约 215～238 MiB 降至
对应修复轮的约 52～58 MiB；总 PSS 没有同步下降，不能将这一改善写成总内存减少。
新增实际 Glide 模型、帧像素及资源共享回归；全量 253 个 suite、1711 项测试无失败或错误，
3 项既有跳过。三机隔离包已卸载，正式应用数据库和设置从本轮开始到卸载后的哈希一致。

本轮没有修改现有记事、覆盖安装正式应用或创建 Git 提交。保留首帧重播隔离修复；测试
探针和媒体夹具仅用于隔离包。详细证据见 owner-performance-2026-10-20.md。

发布结果：debug `202610200245` 已发布；远端元数据及回下载 SHA-256 一致，正常 APK 已确认不含本轮探针、测试依赖或私有媒体。
