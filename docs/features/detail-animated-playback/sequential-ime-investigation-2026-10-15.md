# 逐一播放、键盘与滚动交错时的闪烁

## 新增反馈与语义核对

首轮发布后，用户补充：设置为「逐一播放」，打开键盘后滑动，更容易看到记事底色闪现；怀疑统一 RecyclerView 改造影响了播放语义。

已核对 `d60ef2730`：详情由全量布局改成有界 RecyclerView + ConcatAdapter，播放调度改用分区索引、延后可见性评估，新增实际 detach／recycle。原决策 D3–D7 约定的是「当前可见附件按索引各播一遍；已播完且仍可见则不再排队；离开后重新进入可重播」，无需依赖全量布局。旧 ADR 和领域文档仍描述全量布局前提，须随本次结论纠正。

首轮四档测试覆盖模式切换后播完，没有覆盖真实键盘显示与滑动同时发生。新增隔离包检查使用同一设置键、真实输入法、注入真实触摸滚动，比较键盘关闭与打开两种场景；逐次记录画面、请求、播放决策及透明度，并保留屏幕录像。沿用三台设备授权和原数据校验，不改变正式应用设置。

用户观察第一次操作后指出滑动太慢。375ms 拖动及 180ms 间隔的轮次仅保留作慢速对照，不作为所述快速滑动的验收。改为约 48ms 内跨越 72% 视口高度的甩动，动作间隔 40ms，每种键盘状态执行 56 次连续甩动，包含惯性未停止时反向操作。

用户追加复杂页面、大 GIF 要求。小夹具用于最小化原因；还需用实际编码的大文件、多份动态媒体、通栏与长正文做原始范围回归。快速触摸坐标依据 RecyclerView 与工具栏实际边界，避免键盘缩小视口后触摸起点落在覆盖的工具栏上；只有 IME 可见期间确实采到媒体的轮次才可作验收。

## 已复现与待区分假设

三星慢速键盘对照出现 1 条透明记录；魅族第一轮快速对照出现 5 条透明记录，均是已经显示过的动态附件在等待／停止态重载 `static` 资源，`shouldPlay=false` 且 Drawable 为 null。对应真实窗口无透明度动画。

1. 待播／播完静态代表帧没有独立占位缓存。预测：只补足静态资源缓存即可消除对应空白，且不必改队列语义。
2. 可见项批量变化时，逐项移除／加入之间提前推进队列。预测：记录调度顺序时会短暂选到本批已离屏的项，或未按索引升序选择新项。
3. 键盘或旧异步回调使播放判断过期。预测：出现不可见项仍在播，或实际运行与 shouldPlay 不一致；需区别真实回收与初次加载。

有效快速基线 `sequential-fast3-red-*`：三星 4915 条记录中 2 次空白，魅族 5286 条中 3 次，OPPO 4707 条中 2 次（这 2 次发生在 IME 打开期间）。三机均确认 IME 阶段真实滚动到媒体、键盘持续显示，原应用数据校验未变化；未见 Drawable 在 shouldPlay=false 时仍运行。空白均为 static 请求，不能用首轮只覆盖 GIF 占位的修复宣称已覆盖逐一模式。

复杂基线 `sequential-complex-red-*` 使用 12 个动态附件（视频、动态照片、直接 GIF）、17 张静态图、通栏和 80 段正文。高细节合成视频走真实编码流程：三星视频／动态照片各 35,240,637 字节，OPPO 各 34,143,205 字节，魅族分别 31,543,914／32,507,177 字节；其余为三个真实派生 GIF 的九个独立路径副本（每份约 10.4／15.9／12.9 MB）。它们不是九份不同内容，重复副本用于制造独立请求与回收压力。原应用数据三机均未变化。

对应空白记录：三星 308／15030、OPPO 449／13288、魅族 211／18132；其中键盘快速甩动分别 87、155、87 条。已先遍历附件等待显示，随后才开始采样，区别于首次加载。准备单变量对照：静态代表帧也保存独立占位，单张持久占位上限 65,536 像素，总预算保持不超过 8 MiB／堆的 1/32；原地静动切换快照仍保留原预算。

调度的独立真机基线 `sequential-queue-red-samsung` 已证实假设 2：在真实 RecyclerView 中从附件 0–3 一次滚到 4–7，记录到起播顺序 `[1,2,3,4]`；反向滚回则为 `[6,7,0]`。前三个／前两个都是本批已经离屏的项。该检查仅替换解码边界以记录每次起播，布局、回收和播放控制器均为真实执行，不会因同一帧内又停止而漏掉错误。当前可见项正常推进、播完后仍可见不再排队均通过。

修复调度时保留原「当前可见项按索引各播一轮」定义：先整体替换可见集合、移除全部离屏候选、停止离屏播放，再按索引加入新项，最后推进队列一次。静态占位对照仍使用旧队列 APK，避免两个变量一起改变。

静态占位单变量对照 `sequential-complex-poster-oppo`（12742 条）、`sequential-complex-poster-meizu`（17038 条）均无空白、无误运行，IME 覆盖通过。三星该对照在安装后授予权限时遇到 ADB daemon 连接超时，未进入测试，不计为通过。

视频核对发现复杂夹具曾把 fullSpanEnabled 设在第 4 个附件，但产品只支持第 1 个附件通栏，因此上述复杂基线／占位对照实际是定制网格。保留其有效的大文件、键盘和快速滚动证据，同时另增 `--fullspan`：给第 1 个附件设置通栏，并断言实际测量宽度超过列表的 90%，防止设置存在但布局未生效的假覆盖。

## 大文件同时播放暴露的内存失败

合并后的 `sequential-complex-fullspan-green-*` 共 39,472 条记录无空白，队列检查也修复为 `[4]`／`[0]`。但继续运行默认循环的 12 动态附件场景时，三机出现 OutOfMemoryError，三星／OPPO 首次等待起播超时，魅族重开超时。回看前述逐一日志，三星／OPPO 同样偶发大数组分配失败，故其「无空白」仅是画面连续性结论，不能作为完整播放验收。runner 已将 OOM、致命异常和回收资源异常纳入失败条件。

核对实际 Glide 4.16.0 AAR 字节码与上游代码：[StreamGifDecoder](https://github.com/bumptech/glide/blob/v4.16.0/library/src/main/java/com/bumptech/glide/load/resource/gif/StreamGifDecoder.java) 将完整 InputStream 读入可扩容 ByteArrayOutputStream 后再复制；35 MB 文件可申请 64 MiB 临时数组，吻合设备日志的 67,108,876 字节分配失败。[ByteBufferFileLoader](https://github.com/bumptech/glide/blob/v4.16.0/library/src/main/java/com/bumptech/glide/load/model/ByteBufferFileLoader.java) 则使用只读文件映射；本地注册顺序也确认 File 的 ByteBuffer loader 优先。拟只将本地动态请求模型从 String 改为 File，保留静态／非文件来源加载方式，并记录 GifDrawable buffer.isDirect 验证实际路径，再以相同复杂页面重测。此处没有扩大堆或减少同时播放数量。

File 模型的首轮 `complex-loop-mapped-*` 三机均完成四档、正式回收、Activity stop/start 和重排，buffer.isDirect 通过且日志无内存／生命周期异常。像素检查指出测试仍需修正：只等待前三项就开始采样，把其余项首次解码等待计作循环闪烁；固定 7.5 秒在较慢的大文件并发中仅观测到一次回绕。保留原结果，改为等待全部实际可见项完成首次加载，并实际观测前三项至少两次回绕后继续，不降低循环边界断言。

`sequential-complex-fullspan-mapped-*` 最终严格结果：三星 13750、魅族 14993、OPPO 11729 条记录，所有 12 个动态位置均被观测到；空白、透明动画、错误运行、非映射运行、OOM／致命异常／回收资源异常均为 0，同帧最多一个 GIF 运行。每机 130 个触摸动作，中位时长依次 84／85／75ms，IME 阶段 74 个，动作后仍惯性滚动 96／96／99 个。实际通栏尺寸分别为 1440×1080、1368×1026、1216×912，键盘打开后重新进入可正常排队播放，原应用数据校验均未变化。
