## 范围与授权

## 已核对的风险与历史

- 独立 `GifFrameLoader` 会各自拥有解码缓冲、帧位图及解码工作；同一文件多个显示位置同时
  首帧重播时，不能把内存选项本身很小等同于总开销很小。
- holder 身份虽不引用界面对象，但会减少不同 holder、不同详情实例之间的内存资源复用。
- 首页代码没有启用本次所有者选项；首页与详情仍共享进程内 Glide 池和资源缓存，必须检查
  详情工作集是否影响返回首页后的缓存命中、分配及滚动。
- 10 月 15 日的内存修复要求保留 File 映射、逐帧预裁切、位图池复用、正式回收清理及滚动中
  正常播放。不能通过降画质、缩小媒体、恢复滚动暂停或关闭动画来取得不等价的性能结果。
- 三星当前 `/data` 余量约 2.8 GiB，夹具应限制复制数量并清理隔离包，避免以存储不足改变负载。

## 测量设计

同一个隔离 APK 的调试源副本提供共享／独立开关；正常产品源码与 APK 不包含该开关。
三机采用相反 A/B 顺序，固定同一份媒体与相同遍历范围。先复用现有真实首页及帧／内存采集，
再追加大 GIF 详情、重复进入退出与同源多实例边界。计时期间不抓图、不密集遍历完整资源图；
阶段结束才读取 loader、decoder、缓存及位图持有情况。

记录 PSS、Java／native 分配、Glide 池与缓存上限、实际帧变化、窗口帧耗时、真实滚动位移及
退出后的运行 loader。窗口帧耗时不转换为屏幕 FPS；对比时区分默认循环与需要首帧重播的模式。
保留失败、异常或覆盖不足的轮次，不能只用成功样本下结论。

原应用数据库和设置只读校验，安装前核对 APK 中的隔离包名，测试后卸载本轮隔离包。

## 实施记录

- 使用 25 张首页卡片（清单、图片、视频封面、GIF、长正文、部分通栏和高背景卡片），
  详情使用 6 个 35,240,637 字节 GIF 与 6 个 10,410,687 字节 GIF，全部为隔离文件。
- 每次运行先冷 Glide 磁盘缓存，再遍历首页，依次检查逐一、同时一次、全部循环，随后
  三次打开／关闭逐一播放详情，返回同一个真实首页再次遍历。首页通过实际手指拖动及惯性
  下行／上行分别到边界；计时记录实际距离，检查覆盖等价。
- A/B 只切换 owner 隔离选项，其余尺寸、签名、裁切、循环计算和缓存预算完全一致。
  OPPO／魅族先共享，三星先隔离；三机均使用同一 APK。
- 构建检查发现 AGP 内置 Kotlin 不使用仅替换的 Java source set；第一份缺少开关的 APK
  在安装前被 DEX 检查排除。修正同时设置 Kotlin source set 后，验证适配器字节码确实读取
  `isolationEnabled`，再开始设备测试。此规则已补入 `.agents/rules/gradle.md`。
- `StandardGifDecoder.getByteSize()` 包含完整输入长度、`mainPixels` 和 `mainScratch`；
  File 输入使用直接映射，资源记账字节不能直接相加当作 Java 堆或实际物理占用。边界用例
  单独记录同文件六消费者的唯一 decoder、缓冲与首帧字节。

源码依据：[Glide 4.16.0 StandardGifDecoder](https://github.com/bumptech/glide/blob/v4.16.0/third_party/gif_decoder/src/main/java/com/bumptech/glide/gifdecoder/StandardGifDecoder.java)。

三机共享／隔离六轮全部完成；原应用数据库和设置 SHA-256 均不变，无崩溃、OOM 或已回收位图
异常。全部页面关闭后，已跟踪的运行中 GIF loader 均为 0。各机首页 A/B 遍历距离完全一致。

| 设备 | 返回首页手指拖动 P95，共享 → 隔离 | 同源六消费者的缓冲及首帧占用，共享 → 隔离 |
|---|---:|---:|
| OPPO PLZ110 | 7.079 → 7.148 ms | 6.35 → 29.27 MiB |
| 三星 SM-S9180 | 9.749 → 9.705 ms | 4.00 → 21.82 MiB |
| 魅族 20 INFINITY | 13.345 → 13.282 ms | 3.34 → 20.15 MiB |

缓冲数字为 `mainPixels + mainScratch + firstFrame.allocationByteCount` 的实际持有块总量，
包含位图池／数组池返回的较大块；不是进程 PSS 增量，也不包括播放期间的下一帧等所有开销。
同文件六请求确实从 1 个 decoder 变成 6 个。文件映射输入仍为 direct，不将六份映射长度
直接当作六倍 Java 堆。资源缓存和位图池均未超过各自原定上限。

素材为 720×540、75 帧、每帧 40ms。唯一文件大 GIF 的逐一播放帧推进约 24～25 帧/秒；
六个高复杂度 GIF 同时播放时，三星和魅族共享策略本身也低于素材 25 帧/秒，不能把这一既有
并发解码负载归因于修复。帧推进速度来自同一实例的连续索引采样，不是屏幕 FPS。

魅族首组冷首页惯性有 FrameMetrics 缺报（51 个回调与实际滚动覆盖不相符，dropped 字段
仍为 0）；该区间不能用于流畅度结论。追加第二组在首页直接放入四个 35 MB GIF，A/B 顺序
反转，并用 Perfetto FrameTimeline 交叉检查魅族真实呈现。两组分别使用同组相同 APK，
不能把不同组直接当作同一负载比较。

## 大 GIF 首页追加复现与修复

第二组真实首页包含四个 35 MB GIF，虽然页面遍历结束、应用未退出，运行时检查发现
64 MiB（67,108,876 字节）数组分配 OOM：三星共享组 6 条、OPPO 隔离组 3 条、魅族隔离组
2 条。三轮均判失败并保留原日志，没有继续跑第二个策略来增加相同失败负载；首页问题在
关闭 owner 隔离时也出现，不能归因于本次首帧重播隔离。

根因是 `BaseThingsAdapter` 的首页动态／静态封面入口仍使用 String 路径。Glide 的
`StreamGifDecoder` 先读完整输入、按倍数扩容，再复制最终数组，35 MB 输入会触发上述
64 MiB 临时分配；此前详情页的 File 修复没有覆盖首页。

新增 `localAnimatedImageModel`，仅把存在的本地 GIF／WebP 转为 File；首页缩略图和媒体
背景的动态／静态入口统一使用。视频、普通照片、URI 和缺失文件仍使用原模型。修复保留
帧尺寸、裁切、占位、循环和离屏清理，不扩大堆或 Glide 缓存。

新增真实 Glide 回归验证新路径为 direct buffer，且帧数、
首帧像素与首页同源资源共享保持正确。Windows 上 String 的磁盘盘符被 Android Uri 解析
为 scheme，不能用该路径在 JVM 伪造 Android 的旧入口；旧路径因果证据使用设备失败与
上游 StreamGifDecoder，JVM 使用固定首帧像素断言。首次测试因纯 Application 缺少既有
`AttachmentHelper.SIGNAL` 的 App 初始化失败，调整为省略应用启动副作用的测试 App；
这属于测试环境问题，单列保留。第三组冻结源码只更新首页模型转换及测量断言，三机重新
跑大 GIF 首页 A/B，并要求所有采样到的首页 GIF 输入均为 direct、日志无 OOM。

源码依据：[Glide 4.16.0 StreamGifDecoder](https://github.com/bumptech/glide/blob/v4.16.0/library/src/main/java/com/bumptech/glide/load/resource/gif/StreamGifDecoder.java)。

## 最终结果与限制

第三组六轮均通过，三机每轮实际手指、惯性上下行到达相同边界；播放、尺寸和裁切均使用
生产实现。累计 1583 条首页 GIF 采样全部为 direct，未出现崩溃、OOM 分配错误或回收异常。
全部页面关闭后已跟踪运行 loader 均为 0，资源缓存和位图池未超过各自原有预算。

| 设备 | 大 GIF 首页拖动 P95，共享 → 独立 | 首页 PSS 中位数，共享 → 独立 | PSS 峰值，共享 → 独立 |
|---|---:|---:|---:|
| OPPO PLZ110 | 7.187 → 7.299 ms | 551.2 → 475.2 MiB | 663.7 → 671.3 MiB |
| 三星 SM-S9180 | 10.099 → 10.328 ms | 860.4 → 826.0 MiB | 1024.9 → 1036.1 MiB |
| 魅族 20 INFINITY | 13.332 → 13.430 ms | 921.6 → 871.7 MiB | 1214.2 → 1316.6 MiB |

拖动 P95 相差 0.10～0.23ms；本轮没有发现稳定的大幅退化，但不能说零开销或把单轮 PSS
差异归因于某一个分配器。尤其魅族独立组 PSS 峰值高约 102 MiB，缓存与在运行 decoder
检查未显示对应泄漏；此结果保留，不用中位数降低掩盖峰值。

输入流修复前后按相同设备、相同 owner 策略比较，首页 Java 堆峰值分别为
OPPO 214.8→56.0、三星 237.6→52.2、魅族 237.8→58.2 MiB，64 MiB 临时数组 OOM 消失。
旧组已发生 OOM，不能视为与成功播放全部大 GIF 等价的吞吐基线；总 PSS 未同步下降，
映射驻留、native、图形缓冲和成功解码的工作量仍占内存。没有声称降低了总进程峰值。

魅族共享组惯性仅 73 个 FrameMetrics 回调，而 FrameTimeline 有 1626 个；独立组分别
1673／1674 个，确认窗口回调有缺报。系统呈现标记两组惯性 Late Present 均约 99.6～99.8%，
存在既有时序异常；不能据窗口 P95 或此单轮轨迹断言全部惯性场景流畅。保留系统数据，
不将其直接换算成屏幕 FPS。三机均为本次授权设备，未覆盖低内存机、任意更大分辨率、
用户原记事的完整操作时间线；高并发 GIF 帧推进瓶颈另列后续项。

完整本地回归 253 个 suite／1711 项，0 失败、0 错误、3 项既有跳过。初次测试另暴露了
既有 API 26–28 的 `Bitmap.setColorSpace` 版本判断问题，已记入动态封面 followups，
没有用本轮新版 Android 的结果替代旧系统兼容性验证。
