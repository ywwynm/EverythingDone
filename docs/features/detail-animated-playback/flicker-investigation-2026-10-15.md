# 详情 GIF 闪烁排查

## 范围与复现

用户反馈默认「同时循环播放」下，视频及动态照片派生 GIF 在循环边界、滑动返回或重新加载时可能闪烁，授权在 `3B1629006YC00000`、`R5CW20BLNKL`、`192.168.100.67:40807` 复现并修复。使用隔离测试包和可重复媒体夹具，保留原应用的数据与设置。

## 已核对的历史

- `45bc4cd5b` 修复首页滑动期间的请求暂停、离屏生命周期与 GIF 首帧回显；不是针对详情循环边界的修复。
- `10f009c3d` 在动态封面生成进度功能中修复首页静态封面与 GIF 交接、自动播放开关切换时的短暂空封面。
- 详情在 2026-07-31 已删除吞掉 `onLoadCleared` 的私有 target，改用独立位图快照；不能重新引入持有已释放 Glide Drawable 的方式。
- 旧 ADR 中详情一次性布局全部附件的实现前提现已改变：当前使用统一 RecyclerView，须同时检查视口阈值、临时离屏与正式回收。

## 验证方法

使用真实详情、真实派生编码器和 GIF 解码器，覆盖默认循环、部分离屏返回、正式回收后返回及 Activity 重新进入。记录实际 Drawable、播放帧索引、请求身份和每次预绘制时的 ImageView 媒体像素，区分资源清空、静动资源切换与 GIF 内容本身的首尾变化；阶段截图检查实际界面。程序滚动和播放状态断言用于稳定复现，不声称等同于全部自然触摸路径或录屏逐帧验收。

## 修复前证据

- 用户补充：闪烁看起来是「显示出记事底色」，后续以媒体透明／被清空作为判据，不把普通内容跳变当作已解释的原因。

- 三星 `red2-samsung`、魅族 `red2-meizu`、OPPO `red4-oppo` 原应用数据库与设置校验和一致。
- 部分离屏往返三次，视频与动态照片每次均从 `GifDrawable` 切换到 `BitmapDrawable`；动态照片返回时分别仍绘制 1／1／1 帧及 1／2／1 帧静态主图，随后切回 GIF。
- 正式回收并清空 Glide 内存缓存后返回，三星三个动态附件各出现 1 帧空白；魅族为 1／1／3 帧空白，OPPO 为 1／1／3 帧空白。
- 静止循环阶段每项记录到两个循环边界，未出现黑帧、透明帧或 Drawable 替换。实际生成的 GIF 分别为 75 帧和 69 帧，离线解码没有黑帧或透明帧；不能据此认定所有用户媒体的循环边界均无问题。
- OPPO 前几轮因权限窗口影响中断，保留原始数据但不将这些轮次列为完整通过；权限完成后以 `red4-oppo` 重测得到有效基线。

## 对照验证的假设（按优先级）

1. `shouldPlay` 同时决定资源身份及启停，导致循环模式离屏就切静态图。若仅暂停已经加载的 GIF，部分离屏往返应保持同一实例，且不闪出主图。
2. 正式回收正确清除了 Glide，但详情缺少有界静态占位。若复用独立首帧快照，缓存命中时回显应没有空白，并且继续释放 decoder。
3. 异步交付或 Activity 生命周期重启改变播放状态。需覆盖晚交付、stop/start、播放一次结束和正式回收，不能恢复曾导致崩溃的私有 target 清理方式。

## 单变量对照与缓存补查

- 三星 `policy-samsung` 仅改变循环档的资源选择，三次部分离屏往返均保持同一 GIF，静态主图闪回归零；正式回收后的三个附件仍有 1／1／2 帧空白，证实两类问题需要分别处理。
- 增加首帧独立副本后，三机 `green-*` 合计 12,315 条绘制记录中原场景通过，四档播放、Activity stop/start、重排和回收停止均通过。
- 随后追加“保留 Glide 缓存重新打开，再滚出回收并返回”的三星检查 `warm-samsung`。三个 GIF 的 `firstFrame` 均已为 null，证明已播过的内存资源不会再提供首帧；仅首帧缓存的实现再次出现每项 1 帧透明。该轮像素断言失败，未发布。
- 最终实现优先复制尚存的首帧；没有首帧时，在安装资源后复制 ImageView 当前实际显示结果。若预取时尚未测量，在同 key 附着刷新时补充。始终使用独立位图、相同 LRU 预算与像素上限，不持有旧 Glide 资源。
- 只读抽查三机各三份现有 v10 派生 GIF，没有黑、白或透明整帧，但这只是离线检查，不能证明运行时循环无闪烁。用户补充“露出底色”后继续追加真实媒体的设备播放采样。

## 高分辨率边界补查

三机最终网格采样通过后，复核实际截图及尺寸，发现三星 1440 像素宽、魅族 1368 像素宽，默认通栏比例可能超过原有 1,048,576 像素快照上限，需要增加通栏返回检查，不能用双列结果替代。魅族首次提示遮住了部分截图；隔离包后续先跳过该引导，已有媒体逐次绘制记录保留为底层绘制证据。

三星 `large-red-samsung` 的实际通栏尺寸为 1440×1080，回收返回出现 1 帧空白，像素断言失败。将大尺寸首帧及当前画面按比例缩入既有像素预算，而不是直接放弃快照；LRU 总内存预算不变。该改动同时覆盖高分辨率下默认单媒体与自定义通栏的占位尺寸问题。

三机 `bounded-large-*` 的通栏返回及已播过缓存返回空白均归零，尺寸分别为 1216×912、1440×1080、1368×1026。网格复验中，魅族 `bounded-meizu` 的第三项在第一次解码前被过早归入循环阶段，出现 3 条初始空白，后续循环无空白；保留该轮失败，修正探针为三项均开始播放后才采样循环阶段，再以 `bounded2-meizu` 重测。该修正只改变测试阶段划分，没有修改产品代码。

## 实现与边界

- `DetailAttachmentPlaybackController.usesAnimatedResource()` 将资源类型与当前是否播放分开。默认循环离屏时停止解码，保留同一 GIF；关闭或播放一次结束仍按既有规则显示静态代表帧。
- `ImageAttachmentAdapter` 在已解码资源交付时缓存独立位图；没有首帧则复制当前显示结果。占位键包括文件身份、尺寸、裁切、视频选帧及静动类型。高分辨率快照按比例缩小，单图最多 1,048,576 像素，总缓存最多 8 MiB 且不超过运行时最大堆的 1/32。
- holder 正式回收仍调用标准 Glide.clear；缓存不持有 GifDrawable 或 decoder，不恢复曾导致已回收 GIF 重启崩溃的私有 Target。
- 用户所述「循环结束露出底色」尚未作为独立问题复现。合成媒体和抽取的现有媒体连续循环均检查了多个边界；结论仅限本轮媒体、设备与观察时段。缓存淘汰、首次加载、全部裁切和所有自然交互组合不作无空白承诺。
- 首页 `45bc4cd5b`、`10f009c3d` 确实修过类似问题；它们处理首页卡片路径，不能覆盖本次详情路径的资源切换和占位缺失。
