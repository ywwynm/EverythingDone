# 清单共用范围与粒子预热时机讨论（2026-10-09）

状态：源码核对与方案建议，尚未修改应用代码，未新增设备操作。用户强调预热原本用于降低横滑粒子首帧延迟，不能只以竖滑不再产生准备工作为目标。

## 清单解析的影响范围

`CheckListHelper.toCheckListItems` 是共用入口，内部执行 `normalizeLevels`、`normalizeCompletion` 和完成组边界处理。不能只当作首页适配器的局部函数。

| 调用区域 | 入口与具体场景 |
| --- | --- |
| 首页与复用卡片的界面 | `BaseThingsAdapter.kt:868` 内容绑定、`:907` 颜色重绑；首页继承该适配器，DoingActivity 的适配器（`:454`）、文件夹缩略图等也复用它。 |
| 详情页打开 | `DetailActivity.kt:1073` 解析记事清单，后续根据是否可编辑调整控制标记。 |
| 详情格式转换、撤销／重做 | `DetailActivity.kt:1788` 将普通正文转清单；`:1918`、`:1922` 恢复清单状态。 |
| 清单编辑 | `CheckListAdapter.kt:768` 完成／取消后重新解析；`:705` 缩进／反缩进和 `:979` 删除项后直接归一化；详情拖动及组完成还直接依赖 owner 语义。 |
| 桌面组件等展示与操作 | `ChecklistWidgetService.kt:55`、`AppWidgetHelper.kt:1910/2187`；远程清单勾选通过 `RemoteActionHelper` 进入同一 helper。 |
| 间接解析 | `toContentStr` 内部也调用它，因此通知文本、搜索、分享／导出、统计等使用该转换入口的地方会受到共用算法变化的影响。 |

这是**调用与语义影响范围**，不表示已在每个界面测得同样的卡顿。本次设备证据只覆盖首页。

建议先独立做共用算法的等价优化，保持返回内容、控制标记、组边界、层级纠正与完成态规则不变，不需要改变存储格式。首页展示缓存另外评估：当前返回值是可变列表，详情页会编辑并增删控制标记，不能把缓存的同一份可变列表直接交给多个调用者，更不能用首页截断后的可见行结果替代完整清单。

## 为什么不能简单推迟完整预热

现状在 `ACTION_DOWN` 就执行截图；后续 `ItemTouchHelper` 才识别横滑。预热时间利用了识别之前的间隔，尤其是“按住一会儿再横滑”。如果直接把完整准备移到正式横滑识别后，确实可能把原来已经完成的准备变成可见等待。

当前还有两条约束：

- `ThingsActivity.kt:11697` 明确规定粒子原位消散，准备期间保留原卡片且不平移。上一轮报告中“准备期让原卡片跟手”的建议已修正；不能引入先平移再突然原位消散的过渡。
- 消散起点至少有一个来自最初的 DOWN 触点，见 `ParticleSwipeAnimator.kt:233`；延迟准备时仍应使用这个原始触点，不是准备开始那一刻的新坐标。

## 候选方案：按成本分层，预判与正式识别分开

| 阶段 | 候选行为 |
| --- | --- |
| 页面稳定空闲 | 保留现有共享资源／着色器复用，检查仍落在首次触摸路径的独立初始化；可提前准备的部分不依赖当前卡片像素或触点。限制后台突发负载，不能恢复空闲持续出帧或刷新率投票。 |
| DOWN | 记录卡片身份、触点、指针和内容版本等轻量状态，检查缓存是否有效；不直接启动昂贵的整卡读回／像素分析。 |
| 早期 MOVE 已有较强左向趋势 | 提前启动卡片截图和必要材料准备，仍不拦截手势、不隐藏原卡、不显示粒子。这个启动条件可低于正式识别所需位移。 |
| 原有系统逻辑正式识别横滑 | 按原行为接管；已经就绪的准备直接沿用，未就绪则继续等候真实首帧。若早期预判未命中，正式识别本身就是启动准备的兜底。 |
| RecyclerView 已接管竖滑、取消、多指或目标失效 | 取消尚未开始的工作；已经进入 GPU 的工作只能等待完成后丢弃，不能承诺无成本撤销。竖滑已接管后不再因为后续横向抖动重启。 |

预判只决定能否花成本准备，**不改变手势归属、横滑完成阈值、点击和长按行为**。首页仅左滑需要粒子；Doing 页面双向完成，需使用其允许方向。回拖、跨原点以及已经上屏后的方向处理继续服从现有正式手势逻辑。

### 一个可作为实验起点的条件

用当前窗口的 `ViewConfiguration.scaledTouchSlop` 作为尺度 S；位移相对原始 DOWN，在同一坐标系计算。首页可先比较以下候选：

- 向左位移达到约 `0.5 × S`；
- 同时向左位移至少为纵向位移绝对值的 `1.5` 倍；
- 卡片仍有滑动资格，竖向列表尚未接管。

满足后立即开始重准备；边缘斜向输入可以继续观察，到正式横滑识别时兜底启动，不因未达到较严格的 1.5 比例而拒绝已有横滑。速度与事件历史可以辅助，但不把单次初始速度当唯一依据，也不强制等待固定毫秒数或额外两个显示帧。

**0.5 与 1.5 均是待对比的参数，不是已验证的最佳值。** Touch slop 的平台含义见 [Android ViewConfiguration](https://developer.android.com/reference/android/view/ViewConfiguration#getScaledTouchSlop())；标准 ItemTouchHelper 会结合位移、主导方向和 RecyclerView 状态判断开始横滑，见 [AndroidX 源码](https://raw.githubusercontent.com/androidx/androidx/androidx-main/recyclerview/recyclerview/src/main/java/androidx/recyclerview/widget/ItemTouchHelper.java)。本项目依赖 RecyclerView 1.4.0，具体落地还需核对该版本及本应用的事件分发顺序。

当前 `ThingsActivity.dispatchTouchEvent:301` 在交给下层之前就记录 MOVE，因此可以在输入阶段启动准备，不必等 `onChildDraw` 下一次执行，也不需要另外创建一个抢占事件的手势识别器。

## 对延迟的实际边界

- 若系统阈值假设为 8 dp、手指以 400 dp/s 直接横移，半阈值约在开始移动 10 ms 后达到。这只是启动时刻的量级示例，实际帧延迟还取决于此前准备能否被原有识别等待覆盖、渲染阶段与帧节奏。
- 快速手势可能在第一个 MOVE 就同时越过预判和正式阈值，预判不一定能赢得额外一个输入周期。
- “按住后再横滑”会失去原来按住期间的卡片准备时间；这是实际代价，不能承诺靠更巧的方向阈值完全消除。按住不动本身不能可靠预测随后会向左还是向上。
- 先微横再转竖仍可能误启动一次。更低阈值与更严格方向比例是在误启动和延迟之间取舍，不是绝对正确的意图识别。

所以不建议只改一个 if 条件就结束。至少要同时核对重准备是否还能压缩：

1. 保留并利用已有共享资源缓存，只补确实仍在首次触摸发生的独立初始化。`ParticleMicroflakeRenderer.kt:428` 已明确管线准备不依赖当前触点／材料，且 Shared 已有程序缓存，不能把已有复用再次当成新收益。
2. 飘散优先评估完整卡片硬件快照，减少 GPU→CPU 读回；需要兼容阴影、裁切和透明度，不是直接换一个现有重载就完成。
3. 流体还有像素分析／建材依赖，需独立缩短这些准备。完整材料依赖像素、方向、随机种子和消散触点（`ParticleMicroflakeRenderer.kt:2129`），不能把整套轨迹假定为通用缓存。
4. 若引入卡片准备缓存，只考虑有容量上限、能可靠识别失效的内容；媒体帧变化、裁切、几何／阴影、主题与参数、触点依赖都必须处理。无条件预热所有可见卡片可能把负担搬到滚动停止时，本轮不推荐直接采用。

## 怎样决定是否采用

既有 90 次手势针对竖向滚动，不能证明新方案的横滑首帧延迟已达标。后续对照应至少包含：直接慢横滑、立即快横滑、按住再横滑、斜向开始、横转竖、竖向抖动、长按／取消、跨原点回拖；覆盖两种风格、大卡／小卡以及第一次和后续次数。

同时记录 DOWN、首次实际 MOVE、开始准备、正式识别、截图／材料就绪、首个非零粒子画面的呈现时刻。重点比较：

- 普通竖滑误触发重准备的比例及滚动超时；
- 首次横向移动到非零粒子呈现，以及正式识别到该时刻的中位数和较慢样本；不能用已提交零进度帧代替真正响应；
- 按住再横滑单独成组，避免它的退步被直接快滑平均值掩盖。

推荐先把“早期预判 + 分层准备”作为候选进行上述双向对照，不能以牺牲横滑响应来宣告滚动优化成功。当前没有选定最终阈值或缓存策略。
