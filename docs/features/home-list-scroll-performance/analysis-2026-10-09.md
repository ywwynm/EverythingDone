# 首页列表滚动性能复查（2026-10-09）

状态：三台真机的采集、对照和源码归因已完成。仅修改诊断工具和本文档目录，未修改应用代码，未构建、安装、提交或发布应用。

## 结论

1. **目前主要是局部顿挫，不能再用“首页一直被限制在 60 fps”解释。** 三台设备连续拖动正常片段的实际呈现间隔中位数均约 8.3 ms，两种粒子风格均可达到约 120 fps 的节奏。
2. **三星仍有轻微起手卡顿，原先的按下预热问题没有消失。** 流体、飘散都会为最终成为竖滑的触摸截图。三星大卡的截图读回每次占用 RenderThread 约 14–26 ms；普通滑动对照没有此调用。不过本轮拖动中的程度比旧报告轻，不能把按住时发生的 40–55 ms 准备帧直接说成滑动停顿。
3. **魅族最明显的问题是复杂卡片首次进入视口。** 两种粒子风格的干净样本分别出现约 192／198 ms 的长帧；关闭粒子滑动仍有约 162 ms。系统跟踪和方法采样指向主线程的卡片创建、长清单解析与绑定。后续重复拖动明显更顺，但仍有偶发短顿挫。
4. **OPPO 本轮较轻。** 拖动大部分时候接近高刷节奏，偶有起手超时；流体首轮有一次约 42 ms 的帧完成耗时。它的横屏四列小卡与手机大卡不同，不能据此单独判断芯片差距。
5. **没有足够证据认定流体或飘散稳定地更适合竖向滚动。** 两者共享截图路径，而竖滑通常在真正的粒子轨迹模拟开始前就取消。个别最大值的差异还混有首次绑定、代码热身和媒体负载。
6. **三星近期变顺有两项有依据的解释：高刷限制已解除；本次视频封面实际退回了静态图。** 自动播放偏好仍开着，但 GIF 缺失，生成任务又被系统低存储条件阻止。不能把这部分媒体负载减少当成粒子预热已经修复。

需要同时看下面几项证据：

- 三星流体／飘散按住期间分别出现约 40–52／41–55 ms 的准备帧，峰值起点位于按下后约 57–74 ms，早于 160 ms 的开始移动时刻。这说明无用准备仍重，但不等于移动后持续卡住 50 ms。
- 三星普通滑动对照首轮仍有 28 ms，表明不能把每一个超时帧都归给粒子；正常列表绘制、启动热身、媒体回调等仍可能贡献耗时。
- 通过 `display_frame_token` 关联 SurfaceFlinger 后，两种风格的连续拖动正常片段，上屏间隔中位数分别为：三星 8.334／8.335 ms，魅族 8.279／8.278 ms，OPPO 8.322／8.323 ms（飘散／流体）。这证实已恢复高刷节奏；中位数不代表没有局部停顿。
- 魅族飘散首轮跟踪中，实际呈现间隔出现约 165 ms 的间断；普通滑动对照也有约 149 ms。长绑定不是 `gfxinfo` 字段异常造成的假象。
- 三星与魅族存在较多 `Buffer Stuffing`。它意味着缓冲排队和额外输入延迟，可以与平稳帧率同时存在；不能把全部此类记录相加当成可见卡顿率。本轮将它与 `App Deadline Missed` 分开分析。

样本量、不同卡片面积及未随机化的测试顺序，不支持对两种风格做稳定的优劣排序，也不支持量化“相较 9 月 26 日改善了百分之多少”。

## 原因一：按下时仍对竖滑执行粒子截图

实测三台设备的两种风格共 24 次跟踪手势，**每次卡片起手都有 `copyImageInto`**；普通滑动的 12 次跟踪手势中为 0 次。

| 设备 | 飘散：RenderThread 读回耗时 | 流体：RenderThread 读回耗时 |
| --- | ---: | ---: |
| 三星大卡 | 14.5–24.3 ms | 19.4–25.8 ms |
| 魅族卡片 | 5.1–8.5 ms | 5.9–8.5 ms |
| OPPO 小卡 | 1.7–3.5 ms | 1.5–3.6 ms |

代码链条与设备行为一致：

1. `ThingsActivity.kt:6961` 收到卡片 `ACTION_DOWN` 后，在尚未确认横滑时调用 `warm`。
2. `ParticleSwipeAnimator.kt:45` 当场创建 Session 并执行 `prepare`。`:195` 调用的是需要软件位图的 `ParticleHardwareSnapshot.capture`，两种风格都经过此处。
3. `ParticleHardwareSnapshot.kt:105` 把硬件位图复制为可变 ARGB_8888 位图。虽然调用来自后台线程，GPU 读回仍占用应用共享的 RenderThread；“已经放到后台”并不代表滚动渲染不受影响。`:183` 的离屏渲染还涉及同步提交。
4. 后续 `MOVE` 超出竖向阈值时才取消（`ParticleSwipeAnimator.kt:65`）。取消可以丢弃结果，却不能撤回已提交的截图读回；若截图在方向判定前返回，还会继续创建动画层。
5. `ParticleDismissOverlay.kt:111` 的飘散虽然推迟流体模型构建，普通软件快照仍触发像素复制／解包（`ParticleMicroflakePreparation.kt:69`）。已有“保留硬件位图”的入口不支持此处的完整卡片裁剪与阴影参数，首页滑动未走该入口。

因此更准确的说法是**“不区分竖滑意图的截图和材料准备”**。不能把它等同于“流体已在普通竖滑时计算完整后续轨迹”，也不能认为飘散不做流体轨迹就没有负担。

附加代价包括全图临时内存、像素扫描、GL 资源准备和回收。以约 300 万像素为例，单份 ARGB 数据约 12 MB，软件快照、上传字节、整型颜色数组可同时形成多份副本；这是量级估算，并非本次测得的峰值内存。后台材料线程默认还使用 DISPLAY 优先级，会与当前绘制竞争资源。

`ParticlePerfTuning.swipeMaterialsOnDown` 目前只有声明和配置读取，全源码没有消费该开关的调用；单改这个配置不能关闭现有路径。

## 原因二：长清单的首次解析和绑定阻塞主线程

魅族飘散首轮系统跟踪显示：

- `RV Prefetch` 约 130 ms；内部 ViewHolder 创建约 24 ms，绑定约 105 ms。
- `Prefetch` 在这里仍是 RecyclerView 的主线程工作，并不因为名称含预取就不会挡住下一帧。
- 另一次流体跟踪出现约 398 ms 的 `RV Scroll`、291 ms 的绑定。这是带跟踪、重启后首轮的异常重样本，不把它作为日常典型程度；干净组约 192 ms 更适合说明本轮实际量级。
- 关闭粒子滑动后仍复现约 162 ms 的干净长帧，排除“长停顿全部由粒子导致”。

额外 ART 1 ms 方法采样中，`toCheckListItems` 累计约 130 ms、`normalizeLevels` 约 120 ms、`ownerIndexOf` 约 118 ms；清单视图绑定约 75 ms，另有媒体绑定开销。**这些数字包含采样扰动，仅用于找调用热点，不与上面的无采样耗时相加。**

源码问题明确：

- `BaseThingsAdapter.kt:868` 先解析整份清单，随后才按卡片可见行数截取。`:907` 的颜色重绑又会重新解析。
- `CheckListHelper.kt:342` 对每项调用 `ownerIndexOf`；后者（`:253`）从当前位置向前扫描找更浅层级。一级项根本不可能有更浅父项，却仍会扫到开头。一级项较多时，工作量趋向平方级。
- 对魅族数据库做本地只读数量核验：跟踪中出现的目标清单共有 **148 项，其中一级项 97 项**；按现有层级归一化规则执行，需要约 **9,111 次前项检查**。报告不记录清单正文。
- `ThingCardChecklistView.kt:81` 会为尚未复用的可见行逐个 inflate。这是附加成本，不能只优化 inflate 而遗漏完整内容的解析。

9 月 26 日三星跟踪没有发生卡片重绑，本轮魅族则把此前不在视口中的复杂卡片滑入，因此两次诊断并不矛盾。不能将本轮新暴露的绑定问题反推成当时三星起手问题的唯一原因。

## 近期为何感觉更顺

### 高刷限制发生了真实变化

9 月 26 日曾证实，空闲粒子 Surface 的 60 Hz 投票限制了整个应用的刷新。10 月 6 日记录了空闲撤票等修改；10 月 8 日又进一步开启流体高刷与连续历史插值。当前实际呈现已经约 120 fps，不能继续沿用“流体固定 60 Hz”的旧前提。相关历史见 [粒子移植记录](../harmony-particle-android-port/README.md) 和 [10 月 8 日高刷实现](../particle-animation-performance/implementation-2026-10-08-120hz.md)。

### 三星本次没有同样的动态封面负载

证据链如下：

1. 自动播放偏好为开启，但视频封面日志记录 `ready=false`、`previewExists=false` 和 `fallback-static / gif-not-ready`，最终使用静态 BitmapDrawable。
2. 三星 `/data` 可用空间约 0.6 GB，系统存储状态为 LOW。
3. JobScheduler 的应用任务 320 因 `STORAGE_NOT_LOW` 不满足而无法运行。
4. 本地只读检查 WorkManager 数据库，确认任务 320 的 worker 正是 `VideoCoverPreviewWorker`，其工作名与缺失的封面 GIF 完全一致。源码 `VideoCoverPreviewManager.kt:184` 设置了这个存储约束。
5. 两种风格跟踪的首次起手前 1.5 秒，三星 Glide 动画线程 CPU 时间为 0；魅族约 1.41–1.49 CPU 秒，OPPO 约 1.20–1.22 CPU 秒（各动画线程相加，不是主线程阻塞时长）。魅族普通滑动组这个量有所下降，进一步说明媒体负载并非完全恒定。

因此，本次三星静止时的动态解码与纹理上传压力确实比旧报告小。尚未确定 GIF 最初为什么缺失，不能直接断言是某次代码更新或系统清理导致；能确认的是当前存储条件阻止了重新生成。以后空间恢复、预览就绪时，这部分负载可能回来。

本轮没有清理用户存储、删应用缓存、修改生成约束或关闭自动播放。

## 建议的解决顺序

| 优先级 | 方案 | 收益与边界 |
| --- | --- | --- |
| 第一优先 | **用早期方向预判控制昂贵截图与材料准备**，与正式横滑接管分开 | 同时帮助流体、飘散；不能只把完整准备后移而忽略粒子首帧延迟。当前粒子档是卡片原位消散，准备期也不平移；保留该视觉行为，不以临时平移掩盖准备等待。具体阈值和预热分层仍待验证。 |
| 第一优先 | **优化长清单解析并避免重复解析** | 最小候选是一级项的 owner 直接返回无父项；完整方案是单次遍历维护最多三级的父项信息，按内容版本缓存只读解析结果。保留控制标记分区、层级纠正、完成态与组边界语义，不通过删归一化换性能。 |
| 同步设计 | **让取消传播到后台准备的各个阶段** | 在截图提交前、像素复制前、模型构建前、GL 上传前检查会话状态；取消已排队且未开始的工作。已经进入 GPU 的操作不能假装可以无成本撤回，所以方向判定仍是首要措施。 |
| 后续 | 减少复杂卡片首次绑定中的行创建和重复布局 | 复用清单行、限制预取中不可分割的主线程工作，必要时提前生成不可变展示数据并校验内容版本。单纯扩大 RecyclerView 缓存或关闭全部预取不能替代解析优化。 |
| 后续 | 继续核对动态封面的触摸暂停、可见性和解码尺寸 | 当前暂停发生在滚动状态变化后（`BaseThingsAdapter.kt:400`），起手前仍存在解码负载；应检验更早暂停、离屏／重新附着、文件夹嵌套缩略图等生命周期。9 月 26 日证实过离屏负载，本轮未独立重测所有离屏路径，不将它们全部列为已确认的新根因。 |
| 后续 | 将飘散的硬件快照路径扩展到完整卡片 | 可进一步减少真实横滑需要的 GPU→CPU 读回，但必须支持裁剪、阴影、透明度与方向变换；仍需离屏绘制，也只直接帮助飘散，不能替代前两项。 |

不建议把“减少粒子数、改流体着色器、固定降低刷新率、只延迟固定毫秒数启动预热”作为本问题的首要修复。它们不能消除两种风格共用的整卡截图，也不能解决长清单主线程解析。更不应依赖动态封面偶然不可用来换取流畅。

## 后续实施应怎样验证

- 对普通竖滑、点击、按住再竖滑、多指／取消，确认不会因为这个手势产生粒子截图、材料模型或额外动画层；真实横滑、回拖取消和完成交接保持原有视觉行为。
- 对长清单分别覆盖初次进入与重复进入、不同层级分布、已完成组、控制标记边界，以及内容更新／颜色更新。检验解析工作量随项数近似线性，缓存不会返回旧数据。
- 三台分别做多轮交错顺序测试，保留首次绑定组，不仅看已热身的连续滑动；以 120 Hz 约 8.3 ms 的帧预算安排主线程工作，并使用真实截止时间与呈现间隔判断。
- 动态封面预览必须记录是否实际就绪。三星预览恢复后需要再测，避免静态回退掩盖解码和纹理上传竞争。
- 本轮仅分析，以上方案尚未实施，也未验证优化后的收益。

## 测量口径与可复核资料

- 设备端注入器输出 `System.nanoTime` 与 `elapsedRealtimeNanos` 双时钟标记，用于对齐 `gfxinfo` 与系统跟踪；不混用 `/proc/uptime` 和帧时钟。
- `gfxinfo` 环形数据只保留近期 120 帧，因此手势末尾和尾段各转储一次，再按帧时间去重；真正拖动窗口单独汇总。首帧晚于 DOWN 也可能只是 reset 后尚无帧，不能据此断定缓冲丢失。
- 魅族 Android 15 的 `FrameInterval`／`FrameStartTime` 表头顺序与实际量纲相反，解析器已修正；部分完成时刻早于当前帧，作为无效数据剔除。魅族呈现字段部分缺失、OPPO 为 0，不能直接据此计算掉帧率。
- FrameTimeline 的应用 Actual 切片结束是 GPU／提交完成，**不是屏幕呈现时刻**；呈现间隔通过 display token 关联 SurfaceFlinger。`Buffer Stuffing` 与 `App Deadline Missed` 分开解释。定义依据：[Perfetto FrameTimeline 官方文档](https://perfetto.dev/docs/data-sources/frametimeline)。
