## 2026-09-26 - 三星 SM-S9180 真机采集 run1（子代理，只采数据、不下结论）

- 对象：设备上现装的调试包（16:11 安装，pid 6064），未安装、未编译，未改任何设备或应用设置；旋转设置前后一致
  （`accelerometer_rotation=1`、`user_rotation=0`）。只发竖向手势，列表数据未改动（结束截图为普通状态）。
- 采集：干净 framestats 三组（起手落在视频封面卡 / 7 图卡 / 小标题卡，各 4 次 640 px、280 ms 的竖滑）+ 两次静止
  对照；带 atrace 的两组（小卡、视频卡）；视频卡「按住约 270 ms 再滑」一组 3 次（带 atrace）；SurfaceFlinger、
  设备端落盘的 logcat、`video-cover-preview.log`。原始数据在会话 scratchpad 的 `samsung/run1/`，报告为同目录
  `collection-report.md`。
- 工具：`device/hls_device.py`（驱动，全部手势 x 起止相同）、`device/analyze_framestats.py`、`device/analyze_trace.py`、
  `device/extra_metrics.py`。
- 采集方法上的三条事实：`dumpsys gfxinfo framestats` 只保留最近 120 帧（静止 5 s 渲染 136 帧、只给出 120 行），
  所以每个手势停稳后各转储一次再按 vsync 合并；framestats 是 CLOCK_MONOTONIC、atrace 与 `/proc/uptime` 是
  CLOCK_BOOTTIME，这台设备两者相差 185628.126454 s（用 `Choreographer#doFrame <vsyncId>` 与 FrameStartTime
  对齐求得，三份 trace 一致）；atrace 的 `parent_ts` 是 float，精度约 60 ms，不能用来对齐。
- 22:01–22:03 追加两组对照（报告 3.5 节）：set7_gap 起手在两列空隙（无抓图行、无 CFMS 行），set8_small_again 重复 P_small。
  不开 atrace 时用 `dumpsys power` 的 `mLastWakeTime=<uptimeMillis> (<N> ms ago)` 加前后 `/proc/uptime` 核对 BOOTTIME −
  MONOTONIC 与是否休眠过。同期发现：设备上另有进程在每次手势开始后 3.04–3.11 s 执行一次 `dumpsys gfxinfo`（47/47 次），
  本应用主线程随之处理 `handleDumpGfxInfo`，发起者未查明。

## 2026-09-26 - 实测结论（主代理复核后定稿）

- 空隙起手对照组（set7_gap，4 次）与同时段小卡起手（set8，4 次）补齐后定案：起手那一帧的掉帧来自滑动完成动画（粒子）
  的按下预热——落在卡片上的 27 次手势每次都有整卡离屏渲染 + RenderThread 读回（通栏视频卡 17–23 ms、一次 189 ms；
  小卡 3–5 ms），16 次在越过阈值前建了动画层，主线程晚开帧 12–32 ms；空隙起手 4 次没有一帧超过 16.7 ms。
- 导入的两张动图封面让应用静止时持续约 24.5 fps 出帧、两条 glide-animation 线程每秒 370–693 ms CPU、封面滚出屏幕也照常
  上传 1320×742 纹理；粒子 SurfaceView 的 60 Hz 投票把整个应用压在 60 fps。滚动期间没有任何重绑或布局（RV OnBindView /
  OnLayout / inflate 均为 0）。
- 结论文档：`findings-2026-09-26-device.md`；原始数据在会话 scratchpad `samsung/run1/`。改动方向未裁定。
