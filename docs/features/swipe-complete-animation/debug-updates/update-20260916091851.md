# 滑动完成记事动画调试更新

## 滑走之后仍留在列表里的卡片，回位按档位播动画（第三次，这一版是真机量出来的）

习惯左滑「完成」只是记一次打卡，目标等记事也可能留在原位，私密记事还要先认证——这些卡片回到原位置的过程需要按「滑动完成记事动画风格」播动画。此前两版都不成立：第一版卡片藏两秒多才出现，第二版卡片直接不见了，已整体撤回。两版的共同错误是按推断改时序，从没在设备上看过实际发生了什么。这一轮先在 OPPO 平板上加临时探针，把每一步的到达时刻与卡片每一刻的位移、透明度、视图身份都记下来，再决定怎么改。

探针推翻了此前的四条假设。其一，滑走之后卡片停在负的列表宽度处，而不是卡片自己的宽度，这台设备上是负两千五百二十像素。其二，变更通知会在约二十五毫秒换上另一张视图。其三，默认的换位动画其实一直存在，只是卡片要走完约百分之七十五才进入屏幕，只剩最后几十毫秒可见——这才是「啪地弹回来」的真身。其四，被滑走的那张视图仍归列表的触摸助手管，归还要等到约二百九十毫秒。

第二轮实验直接验出了上一版为什么坏：给这几处的变更通知加上附加标记、让视图持有者原地复用之后，归还整整两秒六都没有到来。原因是归还由「这张视图从窗口上摘下来」触发，而摘下来又要靠换位动画换掉它；持有者一复用这条链就断了，没有任何人把卡片放回来，卡片就一直停在屏外——正是用户看到的「卡片直接不见了」。更糟的是在此期间触摸助手每一帧都把位移按回去，在旧视图上摆好的起点十三毫秒后就被抹掉。

本版的做法是接管换位动画换上来的那张新视图：旧视图归触摸助手管，新视图是自由的。业务判定说「留下」之后的下一帧按位置把新视图找出来，结束掉默认的换位动画，按档位重新播一遍。滑动档从卡片自己左边一个身位滑回来并淡入，二百五十六毫秒，全程可见；粒子档倒放消散，虚拟触点落在卡片正左方，正好是左滑消散的镜像，粒子从同一侧重新聚成卡片，起不来就退回滑动回位。这一版不给变更通知加附加标记：默认的换位动画既是归还能够到来的前提，也是接管失败时的兜底，最坏只是没有改善，不会把卡片弄丢。另外只在卡片真的离开过时才回位——右滑开始做事实测走到业务判定时位移已经归零，再播一段滑入是凭空多出来的动画。

实测对比：同一张卡片同一条手势，一百二十毫秒时刻，修改前位移负一千七百六十七、屏幕上可见零像素，修改后位移负二百一十四、可见四百零五像素（卡片宽五百七十七）。粒子档截图确认粒子确实从左侧聚向卡片区域。其余路径：普通记事左滑仍正常移除，列表由十七条变十六条；右滑不播多余动画，开始做事界面正常打开、返回后卡片完好；滑到一半松手根本不触发，不接管。两档各连续三轮，每轮结束卡片都回到完全相同的位置、区域填充率百分之百，没有残留、没有半透明、没有丢失。

临时探针已全部删除，改动只有首页列表四十八行新增、十二行删除，外加一个新文件。构建通过，本地检查 1036 项，唯一失败是既有的 FableSol 曲线那一项，与撤回后的基线同一项、同一数量。

需要说明验证边界：共有十个接管点，其中七条是真正会发生的业务分支——非记事条目、大于通知目标的类型、需要认证的私密记事、右滑遇到暂停的习惯、右滑的普通情形、习惯左滑打卡、以及完成后记事仍留在当前列表；另有三条是取不到记事的退化守卫。本轮在设备上直接验到的是习惯左滑打卡与右滑这两条，其余五条走的是同一段代码但没有逐条复现。私密记事那条还有一个未验证的细节：认证界面若导致页面暂停，回位会被收尾成直接就位，卡片正常显示，只是没有动画。

测试用的记事已移入可恢复的回收站，平板首页恢复为原有的两个文件夹十五条记事，动画档位改回原来的滑动，设备上的临时文件已清理，用户现有记事一条没动。本轮未提交 Git。
