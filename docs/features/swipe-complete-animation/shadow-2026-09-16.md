# 粒子接管时 elevation 阴影消失（2026-09-16 评估）

## 现象

首页左滑完成记事、粒子档。粒子接管的那一瞬间卡片的 elevation 阴影整块消失；回拖取消时
阴影又一次性满强度出现。卡片本体在两处交接都是连续的，只有阴影是跳变的。

## 根因

卡片是 `InterceptTouchCardView`（CardView），`app:cardElevation` 取
`thing_card_normal_elevation` = **8dp**；滑动期间 `keepActiveTouchItemAboveSiblings` 还按
`ACTIVE_TOUCH_ITEM_Z_OFFSET_DP = 4dp` 抬 `translationZ`，实际 z 约 12dp。这个高度的系统阴影
在浅色列表背景上是明确可见的一层。

**elevation 阴影不由卡片自己画，而是父容器按卡片 RenderNode 的 z + outline 画的，因此它落在
卡片矩形之外，任何以卡片自身 `width × height` 为取景框的机制都拿不到它。** 三处一凑就是现在
的观感：

1. `ParticleSwipeAnimator.Session.prepare` / `activate` 把 `view.alpha` 置 0。alpha 是
   RenderNode 属性，阴影跟着一起归零——这是「一瞬间消失」的直接原因。
2. `ParticleHardwareSnapshot.capture` 按 `view.width × view.height`（或可见区）离屏渲染，
   `node.setPosition(0, 0, w, h)`。里面那两行 `setLightSourceGeometry` / `setLightSourceAlpha`
   只服务卡片**内部**有 elevation 的子 View；根节点自身 z 为 0，也没有容纳阴影的余量。
   所以快照里没有卡片本体的阴影，粒子材料里自然也没有。
3. `dispose()` 里 `view.alpha = originalAlpha` 是一次性恢复。卡片本体此时已由粒子聚合到接近
   完整，看不出跳变；阴影则从 0 直接回到满强度——这是「取消左滑后瞬间出现」。

同一根因还影响另外两条路径：`ThingSwipeReturn.condense` 的倒放回位（`appearContent` 期间卡片
alpha 为 0，约 1.2 秒后恢复，阴影同样是末尾一次性出现），以及正在做事界面的左右滑完成。

## 三条路线的代价

### A. 把阴影烤进快照，让它跟着粒子一起消散

做法是外扩取景框（8dp elevation 的 spot shadow 外扩约 `800dp × 8dp / (600dp − 8dp) ≈ 11dp`，
连 ambient 与向下偏移保守取 20–24dp），离屏节点改成两层：外层容纳阴影，内层设 z + outline +
`clipToOutline`，由 `RecordingCanvas.drawRenderNode` 带出阴影。

两条实质代价：

- **粒子会变粗。** `ParticleMicroflakeModel.build` 的格子数受 `max_cells` 封顶，
  `cell = sqrt(width × height × budget / (max_cells − 1000))`。取景面积增加约 50–65%
  （577×400 的卡片四周各加 24dp@3x），格子边长随之涨约 25%，而多出来的格子全部落在阴影上。
- **阴影像素会飞成一圈淡黑粒子。** `ParticleMicroflakeContent.weight` 末项乘 `alpha/255`，
  阴影像素权重极低，但仍然是有颜色的粒子。低对比度的成片粒子在纯色背景上容易被读成脏
  （见 memory `smooth-fields-read-as-dirt-on-flat-surfaces`）。

另外 API 26–28 走 `captureViaSoftwareDraw`，软件 Canvas 画不出 outline 阴影，那两档拿不到阴影。

### B. 阴影单独成层，不进粒子（推荐）

在卡片原位放一个只画阴影的替身 View：尺寸取 `ParticleCardClip.visibleRect` 的可见区，
`outlineProvider` 给同半径圆角，z 取 `view.z`（含 translationZ），无内容。挂到 **RecyclerView
自己的 `ViewGroupOverlay`**，可以顺带白拿三件事：

- 容器的 `clipChildren` / `clipToPadding` 自动裁掉多出的阴影，与被截断的卡片天然一致；
- 叠放顺序正确——在列表全部子 View 之上、在 `setZOrderOnTop` 的粒子 Surface 之下；
- `ParticleOverlayHost` 已经有「挂 overlay + 自己 measure/layout + 跟随尺寸变化」的成套做法
  可以照搬。

项目里已有同一手法的先例：拖拽浮起的 `DragOverlayImageView` 就是在 overlay 层用 elevation +
自定义 outlineProvider 复现卡片阴影的。

消散规律当时列了两种（整体淡出 / outline 随前沿收窄），倾向后者。**实测把这一条推翻了，
见下面「前沿收窄不成立」。**

交接不需要跨窗口：替身与真实卡片在同一个窗口，「替身浓度置 0」与「真实卡片 alpha 复位」
落在同一帧提交里，既不会空一帧也不会叠两层。

### C. 保留真实卡片的阴影，只让它画不出内容

重写 `InterceptTouchCardView.draw(Canvas)` 在标记位打开时直接返回：display list 为空，但
RenderNode 的 z / outline / alpha 不变，父容器照画阴影。代价是阴影会跟着 ItemTouchHelper 的
`translationX` 一起往左飞，要钉住就得改回弹与 `parkTranslationX` 那一套（`ThingSwipeReturn`
的三次返工都在这条链上）。风险明显高于 B，不建议。

### B 的替身生命周期（不常驻）

替身只在一次滑动手势期间存在，**不是一直挂着**：静止时阴影仍由真实卡片画，两层同时可见会
叠加变深。也不采用「把卡片 `cardElevation` 设 0、阴影永久交给替身」的做法——那会牵动拖拽浮起、
选中态与 `keepActiveTouchItemAboveSiblings` 的 Z 抬升，收益不抵风险。

时间线与 `view.alpha` 的四个写入点严格配对：

| 时刻 | 真实卡片 | 替身 |
|---|---|---|
| 按下（`prepare`） | alpha 1，阴影照画 | 挂进 overlay，alpha 0 |
| 识别为滑动（`activate`／`prepare` 末尾） | alpha → 0 | alpha → 目标值 |
| 消散推进（`draw`） | 保持 0 | 按进度更新 outline／alpha |
| 结束（`dispose`） | alpha 复位（取消回原位／完成被 park 到屏外） | alpha → 0，随后在已有的 `main.post` 里移出 overlay |

三条纪律：

1. **挂载放在 `prepare()`。** 它的两条入口都不在绘制过程中——`warm()` 来自 `ACTION_DOWN` 的
   触摸分发，`draw()` 里就地构造 Session 那条路已经把 `prepare()` post 到下一个消息。
   绘制过程中增删 overlay 子 View 是这套代码反复绕开的坑（见 `aimAt` 与 `dispose` 的注释）。
2. **撤除分两步。** `dispose()` 可能由 `reset()` 在 RecyclerView 绘制过程中调用，所以那一刻
   只改替身自己的 alpha（属性写入是安全的、视觉上即时），移除 View 跟着已有的 `main.post`。
3. **替身钉在布局原位，不跟 `translationX` 平移。** 粒子在原位消散，与 `ParticleCardClip`
   只读 `left/top`、不看 translation 与 scale 的口径一致。

## B 的工作量与待处理清单

- 新增 `ParticleCardShadow`：替身 View + 挂载 + 按进度更新 outline/alpha，约 100–150 行；
  outline 随进度的几何可以做成纯函数加单测，与 `ParticleVisibleBounds` 同一形状。
- `ParticleSwipeAnimator.Session`：在置 `view.alpha = 0` 的同一处建立替身，`draw` 推进时更新，
  `dispose` 时同帧交接。
- `ThingSwipeReturn.condense`：倒放时反向渐入，可挂 `appearContent` 已有的 `onAppearanceProgress`。
- 正在做事界面：`DoingActivity.onChildDraw` 在粒子接管时把列表 alpha 还原成 1，而容器的常驻
  0.84 是烤进快照的；替身要自己乘上 `bakeAncestorAlpha` 的同一个乘积。
- 真机验证：左滑完成、停住、回拖取消、快速甩动、被截断的卡片、倒放回位，两台设备。

尚未决定：消散规律取「整体淡出」还是「前沿收窄」；是否连正在做事界面一起改。

## 前沿收窄不成立（实测）

动手之前先用 `releaseField` 在 JVM 上量了一遍释放场（180° 与 0°、三种长宽比），两个结论都与
动手前的推断相反：

**一、方向反了。** 左滑（粒子朝左飞）时**右侧先释放**：180° 下各列平均释放时刻为
左 0.33 / 中 0.47 / 右 0.13。粒子朝左飞出，卡片的后缘先脱落，与帘子被从一侧拉走同理。
如果按「触点侧先空」去收缩阴影，方向会整条写反。

**二、剩余区不是一个能跟的矩形。** 未释放格子的包围盒是**从两侧向中部收缩**的（180°、
308×214 下 p=0.50 时为 left=0.27 right=0.53），因为中部最后释放。用一个矩形去跟它，观感是
阴影退到中间又要回来。而且释放在 p≈0.62 就全部完成，后半段根本不存在「完整的一块」。

所以最终只做浓度，不动形状：**浓度是唯一既物理正确、又不需要方向假设的量**，左滑与右滑的
曲线也几乎重合（差异集中在浓度已经很低的尾段）。

未释放比例随进度的实测值：

| 进度 | 仍未释放 |
|---:|---:|
| 0.00 | 1.00 |
| 0.08 | 0.97–1.00 |
| 0.17 | 0.78–0.95 |
| 0.25 | 0.57–0.81 |
| 0.33 | 0.42–0.55 |
| 0.42 | 0.19–0.34 |
| 0.50 | 0.02–0.19 |
| 0.58 | 0.02–0.03 |
| 0.65 | 0 |

`ParticleCardShadowFade` 用 `1 − smoothstep((p − 0.05) / 0.60)` 拟合这条曲线，最大偏差 0.17
（在 p=0.25 处，三种尺寸之间本身就差 0.24）。`ParticleCardShadowFadeTest` 拿同一份释放场做
逐点对照，模型改了释放节奏就会报出来。

## 实现（2026-09-16）

- **`ParticleCardShadowFade`**：浓度曲线，纯函数。
- **`ParticleCardShadow`**：替身层。`卡片父容器.overlay → host(FrameLayout) → stand(View)`。
  三处设计各有理由：挂父容器的 overlay 让列表的裁剪与叠放顺序自动正确；阴影由 host 这个普通
  FrameLayout 画（标准 ViewGroup 子 View 绘制，overlay 只负责画 host 的内容）；**浓度放在
  host 上、stand 自己恒为不透明**——Skia 只在 caster 半透明时才把阴影铺满 outline 内部
  （`RenderNodeDrawable` 按 `casterAlpha < 1` 传 `kTransparentOccluder`），而这一层正摆在卡片
  位置上，内圈阴影会叠到粒子画面上去。host 重写 `hasOverlappingRendering` 返回 false，alpha
  直接落到 RenderNode 上，不为此建离屏层。host 的裁剪规则照抄父容器一份（`clipChildren` /
  `clipToPadding` / padding），因为 overlay 的内容不受父容器自己的 `clipChildren` 约束，而真实
  卡片的阴影是被它裁的。
- **`ParticleSwipeAnimator`**：替身在 `recordTouch` 越过 slop 时挂好（输入分发阶段），因为真正
  需要它的 `activate()` 就在 RecyclerView 的绘制过程里；`view.alpha = 0` 的三处统一走
  `hideCard()`；进度由 `onPresentedProgress` 驱动（跟的是已上屏的进度，回拖时自动回来）；
  `dispose()` 里先 `hide()`（同帧交接）、层级等 `main.post` 再撤。
- **`ThingSwipeReturn.condense`**：倒放回位同样受影响（`appearContent` 期间卡片 alpha 为 0，
  末尾一次性恢复）。替身从「完全散开」起步，按 `onAppearanceProgress` 反向渐入。
- **顺带修掉一处**：`bakeAncestorAlpha` 原先在捕获回调里读容器透明度，而宿主在粒子接管的那一帧
  就把正在做事界面的列表还原成 1 了——「绘制过程中就地构造会话」那条路因此没把 0.84 乘进快照，
  接管时会整体提亮。现在改在会话构造时读，替身的浓度用同一个值。

验证状态：`:app:assembleDebug` 通过；单测 1048 项全过（新增 `ParticleCardShadowFadeTest` 5 项）。
**真机画面未验证**，已发布 debug 更新 `202609160946` 交由用户实测。

## 真机实测：卡片矩形内部会露出东西（2026-09-16 第二轮）

用户在 `202609160946` 上截到：粒子把卡片内容带走之后，卡片矩形**内部**露出一块比卡片小一圈、
四边硬边的浅色区域。这一层在 Z 轴上位于卡片之下，静止时被不透明的卡片挡着，所以平时看不见。

几何上它与系统阴影的**本影区**吻合：以卡片 840×490 px、z≈12dp@3x=36px 估算，本影相对 caster
向内收缩约 `lightRadius × z / lightZ = 2400 × 36 / 1800 = 48 px`，并因光源在屏幕上方中央而
向下偏移——实测那一块的边距正是「上 145 / 下 70」这种不对称。也就是说，**它就是系统画
elevation 的内部产物**，用户当时的猜测是对的。

我在上一轮里假设「不透明 caster 时 Skia 会剔除被遮住的那部分阴影几何」（`RenderNodeDrawable`
按 `casterAlpha < 1` 传 `kTransparentOccluder`），于是让替身恒为不透明、把浓度放到外层。实测
说明这条假设至少在这台设备上不成立。**这类平台内部行为不该靠推断**，尤其是在我无法上真机的
情况下。

修法因此改成「把结论定死」而不是「继续推断」：`ShadowHost.dispatchDraw` 先 `saveLayer` 把子
View 连阴影一起画进离屏层，再按卡片的圆角矩形擦一遍。**卡片矩形内部一定是透明的，不管系统
往那里画了什么**；那一块的画面本来就该由粒子和快照负责，而剩下的外圈渐变正是静止时能看到的
那一圈。

离屏层也顺带堵住另一种可能：`hasOverlappingRendering()` 返回 false 时容器没有自己的离屏层，
阴影绘制内部若有任何擦除动作就会直接落在列表的共享画布上，把已经画好的内容一起擦掉——那同样
会表现为「露出一块浅色」。现在两种可能都被同一层挡住。

代价是每帧一次离屏层。为此把 host 的尺寸从「列表全域」收紧到「卡片可见区外扩 3 倍 z」
（约 1056×726 而不是 924×1600），父容器自己的裁剪改由 `dispatchDraw` 里的 `clipRect` 补上
（overlay 的内容不受父容器 `clipChildren` 约束，而真实卡片的阴影是被它裁的）。
