# 按住卡片转列表滚动后的空白卡片与异常阴影

## 用户证据与边界

用户在 debug `202610130134` 后提供截图：右上角短卡片主体和文字缺失，原处留下矩形空白与异常浓重阴影。用户观察到粒子档可偶发，渐隐档没有发现；可能由稍作长按后不抬手向上滚动触发，也可能涉及短卡片重新绑定。这些手势、方向、卡片高度及复用描述都是待验证线索，不能直接认定为原因。

继续保留 SurfaceView、原有粒子表现、动态背景及卡片阴影；修复须覆盖准备后取消、按住转纵向滚动、离屏／复用、左右方向和不同卡片尺寸。沿用三台已授权 Android 设备，仅使用独立测试包和虚构数据，原应用与既有记事不变。

## 本轮验证入口

先复用真实 ThingsActivity 的隔离数据与 UiAutomation 输入，构造按下停留后纵向滚动的重复序列，同时记录卡片 ID、holder 身份、可见性、透明度、几何、阴影属性和屏幕像素。对照相同输入下的粒子与渐隐，不以属性正常替代截图正确。

## 复现与待验证原因

三星 `scroll-baseline-samsung` 第 7 次滚动复现同样的空白矩形与浓重阴影。卡片 `8000012` 的 alpha、transitionAlpha、scale 均为 1，visibility=VISIBLE、elevation=30px、translationZ=0、无临时状态，背景像素匹配率为 0。截图与用户症状一致。随后 24 次重复未再触发；魅族首轮 30 次也未触发，属于时序问题，不能将单轮通过当作排除。

按以下顺序验证：

1. 离屏渲染树引用了仍被原窗口使用的 RenderNode，释放／销毁影响其显示缓存。预测：属性仍正常，空白可发生在未按中的卡片；让销毁前的树不再引用原窗口节点可消除错误。
2. 迟到恢复回调遇到 holder 换绑。预测：问题卡片身份改变，回调执行后才出现异常；持有绑定代次并阻止旧回调可消除。
3. 临时隐藏子控件并直接 draw 改变原树的有效绘制记录。预测：异常在捕获阶段已出现，尚未释放时即可见；同层拆分的原生失效标记与正常情况不同。

Pixel 审计只覆盖已知纯色虚构卡片，先证明同类失败；媒体、复杂卡片和已有手势须在原因收敛后扩大回归。

## 归因对照（进行中）

- OPPO 横屏四列 `scroll-natural-oppo-90` 第 13 次也复现同样矩形空白。除根属性外，完整子树可见性、alpha、背景 Drawable 的 alpha=255、边界和圆角均正常；所有粒子 Overlay 为 0。不是前次批量恢复的选择白罩残留。
- 三星渐隐 30 次未见异常。普通卡片／列表 HardwareSnapshot、截取 RecyclerView 的捕获树、滚动后立即捕获，以及延后 90ms 在后台销毁的简化探针均未复现，说明还不能把“所有硬件捕获都会出错”作为结论。
- 保留完整 `ParticleLiveBackdrop` 的绘制树，但停止 renderer 并断开 Surface 的诊断对照：三星／OPPO 各 60 次均未再出现。此开关仅用于区分正常捕获和清理，不能作为修复发布；它保留绘制树资源，完成归因后须删除。
- Android 16 的 [CanvasContext](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/libs/hwui/renderthread/CanvasContext.cpp) 与 [RenderNode](https://github.com/aosp-mirror/platform_frameworks_base/blob/android16-release/libs/hwui/RenderNode.cpp) 源码显示：destroy 会删除树；失去最后一个父引用的后代同时清除已提交及待提交显示列表。后代引用来自真实 View.draw，需继续确认捕获树清理与列表换绑的交错。
- [RenderNode 的线程约束](https://developer.android.com/reference/android/graphics/RenderNode) 要求在绘制它的同一线程操作；供 View 使用的节点在 UI 线程操作。现有背景清理在 worker 调用 renderer.destroy、discardDisplayList 和 cache.close；与 UI 线程的列表换绑／记录没有串行关系。首个候选只将 LiveBackdrop 的绘制树清理放回记录线程，ImageReader 和图像缓冲继续后台释放，测量清理耗时与窗口帧耗时。
- 同类审计还发现 HardwareSnapshot、ForegroundSurface 和 DoingGlScene 的后台树销毁；先验证背景候选，再统一修正已确认的线程所有权问题，避免只覆盖首页一种取消入口。

## 排除单一线程原因，继续检查失效传播

- `scroll-main-*` 只改 LiveBackdrop 清理线程，三星第 25 次、OPPO 第 13 次仍复现；`scroll-main-all-*` 连同快照与前景清理都改到主线程，仍在同样位置复现。不能将此次问题结论写成“仅后台线程竞争”。
- `scroll-recover-oppo` 在失败后、没有重绑模型或重载媒体的情况下，仅对可见卡片调用一次 invalidate，立即恢复正确内容和阴影。失败时根卡片 RenderNode.hasDisplayList=true，普通 View 属性及 outline 仍正确。这表明原窗口仍认为根显示列表有效，但它所引用的子显示资源已不完整；只销毁捕获侧树，没有将失效传回原 View 的绘制缓存。
- 下一候选：捕获树释放与 View 记录串行，并在释放时对其借用的 View 子树发出一次正常绘制失效通知。只在捕获生命周期结束执行，不在粒子每帧中重绑或重录整个列表。继续用原输入循环及窗口 FrameMetrics 验证。

## 修复与扩大回归

- 加入释放后的失效通知后，三星、OPPO、魅族的 `scroll-invalidate-*` 各 90 次操作全部通过实际像素审计（共 270 次）。包含 0／90／210／350／430／560 ms 按住、上下滚动、短长卡片、离屏复用及长按拖动后返回普通模式。此前两个稳定失败的序列不再失败。
- 正式改动统一覆盖共享 View 节点的三处生命周期：持续背景、单次硬件快照、Doing 整页场景；同步快照兜底也补发失效。拆分捕获记录实际借用的 View，不只通知 DecorView，避免其下仍有效的父缓存跳过失效后代。已经离屏的 View 同样留下失效标记，重新挂载时正常重建。
- 只持有私有软件位图的 ForegroundSurface 不借用真实节点，恢复为原来的后台清理；GPU 读回、栅栏和 ImageReader 仍在原工作队列。没有保留捕获树、反射修改私有标志、强制重绑或每帧刷新列表的做法。
- 临时保留／延迟销毁／反射检查探针已从源码删除；留下真实输入与屏幕像素审计供后续复测。继续做修复前后同条件性能对照和最终包扩大验证。

## 性能口径与异常保留

真实列表的旧包在三星、OPPO 性能循环中再次触发空白而提前退出，不能与新包完整循环做等长比较。最早一份 baseline APK 未实现 press_ms 参数，同样不用于固定手势性能结论。后续使用具有相同参数的 worker-baseline APK，另在相同虚构卡片、动态背景和三次连续回拖上比较两种粒子。

稳态 GL 提交间隔的中位数均约 8.3 ms；三星与 OPPO 的 P95 基本一致（飘散约 9 ms、流体约 17 ms）。魅族初轮新版出现一次首帧回调 424 ms 和一次流体提交阻塞 1031 ms，均未删去：首次硬件快照清理仅 0.54 ms，延迟主要发生在后续 GL 准备／提交阶段，不能直接归因于本次清理操作，也不能据此宣称全场景完全没有延迟变化。增加六次连续回拖复测后，飘散首帧 43–60 ms，流体在热运行后降至 43–58 ms；段内最大提交间隔为 21 ms／62 ms，长停顿未再现。

旧包六次连续回拖补测：飘散首帧为 42–59 ms、流体从 224 ms 逐步降至 43 ms；新版同样有初次准备与热运行差别。两版流体稳态 P95 为 18.02／18.35 ms、最大间隔 58.8／62.2 ms；没有观察到持续帧率回退。初轮新版那次 1031 ms 停顿仍单列保留，未以阈值过滤掉；单次数据不足以确认成因。

这些数据分别代表窗口帧、GL 提交和首帧回调，不能把它们等同于屏幕逐像素验证。没有新增固定等待时间、改变手势阈值或改变粒子轨迹。
