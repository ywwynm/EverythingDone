## 性能测量口径

快速起滑使用 DOWN 后无停顿的系统 MOVE，手指停住后 UP 自然恢复；慢拖另测。只读观察器分别采集实际 DOWN、识别左滑、首个非零提交、纹理更新与窗口帧预算。提交回调不等于物理屏幕扫描。两台设备各自产物目录，禁止混合统计。初版采样脚本使用 CANCEL，旧观察器只将 UP 作为本轮结束，故该轮未进入正常测量统计，改用 UP 重新采样。

## 已验证的根因与修复

- 两台设备的上一发布版均在跨过原点后退出进程；9018f404 两次复现，Samsung 一次复现。
- 只改变 `Session.dispose` 的清理时机：立即关闭会话并隐藏失效粒子层，主线程队列下一轮才真正释放层并通知业务。两台各连续 5 轮跨原点回拖均保留同一进程与原记事，第一项假设成立。
- 不捕获或忽略框架异常，不修改正常右滑业务。具体真实手势回归作为该层级遍历错误的验证入口；普通 JVM 测试无法替代 Android 绘制调用链。

## 连续输入与图片卡片复测

- Samsung 逐条执行 `input motionevent` 有约 70 ms 的事件间隔，不能作为持续快速手指移动的唯一输入。新增 `ParticleGestureInput.java`，以 shell 身份经过 InputDispatcher 连续发送 MotionEvent；不连接应用内部入口。180 ms 左移 36% 卡片宽度，保持 600 ms 再松手，实际每轮约 48–52 个输入样本。
- 输入阶段更新活跃指针距离；当前显示帧只等待所需邻帧，手指停住无需重绘时才多算两档。仍使用相同粒子、随机规则、240 Hz 积分、100 次压力迭代、60 档 float32 历史和小数插值。
- 图片卡片 3 轮按下到非零画面：OPPO 577×573 px，旧版 195.2 / 178.0 / 196.0 ms，候选版 164.1 / 132.4 / 149.4 ms；Samsung 630×679 px，旧版 241.6 / 204.1 / 200.8 ms，候选版 193.4 / 189.8 / 152.0 ms。三星的中位数改善有限，仍有准备等待，不能写成零延迟。
- 慢拖 1.2 秒各 2 轮：OPPO 纹理间隔 P95 约 25 ms，没有确认帧率提升；Samsung 从 33.1 / 34.2 ms 降为 32.1 / 20.7 ms，GL 帧准备 P95 从 17.9 / 18.9 ms 降为 13.5 / 11.7 ms。未达到稳定 60 fps；帧预算仍有超时。
- 快速手势中人为停住的 600 ms 不应作为掉帧。其纹理间隔统计包含该停止期，只用于首个非零画面延迟；播放帧率采用上述连续慢拖测量。
- 图片回归：两台各 5 轮跨原点无崩溃；60% → 20% → 60% 同相位像素最大差均为 0；松手恢复整张卡片像素平均差为 0；根轮廓圆角检查通过。
