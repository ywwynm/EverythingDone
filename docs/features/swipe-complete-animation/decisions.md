# 实现决策

## 2026-09-15 甩动时画面先落后、再逐拍追上手指，不阻塞首帧

性能专项第三批的 3.1 修复，完整数据见
[粒子动画性能专项第三批结果](../particle-animation-performance/batch3-results-2026-09-15.md)。

- **出帧路径不再同步补档。** 甩动在 20–30 ms 就越过识别阈值，那时材料还没建好；等它就绪时
  手指已经拖过 20%，原实现的第一帧要先阻塞补齐 `ceil(position)` 档历史（三星单档约 7 ms，
  十几档就是 80 ms 以上）。改为：这一拍画 `min(手指相位, 已备好的最高档)`。已备档位是整数，
  取整数相位时 `drawGestureFrame` 的插值系数为 0、只用到那一档本身，一定安全。补档全部交给
  常驻线程的 pump，每拍最多拖住一档。
- **「手指要的相位」与「这一拍能画的相位」必须分开。** `wantsFrame()` 用能画的相位判定
  （否则追赶期内手指一停画面就冻住）；速度与「手指停住每拍多备两档」用手指相位
  （新增 `previousWanted`）。
- **提交给 `ParticleGestureProgress` 的进度是实际呈现的相位**，不是手指位置。因此
  `presentedProgress`、ItemTouchHelper 的松手恢复、`finishSwipe` 的快速完成都从画面真正到达的
  地方接着走，不会跳一下；「甩动比准备快时先播完剩余画面再执行完成操作」也从此是字面意义上的真。
- **效果**：识别后首个非零画面，OPPO 快拖 132.3 → **65.0 ms**、三星 201.0 → **122.0 ms**；
  同口径的「提交」侧 118.8 → 49.3 / 163.5 → 25.2 ms。慢拖不退化（OPPO 30.6 → 32.1）。
  追赶过程在逐帧进度里可见：首帧是第 0 档（完整卡片），随后每拍前进 2–6 档，第 8 帧前后跟上。
  「60% → 20% → 60% 同相位」仍是逐像素相同（`sameProgressMaxDifference` = 0）。
  开关 `ParticlePerfTuning.gestureCreepToFinger`，默认开；关掉即恢复原来的阻塞补档。

## 2026-09-14 回拖释放与输入阶段更新

- 回拖跨过原点可在 RecyclerView 绘制内触发释放；会话立即失效并隐藏旧画面，实际移除叠加层及业务回调交给主线程队列，避免改变正在遍历的 DecorView 子数组。没有按下预热的兜底创建也排到绘制之后，兼顾同步软件快照回调。
- 已识别手势的首个粒子帧使用当前距离，不再强制等待零进度帧。未识别左滑仍不接管真实卡片。
- 活跃手指在 Activity 输入分发阶段更新绝对距离，供同一帧的 GL 回调读取；松手后由 ItemTouchHelper 的位移接管恢复。避免在 RecyclerView.onDraw 才更新而落后一个节拍。
- 设置文案采用“左滑完成记事动画风格”“滑动渐隐”，三项重命名同步 13 套语言资源。

## 2026-09-14 按下准备与增量轨迹

- 只为本次按中的卡片准备零进度纹理，识别左滑后才接管。预备状态不推进历史；普通点击、纵移、多指、取消和长按超时清理未接管资源。
- 左滑起步不再等待完整一秒的轨迹。先呈现零进度，按当前手势补齐所需邻帧，每拍最多额外预备两档。保留 240 Hz 积分、100 次压力迭代与原粒子数量。
- 积分与历史回放分别绑定状态缓冲；回拖不能覆盖仍需继续积分的八分量状态，也不能倒拨其固定时步。真实 60% → 20% → 60% 画面散列相等。
- 含图片卡片的根轮廓来自实际 OutlineProvider，不以 CardView.radius 代替。硬件快照复制根裁剪，起步占位复用快照或按实际圆角裁剪。

## 2026-09-13

- 提供“滑动”“粒子”两档，默认保留原滑动效果，独立于弹窗粒子开关。
- 复用共同消散模型的轨迹缓存，以左移距离除以卡片自身宽度定位正向帧；与 ItemTouchHelper 的自动恢复／完成位移使用同一映射。实机发现按 RecyclerView 宽度计算会让平板多列卡片反应过弱，已调整；完成业务阈值仍沿用框架原有判定。
- 指针回退直接读取较早轨迹，不做物理反向积分；停住手指时保持原相位，不因墙钟时间自动结束。
- 生命周期、卡片回收及几何变化应释放叠加层；成功完成和取消分别恢复框架预期的卡片状态，避免卡片复用后透明。
- 保留 ItemTouchHelper 对真实 View 的位移，透明化该 View 并在准备阶段于原位绘制内容。不能把传给框架的 dX 改为零，否则松手恢复动画会错误地从零开始。
- 快速甩动的完成回调若早于粒子呈现，使用实际已呈现相位播放剩余过程后再完成记事；失败、退出页面等清理也只执行一次已确认的完成操作。
- 每张卡片独立持有手势，允许连续操作多张；GL 按实际提交时间戳记录已呈现相位，不能用最新手指距离冒充显示进度。
- 几何保护从父容器屏幕坐标计算卡片布局位置，排除既有按压缩放及手势平移；不能把 View 自身变换引起的原点变化当成重排。

## 2026-09-14

- 正式性能测试必须通过系统触摸真实界面，只读观察器记录实际输入与绘制；不以进程内调用手势或业务入口替代。
- 同一卡片左拖 36% 宽度、耗时 1.2 秒的对照发现：普通滑动正常，粒子纹理约每 50 ms 才更新，而主线程和系统输入约 16.7 ms 更新、GL 准备一帧仅约 3–4 ms。根因是手势进度被取整到 60 档，尚未跨档便跳过绘制。
- 保留 60 档轨迹缓存与原正向解算，在手势播放时插值相邻缓存的位置和速度，用连续进度绘制；不增加缓存档数或减少粒子。普通弹窗／新建的整数帧重放保持原路径。修复后须用同一卡片、同一真实输入手势复测。

## 2026-09-15

- 粒子消散方向不再固定向左，按手指方向镜像；随方向变号的算式集中在 `ParticleSwipeDirection`，
  由单测定死，不靠真机逐个方向试。
- 方向由**第一次越过 touch slop 的横向位移**决定，而不是等 ItemTouchHelper 判定滑动：消散方向
  必须在建动画层之前定下来，否则轨迹已经算完再改向就要整层重建。同一次手势里划过原点换方向，
  只在还没有粒子上屏时允许改向。
- 右滑是否算完成由宿主决定（`allowRightSwipe`）：正在做事界面左右滑都是完成记事，首页右滑是
  「开始做事」，必须保持关闭。
- 宿主容器的整体透明度烤进快照、接管期间容器还原成不透明。粒子画在共享 Surface 上拿不到容器
  透明度，两边只能这样对齐；单独做任何一侧都会在交接处留下亮度跳变。
- 设置项文案用「滑动」而非「左滑」，英文用 finish 而非 complete（与项目里完成记事的统一用词
  一致）。资源名与 SharedPreferences 键不动——键一改就会把所有人已选的档位重置。
- 首页右滑「开始做事」时卡片不再跟手平移，只保留 `flDoing` 蒙层按滑动距离淡入淡出。平移是
  多余的反馈，蒙层的出现与透明度变化已经足够表达手势进度。
- 实现只把传给 `super.onChildDraw` 的 dX 在「滑动且 dX > 0」时改成 0，框架自己的 dX 一个字
  不动。上面 2026-09-13「不能把传给框架的 dX 改为零」那条约束的是粒子那一侧：粒子完成时要
  靠框架把真实卡片停在屏外（`parkTranslationX`）。回弹与完成动画的起点不受影响——
  `ItemTouchHelper` 1.4.0 的 `getSelectedDxDy` 在横向滑动标志下取
  `mSelectedStartX + mDx - itemView.left`，与 `translationX` 无关（已反编译 1.4.0 字节码核
  实），所以松手后蒙层仍从真实手指位移开始淡出／补满。
- 只改首页（`ThingsActivity`）。正在做事界面是另一套回调与另一个 `ParticleSwipeAnimator`
  （`allowRightSwipe = true`），左右滑都是完成记事，跟手位移保留。

## 2026-09-16 回位动画（第三次）

- **接管 `notifyItemChanged` 换上来的那张新 View，不要碰被滑走的旧 View**：旧 View 在
  ItemTouchHelper 的待清理队列里，每帧都会被按回 `-RecyclerView.width`，`clearView` 到来才
  松手（约 290 ms）。
- **不给这几处的 `notifyItemChanged` 加 payload**。payload 让 holder 原地复用，代价是那张 View
  永远不被摘下、`clearView` 永远不来、卡片停在屏外——实测 2.6 秒都不动。默认换位动画必须留着，
  它同时是接管失败时的兜底。
- **只在卡片真的离开过时才回位**（`translationX != 0 || alpha < 0.99`）。右滑（开始做事）走到
  业务判定时卡片已经归位，再播就是凭空多出来的动画。
- 滑动档从**卡片自己一个身位**外滑回，不是从 `-RecyclerView.width`：后者要走完 75% 才进屏，
  正是原本「啪地弹回来」的成因。
- 这一类时序问题一律先在真机上量 `onSwiped` / `clearView` / 业务判定的实际先后与卡片每一刻的
  `translationX` / `alpha` / View 身份，再动手。前两版都是推断时序失败的。

## 2026-09-16 header 记事不再可滑

- header 记事、文件夹条目与 `NOTIFY_EMPTY_*` 占位卡不再拿得到滑动标志。`getMovementFlags`
  此前只判 `is ThingListEntry.ThingEntry`，而 header 正是一个 `type = Thing.HEADER` 的
  `ThingEntry`（`ThingManager` 把它放在列表位置 0），于是 header 一直可以被左右滑：跟手平移、
  右滑还淡入「开始做事」蒙层、左滑在粒子档还会播粒子，松手才被 `completeThingSwipe` 的
  `listPosition <= 0` 原样退回。新增 `canSwipeListEntry`，口径与 `completeThingSwipe` 的几处
  早退对齐（位置 0、非 `ThingEntry`、`type > Thing.NOTIFICATION_GOAL`），不放行则手势自始至终
  不成立。
- 判定放在 `getMovementFlags` 而不是在 `onChildDraw` 里把蒙层藏掉：后者只遮住右滑这一半，
  左滑的平移与粒子仍然会播，且"滑得动但什么都不会发生"本身就是错的。
- `canSwipeListEntry` 不调用 `getThingIndexForListPosition`。它对 `mThings` 做线性查找，而
  `getMovementFlags` 每次按下都会走；header 已由 `type` 判掉，不必再付这个代价。
- `WELCOME_*`（4–8）仍可滑动，那几张欢迎卡本来就能滑动完成。
- 与同日的回位动画（`52d9b0a1`）的关系：`completeThingSwipe` 里 `listPosition <= 0`、
  `!is ThingEntry`、`thingType > NOTIFICATION_GOAL` 这三条早退分支上的 `stays(...)` 从此不再
  可达（手势根本不成立）。留着当防御，不删。真正会用到回位动画的仍是隐私认证被取消、习惯已
  暂停、右滑开始做事这几条「卡片留在列表里」的路径。

## 2026-09-16 快照按可见区裁，且一律按布局位置算

卡片被容器截断时，粒子快照只抓露出来的那一块，不抓整张。两条定死的取舍：

1. **在捕获时裁，不是抓完再裁。** 离屏节点按可见区定尺寸、记录前平移画布、outline 用
   `Outline.offset` 跟着挪、阴影光源原点加同一偏移。抓完再 `Bitmap.createBitmap` 裁一次要多付
   一整张卡片大小的拷贝，而这条路在每次按下卡片时都会走。
2. **可见区一律按 `left`/`top` 这类布局位置算，不看 translation 与 scale。** 滑动中的位移与
   按压反馈的缩放都不改变卡片静止时露出的形状，而粒子要复刻的正是那个形状；按当前 translation
   算会让「先滑一段再松手」这类情形取到一块错位的区域。

整张卡片都露着时走原来那条不裁的路（`ParticleCardClip.visibleRect` 返回 null），逐帧与以前一致。
截断线与圆角的三种关系（完整圆角 / 半截圆角 / 直角）不需要额外判断：圆角已由
`setClipToOutline` 烤进快照，截断是矩形裁剪，两者相交自然得到。
