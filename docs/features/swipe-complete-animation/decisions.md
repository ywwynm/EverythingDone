# 实现决策

## 2026-09-17 FAB 保持位于卡片粒子上方

- 用户确认整段动画保持原有前后关系。Android 14+ 的卡片继续使用共享 SurfaceView；FAB 绘制临时放在该 Surface 的自有子层上，覆盖交接快照及播放中的粒子，输入与业务状态仍由原控件处理。
- 首尾用窗口事务同步交接原 FAB 与临时层；多卡片共用同一 FAB 层，最后一个使用者释放后恢复。接管期间直接提交 FAB 缓冲，避免等待没有可见内容变化的窗口帧。
- FAB 内容使用可复用的小位图，阴影使用真实 Outline、elevation 和窗口光源，由 HWUI 绘制。直接将 RippleDrawable 放入第二个硬件 renderer 的实测会引发自主出帧及 RenderThread 阻塞；仅隔离 FAB 内容绘制，不改变粒子后端。
- 静止 FAB 复用一帧，移动、缩放、透明度和波纹变化时更新；不做 GPU 像素读回。旧系统的 Texture 动画层插在 FAB 之前，保持正常 View 层级。
- 真机反馈回路使用包含真实 FAB 的虚构列表与最终合成录屏，实际点击检查同时确认回聚到末帧。实现取舍、失败尝试和数据见 [FAB 遮挡诊断](fab-occlusion-2026-09-17.md)。

## 2026-09-17 使用 SurfaceView 同步交接卡片阴影

- 用户要求恢复 SurfaceView。Android 14 / API 34 起，卡片消散和回聚复用每个窗口原有的一个 SurfaceView，保留共享 GL 线程、上下文、缓存、时钟及栅栏。
- 阴影仍进入卡片快照和共同粒子材料；只在开始与回位交接时使用短暂的自有 SurfaceControl 快照层。窗口帧用 `applyTransactionOnDraw` 交接，粒子帧由 GL 线程在下一次 swap 前调用 `applyTransactionToFrame` 交接。正常播放不经过 TextureView，也不逐帧创建事务。
- 未采用隐藏 API 或固定延时交接。1 秒仅作窗口停止出帧后的异常回收，正常流程按事务 committed 回调推进；仅预热就取消时不显示快照。
- API 34 以下缺少公开的 SurfaceView 逐帧绑定接口，保留上一版卡片 TextureView 兼容分支；普通弹窗不受此边界影响。
- 魅族 Android 15 已验证短滑、回弹、反拖、快甩完成后回聚、连续输入、系统取消及退出清理。两条后端的热运行首个提交均约 120–160ms，未证明帧率或功耗显著改善。完整证据见 [Surface 同步诊断](shadow-surface-2026-09-17.md)。

## 2026-09-17 阴影进入粒子材料并在同一窗口交接

- 用户否定原位完整阴影独立淡出的方案：短滑后仍有轮廓残留。本轮删除该路线，卡片与其硬件投影一起进入粒子快照、共同消散及回聚。
- 卡片粒子使用 TextureView，与原 View 同帧切换透明度；共享 Surface 仍用于普通弹窗。不能用提交回调或固定延时去交接两个独立 Surface 的半透明阴影。
- 捕获根卡片必须设置带 elevation 的 RenderNode、开启 Z 绘制，并将 Outline alpha 初始化为 1 后调用真实 provider；光源读取设备主题，Android 14+ 复现框架高度修正。Vulkan 还需按窗口缓冲方向旋转绘制面与光源，读回后转正；OpenGL 不预旋转。
- 扩展阴影范围同时按面积增加材料预算，卡片本体粒径保持原值。卡片准备和动画期间统一为静止高度及缩放，释放后恢复正常触摸控制。
- 确认完成后的补全进度不得低于已提交帧，避免呈现通知延迟造成短暂倒退；未完成的手指回拖仍按实际位移倒放。
- OPPO 真实系统手势及合成像素已验证，魅族离线尚未验证。详细证据与兼容边界见 [本轮诊断](shadow-in-window-2026-09-17.md)。

## 2026-09-17 真实卡片在父列表中只显示外部阴影（已由同窗口方案取代）

- 当前实现用 `StablerRecyclerView.drawChild` 的圆角差集裁剪隐藏卡片内容，保留真实 RenderNode 的外部投影；不把阴影加入粒子快照，不新增投影替身。
- 差集裁剪必须有独立的 `Canvas.disableZ / enableZ` 区间。列表原来的 Z 重排会把子节点绘制延后，只有 `save / clipOutPath / restore` 时，整张卡片仍可能露在粒子下方。双机截图及窗口内部像素断言确认独立区间生效。[Android Canvas 文档](https://developer.android.com/reference/android/graphics/Canvas#enableZ()) 明确 Z 状态不随 save/restore 保存。
- 阴影强度跟随已呈现进度，但每次变化有速度上限：满幅淡出 96ms、恢复 144ms，单次迟到回调最多推进 32ms。快速输入不能一步跳完整段，静止后不再发帧；极快完成还要等这段短退场结束才把旧 holder 停到屏外。
- `InterceptTouchCardView` 的内容显示列表保持正常。跳过首次 `draw` 的新卡片虽然 alpha / z / outline 已齐全，Samsung 实测仍不投影，不能再把“空显示列表也投影”当成跨设备契约。
- 粒子期间卡片保持原位和正常高度，强度由原生阴影颜色 alpha 控制；回弹与再次触摸复用当前强度。外部按压反馈及 ItemTouchHelper 不能把 z 再抬高。
- 此实现要求 API 29 的公开 Z 绘制控制；API 26–28 及非 `StablerRecyclerView` 宿主沿用原整体隐藏路径，避免引入未经验证的兼容实现。
- 诊断入口只展示虚构卡片，复用真实动画和换 holder 的回位链路，不调用 DAO 或写动画设置。详见 [本轮诊断](shadow-2026-09-17.md)。
- 粒子首帧到达时必须显式 invalidate 父列表，撤掉它缓存的准备期占位绘制。快速甩动可能已让 ItemTouchHelper 停止重画，不能依赖后续手指输入或只更新阴影颜色来刷新父显示列表。

## 2026-09-15 甩动时画面先落后、再逐拍追上手指，不阻塞首帧

性能专项第三批的 3.1 修复，完整数据见
[粒子动画性能专项第三批结果](../particle-animation-performance/batch3-results-2026-09-15.md)。

- **出帧路径不再同步补档。** 甩动在 20–30 ms 就越过识别阈值，那时材料还没建好；等它就绪时
  手指已经拖过 20%，原实现的第一帧要先阻塞补齐 `ceil(position)` 档历史（三星单档约 7 ms，
  十几档就是 80 ms 以上）。改为：这一拍画 `min(手指相位, 已备好的最高档)`。已备档位是整数，
  取整数相位时 `drawGestureFrame` 的插值系数为 0、只用到那一档本身，一定安全。补档全部交给
  常驻线程的 pump，每拍最多拖住一档。
- **「手指要的相位」与「这一拍能画的相位」必须分开。** `wantsFrame()` 用能画的相位判定
  （否则追赶期内手指一停画面就冻住）；速度与「手指停住每拍多备两档」用手指相位
  （新增 `previousWanted`）。
- **提交给 `ParticleGestureProgress` 的进度是实际呈现的相位**，不是手指位置。因此
  `presentedProgress`、ItemTouchHelper 的松手恢复、`finishSwipe` 的快速完成都从画面真正到达的
  地方接着走，不会跳一下；「甩动比准备快时先播完剩余画面再执行完成操作」也从此是字面意义上的真。
- **效果**：识别后首个非零画面，OPPO 快拖 132.3 → **65.0 ms**、三星 201.0 → **122.0 ms**；
  同口径的「提交」侧 118.8 → 49.3 / 163.5 → 25.2 ms。慢拖不退化（OPPO 30.6 → 32.1）。
  追赶过程在逐帧进度里可见：首帧是第 0 档（完整卡片），随后每拍前进 2–6 档，第 8 帧前后跟上。
  「60% → 20% → 60% 同相位」仍是逐像素相同（`sameProgressMaxDifference` = 0）。
  开关 `ParticlePerfTuning.gestureCreepToFinger`，默认开；关掉即恢复原来的阻塞补档。

## 2026-09-14 回拖释放与输入阶段更新

- 回拖跨过原点可在 RecyclerView 绘制内触发释放；会话立即失效并隐藏旧画面，实际移除叠加层及业务回调交给主线程队列，避免改变正在遍历的 DecorView 子数组。没有按下预热的兜底创建也排到绘制之后，兼顾同步软件快照回调。
- 已识别手势的首个粒子帧使用当前距离，不再强制等待零进度帧。未识别左滑仍不接管真实卡片。
- 活跃手指在 Activity 输入分发阶段更新绝对距离，供同一帧的 GL 回调读取；松手后由 ItemTouchHelper 的位移接管恢复。避免在 RecyclerView.onDraw 才更新而落后一个节拍。
- 设置文案采用“左滑完成记事动画风格”“滑动渐隐”，三项重命名同步 13 套语言资源。

## 2026-09-14 按下准备与增量轨迹

- 只为本次按中的卡片准备零进度纹理，识别左滑后才接管。预备状态不推进历史；普通点击、纵移、多指、取消和长按超时清理未接管资源。
- 左滑起步不再等待完整一秒的轨迹。先呈现零进度，按当前手势补齐所需邻帧，每拍最多额外预备两档。保留 240 Hz 积分、100 次压力迭代与原粒子数量。
- 积分与历史回放分别绑定状态缓冲；回拖不能覆盖仍需继续积分的八分量状态，也不能倒拨其固定时步。真实 60% → 20% → 60% 画面散列相等。
- 含图片卡片的根轮廓来自实际 OutlineProvider，不以 CardView.radius 代替。硬件快照复制根裁剪，起步占位复用快照或按实际圆角裁剪。

## 2026-09-13

- 提供“滑动”“粒子”两档，默认保留原滑动效果，独立于弹窗粒子开关。
- 复用共同消散模型的轨迹缓存，以左移距离除以卡片自身宽度定位正向帧；与 ItemTouchHelper 的自动恢复／完成位移使用同一映射。实机发现按 RecyclerView 宽度计算会让平板多列卡片反应过弱，已调整；完成业务阈值仍沿用框架原有判定。
- 指针回退直接读取较早轨迹，不做物理反向积分；停住手指时保持原相位，不因墙钟时间自动结束。
- 生命周期、卡片回收及几何变化应释放叠加层；成功完成和取消分别恢复框架预期的卡片状态，避免卡片复用后透明。
- 保留 ItemTouchHelper 对真实 View 的位移，透明化该 View 并在准备阶段于原位绘制内容。不能把传给框架的 dX 改为零，否则松手恢复动画会错误地从零开始。
- 快速甩动的完成回调若早于粒子呈现，使用实际已呈现相位播放剩余过程后再完成记事；失败、退出页面等清理也只执行一次已确认的完成操作。
- 每张卡片独立持有手势，允许连续操作多张；GL 按实际提交时间戳记录已呈现相位，不能用最新手指距离冒充显示进度。
- 几何保护从父容器屏幕坐标计算卡片布局位置，排除既有按压缩放及手势平移；不能把 View 自身变换引起的原点变化当成重排。

## 2026-09-14

- 正式性能测试必须通过系统触摸真实界面，只读观察器记录实际输入与绘制；不以进程内调用手势或业务入口替代。
- 同一卡片左拖 36% 宽度、耗时 1.2 秒的对照发现：普通滑动正常，粒子纹理约每 50 ms 才更新，而主线程和系统输入约 16.7 ms 更新、GL 准备一帧仅约 3–4 ms。根因是手势进度被取整到 60 档，尚未跨档便跳过绘制。
- 保留 60 档轨迹缓存与原正向解算，在手势播放时插值相邻缓存的位置和速度，用连续进度绘制；不增加缓存档数或减少粒子。普通弹窗／新建的整数帧重放保持原路径。修复后须用同一卡片、同一真实输入手势复测。

## 2026-09-15

- 粒子消散方向不再固定向左，按手指方向镜像；随方向变号的算式集中在 `ParticleSwipeDirection`，
  由单测定死，不靠真机逐个方向试。
- 方向由**第一次越过 touch slop 的横向位移**决定，而不是等 ItemTouchHelper 判定滑动：消散方向
  必须在建动画层之前定下来，否则轨迹已经算完再改向就要整层重建。同一次手势里划过原点换方向，
  只在还没有粒子上屏时允许改向。
- 右滑是否算完成由宿主决定（`allowRightSwipe`）：正在做事界面左右滑都是完成记事，首页右滑是
  「开始做事」，必须保持关闭。
- 宿主容器的整体透明度烤进快照、接管期间容器还原成不透明。粒子画在共享 Surface 上拿不到容器
  透明度，两边只能这样对齐；单独做任何一侧都会在交接处留下亮度跳变。
- 设置项文案用「滑动」而非「左滑」，英文用 finish 而非 complete（与项目里完成记事的统一用词
  一致）。资源名与 SharedPreferences 键不动——键一改就会把所有人已选的档位重置。
- 首页右滑「开始做事」时卡片不再跟手平移，只保留 `flDoing` 蒙层按滑动距离淡入淡出。平移是
  多余的反馈，蒙层的出现与透明度变化已经足够表达手势进度。
- 实现只把传给 `super.onChildDraw` 的 dX 在「滑动且 dX > 0」时改成 0，框架自己的 dX 一个字
  不动。上面 2026-09-13「不能把传给框架的 dX 改为零」那条约束的是粒子那一侧：粒子完成时要
  靠框架把真实卡片停在屏外（`parkTranslationX`）。回弹与完成动画的起点不受影响——
  `ItemTouchHelper` 1.4.0 的 `getSelectedDxDy` 在横向滑动标志下取
  `mSelectedStartX + mDx - itemView.left`，与 `translationX` 无关（已反编译 1.4.0 字节码核
  实），所以松手后蒙层仍从真实手指位移开始淡出／补满。
- 只改首页（`ThingsActivity`）。正在做事界面是另一套回调与另一个 `ParticleSwipeAnimator`
  （`allowRightSwipe = true`），左右滑都是完成记事，跟手位移保留。

## 2026-09-16 回位动画（第三次）

- **接管 `notifyItemChanged` 换上来的那张新 View，不要碰被滑走的旧 View**：旧 View 在
  ItemTouchHelper 的待清理队列里，每帧都会被按回 `-RecyclerView.width`，`clearView` 到来才
  松手（约 290 ms）。
- **不给这几处的 `notifyItemChanged` 加 payload**。payload 让 holder 原地复用，代价是那张 View
  永远不被摘下、`clearView` 永远不来、卡片停在屏外——实测 2.6 秒都不动。默认换位动画必须留着，
  它同时是接管失败时的兜底。
- **只在卡片真的离开过时才回位**（`translationX != 0 || alpha < 0.99`）。右滑（开始做事）走到
  业务判定时卡片已经归位，再播就是凭空多出来的动画。
- 滑动档从**卡片自己一个身位**外滑回，不是从 `-RecyclerView.width`：后者要走完 75% 才进屏，
  正是原本「啪地弹回来」的成因。
- 这一类时序问题一律先在真机上量 `onSwiped` / `clearView` / 业务判定的实际先后与卡片每一刻的
  `translationX` / `alpha` / View 身份，再动手。前两版都是推断时序失败的。

## 2026-09-16 header 记事不再可滑

- header 记事、文件夹条目与 `NOTIFY_EMPTY_*` 占位卡不再拿得到滑动标志。`getMovementFlags`
  此前只判 `is ThingListEntry.ThingEntry`，而 header 正是一个 `type = Thing.HEADER` 的
  `ThingEntry`（`ThingManager` 把它放在列表位置 0），于是 header 一直可以被左右滑：跟手平移、
  右滑还淡入「开始做事」蒙层、左滑在粒子档还会播粒子，松手才被 `completeThingSwipe` 的
  `listPosition <= 0` 原样退回。新增 `canSwipeListEntry`，口径与 `completeThingSwipe` 的几处
  早退对齐（位置 0、非 `ThingEntry`、`type > Thing.NOTIFICATION_GOAL`），不放行则手势自始至终
  不成立。
- 判定放在 `getMovementFlags` 而不是在 `onChildDraw` 里把蒙层藏掉：后者只遮住右滑这一半，
  左滑的平移与粒子仍然会播，且"滑得动但什么都不会发生"本身就是错的。
- `canSwipeListEntry` 不调用 `getThingIndexForListPosition`。它对 `mThings` 做线性查找，而
  `getMovementFlags` 每次按下都会走；header 已由 `type` 判掉，不必再付这个代价。
- `WELCOME_*`（4–8）仍可滑动，那几张欢迎卡本来就能滑动完成。
- 与同日的回位动画（`52d9b0a1`）的关系：`completeThingSwipe` 里 `listPosition <= 0`、
  `!is ThingEntry`、`thingType > NOTIFICATION_GOAL` 这三条早退分支上的 `stays(...)` 从此不再
  可达（手势根本不成立）。留着当防御，不删。真正会用到回位动画的仍是隐私认证被取消、习惯已
  暂停、右滑开始做事这几条「卡片留在列表里」的路径。

## 2026-09-16 快照按可见区裁，且一律按布局位置算

卡片被容器截断时，粒子快照只抓露出来的那一块，不抓整张。两条定死的取舍：

1. **在捕获时裁，不是抓完再裁。** 离屏节点按可见区定尺寸、记录前平移画布、outline 用
   `Outline.offset` 跟着挪、阴影光源原点加同一偏移。抓完再 `Bitmap.createBitmap` 裁一次要多付
   一整张卡片大小的拷贝，而这条路在每次按下卡片时都会走。
2. **可见区一律按 `left`/`top` 这类布局位置算，不看 translation 与 scale。** 滑动中的位移与
   按压反馈的缩放都不改变卡片静止时露出的形状，而粒子要复刻的正是那个形状；按当前 translation
   算会让「先滑一段再松手」这类情形取到一块错位的区域。

整张卡片都露着时走原来那条不裁的路（`ParticleCardClip.visibleRect` 返回 null），逐帧与以前一致。
截断线与圆角的三种关系（完整圆角 / 半截圆角 / 直角）不需要额外判断：圆角已由
`setClipToOutline` 烤进快照，截断是矩形裁剪，两者相交自然得到。

## 2026-09-16 阴影单独成层，只调浓度不动形状

粒子消散期间的 elevation 阴影由一个只有 outline、没有内容的替身接着投影
（`ParticleCardShadow`），不烤进快照、不随粒子飞走。四条定死的取舍：

1. **不把阴影烤进快照。** 粒子格子数受 `max_cells` 封顶（`cell = sqrt(w×h×budget/(max_cells−1000))`），
   四周各加 24dp 会让取景面积涨 50–65%，格子边长随之粗约 25%，而多出来的格子全落在阴影上；
   `ParticleMicroflakeContent.weight` 末项乘 `alpha/255`，阴影像素还会飞成一圈低对比度的淡黑
   粒子。另外 API 26–28 走软件绘制，那条路画不出 outline 阴影。
2. **只调浓度，不按消散前沿收缩形状。** `releaseField` 实测：左滑时释放顺序是「最右先走、
   最左次之、中部最后」（各列平均释放时刻 右 0.13 / 左 0.33 / 中 0.47），未释放区是从两侧
   向中部收缩的窄条，用一个矩形去跟只会得到往回走的形状；而且释放在进度 0.62 就全部完成，
   后半段不存在「完整的一块」。浓度是唯一既物理正确、又不需要方向假设的量。
3. **浓度加在外层容器上，替身自己恒为不透明。** Skia 只在 caster 半透明时才把阴影铺满 outline
   内部（`RenderNodeDrawable` 按 `casterAlpha < 1` 传 `kTransparentOccluder`），而替身正摆在
   卡片位置上，内圈阴影会叠到粒子画面上去。外层重写 `hasOverlappingRendering` 返回 false，
   alpha 直接落到 RenderNode 上，不为此建离屏层。
4. **挂在卡片父容器的 overlay 上，不挂 decor。** 列表自己的裁剪因此自动生效（正在做事界面按
   直线截断卡片时尤其明显），叠放顺序也跟着对了——在列表全部卡片之上、在页面控件之下。代价是
   overlay 的内容不受父容器自己的 `clipChildren` 约束，所以外层要把父容器的裁剪规则照抄一份。

浓度曲线（`ParticleCardShadowFade`）跟的是「还有多少内容留在原位」，取值量自释放场而不是试出来
的：衰减区间 0.05→0.65，`1 − smoothstep` 形状，单测拿同一份 `releaseField` 做逐点对照。

## 2026-09-16 替身层的卡片矩形内部一律挖成透明

阴影替身在 Z 轴上位于卡片之下，粒子把卡片内容带走之后它那一块就直接露在屏幕上。真机实测：
**系统在 outline 内部画了东西**（几何与本影区吻合：比卡片小一圈、因光源在上方而向下偏移），
静止时被不透明卡片挡着看不见，卡片一消散就露出来。

因此 `ShadowHost.dispatchDraw` 先 `saveLayer` 把子 View 连阴影一起画进离屏层，再按卡片的圆角
矩形擦一遍。**不去推断平台在 outline 内部画了什么、会不会剔除**（上一轮就是按
`RenderNodeDrawable` 的 `casterAlpha < 1` 判定推断的，实测不成立），而是让结果确定：卡片矩形
内部一定透明，那一块本来就该由粒子和快照负责。

离屏层同时堵住另一种可能：容器没有自己的层时，阴影绘制内部若有擦除动作会直接落在列表的共享
画布上，把已经画好的内容擦掉。代价是每帧一次离屏层，为此把 host 收紧到「卡片可见区外扩 3 倍
z」，父容器自己的裁剪改由绘制时的 `clipRect` 补上。

## 2026-09-16（修订）阴影烤进快照，替身方案作废

上面两条「阴影单独成层」的决策**已被推翻**。替身方案有结构性问题：阴影是一层独立的 View，
粒子飞走时它只能整体淡出、**停在原地不跟着走**；而且它在 Z 轴上位于卡片之下，卡片一消散就把
系统画在 outline 内部的东西露了出来。用户裁定后整套删除（`ParticleCardShadow`、
`ParticleCardShadowFade` 及其单测）。

现在的做法是**把阴影抓进快照**：取景框四周按阴影余量外扩，卡片本体套进一个带 z 与 outline 的
子节点，阴影由父节点画在子节点矩形之外，于是成为快照的一部分、跟着粒子一起碎开。三条定死的：

1. **`Canvas.enableZ()` / `disableZ()` 必须包住 `drawRenderNode`。** Z 排序与投影是这对调用打开
   的（框架 ViewGroup 画子 View 阴影用的 `insertReorderBarrier` / `insertInorderBarrier`）。少了
   它一点阴影都没有，而且不报错——第一版就栽在这里，落盘快照逐通道量 alpha 才发现。
2. **光源那五项从设备读，不硬编码，并且用 `hasValue` 判断读没读到。** `lightY` / `lightZ` /
   `lightRadius` / `ambientShadowAlpha` / `spotShadowAlpha` 都是框架的主题属性，设备会覆盖：
   OPPO 平板实测 `lightZ` 是 500dp 而不是 AOSP 常见的 600dp。`getDimension` 的默认值会把
   「属性没读到」伪装成「属性就是这个值」，必须先 `hasValue`。屏幕宽度用 `Display.getRealSize`
   （框架 `ThreadedRenderer.setLightCenter` 用的就是它），不用 `displayMetrics.widthPixels`。
3. **准备期补画的那一层只画卡片本体，不画阴影圈。** 它与粒子 Surface 的首帧有一两帧重叠
   （先显后撤），两边都含阴影时那一圈会叠两层，实测接管瞬间阴影深一倍（9.5 → 20.8 灰阶）。

余量按投影几何逐边算（`ParticleShadowInset`，纯几何 + 单测），四边不对称——光源在屏幕上方中点，
卡片越靠下越靠边，阴影伸得越远。**不用一个保守的常数**：取景面积每涨一分，粒子就粗一分
（格子总数受 `max_cells` 封顶）。

## 2026-09-16（定稿）阴影由真实卡片产生，只调强度

前面三条阴影相关的决策（替身成层、烤进快照）**都已作废**。定稿的做法是用户提的：**阴影仍由
真实卡片产生，只让它的强度随进度平滑退场／入场**——目标本来就是消除跳变，不是让阴影碎开。

依据是一条平台事实：**阴影绘制只看卡片 RenderNode 的 alpha、z 与 outline，与 display list 里
有没有内容无关。** 于是：

1. **`ParticleShadowCaster.shadowOnly`**：卡片把 `draw` 与 `dispatchDraw` 两处记录入口都拦掉，
   alpha 留在 1。两处都要拦——有背景时框架走 `draw`，没背景（`PFLAG_SKIP_DRAW`）时直接走
   `dispatchDraw`。拿不到这个接口的 View 退回原来那条「整块隐藏」的路。
2. **强度按 `ParticleCardShadowFade` 乘到 `elevation` 上**，曲线量自释放场（0.05→0.65）。
3. **粒子档下卡片不跟手平移**（`onChildDraw` 传 `translationDX = 0`）：它只剩一层留在原位的
   阴影，跟着手指走会与原位消散的粒子错开。滑动档仍跟手。
4. **粒子档下不抬 Z**：`keepActiveTouchItemAboveSiblings` 按 `elevation` 反推 `translationZ`
   来维持「盖住兄弟卡片」，会把刚降下去的 elevation 补回来，阴影就淡不下去；而此时卡片内容
   不可见，也不需要盖在别的卡片上。
5. **倒放回位共用同一套**：`appearContent` 新增 `hideContent` 回调，卡片这条路传「只投影」
   而不是整块透明（默认 null 时行为与改动前逐字等价）。

为什么比前两版好：阴影与静止时**逐像素同源**（真机实测接管瞬间与静止完全一致，三个方向同
比例衰减），不存在离屏渲染器与窗口渲染器的差异；取景框不外扩，粒子不会变粗；回位那条路
不需要改抓图链路。代价是阴影整体平滑变淡而不是跟着粒子碎开。

## 2026-09-16（定稿二）阴影抓进快照；光源必须复刻框架的全部算式

「只投影 + elevation 动画」那一版也作废了：快速滑动时那一小段动画来不及，粒子已经散开而阴影
还在。定稿回到**把阴影抓进快照**，让它跟着粒子一起碎。三条定死的：

1. **光源参数要逐项复刻 `ThreadedRenderer.setLightCenter`**，尤其 `lightZ` 不是主题值直接用：
   还要乘 `zWeightedAdjustment = (min(widthPixels, heightPixels) / (450 × density) + 2) / 3`。
   漏掉它，离屏阴影比屏幕上的深 1.7–2 倍。五项都是主题属性（`Lighting` styleable），前三个
   没有公开的 `R.attr`，按名字查 id 并先 `hasValue`；宽度用 `displayMetrics.widthPixels`。
2. **`Canvas.enableZ()` / `disableZ()` 必须包住 `drawRenderNode`**，否则一点阴影都没有而且
   不报错（框架里 ViewGroup 画子 View 阴影用的就是它）。
3. **交接期只能有一层投影**，按的是阴影**颜色**而不是 elevation：按压反馈的 ObjectAnimator
   会一路改写 `cardElevation`，抬 Z 那一套又会按 elevation 反推 translationZ 补回来，两条路
   都按不住；阴影颜色没人抢，且与 outline、圆角裁剪无关。同理，准备期在卡片原位补画的那一层
   只画卡片本体、不画阴影圈（否则与粒子 Surface 的首帧叠两层）。

### 怎么测阴影才算干净

列表里卡片间距 42 px，而阴影余量 30–48 px，**相邻卡片的阴影必然重叠**。只有朝向空白区的那条
边可以用来比对离屏与屏幕（这一版用的是第一行卡片的上缘）。在有邻居的边上量，会得到「下缘深
2 倍、左缘浅 15%」这种完全是假象的结论。

## 2026-09-16 滑动手势结束后，卡片的 z 必须回到静止值

这是「松手后偶尔闪一下」的真凶，也是一条与粒子无关的既有缺陷：

- **按压反馈压低的 `cardElevation` 不会自己还原**——`animateCardTouchDown` 把它压到原值的 2/3，
  而手势被 `ItemTouchHelper` 接管之后卡片收不到 `ACTION_UP`，释放动画不跑。因此
  `clearView` 里要显式还原成 `thing_card_normal_elevation`。
- **抬 Z 只在手指真的还按着时做**（`onChildDraw` 的 `isCurrentlyActive`）。
  `keepActiveTouchItemAboveSiblings` 是按 `maxSiblingZ + 偏移 − elevation` 反推 translationZ 的，
  elevation 一被压低它就补得更多，总高度锁死在 12dp；而 `ItemTouchHelper` 在 `clearView`
  之后还会再画一两帧，把刚清零的 translationZ 重新垫起来。

为什么粒子这条路对它特别敏感：**快照的阴影是按抓取时的 z 画的**，交接之后换成真实卡片的阴影，
两者的 z 一旦不同，观感就是阴影在那一刻突然变深或变浅。也就是说，只要「静止 z」这件事不成立，
任何「让阴影连续」的做法都会漏。

量它的办法：`PROBE-REMIND` 那张卡片的上缘（上方是空白标题区），比「冷启动静止 / 滑动若干次后」
的阴影深度剖面，逐点相同才算对。

## 2026-09-16 交接那一帧的三处叠加源

阴影进快照之后，「粒子层 → 真实卡片」的交接必然有一两帧的不一致（两者在不同的 Surface 上，
做不到绝对同帧）。能做的是把差异压到最小，并且不要自己再引入新的源：

1. **原始阴影颜色必须在动画器级别缓存，且过滤掉透明值。** 交接期这两个值被按成透明，而下一次
   按下可能落在那之前；会话一读到透明，收尾就把「透明」当成原值还回去，卡片从此没有阴影。
2. **还阴影要等粒子 Surface 真的清帧**，不能跟着 `afterRelease` 立刻做——那个回调是在会话
   `cancel()` 之后同步触发的，而 Surface 要等 GL 线程下一次合成才抹成全透明
   （`ParticleWindowSurface.needsFrame`）。早还一帧就是两层阴影同时在。
3. **兜底时限要短**：`afterRelease` 不来时，那段时间屏幕上一层阴影都没有。缺阴影比多一层更
   接近「没变」，但也别缺太久。

判断方向的口径（下次再出问题直接问）：**突然变深 = 还有叠加源；先没了再出现 = 还回来得太晚。**
两者的调整方向相反，不问清楚就改等于瞎猜。

## 2026-09-16 阴影交接等事件，不等固定时长

把阴影还给卡片必须**紧跟粒子 Surface 抹平那一刻**：早了与 Surface 上的阴影叠成两层，晚了空出
一段一层都没有的窗口（阴影从 0 跳到满值，观感同样是「突然变深」）。因此
`ParticleWindowSurface` 提供 `runAfterCleared`——GL 线程在抹平那一帧之后 post 到主线程，
`needsWork()` 把该队列算进去以免线程提前休眠，另配 200ms 兜底。

**不要用估出来的固定延时。** 这一处先后试过 320 / 160 / 34ms，全是猜；逐点打时间戳
（handoff-start / after-release / surface-cleared / shadow-back）一次就看清了真实间隔，改完
间隔降到 0–7ms。凡是跨线程或跨 Surface 的交接，先量时序再动手。

## 2026-09-16 阴影必须进快照：独立衰减在快速滑动下必然突变

「让阴影由真实卡片提供、按消散进度衰减」这条路**被否掉了，理由是结构性的**：用户滑得快时，
进度会在一帧之内跳过整段衰减曲线，阴影于是一步从满值到 0——那正是最初要消除的突变。绑时长
则会滞后于粒子（第四轮）。**只有把阴影抓进快照，它才与粒子画面天然同步，手滑多快都一样。**

代价是「粒子层 → 真实卡片」的交接跨着两个 Surface，做不到绝对同帧。能做的三件事，按收益排序：

1. **等事件而不是等固定时长**（`ParticleWindowSurface.runAfterCleared`），把间隔压到 0–7 ms；
2. **把「还回去」摊成几帧渐入**（64 ms / 四帧），让一次约 15 灰阶的跳变变成每帧 4 个以内；
3. 真要零交接，只能让**粒子 Surface 的最后一帧就不画阴影圈**（GL 侧按卡片本体范围丢掉阴影圈
   的格子），卡片全程保留自己的阴影。这要动 shader 与材料层，还没做。

## 2026-09-17 跨 Surface 交接：提交不等于上屏

把阴影还给卡片的时机要等**粒子 Surface 的空帧真的上屏**，不是等 `eglSwapBuffers` 返回。
`eglSwapBuffers` 只把帧交给合成器，屏幕上还会停留一两帧旧画面；提交即通知会让卡片的阴影与仍在
屏上的旧帧叠成两层，观感是「先深一点、再回落到正常」。

判据用 `ParticleWindowSurface` 现成的两条：`surfaceDirty` 为假（最后一次提交是空帧）+ `pending`
为空（所有帧已判定上屏，`resolvePresented` 走 `ParticleFrameTimestamps` 并带超时上限）。通知点
放在 `resolvePresented` 末尾，`needsWork()` 要把待办队列算进去，否则 GL 线程会在还欠一次通知时
休眠。实测这一改把 dispose→通知从 17 ms 变成 49–51 ms。

**这条适用于任何「View 层与独立 Surface 之间交接画面」的地方**：判定要用呈现时刻，不能用提交
时刻，更不能用估出来的固定延时。

## 2026-09-17 全部撤回（阴影这一整段作废）

用户裁定撤回围绕 elevation 阴影的全部改动，代码回到 `88e570bb`。**上面所有以「阴影」为题的
决策条目一律作废**，保留在此仅作为"走过哪些路、各自死在哪里"的记录：

| 路线 | 死因 |
|---|---|
| 替身层（独立 View 投影） | 阴影停在原地不跟粒子走；卡片消散后露出系统画在 outline 内部的东西 |
| 阴影烤进快照 | 粒子变粗；交接那一帧跨 Surface 无法同帧（最终卡在这里） |
| 只投影 + elevation 固定时长动画 | 快速滑动来不及，粒子散了阴影还在 |
| 只投影 + 阴影强度绑消散进度 | 快速滑动时进度一帧跳过整段曲线，阴影仍是突变 |

仍然成立的**平台结论**（与路线选择无关，将来任何方案都用得上）：

- 阴影绘制只看 RenderNode 的 alpha、z 与 outline，与 display list 内容无关；
- 离屏渲阴影必须 `Canvas.enableZ()` 包住 `drawRenderNode`，否则一点阴影都没有且不报错；
- 光源五项是主题属性且 `lightZ` 要乘 `zWeightedAdjustment`（`ThreadedRenderer.setLightCenter`）；
- 要临时关掉阴影改阴影颜色，不要改 `elevation`（按压反馈与抬 Z 的算式都会抢它）；
- 跨 Surface 交接的判据要用「呈现时刻」（`resolvePresented`），`eglSwapBuffers` 返回不等于上屏；
- 密排列表里量阴影只能用朝向空白区的那条边，相邻卡片的阴影必然叠上来。
