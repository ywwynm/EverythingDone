# 附件复用与按需传输实施

状态：实现、本地测试及三台指定设备模拟验证全部通过，已发布阿里云 debug `202610151736`，远端产物核对一致。

## 已完成的实现与本地检查

- 新增 `TapFileTransfer`：版本 2 TCP 传输先发送记事 JSON 和逐附件类型、大小、完整 SHA-256，再接收缺失编号，仅发送所需内容。按内容建立索引，与文件名和序号无关；同内容的新附件只传一次，额外条目在本地复制以保持独立外观引用。
- `ThingFileWriter.prepareTransfer` 共用原记事序列化，不再预先写完整 ZIP；独立 `.edthing` 导出仍完整打包。
- `TapReceivedPayload` 明确来件所有权。`ThingFileReader` 校验协商描述和复用文件，`ThingFileImporter` 跳过借用文件的移动，`ThingFileUpdate` 只将新文件纳入失败删除集合；写入前再次检查文件状态。
- 详情接收从当前编辑快照取得候选文件并纳入历史保护；首页接收无候选文件，仍完整接收新内容。普通和接收方建组的传输均使用相同协商逻辑。
- 新增 9 项本地协议测试已通过，覆盖重排、同大小不同内容、混合变化、重复内容、缺失、损坏／截断、错误请求及复用文件变化。
- 全量测试发现既有 `TapReceiverServerTest` 在 Windows 上可能把拒绝连接的 TCP RST 当成失败；错误方向的前导被早期拒绝后，EOF 和 RST 均表示关闭。测试改为接受这两种关闭，仍检查三次拒绝计数和之后合法连接成功，没有修改生产身份校验。
- 在独立工作树基于 `f63669e2d` 构建，只复制本次功能改动，排除主工作区其它功能未提交修改。设备与发布都使用该产物。

## 本轮范围

- 两端均升级，碰一碰先传元数据与完整内容摘要，接收方只请求本地缺失的附件内容；独立记事文件导出保持自包含。
- 在当前记事全部附件中按内容匹配，与文件名及顺序无关；匹配后保留本地路径、修改时间及有效 GIF。附件数量、顺序与外观仍按收到的版本更新。
- 相同内容的多个条目保持独立外观引用，避免多个条目被映射成同一路径后互相覆盖设置。
- 接收文件校验、失败清理、借用文件保护及撤销／重做一并验证。
