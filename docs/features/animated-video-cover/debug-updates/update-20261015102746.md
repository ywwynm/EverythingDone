## 修复跨全列表拖动时其它卡片占位空白

用户补充复现条件：列表包含大量长清单、图片、视频及 GIF，一次拖动跨越整个列表，必须在拖动过程中正确显示其它卡片，不能只检查停滚后的画面；同时排查卓易通可能存在的内存限制。

已在三星、OPPO、魅族复现。原拖动源控件离屏后被 RecyclerView 复用给其它记事，`ThingListOverlayDragController` 仍因 View 引用相同将它当作源占位设为透明。空白样本的 GIF 已加载并播放，普通清单也受到影响。修复为始终核对控件当前绑定的稳定 ID，结束拖动恢复原 View 时也核对身份。

最小回归修复前失败、修复后通过。三台设备各使用 97 张混合卡片、80 张媒体完成不松手的全列表往返，共 1128 次采样确认列表仍在移动，没有透明、像素疑点或请求失败样本；每机 48 张动图均记录到帧变化，原源项占位与取消恢复正常。1496 项 JVM 测试 0 失败、1 跳过。

另做三机 3–4 程连续拖动和低截图频率内存对照，未观察到 GIF 后续加载失败或 OOM，缓存与活动资源没有按访问数量累加。但总内存偏高，卓易通实际限制仍未测量，本次没有据推测改变 GIF 质量、自动播放或缓存策略。第一条“完成、恢复后删除了另一条记事”的报告仍未复现；既有六组身份流程测试通过，导入时会重新分配本地 ID，未改动相关删除逻辑。

测试在独立包中完成，三台设备原应用数据库与设置校验和一致，独立包已卸载。正常包构建与测试媒体隔离已核验；发布后另行校验远端更新元数据和 APK。
