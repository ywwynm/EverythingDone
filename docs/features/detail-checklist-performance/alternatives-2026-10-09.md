# 2026-10-09 保留复杂详情页的替代方案

状态：方案分析，未修改应用实现，未做候选方案的真机性能验证。首轮诊断数据见 [实测报告](analysis-2026-10-09.md)。用户明确不接受整页改成一个 RecyclerView，本报告替代首轮的根列表建议。

2026-10-10 补充：[提交历史核查](history-2026-10-10.md) 确认详情一直保留 RecyclerView。9 月改用 LinearLayout 的是记事卡片预览；详情的相关历史调整发生在折叠、测量与焦点处理，不能通过回退卡片改动解决本问题。

## 结论

可以保留图片/视频、标题/正文、清单、音频及底部信息的独立布局。当前值得考虑的两条路线是：

1. **优先做局部因果验证：按外层视口管理清单行的可见性。** 保留当前 NestedScrollView、清单完整高度和每行实际高度，使远离视口的非活动行暂时不可见，检验能否消除已测到的系统区域追踪负担。这主要针对滚动，不能解决全量创建带来的打开成本。
2. **如需同时解决打开、展开与更大规模清单：采用连续嵌套滚动。** 只让清单 RecyclerView 在有界视口内回收，其它区域保留现有布局；外层协调滚动顺序和惯性。需要扩展或替换当前滚动协调层，并非仅开启 nested scrolling。

优先验证第一条，是因为它直接对应已测热点且保留现有几何关系，并不意味着已经确定它能作为最终方案。若兼容性或收益不达标，应转向第二条，不不断叠加临时隐藏规则。

## 已有证据与历史约束

- 展开时 151 个清单行全部挂载；干净滚动样本 43 帧中 38 帧超时，另一次系统追踪得到相近结果。约 3 秒追踪中，系统避让区域和手势排除区域消息合计占用主线程约 1,459 ms；同期没有清单创建、绑定或布局切片。
- 从首页打开时，首次 traversal 约 252 ms；折叠状态也创建全部 57 个清单行。另有同步音频时长读取与绑定触发的无效撤销快照。
- 折叠状态的两组滚动未复现同等级别卡顿，该用户反馈仍待继续复现，不能据此宣布问题不存在。
- [2026-05-26 详情测量决策](../popup-picker-insets/decisions.md) 已记录：不要在 LayoutManager.onMeasure 中创建/绑定编辑行，也不要估算屏幕外清单行高。曾出现抢焦点、与移除竞争及高度不稳定的问题。本次不能为了回收重复引入这些做法。

## 路线一：保留真实高度，管理屏外行的可见性

### 工作方式

继续由 NestedScrollView 滚动整页，清单保持全高布局。布局完成后使用已有行的真实位置计算与外层视口的交集，并留出上下缓冲区：

- 视口及缓冲区内的行保持 VISIBLE。
- 远离视口、没有活动交互的行设为 INVISIBLE，保留占位及实际测量高度。不能使用 GONE，否则会改变内容高度和滚动位置。
- 焦点行、输入法组合文本所在行、选区/操作菜单所在行、拖拽代理和正在播放结构动画的行始终保持可见；待聚焦目标先恢复可见，再执行滚动与聚焦。
- 只处理进入/离开缓冲区的行，不在每次滚动时重新绑定、全量通知适配器或改写行高。结构修改和布局期间暂缓计算，完成后重新获取位置。
- 行离屏不改变模型、完成状态或折叠状态。所有 holder 仍存在，现有依赖首尾 holder 的子树边界计算可继续使用实际几何信息，但仍需回归动画和拖拽交互。

这与已有的画布裁剪不同。Android 15 上游的 ViewRootRectTracker 和 HandwritingInitiator 都会排除不满足 isAggregatedVisible 的视图；仅因父容器裁剪而离屏，并不等价于 View 的可见性变成 INVISIBLE。设置 INVISIBLE 还会清理显示列表，因此存在降低位置回调和追踪集合规模的具体依据。[区域追踪源码](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android15-release/core/java/android/view/ViewRootRectTracker.java)、[手写区域追踪源码](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android15-release/core/java/android/view/HandwritingInitiator.java)、[View 源码](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android15-release/core/java/android/view/View.java)。

这是基于上游源码及设备热点提出的可证伪假设。Flyme 实现、行动画和可见性切换本身的成本仍需同机对照，不能直接等同于修复结果。

### 必须处理的功能边界

| 场景 | 保留条件 |
| --- | --- |
| 输入、光标和选区 | View 变为 INVISIBLE 会清除焦点和无障碍焦点；因此不得隐藏正在编辑或操作的行。要覆盖中文组合输入、长按选择、复制粘贴、滚出后返回 |
| 回车、退格、转换和撤销 | 插入、合并、清单/正文转换以及撤销后产生的目标行先恢复可见，再执行原有聚焦逻辑；隐藏不能改变一次操作的撤销粒度 |
| TalkBack 与硬件键盘 | 隐藏会影响屏外项目的导航可达性。需要主动恢复导航目标，或在相关辅助导航模式下停用这项优化；不能只验证触屏后宣布全部功能保留。停用时性能收益也不成立 |
| 拖拽与动画 | 当前拖拽项、收束/还原动画相关行不隐藏；自动滚动仍走原外层容器。快速跨屏、同级/同父限制和完成区边界需要回归 |
| 截图分享 | 利用 ScreenshotHelper 现有准备/恢复阶段，导出时临时恢复适配器中全部行的可见性，结束或异常后恢复原状态。保持已完成区当前折叠规则，不因优化遗漏内容 |
| 快速惯性滚动与键盘尺寸变化 | 在进入视口前恢复行；缓冲区跟随真实视口变化。不得出现空白、闪现、光标跳动或滚动锚点改变 |

### 能解决与不能解决的部分

- 目标是减少滚动期间实际参与位置/区域追踪的编辑行，验证系统消息耗时和帧回调排队能否显著下降。
- 全量行对象和高度仍保留，内存以及首次创建/测量仍随清单规模增长。不能把它描述成已经实现视图回收，也不能承诺解决打开慢或首次展开停顿。
- 若为兼容功能而必须频繁恢复大部分行，或切换可见性产生新的布局/焦点成本，收益可能不够，应以实测决定是否采用。

## 路线二：清单回收视图，外层协调连续滚动

### 页面组织

```text
外层连续滚动协调容器
  顶部：现有媒体、标题/正文等区域
  清单：有界高度的 RecyclerView，保留原清单数据与交互规则
  底部：现有排序入口、音频、时间与文件夹等区域
```

给清单一个受可用屏幕高度约束的视口，使 LinearLayoutManager 真正只维护附近的行。向下浏览时，外层先滚动顶部内容，随后由清单消耗滚动距离，清单到末尾后外层继续显示底部内容；反向手势及惯性也按同一顺序协调。短清单按内容实际大小展示，不强留整屏空白。

用户仍连续浏览整页，不需要把手指移入一个固定面板才能继续滚动。实现不能只是设置 maxHeight 和 nestedScrollingEnabled，否则父子容器的消费顺序、剩余惯性和跨区手势仍可能不一致。

这类组织已有公开实现可以参考：[ConsecutiveScroller](https://github.com/donkingliang/ConsecutiveScroller) 支持普通控件和多个可滚动控件连续滚动；[QMUI 连续嵌套滚动](https://raw.githubusercontent.com/Tencent/QMUI_Android/master/qmui/src/main/java/com/qmuiteam/qmui/nestedScroll/QMUIContinuousNestedScrollLayout.java) 具有组合滚动距离、统一滚动入口和上下区域协调。这些资料仅证明路线可行，尚未验证与本项目的多级编辑清单兼容。

不直接建议引入现成依赖：检索时 ConsecutiveScroller 最新发布为 2023-02-08 的 4.6.4，仓库最近代码推送为 2023-03-28；需要独立评估 Android 15、RecyclerView 1.4.0、编辑焦点及自定义拖拽。参考滚动协调思路与直接采用库是不同决策。

### 对现有代码的实际影响

| 区域 | 改动与保留要求 |
| --- | --- |
| 外层滚动接口 | 当前多个位置直接使用 NestedScrollView 的 scrollY、scrollBy、smoothScrollTo 和监听。应收敛到统一滚动入口，分别处理顶部、清单和底部的当前位置；不能继续把外层 scrollY 当作整页逻辑位置 |
| 清单布局 | 去掉禁止竖向滚动的布局管理器；清单视口有界，正常使用行回收。普通布局不需要预先估算全部屏外行高度，也不在 onMeasure 中创建编辑行 |
| 编辑状态 | 为条目建立可靠身份，维护焦点、光标、输入法组合状态和待聚焦请求。现有 findViewHolderForAdapterPosition 不能再假定目标总已挂载 |
| 子树拖拽 | 完成区和 owner 边界仍依据模型；跨屏子树的首尾 holder 可能不存在，必须调整 fingerPastSubtreeMid。自动滚动通过协调层消费距离，并正确补偿拖拽位置 |
| 媒体与页面反馈 | 图片/视频和音频不必迁成列表行。自动播放继续以真实可见范围判断；滚动监听、工具栏阴影、回到顶部、键盘避让和滚动恢复需要接入协调层 |
| 长截图 | 现有一次 draw 全高 ScrollView 的方式不再覆盖被回收行。需专用完整布局导出或分段导出，并完整恢复编辑、滚动和媒体状态；不能只截当前挂载行 |

这条路线可以从根本上限制打开时创建的清单视图数，也能减少滚动时同时存在的编辑框。代价是滚动协调和回收状态适配，工作量明显大于路线一，但页面其它内容无需改成 RecyclerView item。

## 可以独立进行的打开与结构更新优化

以下措施对两条路线均适用：

1. 在绑定期间同时阻止 beforeTextChanged 和 afterTextChanged 生成撤销记录；文本未变化时避免 setText。首轮采样已确认绑定触发整份清单序列化。
2. 添加入口、分隔线和完成区标题改用轻量独立布局，避免为控制行创建完整 EditText。
3. 对明确的结构操作发送准确的插入、移除和局部变更，减少 notifyDataSetChanged；保持子树迁移、一次撤销和动画语义。完成区边界在结构变化时更新，避免重复扫描。
4. 音频时长在后台读取并按文件身份和变更信息缓存，绑定不再同步读取媒体文件。

这些改动有已观测成本依据，但只是打开和展开成本的一部分，不能替代视图数量控制；采样耗时也不能相加作为预期端到端收益。

## 不作为优先方案的路径

- **自定义 LayoutManager，根据外层视口回收但保持全清单总高度。** 多行编辑文本的高度随宽度、缩进、字体和内容变化。要保持全高就需要准确知道未测行的高度，或引入估算和后续纠正；本项目已有这类高度及焦点问题的历史。复杂度和风险并不比连续滚动低。
- **关闭自动手写。** Android 15 TextView.shouldTrackHandwritingArea 还可能因 handwritingUnsupportedMessage 标志继续追踪可编辑视图；仅设置 autoHandwritingEnabled=false 未必消除热点，同时会关闭触控笔直接书写能力。不能把它作为“保留全部功能”的修复。[TextView 源码](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android15-release/core/java/android/widget/TextView.java)
- **只改画布裁剪、透明度、缓存或嵌套滚动开关。** 没有解决已确认的挂载编辑框数量与平台追踪路径。隐藏 API 或反射取消平台消息也不适合作为跨系统版本的维护方案。

## 验证顺序与决策标准

1. 本轮先完成方案分析，不修改应用。后续开发先单独验证路线一的可见性假设，避免混入其它改动后无法归因。
2. 使用同一设备、记事、折叠/展开状态和往返手势，分别测干净帧、上屏间隔、主线程区域消息耗时、布局/绑定次数；确认改善没有转化为闪白或焦点问题。不在方法采样开启时比较帧率。
3. 保留原文、层级、完成态和撤销结果的对照，覆盖输入法组合、离屏再返回、回车/退格目标、辅助导航、跨屏子树拖拽、折叠动画和长截图。路线一失败时移除该实验，不把损失功能当作可接受的性能收益。
4. 独立比较绑定和音频优化对打开路径的收益。如果全量创建仍是明显瓶颈，或更大规模样本要求首次打开也随视口而非总项数增长，再实施路线二。
5. 路线二另用非用户正文的 54 / 148 / 512 项、多层级和多行文本样本验证挂载数量受视口约束，并覆盖滚动跨区、反向惯性、动态附件高度和键盘变化。辅助功能使用不同路径时单独报告性能，不能与普通触屏混成一项结果。

目前只有原始问题的真机数据，尚无上述任一候选方案的修复后数据。
