状态：本轮源码与真机诊断完成；未修改应用代码，未编译、安装或发布。原始转储与采样位于本地忽略目录 `tmp/detail-checklist-diagnosis/`。

## 复现与假设

设备 `192.168.100.67:42641`，魅族 20 Infinity，系统属性报告 Android 15；应用 2.0.0 / 43，最近安装时间 2026-10-09 12:55:27。样本是用户指定第一项为「右滑记事的动画优化」的记事。

按优先级验证：

1. 外层 `NestedScrollView` 与全高、不自行滚动的清单列表导致全量行创建、绑定和测量；展开后视图数与耗时应上升。
2. 行绑定内重复文本处理及整份清单撤销快照扩大首帧和全量刷新成本。
3. 大量可编辑行引发滚动期间的视图、输入和系统区域追踪成本。
4. 动态附件播放增加负载；需要与附件已经离开视口的滚动区别。

## 已确认事实

- `activity_detail.xml` 外层为 `NestedScrollView`；清单 `RecyclerView` 为 `wrap_content`，布局管理器禁止自行竖向滚动。
- 初次打开默认折叠底部已完成区，适配器确实通过 `getItemCount` 排除了这 94 项，不能说折叠只是隐藏像素。
- 折叠时挂载 57 个清单行布局：54 个真实项与 3 个控制行；列表高 9,432 px，滚动视口高 2,908 px。
- 展开时挂载 151 个清单行布局：148 个真实项与 3 个控制行；列表高 29,133 px。每个控制行也使用含 `EditText` 的完整编辑布局。
- 首次展开出现约 746 ms 帧，其中布局阶段约 698 ms。展开后 6 次快速往返滚动的独立采集中，43 帧里 38 帧超过截止时间，帧完成耗时中位约 40 ms；主线程帧回调本身约 0.8 ms，大头是回调开始前的排队，不能归结为每帧重新布局整份清单。
- 初次打开、尚未展开的折叠状态，慢速及快速滚动样本未复现同等卡顿。展开后重新折叠、再做 6 次往返手势，也未复现同等卡顿；不能把这一结果扩展成“折叠时一定不卡”。
- 展开滚动的独立 ART 1 ms 采样指向系统 `ViewRootRectTracker` 与 `HandwritingInitiator`，而非清单解析或持续行绑定。采样具有扰动，仅用于归因，不能当作干净帧耗时。

## 根因一：长清单没有按视口回收，持续触发系统区域追踪

当前结构：

```text
NestedScrollView（整页纵向滚动）
  LinearLayout
    图片/视频列表
    标题/正文
    RecyclerView（清单全高、禁止自行竖滑）
      所有展开中的行，每行带 EditText
    排序入口、音频列表、时间与文件夹信息
```

源码位置：`activity_detail.xml:12,71`、`DetailActivity.kt:1105,5884`。问题不是“只要嵌套就必然卡”，而是这个组合把清单高度扩展到所有可展示项的总高度，屏幕外清单行也一直挂载。真机视图树直接证实了 57 / 151 行和 9,432 / 29,133 px 的差别。

展开滚动的约 3 秒系统追踪里：

- `MSG_KEEP_CLEAR_RECTS_CHANGED` 9,513 次，合计 968.1 ms。
- `MSG_SYSTEM_GESTURE_EXCLUSION_CHANGED` 9,513 次，合计 491.1 ms。
- 两者合计约 1,459.2 ms，已足以明显挤占主线程；同期 74 次 traversal 合计只有 181.7 ms。
- 同一窗口没有清单 `RV onCreateViewHolder`、`RV onBindViewHolder` 或 `RV OnLayout` 切片，不支持“滚动时不断重新解析/重绑清单”这个解释。

独立方法采样对应到 `View.updatePositionUpdateListener` 的回调、`ViewRootRectTracker.computeChanges/updateRectsForView` 和 `HandwritingInitiator`。Android 15 上游实现中，视图位置更新会把相关回调放到主线程消息队列前方，再更新系统手势排除、避让和手写输入区域；区域追踪内部又遍历已登记视图。大量挂载的编辑视图一起移动，会放大扫描和消息成本，即使区域列表本身为空也可能仍有追踪工作。

这里的直接证据是设备实际出现的大量系统消息与方法热点；上游源码用于解释机制，并不假设 Flyme 与 AOSP 每一行代码完全相同。复杂度可能表现出接近平方增长，但本轮仅测试 57 / 151 两个规模，不声称完成了系统级复杂度基准。

折叠确实减少挂载行数，重新折叠也能恢复本轮滚动表现。因此没有证据表明“折叠无效”或“已完成项折叠后仍全部挂载”。但剩余 54 个真实项仍全量挂载，架构问题依旧，折叠状态下的其它卡顿触发条件尚待补充。

## 根因二：打开、展开及结构更新集中执行全部行的工作

`CheckListAdapter.onCreateViewHolder` 对编辑行、添加行、分隔行、已完成头都加载同一份 `check_list_et.xml`。控制行同样创建 `EditText`、多个图标和监听，之后再隐藏无用部分。

从首页打开的系统追踪共出现 60 次 RecyclerView 行创建、60 次绑定，分别合计约 91.9 / 72.1 ms；这里包含 57 个清单行、1 个视频行、2 个音频行，不能把 60 次全算成清单。整个首次 traversal 约 251.5 ms，清单全部行创建和布局是主要成本。

独立打开方法采样中，清单创建约 102.6 ms、清单绑定约 39.3 ms。采样还捕获到两类次要开销：

1. `beforeTextChanged` 无条件序列化整份清单。绑定 `setText` 时，虽然 `mWatchEditTextChange=false`，但保护只检查在 `afterTextChanged`，前置撤销快照仍执行。对应 `CheckListAdapter.kt:341,364,376,817`，生产序列化见 `CheckListHelper.kt:201`。采样中此路径约 9.2 ms；全量绑定会形成“每行绑定再扫描全清单”的重复工作。
2. `AudioAttachmentAdapter.kt:99` 在绑定时同步调用 `FileUtil.getMediaDuration`。两段音频的时长读取采样约 30.2 ms，是打开这条具体记事的独立负担，不能全部归到清单。

已完成折叠、完成切换、缩进、增删等结构变动最后走 `notifyChecklistStructureChanged → notifyDataSetChanged`（`CheckListAdapter.kt:544`），重新绑定整个可展示区域。展开既创建新行，又重绑既有行，解释了首次展开的明显停顿。`getVisibleEditTextItemCount` 还在每次查询时 `indexOf("4")` 扫描分界，宜缓存到结构变更时更新，但其优先级低于全量视图和系统追踪问题。

## 首轮建议（已撤回）：整页按视口维护行视图

以下保留为首轮方案记录，不作为当前实施方向。

不建议仅切换 `nestedScrollingEnabled`、增加缓存、固定列表高度或换成另一种 ScrollView；这些没有解决清单所有行一直挂载的问题。也不建议靠关闭手写、选择或辅助功能消除系统回调：这会改变功能，且没有处理首屏创建成本。

推荐详情采用一个真正承担整页纵向滚动的 `RecyclerView`，清单每行都是根列表的一个 item。标题、媒体区、清单、排序入口、音频区和底部信息可通过多种 view type / 分段 adapter 组织。可使用现有 RecyclerView 1.4.0 的 `ConcatAdapter`；清单子 adapter 的位置与全局位置必须明确转换。不能把整份清单塞进根列表的一个巨大 item，否则仍然全量创建。

媒体区可以先作为少量独立区块保留原有网格与内部拖拽，控制本次改造范围；是否进一步将每个媒体格子也纳入根列表、使用统一网格 span，需单独核对附件布局复杂度。两条路径都必须保持详情原有整页滚动体验，不引入固定高度的清单内外双重滚动。

配套先做几项局部优化：绑定期间同时抑制 before/after 撤销记录；仅在文本变化时 `setText`；把控制行改成轻量的独立类型；结构变动发送准确的插入、移除、移动和局部样式更新；缓存完成区边界。它们能减轻打开和操作成本，但不能替代根列表按视口回收。

音频时长可以在后台读取并按文件身份及变更信息缓存，绑定时复用；它是可独立安排的第二优先级事项。

## 首轮建议的实施顺序和验收（已撤回）

1. 先补真实编辑语义回归，明确条目身份、焦点与待聚焦请求；修正绑定期间的无效整份快照，区分控制行类型。
2. 改为根列表按视口回收，完整迁移焦点、拖拽、自动播放和分享；未覆盖这些依赖前不把简单换布局当成完成。
3. 以同一真实记事复测打开、展开/折叠、连续滚动，并用不包含用户正文的 54 / 148 / 512 项结构样本验证：挂载数量应受屏幕容量约束，不随总项数等比例增长。
4. 测试屏幕外新增目标、跨屏子树拖拽、重复文本、中文输入法组合、输入中滚出再回来、撤销重做、退出重新打开、旋转/恢复与长截图；按原有纯函数回归对照保存结果。
5. 对比干净帧、上屏间隔和系统区域消息总耗时；只报告实测改善，不从视图数或算法复杂度推算帧率收益。折叠状态下用户感知的其它卡顿仍保留为待复现事项。

以上是建议，尚未实施，也没有修改数据库或现有功能语义。
