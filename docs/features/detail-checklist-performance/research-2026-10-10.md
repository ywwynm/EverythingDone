# 长清单嵌套滚动调研与现代 Android 布局建议

调研日期：2026-10-10。范围为官方文档、AndroidX 发布源码、第三方组件源码与原始问题报告。本轮没有修改应用代码、测试第三方组件或重新操作设备。

## 结论及适用范围

- 长列表与其它内容共同组成一个连续滚动页面时，优先由一个有界的纵向容器按需创建、布局和回收条目。复杂模块仍可独立实现，统一滚动并不要求统一模块内部布局。
- 新页面采用 Compose 时，对应 `LazyColumn` 的 `item` / `items`；现有 Views 页面对应多类型 RecyclerView，必要时用 `ConcatAdapter` 拼接独立 Adapter。
- 用户此前明确不接受整页 RecyclerView 改造。本次因用户进一步询问现代最佳实践，解释这种架构的适用性及实际成本；这不是用户已接受该改造，也不改变先分析、保留全部功能的约束。
- 若继续保留各区域独立布局及清单独立 RecyclerView，可采用有界清单与连续滚动协调容器。这是需要自行维护和验证的折中方案，不能通过一个 NestedScrollView 属性获得。
- 前次提出的屏外非活动行 `INVISIBLE` 仅为局部性能假设，不是真正回收，也不是长期架构建议；它不解决初次全量创建。

## 问题不在“出现嵌套”本身

本项目当前是 NestedScrollView → LinearLayout → `wrap_content` 清单 RecyclerView，清单 LayoutManager 禁止自身竖向滚动。前次实测展开时全部 151 行挂载，说明清单获得了完整内容高度，而非屏幕内的有限视口。

检查 Google Maven 发布的 `core:1.13.1` 与 `recyclerview:1.4.0` 源码：NestedScrollView 测量直接子内容时使用纵向 `UNSPECIFIED` 约束；LinearLayoutManager 在无限布局条件下会持续填充，并跳过相应滚动回收路径。具体条件还受中间布局、测量模式和尺寸影响，不能概括为任何嵌套都会禁用回收。给子列表真实的有限高度，并让它实际处理内部滚动，可以保留回收。

源码归档来自 [AndroidX Core 1.13.1](https://dl.google.com/dl/android/maven2/androidx/core/core/1.13.1/core-1.13.1-sources.jar) 与 [RecyclerView 1.4.0](https://dl.google.com/dl/android/maven2/androidx/recyclerview/recyclerview/1.4.0/recyclerview-1.4.0-sources.jar)。本项目直接声明上述版本；本轮未运行 Gradle 核实 Core 的最终传递依赖解析版本。

截至调研日，官方列出的 RecyclerView 稳定版仍为 1.4.0，本项目已使用该版本。发布说明未提供“保持完整内容高度，同时自动按祖先可见区域回收”的修复或开关。[官方发布记录](https://developer.android.com/jetpack/androidx/releases/recyclerview)

| 常见建议 | 实际作用与限制 |
| --- | --- |
| `nestedScrollingEnabled=false` | 影响嵌套滚动协作，不把完整内容高度变成有限视口。 |
| `fillViewport=true` | 让不足一屏的内容至少填满视口，不是给长清单设置最大高度。 |
| `setHasFixedSize(true)` | 声明 Adapter 内容变化不改变 RecyclerView 自身尺寸，不是固定行高或开启回收；当前随内容改变整体高度的场景不能随意声明。 |
| 调整自动测量、缓存池或预取 | 不能单独消除已全部挂载的编辑行；自动测量本身仍可能需要按子项布局结果计算尺寸。 |
| 给清单设置有限高度 | 可以建立真实视口，但若仍要求整个页面连续滚动，还要协调父子滚动、惯性、焦点和滚动定位。 |

依据：[NestedScrollView API](https://developer.android.com/reference/androidx/core/widget/NestedScrollView)、[RecyclerView API](https://developer.android.com/reference/androidx/recyclerview/widget/RecyclerView#setHasFixedSize(boolean))、[LayoutManager 自动测量](https://developer.android.com/reference/androidx/recyclerview/widget/RecyclerView.LayoutManager#isAutoMeasureEnabled())。以上是结合 API 职责及源码的判断，不是对所有自定义布局的绝对限制。

## 现代布局如何承载当前页面

Compose 官方明确建议：同向可滚动父容器里，不应嵌入无固定高度的 LazyColumn；头部、不同内容和底部可以通过一个 LazyColumn 的 DSL 组织。具有明确高度的同向嵌套、不同方向的嵌套属于另一类场景。[官方列表指南](https://developer.android.com/develop/ui/compose/lists#avoid-nesting-scrollable)

在现有 Views 体系中，可以将各区域保留为独立布局或 Adapter，由 `ConcatAdapter` 顺序组合，交给一个占据页面可用高度的 RecyclerView。官方 ConcatAdapter 负责类型隔离与条目通知的位置偏移；它不会自动迁移业务代码中的位置计算、焦点或状态。[官方 ConcatAdapter 文档](https://developer.android.com/reference/androidx/recyclerview/widget/ConcatAdapter)

| 当前区域 | 统一纵向容器中的组织方式 |
| --- | --- |
| 图片、视频附件 | 保留媒体组件；按布局拆分条目，或将数量有界的区域作为独立模块。横向轮播可保留独立横向容器。 |
| 标题、正文 | 各自作为独立编辑模块，保留现有 EditText 的样式与行为；特别长的单段正文仍可能有独立排版成本。 |
| 多级清单 | 根据层级与完成区折叠状态生成可见行，每一项独立回收；缩进表达层级，不递归嵌套纵向列表。 |
| 添加、折叠、排序等入口 | 作为轻量控制条目，避免无文本编辑需求的控件也使用完整编辑行。 |
| 音频与信息区 | 分区 Adapter 或不同类型的条目；可能大量增长的音频行同样逐条参与回收。 |
| 固定工具栏与浮层 | 保留在纵向容器外，由根布局管理。 |

不能把整份清单包成一个巨大 item；这样该 item 出现时仍需创建所有清单行。这里的目标是每个可重复增长的清单项独立参与按需布局，而不是仅替换外层控件名字。

这个方案不要求改成“普通列表”的外观。原有间距、背景和模块内部复杂布局可以保留；实际迁移成本集中在依赖具体 View、滚动容器和位置编号的逻辑。

### 保留交互必须解决的事项

1. **编辑与状态**：文本、选区、焦点目标按稳定条目标识管理，不能依赖 ViewHolder 永久存在；绑定、回收和焦点恢复不得打断组合输入或产生无效撤销记录。不能简单把所有编辑行设为不可回收。
2. **层级及完成态**：沿用清单数据规则，由展示行映射处理展开、折叠与缩进；底部已完成区和留在父项下的已完成子项应保持现有语义。
3. **拖拽**：子树代理、跨屏自动滚动和边界判断适配真实回收；避免假定子树首尾 ViewHolder 总能找到。使用 ConcatAdapter 时区分分区内位置与页面位置。
4. **滚动与媒体**：滚动定位、输入法避让、顶部栏更新、视频可见性监听等改接新的滚动来源，媒体播放状态不能随条目回收而意外重置。
5. **完整截图**：原有直接绘制完整 NestedScrollView 的方式需要独立导出方案或分段渲染，保持完整内容与输出样式；不能为了截图长期挂载全部编辑行。

详细现状及行号见 [原始诊断](analysis-2026-10-09.md) 与 [交互保留条件](alternatives-2026-10-09.md)。换容器不会自动完成以上适配，尚无实现或回归验证结果。

## 保留独立清单区域：连续嵌套滚动

可行机制是让外层负责各区域之间的滚动衔接，清单本身高度受限并实际消费滚动距离。清单到达起止边界后再继续滚动上方或下方内容，而不是先把所有清单行展开成整页高度。

### QMUI

[QMUIContinuousNestedTopDelegateLayout 源码](https://github.com/Tencent/QMUI_Android/blob/master/qmui/src/main/java/com/qmuiteam/qmui/nestedScroll/QMUIContinuousNestedTopDelegateLayout.java) 提供 Header、Delegate、Footer 结构；测量时中间 Delegate 受到父容器高度上限约束。配合连续嵌套滚动布局与相应 RecyclerView，可以作为保留复杂前后区域的实现参考。

核查到 [Maven Central 最新发布为 2.1.0](https://repo.maven.apache.org/maven2/com/qmuiteam/qmui/maven-metadata.xml)，元数据最后更新为 2022-03-05；GitHub 的最新 Release 条目为较早的 2.0.1，不能混为一谈。仓库主分支提交 `026e7d486677d6593a96689cd590ec3561176717`，API 返回最近 push 日期为 2024-11-05，调研时未归档。

[问题 #1131](https://github.com/Tencent/QMUI_Android/issues/1131) 曾直接报告连续嵌套 RecyclerView 内逐行 EditText 的键盘遮挡或消失；报告针对 Android 10、QMUI 2.0.0-alpha10，调研时问题仍开放。它不证明 2.1.0 或当前源码必然有同样问题，但足以说明本项目最重要的编辑场景必须单独验证。

### ConsecutiveScroller

[ConsecutiveScrollerLayout 源码](https://github.com/donkingliang/ConsecutiveScroller/blob/master/consecutivescroller/src/main/java/com/donkingliang/consecutivescroller/ConsecutiveScrollerLayout.java) 在容器受限时向子区域传递高度约束，按区域分配滚动距离，并实际调用子列表滚动。它虽然也禁用部分子 View 的嵌套滚动协作，却不依赖将 RecyclerView 完整展开，进一步说明该开关不是回收与否的根因。

[最新 Release 4.6.4](https://github.com/donkingliang/ConsecutiveScroller/releases/tag/4.6.4) 发布于 2023-02-08；仓库 API 返回最近 push 日期为 2023-03-28，调研时未归档，主分支提交 `bad427106fa54044b22c632d9f3a7a546bd9f7e3`。需要注意其对子 View 边距、裁剪和滚动配置的管理；还有仅特定 tag 才启用的 RecyclerView 私有方法反射路径，不应无条件复制。

[问题 #95](https://github.com/donkingliang/ConsecutiveScroller/issues/95) 曾报告输入法弹出后没有正确露出输入框；[问题 #33](https://github.com/donkingliang/ConsecutiveScroller/issues/33) 的维护者曾说明不支持 ItemTouchHelper 场景，拖拽滚动可能冲突。两者均是旧版本报告；#33 后来关闭也不能单凭状态认定当前功能已修复。应把它们作为键盘和拖拽验证依据，而不是宣称新版一定失效。

### 对本项目的判断

- 这些实现说明连续嵌套滚动技术上可行，但不是 AndroidX 提供的开箱即用替换件，也没有证据保证兼容当前多级编辑清单。
- 即使保留外部模块，真实回收仍会改变清单 ViewHolder 的存活方式，因此编辑状态、子树拖拽、长截图适配成本依旧存在，另外增加父子滚动协调成本。
- `CoordinatorLayout + AppBarLayout + RecyclerView` 适用于可折叠头部与主体列表的组合；当前还有正文编辑、清单后方附件与信息区，不能只套入 AppBarLayout 就完整迁移。[官方 AppBarLayout 说明](https://developer.android.com/reference/com/google/android/material/appbar/AppBarLayout)

## 自研回收与统一 RecyclerView 的比较

用户进一步询问两者哪种更好。此处将“自研回收”理解为：保留外层 NestedScrollView 及清单完整占位高度，根据外层视口自行创建、移除和复用清单行。只隐藏屏外行、或使用有界 RecyclerView 而自行协调滚动，是不同方案。

**工程判断：在保留完整功能、改善打开和滚动、长期维护这几个目标下，优先评估统一 RecyclerView / ConcatAdapter；不优先自研完整回收机制。** 这不是两套实现的性能实测结论，也不是用户已选定方案。

| 维度 | 保留全高布局、自行回收清单 | 统一有界 RecyclerView |
| --- | --- | --- |
| 创建数量与内存 | 实现正确时也可只保留视口附近行；若先创建全部行测高，初次打开成本仍在 | 可直接复用已有按需创建及回收机制，避免为清单总高度预建所有行 |
| 多行文本与总高度 | 需要为未创建行提供占位高度，并处理宽度、缩进、字体和内容变化后的失效、补测与滚动位置修正 | 标准 LinearLayoutManager 可按可见区域布局和滚动，不要求预先知道全部行的精确高度 |
| 现有页面改动 | 清单外模块迁移较少，但清单测量、滚动位置、焦点和辅助功能等逻辑需要自行维护 | 页面接入改动更广；模块布局与业务可保留，但状态及滚动监听需要适配 |
| 编辑、子树拖拽、完整截图 | 真实回收会改变 View 的存活方式，不能因外层不变就省略适配 | 同样需要业务适配；现成组件不自动保留这些自定义行为 |
| 长期维护 | 除业务外，还需维护外部视口与布局、回收和变更更新的协调 | 复用 AndroidX 的通用能力，主要维护业务及状态映射 |
| 性能结论 | 专用实现存在优化空间，但没有证据证明优于标准方案 | 是更可靠的工程起点，不承诺未实测的帧率或启动耗时 |

所谓“大的 RecyclerView”是指它承载整页的滚动内容；其自身仍受页面可用高度约束，不应展开成整页内容的总高度。清单行仍逐条回收，ConcatAdapter 仅把独立 Adapter 的内容顺序组合。[官方回收说明](https://developer.android.com/develop/ui/views/layout/recyclerview)、[ConcatAdapter](https://developer.android.com/reference/androidx/recyclerview/widget/ConcatAdapter)

全高自研方案的核心难点是：音频与底部信息位于清单后方，外层 NestedScrollView 需要知道清单占位高度。对于尚未测量的多行文本，要么进行全量高度计算，要么先估算再校正，要么改为按局部视口消费滚动的模型。第一条保留部分随总项数增长的打开成本；第二条涉及本项目已有的高度和焦点问题；第三条则已经转向连续滚动协调，而非原样保持全高布局。

自定义 LayoutManager 可以复用 RecyclerView 的回收池等能力，不必重写全部基础设施；但它仍需要负责测量、定位及回收时机，并适配外层视口与更新、焦点、动画规则。[LayoutManager 的官方职责说明](https://developer.android.com/reference/androidx/recyclerview/widget/RecyclerView.LayoutManager)

建议顺序为：统一 RecyclerView / ConcatAdapter；若模块迁移有具体且显著的障碍，再评估有界清单 RecyclerView 加自研连续滚动协调；只有前两者无法满足明确交互要求时，才考虑自行维护全高虚拟布局。屏外行可见性方案仅是独立缓解实验，不能与真实回收等价比较。

## 当前建议

- **现代架构参考**：一个有界纵向懒加载容器，内部保持独立模块。这是对架构问题的回答，不将此前用户拒绝的整页改造自动恢复成已批准计划。
- **结合现有技术栈**：若后续愿意调整滚动结构，先评估 Views 与 ConcatAdapter 的可行性及迁移成本，不为这一处性能问题直接重写整个页面为 Compose。官方也支持现有 Views 项目的逐步迁移。[Compose 迁移策略](https://developer.android.com/develop/ui/compose/migrate/strategy)
- **保留独立区域的候选**：有界清单加连续滚动协调；须先验证变高 EditText、输入法、子树拖拽、完整截图，再决定是否借鉴第三方源码。
- **有限范围缓解**：屏外非活动行可见性、绑定期间撤销快照、轻量控制行及音频时长读取仍可单独研究，但不称为已解决列表回收问题。
