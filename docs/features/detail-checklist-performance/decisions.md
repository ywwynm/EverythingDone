# 决策

## 2026-10-10 — 用户批准编辑行减负与附件分阶段展示

- 实施每按钮 ripple 复用、直接应用最终行样式，独立测量首滑及绑定变化；先细分构造耗时，不预先承诺拆分行布局的收益。
- 用户确认上一版附件点击 ripple 已及时播放，但弹窗仍等待预览；要求先取得图像/视频尺寸等信息，按正确几何打开并播放现有粒子动画，同时异步加载媒体。
- 元数据读取也放到工作线程；弹窗尺寸沿用原计算，处理图片方向及视频方向。预览未就绪时保留取消，暂不允许裁剪、选帧或确认；完成后在原位置填入媒体，不重播动画、不重建整窗。
- 沿用已授权三机、原记事非破坏性测试与调试发布流程；原有私密认证测试继续等待用户之后配合。

## 2026-10-10 — 继续完成非平板遗漏

- 用户确认继续推进覆盖审计中的未完成项。平板存储限制不再作为停止其它性能优化和回归的理由；沿用三台设备授权及专用夹具保护要求。
- 首滑按已有实际追踪验证假设：编辑行首次创建、绑定/区域更新成本、启动期后台调度分别核查。先单独试验半个视口的邻近内容布局，比较首滑、打开耗时和挂载数量；无收益则撤回，不恢复此前无效的空闲 holder 预创建。

## 2026-10-09 — 先诊断，保留全部清单功能

- 本轮仅做源码与授权设备诊断，不修改、构建或发布应用。
- 诊断以真实记事的打开、展开/折叠和滚动为对象；性能指标区分系统追踪、干净帧和有扰动的方法采样。
- 后续优化不得减少清单数据或删减层级、编辑、拖拽、撤销等功能。
- 首轮曾建议把详情改为单一纵向列表，未实施；用户随后明确否决整页 RecyclerView 改造，该建议已撤回。

## 2026-10-09 — 保留页面各区域，评估两条局部路线

- 不再建议把页面其它内容迁成 RecyclerView item。
- 首选验证路线保留原 NestedScrollView 和清单完整高度，用真实行位置管理屏外非活动行的可见性，以验证能否降低系统区域追踪；必须保护焦点、输入法、辅助导航、拖拽和截图。它不是视图回收，不能独自解决全量创建成本。
- 更完整的候选方案是清单在有界视口内回收、外层负责连续滚动协调。它允许扩展或替换外层协调层，保留各内容区域，而非要求外层控件类绝对不变。
- 不采用估算屏外行高或在 onMeasure 中创建/绑定编辑行的做法；尊重 2026-05-26 相关问题的既有结论。
- 绑定撤销快照、控制行布局和同步音频时长读取可独立优化。
- 继续先分析；上述为建议和候选验证顺序，未将任何替代方案认定为已验证的修复。详见 `alternatives-2026-10-09.md`。

## 2026-10-10 — 区分现代架构建议与已授权范围

- 用户进一步要求联网调研与现代最佳实践。技术上，复杂模块可以共用一个有界懒加载容器；Views 可使用多类型 RecyclerView / ConcatAdapter，Compose 可使用 LazyColumn。页面复杂本身不是排除统一滚动容器的依据。
- 上述是架构分析，不表示用户撤销了此前对整页 RecyclerView 的否决，不启动应用改造。
- 连续嵌套滚动可保留独立区域，但有界清单的真实回收仍要求适配编辑、子树拖拽和长截图；第三方组件的旧版本问题报告提示必须验证，不能宣称直接接入即可保留全部功能。
- 屏外行 INVISIBLE 继续仅作为局部缓解假设，不作为长期架构或打开耗时的完整解决方案。项目已使用 RecyclerView 1.4.0，没有查到通过升级或配置开关修复现有完整高度布局的依据。
- 结论、原始来源和库版本核查见 `research-2026-10-10.md`；本轮不改变应用、不引入依赖。

## 2026-10-10 — 自研回收的方案评估

- 用户询问自行实现回收与统一 RecyclerView 的优劣，未指定采用其中任一方案。
- 工程建议优先复用统一 RecyclerView / ConcatAdapter；保留全高 NestedScrollView 的自研虚拟布局需要处理未知多行文本高度、占位、位置修正及回收交互，不能因外部模块改动少就视为整体工作量小。
- 若统一结构遇到具体模块迁移障碍，优先考虑保留 RecyclerView 回收能力、只自行实现连续滚动协调；这与自行管理清单行的完整回收是不同范围。
- 两种真实回收方案均需适配编辑、子树拖拽和长截图。没有性能对照结果，不宣称标准方案必然更快；本轮仍仅分析。

- 验收覆盖所有详情区域及跨区域行为；不能以清单回收数量、编译或少数交互通过代替全部功能回归。
- 不发布、不提交；应用改动留在工作区。无关的空间照片工作区改动保持原样。
