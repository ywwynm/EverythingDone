# 深度模型升级 PoC · 第一轮（桌面边缘质量）+ 第二轮（导出与真机）

日期：2026-08-01。目标（用户验收口径）：发丝左缘放大对比，halo/碎屑显著优于现有
双模型才算过。测试图为用户「测试空间效果」记事的真实弱光人像（1080×1440）。

## 环境与可复现性

- 环境：`build/spatial-model-poc/venv`（torch 2.12.1+cpu / onnx 1.22.0 / ort 1.28.0，
  与 Android Runtime 同版本 ort）。
- 基线推理：既有发布 ONNX（ZipDepth NPU 384 / DAV2-S 518），预处理与
  `SpatialDepthEngine` 一致（等比缩放 + 居中补边，输出去补边后放回原尺寸）。
- 候选安装：MoGe 与 DA3 均 `--no-deps` 安装核心 + 最小依赖补齐（跳过 gradio/open3d/
  xformers 等演示与训练依赖；DA3 的 xformers 为 try/except 软依赖，CPU 回退可用）。
  权重经 hf-mirror 获取。脚本在 `build/spatial-depth-poc/`（run_baselines / run_da3 /
  run_moge / make_sheet / measure_halo）。

## 量化结果：发丝左缘 halo 宽度（10%→90% 深度过渡，逐行统计）

目检（`out/test1_edge_sheet.png`）：DA3-SMALL 的深度梯度线细锐连续、贴合发丝轮廓，

成圆顶——**当前默认模型正是发丝碎屑带的最大贡献者**。

## 第一轮结论

- DA3-SMALL 在验收口径（发缘 halo）上比当前默认好一个数量级（98→9 px），比 DAV2-S
  好 3 倍，参数量与 DAV2-S 同量级、许可 Apache-2.0 可再分发——**晋级为第三深度模型
  首选候选**。
- MoGe-2 ViT-S 中位数与 DA3 打平（10 vs 9 px）但 P90 差一倍（94 vs 43 px），发缘
  尾部质量不如 DA3；朴素原生分辨率 CPU 跑法 403s 不代表其正常速度（内部未限 token），
  仅作参考。**第二轮以 DA3-SMALL 单候选推进，MoGe-2 留作导出受阻时的 MIT 备选**。
- 注意：34.3M 是加载出的单目分支参数；HF 卡标称 0.08B 含相机分支等，导出 ONNX 时按
  实际使用的分支计。桌面 1.0s 为原生分辨率；App 侧将按固定输入尺寸导出，真机耗时
  另测。

## 第二轮门槛与进展（2026-08-01）

原定四道门槛：① 固定尺寸导出 + 数值核对；② 算子并集核对；③ 真机耗时/内存 +
全链路发丝对比；④ 按 D7/D12/D13 发布。当前 ①② 已过，③ 推进中。

### ① 导出与数值核对 — 通过

- 导出脚本 `build/spatial-depth-poc/export_da3_onnx.py`：绕开 `da3.forward` 的
  天空/相机后处理（数据依赖控制流不可导出），只走 backbone + depth head；输入
  (1,3,518,518)、ImageNet 归一化（与 DAV2 同协议），输出 (1,518,518)。
- 唯一导出障碍：rope 位置生成的 `torch.cartesian_prod` 不可 trace，导出期间垫换为
  meshgrid+stack 等价实现（仅两参用法），导出后还原。
- 产物 `artifacts/da3_small_mono_518.onnx`：100,479,065 字节，opset 18，全部为
  ai.onnx 标准算子（36 种，无 contrib）。SHA-256
  `36277e27cabd0c37bc71ac302e885ff48fce4a895943360d75c20d8f033ec420`。
- PyTorch/ORT 最大绝对误差 4.76e-7（阈值 1e-3）；桌面 ORT 0.16 s @518；与官方
  `api.inference`（含后处理）在测试照片上的深度相关性 0.9898。

### ② 算子并集 — DA3 必须随 r3 重建同发

- `verify-spatial-model-operators.py` 对照 r2 清单：DA3 需要 10 个 r2 未含的
  opset-18 标准算子（Cos、Einsum、Exp、Neg、Pow、Range、Reciprocal、ScatterND、
  Sin、Unsqueeze）——r2 上必然 kernel-not-found，**DA3 不能在 r2 上发**。
- `ort-required-operators.config` 已用五模型（ZipDepth/DAV2/MI-GAN/AOT-GAN/DA3）
  重新生成；优化器新增项 DA3 与 DAV2 同族（Gemm/Split/FusedConv/FusedMatMul/Gelu，
  无 SkipLayerNormalization），com.microsoft 行不变。
- 依据该清单启动 arm64-v8a 单 ABI 的 r3-PoC Docker 构建（MinSizeRel，复用 r2 增量
  编译树，输出 `build/onnxruntime-custom/package-r3poc`，容器
  `everythingdone-ort-r3-poc`）。该构建仅用于真机基准；正式 r3 仍需四 ABI 全量构建
  + 离线签名发布（见 followups）。

### ③ 真机基准（耗时/内存）— 通过

方法：debug `SpatialDepthBenchmarkReceiver` 新增 `da3small` ModelSpec、`--es opt
no_opt|basic|extended` 优化级别与 `--es libsource <目录>` 备用 Runtime 参数。
libsource 从外部 files 复制双库进内部目录（外部存储 noexec）、按 store 同款流程
先 System.load 双库再走 `onnxruntime.native.path` 属性分支——**runtime store 全程
不动**，其完整性设计（size+sha256 标记校验）保持原样。r3-PoC 库能否跑通 DA3 本身
就是「实际加载了哪个 Runtime」的判据（r2 上必失败）。首次实现时漏了预加载核心库，
JNI 库 dlopen 报 DT_NEEDED 缺 libonnxruntime.so——store 注释早已写明该顺序。

OnePlus PLZ110（3B1629006YC00000，SD 8 Elite，CPU 8 线程，8 次迭代）：

| 模型 | Runtime | 优化 | 会话创建 | p50 | p95 | native 增量 | 热状态 |
|---|---|---|---:|---:|---:|---:|---|
| ZipDepth 384 | store r2 | NO_OPT | 30 ms | 31.6 ms | 36.6 ms | 125 MiB | 冷 |
| DAV2-S 518 | store r2 | NO_OPT | 217 ms | 1146.5 ms | 1274 ms | 571 MiB | 冷 |
| **DA3 518** | **store r2** | NO_OPT | — | **失败：ScatterND(18) 无 kernel** | | | 真机复现算子缺口 |
| **DA3 518** | **r3-PoC** | NO_OPT | 248 ms | **893 ms** | 4297 ms | 848 MiB | 冷 |
| DA3 518 | r3-PoC | EXTENDED | 460 ms | 1225 ms | 1433 ms | 953 MiB | 热 |
| DAV2-S 518 | r3-PoC | EXTENDED | 287 ms | 1069 ms | 1158 ms | 548 MiB | 热 |
| DAV2-S 518 | r3-PoC | NO_OPT | 219 ms | 1189 ms | 1387 ms | 578 MiB | 热 |
| DA3 518 | r3-PoC | NO_OPT（复测） | 276 ms | 1266 ms | 1573 ms | 843 MiB | 热 |
| ZipDepth 384 | r3-PoC | EXTENDED | 170 ms | 75.3 ms | 129 ms | 124 MiB | 热 |
| DAV2-S 518 | store r2（恢复后健康检查，4 次迭代） | NO_OPT | 123 ms | 470 ms | 474 ms | 578 MiB | 充分冷却 |

结论：

- **速度**：DA3-SMALL 与 DAV2-S 同一量级、秒级（本轮样本 DA3 0.89–1.27 s、DAV2
  0.47–1.19 s @518；热状态/调度差异可达 2 倍以上，跨热状态的行间对比无效，最后
  一行充分冷却下 DAV2 可到 0.47 s；同热状态下 DAV2 EXTENDED 比 NO_OPT 约快
  10%）。会话创建 ≤0.5 s。换 DA3 不会把生成链路从秒级推到更高档。
- **内存**：DA3 运行期 native 增量约 850–950 MiB，比 DAV2-S 高约 300–380 MiB
  （模型更大 + ViT 中间态）。16 GB 档设备无压力；低内存设备的 P0-only 回退阈值
  在接入时需复核。
- **正确性**：三模型输出 min/max 在 r2/r3、NO_OPT/EXTENDED 之间逐位一致，r3 裁剪
  构建未引入数值偏差；DA3 输出有限且动态范围正常。
- r2 上 DA3 失败于 `ScatterND(18)` 无 kernel，与桌面算子核对完全吻合——**DA3 随
  r3 重建同发**的前提再次确认。

r3-PoC 构建（仅 arm64、MinSizeRel、五模型算子清单）：核心库 11,616,368 字节，比
r2 大 266 KB（10 个新 kernel + 优化器新造算子 kernel 的代价）；JNI 库与 r2 逐位
相同。产物在 `build/onnxruntime-custom/package-r3poc/`，SHA-256
`21017d9e99e6e2e0f8a1cd6018e92e6c10a0dd922c82a69535ac7d3e222f99e1`。

**发丝验收（同管线 A/B，立体模式满强度六方向，放大 2.5×）——未通过：**

- 证据：`out/device-ab-20260801/`（dav2_*/da3_* 原图与 hair_compare_*.png 拼图）。
- DAV2 基线：发丝左缘以柔性「粘连晕」为主，硬碎屑少，整体观感平顺。
- DA3：六个方向发丝左缘均出现**成串的深色阶梯块状碎屑**，头顶发际另有浅色缺口与
  背景穿透撕裂——比 DAV2 更差、与桌面深度质量结论相反。
- 机理：DA3 的深度过渡在 518 输入上仅 1–2 px，映射到 450×600 网格后每个边缘格的
  归一化斜率都远超 D46 的 cut 晋升阈值（3.56）→ 发丝外缘与**发丝内部条缕间**被
  大量晋升为 cut，显露带以网格分辨率成块暴露，MI-GAN 对细带的补图呈发色块状涂抹
  → 视觉即深色碎屑串。DAV2 的 27 px 宽晕反而把过渡摊到多个格，斜率不足以晋升
  cut，走软形变（粘连）路径。**即深度图质量的提升暴露了渲染端（网格分辨率 +
  cut 晋升策略 + 细带补图）对锐利边缘的不适配。**
- 佐证：DA3 manifest strongEdgeRatio 0.0024（DAV2 0.0048）——过渡像素更少、更陡，
  与机理一致；深度方向正确（遮挡关系无颠倒），排除 1/depth 接错。
- 范围限定：仅在测试发丝照、立体模式、满强度下取证；稳定（单层）模式与低强度未
  系统对比，DA3 在稳定模式下可能因晕更窄而占优，待测。

**处置**：r3 runtime 与 DA3 对象/catalog 维持已发布状态（DA3 为非默认可选项，不
影响既有 ZipDepth/DAV2 流程，且这些流程获得 EXTENDED 提速）；**App 侧 debug 更新
暂缓发布**，等渲染端对锐利深度的适配（候选：cut 晋升阈值按模型边缘宽度自适应、
外轮廓与内部条缕区分晋升、disparity 有限带宽预平滑 1–2 格、网格加密、matting
alpha 融合）出结论后由用户裁定。

### 渲染端适配后复验（D53，同日）— 通过

适配 = 闭运算（半径 3）+ 锐边模型旁路引导滤波（细节见 decisions D53）。两次迭代：
半径 2 仅闭运算 → 碎屑减少但发际肤色块与边界抖动仍在（`close_ab_*.png`）；
半径 3 + 旁路引导滤波 → 六方向碎屑链与发际缺口全部消失，边界连贯贴合轮廓
（`skip_ab_*.png`），稳定模式双向平顺（`stable_check.png`）。与 DAV2 相比：DAV2
的宽粘连晕在 DA3 上不存在，背景显露更干净；残留为格级台阶与显露区补图保真度
（与 DAV2 显露区同类）。发丝验收视为通过，最终质量结论待用户亲验。
