# 实施工单：显露带的结构质量（2026-08-11，接 D183–D186）

## 定位（为什么上一轮工单没治住条带）

上一轮工单的主任务（软 α）作用在**断边处 1–3px 的混合像素**上，它确实改善了用户点名
的 00/328° 肩线硬阶梯（台阶能量差异域 −11.8%，D184）。但用户所说的「条带」是
**第二层的显露区**：宽度等于局部视差（00 场景框内中位 27px、p90 102px、最大 133px，
D185），比软 α 的作用域大一个数量级。

显露带的病因已由 D185/D186 用测量收敛：**不是分辨率**（管线无降采样、模型锁死 512、
语料本身 720）、**不是全局色阶**（按深度筛参照后无一致偏置）、**不是局部对比度**
（对齐后指标变好、画面变差，已否决）。剩下的解释经染品红逐点核实：带里画的就是第二层
自己的内容，它在统计上与周围一致，但**结构是错的**——真值是木椅竖边、盘沿高光的延续，
模型给的是一道抹平的晕。一片没有结构的平滑区域嵌在有结构的真实背景中间，看起来就是
「蒙了一层半透明的膜」。

因此本轮主攻：**把真实结构搬进显露带**。生成模型（Big-LaMa / Moebius 这个量级的
回归与扩散）在这类位置只会输出条件均值式的平滑内容，靠换参数、调色阶救不回来。

## 任务一（主攻）：深度约束的结构延续 + 真实块搬运

### 原理
显露带是一条贴着剪影的窄条，它的外边界紧邻**真实背景**。真实背景里的强结构（家具
边线、桌沿、高光条）走到带边界就断了——把它们**按几何延续进带内**，并用**真实背景的
像素块**沿延续线填充，结构就由构造保证，而不是指望模型幻觉出来。

### 与 D179 已否决的「半径限制」的区别（必须先说清，避免重走）
D179 把补全模型的上下文限制在局部半径，结果模型把**前景**（焦糖淋面）抄进带里。
本任务的取块来源有两道硬过滤：
1. **深度过滤**：只允许逆深度落在该带背景层级容差内的像素当来源；
2. **前景排除**：沿用 `--exclude-fg` 语义（D166），前景与其膨胀区一律不得为来源。
开工第一步先做废止实验：在 05 场景验证来源集合里取不到任何淋面/玫瑰像素，再继续。

### 实施步骤
1. **结构检测**：在带外边界外 3–10px 的真实背景环上检测强边缘/梯度脊
   （方向 + 强度），只保留与带边界相交的。
2. **结构延续**：把每条相交结构沿其方向延续进带内（带宽 27–100px 量级，低曲率延续
   成立；两端都命中带边界的结构做端点配对）。产出逐带结构引导图，随资产落盘原始版
   （不得只落裁剪版）。
3. **块搬运填充**：以现有 `_mix` 输出为低频底，沿结构引导图从（深度过滤 + 前景排除后
   的）真实背景取块，PatchMatch/exemplar 式贴入，接缝羽化或泊松贴合。
   **选择性应用**：只在外边界存在强结构的带段上做；无结构的带段（平坦墙面）保持
   `_mix` 原样——D186 的教训是不要动本来干净的区域。
4. **参数纪律**：块尺寸、深度容差、结构强度阈值全局统一、有物理含义，禁止逐图手调。

### 验收
- **新判据「结构延续率」**：带外边界处强结构中，在带内延续 ≥N px 且方向一致的比例。
  与抄袭度（同场景 A/B）、带真值评测（不得回退）并用；D186 教训固定为流程：任何指标
  改善必须同时给 zoom_matrix 目标帧目检，指标单独不作数。
- 目检走 `zoom_matrix.py` 整圈（含 00/328°、270°、05/270° 等既有点名位），九场景
  最大强度。
- 明确不做：全局色阶偏置、局部对比度增益（D185/D186 已否决，不得重走）。

## 任务二（对照实验）：更强生成模型的上界

目的：在写死「搬运是唯一出路」之前，量出「换更强模型」到底能买到多少结构。

1. **OSOR-SDXL**（一步扩散物体移除，权重实发于 HF `QinmingZhou/OSOR`，SDXL-inpainting
   基座，OpenRAIL++ 可商用；约 2.6B，**只做桌面对照，端侧不可行**）接为激进档后端，
   在 00/05/08 上与 Moebius 版对比结构延续与抄袭度。
2. 既有 SDXL-inpaint 路径（`--inpaint-backend` 保留档）在当前掩膜上重跑一次同口径对照。
3. **禁止**使用任何 FLUX 系权重（非商用，连对照产物都不进产品资产）。
4. 判读：若大模型同样输出无结构的晕 → 证实瓶颈是「无结构引导」而非模型档次，任务一
   为唯一主线；若大模型结构显著更好 → 桌面质量档采用之，端侧等蒸馏小模型，任务一
   降级为端侧兜底方案。

## 任务三：逐图/逐带自适应视差上限（上一轮工单任务四，未动）

带宽恒等于视差。00 的 p90 102px 深显露带填不好在信息论上是必然，产品端的正确处理是
**对填不好的地方少显露**：
1. 生成期按带段求「结构延续置信度」（任务一的引导图直接复用）；置信度低的深断崖带段
   局部收紧该方向的安全包络，而不是全局压平视差。
2. 逐图上限写入资产 meta，查看器读取；全局上限数值仍由用户裁定。
3. 验收：困难场景自动收紧、简单场景吃满；四项并列硬门禁不得用「全图变保守」凑数
   （空间感是并列门槛）。

## 顺序与边界

- 任务一为主项；任务二很轻（接后端 + 跑对照），可先做完给任务一定性。任务三在一、二
  出结论后做。
- 软 α 线（D184）的既有收益保留，两条尾巴（按 SAM 3 实例逐个求 matte 提覆盖率、
  前景软裙外延）继续留在 followups，本轮不动。
- 全部只改桌面资产生成器与网页查看器；不连接设备、不发布阿里云；只用许可可商用且
  权重已发布的模型；随做随更新 decisions/followups/sessions。

## 2026-08-11 核对（`band_structure_feasibility.py`）

方向认可：残余缺陷确为结构性（D186 已排除色阶/对比度/分辨率），结构引导 + 真实块搬运
是对症手段。四条需要改的地方，都有实测支撑。

### 1.（本条已作废）带的尺寸——工单原判断成立，是核对方算错了

**2026-08-11 二次更正**：本条第一版写「带比工单以为的窄一个量级、要外推的是个位数
像素」，**是错的，撤回**。两个数各错各的，方向相反：

- D185 的「带宽 27/102/133」：按行取 `np.where(mask[y])[0].size`，那是该行 band 像素的
  **总个数**，一行里几段互不相连的带被加在一起 → **高估**。
- 本条第一版的「到真实背景 3.6px」：距离量到的来源集合是 `(~band) & 深度在背景层级内`，
  而该集合有 28.5%（00 场景）落在主体 matte 内（见下面第 3 条）——量到的"最近真实背景"
  经常就是主体自己 → **低估**。同一个漏洞同时制造了第 3 条的结论和本条的错误。

`band_width_redo.py` 重算（局部宽度 = 带内距离变换 ×2，方向无关；来源排除
`occluders.png ∪ matte_soft`）：

| 场景 | 局部带宽 中位/p90/max（源px） | 渲染px 中位/p90 | 到合法来源 中位/p90/max |
|---|---|---|---|
| 00（用户框内） | **7.2 / 22.8 / 46** | 10.8 / 34.2 | **11.8 / 44.9 / 96** |
| 00（全图） | 6.4 / 19.6 / 46 | 9.6 / 29.4 | 7.2 / 35.8 / 109 |
| 01 | 10.0 / 23.6 / 33 | 15.0 / 35.4 | 12.4 / 64.7 / 116 |
| 05 | 4.4 / 10.8 / 18 | 6.6 / 16.2 | 4.0 / 14.0 / 48 |
| 08 | 5.6 / 16.8 / 35 | 8.4 / 25.2 | 5.0 / 20.0 / 156 |

**到合法来源的距离系统性大于带宽**（00 框内 11.8 vs 7.2、p90 44.9 vs 22.8），
因为合法来源必须排除遮挡物，而带的一侧就是遮挡物——**只有另一侧锚在真背景上**。
所以工单「长距离延续 + 低曲率」的判断成立，端点配对在细颈处也确实有用，
**原文这一段不用改**。要按 p90 40–65px、最坏 100–156px 来设计，不是个位数。

### 2. 可搬的结构比设想的少，任务一的天花板要按这个定

带外边界上"外侧 5px 内存在强结构"的比例（阈值取该图 Sobel 幅值分位，图内相对量）：

| 阈值 | 00 | 03 | 05 | 08 |
|---|---|---|---|---|
| p90 | 41.5% | 72.4% | 31.7% | 30.0% |
| p95 | 24.0% | 47.9% | 17.2% | 16.5% |

「无结构段保持 `_mix` 原样」这条纪律是对的，但它意味着**一半左右的带这条路不作用**。
任务一的预期收益要按"覆盖三到七成带边界"来定，不能按"治好整条带"验收。

### 3. 那道护栏是承重的：深度过滤**单独不够**

工单规定取块来源有深度过滤 + 前景排除两道，并要求 05 先做废止实验——这是对的，
而且比工单以为的更必要。实测**只做深度过滤**时，来源集合里仍有这么多像素落在主体
matte 内：00 **28.5%**、08 **32.4%**、03 19.5%、05 6.5%。深度容差与遮挡物自身的深度
范围本来就重叠，D179 抄前景的坑会原样重现。

废止实验的靶子因此明确：加上 `--exclude-fg` 后，这个比例必须掉到 ~0，且要逐场景报数。

### 4. 任务二的模型可用性未经核实

`QinmingZhou/OSOR` 的权重是否实发、许可是否 OpenRAIL++，本轮没有核实。按本日经验
（工单里已发现四条过期前提），接后端之前先验仓库与 LICENSE 原文，再排期。

### 与既有结论不冲突的部分

任务三方向正确：空洞率随基线的实测曲线（00 场景，关第二层不填充）为
1cm 2.4–2.6%、2cm 3.4–3.6%、3cm 4.4–4.7%、4.5cm 6.1–6.4%（D187），
支持"对填不好的地方少显露"。

## 2026-08-11 废止实验：**没过**，开工前必须先修来源窗口

工单要求"开工第一步先做废止实验：在 05 场景验证来源集合里取不到任何淋面/玫瑰像素"。
跑了，**取得到**。

先说一个无效的做法：把"来源 ∩ 主体 matte"当泄漏率去测，而来源集合本身就是按同一个
matte 排除出来的——必然读出 0.00%，是循环论证，不作数。有效的检查是把来源集合画出来看
（`qa/matte-soft-probe/src-ablation.jpg`）：**05 的来源集合里整个蛋糕主体都在**。

根因是**全局深度窗口**。整条带的背景层级取 `inv_layer[band]` 的 p2–p98，05 得到
深度 **[1.58m, 2.48m]**：

| 位置 | 深度 | 是否落在全局窗口 |
|---|---|---|
| 蛋糕上层淋面 | 1.48 m | 窗口外 ✓ |
| 玫瑰 | 1.54 m | 窗口外 ✓ |
| **蛋糕下层** | **1.63 m** | **窗口内 ← 可被当来源** |
| 背景墙 | 2.44 m | 窗口内 ✓ |

而带有 36 个连通段，各段自己的背景层级窗口差别很大——段 19 是 [2.19m, 2.56m]、
段 28 是 [1.70m, 2.20m]、最大段是 [1.57m, 2.44m]。用一个全局窗口给每一段取来源，
必然把别的段的前景放进来。**这是 D180「遮挡物分割被一个全局深度阈值卡死」在取块这一步
的复发**，本仓库同一个坑的第五次。

**开工前必须改**：来源窗口改成**逐带段（逐实例）**，与 D178/D180 判自遮挡时的分段同源。
改完重跑废止实验，05 的蛋糕主体必须掉出来源集合，并逐场景报数。

### 顺带：`--exclude-fg` 半径的天花板

带像素在 64px 邻域内仍能找到来源的比例：

| 半径 | 00 | 05 | 08 | 03 |
|---|---|---|---|---|
| 0 | 98.6% | 100.0% | 98.4% | 98.4% |
| 6 | 98.2% | 99.3% | 98.0% | 97.3% |
| **12（管线默认）** | 96.0% | 97.5% | 96.4% | **69.2%** |
| 24 | 76.7% | 93.3% | **54.7%** | 61.4% |

12 差不多是上限，再大就没东西可搬（08 掉到 54.7%）。03 在 12 上已经只剩 69.2%，
它的取块半径需要单独放宽或接受覆盖不足——但**不得为此调小 exclude-fg**。

上一节据 `src-ablation.jpg` 判「05 的来源集合里整个蛋糕主体都在」，**错了**——那张图里

### 任务二核对：许可与权重（已查证）

`QinmingZhou/OSOR` 确实存在，但工单写的「OpenRAIL++ 可商用」需要**限定到具体档**。
README 原文：

- **OSOR-FLUX-Fill**：FLUX.1-dev 非商用许可，**不得商用**——与工单"禁止 FLUX 系"一致，
  而且它就在同一个仓库里（`osor-fluxfill/`），下载时必须点名子目录，不能整仓 clone。
- **OSOR-SDXL-Inpainting**：CreativeML Open RAIL++-M，含 use-based restrictions。可用。
- 代码 MIT，但"代码许可不替代权重及其基座的许可"。

权重体积：`osor-sdxlinpainting/weights/sdxlinpainting_phase1.pth` 3,112,285,286 B、
`phase2.pth` 3,112,296,806 B。**本机 torch 是 2.3.1+cpu（无 CUDA）**，SDXL 级别在 CPU 上
逐块推理九场景不现实；WSL2 那套 cu128 venv 是为 gsplat 建的，没有 diffusers/SDXL 基座。
因此任务二**本轮只完成到"可用性与许可查证"**，实跑需要先在 WSL2 venv 里装 diffusers +
下载 SDXL-Inpainting 0.1 基座（约 7GB）+ phase2（3.1GB），这一步单独排期。
