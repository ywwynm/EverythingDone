# 2026-06-24 置顶记事状态变更落位修正

本次更新继续修正置顶记事在完成、删除、恢复后的排序行为。

此前已经确认：置顶记事发生状态变更后不应该丢失置顶状态，也不应该直接保留原本的负数 `location`，否则会出现“先完成的置顶记事仍排在后来完成的置顶记事前面”的问题。正确行为是：每次状态变更都在目标状态列表的当前父级置顶区重新分配一个新的负数 `location`，让后来完成、删除或恢复的置顶记事排在更前面。

上一版发布中，这个重新分配逻辑已经能产生正确的负数位置，但计算放在 `ThingDAO` 的最终落库路径里。根据后续排查和确认，普通非置顶记事的完成流程由 `ThingManager` 编排，因此置顶记事的状态变更落位也应继续放在 `ThingManager` 中保持一致。

本次调整：

- `ThingManager.updateState` 在非撤销、非永久删除的状态变更中，根据原记事是否置顶决定目标 `location`。
- 置顶记事使用 `ThingFolderDAO.getFirstChildLocation(parentFolderId, sticky = true)` 重新分配当前父级置顶区顶部之前的新负数位置。
- 非置顶记事保留既有行为，仍由 `ThingDAO` 使用 `getMaxThingLocation()` 和 header 前移逻辑进入目标状态列表的非置顶区顶部。
- 批量完成、删除、恢复以及文件夹范围内的批量状态变更，同样由 `ThingManager` 为置顶条目预先计算目标位置。
- `DetailActivity` 和 `RemoteActionHelper` 中绕过列表位置的直接 DAO 路径，也会先向 `ThingManager` 获取状态变更位置，避免再次丢失置顶。

验证状态：`:app:assembleDebug` 已通过。本次发布会将上述 `ThingManager` 版本推送到阿里云 debug 更新通道。
