# 新建与左滑粒子性能验证

## 范围与方法

- 用户追问各种性能测试是否已完成。此前仅有功能、顺序和资源清理的正确性验证，没有形成这两个新入口的性能基线；本轮补测，仅操作已授权的 9018f404。
- 分开测量首页点击新建、详情入场、保存后的列表与卡片入场、左滑去程／停住／回拖；以涟漪、边框光效和普通滑动作对照。
- 记录 Android Window FrameMetrics、主线程调度间隔、粒子提交／纹理合成回调间隔、GL 提交和等待完成耗时、进程 CPU 时间，以及重复操作前后的 Java／Native／Graphics 内存和资源数量。
- 动画性能轮不截图或逐帧编码图像，不把低频截图、整个进程累计 gfxinfo 或单元测试当作动画性能结论。GL 的 glFinish 等待包含驱动排队，不称为纯 GPU 执行时间；纹理回调也不等同于面板物理扫描。
- 正式测试使用系统输入操作真实按钮和返回键，固定独立测试标题；debug 观察器只读采样，不驱动业务。轮次结束后恢复设置，测试记事放回收站。
- 最初读取设置为新建粒子、左滑滑动、自动旋转开启，系统热状态为 0。

## 用户补充与测量边界

- 2026-09-14 用户要求以实际按钮、返回等系统输入测试，不能用 ADB 直接调用业务入口代替。
- 首个 `particle-create-1` 使用 debug Activity 在进程内派发触摸，三轮已完成并创建 `CodexAnimationPerfParticleA0`～`A2`。此组只保留作诊断，不计入正式验收。
- 已删除该驱动 Activity，改为 debug 专用只读 ContentProvider 观察器，由独立诊断文件显式开启。它不启动 Activity、不写动画设置、不修改输入内容、不派发触摸，只转发并记录窗口原本收到的系统输入以及 FrameMetrics。
- 正式操作通过当前 UI 层级定位，再向 Android 输入系统注入触摸和返回键；设置从真实设置菜单修改。观察器的开关文件只是采样控制，不调用业务。

## 首组正式数据（real-particle）

- 从桌面真实点击“完事儿”图标进入，再三次点击 FAB；实际收到的 DOWN/UP 均被窗口记录。三次保存包含两次工具栏返回和一次系统返回，系统按键也有实际接收记录。
- 横屏全屏入场：请求到首个粒子提交回调约 363–399 ms；三轮纹理更新间隔 P95 为 17.2–32.5 ms，最长 17.7–33.7 ms。每轮 GL 提交 38 帧，窗口确认 36–38 帧。
- 保存后 577×141 卡片：首帧约 284–301 ms，纹理更新间隔 P95 为 16.9–33.4 ms。末轮确认 32/38 帧，存在合成漏取，不能声称稳定 60 fps。
- 全屏的 GL 提交加等待完成 P95 约 10.7–19.1 ms，卡片约 3.3–3.7 ms；等待包含驱动调度。首次页面创建阶段 Window 总耗时峰值约 46–54 ms。
- 三轮前后 PSS 从 366,174 KiB 回到 356,439 KiB，Graphics 从 41,372 KiB 回到 40,304 KiB，Activity 数均为 1。尚需与对照及重复开关场景一起判断。

## 慢拖问题定位

- 使用真实系统滑动输入，在同一卡片上以 1.2 秒左移 36% 宽度后松手取消。普通滑动两轮 Window P95 约 5.6 ms，没有超过系统帧截止时间。
- 粒子前两轮的系统输入约 60 Hz，主线程间隔 P95 约 16.7 ms；纹理回调间隔中位数却约 49.8 ms，P95 为 67–84 ms。GL 提交加等待完成 P95 仅 3.7–4.3 ms，无法解释该跳变。
- 源码将连续手势取整为 60 个轨迹档位，未跨档时跳过绘制，与测量相符。计划保留缓存规模，改为相邻轨迹插值，使用同一实际手势对照修复结果。

## 插值修复后的同条件对照

- 先加慢拖回归测试：在不足 1/60 进度的位移变化中，原实现把 121 个位置压成少量画面，测试失败；改为连续进度后通过。25 项相关测试通过，包括共同模型、设置兼容、逆向缓存及全部相关 GLSL 实际编译。
- 同一卡片、同一 1.2 秒／36% 宽度系统手势，修复前后各 4 轮。纹理更新间隔中位数从约 49.7–49.8 ms 降到 16.57–16.59 ms；P95 从 67.2–83.8 ms 降到 17.7–22.4 ms。最大值仍约 33.3–36.1 ms，不能说完全没有漏帧。
- 修复后每轮提交 53–54 帧，确认 52 帧；GL 提交加等待完成 P95 约 3.7–4.3 ms。4 轮粒子播放阶段的 216 个 Window 帧均未超过系统提供的截止时间。取消后记事仍在、数量不变。
- 首帧准备仍约 294–304 ms；该修复解决的是拖动时的阶梯感，不消除正向预解算等待。未增加轨迹缓存、粒子数量或全屏渲染分辨率。

## 重复开关的内存采样

- 通过真实 FAB 打开空白创建页并返回，连续 8 轮，交替使用工具栏返回和系统返回；另开内存采样轮，不把带 dumpsys 内存采样的帧数据计入性能统计。
- 共 197 个内存样本：PSS 起始 283,131 KiB、峰值 506,451 KiB、末次 257,216 KiB；Graphics 起始 44,428 KiB、峰值 146,924 KiB、末次 42,672 KiB。采样间隔约 0.5 秒，峰值不保证捕获到每个瞬时极值。
- Activity 数在 1–2 间变化，最后回到 1；16 个阶段结束时粒子线程均为 0，未观察到逐轮持续增长。PSS 峰值约 495 MiB，仍需低内存设备验证，不能据单台平板断言无内存风险。

## 三档对照、竖屏与功能回归

正式设备为 OPD2515 / Android 16，横屏 2520×1680、竖屏 1680×2520。普通界面约 120 Hz，粒子请求 60 Hz。每轮单独记录 Window 帧截止时间，不统一用 16.7 ms 判断所有窗口帧。测试使用现有首页（含原有媒体卡片），没有关掉正常内容来制造轻负载条件。

| 创建页入场 | 轮数 | Activity 恢复至入场结束 | 同一阶段进程 CPU 时间 | Window 总耗时 P95 |
| --- | --- | --- | --- | --- |
| 涟漪，横屏 | 2 | 624–625 ms | 190–193 ms | 14.6–14.8 ms |
| 边框光效，横屏 | 2 | 1,333–1,345 ms | 787–836 ms | 11.4–11.9 ms |
| 粒子，横屏 | 3 | 1,009–1,043 ms | 427–604 ms | 14.0–17.3 ms |
| 粒子，竖屏 | 2 | 1,031–1,058 ms | 500–574 ms | 16.9–22.4 ms |

- 表中 CPU 是整个应用进程累计消耗的 CPU 时间，包含同期 UI、观察器及背景任务；不是粒子单独的 CPU 用量。边框时长本来就较长，不能仅凭累计 CPU 比较单位时间效率。
- 竖屏两轮全屏粒子首帧准备约 385–412 ms，纹理间隔 P95 为 17.7–18.0 ms；窗口初始化峰值 47.8–69.1 ms，仍有卡顿。
- 12 行正文形成 504×632 长卡片，保存两轮均提交并确认 38 帧，纹理间隔 P95 为 17.0–17.1 ms，GL 提交加等待完成 P95 为 7.6–9.1 ms。两轮慢拖的纹理间隔中位数 16.55–16.66 ms，P95 为 17.6–33.2 ms，最长 40.3 ms；GL P95 约 7.6–8.3 ms。长卡片仍有偶发间隔波动。
- 五轮真实粒子保存（横屏三轮、竖屏长卡片两轮）均观察到腾位阶段真实卡片 INVISIBLE；粒子播放期间提前可见帧数和列表动画重叠帧数均为 0，最后提交帧均已确认。
- 修复后停住、回拖、系统取消分别通过系统 MotionEvent 验证；停住两次截图卡片区域完全一致，回拖归零和取消后与原图像素完全一致。截图轮与性能轮分开。90 ms 快速甩动正确完成专用记事，Window 49 帧均未超过系统截止时间。
- 三次在创建页恢复前台后约 122–139 ms 按系统返回均回到首页，同一进程保持存活；之后还能正常打开创建页。修复版进程的 crash buffer 无异常记录。
- 各正式批次开始／结束的系统 Thermal Status 均为 0；没有进行长时间连续高负载、功耗或多机型测试。相关 29 项 JVM 测试全部通过，无跳过，包括真实 GLSL 编译。

## 复现和产物

- 只读观察器由私有文件 `files/thing-animation-performance-enabled` 显式开启，默认不注册采样循环。开启文件后，从桌面真实点击应用图标进入；测试结束删除开关和控制文件。控制 JSON 仅含采样标签，不包含业务指令。
- `device_performance.py` 先从 UI 层级定位按钮、菜单与卡片，再使用系统输入执行点击、输入、返回和滑动。`--set-mode` 也走真实设置菜单；`--memory-sample` 单独标记，分析器排除其帧耗时结果。
- `analyze_performance.py` 只接纳 `schema=2` 且驱动为真实输入观察的正式结果，生成帧间隔、GL 等待、Window 截止时间及保存顺序分析。
- 原始 JSON、内存／温度快照和汇总保存在忽略目录 `tmp/thing-animation-device/performance/`；各批次名称对应上文。`particle-create-1` 为最初内部驱动诊断，始终排除在正式结论之外。
- 清理时注意侧栏状态分段仅当前选中项有文字，未选中的“已完成”只有图标。应从当前 UI 层级取得三个分段的实际边界，结合 `ThingStatusSegmentedView` 明确的“正在进行／已完成／回收站”顺序定位；不能把侧栏内看不到 Finished 文本误判为导航未打开。切换状态后用系统返回收起侧栏，再检查标题与目标记事。

## 当前结论与边界

- 慢拖的进度取整问题已修复，真实输入对照确认更新频率提高；保存顺序、回拖、取消和快速完成没有出现回归。
- 首帧等待、全屏初始化峰值和偶发 33–40 ms 纹理间隔仍存在，不能宣称稳定 60 fps。约 495 MiB 的实测 PSS 峰值也需要低内存设备进一步验证。
- 本轮覆盖单台授权设备的实际使用流程及重复操作，没有覆盖所有机型、长时间压力和功耗；这些不应被本轮结果替代。
