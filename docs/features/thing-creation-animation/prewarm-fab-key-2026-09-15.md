# 提前预算被 FAB 坐标必然判废：出现动画慢四倍（2026-09-15）

## 现象

用户报告：新建记事的粒子动画在华为平板上**有时**播不出来，"会卡一段时间，然后直接显示
记事详情界面"。

## 根因

指纹 `ParticleCreationKey` 里有一项 `fab=<中心 x>,<中心 y>`，取自
`fab.getLocationInWindow()`。这个方法**把 `translationY` 也算进去**，于是记下的是
"按钮此刻被临时顶到哪儿"，而不是"新建按钮在哪儿"。

按钮会随 Snackbar 上移一个 Snackbar 的高度（本机 111.6 px）。而点击处理的第一步就是
`dismissSnackbars()`，之后才取坐标：

```kotlin
dismissSnackbars()                        // translationY 开始回落
mFab!!.getLocationInWindow(fabLocation)   // 于是必然读到落位值
val prewarmKey = currentCreationPrewarmKey()
```

结果是**只要返回首页时有 Snackbar，就必然判废**——空闲预算读到上移后的 1706，点击读到
落回后的 1818，`ParticleCreationMatch` 按"环境变了：fab"丢掉整份算好的轨迹。这不是偶发，
是这条路径上的确定行为；用户说的"有时"，对应的是"返回首页时有没有 Snackbar"。

判废的代价是双份的：白烧一次 600 ms 的 GPU 预算，然后在前台重新现场算一遍。

## 这一项本不该这么严

`fab` 坐标在链路里只经 `sourceX/sourceY` → `appearanceTouchInWindow` → `virtualTouch`，
唯一作用是定出现动画的**方向**（以及可选的 touchGap / touchStrength）。

算一下这 112 px 的实际影响：快照中心 (1440, 960) 到 (2778, 1818) 是 32.67°，到
(2778, 1706) 是 29.1°——**差 3.5°**。为肉眼分辨不出的 3.5° 作废一次预算并不划算。

## 修法

**按钮坐标整项移出指纹**（用户裁定："反正都是从右下角出现"）。

先试过一版"标称中心"：指纹与点击两侧都取减去自身 translation 的布局位置。它解决了
Snackbar 这一种来源，但用户实测仍有判废——按钮还会随列表滚动 `hideToBottom()` 收起，
`getLocationInWindow` 又受 scale 影响（`shrink()` 把 scaleX/Y 设为 0），瞬时读数不止一种
变法。既然这一项的全部作用只是微调方向、而方向差不到 4°，与其逐一堵住每种来源，不如
整项不要。

保留的部分：交给转场的 `sourceX/sourceY` 仍改用 `fabNominalCenter()`（不含 translation 的
布局位置）。它是涟漪档的揭示圆心与粒子的出发方向，取稳定值本身是对的，只是不再参与
"预算能不能用"的判断。

指纹项数由 15 降到 14，两处源码契约测试与 `ParticlePrewarmStore` 的注释一并更新。

一并撤回的错误尝试：最先按"FAB 正在做入场动画"给预算加了 `isSettling` 门槛。实测
`settling=false` 而 `ty=-111.6`——位移根本不经过 `showFromBottom()`，门槛没有生效。
教训是先把状态打出来再动手，不要凭假设改。

## 实测（PCE-W30）

同一个 700 ms 间隔的连续新建脚本，三种方案对照：

| | 原状 | 标称中心 | 整项移除 |
|---|---|---|---|
| 预算命中 | 1 / 4 | 4 / 4 | 5 / 6 |
| 首帧 | 759~829 ms | 172~228 ms | 164~176 ms |

整项移除那一列的十轮里**奇数轮先滚动列表再新建**（按钮会收起，标称中心方案仍会判废的
情形），`环境变了：fab` 一次未再出现。唯一一次未命中是冷启动首次，原因是
"还没有真实创建页快照可作预测素材"，属设计如此，对应那一次 931 ms 的首帧。

命中与否的完整对照：

| | 命中 | 未命中 |
|---|---|---|
| 首帧 | ~170 ms | 1066~1163 ms（冷启动） |
| 帧率 | 60fps (p90 16.67) | 30fps (p90 33.33) |

首帧之前画面停在首页快照上，所以未命中时就是"卡一下再出现"。

## 顺带补上的诊断

这次定位卡在"日志只报项名不报值"上，一并改掉：

- `ParticleCreationMatch.difference()` 现在输出 `fab=2778,1706 → fab=2778,1818`，
  而不是只说一句 `fab`；
- `ParticleDismissController` 的 1100 ms 兜底（`restore`）原本静默，现在打
  "出现未能开播"，带 elapsed / retries / captureQueued / 附着与尺寸；
- `appearContent` 的前置拒绝改为具名的"出现未受理：<原因>"。

均为 debug-only。
