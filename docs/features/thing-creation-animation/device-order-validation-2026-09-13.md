# 保存后卡片入场顺序回归

## 反馈与检查方法

- 用户指出完整卡片在粒子结束前已经显示，要求先腾位、再播放粒子、最后显示真实记事。
- 之前每秒 2–3 张系统截图不足以发现此时序冲突。本轮增加 debug 专用 `NewItemAppearanceProbeActivity`，只旁观实际 ThingsActivity 的预绘制状态和粒子层已提交进度，不替代 RecyclerView 或修改动画参数。
- `device_creation_order.py` 通过真实设置、FAB、详情标题和保存按钮操作。设备固定为用户授权的 `9018f404`，只新建 `CodexAnimationOrder...` 专用记事。
- 排查顺序：ItemAnimator 写回透明度、绑定刷新恢复可见、粒子结束回调提前。通过实际透明度曲线、列表动画运行状态和已提交粒子进度区分。

## 修复前

- 第一轮 `order-before-1`：36 帧提前可见，25 帧列表动画与粒子层重叠。301 ms 时卡片开始普通淡入，418 ms 时 alpha 已为 1，而粒子进度仅 0.2218；899 ms 才观察到粒子末帧。
- 第二轮 `order-before-2`：39 帧提前可见、22 帧重叠；403 ms 时真实卡片完整可见，粒子进度仅 0.1386。同一缺陷连续两轮复现。
- 对应实际 Android ItemAnimator 的添加动画写回 alpha。卡片位置尚在移动时就启动了粒子捕获，既打乱用户要求的三阶段顺序，又让完整卡片提前出现。
- 原始 JSON 与系统截图位于忽略目录 `tmp/thing-animation-device/order-*-order.json`；逐帧断言在修复前失败。

## 修复

- 粒子档先让卡片保持 INVISIBLE，等待 ItemAnimator 的完成通知，再启动共同粒子出现管线。
- 使用实际动画完成通知，不叠加估算延时；原有滚动门控、退出清理和代次校验继续有效。

## 修复后

- `order-after-landscape`：提前可见帧数 0、重叠帧数 0，436 ms 才建立粒子层，1309 ms 在粒子末帧后显示真实卡片。28 项相关 JVM 测试通过，无失败或跳过。
- `order-after-portrait`：提前可见 0 帧、重叠 0 帧；424 ms 建立粒子层，1289 ms 在末帧后显示真实卡片。
- `order-after-scrolled-2`：先滚动列表，再小幅回滚恢复首页正常收起的新建按钮，从真实 FAB 新建并保存；提前可见 0 帧、重叠 0 帧。此轮保存后新卡片已在可见区域，未发生额外平滑滚动，不把它记为目标卡片在屏外的滚动回归。
- 首个滚动脚本在首页按正常规则收起 FAB 后等待超时，未创建记事；调整脚本恢复按钮后重新运行成功。这是测试导航问题，没有修改产品的工具栏行为。
- 发布包 `order-published` 再次通过：提前可见 0 帧、重叠 0 帧；552 ms 建立粒子层，1442 ms 在末帧后显示真实卡片。
