# 2026-10-10 单媒体默认比例不一致排查

## 问题与验收规则

- 用户反馈：只有一个图片或视频、从未确认外观设置时，详情缩略图可能过宽；打开外观编辑器直接确认后，才变成编辑器显示的默认比例。
- 按 2026-06-24 已确认规则，单媒体默认满宽 `4:3`，运行时默认不自动写入外观 JSON；增加第二个媒体后继续使用未定制网格规则。已确认的比例与裁剪按保存值显示。
- 本次获准通过 ADB 验证 `9018f404`（OPD2515 平板）、`R5CW20BLNKL`（SM-S9180 手机）与 `192.168.100.67:42641`（MEIZU 20 Inf 手机）。不操作其它连接设备。

## 验证安排

先增加 debug 专用回归入口，直接比较真实 `ImageAttachmentAdapter` 在未配置与确认默认配置时的目标宽高，并在真实详情页执行打开外观、确认、重新布局。覆盖手机/平板配置、横竖屏、横图/竖图/方图/超宽图/视频，以及增加或删除第二个媒体与已保存比例。

所有界面操作使用专用临时记事；结束后按本次创建的 ID 和固定创建时间删除测试行。修复前后运行同一入口，结果单独保存在功能目录。

## 修复前证据与假设

- 首次真实 Adapter 矩阵共 24 项，8 项不通过：手机/平板横屏 × 图片/视频各有“默认与确认不一致”和“删除至单媒体未恢复默认”两项。示例宽度 2520 px：默认高度 840 px，确认后 1890 px；竖屏两种状态均为 1890 px。现有保存比例 1:2、4:3、65:24 均正常。
- 首轮界面测试因 OPD2515 未响应应用内竖屏请求而超时，未把该轮视为界面验收通过。后续通过系统旋转状态控制测试方向，结束后恢复原值。
- 待核验假设按优先级为：旧横屏尺寸分支直接给出 3:1；确认外观改变网格占列/实际宽度；图片尺寸或视频取帧改变高度。前者预测不依赖设备类别及源图比例，仅依赖横屏与是否存在已保存外观。

## 已确认原因与修复

- OPD2515 真实详情页补测：横屏下横图、竖图、方图、超宽图、视频均为默认 `2520×840`，直接确认后为 `2520×1890`，编辑器比例均约为 `1.33333337`。竖屏五类媒体确认前后均为 `1680×1260`。
- 未配置外观时，`ImageAttachmentAdapter.getItemTargetSize()` 调用 `AttachmentHelper.calculateImageSize()`；其手机和平板横屏分支均把小数量媒体的高度固定为显示宽度的三分之一。确认外观后，Adapter 改走模型的 `4:3` 计算路径。宽度始终不变；旧尺寸计算没有读取图片或视频尺寸，因此后两个假设排除。
- 修复在旧尺寸入口优先处理单媒体，并读取与编辑器相同的默认比例、采用相同的四舍五入方式。不需要修改数据库、图片解码或外观确认流程。
- 首轮截图发现弹窗 Fragment 已移除时，消散动画仍可能显示；宽高记录不受影响，后续截图需等待交互转换结束，避免将动画中截图当成最终界面。

- 每次运行还执行 24 项配置矩阵断言，覆盖手机/平板、横竖屏、图片/视频默认值与删除至单媒体、已保存的 `1:2`/`4:3`/`65:24`、第二媒体网格与重排。六轮共 144 项矩阵检查通过；这是同组配置测试在三机两方向的重复执行，不是 144 个独立产品场景。
- `:app:assembleDebug` 与定向 `:app:testDebugUnitTest` 通过；`AppearanceRemapSourcesTest` 11 项、`ImageAttachmentGifLifecycleSourceTest` 5 项全部通过。`git diff --check` 无错误。
- 六轮修复后各创建并清理 5 条临时记事；系统旋转恢复为平板 `free`、三星和魅族 `lock 0`。
- 原始 JSON 在 [验证目录](validation-2026-10-10-default-ratio/)，截图在工作区 `tmp/detail-media-geometry/`。首次基线超时记录保留，后续成功完成的基线界面记录以 `9018f404-baseline-ui-*` 为准。
