## 0 先补的一处：G0 基线路径缺的顶点属性屏障

`advance()` 的积分循环每步只发 `GL_SHADER_STORAGE_BARRIER_BIT`，而**关掉绘制记录**时
（`withPerFrameBaseline` 走的那条 G0 基线路径）`material.vert` 直接把同一批状态缓冲当
**实例化顶点属性**读，按规范需要 `GL_VERTEX_ATTRIB_ARRAY_BARRIER_BIT`；开着绘制记录时
`writeDrawRecords` 发的屏障带了这一位，关掉之后就没人发了——而所有 G0/G1 对照都以这条路径
为参考。修法是在 `writeDrawRecords` 的早退分支上补发这一位（一行）。

**补完之后魅族上的自比较仍然是 0 帧差异**（`mzparity` 两份产物各一次：`self` 的
`differingFrames=0`、`worstMaxChannelDifference=0`），对照工具本身没有被这一行改动影响。

## 1 归因工具的三条前置判断

| # | 结论 |
|---|---|

## 2 这台设备上的规模读数

**与魅族最大的差别在片数，不在网格。** 13.2 英寸平板上「添加附件」弹窗按 dp 算只有
651×641 px，而累积纹理是整屏 2880×1920：

| 项 | 华为（附件弹窗） | 魅族（附件弹窗，本轮同一格） | 魅族（阶段 0' 的全屏弹窗） |
|---|---|---|---|
| 快照尺寸 | 651×641 | — | 1368×3192 |
| 微片数 | **20,501** | 20,697 | 106,976 |
| 材料格子 | 140×138 | — | 319×314 |
| 压力网格 | 290×288 = **83,520** | — | 290×288 = 83,520 |
| 累积纹理 | 2880×1920（整屏） | 1368×3192（整屏） | 同左 |

**结论一：华为上这一格是「少量微片 + 整屏累积 + 与魅族一样大的压力网格」**，
所以它的成本结构更像阶段 0' 里魅族的**左滑卡片**（压力主导），而不是魅族的弹窗（绘制主导）。
直接照 Adreno 的份额排序去实施确实会排错——这正是方案第一步存在的理由。

## 3 分段表（消融，每条件 3 对，`hwattr-seg/segment-bench.json`）

比值 = 「跳掉这一段之后的整段墙钟 / 紧挨着它跑的基线」，**按配对取中位数**。

### 3.1 现场消散（60 帧，基线 6.31–8.24 ms/帧，中位约 7.4）

| 消融条件 | 比值 | 读作 |
|---|---|---|
| `no-pressure`（整段压力不做） | **0.452** | 压力 ≈ **55%** |
| `no-pass0`（第 0 遍绘制） | 0.861 | pass0 ≈ 13.9% |
| `no-pass1`（第 1 遍绘制） | 0.926 | pass1 ≈ 7.4% |
| `no-resolve` | 1.012 | ≈ 0（噪声内） |
| `no-clear`（不清累积纹理） | **1.125** | **清空是省钱，不是花钱**（见下） |

### 3.2 回放出现（36 采样，基线 2.77–3.29 ms/帧）

| 消融条件 | 比值 | 读作 |
|---|---|---|
| `no-pass1` | 0.749 | pass1 ≈ 25.1% |
| `no-pass0` | 0.798 | pass0 ≈ 20.2% |
| `no-resolve` | 1.022 | ≈ 0 |
| `no-clear` | 1.019 | ≈ 0 |

### 3.3 预读（36 采样，基线 8.60–9.56 ms/采样）

| 消融条件 | 比值 | 读作 |
|---|---|---|
| `no-pressure` | **0.189** | 压力 ≈ **81%** |
| `no-history` | 0.975 | 历史转存 ≈ 2.5% |

### 3.4 这一节最重要的三条

1. **压力是华为上的绝对大头**：现场消散 55%、预读 81%。而这台的压力网格与魅族一模一样
   （83,520 格）——它贵的原因不是微片多，是**网格按卡片尺寸与 span 算出来就是这么大**。
2. **在 Mali 上「不清累积纹理」反而慢 12.5%**（三对分别 1.235 / 1.125 / 1.109）。
   这是 tile 架构的教科书行为：渲染通道开头的 `glClear` 让整块 tile 不必从主存**载入**；
   不清就变成 load-modify-store。**Adreno 上这一项落在噪声里**（阶段 0' 的结论），
   两家在这一条上的方向完全相反。B6「按包围盒局部清空」因此在 Mali 上是**负收益**，
   本专项已经降级的那一项可以彻底划掉。
3. **绘制在华为这一格上只占 21%（现场）/ 45%（回放）**，远低于魅族全屏弹窗的 56% / 87%。
   片数只有魅族那一格的 1/5，而绘制是唯一随片数线性缩放的一段。

## 4 三条新增对照（B1 / B2 / B3）与 `mediump` 判定

口径：离屏逐项 A/B（`ParticleSegmentBench.runPhase2`），每项紧挨着自己的基线跑，
按配对取比值中位数；比值 < 1 即为提速。华为 5–6 对，魅族 4–6 对。

| # | 对照 | 华为（消散 / 出现 / 预读） | 魅族（消散 / 出现 / 预读） | 结论 |
|---|---|---|---|---|
| **B1** | 累积目标 RGBA16F → SRGB8_ALPHA8 | **0.848 / 0.729 / 0.976** | 0.958 / 1.023 / 1.004 | **Maleoon 确实为浮点混合付钱**：消散 −15%、出现 −27%。Adreno 上只有消散 −4%。这是本阶段单项收益最大的一条，但它是 **V 级**（8 位量化），要用户看图定夺 |
| **B2** | 批处理 Jacobi vs **逐次 Jacobi + 活动区域** | **2.964** / 1.004 / 0.798 | —（Adreno 不走这条变体） | **批处理胜出，M3 否决。** 逐次路径即使接上活动区域，现场消散仍慢 **3 倍**（100 次 dispatch + 100 道屏障换不回 shared 的代价）。Arm「shared 不是片上内存」那条规则在**这台设备的这个规模上**不足以翻盘 |
| **B3** | 整网格清零 → 只清活动区域 | **0.929 / 0.932 / 1.012** | 1.004 / 1.002 / 1.011 | 华为上值 **6–8%**，Adreno 上为零（与「Adreno 上清空不要钱」一致）。G0，**采纳** |
| — | `mediump` varying（U5） | 1.047 / 0.989 / 1.014 | 0.975 / 0.969 / 1.018 | 见下 |
| — | `mediump sampler3D`（U2b） | 1.058 / 0.956 / 1.013 | — | 见下 |
| — | `mediump` 的 compute ALU（A1） | 0.985 / 0.985 / 0.977 | 0.969 / 0.978 / 0.993 | 见下 |
| — | **单格取样探针**（去掉三线性） | 1.040 / 0.958 / 1.045 | — | **那 32 次三维取样在 Maleoon 上不是瓶颈**：把 `sample_field` 换成只取一个格子（画面必然错）之后三条路径都没有变快。U2 / U2b / U10 的前提——Arm 给 3D 格式与 highp 采样器各记 2 倍代价——在这台设备上量不出来 |

### `mediump` 到底有没有被驱动听进去

判据按方案第七节第 4 条：**同一段改 mediump 前后比画面**。魅族（Adreno 740）上的逐帧
对照（`mzparity`，61 帧整屏逐像素）给出：

| 改动 | 差异帧 | 最大通道差 | 判定 |
|---|---|---|---|
| `mediump` varying（U5） | **0 / 61** | 0 | **驱动忽略**：声明了等于没声明 |
| `mediump sampler3D`（U2b） | **0 / 61** | 0 | **驱动忽略** |
| `mediump` 的 compute `vec4`（A1） | **55–57 / 61** | **253** | **被接受**：画面真的变了（1.0% 的像素通道差 > 0，位置偏差 0.18–0.40 px），而墙钟只省 2–3% |

也就是说：**图形管线里的 `mediump` 在 Adreno 740 上是空声明，compute 里的 `mediump` 是真的**。
前者「没有回归」不是好消息，是「这台设备上这类改动无效」；后者「有收益」也不成立——
2–3% 换 1% 像素变化不划算。三项**全部回退**。

### 一条实施中途才看清的因果：绘制记录不许变宽

U4 第一版把绘制记录从 4 段（64 B）扩到 5 段（80 B）来放新增的逐片量，实测在华为上
**现场消散 −15% 但回放出现 +8%**——回放路径每帧要把这一份记录整个写一遍再读一遍，
宽 25% 的代价盖过了片元侧省下的四个 `smoothstep` + 一个 `sin` + 一个 `pow`。

把 `replica` 与 `alive` 合成一个标志位、`radial` 与 `loosen`/`age_beat` 各用
`packHalf2x16` 打包之后，记录**仍是 64 B**，同一台设备上变成
**消散 0.953 / 出现 0.814 / 预读 1.063**，两条可见路径都是正收益。

这条因果同时解释了 U10a 为什么不成立：它要的第五段记录（+16 B/片/帧）比它省下的那一路
顶点属性更贵。**在这条管线上，绘制记录的每片字节数是比「属性流条数」更强的自变量。**
