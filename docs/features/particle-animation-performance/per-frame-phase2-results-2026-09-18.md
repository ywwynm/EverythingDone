## 1 采纳清单

按本专项的纪律：**两台都不劣化、至少主力机有可测收益**才收；华为量不出提升的项回退。
比值 = 离屏逐项 A/B 的配对中位数（`ParticleSegmentBench.runPhase2`），< 1 即为提速。

| 项 | 做法 | 华为（消散/出现/预读） | 魅族（消散/出现/预读） | 逐位 | 结论 |
|---|---|---|---|---|---|
| **U1** | compute→compute 的屏障只发 `SHADER_STORAGE`，只有 `resolveField` 保留三位全开 | **0.901** / 0.925 / 0.975 | 0.970 / 1.014 / 0.983 | 两台 **0 帧差异** | **采纳** |
| **U6** | `pressure-batched.comp` 的散度与占据度移出 shared（16 → 8 KiB） | 0.994 / 1.007 / 0.992 | **0.865** / 1.022 / **0.793** | 两台 **0 帧差异** | **采纳**（Adreno 上大赚） |
| **M1** | 非 Adreno 的工作组变体：一维核 256 → 64、`peel-blur`/`peel-project` 16×16 → 8×8 | **0.885** / 0.942 / 0.992 | 1.006 / 1.014 / 0.981（不走这条变体） | 两台 **0 帧差异** | **采纳** |

（浮点结合律变了），但两台实测**画面逐位相同**，实际上也是 G0。

### 回退的项与理由

| 项 | 两台的比值 | 回退理由 |
|---|---|---|
| **U2** 流场与置信度合成一张 RGBA16F | 1.065 / 0.968 / 0.978（华为） | **单格取样探针**（把 `sample_field` 换成只取一格、画面必然错）在三条路径上是 1.040 / 0.958 / 1.045——**那 32 次三维取样在 Maleoon 上根本不是瓶颈**，U2 的前提不成立 |
| **U2b** 三维采样器改 `mediump` | 1.058 / 0.956 / 1.013（华为） | 同上；且**画面逐位相同**（Adreno 61 帧全同）⇒ 驱动忽略 `mediump` 采样器 |
| **U3** `peel_field` RGBA32F → RGBA16F + 硬件双线性 | 1.131 / 1.001 / 0.939（华为） | 消散变慢。附带一条事实：**GLES 3.1 的存储图像格式表里没有 `rg16f`**，Adreno 740 直接拒绝编译，只能退到 `rgba16f` |
| **U5** varying 改 `mediump` | 1.047 / 0.989 / 1.014（华为）、0.975 / 0.969 / 1.018（魅族） | **两台的画面都逐位相同** ⇒ 两家驱动都把 `mediump` varying 当 highp 处理。按方案第 5 节的退出规则：**不要因为「没有回归」就留着** |
| **A1** `curl()` 与 `peel-blur` 的 `vec4` 改 `mediump` | 0.985 / 0.985 / 0.977（华为）、0.969 / 0.978 / 0.993（魅族） | 与 U5 相反，**compute 里的 `mediump` 是真的被接受的**：Adreno 上 55–57/61 帧画面不同、最大通道差 **253**、位置偏差 0.18–0.40 px。2–3% 的墙钟换 1% 的像素变化不划算 |
| **U10a** 合并成一个实例化顶点缓冲 | **1.126** / 1.080 / 0.982（华为）、1.011 / 1.023 / 1.025（魅族） | 它要的第五段绘制记录（+16 B/片/帧）比省下的那一路顶点属性更贵 |
| **M2 / M3** Mali 上改用逐次 Jacobi（含活动区域） | **2.964** / 1.004 / 0.798（华为） | 现场消散慢 **3 倍**。M2 只在 M3 打开时才起作用，随之一起否决 |

**一条贯穿本阶段的因果：在这条管线上，「绘制记录的每片字节数」是比「属性流条数」更强的自变量。**
U4 第一版把记录从 64 B 扩到 80 B 去放新增的逐片量，实测华为**现场消散 −15% 但回放出现 +8%**；
把 `replica` 与 `alive` 合成一个标志位、`radial` 与 `loosen`/`age_beat` 各用 `packHalf2x16`
打包回 64 B 之后，变成 **0.953 / 0.814 / 1.063**，两条可见路径都是正收益。U10a 的否决是同一条因果。

### U9：按实测帧率自动调低一档（已实现，**默认关**）

规则是纯逻辑（[ParticleAutoDowngrade]），JVM 单测覆盖六条：连续两轮「呈现/应有 < 0.8」才动手、
这一轮没采到就既不算好也不算坏、一轮达标就把连续计数清零、只降一档、用户自己改过之后不再自动降、
两项都到最省的一档时不再写设置。降档时**粒子大小与流动精细度各降一档**（第四批实测：
华为上这两项各调一档才从 0.19 回到 1.01，单调一项不够）。

界面上在读数行下面多一行提示，并告诉用户「恢复默认」可以改回去；文案进了全部 13 个语言目录。
**默认值不变**是用户上一轮的裁定，所以开关默认关，等裁定后再打开
（`ParticlePerfTuning.autoDowngrade`）。

## 5 批 E：交互到首帧

| # | 结论 |
|---|---|
| **L1** 首帧的呈现时刻写「尽快」 | **已经是对的，不用改。** 相位锁定之后 `ParticleClock.phaseLockedTarget` 返回的就是**本次 vsync 的时刻**（已经过去的时刻），`eglPresentationTimeANDROID` 的语义是「不早于」，所以首帧这一次写的就是「尽快」。第三批还把「呈现时刻下限」整段撤掉过（魅族的 SurfaceFlinger 不按 `desiredPresentTime` 推迟缓冲） |
| **L2** 左滑建材提前到 `ACTION_DOWN` | **已经是对的，不用改。** 首页的 `onInterceptTouchEvent` 在 `ACTION_DOWN` 就调 `ParticleSwipeAnimator.warm()`，它立刻抓快照并建动画层，`ParticleMicroflakePreparation` 的建材任务在动画层构造那一刻就派出去了——不等 `ItemTouchHelper` 判定。方案里「现在建材等判定」这个前提对首页不成立 |
| **L3** ADPF `PerformanceHintManager` | **已落地**（[ParticlePerformanceHint]）。周期负载：常驻 GL 线程每拍报一次本拍真实耗时，目标 16.6 ms；突发负载：建材线程在按下那一刻报一个 30 ms，让调速器在识别发生前升频。两条会话都是**线程局部**的，取不到（ROM 空实现）就整段是空操作 |
| **L4** 抓图按内容包围盒 | **没有头寸，不做。** 弹窗的离屏抓图用的是**弹窗窗口自己的 decor**，实测华为上附件弹窗的快照就是 651×641（不是 2880×1920 的整窗）；创建页那条链路抓的是整屏，而创建页本来就是全屏内容，包围盒等于整屏 |
| **L5** 前景纹理的上传路径 | **本轮只补了取证**：会话在 `startupTimings` 末尾追加了前景上传那一次 `glTexImage2D` 的墙钟，下一轮矩阵即可判断值不值得换 PBO。没有在没有数字的情况下先改 |
| **L6** `primeParticleSurface` 的覆盖面 | 开关默认开，左滑与创建页两条路径都走同一个 `ParticleWindowSurface`；本轮矩阵里「请求 → 首帧呈现」没有出现「第一次特别慢」的形态，判为已覆盖 |
