**读法**

1. **最差的一格是「弹窗 A 消散接 B 出现」**：A 的消散呈现间隔 p90 85.6 ms、最大 227.8 ms；

   （观察器 `precomputeMs`），A 的出帧就排在这一大批 compute 后面。这是方案 F14（双上下文分优先级）
   最直接的证据。
2. **快拖只出 9 个不同画面**（移动期 791.9 ms，含末尾按住不动的 600 ms；真正在动的 180 ms 内更少），
   间隔 p90 恰好是 33.22 ms = 2 × 16.6 ms，即**每两个 vsync 才出一帧**。
3. **点外部关闭比返回键关闭更差**（0.815 对 0.886，最大间隔 223.7 对 87.9 ms）：没有涟漪结算这段缓冲，
   消散与「弹窗窗口拆除」撞在一起。
4. **颜色面板（15.8 万片）消散 0.776**，是弹窗里最差的一格；它的片数比附件弹窗多 48%。
5. **新建记事的预算在这台设备上一次也没命中**——见第 6 节的缺陷。

## 3 每帧分段归因

### 3.1 方法与它的两条边界

沿用阶段 0 的三条口径，但这一轮把它们的适用范围划清了：

- **分段 `glFinish`（探针模式 c）**：给出所有段的**相对量级**，包括 compute 段（Adreno 的
  `EXT_disjoint_timer_query` 不计 compute dispatch）。代价是串行化，本轮实测整段比无插桩慢约 20–25%，
  而且**每一段的读数 = 该段 GPU 时间 + 失去的 CPU/GPU 重叠**，所以不能直接当份额。
- **消融（离屏基准，成对 A/B）**：给出**份额**，但只对**不回灌模拟的段**成立。
  2026-09-17 首轮实测：单独跳掉 splat / blur / jacobi / project 中的任何一级都会改变压力场的内容，
  进而改变活动 tile 列表与粒子散布范围——`no-jacobi` 与 `no-project` 因此比基线还**慢** 9%–23%。
  **这类消融测的不是「那一段值多少」，而是「场坏掉之后整条管线变成什么样」，已从条件表里删掉。**
  留下的是绘制侧（pass0 / pass1 / resolve / clear）、历史转存，以及「整段压力都不做」。
- **绝对值以整段墙钟为准**：离屏基准整条序列只在末尾 `glFinish` 一次。
  首轮逐帧 `glFinish` 时同一条件两遍能差 2–3 倍（GPU 在每次 CPU 提交期间空转，调速器随即降频），
  改成整段一次之后三遍的离散度降到 ±3% 以内。另外先跑一遍热身丢掉、按「外层配对、内层条件」轮转。

### 3.4 每帧 dispatch 数与 CPU 提交

探针的 `count:` 计数（`gpu/fenceA`、`gpu/fenceB`）：

| 帧类型 | compute dispatch | 绘制调用 | 合计 GL 提交 |
| --- | --- | --- | --- |
| 现场消散一帧 | 25（积分 4 + splat 2 + blur 2 + tiles 2 + Jacobi 14 + project 1） | clear 1 + pass0 1 + pass1 1 + resolve 1 | **29** |
| 回放一帧 | 1（历史恢复） | 同上 4 | **5** |
| 预读一个采样 | ≈ 41（积分 6.5 + 1.62 次压力 × 21） | 0 | **≈ 41** |

Jacobi 的 14 次 = 100 次迭代按每批 8 次分成 13 批，加一次 tile 目标清零。

CPU 提交时间（观察器 `draw` 时间戳，本会话发 GL 命令那一段的墙钟，不含 `eglSwapBuffers`）：

| 场景 | p50 | p90 | 最大 |
| --- | --- | --- | --- |
| 弹窗现场消散 | 1.4–1.8 ms | **2.6–3.1 ms** | 5–9 ms |
| 弹窗回放出现 | 0.4–0.5 ms | 0.53–0.69 ms | 1–3 ms |
| 左滑（回放 + 预读） | 0.5–0.6 ms | 0.86–0.91 ms | 2–4 ms |

消散一帧的 CPU 提交 p90 是 2.6–3.1 ms，对 8.99 ms 的 GPU 帧是 29%——**29 次 GL 提交里 25 次是 compute**，
A2（把逐步的量提成 uniform / 预算进材料缓冲）省的正是这一段的重设与提交。

### 3.5 这一节最重要的三条

1. **两遍实例化绘制是弹窗路径的大头**：现场消散 56.3%、回放出现 87.1%。回放帧几乎就是「一次历史恢复 + 两遍绘制」。
2. **压力是左滑路径的大头**：现场帧 46.4%、预读 86.9%，其中 Jacobi 占一半以上。而它贵的原因不是粒子多
   （只有 2.4 万片），是**网格格数比整屏弹窗还多 44%**。
3. **全屏清空在 Adreno 740 上不要钱，resolve 也很便宜**：清空实测落在 ±1% 的噪声里，resolve 0.24–0.33 ms。
   方案 B6（原子包围盒 + scissor 清空/resolve）在这台设备上的**收益上限只有约 0.35 ms/帧（≤4%）**。

## 4 呈现链

`dumpsys SurfaceFlinger` 全量落盘再解析，摘录在
`tmp/particle-perf/per-frame/392QBFED2226B/composition/layers.md`（原始转储 gz 存档）。

- **粒子层全部由硬件合成器直出**。左滑期间 7 层、附件弹窗 → 录音弹窗期间 9 层（含**两个**粒子
  SurfaceView），**每一层都是 `composition: Device/Device`，没有任何一层退化为 Client（GPU）合成**。
  格式 `RGBA_8888_UBWC`、`dataspace:0x08810000`（FULL | SRGB | BT709），与宿主窗口一致。
- **缓冲**：全屏粒子层 1368×3192、**5 个**缓冲各 17.7 MB = 88.5 MB；录音弹窗那一层按弹窗尺寸
  1086×1470、5 × 6.3 MB = 31.5 MB。层是按窗口尺寸建的，不是一律全屏。
- **刷新率**：面板支持 60 / 120 / 20 Hz，统计上 60 Hz 占绝大多数（1d10h 对 120 Hz 的 20 min）。
  `FrameRateOverrides` 里有且只有一条 `(uid, frameRate)={10139, 60.00 Hz}`——**我们的 60 Hz 投票是生效的**，
  采样时刻的 `VSYNC period` 就是 16.67 ms。
- 但**左滑那两轮的宿主主线程节拍 p50 是 8.28 / 8.29 ms（120 Hz）**，而粒子层的呈现间隔 p90 是
  33.1–33.2 ms。也就是说：手指在屏上时系统把窗口拉到 120 Hz，我们的粒子层按 60 Hz 投票出帧，
  实际却是**每两个 60 Hz vsync 才出一个新画面**（30 fps）。瓶颈不在合成，在出帧本身（第 3.3 节）。

**结论：呈现链没有问题**，不必在 F16 上花时间；帧率问题全部在我们自己的每帧 GPU 工作量与
GPU 争用（F14）上。

## 6 顺带发现的缺陷：创建页的提前预算在这台设备上必然未命中

`matrix2` 连跑三次新建，三次的 `prewarm.outcome` 全是 `miss`：

| 轮次 | outcome | detail | 请求 → 首帧呈现 |
| --- | --- | --- | --- |
| 第 1 次（冷启动后） | miss | 还没有真实创建页快照可作预测素材 | 1065.9 ms |
| 第 2 次 | miss | **环境变了：hz=120 → hz=60** | 583.6 ms |
| 第 3 次 | miss | **环境变了：hz=120 → hz=60** | 574.4 ms |

`ParticleCreationPrewarm` 的缓存键里有一项 `|hz=`，取自 `decor.display?.refreshRate`。首页空闲时预算
（刚触摸过，窗口在 120 Hz）与点新建按钮时（已回落 60 Hz）读到的值必然不同，键因此**永远对不上**，
每次新建都白算一遍 307–367 ms 的轨迹再丢掉。这正是 `cache-keys-must-use-stable-values` 那条：
指纹里放了瞬时读数。已记入 followups。

## 7 实施批次建议排序

先把方案第 3 节逐条对着实测标注。「每帧收益」按第 3 节的份额给出，弹窗以 8.99 ms/帧、
左滑以 4.15 ms/帧、回放以 6.70 / 2.20 ms/帧为基数。

同一天并行跑的阶段 R（[research-2026-09-17-per-frame.md](research-2026-09-17-per-frame.md)）从资料与代码
事实那一侧给出了另一份裁定。下表在「结论」列里把两边合在一起；两份文件**在 A1 最优先、C10 提到第二、
B6 降级这三条上独立得出同一结论**，分歧只在 B4 / B5（调研否定、本轮的份额数字本身分不出来，以调研为准）。

| 项 | 实测对应的份额 | 预期收益 | 结论 |
| --- | --- | --- | --- |
| **A1** 逐顶点 → 逐片每帧一次 | 两遍绘制：弹窗消散 56.3%、回放 87.1%、左滑消散 28.9% | 顶点阶段的 sin/cos/exp/pow 全部消失。调研进一步指出是 **16 → 1** 次求值（Adreno 把顶点着色器编成 bin-pass 与 render-pass 两份），不是方案写的 8 → 1 | **第一优先** |
| **A2** 逐步 → 常量 / 材料缓冲 | 积分 + CPU 提交 19.0%（弹窗消散）、32.2%（预读） | 同时省 GPU 与那 25 次 compute 提交的 uniform 重设 | 高 |
| **A3** 流场采样次数 | 含在积分那一档里，未单独拆 | 调研查明是**每步最多 32 次 3D `texelFetch`**，落在上面那 19% / 32% 里 | 高，与 A2 同批 |
| B4 顶点拉取 + 索引四边形 | 同 A1 的两遍绘制 | Adreno 740 实测 `ssbo顶点=4`、`纹理缓冲=128 MiB`，路是通的；但调研指出 4 顶点带状实例化已经是最少的 VS 调用数，换形态不减少调用 | **不做**（调研否定，本轮份额数字分不出 A1 与 B4） |
| B5 两遍合一 | pass0 + pass1 中较小的一遍：弹窗 25.6% / 回放 40.2% | 调研指出表面与颗粒在交接时**可以同时存在**，合一省不掉顶点工作量，只换来叠画顺序变化 | **不做**（调研建议放弃） |
| **B6** 包围盒 scissor 清空与 resolve | 清空 ≈ 0（噪声内），resolve 3.4% / 3.5% | **上限 ≤ 0.35 ms/帧**；调研另指出 scissor 只能加在 resolve 上，清空必须保持整屏 | **降级，本专项不做** |
| **C7** Jacobi 迭代数 | 弹窗消散 10.3%、预读 31.8%；左滑消散 28.6%、预读 **53.5%** | 迭代减半 ⇒ 左滑预读每采样省约 1.1 ms（−27%） | 高（左滑与出现延迟） |
| C8 红黑 GS / SOR | 同 C7 的目标 | 收敛快 2–3 倍即等价于 C7 的更强版本 | 中，排在 C7 之后 |
| **C9 + C10** 网格与 halo | 压力总量：左滑现场 46.4% / 预读 86.9% | **左滑卡片 120,096 格 > 整屏弹窗 83,520 格**；调研另查明 halo **82%–89% 恒零**，且活动 tile 列表**只用在 Jacobi**，splat 清零与两遍 11 抽头 blur 仍是全网格 dispatch | **第二优先** |
| D11 精度 `mediump` | 积分 + 压力：弹窗 40.4%、左滑 64.2% | 调研把期望调低（ES 3.1 只有 `mediump`，Godot 实测 2–3%），且该改的是 `material.frag` 的颜色链与 `peel-blur.comp` 的 `vec4` 卷积 | 中，排第二批之后 |
| **E12** 按 dp 定微片尺寸 | 片数直接缩放绘制（56–87%）、splat、积分与建材 | 15.9 万 → 约 7 万；是唯一同时压住所有段的一项 | 高，但**须用户看图定夺** |
| E13 按场景分档 | 同上 | 左滑卡片已经只有 2.4 万片，收益主要在弹窗 / 创建页 | 中 |
| **F14** 双上下文分优先级 | attach-audio 那一格：A 的消散间隔 max 227.8 ms，同时 B 在跑 907 ms 预计算 | 直接修掉最差的一格；调研提醒优先级只是规范定义的 hint，必须 `eglQueryContext` 读回，且 Adreno 的抢占点在 bin 边界，`yieldToWindow` 不应直接删 | **第三优先** |
| F15 左滑预读档数 | 预读 4.16 ms/采样 | 采样便宜下来（C9/C10）之后再定 | 低，排在 C9 之后 |
| **F16** 合成侧 | **实测全 Device 合成、无 Client 回退、60 Hz 投票生效** | 无 | **不做**（第 4 节已结论） |
| G17 左滑首帧 | 建材 11.9–16.2 ms、识别 → 首个非零 64.9 / 73.7 ms | 目标 < 50 ms；魅族的建材已经不是大头（三星是 63–72 ms） | 中，随 C9/C10 一起看 |
| G18 弹窗消散压进涟漪期 | 魅族上请求 → 首帧提交已是 72–98 ms | 魅族没有 OPPO 那种 1.5 s 结算等待 | 低（魅族），保留给 OPPO |
| G19 创建页窗口起来 | 本专项不动 | — | 不做 |

**建议的前三项**

1. **A1 + A2 + A3 一起做「把不变量挪出逐顶点 / 逐步」那一批**（全部 G1）。A1 打的是弹窗消散 56%、
   回放出现 87% 的两遍实例化绘制——注意**绘制形态不用换**（B4/B5 已被调研否定），要换的是
   顶点着色器里算什么；A2/A3 打的是积分那 19%（弹窗消散）/ 32%（预读），其中 A3 的
   「每步最多 32 次 3D `texelFetch`」是单点最集中的一块。
2. **C9 + C10「压力网格与 halo」**。左滑那张卡的网格比整屏弹窗还大 44%，压力占左滑现场帧 46%、
   预读 87%；halo 有 82%–89% 恒零，而活动 tile 只用在 Jacobi，splat 清零与 blur 仍跑全网格。
   收益是「左滑跟手」与「出现预计算 / 首帧延迟」两头一起动，且卡片内可做 G0 逐位对照。
3. **F14 双上下文分优先级**（G0，不改任何画面）。最差的一格（弹窗 A 消散接 B 出现，间隔最大
   227.8 ms、B 的首帧 940.7 ms）的直接成因就是 B 的 907 ms 预计算与 A 的出帧抢同一条队列。

同时**把 B4 / B5 / B6 / F16 从排期里拿掉**（前两条调研否定，B6 实测 ≤ 0.35 ms/帧，F16 实测为零），
并把第 6 节那条预算缓存键的缺陷单独修掉——它比本专项里任何一项都便宜，而每次新建能省
307–367 ms 的白算。
