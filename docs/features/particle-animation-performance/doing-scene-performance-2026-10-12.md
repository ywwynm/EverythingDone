# Doing 整页绘制性能回退优化（2026-10-12）

用户要求继续消除三星流体与魅族飘散的回退，保留 SurfaceView、动态背景、现有动画表现；三台 Android 的画面、功能、帧率和响应通过后，才设为正式方案并发布阿里云。授权继续使用既有三台设备，不修改真实记事；不创建 Git 提交。

## 反馈循环与假设

复用上一轮固定种子 `20261012`、90 行虚构长卡片、真实计时控件及手势的同包 A/B。性能运行不录屏、不导出关键图像；可见画面和动态背景单独检查。先复测三星 FLOW、魅族 DRIFT 各一组，随后按归因补最少量试验，最终三机合并回归。没有粒子有效显示窗口或发生降级的样本不能算作通过。

上一轮复现：三星 FLOW 98.4→89.5 FPS（前一组 100.9→89.2），魅族 DRIFT 118.1→111.3 FPS，首回调 323.7→357.0ms。回调不代表屏幕光学延迟。

按优先级检验：

1. 整页导入后的 GPU 复制与粒子争用。如果消除重复复制而保持缓冲生命周期安全，绘制／等待成本应下降，动态内容不变。
2. 没有内容变化也反复捕获。如果按真实失效记录调度，静止阶段捕获次数应下降，而计时变形、滚动、GIF 和独立 Surface 仍持续刷新。
3. 页面生产、图像回收和 GL 显示串行化。如果减少无必要的队列等待，呈现间隔改善；不能以提前归还缓冲或跳过交接换取收益。
4. 首卡材料准备与页面更新竞争。如果仅优化准备期间的重复工作，首粒子回调改善，而稳态粒子数量、样式与随机参数保持一致。

## 首轮复测与单变量候选

- 同包复测三星 FLOW 为原路径 101.7、整页 96.0 FPS；魅族 DRIFT 为 115.8、118.1 FPS，但首回调 282.3→325.5ms。魅族帧率回退并非每次出现，保留此前负面样本，不能以本次无回退结束验收。
- 首先只替换页面图像所有权：直接导入 HWUI 缓冲，当前显示帧一直保留，前帧最后一次 GPU 读取完成才归还；下一张捕获同时等旧帧归还与层交换完成。没有改粒子材质、颜色或模拟。
- `ParticlePageFrameGate` 在真实页面消费者处协调两种回调顺序；四项单测覆盖首帧保留、GPU 延后归还、归还早于交换和退出后迟到释放。页面缩放暂存旧 ImageReader，直到仍在显示的旧图像释放，不能提前关闭。
- ImageReader 上限为四张：显示帧和交接帧外，为 `acquireLatestImage()` 留出两个空位；额外 Ripple 帧继续在消费者线程立即归还，避免重新形成退出时的队列互等。接口约束见 [Android ImageReader 文档](https://developer.android.com/reference/android/media/ImageReader#acquireLatestImage())。候选性能与画面尚待同输入实测。

## 阶段测量

- 直接导入后，三星 FLOW 两次为 105.2／106.2 FPS，高于本轮原路径约 101.7。页面上传采样中位从约 1.69ms 降到 0.32～0.42ms；原先高位上传可超过 8ms。支持重复复制是三星回退的主要来源。
- 魅族直接导入后仍有 109.1／115.6 FPS，原路径约 115.8～119.4，不能宣布已解决。节拍级取证中 GPU fence 中位约 0.009ms、P90 约 0.016ms，普通绘制 CPU P90 约 0.93ms；不像持续 GPU 饱和。另一次主线程页面记录中位 0.26ms、P90 2.38ms，而 syncAndDraw 中位约 0.25ms，不支持把整个问题归给同步调用阻塞。
- 页面硬件导入仍每帧重新建 EGLImage。加入按 HardwareBuffer ID 的导入对象复用，保持每次取得图像都等待生产者 fence 并重新绑定纹理；缓存只省对象建立，不复用旧像素。页面退出时有引用的纹理保留到窗口移除，无引用的及时释放。
- 连续页面更新原本经历上传→主线程回调→GL 换层；改为同一 GL 任务内上传并换层，首帧和卡片交接仍走提交确认。此项只改变排程，不减少内容刷新频率。正在同输入验证。

## 冷启动内容取样归因

- 单次短手势不能代表持续表现，扩展为同一页面连续三次相同滑动，并启用既有 debug 节拍记录。魅族整页前三次为 108.7／111.5／116.6 FPS，原路径约 117.2～118.6；首回调整页 352／342／126ms，冷启动竞争仍存在。
- 内容分析线程的独立测量：原路径首次取样 179.4ms、分析 60.8ms；整页首次取样 189.0ms、分析 76.9ms；取样随 JIT 预热逐次下降。CPU 时间接近墙钟，证实主要在逐点 `DirectByteBuffer.getInt` 及内容分析，不能把这段计成背景 PixelCopy 或 GL 等待。
- 改为一次批量读取 RGBA 整字到数组，随后按原取样下标和顺序选择样本；颜色、预乘值、量化、权重及粒子数公式不变。现有 `ParticleDriftContentSamplesTest` 与旧实现逐位比较，覆盖字节序、只读缓冲、非零位置、各尺寸及透明度；以这些真实算法对照验证后再上机。
- 另一次脚本失败来自 ADB push 替换 `ui-request` 时的文件间隙，非页面崩溃。脚本改为临时文件加原子重命名；失败运行不计入有效性能样本。

- 批量缓冲读取先将魅族首次取样降到约 70～76ms，连续取样约 13～22ms；继续把相同下标的整字提取移至既有材料 JNI 库，避免冷态 Java 循环成本及整图临时数组。只提取原始 32 位值，不迁移颜色分析、浮点权重或分布公式；不可用时保留批量 Java 路径。
- 三台实际设备各完成 20 组 JNI／独立字节基准／Java 分析对照与 2 组越界检查。覆盖大小尺寸、两种字节序、只读缓冲、非零当前位置、非对齐切片、重复颜色与透明像素，逐位通过。正在执行不带录屏和节拍取证的三机两样式连续滑动配对。
- 三星、OPPO 的长卡片上下滚动、计时填充／描边变形、无限呼吸和动态色条已完成新旧配对；两侧均正常回到静止 25:00，卡片恢复 alpha=1、容器 alpha=0.84。三星录像已顺序解码并核查，未见卡片空白；OPPO 仍只有截图和状态证据，不计为逐帧验收。

## 魅族排程定位

- JNI 取样后的三机连续滑动中，三星 FLOW 整页 107.4／111.8／112.2 FPS，原路径 103.6／104.0／105.8；魅族 DRIFT 整页 110.5／114.1／117.7，原路径 118.5／117.5／119.6。魅族仍未达到切换默认的条件。
- 将显示列表记录与图像消费解耦、每次 preDraw 都记录的试验没有改善，已撤回。存在首次异常低值 68.6 FPS；后续配对仍约 108.7／113.2／118.6，不能保留这个额外工作。
- Perfetto 与驱动时间戳对应：粒子每拍均有提交，部分帧错过显示后被下一帧替代。四个丢帧样本的 GL 线程已就绪，但被同核的主线程抢占约 2～2.8ms；主线程正在进行整页记录，GPU fence 本身很短。候选应调整整页记录与粒子合成的先后，不能通过降低背景刷新频率掩盖问题。
- 诊断序列化还带来额外 CPU 和一次约 3.3ms 的报告锁争用，需缩小锁范围并降低实时落盘干扰；导出的事件内容不能缺失。

### GPU 与 Java 热点补充

- 驱动 GPU 完成时间显示，整页绘制比原路径约多 0.3～0.4ms，叠加主线程调度后部分帧错过显示。延后背景合成和直接 blit 的试验尚未稳定消除回退；不能只计第三次预热后的 120 FPS。
- simpleperf 与 ART 方法采样用于定位，不计为性能验收。计时器 Path.lineTo 与轮廓装配占有明显主线程开销，原路径也有。开始验证按字形版本缓存完全相同的 Path，去掉轮廓光／字形之间及静态数字的重复装配，不减少动画采样频率。详细决策同步记录到 timely-digit-typography。
- 直接 blit 未稳定消除魅族回退，已移除该分支与额外 FBO。候选改为在第一个飘散会话的最终合成中读取唯一整页底图，采用相同的预乘 src-over 公式，省去一次整页背景绘制。原路径编译原始着色器，多个会话仍按创建顺序逐层绘制，不限制重叠转场。
- 三机各 60 组实际 GPU 分层／合并对照通过，覆盖透明／半透明图像、1／0.84 源透明度、加光／src-over、正负偏移、裁剪及倒放；各机最大通道差 1/255，差异通道约 0.06%～0.09%，来自两次绘制与一次浮点合成的量化差异。此为缓冲像素证据，仍需屏幕录像检查动态与交接。
