# 粒子动画性能优化方案（2026-09-14，阶段 0 之后修订）

分析见 [analysis-2026-09-14.md](analysis-2026-09-14.md)，平台调研摘要见 [research-2026-09-14-platform.md](research-2026-09-14-platform.md)，阶段 0 的基线与归因见 [phase0-baseline-2026-09-14.md](phase0-baseline-2026-09-14.md)。用户裁定 D1–D6 见 [decisions.md](decisions.md)。本方案不改粒子模型：材料规则、随机、粒子数量、240 Hz 积分、100 次压力迭代、寿命、材质与时长全部保留。

## 视觉保证级别与验收口径

- **G0**：GPU 输出逐位不变。验收沿用现有工具（`ParticleTrajectoryCheck` 一类离屏对照）：固定素材、方向、种子，两台设备 61 帧 RGBA 散列必须与改动前一致。
- **G1**：算式不变、只有浮点合并顺序不同。验收：同一输入的并排视频（1 倍速与 0.5 倍速）、逐帧差值图与 ꟻLIP 误差图、沿主前沿的放大分页，先自己逐页看再交用户判断；数值只用来定位差异位置；门禁显式挡 NaN。只有 2.5 可能用到。
- 性能口径：真实系统输入 + 只读观察器 + 窗口 FrameMetrics，按阶段 0 第 6 节的基线表在右侧加列复测；四个固定场景（添加附件 → 录音行、新建按钮 → 创建页、卡片慢拖与快拖、同一弹窗连开关 10 次）两台设备各至少三轮，报告分布。工具：`device_particle_perf.py`、`analyze_particle_perf.py`、`device_particle_cleanup.py`。

## 阶段 0 已完成，结论摘要

- 屏障不是瓶颈：去掉积分步之间的 240 次屏障，耗时不变、输出零差异。预计算 1540–1660 次 dispatch 里，压力更新占 39–45%、积分含计算 21–33%、其余（历史转存、重绑、CPU 提交、历史缓冲分配）22–40%；栅栏同步与 DVFS 都不是。
- 涟漪：60 Hz 窗口投票把 OPPO 上涟漪期的弹窗帧数从 34 砍到一半（撤掉后 67–69 帧、P95 10–17 ms）；GPU 排队只占 1–4 ms；三星上自绘涟漪单帧成本本身偏高（P95 32–63 ms，系统涟漪 8–17 ms）。
- 缺陷：OPPO 上点"录音"后 `ParticleTouchFeedback` 等不到涟漪结算、走满 1.5 s 超时，添加附件面板的快照多停 1.3 s。
- 主线程有活停顿的栈顶多在 RenderThread 同步、Binder、TextureView 拆除（`nDetachSurfaceTexture`）与录音弹窗自身的传感器/通知渠道初始化。
- 三星正向消散每帧 GL 提交 + `glFinish` 等待 P50 已达 14–15 ms，消散是帧率临界路径；三星快拖 180 ms 只出 8 个画面。

## 第一批（G0，一次发布）

### 1.9 修 `ParticleTouchFeedback` 的结算缺陷（新增，优先级最高）

现象：OPPO 上 `GradientRippleDrawable.hasVisibleFeedback` 一直为真，消散等到 `500 + 1000 × 时长缩放` 的兜底超时才开始。要求先在 OPPO 上复现并记录涟漪状态机（pressed 变化、三个动画器的 start/end/cancel、`alphaFraction` 时间线、控件 attach 状态），找到淡出为什么没开始，修根因；再把兜底改成与涟漪实际寿命匹配的量（扩散 256 + 淡出 300 ms，乘时长缩放，再加少量余量），并在源控件已 detach 或动画器都不在运行而 `alphaFraction > 0` 时视为已结算。验收：OPPO 与三星上"添加附件 → 录音行"的消散首帧回到与"返回键消散"同量级（约 100–130 ms），涟漪本身仍完整播完。

### 1.8 粒子时钟脱离主线程

`ParticlePlaybackClock` 的 Choreographer 改挂 GL 线程自己的 Looper；进度按目标呈现时刻推进，不用 `frameTimeNanos` 差值判断隔了几拍（120 Hz 上一次 8.33 ms 迟到就会被重吸附相位）；`eglPresentationTimeANDROID` 继续逐帧设置。阶段 0 条件 (d) 已验证它不退化帧数与间隔，并减少"有活停顿"样本。

### 1.6 主线程减负

- 圆角遮罩从主线程挪到材料线程，在取像素之前做。
- 暗层与粒子层改挂 DecorView 的 `ViewGroupOverlay`（不触发整窗 `requestLayout`，自行 `measure` + `layout` 成全屏）；TextureView 放进 overlay 后要验证 SurfaceTexture 创建、`postInvalidateOnAnimation` 与拆除都正常，不正常则退回普通 `addView` 但给固定尺寸布局参数。
- 录音弹窗自身：倾斜传感器注册（`startTiltSensor`）与通知渠道创建（`ensureNotificationChannel`）移出主线程或延后到出现动画结束之后，行为不变。
- 快照录制保持在主线程，`syncAndDraw` 之后不再做任何等待。

### 1.7 CPU 线程优先级

材料线程与预计算在涟漪或播放期间用默认优先级，只有播放 GL 线程保持 `THREAD_PRIORITY_DISPLAY`。

### 1.5 常驻渲染线程与上下文（D4：全部常驻不释放）

进程内一条常驻 GL 线程与 EGL 上下文；程序编译一次；累积纹理按屏幕尺寸常驻；流场纹理上传一次；历史缓冲改为常驻、只增不减，按需要的最大尺寸分配（阶段 0 的"其余"一档里含 `createHistory` 的 60–120 MB 分配，实施时记录它的实际耗时）。每次动画只创建自己的材料/状态 SSBO，结束只删这些；多个叠加层共用同一线程，每个节拍依次画各自的帧（本批仍是每层一个 TextureView 表面，同一上下文切换表面；第二批收敛为一窗口一个 Surface）。预热改为在同一上下文上真正预热。

### 2.2 Jacobi 扩大 tile、增加每批迭代（G0，GPU 侧最高优先级）

压力更新是预计算与每帧 GPU 的最大单块。Adreno 分支：32×32 tile；k=12（shared 约 25 KB，每次更新 9 次 Jacobi dispatch）或 k=16（约 32 KB，贴上限，7 次），实测选；散度与占用留寄存器；运算顺序不变，61 帧散列必须一致。非 Adreno 保留现状（Mali 无片上 shared）。同时在压力更新内部找安全的 G0 合并：模糊两遍合一（2.3）、tile 计数器复位并入前一个 dispatch、清目标与下一趟的合并等，每一处都以散列一致为准。

### 2.1 历史转存并入积分（G0）

第 4 步积分着色器末尾直接写历史（纯拷贝）。按"少一次 dispatch 和一次全缓冲往返"预期收益，不是按屏障。

### 2.4 首生之前跳过积分与压力（G0）

由材料的最早出生时间决定；之前的状态与压力场恒为初值。

### 2.5 四步积分合并：只做探针（D1）

本批只实现诊断变体：着色器内循环四步、每子步仍写回并读回 SSBO（`volatile`），测预计算与每帧墙钟差值并核对 61 帧散列。散列一致且预计算收益 ≥ 10 ms 才保留为正式改动；否则记录数字、删除变体，不进入 G1 流程。

### 1.10 三星自绘涟漪单帧成本（诊断 + 小修）

用阶段 0 原始数据里录音行场景的 FrameMetrics 分段（输入、布局、绘制、同步、GPU）先定位三星上 32–63 ms 单帧花在哪一段；若在 `GradientRippleDrawable` 自身（重建 shader、失效范围过大、触发布局），在不改外观的前提下修；若在窗口层面（软件渲染、整窗重绘），记录并留到第二批。

## 第二批：SurfaceView 与刷新率（D3、D5）

### 1.4 叠加层从 TextureView 改为 SurfaceView，一个窗口只用一个 Surface

`setZOrderOnTop(true)`、`setFormat(TRANSLUCENT)`；所有并发会话由常驻线程画进同一个 Surface；去掉每帧 `glFinish`，改栅栏节流；"首个粒子帧已显示"改由 `EGL_ANDROID_get_frame_timestamps` 的显示时间判定（先探测支持、处理 PENDING），不支持时退回窗口帧提交回调。快照 `ImageView` 的遮蔽逻辑不变。表面仍在 Dialog 窗口之下，与现有"先就位、后揭开"顺序一致。海浪窗口等独立 Surface 的交接像素回归整套重跑。这一批单独发布并做交接回归。

### 1.2 取消窗口刷新率投票，改 Surface 无缝投票

删除 `ParticleWindowFrameRate` 的窗口属性投票；粒子 Surface 创建时一次 `setFrameRate(60, FRAME_RATE_COMPATIBILITY_DEFAULT, CHANGE_FRAME_RATE_ONLY_IF_SEAMLESS)`；每帧继续 `eglPresentationTimeANDROID`。阶段 0 已证实撤掉投票后 OPPO 涟漪帧数翻倍。

## 第三批：延迟专项

### 3.1 左滑

按下准备完成、GPU 空闲时先预备前 6 档；手指在动时按速度预读 1–2 档；验收指标是三星快拖 180 ms 的不同画面数从 8 提上去、识别后首个非零画面在一个节拍内。

### 3.2 出现前的固定段

快照像素只拷贝一次，`copyPixelsToBuffer` 的字节直接上传；材料线程读同一份。EGLImage 零拷贝留后续。

## 推迟或不做

- **1.3 低优先级上下文：推迟。** 阶段 0 证实 GPU 排队只占涟漪卡顿的 1–4 ms；两批做完后按同一口径复测再定。
- **1.1 涟漪混合方案：看第一、二批后的复测。** 三星上仍有 > 33 ms 的有活停顿落在扩散期内时再做。
- **2.6 限定 resolve 范围、EGLImage 零拷贝、ADPF 抬频**：后续事项。
