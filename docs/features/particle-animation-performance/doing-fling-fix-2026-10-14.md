# DoingActivity 三台手机惯性滚动修复

后续反馈：用户在 `202610141152` 上仍能观察到 OPPO 惯性到底部回弹／急停卡顿，指定首项为“右滑记事的动画优化”的清单。以下结果只证明此前所测持续滚动阶段改善，不能据此认定边界停止和回弹已解决；新增边界专项取证见 [边界诊断](doing-edge-scroll-2026-10-14.md)。

## 范围与已有证据

本轮在三星 `R5CW20BLNKL`、魅族 `192.168.100.67:40807`、OPPO `3B1629006YC00000` 上修复并验证。OPPO 实际报告 PLZ110／API 37；平板已断开。保留整页 GL、粒子、计时数字与 GIF 动画。

前一轮长清单 SETTLING 的完整活动窗口呈现率：三星 117.11、魅族 34.05 帧/秒；长文本加 GIF 为 113.35／38.13。魅族输出节拍仍约 120 Hz，页面记录和最终 GL 合成耗时较低，延迟集中在页面 ImageReader 获取、等待栅栏与 GL 交接。详情见 [真实清单测量](doing-real-checklist-scroll-2026-10-14.md)。

## 排序假设与验证计划

1. 离屏生产者在松手后被延迟调度：拆开 ImageReader acquire、生产者 fence、HardwareBuffer 包装的耗时。如果真正耗时在生产者等待，检查提交帧时间及 RenderThread/GPU 调度。
2. 缓冲持有或归还引起隐式等待：记录获取、释放、导入边界，验证队列是否持续有足够空闲缓冲；不能通过删掉正确性所需栅栏来掩盖问题。
3. GL 队列阻塞：拆开提交→开始执行与实际导入，判断是否有其它任务占用该线程。

先在新 OPPO 补充现版本长清单和 GIF 基线各一轮；归因探针优先在魅族合并一轮，只有证据不足时增加有明确区别的实验。确认修复后，三机各做一轮合并矩阵；用户要求的反复 fling 每场景包含多次交替滑动。真实记事与计时记录只读校验。

## 第一轮细分结果

- 三机当前 APK SHA256 相同，均为此前发布的 `202610140919`；已备份 APK 与数据库只读校验。新 OPPO 长清单 12 次 fling 的完整活动窗口呈现率 64.37 帧/秒，100ms 之后的帧间隔指标为 60.06 FPS，尚未出现魅族的数百毫秒停顿。
- 魅族追加 8 次 fling 的阶段探针确认：100ms 后生产者 fence 等待 P95 仅 0.317ms、GL 排队 P95 0.650ms；此前合并统计的“fence”长耗时实际主要发生在 `Bitmap.wrapHardwareBuffer`（P95 84.151ms）及 GL 导入步骤（P95 42.545ms）。因此不能称为 GPU 栅栏等待慢。下一步去掉持续页面中间的 Bitmap 包装，直接导入同一 HardwareBuffer；保留生产者 fence、消费者 GPU 读取栅栏及原缓冲租约。
- OPPO 视频样本两次未开始采样：新设备缺少隔离测试媒体 `doing-refresh-fixtures/video.mp4`，触发探针的明确检查。排除这两次运行，先补齐与其它设备相同的测试媒体再测；不属于业务界面崩溃。

## 第二轮归因

- 直接缓冲后，魅族包装 P95 降为 0.078ms（此处已只是取得句柄），导入 P95 降为 0.112ms。仍有 100ms 以上停顿，全部与 `SYNC_FRAME_DROPPED` 对应；API 约定渲染器自动在下一 vsync 续帧，但本机实际等到数百毫秒至一秒。追加一轮 Perfetto 对照 RenderThread，区分调度与同拍重复提交。
- OPPO 视频详细探针：页面请求／GL 输出节拍均约 120Hz，生产者、包装、导入均无长等待；主线程派发中位 3.309ms，GL 完成后的回调总延迟中位 8.433ms，完整捕获中位 16.611ms。GL 队列和导入均约 0.1ms，怀疑同步 Handler 被下一次遍历的消息屏障延迟。只将已完成图像及 GL 完成回调改为异步 Handler；输入反馈的原窗口遍历顺序保持原样。
- OPPO 新装调试包出现系统 16KB ELF 对齐提示，已按实际 UI 树点击“确定”；不改变“不再显示”设置。测量脚本识别这一确切提示并等待目标卡片出现；未开始的样本排除。此提示与本次滚动问题分开记录。

## 已确认的修复

1. 魅族 Perfetto 的长等待中持续出现 `Frame skipped: AlreadyDrawn`，RenderThread 仍在调度，并非长时间占用 GPU。追加提交时钟探针确认：`AnimationUtils.currentAnimationTimeMillis()` 在 fling 中相对 `System.nanoTime()` 中位领先 15.111ms、P95 439.821ms、最大 690.465ms。`HardwareRenderer.createRenderRequest()` 默认继承前者，污染离屏帧时间；改为公开 API `setVsyncTime(System.nanoTime())` 后，1829 个 fling 后段捕获全部状态 0、捕获链 P95 6.983ms、最大 17.370ms。未改控件或粒子的动画进度。
2. 持续页面直接将 ImageReader 的 HardwareBuffer 交给现有 EGLImage 缓存；不再先包装 Bitmap 再取回 HardwareBuffer。保留生产者 fence、Image 租约及 GPU 读取结束后归还；不支持直接导入时保留原 Bitmap／像素回退。
3. 已完成图像与直接缓冲上传完成的回调通过异步主线程 Handler 派发。OPPO 后段捕获链中位从 16.611ms 降到 5.694ms，主线程接收 P95 0.215ms、上传完成 P95 0.428ms，捕获节拍约 121Hz。输入反馈仍通过原同步 Handler 等待原窗口遍历，保护原生 Ripple 初始化。

时钟依据：[HardwareRenderer.FrameRenderRequest](https://developer.android.com/reference/android/graphics/HardwareRenderer.FrameRenderRequest) 允许 CLOCK_MONOTONIC 的 `System.nanoTime()`；[AOSP FrameRenderRequest](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android15-release/graphics/java/android/graphics/HardwareRenderer.java) 默认来自 AnimationUtils；[CanvasContext](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android15-release/libs/hwui/renderthread/CanvasContext.cpp) 以帧时间差判断 AlreadyDrawn。厂商预测时间的具体来源未反编译确认，结论限于本机实测的 API 返回值与渲染行为。

性能回归使用真正的设备输入、完整 SETTLING 窗口及驱动呈现时间戳，作为原问题的回归判据；单纯 JVM 测试无法覆盖 OEM 帧时钟和 MessageQueue 屏障。另增加实际 HardwareBufferRenderer 生产的 12 帧／三缓冲复用像素对照，检验直接导入与原 Bitmap 路径一致。

## 三机复杂卡片反复 fling

每机四类卡片各 12 次交替上下甩动，共 144 次；140ms 和 80ms 两种输入，松手后等待 2.4 秒，清单为实际渲染的 90 项三级清单，视频由同一 MP4 生成 75 帧 GIF，测前确认正在播放且帧号变化。下表按完整活动窗口计唯一真实呈现帧，单位帧/秒。此阶段不录屏、不启用详细时序探针。

| --- | ---: | ---: | ---: | ---: |
| 三星 SM-S9180 | 116.04 | 112.92 | 111.81 | 113.40 |
| 魅族 20 Inf | 119.18 | 120.23 | 119.99 | 120.10 |
| OPPO PLZ110 | 118.49 | 119.18 | 119.04 | 118.95 |

原版本同类长清单／GIF：三星 117.11／113.35，魅族 34.05／38.13；新 OPPO 本机现版本基线 64.37／65.76。三星保持原有水平，魅族与 OPPO 明显改善；各机分辨率、布局、系统惯性时长不同，不把表格作为硬件排名，也不宣称三星所有帧均达到 120。魅族面板实测略高于 120Hz，故有效呈现率可略高于 120。

三机 12 个场景中的最大呈现间隔不超过 25.014ms，未再出现此前魅族约 0.55 秒停顿。长清单最大间隔为三星 25.014、魅族 16.607、OPPO 16.593ms；P95 分别 8.338／8.289／8.297ms。本轮主体样本的 OPPO 惯性约 0.4 秒，另加更大位移的长 fling 与内容位移探针，单独核验持续阶段，避免外推。

三机各通过：12 帧三缓冲复用的直接／Bitmap 导入像素完全一致；60 组合成最大通道差 1；792 组计时路径逐像素一致；3 个流体相位程序逐像素一致。JVM 共 1496 项，0 失败、0 错误、1 跳过。首次新增像素探针错误复用了会被旧 Bitmap 路径关闭的 Java 句柄，已改为独立句柄后重跑通过，非生产代码缓冲失效。

## 持续滚动、真实记事与画面回归

追加三机各 4 次大位移 fling，同时记录 RecyclerView 实际滚动偏移和每次页面捕获。三星／魅族／OPPO 完整惯性窗口呈现率为 118.29／118.89／119.50 帧/秒；最大惯性时长分别 0.916／2.669／0.874 秒。魅族四段均超过一秒，松手一秒后帧间隔 P95 8.294ms、最大 16.579ms。三星和 OPPO 在本次输入下未超过一秒，不宣称这两台取得了一秒后的样本，也未修改系统惯性参数。

松手后 100–600ms 内，含新清单偏移的捕获间隔 P95 为 9.400／8.766／8.585ms，最大 10.851／13.449／15.464ms。确认计时之外的卡片内容持续更新。部分系统一拍可执行多个位移回调或页面捕获，因此此处仅检查内容连续性，不把捕获次数称为屏幕 FPS；此详细探针批次也不混入前面的低开销表格。三机退出后的 scene 关闭、捕获资源释放、窗口分离事件均已确认。

指定真实记事“右滑记事的动画优化”在三星／魅族各完成 12 次 fling，完整窗口为 118.32／117.24 帧/秒，最大间隔 25.014／24.872ms。真实卡仍沿用既有满宽清单 12 行行为，惯性时长不足半秒；长清单结果来自独立 90 项样本，未改用户卡片或其显示规则。

另完成三机 × 四卡型 × 飘散／流体，共 24 轮横向取消及纵向拖动。流体平均帧率三星约 114–116、魅族约 97–107、OPPO 约 113–116；不宣称所有粒子场景均达 120。魅族视频首次流体可见回调约 310ms（上一轮约 340ms），后续约 103／86ms；视频首次飘散约 656ms（上一轮约 525ms），后续约 94／69ms，冷启动差异仍需单独优化，不能把本轮惯性改善外推为所有首次动画都更快。

三机两样式共六轮录屏与无损截图已检查，覆盖 GIF 持续播放、计时填充／描边／无限模式、横向取消和模拟完成、原生波纹、加时弹窗返回、尺寸变化及 HOME 恢复。计时恢复静态区域与原图逐像素相同，GIF 区域确有持续变化，未发现黑屏或卡片丢失。录屏仅作画面证据，未用于性能表。对三机全部有效记事及 doing_records 做只读行内容摘要，测试前后完全一致。
