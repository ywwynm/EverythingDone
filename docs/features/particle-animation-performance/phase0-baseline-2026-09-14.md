# 阶段 0：测量与归因（2026-09-14）

对应 [plan.md](plan.md) 的「阶段 0」。本轮只测量、不优化：没有改动粒子模型、材料、随机、积分步数、压力迭代与着色器数学。留在代码里的只有 debug 专用计时钩子（`ParticlePerfProbe`，默认关闭）；八个临时诊断变体（四个涟漪对照、无屏障、跳过压力、积分步距、栅栏步距）在测完后已全部删除，`git diff` 里不再有它们。

## 方法与口径

- 设备：OPPO `9018f404`（OPD2515，Android 16，Adreno 829，横屏 2520×1680，普通界面 120 Hz）与三星 `R5CW20BLNKL`（SM-S9180，Android 16，Adreno 740，竖屏 1440×3088）。两台均由用户在本专项期间显式授权。
- 输入：除「从启动器图标启动应用」外，全部操作都是注入 Android 输入系统的真实点击、返回键与连续 MotionEvent（`ParticleGestureInput`，shell 身份经 InputDispatcher）。没有调用任何业务 Intent、广播或应用内入口。
- 采样：debug 专用只读 ContentProvider 观察器（`ThingAnimationPerformanceObserver`），由私有文件 `files/thing-animation-performance-enabled` 显式开启。本轮给它加了两项只读能力：弹窗 Window 的 FrameMetrics（此前只观察 Activity 窗口）、主线程停顿栈采样。
- GPU 计时：debug 专用 `ParticlePerfProbe`，由私有文件 `files/particle-perf-probe.json` 显式开启，缺文件时全部钩子为空操作。
- 帧率类统计的轮次不做截图、录屏或内存采样。每个条件每台设备至少 3 轮，第 1 项与基线至少 5 轮；报告分布而不是最好的一次。
- `glFinish` 等待包含驱动排队，不称为纯 GPU 执行时间；纹理/提交回调不等同于面板物理扫描。

### 工具链结论：Adreno 的 `EXT_disjoint_timer_query` 不计 compute dispatch

两台设备的 GL 扩展串里都有 `GL_EXT_disjoint_timer_query`，`glBeginQuery(GL_TIME_ELAPSED_EXT)` 也不报错（`timerSupported=true`，`GPU_DISJOINT` 全程为 0），但结果只对**绘制**有效：

| 计时对象 | OPPO | 三星 |
| --- | --- | --- |
| 整段预计算（模式 A，一对查询包住约 1550 次 dispatch） | 0.3 ms | 0.6 ms |
| 每帧绘制（模式 B，包住两遍实例化微片 + resolve） | 消散 P50 1.73 / P90 2.42 ms | 消散 P50 2.73 / P90 3.41 ms |
| 积分段（模式 B，每次 `advance` 一段） | 5 轮合计 0.1 ms / 440 段 | 5 轮合计 0.1 ms / 440 段 |
| 压力更新（模式 B，每次一段） | 5 轮合计 0.2–0.3 ms / 300 段 | 5 轮合计 0.5 ms / 300 段 |

同一个查询机制下绘制给出合理值、compute 给出接近零的值，说明 Adreno 的 TIME_ELAPSED 计数器只累计渲染通道的时间。**因此「预计算的 GPU 忙时间」用计时查询测不到**，本轮改用三条替代口径：整段墙钟、内核 `gpubusy` 计数器、按段 `glFinish` 的墙钟（模式 C，会串行化流水线，只用于比较量级），再由第 2 项的消融实验做归因。Java 绑定里没有 `glQueryCounterEXT` / `glGetQueryObjectui64vEXT`，无法换 `GL_TIMESTAMP` 口径。

## 1. 出现预计算：墙钟、分段与 GPU 忙时间

固定素材是真实「添加附件」弹窗的出现（约 10.8 万片微片）。

**先更正一处计数**：`analysis-2026-09-14.md` 把出现预计算估成「0.6 s × 240 Hz = 144 次积分 + 36 次压力 + 37 次历史 ≈ 937 次 dispatch」。实测不是这样——`ParticleReversePlan.time(frame) = frame / samples`，t 跑满 0→1.0，所以**积分是完整的 240 步**，只有历史采样按 0.6 s × 60 Hz = 36 个采样（共 37 帧）保存。探针记录的实际段数是每次预计算 **240 次积分 dispatch、60 次压力更新、37 次历史转存**，按每次压力更新约 21–23 次 dispatch 算，合计约 **1540–1660 次 dispatch**，比原估算多七成。源码注释「仍积分完整 240 步」也是这个意思。

下表是 `prepareReverse` 内部的墙钟（探针直接记录，不含前面的快照、建材与上传），每台 5 次热运行，按升序列出。

| 条件 | OPPO（ms） | 三星（ms） |
| --- | --- | --- |
| 预计算墙钟（基线，a1base） | 178 / 190 / 191 / 194 / 233 | 256 / 257 / 260 / 264 / 315 |
| 模式 A 附带的墙钟（a2modea） | 173 / 193 / 197 / 198 / 230 | 265 / 275 / 278 / 295 / 334 |
| 模式 B 附带的墙钟（a3modeb） | 194 / 208 / 217 / 217 / 245 | 273 / 279 / 279 / 281 / 327 |
| 模式 C（按段 `glFinish`，a4modec） | 567 / 615 / 729 | 643 / 646 / 703 |

模式 A 与模式 B 的插桩本身各让墙钟涨 1–10%；模式 C 涨到 3 倍以上，所以它的绝对值不能当成 GPU 时间，只能看三段之间的比例。

**三段的相对量级（模式 C，按段 `glFinish` 的墙钟，含每次约 2–3 ms 的驱动往返）**

| 段 | OPPO 合计 / 段数 | 三星 合计 / 段数 |
| --- | --- | --- |
| 积分（共 240 次 dispatch，分成 88 段） | 178 / 191 / 214 ms | 188 / 188 / 190 ms |

**正向消散播放每帧三段（消散场景，模式 B 的绘制是真实 GPU 时间，积分与压力测不到；模式 C 是串行化后的上界）**

| 段 | OPPO P50 / P90 | 三星 P50 / P90 |
| --- | --- | --- |
| 绘制（模式 B，真实 GPU 渲染通道） | 1.73 / 2.42 ms（max 5.74） | 2.73 / 3.41 ms（max 7.85） |
| 积分（模式 C 上界） | 1.99 / 2.93 ms | 3.14 / 3.95 ms |
| 压力（模式 C 上界） | 5.97 / 7.05 ms | 6.82 / 8.19 ms |
| 绘制（模式 C 上界） | 5.22 / 7.02 ms | 7.81 / 9.01 ms |

**内核 `gpubusy` 计数器**：`/sys/class/kgsl/kgsl-3d0/gpubusy` 对应用 uid 可读（`run-as` 验证过），探针在预计算前后各读一次。实测该节点**不是「自上次读取以来」的累计值**：它由 devfreq 调速器约每秒更新一次，两次快速读取之间返回 `0 0`。13 次带括号的预计算里只有 4 次拿到非零值（OPPO 1 次：忙 118.6 ms / 窗口 1003 ms，同次预计算墙钟 195.7 ms；三星 3 次：忙 575 / 584 / 199 ms，窗口约 1004–1017 ms）。窗口长度固定约 1 s、无法对齐到 195–280 ms 的预计算，**这条口径本轮未能成立**，只能说明 OPPO 那一次的 1 秒窗口里 GPU 总忙时间（含 HWUI）不超过 119 ms。预计算的忙/闲划分最终由第 2 项的消融实验给出。

不插桩时每个消散帧的 GL 提交加 `glFinish` 等待（`glReadyMs`，包含驱动排队）：OPPO P50 10.1–11.2 ms、P90 12.1–12.7 ms、最大 14.1–17.0 ms；三星 P50 14.3–15.0 ms、P90 17.5–18.6 ms、最大 21.9–24.8 ms。出现播放（只回放历史 + 绘制，不再积分）便宜得多：OPPO P50 约 8.0 ms、三星约 5.4 ms。

## 2. 屏障判别实验

三个临时变体各 3 轮，输入与第 1 项相同，只看预计算墙钟（模式 A 的 GPU 时间对 compute 无效，见上）。

| 变体 | OPPO（ms，升序） | 中位数相对基线 | 三星（ms，升序） | 中位数相对基线 |
| --- | --- | --- | --- | --- |
| 基线 | 178 / 190 / 191 / 194 / 233 | — | 256 / 257 / 260 / 264 / 315 | — |
| (i) 积分步之间不发 `glMemoryBarrier`（去掉 240 次） | 184 / 193 / 213 | +0.8% | 264 / 267 / 325 | +2.7% |
| (ii) 完全跳过压力更新 | 110 / 116 / 161 | −39% | 127 / 143 / 194 | −45% |
| (iii) 两者都去掉 | 119 / 127 / 154 | −34% | 134 / 137 / 206 | −47% |

变体确实生效：探针产物里 `noBarrier` / `noPressure` 字段逐条记录了当次的开关状态。

另外用既有的离屏轨迹核对（`ParticleTrajectoryCheck`，同一输入跑原路径与批处理路径各 61 帧、逐帧 SHA-256）在两台设备上各跑了一次「有屏障」与「无屏障」：**去掉 240 次屏障后，61 帧仍然零差异、零像素差**。两条路径都去掉了屏障，所以这不是与「有屏障参考」的比对，但 10 万片微片、61 帧完全没有出现竞态，足以支持一个解释——Adreno 本来就把同一队列里相邻的 compute dispatch 顺序执行，API 屏障既不花时间也没有改变行为。

**结论**：预计算耗时里，

- **屏障/空转：测不出份额，上限约 3%**。去掉积分步之间的 240 次 `glMemoryBarrier` 后两台设备都没有变化。合理解释是 Adreno 本来就把同一队列里相邻的 compute dispatch 串行执行，API 级屏障没有额外代价。
- **压力更新：约 40–45%**（OPPO 39%，三星 45%）。它包含 splat 清零与累加、两遍分离模糊、tile 收集、100 次 Jacobi 迭代、清目标与投影，每次约 21–23 次 dispatch。
- **积分本身 + 历史转存 + CPU 提交：约 55–60%**，即去掉压力后剩下的 110–161 ms（OPPO）／127–194 ms（三星）。

### 2.1 补充诊断：积分 dispatch 的边际成本

上面的 (ii) 只说明「压力占四成」，没有说明剩下六成里 dispatch 次数占多少。补了一个额外的临时变体 `integrateEvery`：只发第 N 步的积分 dispatch（`step` 照常推进，结果错误无所谓），与「跳过压力」叠加，在**同一个进程里交错 8 轮**（stride 1 / 4 轮流），避免跨组的热状态差异。

| 条件（均跳过压力） | OPPO 墙钟（ms，4 轮升序） | 三星墙钟（ms，4 轮升序） |
| --- | --- | --- |
| 240 次积分 dispatch（stride 1，现状） | 112.0 / 122.6 / 138.4 / 140.2 | 129.1 / 130.8 / 136.0 / 186.9 |
| 60 次积分 dispatch（stride 4） | 93.0 / 99.8 / 100.2 / 101.7 | 68.5 / 68.6 / 69.0 / 70.8 |
| 差值 ÷ 180 次 = 每次积分 dispatch 的边际成本 | 约 0.17 ms | 约 0.36 ms |

注意这个差值同时去掉了 dispatch 的**启动开销和它的计算**，所以它是「240 次积分（含计算）」的总量，**不是**「把 4 步合并成 1 次能省下的量」。由此得到的预算：

| 组成 | OPPO（相对 191 ms 中位） | 三星（相对 260 ms 中位） |
| --- | --- | --- |
| 压力更新（60 次 × 约 21–23 dispatch） | 约 75 ms（39%） | 约 117 ms（45%） |
| 积分 dispatch（240 次，含计算） | 约 40 ms（21%） | 约 86 ms（33%） |
| 其余（37 次历史转存、状态重绑、CPU 提交、`createHistory`；栅栏同步已由 2.2 节排除） | 约 76 ms（40%） | 约 57 ms（22%） |

跨组的轮间波动不小（同为「跳过压力」，b2nopressure 中位 116 ms、f4strideab 的 stride 1 中位 138 ms），所以上表按「同组交错」的差值算，绝对份额有约 ±10 个百分点的不确定度。

### 2.2 补充诊断：有界队列的栅栏同步不是开销

「其余」那一档里最可疑的是 `ParticleGpuWork.PreparationQueue`——每个 60 Hz 采样都做一次 `glFenceSync` + `glFlush` + `glClientWaitSync`，一次预计算 37 轮。用同样的交错 A/B（`batchEvery` = 1 对 6，即 37 轮同步降到 7 轮，8 轮交错）：

| 条件 | OPPO 墙钟（ms，升序） | 三星墙钟（ms，升序） |
| --- | --- | --- |
| 每个采样同步一次（现状） | 174.7 / 198.4 / 201.9 / 211.3 | 254.5 / 266.2 / 288.9 / 314.5 |
| 每 6 个采样同步一次 | 176.4 / 191.1 / 203.6 / 206.2 | 261.2 / 265.6 / 266.2 / 292.9 |

**没有差别**（两台的中位数差都在 4% 以内、完全落在轮间波动里）。所以「其余」那一档不是栅栏同步造成的，主要成分是 37 次历史转存 dispatch、每采样的状态重绑、CPU 侧提交与 `createHistory` 的一次性分配。这也解释了第 4 节条件 (c)：把在途批次从两批收紧到一批之所以让出现变慢，是因为它把 CPU 提交与 GPU 执行的重叠取消了，而不是因为同步本身贵。

## 3. GPU 频率（DVFS）

同一预计算，「GPU 空闲 ≥2 s 后直接触发」（a1base，每轮之间强制 2.2 s 空闲加约 1 s 的 UI 轮询）对「触发前先跑 100 ms 无意义 compute 负载」（c1warm）。

| 条件 | OPPO 墙钟（ms） | 三星墙钟（ms） |
| --- | --- | --- |
| 冷（空闲后直接触发） | 178 / 190 / 191 / 194 / 233，中位 191 | 256 / 257 / 260 / 264 / 315，中位 260 |
| 热（先跑 100 ms 负载） | 166 / 180 / 191，中位 180 | 264 / 273 / 328，中位 273 |

**结论**：爬频在 OPPO 上占约 6%（191 → 180 ms），在三星上测不出（中位数反而高 5%，落在轮间波动范围内）。DVFS 不是预计算耗时的主要来源，不值得为它做专门处理。

## 4. 涟漪归因对照

场景：添加附件弹窗已打开，点其中的「录音」长条行（`GradientRippleDrawable` 作 background），触发前一弹窗消散 + 录音弹窗出现。基线与四个条件各 3 轮，每次只改一处。

「涟漪期」定义为按下后 600 ms 内、承载按钮那个弹窗窗口的 FrameMetrics。

### 4.0 先说一条基线里就暴露的问题：消散被涟漪结算卡住

| | OPPO | 三星 |
| --- | --- | --- |
| 添加附件弹窗消散的首个粒子提交（从请求算起） | **1523 / 1527 / 1528 ms** | 435 / 462 / 469 ms |
| 其中上传完成到首帧之间的等待 | 约 1.33 s | 约 0.33 s |

`ParticleDismissRenderer` 在播放消散前调用 `touchFeedback.awaitPlayback`，等 `GradientRippleDrawable.hasVisibleFeedback` 变假。OPPO 上它一直为真，直到 `ParticleTouchFeedback` 自己的超时（`500 + 1000 × animator_duration_scale` = 1500 ms）兜底才放行；三星上约 330 ms 放行。两台都用 90 ms 按压的连续 MotionEvent 复测过，不是注入方式导致的。也就是说：**在 OPPO 上点「录音」之后，添加附件面板的快照要在屏幕上多停 1.3 秒**，录音弹窗的凝聚在它上面先演完。

把行背景临时换成系统 `RippleDrawable`（条件 b）后，`ParticleTouchFeedback.begin` 找不到自绘涟漪、直接返回 null，这段等待完全消失：OPPO 首帧 211 / 244 / 377 ms，三星 204 / 216 / 281 ms。这就是该等待归因的直接证据。

**逐条读法**

- **(a) 刷新率投票**：这是对涟漪本身最明确的一项。OPPO 上撤掉投票后，涟漪期内弹窗窗口出的帧从 34–35 翻到 67–69（600 ms 内 57 fps → 112 fps），单帧总耗时 P95 从 21.7–27.6 ms 降到 10.4–16.9 ms。换句话说，当前的 60 Hz 投票把整条涟漪的采样率砍了一半，256 ms 的扩散只有约 15 帧。三星上撤掉投票同样让节拍回到 120 Hz，但因为截止时间同时减半，超截止帧数从 3–7 升到 7–9，P95 没有改善——三星的涟漪帧本身就比一帧预算长，提高刷新率救不了。
- **(b) 系统涟漪**：唯一能大幅改善消散起步的一项（见 4.0）。三星上涟漪期帧耗时 P95 从 31.9–62.7 ms 降到 7.9–17.4 ms，说明三星上自绘渐变涟漪的**单帧绘制成本**本身就很高（长条按钮铺满半径大、每帧重建 LinearGradient 扩散圆）。OPPO 上这一列反而变差，但不可直接对比：消散提前 1.3 s 开始，添加附件窗口在 600 ms 窗口内只剩 13–22 帧，且这些帧与粒子消散、录音弹窗凝聚完全重叠。
- **(c) 在途批次两批降一批**：涟漪 P95 在 OPPO 上从 21.7–27.6 降到 20.5–23.2 ms（小幅），三星上没有改善；代价是出现首帧变慢（OPPO 497–944 ms 对基线 367–712 ms，三星 653–851 对 565–943）。**GPU 排队不是涟漪卡顿的主因**。
- **(d) 粒子时钟挂 GL 线程**：涟漪指标与基线同量级；OPPO 上「有活的主线程停顿」样本从每轮 1–3 降到 0–1，出现与消散的帧数、间隔都没有退化。它解决的是「主线程停顿时粒子帧一起停」，不是涟漪。
- **显示模式切换**：本轮不用 `dumpsys SurfaceFlinger` 抽样（会干扰被测帧），改用两个无干扰信号——主线程 Choreographer 间隔与 FrameMetrics 的 `DEADLINE`。两者一致：基线和 (b)(c)(d) 里都能看到窗口截止时间在 8.33 ms 与 16.67 ms 之间切换，(a) 之后全程停在 8.33 ms。没有观察到「切换本身产生 50–70 ms 长帧」的证据：基线涟漪期的最大帧耗时是 26.7–40.5 ms（OPPO）、37.7–65.3 ms（三星），与 (a) 条件同量级。

## 5. 主线程停顿采样

## 三条建议

### 建议 1：阶段 2 的「减少 dispatch」不值得全做，重心应移到压力求解

plan.md 里阶段 2 的前提是「屏障空转占大头」。**这个前提不成立**：

- 去掉积分步之间的 240 次 `glMemoryBarrier`，两台设备的预计算耗时都没有变化（OPPO +0.8%，三星 +2.7%，都在轮间波动内），而且 GPU 输出没有出现任何竞态。可以认为 Adreno 本来就顺序执行同队列的相邻 compute dispatch，API 屏障既不花时间也没有语义作用。
- 预计算耗时的分布是：压力更新约 39–45%、积分 dispatch（含计算）约 21–33%、其余约 22–40%。「其余」里已经排除了栅栏同步（见本文 2.2 节），主要是 37 次历史转存、每采样的状态重绑与 CPU 提交。

逐项建议：

| 阶段 2 项 | 建议 | 依据 |
| --- | --- | --- |
| 2.2 Jacobi 扩大 tile、增加每批迭代 | **做，优先级最高** | 压力是唯一占到四成以上的单块；它同时减少 dispatch 次数与对 tile 的重复读写 |
| 2.4 首生之前跳过积分与压力 | **做** | 直接砍掉整段采样，收益与材料的最早出生时间成正比，零风险 |
| 2.1 历史转存并入积分 | **做**，但按「减少一次 dispatch + 一次全缓冲往返」来预期，不是按「减少一次屏障」 | 历史转存落在「其余」那一档里，那一档在 OPPO 上有 76 ms |
| 2.3 模糊两遍合一 | 做，收益小（每采样 1 次 dispatch） | 同上 |
| 2.5 四步积分合并 | **先做一次一次性探针再决定，不要直接排期** | 本轮只能给出「240 次积分 dispatch 含计算共 40 ms（OPPO）／86 ms（三星）」，无法分离其中的启动开销；合并只能省启动开销那一部分。而 2.5 是唯一可能掉到 G1 的一项，收益不明确时不值得付这个代价 |

已经排除掉的一条：**放宽有界队列的栅栏同步没有收益**（见本文 2.2 节，37 轮同步降到 7 轮，两台都没有变化），不要在这个方向花时间。

### 建议 2：1.3「预计算放到低优先级上下文」不需要，至少不该排在前面

条件 (c) 是「GPU 排队是否拖慢涟漪」的直接对照：把在途批次从两批降到一批，相当于让预计算更频繁地让出 GPU。结果是涟漪期帧耗时 P95 在 OPPO 上从 21.7–27.6 ms 降到 20.5–23.2 ms（约 1–4 ms），在三星上没有改善（38.0–55.1 对 31.9–62.7）；代价是出现动画首帧慢 100–250 ms。

也就是说，**涟漪卡顿里 GPU 排队最多占 1–4 ms**，与 60 Hz 投票造成的「涟漪采样率减半」（OPPO 上 34 帧对 67 帧）和自绘涟漪本身的单帧成本（三星上 P95 31.9–62.7 ms 对系统涟漪的 7.9–17.4 ms）完全不在一个量级。1.3 需要引入共享上下文、跨上下文栅栏与能力探测，复杂度高而这里的可回收量很小。建议推迟到阶段 1、2 做完后按同一口径复测再定。

### 建议 3：涟漪混合方案先不做，但先修三件更靠前的事

按阶段 0 的数据，长条按钮上「波前跳跃」的成因排序是：

1. **60 Hz 投票把涟漪的帧率砍了一半**（OPPO：涟漪期弹窗窗口 34–35 帧 → 撤掉投票后 67–69 帧）。256 ms 的扩散只有 15 帧，跳跃当然可见。这一项由 D5 已裁定的「删除窗口投票、改 Surface 无缝投票」解决。
2. **OPPO 上消散要等 1.5 s 的涟漪结算超时**（第 4.0 节）。这是 `ParticleTouchFeedback` 的生命周期缺陷，不是渲染问题，应当单独修。
3. **主线程有活停顿**：涟漪场景下 OPPO 每 3 轮 6 个样本、单次最长 25–43 ms；三星 19 个样本、最长 33–61 ms。栈顶集中在 `nSyncAndDrawFrame`、`BinderProxy.transactNative`、录音弹窗自己的传感器与通知渠道初始化，以及粒子侧的 `nDetachSurfaceTexture`。1.6（主线程减负）与 1.4（去掉 TextureView）都直接命中。

三星上一次 33–61 ms 的停顿落在 256 ms 的扩散里就是 13–24% 的进度跳跃，肉眼可见。所以**不能现在就断言混合方案不需要**；正确顺序是先做 1.2/1.4/1.6/1.8，然后用本文第 4、5 节的同一口径复测：若三星的涟漪场景仍有 > 33 ms 的有活停顿落在扩散期内，再做「半径上 `createCircularReveal`、透明度留主线程」的混合方案。

补充一条与混合方案相关的实测：三星上自绘渐变涟漪的单帧成本本身就很高（涟漪期 P95 31.9–62.7 ms，换成系统 `RippleDrawable` 后 7.9–17.4 ms）。混合方案只把**半径**挪到 RenderThread，每帧仍要重建渐变扩散圆，这部分成本不会消失。真要解决三星的涟漪帧成本，得先看 `GradientRippleDrawable.draw` 本身（例如缓存 shader、缩小重绘区域），那是另一条线。

## 本轮发现的、不在原计划里的问题

1. **`ParticleTouchFeedback` 的 1.5 s 超时在 OPPO 上每次都会走到**（第 4.0 节）。点「录音」之后添加附件面板的快照要多停 1.3 s。三星上约 330 ms 放行，不触发超时。原因在 `GradientRippleDrawable.hasVisibleFeedback` 一直为真——控件被移除时 `exit()` 没有走到，淡出动画从未开始。已记入 followups。
2. **三星快拖 180 ms 只提交 8 个不同画面**（OPPO 24–39）。按需补档在三星上跟不上手指，这是「左滑不跟手」在三星上的具体形态。
3. **三星的正向消散每帧 GL 提交 + `glFinish` 等待 P50 已达 14.3–15.0 ms、P90 17.5–18.6 ms**，几乎用完 60 Hz 的预算；OPPO 是 10.1–11.2 / 12.1–12.7 ms。消散才是帧率的临界路径，出现播放（只回放历史 + 绘制）便宜得多。
