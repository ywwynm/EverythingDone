# Doing 滑动帧率与刷新率请求测量

## 请求与范围

- 用户感觉中间记事卡片滑动不够流畅，要求在 `R5CW20BLNKL`、`9018f404`、`192.168.100.67:40807` 三台设备统计，并核对是否请求最高刷新率。
- 本轮先测量现有实现，不修改生产渲染策略。复用 debug 中的真实 Doing 布局、输入和粒子流程，使用 90 行虚构长文本记事及真实计时控件，不创建或修改用户记事。
- 数据核验以用户记事和计时记录为准：应用初始化会重建内部 `type=-1` 的 HEADER 元数据，因此整个 SQLite 文件哈希会变化，不能把整库字节一致作为标准。三机真实记事的创建、更新、完成时间均早于本轮，未新增计时记录；OPPO 真实记事内容还与既有只读快照逐字段一致。
- 一次合并测量覆盖两种粒子样式、连续三次横向拖动回弹，以及长卡片上下滚动；性能测量不录屏、不采样图像。报告采用驱动呈现时间戳，窗口主线程的 gfxinfo 不作为 GL 实际帧率的替代。

## 测量前核对

- API 34 以上的正式 Doing 粒子路径由 `ParticleDoingPage` 将原控件树交给 `ParticleDoingGlScene` 进行 HWUI 捕获，再通过 `ParticleWindowSurface` 由 GL 合成显示；仍使用原控件布局及输入逻辑。
- `ParticleGl.updateFrameRate()` 在整页内容活跃时会请求高刷，`ParticleWindowSurface.HIGH_FRAME_RATE` 固定为 120；窗口通过 `ParticleWindowFrameRate` 请求同分辨率显示模式，选择能满足 120 的最低档，而非总取设备最高档。
- 设备初始查询：三星 `SM-S9180`／API 36；平板 `OPD2515`／API 36，支持 144 Hz，系统 peak 设置为约 120；魅族 `MEIZU 20 Inf`／API 35。三台均未开启系统低电量模式。
- 待区分的原因：固定 120 请求低于最高档；系统未接受高刷请求或应用帧率覆盖；请求已生效但页面捕获、粒子绘制及合成未赶上显示节拍。不能把系统标称刷新率等同于内容实际呈现帧率。

## 结果

纯文本基线已完成：三星上下滚动 60.6–64.5 FPS，OPPO 82.1–96.1 FPS，魅族 118.2–120.1 FPS。三星、OPPO 前后显示状态均为 120 Hz；魅族在手势前空闲快照为 60 Hz，手势后为 120 Hz，滑动的驱动呈现间隔约 8.28ms。三机窗口均请求 mode 1（120 Hz）。详细原始证据保存于 `tmp/doing-refresh-rate-20261014/`。

用户随后补充必须覆盖图片附件、已生成 GIF 封面的视频附件和长 checklist。纯文本结果不代表这些卡型；追加使用独立虚构数据，按卡型分别记录。复用真实媒体加载、视频封面生成与清单渲染，采样前确认媒体加载完成、GIF 正在播放，避免把占位图计作复杂媒体负载。

## 采样口径

- 基线包为已发布 `202610140713`。复杂样本只扩展 `src/debug` 下的两个既有探针：`doing_fixture` 参数支持图片、视频和 90 项三级清单；生产代码无改动。
- 图片为 2048×1536 合成图案；视频为 1920×1080、30 FPS、6 秒 H.264 合成图案，通过正式 `VideoCoverPreviewManager` 生成 75 帧循环 GIF。两者均搭配与基线相同的 90 行长文本，封面放在卡片顶部；清单为 90 项、三级层级，最后六项为已完成。所有卡片只驻留内存，不新增、完成或修改数据库记事。
- 三星、魅族保留竖屏；OPPO 保留当前横屏。相同卡型在不同设备的布局、分辨率不同，结果用于各机问题定位，不作硬件性能排名。
- 每台、每种卡型测试飘散（DRIFT）、流体（FLOW）各一轮。每轮三次 1.8 秒小幅横向拖动后回弹、两次 1.8 秒上下拖动，计时数字持续动画。未测试完成记事，不录屏、不抓图，不关闭 GIF。
- 横向窗口为首次粒子可见回调后 150ms 至活动会话释放，只统计带粒子会话的提交；纵向窗口为 RecyclerView 进入拖动状态后 150ms 至松手进入减速／停止，只统计不带粒子会话的提交。
- 通过 `frameId` 对应 `particle_buffer_submitted` 与 `particle_presentation_decision`，只使用 `basis=driver_timestamp` 的正呈现时间戳并去重，FPS 为 `(帧数−1)/(末次−首次呈现时间)`。`later_frame_presented` 等回调不算真实出帧。结果是短时样本范围，不是长期平均或置信区间。
- 纯文本基线三台六轮完整、报告溢出计数均为 0。魅族首次 UI 树为空的样本未执行手势，排除；复杂卡片首轮三星／魅族因 ADB 服务连接中断而提前结束，应用结果无异常，排除并只补测这两台。

复杂卡型 18 轮完整，日志溢出计数全部为 0。三台各两轮视频样本均确认：来源为 MP4、派生预览存在、`GifDrawable.running=true`、75 帧、采样前后帧号不同。GIF 解码与播放保持真实业务行为，未替换成静态图片；图片／视频占位加载阶段不纳入滑动 FPS。

魅族长清单纵向间隔 P90 约 16.57ms，和图片／视频的约 8.29ms 明显不同。因此“魅族接近满帧”只适用于本轮纯文本、图片和视频样本，不能外推到复杂清单。

魅族视频流体首次手势有一次异常：识别至首个粒子呈现回调 823.3ms，后两次 143.4／77.9ms；该窗口稳定区间 FPS 79.5，后两次约 106.3。仅对此组合追加一次复核，首轮仍为 590.8ms，后两次 169.8／85.6ms；横向 FPS 81.9／100.3／104.9，纵向仍为 118.8／118.2。首次启动偏慢在两轮均出现，未被后续较好结果覆盖。复核报告有一条 `timeout_estimate`，未纳入实际 FPS；报告事件未溢出。

首轮异常的事件顺序为：滑动识别 7656ms → 页面进入粒子阶段提交回调 8008ms → 卡片切为粒子 8456ms → 首个粒子呈现回调 8479ms。说明卡片准备／交接／粒子首帧还存在等待，不能只看后续稳定出帧。尚未用线程追踪或 GPU 时间线拆分这些等待，下一步需定位准备和调度阶段。

## 已确认与待定位

1. **已有高刷请求。** 两种粒子样式默认启用高刷，页面内容活跃时 Surface 请求 120 FPS，窗口请求 120 Hz 的同分辨率 mode 1。三星、OPPO 前后均为 120 Hz；魅族空闲可能降为 60 Hz，滑动后为 120 Hz、应用帧率覆盖为 120，滑动呈现节拍也约 8.28ms，不能用单次空闲快照判断“被锁 60”。
2. **OPPO 没有请求设备最高的 144 Hz。** 代码目标固定 120，模式选择取满足目标的最低档；该机系统 peak 设置及显示模式约束也为 120。即使以后改请求值，也需核对系统是否允许 144，不能承诺改一个常量就能稳定 144 FPS。
3. **纵向滚动的主要差距发生在已请求高刷的情况下。** 三星纯文本的整页捕获到完成回调稀疏样本约 8.3–10.5ms，已超过 120 Hz 的 8.33ms 单帧预算；相邻页面捕获计数的速率约 61–68 次／秒，接近最终纵向出帧速率。单次 GL 合成提交墙钟中位约 1ms，不能把剩余时间直接称为 GPU 耗时。
4. **证据指向整页内容生产与同步链路，尚未细分因果。** `capture()` 在 `busy` 为真时不能继续，需经过 HWUI 捕获、ImageReader／fence、主线程与 GL 上传及帧资源归还后再刷新。后续应细分这些阶段和线程调度，不能仅凭上述总时长断言某一个调用就是根因。
5. **横向稳定 FPS 与起步延迟分开看。** 纯文本飘散多数接近 120；流体部分窗口约 96–114。识别滑动至首个粒子可见回调在本轮约 46–262ms，存在第一次较慢的情况；该值不是外部摄影测得的触摸延迟，也没有被稳态 FPS 包含。
