# 逐帧成本专项：模拟、计算、绘制、呈现（2026-09-17，方案）

前几批做的是缓存与提前预算（常驻上下文、一窗一 Surface、创建页预算、跳过尾段），没有动过每一帧本身的成本。
本专项直接压每帧的 GPU/CPU 工作量与交接延迟。**目标设备是魅族 20 Infinity `392QBFED2226B`（Adreno 740，
Android 15，1368×3192）：所有粒子场景稳定 60 fps，且交互到首帧的延迟不劣化、尽量缩短。** 用户接受轻微的
视觉变化（含适当减少粒子数），但每一处变化都要给他看画面定夺。实施、测试、看画面全部由 Opus 执行。

## 1 口径

- **帧率**：一次动画里真正呈现的帧数 / 应有帧数（60 Hz × 时长），以及呈现间隔的 p90 与最大值；不用「帧耗时
  百分位」（见 adb.md 关于 `DEADLINE` 的纪律）。观察器（`ThingAnimationPerformanceObserver`）已经记录提交与
  呈现时间戳。
- **首帧延迟**：请求（点击/识别左滑/点新建）→ 首个粒子帧确认上屏，观察器已有；左滑另记「识别 → 首个非零画面」。
- **画面**：魅族能 `screenrecord`（OPPO 不能，见 adb.md）。每个场景修前修后各录一段，取同一进度的帧做
  3–4 倍放大的并排裁剪图，落盘给用户看；不许只报数字。
- **设备**：魅族为主；OPPO `OPD2515`（Adreno 829）与华为 `5JB0224328002836`（Maleoon 910）在线时各回归一轮。
  三星 `R5CW20BLNKL` 与魅族同 GPU，在线时可替代。每批每台一轮，不做逐项 A/B（`device-test-runs-sparingly`）。
- **数据安全**：左滑会改数据，一律先建测试记事（`PROBE-*`），测完移入回收站；不用用户的真实记事。

## 2 现状：每帧都在算什么

| 路径 | 每帧 GPU 工作 | 已知数字 |
|---|---|---|
| 消散（现场） | 4 步积分（每步 1 次 dispatch）+ 1 次压力更新（splat 2、blur 2、Jacobi 100 次/8 一批 ≈ 13、project 1）+ 2 遍实例化绘制 + resolve ≈ 26 dispatch + 3 draw | 华为 106k 片 54/61 帧、157k 片 32/61 帧；魅族 47–58/61 帧 |
| 出现（回放） | 1 次历史转存 + 2 遍绘制 + resolve | 华为、魅族都满帧 |
| 左滑（回放 + 按需预读） | 同上，另加每拍 1–2 个采样的预读（每个采样 = 一帧现场消散的量） | 三星快拖 180 ms 只出 8 个不同画面；魅族用户感到掉帧与延迟 |
| 创建页 | 命中 = 回放；未命中 = 现场预算 1550 次 dispatch | 命中 171 ms（OPPO）、305 ms（三星） |

着色器里的逐步 / 逐顶点数学（`shared/particle-dismiss/`）：`step.comp` 每片每步 17 次 sin/cos、9 次 exp/log/pow、
7 次 sqrt 类；`material.vert` 每顶点 11 次 sin/cos、7 次 exp/log/pow，每片每帧 4 顶点 × 2 遍 = 8 次求值；
全部 `highp`。累积纹理是全屏 RGBA16F（魅族 4.4 MP ≈ 35 MB），每帧整屏清空 + 整屏 resolve。
粒子数由 `max_cells` 封顶（`ParticleMicroflakeModel`：`cell = max(cell, sqrt(w·h·budget/(max_cells−1000)))`），
即按**像素**分格，高 dpi 手机上的微片物理尺寸比平板小、数量顶到上限。压力网格 `gridCell = span/96`，
两个方向各加 192 格 halo。历史缓冲每片每采样约 8.7 B（5 分量）。

## 3 优化方向（按预期收益 / 风险排序，视觉等级：G0 逐位相同、G1 浮点噪声、V 可见）

### A 把不变量挪出逐步 / 逐顶点（G1）
1. **逐顶点 → 逐片每帧一次**：`material.vert` 里只依赖片与时间的量（旋转 cos/sin、尺寸、透明度、色素调制、
   exp/log 曲线）改在积分的最后一步（现场）或历史转存（回放）里算好，写进一个紧凑的「绘制记录」缓冲
   （每片 16–32 B）；顶点着色器只做二维仿射展开。每片从 8 次求值降到 1 次。
2. **逐步 → 常量**：`step.comp` 里只依赖本次动画方向的量（风向量、旋转矩阵、方向相关系数）改成 uniform；
   只依赖片固定参数的量（出生、寿命、相位、自旋速率的派生值）在建材时算进材料缓冲（当前 48 B/片，
   有 std430 对齐的空位可用）。剩下真正随步变化的才逐步算。
3. **流场采样**：核实积分里 3D 流场（guide / confidence）的采样次数与过滤方式；若每步采样多次，改为每步一次
   加线性外推，或每两步一次（V 级，需看画面）。

### B 绘制（G1 / V）
4. **绘制形态**：4 顶点实例化改为顶点拉取（`samplerBuffer` / 纹理缓冲，ES 3.2 核心，Mali 顶点阶段无 SSBO
   但可用纹理缓冲）+ 索引缓冲（每片 6 索引 4 顶点，命中后变换缓存），一次 draw。Mali 上小实例的实例化开销大，
   Adreno 上中性偏正。
5. **两遍合一**：`material_pass` 0/1 的差别是采样过滤（NEAREST / LINEAR）与静止/运动的片选择。ES 3.2 有
   采样器对象，同一纹理绑两个单元用两种过滤，按片选择即可一遍画完。**代价是混合顺序变化**（现在 pass 0 全部
   先于 pass 1），属 V 级，要看画面；若不可接受则保留两遍但至少共享绘制记录。
6. **包围盒清空与 resolve**：积分 / 转存着色器用原子 min/max 写出片包围盒（按最大片尺寸与一步位移外扩即保守），
   合成时按「本帧 ∪ 上一帧」的包围盒设 scissor 做清空与 resolve，其余区域不动。plan.md 2.6 当年因「必须证明保守」
   搁置，原子包围盒是精确的，条件已满足。全屏 RGBA16F 清空 + resolve 在 4.4 MP 上是每帧固定开销。

### C 压力求解（G1 / V）
7. **迭代数**：先测残差随迭代的收敛曲线（同快照同种子，落盘每 10 次迭代的场差），再定 Jacobi 100 能否降到
   40–60；已有上一时刻的暖启动。
8. **求解器**：红黑 Gauss-Seidel / SOR 在同一分块核里实现，收敛快 2–3 倍；两层多重网格是更大的改动，只在 7 与
   8 都不够时考虑。
9. **网格**：`span/96` → `span/64` 或按设备 dpi 定格（单元 ≈ 3 dp），格数降一半以上；V 级。
10. **halo 与活动 tile**：已有活动 tile 列表与 indirect dispatch，核实 splat / blur 是否也只跑活动 tile；
    192 格 halo 是否按粒子实际到达范围收缩。

### D 精度（G1）
11. 积分与压力着色器里位置保持 `highp`（3192 px 的屏幕需要），速度、年龄、权重、色素、模糊与 Jacobi 的中间量
    改 `mediump`（Adreno 7xx fp16 ALU 两倍吞吐，Mali 同样受益）。**先做 Adreno + Maleoon 两台的散列自比较**
    再看 A/B（G0 判据两步走，见 followups）。

### E 数量与密度（V，用户定夺）
12. **按 dp 定微片尺寸**：以平板 / 三星现在的物理微片大小为准（约 2.2 dp），魅族 560 dpi 上每片 ≈ 7.7 px，
    全屏片数约从 15 万降到 7 万。积分、splat、绘制、建材全部按比例下降，也直接缩短左滑按下时的建材（35–70 ms）。
    这是**同样物理大小的微片**，不是单纯减量；仍要给用户看并排放大图。
13. 按场景分档：左滑卡片、弹窗、全屏各自的 `max_cells`；弱设备档位由实测帧率触发而不是机型表。

### F 调度与呈现（G0）
14. **两个上下文分优先级**：`EGL_IMG_context_priority`（魅族、华为、OPPO 都在扩展串里）。出帧上下文
    （转存 / 现场积分 / 绘制 / resolve / swap）高优先级，后台预算上下文（出现预计算、左滑预读、创建页预算）
    低优先级，同一 share group，历史采样用 `glFenceSync`/`glWaitSync` 交接。目的：一帧的绘制不再排在几十次
    dispatch 之后，`yieldToWindow` 那类栅栏串行化可以拆掉。这一条同时解决「弹窗 A 消散时弹窗 B 预计算抢 GPU」。
15. **左滑预读策略**：按实测每采样成本定预读档数；采样便宜之后追赶消失。
16. **合成侧**：`dumpsys SurfaceFlinger` 核对粒子层是 Device 还是 Client 合成，宿主窗口 + 弹窗 + 粒子层三层
    有没有把整屏拖成 GPU 合成；宿主窗口在粒子播放期的 FrameMetrics（暗层淡出、列表）。

### G 首帧延迟
17. 左滑：建材（三星 63–72 ms 未归因，先试大核亲和 / `THREAD_PRIORITY_URGENT_DISPLAY`）+ E12 的按比例下降
    + 预备档数；目标识别 → 首个非零画面 < 50 ms。
18. 弹窗消散：涟漪结算等待是设计（保留），把建材与管线准备完整压进涟漪期，结算后第一拍就出帧。
19. 创建页：命中路径的大头在窗口起来与首次布局（followups 已记），本专项不动。

## 4 阶段

- **R（调研，Opus，与 0' 并行）**：上网检索并对照本管线写出可落地的结论：移动端（tile-based）GPU 粒子系统的
  绘制形态（实例化 vs 顶点拉取 vs 索引四边形）、fp16 在 Adreno/Mali 的收益与陷阱、compute 的工作组与屏障
  实践、GPU 压力投影的快速方法（RBGS/SOR/多重网格/PCG，迭代数经验）、粒子-网格 splat 的原子与排序方法、
  历史/回放缓冲布局（帧主序 vs 片主序）、`EGL_IMG_context_priority` 与多上下文抢占、Android 呈现链
  （`eglPresentationTime`、SurfaceView 合成）。产出 `research-2026-09-17-per-frame.md`，每条附来源与
  「对本管线的适用性 / 预期收益 / 风险」。
- **0'（归因，Opus，与 R 并行）**：魅族上的基线矩阵 + 每帧分段归因（消融 + 分段 `glFinish` 相对量），产出
  `per-frame-baseline-2026-09-17.md`，含每个场景的修前录屏。
- **1–4（实施，Opus，按 0' 的数字排序）**：预计 批 1 = A1+A2+B6+F14（G0/G1，先做无视觉风险的）；
  批 2 = C7+C10+D11；批 3 = B4+B5+E12（V 级，交用户看图）；批 4 = C8/C9、G17/G18。每批一轮真机、一版 debug
  更新、一份并排放大图。**任何一批若魅族帧率没有可测提升就回退该项**，不留「理论上更快」的改动。

## 5 验证矩阵（每批都跑）

| 场景 | 指标 |
|---|---|
| 左滑记事卡片，慢拖 / 快拖 | 移动期不同画面数、识别→首个非零画面、呈现间隔 p90/max |
| 左滑按住来回滑（动画反复前进/后退，用户 2026-09-17 点名，魅族明显不跟手） | 每秒不同画面数、p90/max、手指相位与画出相位之差（滞后曲线，反向峰值与恢复拍数） |
| 弹窗消散：点按钮（涟漪 → 粒子先后）/ 点外部（无涟漪） | 帧数、p90、请求→首帧 |
| 弹窗 A 消散接弹窗 B 出现（附件 → 录音） | 两条会话各自的帧数；B 的首帧 |
| 复杂内容弹窗（习惯详情、调整颜色面板）出现 + 消散 | 同上 |
| 录音弹窗（FableSol 在播）出现 + 消散 | 同上，另看 FableSol 自身的帧率有没有被拖 |
| 新建记事（命中 / 冷启动未命中） | 点按钮→首帧、出现帧数 |
| 涟漪与粒子同步播放（记事行、工具栏图标） | 宿主窗口 FrameMetrics 与涟漪帧数 |

每格附画面：修前修后同一进度帧的并排 3–4 倍放大裁剪（`zoom-before-claiming-fixed`），V 级改动另附整帧。
