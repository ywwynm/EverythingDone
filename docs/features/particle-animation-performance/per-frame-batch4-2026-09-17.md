## 1 C7：先把「40 与 100 逐位相同」这件事拆开

第三批只比了画面，于是三种解释分不开：① 压力真的在 40 次之内收敛到浮点不动点；
② 压力算出来了但没进积分；③ 压力根本没算。本批在受控对照工具
（`ParticleOptionFrames`）里给每一档多记四项，一次就把三者分开：

| 记的量 | 从哪读 | 能分开什么 |
| --- | --- | --- |
| 活动 tile 数 | 工作缓冲表头第一个 uint（间接分发的组数） | 为 0 ⇒ Jacobi 一个工作组都没跑 |
| 压力场的非零格数 / Σ\|p\| / max\|p\| | Jacobi 最后写进去的那一份 | 随迭代数变而画面不变 ⇒ 压力没进积分 |
| 积分结果的 64 位散列 | `readState()` 的状态缓冲 | 与画面同步 ⇒ 差异确实来自模拟 |
| 活动区域与 splat 的 tile 包围盒 | 表头的 `region` / `previous` | 区域退化 ⇒ 缺陷在 C10 那一侧 |

## 2 根因：向量分量上的原子操作在 Maleoon 上不按下标寻址

`peel-splat.comp` 原来是

```glsl
layout(std430,binding=4) buffer D{ivec4 accumulation[];};
…
int k=cell.y*grid_shape.x+cell.x;
atomicAdd(accumulation[k].x, …);
atomicAdd(accumulation[k].y, …);
atomicAdd(accumulation[k].z, …);
```

原子操作的目标是**数组元素的一个向量分量**。Adreno 按预期寻址；Maleoon 910 上这三次累积
落到的地址与 `k` 无关，全部压在第 0 个元素上。后果是一条完整的链：累积缓冲除第 0 格外恒为零
→ `peel-blur.comp` 算出的占据度恒为零 → `pressure-tiles.comp` 一个 tile 都收不到
→ 间接分发的组数为 0 → **Jacobi 一次也不跑**，压力场保持上一帧的残值。这台设备上
压力投影从来没有真的工作过，迭代数自然改不动任何东西。

同一种写法在仓库里还有一处：`pressure-tiles.comp` / `pressure-tiles-large.comp` 的
`atomicAdd(workgroups.x, 1u)`。它的目标恰好是表头第 0 个元素，所以「碰巧是对的」——
但它是同一类不可靠的写法，一并改掉。

### 修法

1. `peel-splat.comp` 的累积缓冲改成**标量数组**：`buffer D{int accumulation[];}`，三个分量按
   `k*4`、`k*4+1`、`k*4+2` 寻址。std430 下 `ivec4` 的步长就是 16 字节，所以这与原来是
   **同一批字节**，读它的 `peel-blur.comp` 仍按 `ivec4` 取，一个字不用改。
2. 工作缓冲表头的 `uvec4 workgroups` 改成四个标量 `uint group_count, group_y, group_z,
   group_pad`（六个声明该块的着色器一起改），字节布局不变，`WORK_HEADER_BYTES` 仍是 64。
3. 单测加一条**判据式**的契约：把每一处 `atomic*` 调用的第一个实参切出来，只要它以
   `.x/.y/.z/.w` 收尾就失败。这样换个变量名、多一层下标都同样挡得住
   （见 `ParticlePerFrameBatchFourTest`）。

### 代价必须一并报告

压力这一段在那台设备上从没跑过，修好即是新增的工作量：

| 华为，附件弹窗素材 | 修前 | 修后 |
| --- | --- | --- |
| 现场消散每帧（100 次迭代） | 23.91 ms | **40.69 ms** |

## 3 两项参数进设置

用户裁定（[decisions.md](decisions.md) 2026-09-17 条）：微片尺寸与 Jacobi 迭代数都放进设置，
做成「上面实时预览、下面参数」的形式；微片尺寸的档位否决了 2.2 dp 并要求有更细的低档。

| 项 | 档位 | 默认 |
| --- | --- | --- |
| 微片尺寸 | 0.9 / 1.0 / 1.2 / 1.6 / 2.0 / 2.4 / 2.7 / 3.0 / 3.2 dp | **0.9** |
| 压力求解迭代数 | 20 / 30 / 40 / 60 / 80 / 100 | **100** |

### 默认值为什么真的是「现状」

材料在「720 逻辑像素 = 384 dp」的归一空间里建，一个 dp 是 1.875 个单位，而
`rules.properties` 里的下限 `cell=1.65` 个单位 = **0.88 dp**，写成一位小数就是 0.9。
如果最低一档真的往模型里写 0.9 dp（1.6875 个单位），格子会比现状小一点点，G0 就不成立了。
所以**最低一档不写下限**（`ParticleTuning.cellDpFloor(0)` 返回 0），标签仍显示 0.9 dp。
这一条有单测守着。

### 缓存键

两项都进 `ParticleCreationPrewarm.recipe()`。取的是**设置值**（`microflakeCellDp` /
`jacobiIterations`）而不是带线程局部覆盖的 `…Now` 读点——后者是离屏受控对照临时切的瞬时状态，
写进指纹会让预算必然判废。持久化的预测素材与内存里的预算共用同一个键，所以改了设置旧素材
一并判废，不必另加机关。

### 作用范围

`ParticlePerfTuning` 是进程里唯一的读点，弹窗、页内面板、创建页、左滑卡片全部经它。
`ParticleTuning.apply` 在 `App.onCreate` 与每次改动之后各推一次；**debug 的 A/B 配置文件
写过同名键时以文件为准**（那个文件是用来复测某一档的，被用户设置盖掉就白跑了）。

## 4 调参页：一个二级页面，不是弹窗

用户在实施中途把形态从弹窗改成**二级页面**（`ParticleTuningActivity`，入口在设置页
「音频海浪动画设置」之后）。这一改直接消掉了原方案里最大的一处风险：粒子层是
「一窗一 Surface」且以 Activity 为键（`ParticleWindowSurface.of(activity)`），做成弹窗就要
把它推广为按 Window 建，会动到「先显后撤、暗层交接、`hosts` 弱引用表」三处不变式；
做成二级页面之后预览与普通页面共用同一个粒子层，一行都不用动。

顶部预览有两种内容，可切换：

1. **记事卡片**——`RecyclerView` + `ItemTouchHelper` + `ParticleSwipeAnimator`，
   `warm` / `recordTouch` / `draw` / `finishSwipe` / `reset` 五个调用点与 `ThingsActivity`
   的回调逐条对应（单测把这一条钉住），所以预览里用手指左滑走的是**与首页同一条代码路径**；
   松手按 `ItemTouchHelper` 现有阈值判完成或回位，完成之后卡片自动回原位，可以反复试。
2. **示例面板**——圆角与内容照确认弹窗，由 `ParticlePanelAnimator`（详情页里的面板用的就是它）
   循环播出现与消散，点一下立刻走下一步。平板上按 360 dp 封顶，否则会铺满整行、片数虚高。

预览下方是本机读数：**片数 · 上一轮 x / y 帧（比值）· 间隔 p90**。片数由建材的两条出口
（`ParticleMicroflakeModel`）报上来，帧数由 `ParticleFrameStats` 在
`ParticleWindowSurface` 确认呈现时逐帧记（拿不到驱动呈现时刻的路径退回本拍的目标时刻）。
只在调参页开着时采集，别的时候第一行就返回。

参数改动后 **300 ms** 重建材料：滑杆抬手才落盘（拖动过程中每一档都重建会把正在播的那一轮
反复打断），落盘之后 300 ms 把预览那一轮重开，于是下一轮用的就是新值。

### 5.2 默认值下的 G0

本批改的是着色器里原子操作的寻址写法，**在 Adreno 上是逐位恒等的**：目标是同一批字节，
整数 `atomicAdd` 与顺序无关，清零写的也是同样四个 int。设置的默认值同样是恒等的：
最低一档的 dp 下限返回 0（= 不加下限），迭代数默认 100。

魅族 `ParticleTrajectoryCheck` 两份（一轮里出现与消散各一个动画层）**全部 `passed=true`**，
其中与本批直接相关的两格：

| 对照 | 帧数 | 有差异的帧 | 最大通道差 |
| --- | --- | --- | --- |
| 消散 自比较（同一条路径两遍） | 61 | **0** | 0 |
| 消散 C10 开 / 关（压力活动区域，重度使用累积缓冲） | 61 | **0** | 0 |
| 出现 自比较 | 37 | **0** | 0 |
| 出现 C10 开 / 关 | 37 | **0** | 0 |
| 消散 / 出现 第一批整体开 / 关（A1 是 G1，预期有差异） | 61 / 37 | 57–58 / 33–34 | 246 / 235 |

**没有做两版 APK 的逐位对照**：本项目的既有做法是「同一个二进制把开关关掉」，而这次的
改动没有开关（加一个就要同时保留两份着色器变体）。上面那两条 0 帧差异是最接近的旁证——
C10 的不变式恰好重度依赖累积缓冲的正确寻址。

创建页预算 hit：预算耗时 401.8 ms

创建页预算 hit：预算耗时 256.4 ms

指纹里没有这两项的话，第二对读到的会是同一份旧预算（仍报 407 ms），画面也仍是旧档位。

### 5.5 华为的轨迹对照没跑完

`ParticleTrajectoryCheck` 在华为上跑了 **42 分钟仍未收尾**（线程一直在跑、不是卡死），
超过驱动脚本 2400 秒的等待窗口，为了把矩阵与调参页这两项跑完而中止。原因是可归因的：
那块屏是 2880×1920 = 5.5 MP，而对照要在 CPU 上逐像素比几十条 61 帧的序列，本批修复之后
每帧的 GPU 成本还翻了近一倍。这一格欠着，下次在华为上跑要么先缩小对照规模，要么单独留一轮。
