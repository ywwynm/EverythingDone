# 用户偏好（本专项）

## 2026-10-07：大小统一改用倍率

- 用户在两种样式的尺寸分析后决定：设置里的粒子大小统一为倍率，不再使用绝对值，改完发布阿里云。此决定取代之前按可见直径校准 dp 的实施方向。

## 2026-10-07：大小设置应对应可见粒子

- 用户反馈飘散显示 2.4 dp 默认档，但实际看见的单颗粒子明显更小，要求核对默认值与尺寸含义。
- 两种动画的「粒子大小」都应对应屏幕上单颗可见粒子的大小，不应使用承载它的四边形、材料片或发射网格大小代替。
- 用户随后要求对流体也做实际核对；其主观感觉较符合设置数值，但希望确认，不能只依据上一轮对源码的初步判断。

## 2026-10-07：飘散连续播放去重与统一参数

- 用户随后指定两种样式大小共用 0.5～6 dp 范围：保留流体现有 16 档，新增 0.5、0.54、0.56、0.6、3.6、4.0、4.2、4.5、4.8、5.0、5.1、5.4、5.6、6，共 30 档；取代此前仅换算显示、保留不同范围的临时方案。
- 用户要求飘散连续两次播放不要选到相同的参考轨迹，范围包括反复开关同一弹窗、不同界面的弹窗，以及新建记事和卡片动画；同时检查出现动画的选择方式。
- 从飘散随机候选中移除灭霸轨迹，原因是用户认为其观感不佳。
- 两种样式的粒子数量下限都降为 0.1 倍；结合实际尺寸含义，评估并统一两种样式的粒子大小单位与可调范围。

## 2026-10-07：分析流体初段的方块感

- 用户反馈：流体数量减少或粒子增大后，刚开始消逝的颗粒呈现明显马赛克状，询问是否来自此前的「碎片／微片」实现，以及能否始终接近圆形。
- 首轮按用户要求仅分析；随后用户明确要求改为近圆轮廓并查看实际效果，进入实施与验证。

## 2026-10-06：流动样式也提供粒子数量设置

- 用户要求在原有「流体」（用户称「流动」）样式下增加与飘散同类的粒子数量设置，保留粒子大小设置。
- 本轮明确授权 ADB 真机验证、截图确认，然后发布阿里云调试版本；优先使用在线的三星 R5CW20BLNKL。

## 真机测试要省着跑（2026-09-14）

- 用户在第一批实施中指出：子代理"跑了一遍又一遍"真机测试，电脑性能受影响，要求"有把握了再跑"。
- 规则：实施类子代理先用 JVM 单测、离屏 61 帧散列对照、静态推理把改动做到有把握；真机只跑**一轮合并验证**（每台设备每个场景一轮，多项改动一起测），不做逐项 A/B、不做探索性对照、不做多轮重复；编译也合并，不为单个小改动反复 assemble/install。
- 需要做归因实验时，先在文档里写明目的与预计轮数，由 Fable 决定是否值得，或只在一台设备上跑一次。
- 阶段 0 那种 176 轮的测量矩阵是一次性的基线，不是常态。

## 分工（2026-09-14）

- 具体实施交给 Opus 子代理，Fable 只负责规划、任务书与关键部分的检查，以节省额度。

## 创建页出现动画的观感（2026-09-15）

- 用户希望新建记事时的出现粒子"确实从右下角 FAB 那里开始播放"，起始段要明显、有方向性；这是用户主动提出的外观调整，不受"粒子动画视觉不变"约束，但仍不改粒子模型本身，且要给用户看实机后可回退。

## 2026-09-17 逐帧成本专项：不得只对目标机过拟合

用户要求每一批都同时在连着的第二台设备上测（2026-09-17 当时是三星 SM-S9180，与魅族同一款 Adreno 740，防的是
ROM、面板与刷新率上的过拟合；OPPO / 华为在线时再各回归一轮），不只测目标机魅族。取舍规则：两台都不劣化、至少目标机
有可测收益；只在魅族上有收益而另一台变慢的项不收。真机 UI 矩阵两台各跑完整一轮，视觉对照两台各出并排放大图
（OPPO 不能录屏时用应用侧帧落盘或按进度点截图）。

## 2026-09-17 左滑测试记事必须覆盖复杂卡型

用户指出子代理建的测试记事太简单（一行字、卡片很矮）。左滑类场景要在一组不同复杂度的 `PROBE-*` 记事上各跑：
矮卡（一行字）、接近最大高度的长文本卡、10 条左右的清单卡、带图片附件的卡，以及布局不同的卡型（如习惯卡）；
指标按卡型分行报告。测完移入回收站，绝不用真实记事。

## 2026-09-17 左滑必须在一组不同复杂度的卡上测

用户在第三批中途指出：此前所有左滑都只在**一行字的矮卡**上做，而卡片高度直接改片数、
压力网格与 `ItemTouchHelper` 的阈值——实测矮卡与清单卡的片数差 **6.8 倍**（魅族 24 840 vs
169 050），清单卡的片数已经超过整屏弹窗。规则：左滑三格（慢拖 / 快拖 / 来回滑）从此在
**矮卡 / 高文本卡 / 清单卡 / 带图卡**（以及列表里若有习惯卡等别的卡型）上各跑一遍，
三格指标（呈现比、移动期不同画面数、间隔 p90/max、滞后曲线、识别→首个非零画面、
按下时建材耗时、片数）**按卡型分行报告**，两台都要。建卡用
`device_batch3_setup.py cards|make-list`，驱动用 `device_per_frame.py --swipe-titles 类型=标题,…`。

## 2026-09-17 取证与实施分开：先把假设逐条否掉

第三批的做法得到验证并应保持：任务书列出若干假设时，**先加一轮只读的取证**（本批是
`ParticleBeatTrace` 节拍级记录），用一轮真机把假设逐条判真假，再动手。本批五条假设里
四条当场被否（节拍没跳、栅栏只等 0.02 ms、pump 没赶不上、没有一拍卡在阶段/可见性上），
省掉的返工远多于取证本身的代价；而被证伪的两项改动（栅栏轮询、呈现时刻下限）**整段删除**，
不留「理论上更快」的代码。
