## 2 做法

### 2.1 三步序列的由来是奇偶性，不是别的

第 10 批及以前进对话框预览走的是 `startDialogSequence()`：

```kotlin
sampleDialog?.visibility = View.INVISIBLE      // ← 切过去的第一帧是空的
dialogStepsLeft = OPENING_STEPS                // ← 3：出现 → 消散 → 出现
main.postDelayed(dialogStep, FIRST_STEP_DELAY_MS)
```

为什么非得是三步，第 7 批的注释里写着：静止态必须**可见**（否则「稍后 / 继续」两个按钮点不到），
而**从不可见起步、以可见收尾，出现的次数必然比消散多一次**。三步里的第一次「出现」纯粹是为了
凑这个奇偶性，代价是粒子动画白播一遍，外加开头那一帧空白。

把静止的可见态**同时当成起点**之后，这条约束自己就消失了：起点可见、终点可见，
一轮「消散 → 出现」就闭合了。`OPENING_STEPS` 与 `startDialogSequence` 整段删掉，
`dialogStepsLeft` 从此只有两种取值——`ROUND_STEPS`（2）或 0，单测里有一条判据式断言盯着这件事。

### 2.2 三道「不许出现空白」的闸

静止显示不是「设一下 `visibility` 就完了」，中间有三处可能把它弄没：

| 时刻 | 会出什么事 | 这一批的做法 |
| --- | --- | --- |
| 切过去的那一帧 | 对话框从 `INVISIBLE` 起步，第一帧是空的 | `switchPreview` 的**对话框那一支不再置 `INVISIBLE`**（只有切回卡片那一支还置），`beginDialogPreview` 在同一次事件里把它设成可见——两个 `visibility` 一起在下一次遍历生效 |
| 上一轮留下的状态 | 原子交接期间真实面板的 `alpha` 是 0，中途切走再切回来就停在那里，看上去像「对话框没了」 | `showDialogIdle` 把 `alpha`、`translationX/Y`、`visibility` **一次写全**；`panelAnimator.cancel` 只撤动画层，撤不掉这些 |
| 那一轮起步时 | 对话框刚从 `GONE` 里出来、还没布局，`startContent` 会因为「尺寸为 0」直接拒收，`stepDialog` 旧代码随即把它置 `INVISIBLE` | 起步前先**等一帧真的提交**（`ParticleDismissController.runAfterShown`），再轮询 `dialogReadyForRound`（已附着 / `isShown` / `isLaidOut` / 尺寸非零 / 没有待落地的布局请求）；等过头（2 s）就干脆不播这一轮，**也不把它藏起来** |
| 消散起不来 | 系统动画被关掉、快照失败时 `dismiss` 返回 false，旧代码置 `INVISIBLE` 再等一步才补回来 | 整轮作废、撤掉已排下的那一步、`showDialogIdle()` 回到静止显示 |

「等一帧提交」不能用 `post` 代替：那只能证明这一次遍历排完了，证明不了 RenderThread 已经提交
（与跨窗口交接同一条纪律）。拿不到提交回调时走 300 ms 的兜底，最坏只是这一轮晚一点开始——
那段时间里对话框是静止显示的，画面不会空。

### 2.3 其余入口一律走同一轮

| 入口 | 第 10 批 | 第 11 批 |
| --- | --- | --- |
| 切到对话框那一格（`switchPreview`） | 空白 + 三步 | **直接显示 + 一轮** |
| 回到页面（`onResume`） | 空白 + 三步 | **直接显示 + 一轮** |
| 改参数重建材料（`restartPreview`） | 空白 + 三步 | 静止着就**直接显示 + 一轮**；**正播着就不打断**，等这一轮走完再用新参数补一轮 |
| 换方向（`applyDirection`） | 可见时一轮（第 9 批）；不可见时退回三步 | 可见时一轮；**不可见时也是「直接显示 + 一轮」** |
| 点「稍后 / 继续」（`replayDialogRound`） | 一轮 | 一轮（没动） |

`restartPreview` 那一条是本批顺带修的：拖滑杆时如果正播着，旧代码会把半散的对话框一把掐掉重来，
那也是一次瞬间跳变。`directionRoundPending` 因此改名 `pendingRound`——现在它有两个来源
（换方向、改参数），名字不该只说方向。

## 3 逐帧证据：两台各两段录屏

驱动是新增的 `device_batch11_ui.py`，两个子模式：`enter`（先进一次量下 bounds，退出页面再重新
进来，录**首次**切到对话框那一格）与 `back`（从静止的对话框出发，切到卡片、等 1.8 s 再切回来）。
`screenrecord` 是变帧率，逐帧读时间戳、解码加 `-vsync 0`，并断言帧数与时间戳数一致。

判据与取样区都从这一段录屏**自己身上**取，不写死任何颜色：

- `idle_color` = 末帧里对话框本体（内缩 8 px）**出现次数最多**的颜色，两台都是 (255,255,255)、
  占比 0.854–0.857；`page_color` = 预览区最左侧一条（页面底色，卡片与对话框都够不到）里出现
  次数最多的颜色，两台都是 (237,237,237)、占比 0.90–0.92。**不取单点**（第 10 批的教训）。
- `dialog_share` / `page_share` = 本体区域里与这两种颜色相差 ≤6 的像素占比。
- 「卡片还在不在」取**卡片左侧露出来的那一条**（卡片 640 dp 比对话框 320 dp 宽，这一条只有卡片）。

| 设备 | 场景 | 切换落地那一帧的 `dialog_share` / 静止态 | 切换 → 消散之间的静止帧数 / 秒 | 空白帧 | 穿越中点 | 单帧最大变化 | 孤立单帧跳变 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 魅族 | 首次切入 | **0.9121 / 0.9127（99.9%）** | 54 帧 / **0.659 s** | **0** | **2 次**（4.28 s 下、6.40 s 上） | **1.25** 灰阶 | **0** |
| 魅族 | 切走再切回 | **0.9069 / 0.9119（99.5%）** | 34 帧 / **0.613 s** | **0** | **2 次**（4.03 s 下、6.07 s 上） | **0.94** 灰阶 | **0** |
| 三星 | 首次切入 | **0.9178 / 0.9322（98.5%）** | 60 帧 / **0.722 s** | **0** | **2 次**（4.30 s 下、6.51 s 上） | **1.95** 灰阶 | **0** |
| 三星 | 切走再切回 | **0.9289 / 0.9323（99.6%）** | 38 帧 / **0.666 s** | **0** | **2 次**（3.98 s 下、6.20 s 上） | **1.43** 灰阶 | **0** |

四条判据逐条说明：

1. **切换落地那一帧对话框就已经在**。判的是「卡片撤掉的那一帧」上的 `dialog_share`，
   与静止态之比 98.5%–99.9%（差的那一点是 H.264 在场景切换那一帧的压缩残差）。
   三星上尤其干脆：**切换前只有一帧卡片**（t=3.421，`card_diff` 88.9），**7 ms 后的下一帧**
   就是完整的静止对话框（`dialog_share` 0.918）。
2. **切换到消散之间没有一帧空白**（`page_share ≥ 0.9` 的帧数为 0）。静止显示持续 0.61–0.72 s，
   正是 350 ms 的停顿加上抓图、建材与首帧上屏。
3. **穿越中点恰好 2 次** = 一次消散 + 一次出现，**一共一轮**。三步序列会穿 4 次。
   中点取「切换落地之后」那一段的静止值与最低值的中点——切换之前画面上是示例卡片
   （本体亮度 163–169，比页面底色低得多），把它算进去中点会落在卡片与对话框之间，
   穿越次数与单帧变化量都失去意义。
4. **单帧最大变化 0.94–1.95 个灰阶**，全程逐帧渐变；孤立单帧跳变 0 条。

并排图 `*-switch-montage.png`（切换前 3 帧 + 切换后 9 帧）上肉眼也是一样的结论：
橙色的示例卡片之后**紧接着**就是完整的对话框，中间没有空白的一格。

## 4 静止显示与出现末帧是同一个画面：逐像素对照

6. **改参数时「正播着就不打断」只有单测覆盖**：真机上拖滑杆的那一格没有专门录屏。

## 8 真机驱动踩到的三条

1. **判「卡片还在不在」不能贴着对话框上缘取带**。第一版取「卡片顶部到对话框上缘之间」那一条，
   三星上它只有 **4 px**（卡片上缘 635、对话框 640），量到的基准只有 15 个灰阶，判出来的切换
   时刻晚了两秒——正好落在消散开始的地方，看上去像「切过去是空白的」。改取**卡片左侧露出来的
   那一条**（卡片 640 dp 比对话框 320 dp 宽），基准稳定在 82–89 个灰阶。
2. **`screenrecord` 只在画面变化时出帧，「前几帧的中位数」不能当基准**。卡片那一格是静止的，
   三星上切换之前**只有一帧**，按「前 4 帧的中位数」算出来的基准已经是切换之后的值了。
   基准改取整段里的**最大值**，并断言它 ≥ 20（否则说明窗口取错、整段里根本没有卡片）。
3. **「两个画面是不是同一个」不能用录屏判**。H.264 在大场景切换之后要几帧才收敛：两帧**内容
   完全相同**的静止态之间就能差 p99 = 16–18 个灰阶、8%–11% 的像素差 > 4，与要测的信号同量级。
   这种判据必须换无损通路——把 `input tap` 与 `screencap` 合并成一次 `adb shell`，
   落进那 0.6 s 的静止窗口，两张 PNG 逐像素比，得到的是干脆的 0。
