# 颜色精度与大粒子绘制

## 起点与范围

此前优化已按用户要求提交为 `0f8f9b459`。本轮沿用三星 R5CW20BLNKL 授权，重点检查附件与颜色大弹窗；停止的压力求解器不再试验。现有真实记录已反复确认高负载流体颜色消散达不到稳定 120 fps，默认档也有设备状态波动，不重新重复建立同一基线。

## 颜色精度核对

- 流体“高”默认使用 `RGBA16F` 累积纹理；“标准”为 `SRGB8_ALPHA8`，每通道 8 位归一化整数，并通过纹理／目标格式处理 sRGB 转换。
- 飘散原先没有设置，默认 `RGBA16F` 工作面，不支持浮点帧缓冲时回退 `RGBA8`。它当前在 sRGB 数值上混合，新增标准档应使用 `RGBA8`，不能直接照搬流体的 sRGB 纹理格式而改变混合语义。
- 这些是中间混合缓冲的精度，不意味着来源快照和最终屏幕输出也都是 16 位浮点。每像素缓冲存储从 8 B 减为 4 B，不等于整帧耗时减半。

## 本轮判断与验证

1. 颜色混合的存储和带宽可能仍然昂贵：使用两种格式进行同输入成对比较，同时覆盖 src-over、加光、深浅背景、密集大粒子和消失末段。飘散新增独立设置，默认高精度，流体旧设置原样继承。
2. 圆形粒子的透明外围与软边计算可能有可裁减成本：先以正式 GLSL 数值／图像对照筛选，不预先增加几何顶点或采用近似。
3. 真实长帧可能主要集中在密集叠加阶段，也可能受调频和呈现队列影响：沿用已确认的实际呈现和固定输入逐帧口径，不把离屏均值直接换算成稳定帧率。

实施和验证结果随进展回填。

## 后续要求：统一颜色管线

用户追问两种样式为何不同、能否统一。差异来自既有实现：流体在线性空间混合，飘散沿用参考实现对 sRGB 数值直接混合。统一目标为高档 `RGBA16F`、标准档 `SRGB8_ALPHA8`，都在线性空间累积，然后转换为 Android 窗口所需的颜色输出。需同时检查普通透明叠加和加光；飘散的加光颜色可能大于 alpha，不能照搬流体的零 alpha 丢弃规则。先做固定输入画面对照，再决定具体实现。

离屏原型完成五组素材、80 组比较。普通透明叠加的全图平均变化最大约 0.84／255，加光参考最大约 10.69／255，亮带和暗部变化明显；高、标准档缓冲之间的差异远小于更换混合空间的变化。用户查看对照后明确选择保留现有观感，因此不接入线性原型，不修改正式飘散 GLSL。两种样式统一设置操作和精度档位含义，保留各自的混合规则。原型及对照在 `tmp/particle-color-drawing-20261008/linear-prototype/`。

`RGBA8` 与 `SRGB8_ALPHA8` 均为 4 B／像素，后者自动转换 RGB 的颜色编码、alpha 保持线性。是否更快取决于硬件和被替代的着色器工作，不能声称统一格式能直接加速。曾拟将这些细节写入界面说明，用户明确要求保留原有面向用户的简单表述，已撤回文案修改。

## 三星首轮结果

- 流体标准档在四组同输入大场景中，现场消散耗时减少约 3%～8%；倒放有波动，不能承诺所有情况都变快。
- 飘散初版 `RGBA8` 标准档在附件、颜色和加光颜色场景中，单帧耗时减少约 2%～3%。该结果属于统一颜色空间之前的版本，后续修改后须重新确认。
- 关闭最终混合的直接覆盖候选虽然像素一致，但现场消散略慢、倒放慢约 4%～7%，已撤回。
- 圆边平方距离近似在静态验证中误差很小，三星净收益不稳定，已撤回，不增加正式着色器复杂度。
- 两种样式颜色设置的默认值、独立保存、页面重启与恢复默认已通过真实 UI 检查。

## 离屏检查与视觉代价

- 新增飘散独立偏好 `drift_color_precision_standard`；流体继续使用原键，不迁移或覆盖它的值。切换样式刷新选中态，恢复默认清除两种颜色设置；渲染器创建时固定本轮格式，播放中不重建工作面。
- `checks/check_color_drawing.py` 已完成 80 组正式飘散着色器对照，覆盖五组既有素材、深浅背景、1×／3× 大小和四个时刻。标准档的全图平均通道差最大约 0.413／255；src-over 密集区域个别通道可差 34／255，超过 2 灰阶占比最多约 3.56%。加光场景差异较小。
- 并排目检发现标准档的密集纯色区域可出现额外的浅深颗粒纹理。这是每次混合的 8 位舍入累积，不能声称两档完全等价；因此仍默认高精度，标准档作为用户明确选择的性能取舍。
- 圆形软边的平方距离三次近似，解析覆盖最大误差约 0.000651（单层约 0.166／255），8 组多粒子 GLSL 叠加对照最终 RGBA8 最大差 1 灰阶。完整覆盖输出关闭混合的两组偶数／奇数尺寸对照像素完全相同；两项均因三星净收益不足而撤回。
- 参考 [Khronos 帧缓冲说明](https://wikis.khronos.org/opengl/Framebuffer) 与 [Arm 图形性能指南](https://documentation-service.arm.com/static/67a62b17091bfc3e0a947695)：颜色格式、混合与无效写入可能影响带宽和片元工作；本轮不套用其他设备的加速倍数。

## 大弹窗实际呈现与长帧

三星真实空白新建页，数量 1.6×、大小 3×，每种档位一轮附件／颜色出现与消散。实际颜色快照为 1380×2281，合成固定输入基准为 1380×1582，不能混用。各轮真实随机材料和运行状态不同，只用于边界检查，不将前后 FPS 差值归因于格式。

| 样式与精度 | 附件出现／消散 fps | 颜色出现／消散 fps |
|---|---:|---:|
| 流体高 | 120／113 | 120／101 |
| 流体标准 | 120／120 | 116.1／90.2 |
| 飘散标准 | 120／118 | 118.3／120 |

- 流体颜色消散的呈现间隔 P90 均为 16.67 ms，高档最大 25 ms、标准最大 16.68 ms。标准档仍有长帧，不能以固定输入平均收益声称稳定 120 fps。
- 流体颜色消散等栅栏 P90 约为 9.8／13.2 ms，含等待的合成阶段 P90 为 10.7／14.9 ms；交换缓冲约为 0.95／1.13 ms。两个含等待的数不能相加。慢提交主要在消散中前段：高档约 13%～47%，标准约 17%～70%，符合生产者 GPU 工作尚未完成的表现，不能仅凭它断言全由透明叠加造成。
- 飘散标准档两次消散的提交 P90 为 3.65／3.34 ms，没有超过 8.33 ms 的提交；附件仍有一次 25 ms 呈现间隔，说明减少颜色带宽不能消除所有调度／呈现偶发间隔。
- 原始记录在 `tmp/harmony-particle-android-port/color-{flow-high,flow-standard,drift-standard}/`，分段结果在 `tmp/particle-color-drawing-20261008/long-frames.json`。仅操作空白新建页，不保存记事；脚本最终恢复原偏好与诊断配置。
