# 粒子动画性能分析（2026-09-14）

## 范围与依据

用户反馈四点：按钮涟漪与弹窗出现粒子争抢资源、涟漪播不完整（长条形按钮最明显）；点新建按钮后要停顿一下粒子才出现，比涟漪、边框光效两档明显迟；左滑触发粒子不跟手；粒子帧率不稳，内容复杂、反复开关、弹窗接弹窗（添加附件 → 录音）时更差。

本文只做分析，不改代码。依据是三部分：`views/particledismiss/` 全部源码与 `shared/particle-dismiss/` 着色器；GPT-6 留下的真机测量记录（`dialog-particle-dismiss/` 下 startup-latency、appearance-startup、ripple-transition-performance、concurrent-feedback-and-dismissal、repeated-appearance-and-wave-handoff、presentation-continuity 六份，以及 `thing-creation-animation/performance-validation-2026-09-13.md`、`startup-and-outline-2026-09-14.md`、`swipe-complete-animation/reverse-and-latency-2026-09-14.md`）；两项平台调研（另见 `research-2026-09-14-platform.md`）。本轮没有连接设备，没有新测量。

约束：出现与消失的粒子动画在视觉上不能有可察觉变化。下文把每项候选改动按保证级别标注：**G0** 表示 GPU 输出逐位不变；**G1** 表示算式相同、只有浮点合并顺序不同，差异在浮点噪声量级，需要用并排视频与差值图确认视觉不可分辨。

## 现有管线：一次动画从请求到首帧发生了什么

### 共同基础

- **叠加层**：每次动画在宿主 Activity 的 DecorView 上 `addView` 一个全屏 `FrameLayout`，内含全屏透明 `TextureView`，消失路径再叠一张快照 `ImageView`（`ParticleDismissOverlay.kt:86`）。`addView` 会触发整个窗口的重新测量与布局。GL 每交换一次缓冲，`onSurfaceTextureUpdated` 就 `postInvalidateOnAnimation()`（`ParticleDismissOverlay.kt:189`），HWUI 要把整屏内容加这张全屏纹理重新合成一遍，再交给 SurfaceFlinger。
- **渲染线程**：每个叠加层各起一个 `ParticleDismissGl` 线程，新建 EGLDisplay 连接、EGLContext、窗口表面，然后编译全部着色器程序（`preparePipeline` 六个程序、`prepareReversePipeline` 四个，`ParticleMicroflakeRenderer.kt:66-99`），分配全屏 RGBA16F 累积纹理（2520×1680 约 34 MB，`ParticleMicroflakeRenderer.kt:79-81`），上传两张 64×64×48 的三维流场纹理。动画结束线程退出，全部资源销毁。反复开关就反复做这一套。
- **播放时钟**：`ParticlePlaybackClock` 把 Choreographer 回调挂在**主线程** Looper 上，再 post 到 GL 线程（`ParticlePlaybackClock.kt:50-58`），120 Hz 屏幕上按每隔一拍取样到 60 Hz（`:24`）。这意味着主线程一停，粒子帧也一起停。GL 线程每帧画完后 `glFinish()` 再 `eglSwapBuffers`（`ParticleMicroflakeRenderer.kt:396-400`）。`glFinish` 是为 TextureView 加的：TextureView 只保留最新一个缓冲，GL 若领先 HWUI 一拍，旧帧会被直接替换掉。
- **刷新率**：请求动画时对源窗口和宿主窗口同时设置 `preferredRefreshRate = 60` 并关闭省电平衡（`ParticleWindowFrameRate.kt:14-19`），最后一层退出时恢复。GPT-6 的系统 trace 把两次 55–72 ms 的长帧归到刷新率切换（concurrent-feedback 记录）。调研指出 `preferredRefreshRate` 的文档口径本身就是无缝切换，所以这两次长帧更可能来自两个窗口各做一次 `Window.setAttributes` 引发的完整 relayout 与表面重配置，动画开始与结束各来一遍；归因要在阶段 0 重测。
- **涟漪**：应用自绘的 `GradientRippleDrawable` 用三个主线程 `ValueAnimator` 驱动半径（256 ms）、淡入（60 ms）、淡出（300 ms），每个 tick `invalidateSelf()`（`GradientRippleDrawable.kt:212-261`）。系统 `RippleDrawable` 的动画跑在 RenderThread 上，主线程阻塞时仍按 vsync 推进；自绘版本没有这层保护。
- **快照**：API 29+ 用离屏 `HardwareRenderer`：主线程录制显示列表（`ParticleHardwareSnapshot.kt:78`）并 `syncAndDraw`（`:89`），工作线程等栅栏、包装硬件缓冲、`copy(ARGB_8888)`（`:59`）。之后材料线程再 `getPixels` 成 IntArray（`ParticleMicroflakePreparation.kt:29`），GL 线程再 `packColors` 成 RGBA 字节上传。全屏一次是四份 17 MB 的拷贝。进程内只有一条 RenderThread，离屏渲染与源窗口涟漪的帧在同一条队列上排队。

### 出现（弹窗、新建页、保存后的卡片）

出现动画是共同消散模型的倒放：先完整正向解算 0.6 秒轨迹，把每片粒子可见寿命附近的状态存入历史缓冲，再从末帧倒序显示。倒放的第一帧就是正向的最后一帧，所以**预计算不结束，任何一帧都画不出来**，这是结构性的等待，不能靠流式播放消掉。

链路（`ParticleDismissController.appearContent`，`ParticleDismissController.kt:314-426`）：

1. 面板 alpha 置 0，等布局稳定（preDraw → post → 重试）；
2. 硬件快照 + 圆角遮罩（遮罩在主线程软件绘制，`:557-568`）；
3. 创建叠加层并 `addView`（`:416`），GL 线程起、建链、编译、分配；
4. 材料线程 `getPixels` + 本地库建材（约 13–37 ms）；GL 线程上传前景与状态；
5. GPU 预计算：0.6 s × 240 Hz = 144 次积分 dispatch，每 4 步一次压力更新（36 次），每帧一次历史转存（37 次）；
6. 首帧交换 → `onSurfaceTextureUpdated` → HWUI 下一帧合成 → 帧提交回调 → 撤快照、启动暗层。

GPT-6 的实测（已发布包，热运行）：弹窗请求到首帧 OPPO 约 221–246 ms、三星约 287–331 ms，另有 48–91 ms 布局与捕获；新建页全屏约 333–415 ms，其中轨迹预计算约 226 ms、建材等待约 37 ms、上传约 21 ms。

### 消失（弹窗、页内面板）

正向实时播放：每个 60 Hz 帧推进 4 个积分步和一次压力更新，再画两遍 160k 实例的微片、一遍全屏 resolve。请求到首帧约 86–125 ms，主要是快照、建材、上传。若源控件上有自绘涟漪，消散会等涟漪自然结束再开始（`ParticleDismissRenderer.kt:165`），因为快照里不能带涟漪。

### 左滑

按下卡片即 `warm()`（`ParticleSwipeAnimator.kt:31`，由 `ThingsActivity.kt:6599` 在 RecyclerView 的 DOWN 触发）：捕获卡片快照、建全屏叠加层（alpha 0）、起 GL 线程、建材、上传、算第 0 帧。识别左滑后叠加层显示，轨迹按手指进度按需补算（`ParticleMicroflakeRenderer.kt:344-352`）：手指在动时只算到当前进度所需的相邻档，手指停住才多预备两档。

实测：按下到零进度就绪约 130–200 ms；识别左滑到首个非零画面约 43 ms；慢拖纹理间隔 P95 约 25–33 ms。

### 每帧 GPU 工作量（按现有着色器计数）

一个 60 Hz 帧（正向播放或预计算的一个采样）：

| 阶段 | dispatch 次数 | 说明 |
| --- | --- | --- |
| 积分 `step.comp` | 4 | 每次 625 个 256 线程工作组，每片 2 次三维流场显式三线性采样、2 次三八度 curl、压力场采样；每次后 `glMemoryBarrier` |
| 压力：splat 清零 + 累加 | 2 | 原子加 |
| 压力：分离高斯模糊 | 2 | 横竖两遍 |
| 压力：tile 收集 | 2 | 两遍，另加一次命令屏障 |
| 压力：Jacobi | 13 | 100 次迭代按 8 次一批，32×32 shared tile；只处理非空 tile |
| 压力：清目标 + 投影 | 2 | |
| 历史转存（预计算/手势） | 1 | 纯拷贝 |
| 绘制 | 2 次实例化绘制 + 1 次 resolve | 全屏 RGBA16F 清空、两遍 160k 实例、全屏线性→sRGB |

合计每帧约 26 次 dispatch、27 次屏障。**阶段 0 更正**：出现预计算的积分跑满 240 步（`ParticleReversePlan.time` 的 t 从 0 到 1.0），只是历史按 0.6 s × 60 Hz 采样，实测每次预计算是 240 次积分 dispatch + 60 次压力更新 + 37 次历史转存，约 1540–1660 次 dispatch，而不是本文初稿估的 937 次；左滑完整 1 秒轨迹同样约 1560 次。本文初稿假设"每次屏障都是一次流水线排空、空转占大头"，阶段 0 的消融实验已经否定：去掉积分步之间的 240 次 `glMemoryBarrier`，两台设备耗时不变、61 帧输出零差异。实测分布是压力更新约 39–45%、积分 dispatch 含计算约 21–33%、其余（历史转存、状态重绑、CPU 提交、历史缓冲分配）约 22–40%。详见 [phase0-baseline-2026-09-14.md](phase0-baseline-2026-09-14.md) 第 1、2 节。

## 逐条诊断

### 1. 涟漪被粒子出现抢资源，播不完整

四个机制同时存在，按我判断的权重排序：

1. **主线程被同一次点击的后续工作占满。** 点击 → 关闭当前弹窗（`GestureAnchoredDialog.dismiss` → `ParticleDismissController.start`，树遍历、快照录制、遮罩、叠加层 `addView` 与整窗重布局）→ 打开下一弹窗（Fragment 事务、充气、`onStart` 里 `startCondense`、暗层、再一次快照与叠加层）。GPT-6 实测这段主线程最长间隔 35–85 ms，录音弹窗首次创建更长。涟漪的三个 `ValueAnimator` 在主线程上，主线程停多久涟漪就停多久，恢复后按时间跳到对应进度。长条形按钮的铺满半径大（到最远角，平板上超过 1000 px），256 ms 的扩散里跳掉 60–80 ms 是一大段可见的波前跳跃；小按钮几帧就铺满，跳跃不明显。这与"长条形最明显"吻合。
2. **刷新率切换。** 关闭请求一发出就对两个窗口投 60 Hz，OPD2515 立即从 120 切到 60，切换本身带来 50–70 ms 长帧，正落在涟漪扩散期。
3. **GPU 队列先进先出。** 下一弹窗的逆向预计算在 GL 线程上按批提交，最多两批在途（`ParticleGpuWork.kt:12-23`），每批约 26 次 dispatch。源窗口 HWUI 画涟漪的一帧排在这些批次后面，同优先级的上下文按提交顺序执行，涟漪帧就被推迟。GPT-6 的让步实验（每批后让出）把消散纹理最长间隔从 166 ms 降到 30 ms，证明预计算确实会饿死别的 GPU 工作，但只是减轻，没有优先级。
4. **RenderThread 与 CPU 争用。** 离屏快照的 `syncAndDraw` 与涟漪帧共用进程唯一的 RenderThread；材料线程与 GL 线程都以 `THREAD_PRIORITY_DISPLAY` 运行，与主线程、RenderThread 抢大核。

新建按钮本身用系统涟漪（`FloatingActionButton.kt:83-96` → `BackgroundUtil.circularRipple`），跑在 RenderThread，所以问题 2 里没有涟漪被截断的现象，反过来印证机制 1。

### 2. 点新建按钮后停顿一下粒子才出现

三档共同的前置开销：点击后先对首页整屏做硬件快照并复制（`ThingCreationTransition.kt:209`），回调里才 `startActivityForResult`（`:204`），然后 DetailActivity 创建、初始化、首次布局。涟漪与边框光效两档在内容首次 preDraw 就开始动画，之后没有任何准备。粒子档在同一时刻才开始上面"出现"链路的第 1–6 步，热运行 333–415 ms，其中：

| 段 | 约耗时 | 性质 |
| --- | --- | --- |
| 等布局稳定 + 全屏硬件快照与复制 | 50–90 ms | 部分可省（少拷贝、不等整窗重布局） |
| 材料建材（本地库） | 13–37 ms | 已优化，剩余有限 |
| 前景转换与上传（17 MB） | 约 21 ms | 可零拷贝 |
| GPU 预计算 0.6 秒轨迹 | 约 226 ms | 主体；结构性等待 |
| 首帧经 TextureView 合成上屏 | 1–2 帧 | 可省一跳 |
| 120→60 Hz 切换 | 50–70 ms 长帧 | 可去掉 |

在这段时间里屏幕停在首页快照上不动，暗层也按设计等首个粒子帧才起（用户此前明确不要暗层先于粒子），所以用户看到的就是"停一下"。缩短它只能靠让预计算更快、把预计算前后的固定开销去掉、去掉刷新率切换。

### 3. 左滑不跟手

- 按下到零进度就绪 130–200 ms 里，大部分是每次都重来的固定开销：快照与复制、全屏叠加层 `addView` 引发的整窗重布局、EGL 建链、十个程序编译链接、34 MB 累积纹理分配、三维纹理上传，然后才是 13–20 ms 的建材。真实左滑通常在按下后 50–150 ms 就开始移动，此时准备常常还没完。
- 识别左滑后的 43 ms：第一个非零画面需要第 1…k 档轨迹，每档一次完整压力更新（约 5–8 ms GPU），k 由当时进度决定；而"手指在动时不预备后续档"的策略让 GPU 永远落后手指一步，每帧的显示都要等当次补算完成。
- 拖动中每新增一档都是 26 次 dispatch；中速拖动一帧要新增 2–4 档，GPU 每帧 10–30 ms，于是 P95 25–33 ms。
- TextureView 比 SurfaceView 多一跳 HWUI 合成，输入到显示多约一帧；按下时的 60 Hz 投票又触发一次模式切换。

### 4. 帧率不稳，弹窗接弹窗最差

- **单帧 GPU 结构**：26 次 dispatch、27 次屏障加三次绘制，屏障空转叠加实际计算，估计 10–13 ms；同一帧里 HWUI 还要为 TextureView 重新合成整屏（2–4 ms），弹窗窗口再画涟漪，SurfaceFlinger 再合成三层。预算 16.7 ms 几乎没有余量，任何抖动都掉一帧。
- **`glFinish` 串行化**：GL 线程每帧等 GPU 做完才交换，CPU 编码与 GPU 执行不能重叠；这是 TextureView 缓冲替换逼出来的。
- **弹窗接弹窗**：A 的消散每帧 26 次 dispatch 正在播；B 的预计算 937 次 dispatch 在 200–350 ms 内挤进同一个 GPU 队列；B 的窗口在主线程创建、A 的窗口在移除、涟漪在画。先进先出之下 A 的帧被排在 B 的批次后面。更直接的一条：A 的播放节拍来自主线程 Choreographer，B 的窗口创建让主线程停 35–85 ms 时，A 的粒子帧按构造就一起停，与 GPU 无关。GPT-6 实测重叠时仍有约 30 ms 波动，首次录音出现只确认到 19 个不同纹理帧。
- **反复开关**：每次动画都新建 EGL 上下文、重新编译链接十个程序、分配并释放 34 MB 累积纹理与若干 SSBO，Graphics 内存在 41–147 MB 之间来回；每次开始和结束各切一次刷新率。
- **主线程**：叠加层 `addView` 整窗重布局、圆角遮罩软件绘制、快照录制都在主线程，与暗层动画、弹窗窗口动画抢同一条线程。

## 成本模型里还没有数的地方

1. 预计算 GPU 忙时间与墙钟时间之比。这决定合并 dispatch 的收益上限。
2. 单帧内积分、压力、绘制三段各占多少。
3. 涟漪卡顿在主线程停顿、刷新率切换、GPU 排队三者之间的归因。用三个只改一处的对照就能分开：临时不投 60 Hz；临时把长条按钮换回系统涟漪；临时把在途批次降到一批。
4. 三星与 OPPO 的差异来源：三星预计算慢 30–40%，Adreno 740 的算力并不弱，更像是每次 dispatch 的固定开销更高。

这四项放进方案的第 0 阶段。

## 结论

四个反馈指向同一组结构性原因，不是某个参数：预计算的压力求解与 CPU 侧逐 dispatch 提交（屏障本身不是问题，阶段 0 已否定）；叠加层走 TextureView 并因此需要 `glFinish` 与 60 Hz 投票，后者把涟漪帧率砍半；每次动画重建整个 GL 环境；粒子时钟挂在主线程；另有阶段 0 发现的 `ParticleTouchFeedback` 在 OPPO 上走满 1.5 s 超时的生命周期缺陷。这些都可以在不改粒子模型、不改材料、不改积分与压力迭代次数的前提下处理，绝大部分是 G0；只有"把 4 个积分步合并进一个 dispatch"可能落到 G1，因为此前已经证实直接合并后浮点结果不逐位相同，方案里先用"合并但保留每步 SSBO 往返"争取逐位相同。具体方案见 `plan.md`。
