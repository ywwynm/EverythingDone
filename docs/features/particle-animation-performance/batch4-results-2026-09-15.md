## 1. 缓存键清单：创建页首帧到底由什么决定

先按用户要求核实「影响创建页 UI 的变量不多」。逐条查了 `DetailActivity` 创建模式的初始化路径
（`onCreate` → `init` → `initMembers` / `findViews` / `initUI` / `setActionbar` / `setEvents`），
结论是**变量不算少，但可以按「会不会改首帧像素」筛掉一大半**。

### 1.1 进了缓存键的

| 输入 | 来源 | 键里的名字 |
| --- | --- | --- |
| 新记事背景（纯色 / 渐变 + 方向） | `App.newThingBackground`，`ThingsActivity` 建 Intent 时读 | `bg` |
| 所在文件夹（整条祖先 id 链 + 状态 + 类型筛选 + 私密鉴权态） | `ThingListProjection.key()` + `isCurrentFolderPrivacyAuthenticated()` | `folder` |
| 深浅色 | `Configuration.uiMode & UI_MODE_NIGHT_MASK` | `night` |
| 语言 | `Configuration.locales.toLanguageTags()` | `loc` |
| 字号缩放 | `Configuration.fontScale ×100` | `font` |
| 屏幕密度 | `Configuration.densityDpi` | `dpi` |
| 窗口尺寸 | 首页 DecorView 的 `width×height` | `win` |
| 方向 | `Configuration.orientation` | `ori` |
| 多窗口 | `Activity.isInMultiWindowMode` | `multi` |
| 系统栏 + 刘海 inset | `WindowInsetsCompat.systemBars() or displayCutout()` 的 top / bottom | `bars` |
| 输入法高度 | `WindowInsetsCompat.ime()` 的 bottom | `ime` |
| 新建动画档位 | `ThingAnimationPreferences.creation()` | `mode` |
| 系统动画时长缩放 | `AnimatorDurationScale.scale() ×100` | `scale` |
| 刷新率 | `display.refreshRate` | `hz` |
| 新建按钮中心（2b 的真实触点） | FAB 在窗口里的中心，取整 | `fab` |
| 影响轨迹的全部开关 | 触点档位、2c 开关与门槛、2.4、2.2、2.1 | `recipe` |

键在**点新建按钮的那一刻**由 `ThingsActivity` 算出来，随 `ThingCreationTransition.launch` 传给
创建页——创建页起来之后再算就分不清是不是同一份环境了。

### 1.2 查过但没进键的，以及为什么

| 输入 | 为什么不进 |
| --- | --- |
| 文件夹的**名字与配色** | 完整祖先链路径要逐级查数据库（`ThingFolderDAO.getFolderPath`），不能压在点击那一刻的主线程上。改名/改色只让预测素材稍微过时（影响途中每一片的权重），末帧仍由真实贴图拼回，下一次真实新建自动纠正 |
| 「快速新建」常驻通知 | 第三批已挪到入场动画之后，不在首帧路径上 |
| 快速提醒的默认档位 | 每次新建恒为「15 分钟后」，不是偏好；只有每日待办入口走另一档 |
| 分享进来（`ACTION_SEND`）、每日待办、桌面快捷方式、常驻通知四个入口 | 它们不经 `ThingCreationTransition.launch`（没有 `EXTRA_TOKEN`），根本不播粒子入场，也就没有预算可命中 |
| 自动链接偏好、密码保护、附件区 | 新建记事的标题/正文/附件恒为空，这三支在 CREATE 首帧上恒定 |
| 状态栏图标明暗 | `post` 出去的，且只改系统栏、不改 content 内像素 |

### 1.3 键之外还有两道硬核对

即使键判相同，也还要过两关，任何一关不过就**原样退回完整路径**（绝不会播错画面）：

1. 主线程 `take()`：真实快照的**尺寸**与**原点**必须与预算时完全一致；
2. GL 线程 `adopt()`：共享资源（累积纹理）尺寸与快照尺寸再核一次。

## 2. 为什么预测快照用的是「上一次真实创建页的首屏」

用户认可的设计是**轨迹与贴图分离**：用预测快照建材、预算轨迹，点新建之后只把**真实快照**换成
前景贴图。这一条成立的依据在 `material.vert`：第 0 遍（表面）把每个格子按 `uv = source / card`
采样前景纹理、画在 `world = offset + source`——**采样位置与屏幕位置是同一个恒等仿射映射**，
所以倒放末帧（t = 0，全部格子 `surface_out = 1`、复制片全被裁掉）就是这张贴图的一次逐像素拷贝，
**与格子分辨率无关**。换句话说，预测快照即使把格子切得完全不同，末帧仍然是真实页面。

预测快照本来的首选方案是「把创建模式的视图初始化拆成可作用于离屏 View 树的函数，用
`HardwareRenderer` 离屏渲染同尺寸的创建页」。调研之后**判定改造过大**，四条具体阻碍：

1. **首帧几何 100% 由 decorView 的 inset 回调链决定**：正文区 `marginTop = 56dp + statusBarTopInset`、
   根布局 `paddingBottom = max(导航栏, 输入法)`。离屏树没有 ViewRootImpl，这条链根本不会触发，
   只能手工注入一份复刻的 `WindowInsets`——而其中的**输入法高度**在预测那一刻无从得知；
2. **`App.updateNewThingColor()` 就写在 `initMembers` 正中间**，离屏跑一遍会把下一次的随机背景
   提前掷掉，缓存永远命中不了；同一段里还有全局计数器、两次 `registerReceiver`、一次可能写偏好
   并弹窗的版本升级检查；
3. **actionbar 上那三个图标走 `AppCompatDelegate`**（`setSupportActionBar` + `menuInflater`），
   与 Activity 绑死，离屏要另写一套——那是对真实页面行为的改动，不是纯提取；
4. `DetailActivity` **5840 行**，创建路径触碰约 **50 个类级字段**，抽出来等于重写这个 Activity。

因此采用退路：**把上一次真实创建页的首屏像素留在进程里**当预测素材。代价是背景色与真实页面
不同（只影响途中每一片的出生、寿命与复制片数），收益是零额外渲染、零副作用。**进程启动后的
第一次新建必然未命中**（没有素材），第二次起才有提速——这与任务书里「首次为未命中、第二次为
命中」的预期一致。

预测素材不额外拷贝像素：材料线程本来就要把快照解成一份 ARGB 数组交给模型，这里只多留一个引用。

### 2.1 随机掷点提前

`App.updateNewThingColor()` 原来写在创建页的 `initMembers` 里。本批改成：

- 创建页只调 `App.consumeNewThingBackground()` 标记「用掉了」，不当场重掷；
- 首页 `onResume`（含每次创建页关闭之后）调 `App.ensureNewThingBackground()` 重掷，随后才开始预算；
- **每一个读预掷值的地方**（首页两处 Intent、桌面快捷方式、每日待办、常驻通知、创建页兜底）
  都先调一次 `ensureNewThingBackground()`：已消费而还没重掷时立刻补掷，**两条记事绝不会同色**。

## 3. 创建页的整条时间线（两台、两次）

自**新建按钮抬手**起算，单位毫秒。第一次是未命中（进程刚启动、没有预测素材），第二次是命中。

| 分段 | OPPO 未命中 | OPPO **命中** | 三星 未命中 | 三星 **命中** |
| --- | --- | --- | --- | --- |
| 首页快照完成 | 30.6 | 33.6 | 45.9 | 49.0 |
| `DetailActivity.onCreate` | 52.4 | 54.8 | 92.6 | 86.8 |
| `init()` 全部完成 / 出现请求 | 77.7 | 76.3 | 125.9 | 118.2 |
| 首次布局稳定 | 131.8 | 124.5 | 250.2 | 209.2 |
| 快照完成 | 150.8 | 139.2 | 285.0 | 242.8 |
| 材料建完 / **贴图换完** | 199.9 | **153.5** | 373.6 | **264.3** |
| 预计算完成 | 460.8 | **153.5** | 848.0 | **264.3** |
| 首帧提交 | 468.7 | **157.2** | 868.1 | **273.6** |
| **首帧真的上屏** | **485.4** | **171.3** | **897.7** | **304.6** |
| 首帧存活片占比 | 13.3% | 15.0% | 14.9% | 14.6% |

- **命中时 OPPO 171.3 ms，达标**（目标 ≤ 250 ms），比 3b 的 483.7 ms 少 **312 ms**。
- **命中时三星 304.6 ms**，比 3b 的约 871 ms 少 **567 ms**；没进 250 ms，剩下的全部是
  「窗口起来 + 首次布局稳定 + 抓图」这一段（118 → 243 ms，占 80%），与粒子无关。
- 命中路径省掉两块：建材（OPPO 33.5 / 三星 68.4 ms，命中时根本不建材）与 GPU 预计算
  （OPPO 250.3 / 三星 454.8 ms）。剩下的只有「上传真实贴图」13.3 / 19.2 ms。
- 未命中那一次与 3b 持平（485.4 对 483.7；三星 897.7 对约 871，其 `onCreate` 本身晚了 6 ms，
  加上面板侧的呈现延迟）——**提前预算没有拖慢未命中的路径**。

观察器每次都记 `prewarm`（只记在创建页那一行）。本批实测到的三种：

| --- | --- | --- |

## 4. 三星涟漪：根因是刷新率被压，不是哪一段画得慢

用掉了任务书批准的那**一次** atrace 采集（只三星、只涟漪场景、一次）：
`atrace --async_start -b 40000 gfx view sched freq binder_driver` + `dumpsys gfxinfo framestats`，
产物 52 MB，落在
`E:\projects\EverythingDone\tmp\particle-perf\batch4\R5CW20BLNKL\trace\ripple-trace.txt`。

采集轮里那批长帧的解剖（DetailActivity 窗口，工具栏图标 → 弹窗）：

| t（自按下） | TOTAL | MEASURE | DRAW | SYNC | **ISSUE** | SWAP | **GPU** | **DEADLINE** |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| +296.9 | 35.55 | 0.20 | **0.28** | 0.10 | 12.11 | 1.32 | 15.67 | **33.3** |
| +313.6 | 40.11 | 0.19 | **0.47** | 0.13 | 16.79 | 1.10 | 18.44 | **50.0** |
| +330.3 | 35.98 | 0.24 | **0.33** | 0.11 | 13.47 | 3.89 | 16.08 | **50.0** |
| +346.9 | 36.16 | 0.16 | **0.31** | 0.19 | 12.83 | 1.11 | 15.81 | **50.0** |
| +363.6 | 35.99 | 0.26 | **0.24** | 0.12 | 15.17 | 1.10 | 15.69 | **50.0** |

trace 里同一批 `DrawFrames` 切片的内部构成（应用进程的 RenderThread）：

```
t=+275.3ms DrawFrames  dur=22.86ms     dequeueBuffer 20.04ms  Drawing 748,140→928,320  2.44ms
t=+311.9ms DrawFrames  dur=18.19ms     dequeueBuffer 15.70ms  Drawing 同上             1.97ms
t=+330.2ms DrawFrames  dur=17.65ms     dequeueBuffer 12.30ms  Drawing 同上             4.88ms
t=+362.2ms DrawFrames  dur=16.55ms     dequeueBuffer 13.96ms  Drawing 同上             2.07ms
```

三条事实合起来只有一个解释：

1. **画得极快**：`DRAW` 0.24–0.47 ms；trace 里的绘制区域是 `748,140 → 928,320`，即 **180×180 px**，
   占 1440×3088 窗口的 **0.73%**——HWUI 的脏区本来就很窄，「失效区域太大」这条假设被直接否掉；
2. **时间全花在 `dequeueBuffer` 12–20 ms**：生产者在等一块空缓冲，也就是在等消费端的节拍；
3. **`DEADLINE` 从 16.7 一路涨到 50.0 ms**：这些帧**根本没有超时**（TOTAL 36 < DEADLINE 50），
   是窗口的刷新率被系统压到了约 20 Hz。

Android 15 起的可变刷新率按**脏区面积**投票，小面积更新会被降档。自绘涟漪正好是「一小块区域
连续重画」，于是整窗被压下去，同一段动画能画出来的帧数少了一截——用户看到的就是「涟漪一顿一顿」。

**修正**：`GradientRippleDrawable` 在 `enter()` 时给宿主 View 投
`View.REQUESTED_FRAME_RATE_CATEGORY_HIGH`，淡出播完与 `jumpToCurrentState()` 两条收尾路径撤回
成 `REQUESTED_FRAME_RATE_CATEGORY_DEFAULT`。API 35 以下没有这套机制，也就不存在这个问题。
**外观一个像素不变**，只是同一段动画多出几倍的帧。顺带把每帧无谓的 `paint.shader = …` /
`paint.color = …` 改成「已经是这个值就不写」（改 genID 会打断 Skia 批处理）。

**同一个包上的 A/B（三星，各一次，按下后 600 ms 内 DetailActivity 窗口的帧）**：

| `rippleHighFrameRate` | 帧数 | TOTAL p50 / p95 / max | ISSUE p90 | GPU p90 | DEADLINE p50 / max |
| --- | --- | --- | --- | --- | --- |
| 关 | 33 | 2.4 / 20.5 / 44.1 | 0.68 | 11.90 | 16.1 / 33.3 |
| **开** | **42** | 9.0 / 23.0 / 53.8 | 1.63 | 14.50 | 16.7 / 50.0 |

**要点必须说清楚**：出帧数 33 → 42（**+27%**），这正是「涟漪流不流畅」的直接量；而
**「P95 与最大值下降」这一条没有达成**，也不应该按它验收——采集已经证明那些长帧不是丢帧，
而是低刷新率下被拉长的正常帧。刷新率提上来之后每帧预算变小，同样的绝对耗时在百分位上自然更难看。
本批把两个口径都记下来，由用户看实机定夺；开关随时可关。

**OPPO 不退化**：同场景 600 ms 内 70 帧（第二、三批是 62–68 帧），TOTAL p50 3.8 / p95 11.5 /
max 27.0，ISSUE p90 1.03。

**采集轮的绝对值不能直接当基线**：`gfx view sched freq binder_driver` 五类、8 秒 52 MB 的采集本身
明显加重设备负载，采集轮里 `ISSUE` p90 13.47 ms 这一档在**关掉高帧率票的干净复测里只有 0.68 ms**。
可用的是它的**结构**（DRAW 极小、dequeueBuffer 占满、DEADLINE 50），不是它的毫秒数。

**另一个候选修正没有启用**：`yieldPrecomputeDuringFeedback`（涟漪期把预计算的驱动队列压到一个
压力批次以内）默认关。采集证明长帧不是排在我们的 compute 后面——`GPU` 那一栏在开关两种状态下
都是 12–15 ms，而 `DRAW` 恒定 0.3 ms。开关留着便于以后复现。

## 5. ④ 材料工作线程跟随调用线程优先级

`particle_material.cpp` 的工作线程原来在创建时 `setpriority(PRIO_PROCESS,0,0)` 钉死在默认档，
而调用线程（`ParticleMaterial`）跑在 `THREAD_PRIORITY_DISPLAY`。改成**每段工作开始前把自己的
nice 设成派发这段工作的线程的 nice**：

- 1.7 的「已经有触摸反馈或别的层在播时让出到 DEFAULT」照样成立——那时调用线程就是 nice 0，
  工作线程读到的也是 0，语义一个字没变，本地库里不需要再判一次；
- `getpriority` 的 −1 是合法值，必须先清 `errno` 再按 `errno` 判失败。

优先级不改变任何数值，逐位对照证明不了它生效，所以新增设备端读回对照，在两种调用线程优先级下
各跑一次真正的并行段：

| 设备 | 调用线程 nice | 工作线程 nice | 逐位对照（1 道 vs 6 道） |
| --- | --- | --- | --- |
| OPD2515 | −4 / 0 | **−4 / 0** | 320×480 与 630×1074 两种尺寸 `bitIdentical: true` |
| SM-S9180 | −4 / 0 | **−4 / 0** | 同上 |

**顺带修掉一个真缺陷**：`ParticleMaterialNative.setLanes(0)` 本意是「恢复按核数自动决定」，
但实现写的是 `lanes.coerceIn(1, 16)`，0 被夹成 1——于是 3b 那条「1 道 vs 默认道数」的对照
**比的是两次串行运行**（恒等式），而且跑过 `nativeCheck` 的进程此后一直串行。
产品路径不受影响（正常运行从不调 `setLanes`，`laneLimit` 恒为 0 → 6 道），但那条对照当时是
**空的**。修好并在对照里加了两条 `check`（切到 1 道要真是 1，恢复之后要真 > 1）之后重跑，
才第一次真正比到「1 道 vs 6 道逐位相同」。

**效果**（「管线就绪 → 输入就绪」，全屏快照，单次）：OPPO 43.2 → **33.5 ms**，
三星 72.5 → **68.4 ms**。**三星几乎没有变化**——优先级确实传下去了（−4 → −4），
所以 3b 推测的「工作线程被调度到小核」不成立，三星建材的瓶颈在别处，写进 followups。

## 6. ① 弹窗 / 面板 / 新卡片的出现也跳过尾段空白

机制、门槛（`appearanceAliveRatio` = 10%）与逐位一致性保证与创建页完全相同；分两个开关
（`creationAppearanceSkipEmptyTail` / `dialogAppearanceSkipEmptyTail`）只是为了能单独回退。
会话不再自己与开关相与，只看 `spec.skipEmptyTail`——取值在 `appearContent` 那一层就解析完。

实测起点与首帧存活占比：

## 7. G0：GPU 输出逐位不变，以及命中路径的两条对照

`ParticleTrajectoryCheck` 在既有四条对照之外**新增两条**，专门守住「命中提前预算」这条路：

- **A（相同预测）**：预测快照 == 真实快照时，「先建前景纹理 → 预算 → `replaceForeground` →
  从起点播到 0」必须与正常路径**逐位相同**；
- **B（不同预测）**：故意用一张 R/B 对调的「预测图」建材（面板分类、片数、寿命全都不同），
  预算完再把真实像素换上去，**末帧散列必须等于真实页面那一帧**。

| 设备 | 消散 61 帧 | 出现 37 帧 | 交错 | 截断（2c） | **A 命中逐位** | **B 末帧等于真实页面** |
| --- | --- | --- | --- | --- | --- | --- |
| SM-S9180 ×2 | 0 差异 | 0 差异 | 0 差异 | 0 差异 | **通过** | **通过** |
| OPD2515 ×2（主轮） | 1 份出现 1 帧差异 | 0 差异 | 0 差异 | 1 份 1 帧差异 | **通过** | **通过** |
| OPD2515 ×2（关掉提前预算复测） | 0 差异 | 0 差异 | 0 差异 | 0 差异 | **通过** | **通过** |

**OPPO 主轮那两处单帧差异要说清楚**：两份对照各出现一次，且不是同一处——一份是截断对照的
第 12 帧，另一份是正向第 33 帧，整帧**只有 1 个像素**不同、最大通道差 49/255、平均 1.1e-05，
且 `referenceRepeatEqual: true`（参考路径本身可复现）。同一台设备把提前预算关掉之后两份全部
清零，三星两份本来就全部清零。

判定：**不是本批的逻辑改动**。本批一个着色器字节都没改；Kotlin 侧动到这条路径的三处
（`advance()` 里的让路分支、`stepReverse` 的 trace 包装、`beginReverse` 的 `throttled` 参数）
在开关关闭时都是死代码。最可能的解释是离屏对照的两次运行处在不同的并发 GPU 负载下
（提前预算此时正在常驻上下文里跑），而对照本身对这种差异没有免疫。写进 followups：
下一批用固定种子 + `diagnosticOnly` 在同一负载下复现一次再定性。
