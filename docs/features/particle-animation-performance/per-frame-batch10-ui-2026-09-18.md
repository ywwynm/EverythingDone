## 2 第 1 条：状态栏 + 顶栏铺同一条渐变

### 2.1 根因：`GradientDrawable` 按**各自的 bounds** 铺

`applyThemeColor` 此前是这么写的：

```kotlin
BackgroundUtil.applyBackground(f<View>(R.id.view_status_bar), background)
BackgroundUtil.applyBackground(toolbar, background)
```

`BackgroundUtil.applyBackground` 的渐变分支拿的是 `GradientDrawable`，而它的渐变**按自己 View 的
bounds 从头铺到尾**。于是状态栏那一块跑完一整条、顶栏又从起点重新跑一条：竖直分量越大，
交界处跳得越狠。

### 2.2 做法

布局里套一层容器，两个子 View 自己保持透明：

```xml
<LinearLayout android:id="@+id/ll_particle_tuning_header" orientation="vertical">
    <View android:id="@+id/view_status_bar" … android:background="@android:color/transparent"/>
    <Toolbar android:id="@+id/actionbar" … android:background="@android:color/transparent"/>
</LinearLayout>
```

代码里只给容器上一次色。顶栏投影与内容区的 `layout_below` 一并改挂到容器上——位置一个像素没动。

**只改了这一页。** 设置页、空间照片效果、帮助页等二级页面是同一种写法，但它们的主题色固定是
应用的强调渐变（`LB_RT`，竖直分量很小，实测交界跳 1–2 个灰阶），本轮不横切，已记进 followups。

### 2.3 判据与两台的读数

判据取「**交界线上下相邻两行**的逐像素色差」，并用「**同一块内部**相邻两行的色差」作噪声底——
同一条渐变里相邻行本来就有一档色差，拿它当尺子，结论才与具体颜色无关。取样避开左右各 8%
（圆角与挖孔）与状态栏图标所在的高度。

| 设备 | 主题色 | 竖直跨度 | 交界相邻两行（平均 / 最大） | 噪声底 | 判定 |
| --- | --- | --- | --- | --- | --- |
| 魅族 | **修前** 强调渐变（进页面的默认） | 1.1 | **1.061 / 2.000** | 0.010 | **断开**（是噪声底的 106 倍） |
| 魅族 | **修后** 强调渐变 | 1.1 | **0.018 / 1.000** | 0.014 | 连续 |
| 魅族 | **修前** 记事渐变（换色第 4 次抽到） | 152 | **152.0 / 152.0** | 1.000 | **断开** |
| 魅族 | **修后** 记事渐变（换色第 10 次抽到） | 105 | **0.000 / 0.000** | 0.000 | 连续 |
| 三星 | **修后** 强调渐变 | —— | **0.017 / 1.000** | 0.023 | 连续 |
| 三星 | **修后** 记事渐变（换色第 14 次抽到） | 150 | **0.000 / 0.000** | 1.000 | 连续 |

「竖直跨度」= 顶部这一整块最上一行与最下一行的色差，用来判断这一次随机到的主题色**竖直方向上
到底有没有渐变**：纯色与纯横向渐变都是 0，交界断不断开无从谈起。魅族修前那一次抽到的是一条
`T_B` 的记事渐变，交界线上下两行的原始取值是

```
状态栏下沿 (84, 216, 217)      ← 渐变的末端色
顶栏上沿   (236, 243, 236)     ← 渐变又从起点色开始
```

**修后没有一次断开**：两台各连点 6 / 14 次换色，抽到的纯色全是 0.000，抽到的竖直渐变也是 0.000。

产物：`seam-before-after.png`（四条并排，红线是交界线）、`*-seam-strip.png`（交界上下各 24 px

## 3 第 2 条：滑动条两端的对齐

### 3.1 一条恒等式：「轨道内缩」与「滑块外探」之和 = 滑块半径

`AbsSeekBar.setThumb` 把 `mThumbOffset` 取成滑块宽的一半，滑块**中心**因此正好停在
`paddingLeft`（progress = 0）与 `width − paddingRight`（最大值）上。本页的滑动条走全宽，
所以只要记 `内边距 = 行内边距 + x`：

```
轨道内缩 = x                滑块外探 = 滑块半径 − x
```

两者之和恒等于滑块半径，**只能分配、不能同时归零**。本项目的滑块由
`DisplayUtil.buildSeekBarThumbDrawable` 画，固定 20 dp，半径 **10 dp**：

- `x = 0`（第 9 批的写法，`Widget.Material.SeekBar` 自带 16dp 内边距）：轨道严丝合缝地落在
  标题左缘上，**滑块整整外探 10 dp**——这就是用户第一次提的那条；
- `x = 10 dp`：反过来，滑块两端外缘与文本边缘重合，**轨道内缩 10 dp**；
- 折中：`x = 半径 × SLIDER_EDGE_BALANCE`。

用户补充的意见是「滑块可以稍微超出一点点，好让轨道也更接近对齐——滑块并不总在两端，轨道的
视觉对齐同样重要」。**取中点**（`SLIDER_EDGE_BALANCE = 0.5f`）：滑块只在两端才顶到边，
轨道却一直在，两边各让一半。半径从滑块自己的 `intrinsicWidth` 取，不写死。

**如实记一条**：用户举的例子是「轨道内缩 2–4 dp、滑块外探 2–4 dp」，而这两个数之和恒等于
半径 10 dp，同时落进 2–4 dp 做不到（除非把滑块改小，而那会改掉全应用滑动条的样子）。
按「按滑块半径定」取了中点，两个数都是 5 dp 上下。要改成别的分配，只是 `SLIDER_EDGE_BALANCE`
一个常量。

### 3.2 两台的实测

量法：滑杆推到 **0 / 中间 / 最大值**各截一张。两端量**滑块外缘**（滑块比轨道高，两端的最外侧
墨迹就是它），中间量**轨道两端**（滑块让开了，两端的轨道才露出来）。文本边缘按 uiautomator 的
bounds 取，右端统一换算成开区间口径。

| 设备 | 条件 | 轨道左端 − 标题左缘 | 轨道右端 − 读数右缘 | 滑块左外缘 − 标题左缘 | 滑块右外缘 − 读数右缘 |
| --- | --- | --- | --- | --- | --- |
| 魅族 | **修前**（第 9 批） | 0.00 | 0.00 | **−10.00** | **+10.00** |
| 魅族 | **修后** | **+5.14** | **−5.14** | **−4.86** | **+4.86** |
| 三星 | **修后** | **+5.07** | **−5.07** | **−4.80** | **+4.80** |

正号 = 往页面内侧缩，负号 = 往外探。两台的两根滑杆（粒子大小、流动精细度）**逐项相同**，
且 `内缩 + 外探 = 10.00 dp` 严格成立（魅族 5.14 + 4.86，三星 5.07 + 4.80 = 9.87，差的 0.13 dp
是 `17.5 px` 取整到 18 px 带来的）。

产物：`slider-align.png`（四格：滑块在 0 / 在最大值 / 轨道左端 / 轨道右端，蓝线是文本边缘、
红线是被量的那条边）、`slider-thumb-align.png`（修前修后的滑块两端并排）、
`batch10-slider-final.json`。

## 4 第 3 条：半角括号与右缘对齐

### 4.1 全角括号：4 个语言目录

`particle_tuning_cell_size_value` 在 13 个语言目录里有 13 份，其中 **ja / zh-rCN / zh-rHK /
zh-rTW 四份用的是全角括号**，其余九份本来就是半角。四份一并改成与英文同一种写法：

```
%1$s dp (%2$s px)      →  0.96 dp (3.4 px)
```

单测里除了逐目录比对这一条，还加了一条「设置页的 `particle_tuning*` 文案里不许再出现
`（` / `）`」的判据式断言。

### 4.2 全角括号正是右缘对不齐的根因

全角 `）` 占一个全角宽，而墨迹只在左半边。魅族实测（读数是 `3.2 dp（11.2 px）`）：

| | 修前 | 修后 |
| --- | --- | --- |
| 粒子大小读数 **墨迹**右缘到屏幕右 | **27.43 dp** | **17.71 dp** |

也就是白白空出了 **11.43 dp**——这一列其它行都在 16 dp 上，只有这一行看着往里缩了一大截。

### 4.3 勾选框：补掉方框自带的 2 dp 透明内缩

`BackgroundUtil` 画的勾选框在 24 dp 的占位里向内缩 3 dp（`boxInsetPx`），2 dp 的描边压在内缩
矩形的边线上、内外各占一半，所以**看得见的**外缘落在 `3 − 1 = 2 dp` 处。魅族实测修前
`bounds` 右缘 16.00 dp、**墨迹** 18.00 dp，与同一列的胶囊（16.00）差整整 2 dp。

做法：给勾选框一个 **−2dp** 的外边距，并把这个数写成 `BackgroundUtil.CHECKBOX_VISUAL_INSET_DP`
（连同推导写在常量的文档注释里），单测断言布局里的负外边距与它一致。

**这一处是本批对参照页的一次有意偏离**：「空间照片效果」设置页的勾选框贴的是 `bounds`
右缘（第 9 批据此对齐过），本页改成贴**可见**右缘，因为用户这一条要的是看得见的那条线。
代价是勾选框的 `bounds` 右缘变成 14.0 dp。

### 4.4 两台的四项读数

| 控件 | 魅族 bounds / 墨迹 | 三星 bounds / 墨迹 |
| --- | --- | --- |
| 粒子大小读数 | 16.00 / **17.71** | 16.00 / **16.53** |
| 流动精细度读数 | 16.00 / **16.86** | 16.00 / **16.80** |
| 颜色精度胶囊 | 16.00 / **16.00** | 16.00 / **16.00** |
| 性能自动调节勾选框 | 14.00 / **16.00** | 13.87 / **15.73** |
| （对照）粒子大小标题右缘 | 307.43 / 307.71 | 301.87 / 302.40 |

- **形状那两项（胶囊、勾选框）的可见右缘完全重合**：魅族 16.00 / 16.00（差 0.00 dp），
  三星 16.00 / 15.73（差 0.27 dp，−2dp 在 3.75 密度上取整成 8 px 带来的）。
- **文本那两项**分别比形状再往里 0.86 / 1.71 dp（魅族）与 0.80 / 0.53 dp（三星）。
  这一段是**字形自带的右侧留白**：右对齐的文本按字符的前进宽度排，`)` 的留白比数字多，
  而 CJK 的「默认」几乎没有留白（三星停在默认档，读数结尾是「· 默认」，所以只有 0.53 dp）。
  末尾那一行对照可以印证这个量级：`wrap_content` 的标题 `bounds` 与墨迹差 0.28 / 0.53 dp。
- **四项的墨迹极差**：魅族 **1.71 dp**、三星 **1.07 dp**（修前魅族是 **11.43 dp**）。
  没有达到用户说的 ≤ 1 dp，理由与不继续补偿的取舍写在第 7 节。

产物：`right-edges.png`（逐控件一格，蓝线是 16dp 的网格线、红线是墨迹右缘）、
`right-edges-before-after.png`（魅族修前修后并排）、`batch10-edges-final.json`。

## 8 真机驱动踩到的三条

1. **滑杆的底色不能只取一个点**。原来取「滑杆上沿那一行的中点」，而 `Widget.Material.SeekBar`
   的上下内边距是 **0**，滑块停在正中时那一点正好落在**圆顶**上：底色一旦取到墨迹，整条滑杆
   都会被判成墨迹，两端读数变成滑杆自己的边（实测报成 ±16.00 dp）。改成取整条里**出现次数
   最多**的颜色，并断言它的占比 ≥ 0.5。
2. **「先收齐 bounds 再截一张图」在需要滚动时必然错位**。三星上第一屏放不下全部五个控件，
   驱动滚了一屏再收剩下的，而第一屏那几个的 y 已经变了——拿旧 bounds 去新截图上量，症状是
   「流动精细度读数量不到墨迹」「标题的墨迹右缘跑到探测框边上」。改成**逐屏**测量：每一屏都在
   同一个状态下先 dump、再截图、再 dump 一次核对 bounds 没变，才认这一屏的读数。
3. **PowerShell 写回 `shared_prefs` 会带上 BOM**。`Get-Content -Raw | adb shell 'cat > …'` 写出来的
   文件头是 `ef bb bf`，`od` 一查就看得出来（SharedPreferences 的解析器不认它）。要写原文就走
   驱动脚本里那条 `run-as … sh -c 'cat > 文件'`、用标准输入喂 **UTF-8 原始字节**，写完一律
   `od -An -tx1 -N 8` 核一遍文件头。
