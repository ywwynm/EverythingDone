## 待证伪方向

1. 显示 Surface 与隐藏真实卡片只同步了窗口帧，未把该次 Surface 生产者帧加入同步；若容器显示变化要等下一缓冲，窗口先隐藏就会出现空档。应将下一次 GL 缓冲与窗口更新共同协调，比较是否仍出现空档。
2. 静态 GL 卡片与首个粒子缓冲之间有空帧；检查逐缓冲层清单和生产提交顺序，若中间始终有卡片或粒子即可排除应用端清空。
3. 原卡片透明度／按压恢复在交接之前被修改；核对输入、姿态锁与隐藏时刻，若隐藏仅发生于正式交接，则不以改透明度参数处理。

本轮仍保留 SurfaceView、动态壁纸与共同默认，不采用固定等待、提前隐藏或短暂双画来掩盖空档；目标机无法 ADB，修正后的最终合成需用户同一场景复验。

## 接口核对与不能直接采用的替代

发现上一轮实现存在明确接口约定错误：`ParticleGlCardHandoff.switchSurface()` 和释放路径直接向 `SurfaceView.surfaceControl` 设置 alpha。Android 文档及本地 API 36 SDK 源码说明，`getSurfaceControl()` 返回的对象实际上只读，应用只能用它挂载子 SurfaceControl，不应修改其显示属性；SurfaceView 随时可能覆盖应用请求。因此此前“自有 SurfaceControl alpha 事务”表述不准确，应用拥有 SurfaceView 不等于拥有该框架控制器的属性写入权。需要纠正，不能再以原生 Android 恰好通过证明该用法受支持。依据：[SurfaceView.getSurfaceControl](https://developer.android.com/reference/android/view/SurfaceView#getSurfaceControl())。

但不能仅把这一发现当作卓易通单帧空白的全部根因：此前 debug `202610111028` 使用公开 `SurfaceView.alpha` 与窗口同步，也已由用户录像证实起滑全组空白。因此简单改回该路径，或增加固定延迟，没有足够证据。公开 `SurfaceSyncGroup` 也不提供 `add(SurfaceView, ...)`，本地源码中的这一重载标为隐藏 API，不应通过反射补同步。

静态 GL 进入和恢复图像逐像素相同，粒子图像并非空白；输入到交接的源码检查没有发现早于正式交接的 alpha=0 写入。ZIP 分析阶段没有修改应用或发布；随后收到用户录像，以下为新增证据和实施方向。

## 录像复现与修正方向

- `0ee45e563ff27352cbed070737db1d09.mp4`，2,177,147 字节，SHA-256 `550d0d28da7ff432d7c27535e04d18f74cbcf3d377a4f2a47798a7025e61c5b1`；1136×1920，顺序解码 428 帧。录像与 ZIP 并非可证明的同一次手势，不强行对齐绝对时间。
- 从 0 计帧，f174（2.891767 秒）和 f175（2.907544 秒）卡片区域橙色像素为 0；f176（2.925144 秒）直接恢复为已经开始消散的粒子卡片。前后橙色像素分别约 77,049 和 75,701；空档约 33.38ms，触点和周围控件仍在。最终屏幕空白得到直接复现，不是粒子颜色变化。
- f252（4.185144 秒）恢复真实卡片后，卡面中值 RGB 从 `(206,127,65)` 变为约 `(248,152,78)`，之后持续保持偏亮直到新弹窗变暗。不能称作只有一帧的重叠；正常浓度 0.84 没有持续恢复。
- 当前 `holdCard()` 将祖先浓度乘到原 View，Doing 又将列表设为 1；释放时子 View 恢复 1，而 `clearView()` 的列表 0.84 可能再次被恢复动画的 `onChildDraw(dX=0)` 覆盖为 1。这套透明度转移没有必要，改为原容器管理原 View、GL 最终合成单独使用捕获的祖先浓度。
- 透明窗口候选改用公开 `translationX` 在视口外准备同一 SurfaceView，在同一窗口帧将其复位并隐藏原 View。Android 从 API 24 起明确保证 SurfaceView 位置与其它 View 绘制同步，本地 API 36 源码的 RenderThread 位置事务也会合入对应窗口缓冲。它绕开旧 alpha 切换，保持生产者、缓冲尺寸及壁纸不变；不插入固定等待，不引入 TextureView。依据：[SurfaceView 位置同步约定](https://developer.android.com/reference/android/view/SurfaceView)。
- 收尾将 GL 卡片和前景整组撤除后才归还显示控制，避免复用旧路径中前景先于卡片关闭的错误。正常不透明首页与 Dialog 不进入这个透明窗口分支。
- 预计三台授权 Android 设备各做一轮合并回归，包含 Doing 的取消／完成与两种样式，以及首页和连续弹窗的邻接回归。没有 JVM 测试能够重现卓易通最终合成器；录像逐帧与应用内诊断构成验证入口，不把状态机通过当作目标机显示通过。修复后仍需用户在卓易通复验。

### 本轮验证过程中的补测原因

- 三星旧包取消基线复现恢复后卡面中值 RGB 由 `(214,170,113)` 变成 `(237,187,115)`；新候选恢复为 `(214,171,112)`。三机新候选退出后的真实列表 alpha 均为 0.84、卡片 alpha 为 1、位移为 0。
- 首轮脚本传入了大写 `FLOW`，但 `ParticleStyle.of()` 只识别小写 key，实际仍运行 DRIFT。发现后不将这六个样本计作流体通过；脚本统一转小写并断言回执实际样式，三机仅补流体取消与右滑完成各一次，同时验证导出 ZIP。此为验证脚本纠错，不改产品样式解析。

## 实施和验证结果

- `ParticleGlCardHandoff` 的共同透明窗口分支改为公开位置同步：真实卡片保持可见，在视口外提交完整 GL 静态帧，再按窗口帧复位 SurfaceView 并隐藏真实卡片。整个过程 SurfaceView alpha 恒为 1；不改变 EGL 生产者、缓冲尺寸、壁纸或粒子模型。仍保留先前旧方案供 debug 对照。
- 卡片与前景改为完整 GL 组，原 View 属性恢复后保持 GL 完整组，待窗口切换后一起撤除；清空提交完成才恢复空闲位置，不能先关闭 GL 前景再留一帧卡片。
- `ParticleSwipeAnimator` 不再将祖先 alpha 乘到原 View；`DoingActivity` 不再将列表临时改成 1，恢复帧的滑动回退也以 0.84 为基准。诊断增加位置切换、原 View／容器 alpha，以及虚构 Doing 结束后的真实属性采样。
- 三台各 6 个有效场景，共 18 个：DRIFT Doing 取消／快速完成、FLOW Doing 取消／右滑完成、360dp 高卡片与前景／动态背景、连续弹窗。所有场景实际后端为 SurfaceView，无失败／超时；完成回调恰好一次且呈现进度达到 1。连续弹窗同时包含 2 个会话，6 份导出 ZIP 的 CRC 正常。
- 三星和魅族逐帧录像中的 Doing 起滑未发现整卡空档；两种样式取消后的卡面中值各通道差值均在 1 以内。三星旧包同手势恢复后的红／绿差值为 23／17，检测能够识别该回归。OPPO 仅核对起止截图、实际提交和恢复属性，不计作逐帧通过。截图色值判断也不替代人工观察透明壁纸中的文字连续性。
- 15 项相关 JVM 测试通过，涵盖 GL 静态层替代、迟到交接回调、一次性完成和滑动方向；没有新增无法模拟最终合成器的浅层“空白修复”测试。原始视频、测试驱动与日志位于 `tmp/particle-doing-flash-20261012/`；脱敏汇总见 [回归证据](diagnostics/doing-start-flash-2026-10-12/regression.json)。
- 三台恢复测试前 APK 并核验 SHA-256；三星 371、魅族 180、OPPO 72 条用户记事及其它数据库表与本轮基线一致，排除既有启动流程的 `Thing.HEADER`。未创建 Git 提交。

### 继续核对后的接口边界

- `ParticleGlCardHandoff` 先用 `changeGlLayersCommitted` 提交静态 GL 缓冲，再用 `ParticleWindowFrameSwitch.run` 提交窗口内容与 SurfaceView 位置；这是两步，不是将原 View 缓冲与 GL 缓冲合成成一张图像。已有 API 成功回调不能推翻目标机可见的空档／重复帧。
- 对照 API 36 源码和 [SurfaceSyncGroup 公开接口](https://developer.android.com/reference/android/window/SurfaceSyncGroup)，接收 `SurfaceView` 并同步其下一缓冲的重载仍为隐藏 API；公开重载只接收窗口根或 `SurfacePackage`。不能通过反射把隐藏重载作为正式修复。
- [SurfaceView.applyTransactionToFrame](https://developer.android.com/reference/android/view/SurfaceView#applyTransactionToFrame(android.view.SurfaceControl.Transaction)) 能将自有 SurfaceControl 事务绑定到下一张 Surface 缓冲，但不接收普通 View 的绘制缓冲。因自有层在目标机不可见，既有卡片桥接不能直接恢复使用。
- `SurfaceHolder.Callback2` 也不等价于捕获任意一次生产者缓冲：本地 `SurfaceView.updateSurface()` 仅在窗口管理器请求同步且发生对应 relayout／redraw 时走 `handleSyncBufferCallback`。修改尺寸、格式或层级强行触发属于另一种未经验证的行为变更，不作为“已经找到可靠同步”的证据。
- 不能将不透明首页的完整 GL 底图直接用于 Doing：该窗口透明并展示系统壁纸，窗口内截图不包含系统壁纸；半透明底图再次叠加会重复变暗。把壁纸改成静态图、固定黑色或把 0.84 改成 1 都不满足用户原有约束。
- 接口核对阶段没有修改应用代码、安装设备或发布包。尚未找到经过目标机验证、同时保留该透明窗口 SurfaceView 与原有画面的新交接方案；这不是证明所有 SurfaceView 方案不可能，只是明确当前可验证方案的边界。

### 后续隔离实验：Doing 自首次显示起由同一 GL 输出

- 公共同步接口复核后继续构建最小对照：只在 debug 的虚构 Doing 入口启用整页 GL 绘制，普通业务页、原 Doing 测试入口和其它动画路径不切换。仍使用共享 SurfaceView／既有粒子线程，不改为 TextureView，不按品牌选择实现。
- 原页面树继续处理布局、输入与控件动画；调试专用容器只在原窗口绘制时跳过 draw，捕获时绘制实际子树，不改变 alpha 或 transitionAlpha。系统壁纸仍在系统窗口实时显示，页面的 0.4 暗层和 0.84 卡片只合成一次。
- 双纹理保留已显示整页；新整页捕获／上传完成后，在一个 GL 任务中同时替换页面内容、静态卡片与粒子。快速取消发生于捕获期间时，也保留与已隐藏原卡片配套的 GL 静态卡片，直到包含恢复卡片的新整页一起替换。
- 此实验改变了该测试页的持续绘制方式，尚不能视为局部修复完成。必须测量首次页面显示、原控件动态更新、起滑／返回、两种样式、快速松手以及长帧／交互延迟；不能仅因没有跨 Surface 切换就宣称画面等价。

### 隔离实验的首轮反馈

- 首版用根 transitionAlpha=0 隐藏绘制，三星 UIAutomator 实测整页可访问性子树也被过滤，已撤掉此做法。改为 debug 专用 FrameLayout 的绘制门控后，控件树可以正常定位、真实输入可驱动原滑动流程。
