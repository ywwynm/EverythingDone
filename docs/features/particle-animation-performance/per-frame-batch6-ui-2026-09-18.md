## 2 新增了哪两项设置，其余候选为什么不做

### 颜色精度（`color_precision_standard`，默认「高精度」）

直接映射第二阶段的 **U7**（累积目标 `RGBA16F` ↔ `SRGB8_ALPHA8`）。选它是因为两个条件都满足：

- **有可测的性能影响**：第二阶段在华为上离屏成对 A/B 给到 消散 **0.848** / 出现 **0.729**，
  默认档位每帧 43.04 → 40.53 ms；
- **用户能理解**：就是「颜色过渡细不细腻」与「每帧贵不贵」的取舍，而且第二阶段的
  alpha 直方图证明 8 位的 64 档全部用到、并排放大图上看不出条带，不是一个会把画面弄坏的选项。

界面文案：「高精度用 16 位浮点累积颜色，过渡更细腻；标准用 8 位，每帧的开销更低。」

### 性能自动调节（`auto_performance_tuning`，默认关）

就是第二阶段的 **U9**（[ParticleAutoDowngrade]）。规则没有变，只把 0–100 的流动精细度
「降一档」定义成 −20（沿用上一版梯度相邻两档之差，第四批实测的「各调一档」就是这个幅度）。

文案与用户口述的一处差异：用户给的是「连续掉帧时自动**降低**粒子大小与流动精细度」，
但这条规则实际上是把粒子**调大**（粒子少了才省），「降低粒子大小」会被读成反的。
落地文案改成「连续掉帧时自动**调整**粒子大小与流动精细度以减轻负担并提示，可随时改回。」

### 判过但不做的候选

| 候选 | 有没有可测的性能影响 | 用户能不能理解 | 结论 |
| --- | --- | --- | --- |
| 出现动画**跳过尾段空白**（2c，两个开关） | 有：首帧提前 60–100 ms，预计算按比例缩短 | 能，但**只有一个方向是好的** | **不做**。关掉它只会让动画起步更晚、预计算更久，没有「取舍」可言，给用户一个只能选差的开关是噪声 |
| **U8** splat 双线性 → 最近格 | 只有 2%，而画面变化是 U7 的三十倍（50% 处 p99 差 240） | 能理解「更粗糙」 | **不做**。收益与代价不成比例，第二阶段已判「不建议」 |
| **U10** `sample_field` 改硬件三线性 | **更慢**（41.78 vs 40.95 ms），且破坏跨设备一致性 | —— | **不做** |
| 涟漪期投高帧率票、预读异步化、双上下文、节拍相位锁定等 | 有，但都是纯收益 | 不能：全是实现细节 | **不做**，保持默认开 |
| 创建页的**提前预算**（空闲时为下一次新建备料） | 有：点新建到首帧 484 → 171 ms | 勉强能（「用一点空闲换更快的新建」） | **本轮不做**。它的代价是空闲时的一点 GPU 与磁盘缓存，不是画面取舍；要做也该和别的「后台预备」类设置放一起，不属于粒子动画设置页 |

## 3 流动精细度：0–100，以及两次键名迁移

- 取值就是压力投影的迭代数，**0 表示整段压力更新都不跑**——`skipPressure` 直接早退，
  修正场保持 `PeelPressure` 构造时 `resolveField()` 清出的零场。做成「整段不跑」而不是
  「迭代 0 次」，是因为后者仍会 splat、模糊、收集 tile，还会在压力缓冲里留下没被求解过的散度。
- 键名从 `jacobi_iterations_index`（存下标）换成 `flow_detail`（存取值）。**迁移按取值搬**：
  旧的第 k 档搬成 `LEGACY_FLOW_LEVELS[k]`；最高一档（100）本来就是默认值，等价于「未设置」，
  所以只删旧键、不写新值。
- 真机核对：测试前设备上是 `jacobi_iterations_index=0`（= 20 次），装上本版启动一次之后
  读回来正是 `flow_detail=20`，粒子大小那一项一个字没动。

## 4 滑到底松手之后怎么倒放回来

### 为什么不能沿用「判完成 + 自己倒放」

按 `ItemTouchHelper` 的阈值判完成之后，那张 itemView 就归它的**待清理队列**管：每一帧都被按到
`translationX = −列表宽度`，要等 `clearView` 到来才松手，而 `clearView` 又要靠
`notifyItemChanged` 换上一张新 View 才会触发（见 `memory/recyclerview-swipe-return-view-identity`）。
上一版「啪地弹回来」正是这条链路的默认换位动画。

### 做法

让这一页的滑动**永远判不成完成**：`getSwipeThreshold` 与 `getSwipeEscapeVelocity` 都返回
`Float.MAX_VALUE`。松手之后 `ItemTouchHelper` 一律播 `ANIMATION_TYPE_SWIPE_CANCEL` 那条回位动画，
它每一帧回调 `onChildDraw` 且位移单调回零——`ParticleSwipeAnimator.draw` 据此把手势相位
从末端一路喂回 0，**粒子沿原轨迹聚回卡片**（历史采样只增不减，倒放画的就是正向画过的那几档）。
动画结束时 `clearView` 到来，会话在那一刻把像素交回真实卡片，卡片全程停在原位。

三处配套：

- **时长**按滑走的比例缩放，整张卡走完取 420 ms（与 `ParticleSwipeAnimator` 里
  「松手之后把剩下那一段播完」同一个速率），下限 96 ms；
- **倒放期间禁用滑动**：页面自己的 `OnItemTouchListener` 直接吞掉整个手势，而且**必须先于
  `ItemTouchHelper` 注册**——它的 `onInterceptTouchEvent` 在 `ACTION_DOWN` 会接管正在跑的
  回位动画（`endRecoverAnimation(…, true)` 之后 `clearView` 不再到来），只靠
  `getSwipeDirs` 返回 0 挡不住；
- **看门狗**：解锁本来由 `clearView` 负责，万一它没到卡片就再也滑不动了，因此另留一条按
  设备动画缩放算出来的超时解锁。

### 代价（如实记）

半程松手不再自动播完，而是从松手那一刻的相位往回倒放。也就是说这一页从「滑过一半就完成」
变成了「滑到哪儿就是哪儿，松手原路退回」。**首页真实列表的完成语义一个字没改**，
`ParticleSwipeAnimator.finishSwipe` 仍然只由首页调用。

### 真机证据

录屏（`screenrecord`，变帧率，逐帧读 `best_effort_timestamp_time`）取松手前后 ±1.2 s 的帧：
