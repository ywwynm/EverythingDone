# 实现决策

## 2026-10-14：Doing 卡片使用真实节拍推进惯性与边缘重绘

- 所有卡型共用 `DoingRecyclerView`。普通帧保留 UI 动画阶段执行原 ViewFlinger；检测到动画时间超前实际时间超过 1ms 时，将同一次回调交给异步 UI 队列，等当前阶段解除时间锁定后执行。不修改滚动／回弹物理参数，不按品牌切换。
- 仅当 EdgeEffect 仍活动且整页捕获遇到未来动画时间时，等当前动画阶段结束再记录；正常惯性不额外推迟。继承系统 EdgeEffect，只在未来动画时间下暂不推进 draw，实际时间仍执行系统原算法。原窗口可能提前缓存子 View，因此延后记录前使滚动容器失效，保证真正重新绘制；保留原布局、属性更新、缓冲租约与 GL 合成。
- 到边界后 RecyclerView 已经 IDLE，但 EdgeEffect 仍可能活动。首次 absorb 的 draw 不一定返回继续失效，因此同时在绘制后检查真实效果的 isFinished 和既有失效请求，按真实 vsync 接续一帧；尺寸／层级未布局时仍先走布局。效果结束且没有新请求即停止，后台和退出取消，不设置固定续帧时长。
- 不能反复跳过超前帧等待“正常帧”：魅族会持续进入预测阶段，实验已证明这会停住惯性。独立节拍仅用于 EdgeEffect 已请求的续帧；把所有惯性或所有捕获移到其它阶段会损失持续 fling 帧率，相关候选均弃用。
- 验证区分页面 preDraw、实际 RecyclerView.draw、离屏记录和驱动呈现。最终同口径比较边界后的相邻捕获间隔，同时确认内容进度；不再只用平均 FPS 或顶部附近往返判断底部手感。详见[完整取证](doing-edge-scroll-2026-10-14.md)。
- Doing 的 Surface 启动等待从首次实际请求 Surface 的遍历开始计时，仍保持 2 秒期限；不把复杂内容初始化和首次布局的耗时算作 Surface 已经等待的时间，避免魅族长清单首开被提前判失败。

## 2026-10-14：持续页面直接交接硬件缓冲，独立处理渲染时间与动画时间

- Doing 的离屏提交显式使用实际 CLOCK_MONOTONIC 时间，不继承厂商可能预测到未来的 AnimationUtils 时间。只改变渲染调度，计时、清单、GIF 与粒子的原有动画器不变。
- 页面 HardwareBuffer 直接导入现有 EGLImage 缓存；保留生产者 fence、消费者读取栅栏、图像租约、退出和尺寸变化保护，以及不支持导入时的原回退。
- 已完成图像／上传的主线程回调使用异步 Handler，避免被原窗口的同步屏障额外延迟一拍；输入反馈初始化仍等原窗口遍历。此次不提高固定 120Hz 请求，也不按品牌切换绘制方案。
- 依据：[三机 fling 诊断与修复](doing-fling-fix-2026-10-14.md)。详细取证和低开销 FPS 分开；增加实际内容位移核验，避免把计时文字出帧当成卡片滚动更新。

## 2026-10-14：惯性滚动单独验收，完整时段计帧

- 按用户补充要求分离 `DRAGGING` 和 `SETTLING`，用设备端 ACTION_UP 与实际滚动位移验证 fling；短卡片到边缘过快时，增加已有虚构长卡片，不改真实内容来凑样本。
- 最终平均帧率用完整活动时段中的唯一驱动呈现帧计数，保留首尾无新帧的时间；相邻帧间隔换算值作为另一个明确字段，不能在存在长停顿时混用。
- 指定真实记事与虚构压力样本分开，PMA110 手机与已连接 OPPO 平板分开。当前只形成性能诊断，不据未验证的推断修改整页 GL 或粒子效果。

## 2026-10-14：消除已遍历更新的额外等待，复用首用准备结果

- 整页 GL 继续作为 Doing 的正式兼容方案。上一张捕获完成后，仅立即消费已经过 preDraw 的普通更新；原生波纹续帧／收尾仍要求真实窗口遍历，GPU 图像释放门槛不变。
- 既有后台流体预热使用共享 EGL 上下文，完成 GPU 工作后仅移交程序；会话、纹理和 FBO 仍独立。正式线程若已编译同配方程序则保留现场对象，删除预热副本，避免并发修改正在使用的 uniform。
- 材料边界和手势历史在已有材料线程计算。像素分类、材料边界与历史范围复用现有 JNI 库，保留相同采样、整数统计与浮点顺序；Kotlin 路径继续作为回退和独立对照，不改变粒子数量、公式、着色器、计时动画或 GIF 策略。
- 采用三机逐位／逐像素对照与真实队列帧率验收，完整矩阵不同时录屏。详见 [验证与边界](doing-scroll-flow-optimization-2026-10-14.md)。

## 2026-10-12：只为反馈输入调整整页提交，复用真实卡片姿态

- Doing 原生反馈刚被触摸／按键改变时，离屏提交放到当前原窗口遍历后；普通动态帧保留原节拍。弃用所有帧持续后移的候选，实测它导致魅族流体回退。末帧由真实续帧触发有界窗口提交后的清理，退出后不恢复生产。
- 设置页模拟卡片复用 `InterceptTouchCardView`，与真实记事卡片使用相同粒子姿态锁，不按阶段手工改阴影浓度。
- 零旋转不再等待无用的本地后端判断；Dialog 外阴影与内容并行捕获。布局与捕获各有界，独立 Surface 使用原有完整 900 ms 捕获期限，成功即继续；慢准备的总容忍时间因此比原单一 1100 ms 期限长，不增加固定等待。
- 继续保留 SurfaceView、动态背景、重叠转场和原粒子模型，三机验证不等于卓易通最终屏幕验收。性能抽样保留小幅差异，不承诺逐帧严格相同。详见 [实施与对照](ripple-recording-preview-2026-10-12.md)。

## 2026-10-12：分开处理粒子材料与真实触摸反馈

- Doing 原生续帧按需请求受控刷新并使相关按钮失效，保留繁忙时的末帧请求；保留有界缓冲和退出保护，不把任意续帧当成卡片交接完成。
- 保留 SurfaceView、重叠弹窗和粒子参数，不引入独立兼容模式。通用原生静态材料过滤及既有 Doing 原生波纹首帧偏深另列后续，见 [实施记录](ripple-capture-implementation-2026-10-12.md)。

## 2026-10-12：整页性能回退消除后正式接入

- 覆盖下面“本轮不推广”的阶段结论。三星 FLOW 连续三次均值 98.6→107.2 FPS；魅族 DRIFT 117.8→118.9 FPS，原有约 7～9 FPS 回退已消除。使用同包、固定种子、同一长卡片与手势，测量不录屏，保留所有逐次样本及异常复测，详见 [优化记录](doing-scene-performance-2026-10-12.md)。
- API 34 及以上，Doing 选择粒子动画时默认使用动态整页 SurfaceView；长短卡片共用同一路径，不按品牌分流。低版本保留既有能力回退，未选择粒子不增加整页捕获。debug 原实现对照与诊断导出继续保留。

- 三台原 APK 恢复并校验 SHA-256；371／180／72 条记事及其余数据表未变（排除已有 HEADER 初始化）。本轮不创建 Git 提交。

## 2026-10-12：整页实验的退出按窗口生命周期收尾

- 已取得卓易通滑动首尾与动态色条的正面反馈，继续保留 SurfaceView。退出故障在原生 Android 也可复现，因此修正共用的 debug 实验实现，不增加按品牌选择的分支。
- ImageReader 消费者最多持有一张跨线程 Image，GPU 归还缓冲且页面交换结束后才开始下一轮；Ripple 额外产生的帧在消费线程及时归还，不能等主线程才能排空队列。合并图像通知产生的 null 不作失败。
- Activity 确定退出后停止新的整页捕获，屏幕中已有整页交给原窗口转场退出；onDestroy 不再提前提交透明整页，纹理随 decor 分离释放。保留系统转场，不通过关闭窗口动画或固定等待掩盖问题。滑动过程中仍持续捕获动态内容，区别于退出时停止已结束页面的生产者。
- 调试结果汇总和历史 JSON 解析移到报告工作线程，返回主页不等待汇总。加入退出、生产者停止、窗口分离、资源释放、主页焦点／首个触摸／滚动记录，维持无 ADB 导出。
- 真实业务页面本轮未接入整页实验。魅族捕获／材料准备的性能问题仍待处理；本轮聚焦退出，不声称整个方案已达到全局等价。见 [诊断与回归](doing-scene-exit-2026-10-12.md)。

- 原页面门控同时覆盖 draw／dispatchDraw，并保持控件 alpha、可访问性和输入树正常。不能使用根透明度隐藏整个控件树，也不能只拦截会被容器快速路径绕过的 draw。

## 2026-10-12：根据 Doing 空白录像撤回框架 SurfaceControl alpha 修改

- 用户录像复现起滑约 33ms 空白及取消后持续提亮。直接修改 `SurfaceView.surfaceControl` alpha 违反该对象的只读约定，撤回上一条决策中的这项实现；不能再称它为应用自有控制器。
- 透明窗口使用公开 SurfaceView 位置属性，在视口外准备后按宿主绘制帧恢复位置。保留 SurfaceView、原缓冲尺寸与动态壁纸；首页不透明底图和 Dialog 路径保持原交接方式。位置同步在原生 Android 有文档约定，卓易通仍需最终画面复验。
- 原 View 的祖先透明度继续由原容器合成，只给窗口外 GL 输出补祖先浓度，不再在子 View 与容器之间临时转移。卡片及前景作为同一 GL 组退出。
- 本轮补一个三星旧包 Doing 取消基线，用于确认亮度回归检测能够失败；随后三台各一轮合并验证，不重复此前全量场景矩阵。证据与边界见 [起滑空白记录](doing-start-flash-2026-10-12.md)。

## 2026-10-12：透明窗口、外部阴影和连续会话按实际职责交接

- 保留共同 SurfaceView 实现，以窗口背景是否不透明选择交接方式，不识别品牌。Doing 透明壁纸窗口不复制整页背景，使用应用自有 SurfaceControl alpha 事务与真实 View 同帧交接；这补充此前“SurfaceView alpha 保持稳定”的描述，View.alpha 本身仍不作为统一路径的交接开关。

- Dialog 根投影独立捕获和渐变，跨窗口同步原生／承接阴影，不扩大粒子材料或改首页卡片的阴影规则。

## 2026-10-11：按用户要求采用统一 SurfaceView 方案

- 共同实现接入普通首页、Doing 页面与 Dialog，不识别设备品牌、不新增用户兼容模式；旧路径仅保留 debug 应用内进程对照。以下“仅诊断、不推广”是先前轮次状态，本决策取代其接入限制。
- 首尾完整 GL 画面协调真实 View 的隐藏／恢复，播放时撤去底图，由原窗口保持动态背景；返回必须重新捕获当下背景。粒子 SurfaceView alpha 保持稳定。
- 普通子树沿用硬件绘制，独立 Surface 取生产者像素并保留祖先变换、裁剪、阴影；FableSol 在自身 GL 提交前绑定恢复事务。普通 Dialog 继续支持重叠，不串行化“添加附件 → 录音”。

## 2026-10-07：纠正大小统一后的尺寸含义

## 2026-09-17 逐帧成本专项 第三批：节拍要锚在真实 vsync 上，不能自由计时

见 [per-frame-batch3-2026-09-17.md](per-frame-batch3-2026-09-17.md)。

**根因：自由计时的节拍相对面板持续漂移。** 此前的节拍目标是「起点 + k × 16 666 666 ns」。
魅族 20 Infinity 触摸期两个 vsync 实测是 **16.55 ms**（面板 120.8 Hz，一个 vsync 8.276 ms），
**我们每拍多 0.117 ms**。逐帧看得很干净：「真实呈现时刻 − 本拍目标」每帧递减 0.11 ms，
减到跨过一个显示周期就跳一档，呈现间隔于是在 8.3 / 16.6 / 24.8 / 33.1 ms 之间来回。
三星是最好的旁证——它的面板周期是 16.602/16.667 ms，与写死的值几乎相等，**于是几乎不漂**，
同一份代码在它上面慢拖 88.5% 的间隔是一拍，而魅族只有 72.9%。**均值看着接近 60，
看起来却一直在抖。**

**修法：目标就是本次 vsync 的时刻，出不出拍按「距上一拍够不够久」判。** 门限取
`16.667 ms − 半个 vsync − 0.5 ms`，语义是「离 60 Hz 最近、且不低于它的那一档」
（120 Hz 出 60、144 Hz 出 72、90 Hz 出 90）。**不按 vsync 计数分频**：这条线程收到的 vsync
本身就不规律（同一次左滑里 8.28 与 16.55 交替，直方图 101 : 83），按计数分频会跟着乱——
第一版正是这么写的，实测把左滑「被卡住的帧」占比从 3.9% 推到 12.7%（预算截止时间跟着
推算出来的周期在 10 ms 与 2 ms 之间摆，预读被饿死）。**凡是从一个不稳定的观测量推算出
控制参数的地方，都要先问它稳不稳。**

**目标不取系统给的「预期呈现时刻」。** 魅族上 `FrameData.preferredFrameTimeline` 给的是
vsync + **26.0 ms**（入队截止 vsync + 13.7 ms），而我们实际达到的是 vsync + 17.7 ms——
按它写目标等于主动多等一个显示周期。它只适合当「平台认为你该瞄哪」，不适合当我们的目标。

**`eglPresentationTimeANDROID` 在魅族上不能用来推迟自己的帧。** 试过把它写成「本拍 vsync +
一个输出周期 − 4 ms」当下限，想挡住「早到一个显示周期」的那一档：下限写在 vsync + 12.6 ms，
实测仍有 **28/69 帧**在 vsync + 8.3 ms 就上屏了。这台的 SurfaceFlinger 不按 `desiredPresentTime`
推迟我们的缓冲，整项撤掉。

**`awaitFence` 不是瓶颈，「在途只留一帧把提交串成一条链」这条假设被证伪。** 实测等待
**0.02 ms**（两台、三个左滑场景的 p50/p90/max 全在 0.07 以内）。同批做出来的「栅栏挪到
两拍之间轮询」因此整段删除。

**「左滑远低于 60 fps」这个前提要修正。** ① 三格的「呈现/应有」把手指停住的那一段也算进了
分母（快拖甩动只有 180 ms、实测就出 11 帧，**那一段是满帧的**，整格 0.31–0.45 差的全是
后面 600 ms 的停住）；② 出拍没画的那些拍**100% 是「相位没变」**，没有一次卡在阶段、可见性
或渲染器上，而相位不变的直接原因是输入事件只有 54–61 Hz、与我们 60 Hz 的节拍相位交错；
③ 真正剩下的缺陷是**节奏不齐**，不是帧率低。

**左滑必须在一组不同复杂度的卡上测。** 用户 2026-09-17 指出此前只用一行字的矮卡。实测
矮卡与清单卡的片数差 **6.8 倍**（魅族 24 840 vs 169 050），清单卡的片数已经超过整屏弹窗。
本批起 SHORT / TALL / LIST / IMAGE 四种各跑一遍，指标按卡型分行。

**E12 在弹窗上的现状是 0.88 dp，不是方案里写的 2.2 dp。** 弹窗这块面积上 `max_cells`
那条上限没有生效，起作用的是 `rules.properties` 的下限 `cell=1.65`（归一空间，1 dp = 1.875 单位）。
所以 E12 取 2.2 dp 是 **6.2 倍**减量而不是「减半」：片数 106 784 → 17 190。

**E12 的收益在弱设备上才是大头。** 片数降 84% 时，魅族的「现场每帧」只省 9%
（10.40 → 9.50 ms，它被与片数无关的整屏清空 + resolve + 压力网格主导），而华为省 **71%**
（23.77 → 6.82 ms）。建材两台都直接减半到四分之一。

**华为 Android 12 上左滑走的是 TextureView 不是共享 SurfaceView**（`synchronizedCard`
要 API 34+），因此那几格拿不到 `EGL_DISPLAY_PRESENT_TIME`，呈现时刻退回宿主窗口的
frame-commit 回调，数字要按这个口径读。

**Maleoon 910 上前两批的两条前提都成立**：`ssbo顶点=0`（Mali 系顶点阶段无 SSBO，A1 绕开的
做法是对的）、`ssbo计算=8` ≥ C10 需要的 5 个（走活动区域，没有退回整网格）；
`EGL_IMG_context_priority` 读回 **HIGH / LOW**，切换 15 µs/次。


## 2026-09-16 有可见 Surface 的弹窗，离屏那一步必须用软件绘制

「窗口 PixelCopy 失败就退到离屏重录 + 逐个 Surface 合成」修好了「不播」，却带出一个两帧的
闪烁：关闭录音弹窗时，海浪那一层被裁成 974×1357（弹窗本身 1086×1470），内容位置一个像素
没动、只是可见区域被裁小，四角因此是直的，整屏亮度掉约 10 个灰阶。

**根因是用第二个 `HardwareRenderer` 去画活着的视图树。** Android 15 起 `SurfaceView` 的
位置与 crop 由 RenderThread 驱动（`Flags.clipSurfaceviews`，`replacePositionUpdateListener`
逐帧上报「这一帧把它的 RenderNode 画到了哪里」）。离屏渲染器把同一个 RenderNode 再画一遍，
上报的就是离屏那一帧的边界，被应用到**真实的** SurfaceControl 上；真实窗口下一帧上报正确
边界后又自己恢复，所以只闪两帧。

排除过程写在这里，因为每一步都花了一轮真机：

1. 差异严格落在弹窗的 bounding box 内、窗外页面逐像素相同 ⇒ **不是暗层交接乱序**；
   录音按钮（画在窗口缓冲里）仍在原位 ⇒ **被裁的只有 Surface 那一层**。
2. 把窗口 `PixelCopy` 的重试预算从 700 ms 收到 48 ms，闪烁照旧 ⇒ **不是重试次数**。
3. 改成两条路都先走离屏之后，**返回键那一格也开始闪** ⇒ 触发者是离屏抓图本身，
   不是失败的窗口捕获。
4. 落盘的合成图四角 alpha 为 0（圆角完好）⇒ **不是合成图本身是直角的**。

**修法**：`captureSnapshotAsync` 在「弹窗里有可见 `SurfaceView`」时改走 `captureViaSoftwareDraw`。
软件 `Canvas` 不经过 RenderNode，也就没有那条上报。代价是子 View 的 `clipToOutline` 不生效、
绘制在主线程同步完成；走这条路的只有录音与音频附件播放两个弹窗，它们的圆角来自窗口背景。
`SurfaceView` 的透明洞由框架的 `punchHole` 记下，`BaseCanvas` 有原生实现，软件画布同样可用——
实测合成图与同一时刻的系统截屏逐通道绝对差均值 0.17（魅族）/ 0.28（OPPO），四角透明，
且相隔几十秒的两张合成图上部控件区完全相同而水体区有变化。

同时定下的两条：

- **消散一律先离屏，窗口 `PixelCopy` 只作回退**（`ParticleCaptureRoute.preferOffscreen` 的
  `dismissal` 参数）。窗口那条在这台设备上对这两类弹窗本来就取不到数据，先试它只是白等
  ——抓图耗时因此从 1.07 s 降到 59 ms。**出现动画不跟着改**：它的末帧要与随后揭开的真实
  弹窗逐像素相同，窗口缓冲是那条契约最直接的来源，且两台设备上一直好用。
- **盖在真实弹窗上的交接图按弹窗圆角裁一刀**（`ParticleSnapshot.coverSurfaces` 的
  `cornerRadiusPx`）。`maskOnMaterialThread` 为真时圆角遮罩在材料线程上、对着粒子那一份做，
  盖回真实弹窗的这一份是没裁角的；此前只是恰好四角透明才没出事。

## 2026-09-15 窗口 PixelCopy 失败时改走「离屏重录 + 逐个 Surface 合成」

阶段 A 把「没有可见独立 Surface 就走离屏硬件抓图」这一半修好了，但**有**可见 Surface 的
弹窗仍然只有窗口 `PixelCopy` 一条路。魅族 20 Infinity 上录音弹窗（准备态、点外部关闭）正是
卡在这里：窗口 `PixelCopy` 整个 700 ms 重试窗口都返回 `ERROR_SOURCE_NO_DATA`，**修前 2/2
不播**；同一弹窗用返回键关闭走同一条路却正常。现在补上另一半回退。

- **两条回退互斥，各自只发生一次。** 没有可见 Surface：首选离屏、退窗口 `PixelCopy`；
  有可见 Surface：首选窗口 `PixelCopy`、退「离屏重录 + 逐个 Surface `PixelCopy` 再合成」。
  规则全在 `ParticleCaptureRoute`，单测从 6 项扩到 11 项（含「两条回退互斥」这一格）。
- **窗口缓冲仍是首选，不调换顺序。** 它是最直接的来源，且华为上 16/16 一直好用；
  离屏那条只在它失败之后才走。
- **撤销阶段 A 的一条判断：「离屏重录画不出 SurfaceView 的真实透明洞」只对软件 `Canvas`
  成立。** `ParticleHardwareSnapshot` 用的是 `RenderNode.beginRecording()` 给出的
  `RecordingCanvas`，`SurfaceView.draw` 在它上面照常记下 `punchHole`（`BaseRecordingCanvas`
  有原生实现），而离屏渲染器 `isOpaque=false`，洞是真的。实测旁证：回退合成出来的快照与
  同一时刻的系统截屏，不透明区逐通道绝对差均值 0.07、p99 = 2、98.3% 的像素差 ≤ 2；
  相隔 33 秒的两张合成快照，上部控件区完全相同而水体区 10% 的像素有变化——水体确实是
  Surface 的真实像素合成回来的。
- **`ParticleCaptureDump` 只在这条回退真的触发时落盘**（仅 debug）。正常路径一次也不写，
  因此不设开关文件；它是上面那条旁证的来源，也是以后再遇到同类问题的现成证据。

## 2026-09-15 第五批实施决策

数据与完整论证见 [batch5-results-2026-09-15.md](batch5-results-2026-09-15.md)。已发布 `202609150517`。

- **第四批那两处单像素差异定性为「驱动层面的非确定性」，不是共享资源泄漏，也不是对照工具的
  回读不稳。** 决定性的做法是把对照从「参考路径 vs 优化路径」改成**每条路径自己跑多遍**：
  同一个渲染器、同一批着色器、同一份 uniform、同一份材料、同一个上下文、同一条线程，
  两遍之间**没有任何代码上的自变量**，而它照样会有一帧不一样（OPD2515 上约 0.5–0.9% 的运行）。
  并发负载开 328 试次 3 次、关 472 试次 3 次，**分不出差别**——第四批「关掉提前预算后清零」
  是 2 次运行的结论，按这个事件率本来就有 98% 的概率清零。
- **定点复现给出了决定性的一帧**：出事那一帧的**八分量状态缓冲逐位相同**（`stateEqual: true`），
  而画出来的像素差了 2 个（相邻，最大通道差 13）。绘制的其余输入（材料、色素、前景纹理、
  uniform）全是静态或同一份——**喂给绘制的东西一个比特没变、出来的却不同**，
  分歧在顶点/光栅/混合/解析那一段，不在我们的 compute 着色器里。
- **「是不是对照工具自己的问题」用逐帧连读两次排除。** 画面不重画、只再 `glReadPixels` 一次，
  两次读到的一样才说明差异在被读回来之前就存在。全部轮次 `unstableReads` 恒为空。
- **固定种子下出事的永远是同几帧**（本批出现路径第 11 帧、消散路径第 10 帧），
  符合「某个量卡在判据边界上」。判据在 `velocity[i].z > .025`、`max(…, 0.)` 与四边形边压在
  像素中心这三处。差异幅度是单个像素上的一次覆盖翻转，产品路径上看不见。
- **G0 的验收口径因此改了：孤立单帧、个位数像素的差异不再直接判成回归**，先跑一遍自比较
  （`--gpu-diagnostics`）；自比较也出分歧就是本底噪声，自比较干净而 A/B 有差异才是真回归。
- **共享状态审查找到一处真实的隔离缺陷并修掉：`withBaselineGpu` 改的是进程级开关。**
  G0 对照跑在自己的线程上，而常驻 GL 线程上的提前预算每次 `advance()` 都读
  `skipBeforeFirstBirth`、`prepareReversePipeline()` 读另外两项并在编译时锁定、
  `ParticleCreationPrewarm.recipe()` 把三项都写进缓存键。改成「线程局部的基线标记 + 进程级
  设置值」两层，读点一个字没动。默认配置下没有画面后果（基线值与生产值只有
  `skipBeforeFirstBirth` 不同，而 2.4 是逐位恒等式），但缓存键会因此白白未命中。
  **教训：诊断工具不得改生产路径会读的进程级状态；要改就改成线程局部的。**
- **创建页预测素材持久化（用户批准的追加项）落地。** 把空白创建页的首屏无损压缩
  （API 30+ `WEBP_LOSSLESS`，以下 PNG）存进 `filesDir/particle-prewarm/`，与**去掉新记事
  背景色之后的那 15 项键**和来源时间一起；冷启动后在预算那条后台线程上按键读回。
  **背景色不进磁盘键**：它每次新建都重掷，进了键就永远不命中，而它只影响途中权重，
  末帧照旧由当次真实快照拼回。淘汰：最多 4 个配置、总量 8 MB，两条都从最旧那一端走；
  **单张超上限时先量临时文件再改名**——同键的文件名是同一个，先改名会把盘上好好的那张
  覆盖掉再删掉。实测冷启动第一次新建 OPPO 549.7 → **221.5 ms**、三星 971.2 → **324.9 ms**，
  与同进程第二次（196.1 / 310.2 ms）基本持平；单张 WEBP 只有 69–143 KB，两种配置合计 0.2 MB。
- **`trimMemory()` 撤掉待办预算调度这一条语义不动**：内存告警之后立刻重建 17 MB 的预测素材
  不合适，等下一次用户交互或回到前台时的 `onHomeVisible` 重新排上即可。实测「退后台 +
  `RUNNING_CRITICAL` + 回前台」之后 `sourceKind` 仍是 `disk`，磁盘缓存可用。
- **方向变化这一项两台都测不成**（OPD2515 显示根本不转；SM-S9180 转得动，但
  `screenOrientation="user"` 在自动旋转关掉时把新进程锁回自然方向），键失效改用**深浅色**
  验证——同在那 15 项里，且真的换了一张明显不同的图。
- **`verify_repeated_appearance.py` 的 `--check` 阈值早于第四批的 2c，不再使用**；
  第二批那一轮其实也是不带 `--check` 跑的（它留下的原始 `summary.json` 里三星有六格
  `max` 越过 65）。回归判据回到脚本的常开断言 + 与第二批的数字对表。

  播完撤回。**「P95 与最大值下降」这条验收标准本身不成立**：那些长帧是低刷新率下被拉长的正常帧，

  长帧不是排在我们的 compute 后面，`GPU` 那一栏在开关两种状态下都是 12–15 ms。
- **工作线程优先级跟随调用线程，1.7 的语义不在本地库里重复判一次。** 调用线程已经按

- **`ParticleMaterialNative.setLanes(0)` 的 `coerceIn(1, 16)` 是真缺陷**：0 被夹成 1，于是 3b 那条

## 2026-09-15 第三批实施决策

数据与完整论证见 [batch3-results-2026-09-15.md](batch3-results-2026-09-15.md)。

- **3.1 的回退改成「先画备好的最高一档，再逐拍追上手指」，不在出帧路径上补档。**
  第二批的问题是首帧同步补齐 `ceil(position)` 档历史；本批把「手指要的相位」与「这一拍真的
  能画的相位」分开：出帧只画 `min(手指相位, 已备档位)`（整数相位，`drawGestureFrame` 的
  fraction 为 0，一定安全），补档全部交给 pump（每拍最多拖住一档）。`presentedProgress`、
  ItemTouchHelper 的松手恢复、快速完成都改用**实际呈现的相位**，所以「甩动比准备快时先播完
  剩余画面再执行完成」变成了字面意义上的真。开关 `gestureCreepToFinger`，默认开。
- **「手指停住」与「画面停住」必须分开判定。** `wantsFrame()` 若继续比较手指相位，追赶期内
  手指一停画面就冻住；改为比较这一拍能画的相位，同时新增 `previousWanted` 专门给速度与
  「手指停住多备两档」用。
- **2b 只改材料输入，不改模型。** 真实触点（新建按钮中心）经窗口坐标在抓图那一刻换算到快照
  局部坐标，方向取「内容中心 → 触点」，`touchGap` / `touchStrength` 按真实触点算。触点落在
  内容里时二者都是 0——这与弹窗里点按钮关闭的现有配置完全相同，是已经验证过的取值范围。
  无论开关开关，真实触点都记进 `ParticleDismissSpec.appearanceTouchXPx/YPx`，供对比工具重建
  两种输入。开关 `creationAppearanceFromFab`，默认开。
- **2c 的「时间值」绝不能跟着缩短。** `ParticleReversePlan.time(frame) = frame / samples`，
  samples 一旦改变，每一个采样的积分时刻都会变，保留段就不再逐位相同。实现是：samples 不动，
  只把**预计算的终点**与**播放的起点**改成 `appearanceStartFrame`，播放时长按 `start/samples`
  缩短。起点判据用 `material.vert` 的裁剪条件（`0 < t - birth < life` 开区间）算每个采样的存活
  片数，取「仍 ≥ 5%」的最晚采样。5% 写成 `APPEARANCE_ALIVE_RATIO` 常量便于调。开关
  `creationAppearanceSkipEmptyTail`，默认开，只作用于创建页（弹窗出现不传 `skipEmptyTail`）。
- **第三项（为下一次新建预算轨迹）不做。** `App.newThingBackground` 每次创建页打开时重掷全谱
  随机 RGB（50% 渐变），而材料模型直接吃快照像素（面板分类、白占比、逐片内容权重、复制片数），
  换个背景色连出生与寿命都变；下一页的像素在它真正布局渲染之前拿不到。折中方案见结果文档第 8 节。
- **2b 的预计算代价（每采样 +21–25%）本批不自行归因。** 两台方向一致，最可能是
  `touch_strength` 0.5 → 0 让 `distance_gain` 从 1.0 降到 0.55、采样散布扩大 1.8 倍。已把

## 2026-09-14 第一批实施决策

- **1.9 的根因不是生命周期缺陷，而是时长缩放口径不一致。** OPD2515 上 `Settings.Global` 里
  根本没有 `animator_duration_scale` 这一行（读到默认 1.0），而框架给 `ValueAnimator` 施加的是 5.0。

  同一条时间基准；兜底改成按涟漪真实寿命算，并新增「控件已 detach」「没有动画器在推进却 alpha>0」

- **验收目标「消散首帧 100–130 ms」不适用于录音行这条路径，不追。** 100–130 ms 是返回键路径的数字，

  实测两台 399–451 ms，已经贴住下限。
- **1.8 的时钟不能挂 GL 线程自己的 Looper。** 绘制期间那条 Looper 在跑绘制、收不到 vsync，

  （`ParticleClock`），保留原来的「节拍与绘制分属两条线程、画完立刻接上最新一拍」结构，

- **1.7 只在「已经有反馈或别的层在播」时让出优先级**，不是无条件降级。无条件降级会让左滑的

读后再判是安全的：包围盒只单调外扩，读到旧值只会让判定偏保守。

**A2（方向常量提成 uniform）与 A3（流场与置信度并成一张纹理）删除。** 两项在三条路径上
都落在 ±2% 的本底噪声里；判据是「回放路径根本不做积分，却也报同样量级的变化」。
按本专项「魅族上没有可测收益的项回退，不留理论上更快的改动」的纪律整段删掉，不留开关。

**B7（第 0 遍改成一张权重图）不做。** 等价性分析不成立：第 0 遍的四边形四角带整数散列抖动
（相邻片共用顶点，是一张**抖动的密铺网格**），而权重图 + `NEAREST` 会把像素归属换成
`floor(p/cell)` 的轴对齐矩形。魅族上格子约 4.3 px、抖动 ±1.3 px，`surface_out` 又含每片独立的
释放抖动——释放前沿的形状会从抖动边界变成网格边界。这是结构性差异、不是浮点噪声，
超出本批「不含需要用户看图定夺的可见改动」的约束。且 A1 之后第 0 遍的顶点成本已经很低，
片元数量本来就等于卡片面积、一个也省不掉。

**创建页提前预算的键里去掉刷新率。** `samplesFor` 对刷新率做 `coerceIn(30f, 60f)`，
≥ 60 的任何值给同一个采样数，所以 120 与 60 本来就等价；真正该用的是粒子层自己投的
60 Hz（`ParticleWindowSurface.VOTED_FRAME_RATE`），会话与预算两侧从此是同一个常量。

## 2026-09-17 逐帧成本第二批：双上下文 + 异步预读留下，首帧提前量默认关

逐项数字见 [per-frame-batch2-2026-09-17.md](per-frame-batch2-2026-09-17.md)。本批**全部是 G0**
（不改着色器、模型、参数与采样内容），只改「什么时候、在哪条命令流上算」。

**F14（两个 EGL 上下文分优先级）留下。** 两台真机都真的读回了 `HIGH` / `LOW`，
所以这一项的结论可归因。**后台放同一条线程、按需 `eglMakeCurrent` 切换**，不另起线程：
一是同线程切换实测只要 10–17 µs，一整轮九个场景的矩阵总共才切 270–302 次、合计 10–13 ms；
二是两个上下文共用同一批**程序对象**，而 uniform 是程序对象的状态——另起线程就要给
「切换会话时整套重设 uniform」那条既有机制加锁，风险远大于收益。

**三条交接纪律写进代码，不是注释。** ① 优先级请求值只是 hint，建完必须 `eglQueryContext`
读回，读不到或两档没分开就销毁第二个上下文、退回单上下文；② 切到后台之前
`glFenceSync` + `glFlush`，切过去再 `glWaitSync`；③ **切回出帧时不插任何等待**——让高优先级
的一帧去等低优先级上下文里全部在途的工作就是优先级反转，可见性改由数据那一侧保证。

**F15（预读提交即返回、栅栏轮询确认）留下，但在途深度仍是两批。** 改的是「CPU 不再阻塞
等它」，不是「往驱动里排更多」：排得更深会让弹窗 A 的一帧要等上后台几十毫秒的 compute，
而「低优先级一定会被抢占」在 Adreno 上没有公开保证（调研第 8 节：抢占点在 bin 边界，
compute dispatch 内部能不能抢占没有资料）。深度留成可调项 `reverseInFlight`。

**`preparedSamples` 的定义改成「已经确认写完的采样」**，另开 `submittedSamples` 记已提交的。
出帧侧只许画到前者——这一条同时消掉了跨上下文的可见性问题（客户端观察到栅栏发信号，
那之前的写入对 share group 里任何上下文都可见），所以出帧侧一次 `glWaitSync` 都不用插。

**「首帧绕开节拍」默认关闭。** 调研第 10 节说它最多省一整拍，实测**两台都量不出收益**：
上限本来就只有 16.7 ms，而第三批的 `beatDuringPreparation` 已经让节拍在准备期间就跑着，
魅族三个左滑场景 + 两个弹窗场景的「请求 → 首帧呈现」在开与关之间全落在单轮噪声里
（±20–40 ms）。按「没有可测收益就回退」的纪律默认关，开关与实现留着。

**它踩出来的那条时序教训必须记住：提前出的一帧，要替掉的那一拍必须真的吃掉。**
提前的那一帧会在 `now` 之后的第一个 vsync 上屏，而节拍目标就锚在各个 vsync 上；只把
「已消费的节拍」推到 `now`，紧接着那一拍会再提交一帧，**两张缓冲落在同一个显示周期里，
SurfaceFlinger 只 latch 新的、把先提交的直接丢掉**。被丢掉的那一帧永远等不到
`EGL_DISPLAY_PRESENT_TIME`，卡在待确认队列的队头，后面的帧要等队列溢出才一起放行——
观察器里的形态是**六个确认时刻挤在 1.7 ms 之内**，而症状看起来只是「首帧上屏晚了 60 ms」。

**「来回拖不跟手」不在预读这条链路上。** 新增的滞后曲线（每画一帧记一次「手指要的相位 −
实际画出的相位」）给出：慢拖与来回拖两台、两种条件下 p90 都是 **0.00 档**，画面逐帧跟着
手指；滞后只出现在**第一次拖到从没到过的深度**那一两帧（max 1.8–6.9 档、占 3%–7%），
因为历史只增不减，越过之后再怎么来回都是现成的。来回拖剩下的问题是**帧率**
（移动期约 38 fps、呈现间隔 p90 33 ms），而那时预读早就停了，不是预算在抢。记入 followups。

## 2026-09-17 逐帧成本第四批：C7 的根因是原子操作的写法，两项参数进设置

逐项数字见 [per-frame-batch4-2026-09-17.md](per-frame-batch4-2026-09-17.md)。

**C7 在华为上「40 与 100 逐位相同」不是收敛，是缺陷。** `peel-splat.comp` 原来写
`atomicAdd(accumulation[k].x, …)`——原子操作的目标是**数组元素的一个向量分量**。
Maleoon 910 上这种写法不按下标寻址，十万片的累积全部落进第 0 格，于是占据度恒为零、
活动 tile 数恒为 0、间接分发的组数为 0，**整条压力投影在那台设备上从来没有运行过**。
改成标量数组（`int accumulation[]`，下标 `k*4+c`，同一批字节）之后，华为的活动 tile
0 → 54、压力场总和 0.0024 → 3920，三档迭代数的画面与状态散列全部不同，与魅族一致。
同一种写法在 `pressure-tiles*.comp` 的 `atomicAdd(workgroups.x, 1u)` 上还有一处
（目标恰好是第 0 个元素，因此碰巧正确），一并改成标量成员。

**这条修复会让华为变慢，而且必须如实报告**：那一段本来就该跑，现场消散每帧
23.9 → 40.7 ms、出现预计算 446 → 978 ms。迭代数调到 40 即回到 26.9 ms——这正是把参数
交给用户的用处。**默认值不动**。

**契约写成判据而不是写法**：单测把每一处 `atomic*` 调用的第一个实参切出来，只要以
`.x/.y/.z/.w` 收尾就失败，换个变量名或多一层下标同样挡得住。

**两项参数进设置，形态是二级页面而不是弹窗**（用户在实施中途改的）。这一改同时消掉了
原方案里最大的一处风险：粒子层是「一窗一 Surface」且以 Activity 为键，做成弹窗就要把它
推广为按 Window 建，会动到「先显后撤、暗层交接、`hosts` 弱引用表」三处不变式。

**微片尺寸最低一档「0.9 dp」不往模型里写下限。** 归一空间里一个 dp 是 1.875 个单位，
规则里的下限 `cell=1.65` 正好是 0.88 dp；真写 0.9 dp 会让格子比现状小一点点，默认值就不再
与此前逐位相同。这一档因此返回 0，标签仍显示 0.9 dp，由单测守着。

**两项都进创建页预算的指纹，取的是设置值而不是 `…Now` 读点**——后者带线程局部覆盖，
是离屏受控对照临时切的瞬时状态，写进指纹会让预算必然判废。

## 2026-09-18 逐帧成本第二阶段：按华为的实测份额重排，七项回退

结果见 [per-frame-phase2-results-2026-09-18.md](per-frame-phase2-results-2026-09-18.md)，
第一步的归因见 [per-frame-huawei-attrib-2026-09-18.md](per-frame-huawei-attrib-2026-09-18.md)。
已发布 `202609172005`。

**一、方案第 2 节的排序是按资料推断的，实测把它整个改了。** 调研给出的前三名是
「累积目标换格式 / 三维取样 / varying 精度」，实测只有第一名成立：

- **三维取样在 Maleoon 上根本不是瓶颈。** 判据是一条**单格取样探针**——把 `sample_field` 换成
  只取一个格子、不做三线性（画面必然错），三条路径的墙钟比值是 1.040 / 0.958 / 1.045。
  Arm 给「3D 格式 2× + highp 采样器 2×」的那两条在这台设备上量不出来，U2 / U2b / U3 / U10 随之落空。
- **`mediump` 在图形管线里是空声明，在 compute 里是真的。** 两台的 varying 与采样器改 `mediump`
  之后**画面逐位相同**（61 帧 0 差异）⇒ 驱动忽略；而 `curl()` 与 `peel-blur` 的 `vec4` 改 `mediump`
  之后 Adreno 上 55–57/61 帧不同、最大通道差 **253**、位置偏差 0.4 px，只换来 2–3% 的墙钟。
  按方案第 5 节的退出规则，**前者「没有回归」不是留下的理由**，后者不划算，三项全退。
- **逐次 Jacobi 在 Mali 上不成立。** Arm 明写「shared 不是片上内存、不要把全局内存抄进 shared」，
  但把活动区域接上逐次路径之后，华为的现场消散仍然慢 **2.96 倍**——100 次 dispatch + 100 道屏障
  换不回 shared 的代价。M2 / M3 一起否决。

**二、在这条管线上「绘制记录的每片字节数」是比「属性流条数」更强的自变量。**
U4 第一版把记录从 64 B 扩到 80 B 去放新增的逐片量，华为上**现场消散 −15% 但回放出现 +8%**；
把 `replica` 与 `alive` 合成一个标志位、`radial` 与 `loosen`/`age_beat` 各用 `packHalf2x16`
打包回 64 B 之后变成 0.953 / 0.814 / 1.063。同一条因果也否掉了 U10a（Arm 5.9 的
「一次绘制不要超过一个实例化缓冲」）：它要的第五段记录比省下的那一路属性更贵。

**三、Mali 上「不清累积纹理」反而慢 12.5%。** tile 架构上渲染通道开头的 `glClear` 让整块 tile
不必从主存载入；不清就变成 load-modify-store。Adreno 上这一项落在噪声里（阶段 0' 的结论）——
两家方向完全相反，B6「按包围盒局部清空」在 Mali 上是负收益，彻底划掉。

**四、验收目标没达到，两条后手默认关。** 华为默认档位的附件弹窗消散 0.186 → 0.229，
离「2.4 dp / 40 的 1.01」仍差一个量级。U7（累积目标换 `SRGB8_ALPHA8`）与 U9（按实测帧率自动
调低一档）都已实现、默认关，等用户看图裁定。**用户在那台设备上已经把档位改成 2.0 dp / 20**，
那一列不掉帧；默认档位的差距是「新装用户会遇到什么」的问题。

**五、L1 / L2 / L4 三项「实施」实为核对，结论是已经对了或没有头寸。** 相位锁定之后首帧的呈现
时刻本来就写「尽快」；首页的建材在 `ACTION_DOWN` 就派出去了（`ParticleSwipeAnimator.warm`），
不等 `ItemTouchHelper`；弹窗的离屏抓图用的是弹窗窗口自己的 decor，本来就不是整窗。
落地的是 L3（ADPF 的周期与突发两条会话）。

**六、两条工程事实**，都是踩过才知道的：GLES 3.1 的**存储图像格式表里没有 `rg16f`**
（Adreno 740 直接拒绝编译，只能退到 `rgba16f`）；**EMUI 会拦掉发给清单接收器的广播**
（`am broadcast -n <组件>` 返回 `result=0`，系统日志里是 `targets O+, restricted`，
接收器一次也没跑），所以着色器变体的编译矩阵改成一个导出的 debug Activity。

   的散度。键名换成 `flow_detail` 并**按取值迁移**（旧的第 k 档搬成那一档的迭代数；

   刷一次；滑动条的渐变着色每步都要重建 drawable，按约 12 档节流）。
5. **预览页的滑动永远判不成完成，松手一律沿原轨迹倒放回来。**
   `getSwipeThreshold` 与 `getSwipeEscapeVelocity` 都给到不可能达到的值，松手走
   `ItemTouchHelper` 的 `ANIMATION_TYPE_SWIPE_CANCEL`，它每帧回调 `onChildDraw` 且位移单调
   回零，`ParticleSwipeAnimator` 据此把相位从末端喂回 0——粒子沿原轨迹聚回卡片，卡片全程停在

   代价是**半程松手不再自动播完**，而是从松手那一刻往回退；**首页真实列表的完成语义一个字没改**。

   `ItemTouchHelper` 注册**（它在 `ACTION_DOWN` 会接管正在跑的回位动画，之后 `clearView`

8. **示例文案由协调方拟定，逐字采用**：记事卡片「河流的答案」、示例对话框「留在此刻」
   与「继续 / 稍后」，其余 11 个语言目录按此意译，代码里零写死。
