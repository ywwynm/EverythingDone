# DoingActivity 边界回弹与急停卡顿

## 最终结论与验收

本轮确认不只清单受影响：旧版 OPPO 的长文本、图片附件、视频 GIF 卡片均复现约 33ms 的边界捕获空档。共同原因是厂商预测动画阶段让惯性与 `EdgeEffect.draw()` 读取未来时间，以及惯性停止后边缘效果的下一帧等待。最终在所有 Doing 卡型共用的 `DoingRecyclerView` 与整页所有者中修正调度；保留系统滚动／回弹算法、整页 GL、粒子模型、计时动画和 GIF。

## 反馈与复现过程

用户在 OPPO `3B1629006YC00000` 的 debug `202610141152` 上仍感到惯性到底部、回弹或急停卡顿，指定首个清单项为“右滑记事的动画优化”的记事。沿用已有三机操作授权，重点先在 OPPO 复现，真实内容只读。保留整页 GL、粒子、计时和 GIF。

此前主体指标只覆盖 RecyclerView SETTLING 的移动窗口；到达边界后可能已经变为 IDLE，但系统边缘效果或回弹仍在运行。新的反馈要求把停止前后的内容变化及屏幕呈现单独测量，不能用平均 FPS 代替边界观感验证。

第一组复现方法无效：沿用 18% 视口的交替 fling，实际向下滚到约 571px，而该卡底部为 974px；没有覆盖底部。用户现场指出一直在顶部附近往返，已改为 64% 视口的同向向上甩动，先实际抵达内容底部，再反复触发底部效果。该初始组不作为底部卡顿证据。

## 底部复现与假设

第二组确认真实到达 974px 底部，并连续六次向上甩动。当前整页路径在边界窗口捕获的最大间隔为 41.8–57.8ms；同一记事保留原生绘制对照。录像仅作内容轨迹检查，不把静止期或录像帧率当作卡顿证据。

排序假设：

1. 边缘效果未持续请求绘制：若 EdgeEffect 仍未结束，但 preDraw／捕获出现长空档，应优先检查失效传播。
2. 主线程动画节拍或时间源改变：若原生与 GL 的绘制节拍或回弹进度差异明显，而消费者仍流畅，则检查主线程／动画时钟。
3. 完成图像交接延迟：若 preDraw 连续而捕获链或呈现中断，检查在途图像／释放门槛。

增加 debug 专用的逐遍历只读状态：上下 EdgeEffect.distance／isFinished、清单偏移、滚动状态、动画时间与实际时间。只读取现有实例，避免替换 EdgeEffect 本身而改变待测行为。

## 归因进展

从距底部约 400px 的位置反复甩到底部，GL 和原生各六次均复现：到边界前每隔 3–4ms 发生一次遍历，动画时间累计超前实际约 24ms；到边界后下一次遍历间隔约 33ms，首次实际回弹进度变化要约 41ms。稳态回弹约 8.3ms 一次，图像捕获链中位约 5.6ms且没有长耗时，全部提交成功。此前整窗口 40–58ms 的最大捕获间隔还含静止期，不直接当作卡顿幅度。

因此主要问题位于清单惯性推进／主线程动画时钟，原生绘制也复现，不能通过撤销整页 GL 来解决。单变量实验：仅把 Doing RecyclerView 的 postOnAnimation 回调改用公开 Choreographer 帧回调派发，保留取消／销毁语义、原 OverScroller 和原 EdgeEffect；先只在 debug 探针启用，与现路径配对验证，不调用隐藏时钟 API。

该实验未改善：六次撞底仍约 41ms 后回弹开始。追加记录 145 次 Choreographer 回调，其帧时间全部不晚于实际时间，基于帧时间的防超前分支一次也未触发。说明提前发生在系统动画时钟路径，不是简单换一种 postOnAnimation 派发就能解决。失败实验副本仅保留在本地实验目录。

## 已确认的系统行为与修复

只读检查该 OPPO 设备的系统框架：`ChoreographerExtImpl.doAnimAheadCallback()` 取预测时间，调用 `AnimationUtils.lockAnimationClock()`，再执行动画阶段回调。这些回调的帧参数仍可能是旧帧时间。未调用隐藏 API，也未修改系统设置；框架文件和反汇编仅保留本地。

改用公开 `AnimationUtils.currentAnimationTimeMillis()` 与 `SystemClock.uptimeMillis()` 比较，超过 1ms 时推迟本次清单回调。相同六次撞底实验中，回弹首次进度变化间隔从 35.8–41.9ms 降为 13.7–16.8ms，边界遍历最大间隔降至 8.8–10.4ms。327 次回调尝试中有 242 次来自未来动画时间，均未提前推进惯性。此结果确认了根因，并不表示其它阶段完全没有掉帧。

该候选在三机回归时被否决：魅族的连续预测时间让它反复推迟，惯性几乎停住，不能发布。下一候选改为在检测到未来动画时间时，将同一次回调交给 UI Handler，等当前动画阶段返回、系统解除时钟锁定后执行，而非等待下一帧。三星无未来时间时仍按正常帧执行。两种候选的负面证据均保留。

修复范围为所有 Doing 卡片共用的 RecyclerView，而非仅清单。保留 OverScroller／EdgeEffect 算法和整页 GL，不改变粒子、计时数字或 GIF 的动画时钟。不限定厂商，不强制帧率。保留重复投递、取消、回调内再次投递和卸载清理；移除实验开关及生产路径临时诊断行。正在补充真实急停和三机回归。

## 其它卡型与后续单变量实验

修复前 OPPO 长文本、图片附件、视频派生 GIF 卡片各两次真实撞底均复现，首次回弹变化间隔分别为 41.55–41.57ms、41.50–41.68ms、41.66–41.72ms。因此已确认共同滚动容器受影响，并非仅清单。相同进程内在 UP 后 40ms 再次 DOWN，真实清单与三种卡型共 12 次，全部在惯性状态下被打断；按下后约 3.4–5.3ms 即停止惯性。此次未发现急停触摸处理本身的长阻塞，不能把边界改善直接称为所有急停问题都已解决。

仅将超前回调转交 UI Handler 后，魅族不再停住，但 OPPO 边界仍停等约 33ms，候选未通过。改为通过既有 `ParticleClock` 线程接收一次性真实 vsync，再回 UI 队列执行原 ViewFlinger，避免在 UI 预测动画阶段执行；该回调独立于粒子分频和启停。OPPO 三次首次进度变化为约 5.6／33.5／4.5ms，仍有一次失败。对应失败窗口显示：惯性已经按真实时间推进，但整页捕获仍在预测遍历中调用 `EdgeEffect.draw`，绘制读取了未来约 24ms 的动画时间。

继续只修正这个记录阶段：检测到未来动画时钟时，将整页记录合并投递到同一 UI 异步队列，等当前动画阶段结束后执行；保留布局、属性更新及后续 GL 提交流程。该候选尚在实机复验，以上中间版本均未发布。

两个执行阶段同时修正后，OPPO 同条件三次撞底的首次变化间隔降为 5.49／4.53／4.40ms；魅族为 9.95／0／6.48ms，惯性正常推进。每台两次真实急停均成立；重复投递、取消、非 UI 线程投递／取消、回调内重入、挂载前排队和卸载清理检查通过。最终扩大为三机五类卡片的合并回归，结果待下文回填。

扩大到长图后仍出现一次约 33ms 的捕获间隔：此时 ViewFlinger 已结束，系统仍延迟 EdgeEffect 请求的下一次重绘。因此最终还接续 RecyclerView 在 IDLE 状态发出的 `postInvalidateOnAnimation()`：使用真实 vsync 通知整页所有者，下一帧先使源 View 失效，再记录已经布局的内容；存在布局请求时继续等待原生布局。仅按实际动画请求续帧，后台／退出取消，没有常驻循环。长图候选 OPPO 三次边界捕获间隔为 9.25／5.10／7.76ms，魅族为 8.49／8.39／7.88ms。

指标补充：preDraw 的旧状态观察会比实际绘制晚一帧，且最终可以在两个原窗口遍历之间记录。最终增加 debug 专用的实际 draw 观察（状态行 20），避免把原窗口遍历间隔误当成 GL 画面停顿；新旧统一主指标使用 PAGE_CAPTURE 的记录开始时刻。OPPO 原版长文本／图片／GIF 的边界相邻捕获间隔为 33.17–33.64ms，旧 preDraw 对应看到首个非零回弹为约 41–42ms。两种指标不能混为同一数值。

最终合并测试中发生一次 ADB 服务中断，OPPO／魅族各一份长文本报告不完整，已排除并补跑；设备端结果未记录应用异常。这不是一次通过的回归样本。

## 持续惯性的兼容性修正

独立节拍推进惯性、加上边缘续帧的候选，三机五卡型共 30 次撞底和 15 次急停都通过；但持续 fling 中 OPPO 约 106–114 FPS、魅族约 107–112 FPS，低于此前约 119 FPS 的水平。将回 UI 队列改为异步 Handler 后没有充分恢复，故不将该候选标作最终完成。

收缩调度改动：普通帧保留原 UI 动画阶段的执行时机，仅在动画时间确实超前时把同一次惯性回调移到当前阶段结束后的异步 UI 队列。不反复跳帧、不改变物理模型。独立节拍仅负责惯性已停止后的实际边缘重绘请求。正在用相同四卡型 fling 对照确认。

一次魅族长清单测试在输入前报告 `bootstrap_surface_unavailable`，该轮按失败保留，没有纳入 FPS；下一候选同类测试启动成功。不能把失败报告当作成功退出样本。

保留正常 UI 动画阶段后，OPPO 长文本／长图恢复约 119／118 FPS，魅族仍约 111／114。继续缩小整页记录的推迟条件，仅在默认 EdgeEffect 实例仍活动时处理未来时间，正常惯性不推迟记录。新的长文本对照：三星约 115、OPPO 119、魅族 120 FPS；这个结果说明不能把所有捕获都移出预测阶段。默认 EdgeEffect 通过公开工厂观察，未替换算法，尺寸改变同步清理观察引用。最终确认候选继续覆盖另外三类复杂卡片与边界／画面回归。

又一次长图取证显示，原窗口在整页捕获之前也可能更新 RecyclerView 的显示列表，把回弹推进到未来，单独延后 GL 记录仍不充分。最终在继承的系统 EdgeEffect.draw 入口拦住未来时间推进，实际时间仍调用原系统实现；延后记录时使 RecyclerView 失效，避免复用预测阶段的缓存。每次实际 draw 后，只要边缘效果尚未结束且惯性已停止，就按真实节拍接续；不再仅依赖首次 absorb 是否返回重绘标记。

魅族长清单再次复现启动前 `bootstrap_surface_unavailable`，已定位原有期限起点错误：记事布局和 Activity 启动期间已经耗尽 2 秒，首次请求 Surface 的遍历便直接判超时。该失败记录中，UI 准备约 2903ms、失败约 3263ms，窗口约 4223ms 才获焦点。改为首次实际遍历请求 Surface 时开始原有 2 秒等待，不延长 Surface 自身期限，也不掩盖真正失败。增加启动时刻事件，最终在长清单冷启动中核验。

最终冷启动实测：魅族 90 项长清单在约 2489ms 开始请求 Surface，约 3696ms 创建整页 GL（实际等待约 1207ms），约 4124ms 首帧就绪；没有回退原生。该轮同时通过真实撞底、急停、退出和资源释放检查。
