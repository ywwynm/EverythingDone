## 逐帧成本第二批：两条命令流分优先级、预读不再卡住节拍

这一版一个像素都没改——不动粒子模型、着色器、参数与采样内容，只改「什么时候、在哪条命令流上
算」。魅族 20 Infinity 与三星 SM-S9180 两台各测一轮修前、一轮修后。

### 出帧与后台预算分成两条命令流

粒子的渲染线程现在有两个 EGL 上下文：出帧那一个（现场积分、绘制、合成、交换）请求高优先级，
后台那一个（弹窗的出现预计算、左滑的历史预读、新建页的提前预算）请求低优先级，两者共享同一批
着色器程序、缓冲与纹理。这样一帧的绘制不再排在几十次计算后面——最典型的就是「关掉一个弹窗、
同时打开另一个」：前一个的消散要和后一个近一秒的预计算抢同一块 GPU。

优先级在规范里只是一个「建议」，驱动可以不理，所以建完立刻读回来核对：**两台读到的都是
HIGH / LOW**，读不到或者两档没分开就自动退回单上下文，行为与上一版完全一致。两个上下文放在
同一条线程上按需切换，实测一次切换只要 10–17 微秒，一整轮九个场景的测试总共才切 270–302 次。

### 预读改成「提交完就走」

以前每算好一个历史采样都要停下来等 GPU 确认（左滑约 4 毫秒、弹窗 5–7 毫秒），而一拍留给准备
工作的预算只有 8 毫秒——一拍里塞不下两个采样，这段等待又正好压在出画的节拍上。现在改成提交之后
立刻返回，由一个轻量的轮询确认哪些采样真的写完了；**画面只会画已经确认写完的采样**，所以既没有
读到半成品的风险，也不再占着节拍。同时按实测重新定了三个档数：按下阶段先备 6 → 12 档，
手指停住时每拍多备 2 → 6 档，手指在动时按速度成比例（原来固定 1 或 2 档）。

另外，只要有动画正在逐帧出画，一次准备工作就不许跨过下一拍——给合成与上屏回调留出余量。

### 实测

左滑快拖（甩一下就松手）是收益最实的一格：移动期真正出现的不同画面，魅族 7 → 9、三星 7 → 12；
魅族的「手指要到的位置 − 画面实际画到的位置」九成位从 16.2 档降到 10.3 档（一档约等于卡片宽度的
三十六分之一）。

弹窗侧是最长停顿与九成位停顿的普遍缩短：

| 场景 | 修前 → 修后 |
| --- | --- |
| 附件弹窗 返回键消散 最长间隔（魅族） | 228.8 → 87.8 ms |
| 附件弹窗 点外部消散 间隔九成位（魅族） | 62.0 → 33.1 ms |
| 调整颜色面板 出现 间隔九成位（魅族） | 96.6 → 24.8 ms |
| 调整颜色面板 消散 出帧比例（魅族，15.8 万片） | 0.725 → 0.842 |
| 附件弹窗 点外部出现 最长间隔（三星） | 238.0 → 94.8 ms |
| 录音弹窗 消散 最长间隔（三星） | 33.3 → 25.0 ms |

### 顺带查清的两件事

**「按住不放来回滑动时不跟手」不是预读跟不上。** 这一版新加了一条逐帧的滞后曲线，把「手指要到
的位置」与「画面实际画到的位置」逐帧记下来。结果是：慢拖与来回拖，两台设备、修前修后四种条件
下，滞后的九成位都是 **0 档**——画面是逐帧跟着手指的，一档都不落后。落后只出现在「第一次拖到
从来没到过的深度」那一两帧，因为那时的历史才刚算出来；越过之后再怎么来回都是现成的。
来回拖剩下的问题是帧率本身（移动期约 38 fps），与预读无关，下一版单独查。

**「首帧不等节拍直接出」做了，但两台都量不出收益，这一版默认关着。** 它理论上最多省一拍
（16.7 毫秒），而上一批已经让节拍在准备期间就跑起来了，实际能省的更少；两台的「点下去到首帧
上屏」在开与关之间全落在单轮波动里。实现与它踩出来的一个时序坑留在代码里：提前出的那一帧会
占用下一个屏幕刷新，如果不把它要替掉的那一拍真的跳过，两张画面会落在同一个刷新周期里，
系统只显示新的那张、把先提交的直接丢掉——而被丢掉的那一张会一直等不到「已上屏」的回执，
把后面几帧一起卡住。

### 稳妥性

两台设备的逐帧散列对照各两份全部通过：同一条路径自己跟自己比 0 帧差异，压力活动区域逐位相同，
唯一的差异仍是上一批那一项已知的亚像素噪声（万分之二的像素）。全程没有一条新的告警或回退日志。
魅族六段录屏做了逐帧亮度差分扫描，最大的几帧全部落在正常的连续过渡上，没有孤立的单帧跳变。
上面每一项都有独立开关，可以逐项关回上一版的行为。
