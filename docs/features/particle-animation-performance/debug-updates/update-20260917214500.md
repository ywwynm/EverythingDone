## 逐帧成本第三批：把粒子的节拍锁到屏幕真正的刷新节奏上

这一版同样一个像素都没改——不动粒子模型、着色器、参数与采样内容，只改「这一帧该在什么时刻
出」。魅族 20 Infinity 与华为 MatePad Pro 13.2 两台各测一轮修前、一轮修后。

### 先查清楚，再动手

上一版之后，左滑仍然看着不跟手，但已经排除了「画面落后手指」这条——画出来的就是手指要的位置。
这一版先加了一条只在调试包里生效的记录，把一帧从屏幕刷新信号到真正上屏的每一步都记下来：
节拍什么时候来、有没有跳过、这一拍为什么没出画、等上一帧画完花了多久、提交之后隔多久才上屏。

一轮下来，之前怀疑的五条里否掉了四条：节拍一次都没跳过；等上一帧画完只要 **0.02 毫秒**；
准备工作根本没占住节拍；也没有任何一拍卡在动画状态或可见性上。

### 真正的原因：我们的节拍和屏幕对不上

粒子按每秒 60 帧出画，一拍算 16.667 毫秒。但魅族这块屏在触摸时跑 120.8 赫兹，**两次刷新其实
只有 16.55 毫秒**——我们每一拍都比屏幕多走 0.117 毫秒。几十拍之后就整整错开一次刷新，同一批
画面的上屏时刻因此散在四个档位上，间隔在 8.3 / 16.6 / 24.8 / 33.1 毫秒之间来回跳。均值看着
接近 60，看起来却一直在抖。

现在改成：**每一拍的目标时刻直接取屏幕这一次刷新的时刻**，出不出这一拍看「距上一拍够不够久」。
这样目标永远落在真实的刷新点上，不会越漂越远；屏幕是 90 赫兹就出 90 帧、144 赫兹就出 72 帧，
都不会低于 60。

### 实测

魅族：从「这一拍该出画」到画面真正提交出去，九成位 **11.6 → 5.7 毫秒**；从这一拍到真正上屏，
九成位 **41.6 → 34.0 毫秒**（正好省下一次屏幕刷新），十二格左滑里十二格的提交延迟都下降。

华为是三台里掉帧最重的一台，收益体现在帧数上：一轮左滑总共画出的帧 **478 → 582**（多两成），
画面间隔落在「正好两次刷新」上的比例 53.8% → 61.7%；手指移动期真正出现的不同画面，
十一格里八格上升，其中一格（矮卡来回滑）从 61 帧升到 72 帧、间隔九成位 47.5 → 33.8 毫秒。

### 顺带修正一个说法

之前说「左滑远低于 60 帧」，这里面有一半是统计口径造成的：测试动作末尾都有一段手指按住不动，
而手指不动时不出新画面是对的——快拖真正甩动的那 180 毫秒实际上是满帧的。剩下的问题是节奏不齐，
不是帧数不够，而节奏正是这一版修的东西。

### 另外

- 同一批里试过的两项改动，因为量不出收益被整段删掉：一项是把「等上一帧画完」挪到两拍之间
  （实测只要 0.02 毫秒，本来就不占时间），另一项是给上屏时刻设下限（魅族的系统合成器并不
  按这个下限推迟画面）。宁可不留，也不留「理论上更快」的代码。
- 左滑的测试从这一版起在四种卡片上各做一遍：一行字的矮卡、满屏文字的高卡、十一条的清单卡、
  带图片的卡。它们的粒子数最多差 **6.8 倍**，清单卡的粒子比整屏弹窗还多——此前所有结论都
  建立在最轻的那一种上。
- 补齐了华为这台在前两批欠下的验证：着色器全部正常编译链接，两条命令流的高低优先级
  在它的 GPU 上同样拿到了。
