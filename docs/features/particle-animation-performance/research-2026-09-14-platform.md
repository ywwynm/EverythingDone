# 平台调研摘要（2026-09-14）

两份完整报告由 Opus 调研员产出，原文与全部来源见 [research-2026-09-14-platform-full.md](research-2026-09-14-platform-full.md)（Android 图形栈：上下文优先级、SurfaceView、刷新率、RenderThread 动画、Choreographer）与 [research-2026-09-14-gles-full.md](research-2026-09-14-gles-full.md)（GLES 计算：dispatch/屏障开销、数值确定性、零拷贝纹理、多上下文同步、Jacobi 分块）。本文只保留对方案有直接影响的结论，并标注对应的方案条目。取证限制：Qualcomm 文档站是 JS 渲染，Adreno 闭源驱动的行为多为内核源码与工程实践推断；`registry.khronos.org` 与 `developer.android.com/reference` 改用 GitHub 镜像与 AOSP 源码核对。

## 对方案有决定性影响的结论

1. **`View.animate()` 不在 RenderThread 上跑。** `ViewPropertyAnimatorRT` 在 API 29 之前已从 AOSP 删除，当前实现是主线程 `ValueAnimator`。`ViewAnimationUtils.createCircularReveal` 走 `RevealAnimator extends RenderNodeAnimator`，在 RenderThread 上按自己的 vsync 推进；系统 `RippleDrawable` 两代实现都用 `CanvasProperty` + `RenderNodeAnimator`，连 startDelay 都由 RenderThread 计时。公开 API 里没有能在 RenderThread 上驱动任意 Drawable 透明度的机制。→ 方案 1.1 改写：自绘渐变涟漪做不到"完全 RenderThread 驱动"，半径可以，透明度不行。
2. **RenderThread 动画只免疫"开始之后"的主线程停顿。** 动画必须先 start 并完成一次 UI 线程 sync 才进入 RenderThread；结束回调仍回主线程。→ 涟漪问题的根本解法仍是把点击后的主线程重活挪走（方案 1.6、1.8）。
3. **`ViewGroupOverlay.add(View)` 不触发宿主 `requestLayout`，也不自动布局**：`OverlayViewGroup.onLayout` 为空实现，加入的 View 需自行 `measure` + `layout`；画在宿主全部子 View 之上；不接收输入。→ 方案 1.6 用它挂载暗层与粒子层，避免整窗重布局。
4. **`preferredRefreshRate` 按文档等价于 `Surface.setFrameRate(rate, DEFAULT, ONLY_IF_SEAMLESS)`**，本身不应触发非无缝模式切换。因此现在观察到的 50–70 ms 长帧更可能来自 `Window.setAttributes` 引发的两个窗口完整 relayout 与表面重配置，或是无缝切换瞬间 vsync 周期改变。这两条都是推断，需要阶段 0 实测区分。SurfaceFlinger 对 60 Hz 投票优先选择倍数刷新率，120 Hz 面板上会留在 120；官方要求这种情况下逐帧提供呈现时间戳以避免 judder。`FRAME_RATE_COMPATIBILITY_FIXED_SOURCE` 只给视频用。→ 方案 1.2：去掉窗口属性投票，改在自己的 Surface 上 `setFrameRate(60, DEFAULT, ONLY_IF_SEAMLESS)` 一次，并保留 `eglPresentationTimeANDROID`。
5. **上下文优先级可用但有条件。** `EGL_IMG_context_priority` 是提示不是契约，创建后必须回读实际值；HWUI 的 RenderThread 对普通应用不传优先级属性，落在默认 MEDIUM，所以 LOW 的预计算上下文确有一级差；Chromium 的用法正是"慢而可延迟的 GL 工作放 LOW"。Adreno（KGSL）按上下文优先级分 ring，与进程无关；能查证的抢占粒度对 compute 只到**提交边界**，所以预计算必须按批 `glFlush` 成多次提交（现有 `PreparationQueue` 已按批 flush）。HIGH 不要用（Mali 要 `CAP_SYS_NICE`，Chromium 明确劝退）。跨上下文 fence：生产端 `glMemoryBarrier` → `glFenceSync` → `glFlush` 一条都不能少，消费端用 `glWaitSync`；两上下文用同一 EGLConfig、各配专用线程。→ 方案 1.3。
6. **SurfaceView 优于 TextureView 有官方原文**：TextureView 内容要在内部再拷贝一次、每个可见像素合成两次，官方在 API 24+ 推荐 SurfaceView。`setZOrderOnTop(true)` 时 SurfaceView 根本不打洞（`isAboveParent()` 恒真，`clearSurfaceViewPort` 不执行），"透明洞闪一帧"在这个配置下不成立；必须显式 `setFormat(TRANSLUCENT)`，默认是 RGB_565。表面被 parent 在 Activity 窗口的 layer 内，仍在 Dialog 等独立窗口之下——这正是现有交接顺序需要的（粒子层先在弹窗窗口之下就位，再撤弹窗）。**同一窗口内两个都 `setZOrderOnTop` 的 SurfaceView 相对顺序未定义。** API 34 起 SurfaceView 支持任意 `setAlpha`。→ 方案 1.4：一个窗口只用一个粒子 Surface，所有并发会话在同一 Surface 里合成。
7. **帧真正上屏的判定**：只有 `EGL_ANDROID_get_frame_timestamps` 的 `EGL_DISPLAY_PRESENT_TIME_ANDROID` 直达扫出时刻，需先 `eglSurfaceAttrib(EGL_TIMESTAMPS_ANDROID)` 打开并用 `eglGetFrameTimestampSupportedANDROID` 探测，可能返回 PENDING 需轮询；TextureView 的生产者由 HWUI 消费，present 类时间戳大概率无效。`SurfaceControl.Transaction.addTransactionCompletedListener` 要 API 35 且 latch ≠ present；`FrameMetrics` 拿不到 present 时间。→ 方案 1.4 的交接判定。
8. **Choreographer**：`frameTimeNanos` 迟到超过一个 vsync 周期就被重新吸附到最近的 vsync 边界（120 Hz 上是 8.33 ms），靠差值判断"隔了几拍"会错相位；NDK 文档明确"动画时钟应当用 expected presentation time 推进，不用 frameTimeNanos"；API 33 的 `postVsyncCallback` 给出 frame timelines，但 Java 侧没有把 vsyncId 交回 SurfaceFlinger 的公开接口，呈现时刻只能靠 `eglPresentationTimeANDROID` 钉住。`eglSwapBuffers` 在队列满时阻塞，若 Choreographer 挂在 GL 线程自己的 Looper 上，阻塞会推迟回调；反之挂在主线程则受主线程停顿影响。Android 官方文档没有关于 `glFinish` 的明文立场，Arm 与三星文档明确反对管线排空类调用。→ 方案 1.8：粒子时钟脱离主线程、用呈现时间推进、去掉 `glFinish`。
9. **dispatch/屏障开销**：Qualcomm 原文"compute shaders require kernel output to be written to memory before the next kernel can begin execute"；开源 Adreno 驱动里 `glMemoryBarrier` 任何 bit 组合都是整批 flush，减少 bit 没有意义；Adreno 750 上一次同步后重新提交的额外开销约 50–100 µs（HeteroLLM 论文），960 次即 48–96 ms，而本项目反推约 180–240 µs/次，说明还有别的成本（DVFS 未爬满频是嫌疑之一）。`EXT_disjoint_timer_query` 逐 dispatch 求和不含间隙，与墙钟差值正是空转量；必须检查 `GPU_DISJOINT_EXT`。→ 阶段 0 的判别实验：把 960 次积分改成无依赖不发屏障的空转版本只测墙钟。
10. **数值确定性**：GLSL ES 3.10 的 `precise` 来自 `GL_EXT_gpu_shader5`（ES 3.2 核心），要 `#extension` 声明并先查支持；它逐变量禁止收缩与重排，但 GLES 没有关闭 fast-math 的总开关。SPIRV-Tools 的案例证明 fma 收缩会被工具链自动施加且在 Adreno 上走不同硬件路径。SSBO 往返本身精确，差异来自往返被移除后编译器获得的跨步优化自由度。→ 方案 2.5 改为先试"合并 dispatch 但保留每步 SSBO 往返（`volatile`）"争取逐位相同，不成再用 `precise` + 误差门禁（建议用 NVIDIA ꟻLIP 做视觉差异评估，门禁显式挡 NaN）。
11. **Jacobi 分块**：Adreno / Mali / Xclipse 的 shared memory 上限都是 32 KB（Xclipse 960 为 64 KB），分配按 16 KB 设防；当前 16×16 tile + 8 边带的冗余率 2.15×，只用了上限的一小部分，扩大 tile 能减少工作组数与冗余，增加每次 dispatch 的迭代数才能减少 dispatch 数；k=8 处在文献的合理区间。**Mali 没有片上 shared memory，Arm 明确建议不要把 global 拷进 shared**，分块 Jacobi 的前提在 Mali 上不成立，需要单独参数甚至保留原路径。→ 方案 2.2 按设备分支。
12. **零拷贝与像素格式**：`Bitmap.copyPixelsToBuffer` 对 ARGB_8888 输出的内存字节就是 R,G,B,A，可直接 `glTexImage2D(GL_RGBA, GL_UNSIGNED_BYTE)`，注意 `rewind()`、内容为预乘 alpha。AHardwareBuffer → EGLImage 零拷贝必须经 JNI，且有 sRGB 与 mipmap 的坑。→ 方案 3.2：像素只拷一次、免转换上传；EGLImage 列入后续事项。

## 与既有记录的关系

- 现有 `ParticleWindowFrameRate` 的 60 Hz 投票依据是 2026-09-13 的 trace 判读，本次调研没有找到当前 AOSP 中名为 `ActiveModeFps` 的计数器，且 `preferredRefreshRate` 文档口径是无缝切换；两者需要在阶段 0 用同一台设备重新对照。
- 现有"最多两批在途、每批 flush"的有界队列恰好满足"按提交边界抢占"的前提，优先级方案建立在它之上，不推翻它。
- 现有 61 帧散列对照工具继续作为 G0 验收；G1 新增 FLIP 与并排视频。
