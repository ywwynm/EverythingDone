「第二批范围与时间基准裁定」。口径沿用 [phase0-baseline-2026-09-14.md](phase0-baseline-2026-09-14.md)

（OPD2515 / Adreno 829，SM-S9180 / Adreno 740）。

**一句话结论**：一窗一 Surface 的 SurfaceView + 常驻 GL 线程与上下文全部落地，G0 逐位一致

非零画面仍比阶段 0 慢**（OPPO 132–156 对 80–128 ms，三星 201–228 对 114 ms），这一项按

## 1. G0：GPU 输出逐位不变

`ParticleTrajectoryCheck` 在第一批两条对照（消散 61 帧、出现 37 帧）之外**新增一条**，
针对第二批最大的风险——「一个上下文里多个会话共用同一批程序对象、累积纹理与历史缓冲池，
uniform 只要漏重设一项，交错播放就会画错」：

- **正向交错**：两个会话逐帧轮流画同一输入的 0–60 帧，两边每一帧都要与单独跑时逐位相同。
- **出现 × 消散交错**：一个逆向会话按批预计算，每批之间夹一帧正向绘制；预计算完成后
  两个会话逐帧轮流出画。这正是真实的并发形态（上一个弹窗消散 + 下一个弹窗出现）。

| 设备 | 消散 61 帧 | 出现 37 帧 | 交错对照 | 上传字节 |
| --- | --- | --- | --- | --- |
| OPD2515 / Adreno 829 | 0 差异 ×2 | 0 差异 ×2 | 0 差异 ×2 | 一致 |
| SM-S9180 / Adreno 740 | 0 差异 ×2 | 0 差异 ×2 | 0 差异 ×2 | 一致 |

绝对散列已写进 `gpu-parity-*.json` 的 `forwardHashes` / `reverseHashes`，后续批次可以直接跨版本比。

**跨版本对照的口径说明**：本次没有装回第一批的包逐帧比散列（那需要额外的安装与运行轮次）。
证据链是：①`shared/particle-dismiss/` 与 `app/src/main/assets/particle-playback/` 一个字节都没改；
②上传字节由 JVM 测试证明与旧路径逐字节相同；③本批的三条设备端对照全部零差异。

## 3. 首帧「真的上屏了」用的是哪条口径

**两台设备都走 `EGL_ANDROID_get_frame_timestamps`**：`eglSurfaceAttrib(EGL_TIMESTAMPS_ANDROID)`
打开后 `eglGetFrameTimestampSupportedANDROID(EGL_DISPLAY_PRESENT_TIME_ANDROID)` 返回真
（日志 `粒子 Surface 就绪 帧时间戳=true`）。Java 侧没有这三个入口的绑定，走 JNI
（`particle_frame_timestamps.cpp`，`eglGetProcAddress` 动态取，取不到就整体报不可用）。

判定规则：按提交顺序逐帧问 `EGL_DISPLAY_PRESENT_TIME_ANDROID`，PENDING 就继续等并保序
（否则暗层会先于粒子首帧启动），拿到时刻或驱动报 INVALID 就放行；单帧 250 ms 硬上限兜底。
**探测不到时退回保守判定：缓冲已入队 + 下一次 vsync**（`ParticleWindowSurface.shouldRelease`，
有 JVM 测试）。撤真实弹窗、撤快照、启动暗层仍挂在这一刻；出现动画的末帧留在 Surface 上，
直到宿主确认真实面板上屏才让会话退出。

## 6. 左滑：慢拖改善、快拖未达标

「识别左滑之后的首个非零画面」（阶段 0 认定的关键延迟）：

| 设备 | 慢拖 1.2 s（阶段 0） | 慢拖（第二批） | 快拖 180 ms（阶段 0） | 快拖（第二批） |
| --- | --- | --- | --- | --- |
| OPPO | 50.7 / 51.1 / 52.1 | **29.7 / 30.6** | 110.8 / 127.7 / 79.9 | **132.3 / 155.7** |
| 三星 | 51.2 / 51.6 / 53.2 | **115.6 / 118.6** | 113.8 / 115.1 / 114.0 | **201.0 / 227.8** |

- **慢拖在 OPPO 上达标**：按下阶段先备 6 档（`GESTURE_PREROLL`）之后，识别左滑时需要的档位
  通常已经在手上，首帧落在一个节拍里。
- **快拖两台都没达标，三星连慢拖也退化**。原因是快拖在**材料还没建好**的时候就被识别成左滑
  （触发阈值约 24 dp，180 ms 的手势里 20–30 ms 就越过了），此时预备根本还没开始；
  等材料就绪（OPPO 37–53 ms、三星 47–56 ms）时手指已经拖过 20% 以上，第一帧必须先阻塞补齐
  `ceil(position)` 档历史。三星单档约 7 ms，补 12 档就是 80 ms 以上。
- 帧距本身是好的：慢拖两台中位都是 16.67 ms（OPPO P90 也是 16.7，阶段 0 是 32.3–33.6）；
  快拖 180 ms 的移动期内 OPPO 出 11 帧、三星 8 帧，与阶段 0 的三星 8 帧持平。
- **中途发现并修掉的一个真缺陷**：节拍的启停原本跟着「这一拍要不要出帧」走，手指停一下节拍就断，
  重启要重新登记 Choreographer、等下一次 vsync。三星慢拖整段掉到 30 fps、快拖在补档结束后节拍
  再没起来过（一次左滑只提交 2–3 帧）。改成「节拍是否继续跑」与「这一拍出不出帧」分开判定
  （`ParticleSession.needsBeat` / `wantsFrame`）后恢复正常。这条占掉了本批两次补跑里的一次。

按「整批最多补两次」的规则，快拖这一项**停在这里并写入 followups**，不再继续调。

## 8. 功能回归

### 8.1 九种动画层形态 + 出现中快速关闭 + 准备中退出（两台各一轮）

`verify_dialog_coverage.py` + `ParticleCoverageProbeActivity`，11 种形态在两台上全部通过
（脚本内含断言：必须真的创建出现层与消散层、GPU 日志出现完成、窗口最终移除）：
plain / transparent / hidden-surface / texture / surface / panel / floating /
**surface-quick（准备中快速关闭）** / **finish-during-capture（抓图期间 finish）** /
surface-handoff / audio-play-handoff。

- surface-quick：出现层在 123 ms（OPPO）/ 193 ms（三星）内释放，消散照常播完并移除，无残留。
- floating（透明宿主）：宿主等动画结束 `hostWaitMs` 2091（OPPO）/ 1480（三星）。
- finish-during-capture：`hostWaitMs` 2120 / 1539。

### 8.3 弹窗四条关闭路径

`verify_repeated_appearance.py`，每条路径 3 个循环、真实系统输入，两台设备各一轮：

18.8–25.2 ms（三星）。

三星上出现层偶尔 `committed` 比 `submitted` 少 1–2 帧：宿主确认真实面板上屏后立刻撤会话，
最后一两帧的呈现回调不再派发（会话已退出）。这是记账差异，不影响画面——末帧本来就等于真实面板。

### 8.4 左滑

- **按住跨过原点再拉回不崩**：两台各 2 轮，进程 pid 不变、记事仍在、记事数不变。
- **60% → 20% → 60% 同相位**：`sameProgressMaxDifference` = **0**（两台）。第一批同一指标是
  约 0.7% 的像素不同、最大通道差 237，改动前约 1.0%。**本批把它做成了严格逐像素可重入**，
  followups 里那条可以关掉。同一次停顿内两张图也逐像素相同（`heldStableMaxDifference` = 0）。
- **回原点抬手后卡片复原**：`afterMeanDifference` 0.0024（OPPO）/ 0.0003（三星），
  即「左滑取消末帧等于卡片本身」成立。

- **三星上 `ps` 里有 6 条名为 `ParticleGl` 的线程**：Adreno 驱动在我们的 GL 线程上首次建上下文时
  会派生若干工作线程并继承父线程名。冷启动后只有 1 条，重度使用后稳定在 6 条，**不随动画次数增长**，
  OPPO 上一条都没有。
- Graphics 内存首次动画后上一个台阶就不再增长：OPPO +28.7 MB。这是 D4 的常驻代价——
  全屏 RGBA16F 累积纹理（2520×1680 约 33.9 MB）、两张流场三维纹理、历史缓冲池。
  `App.onTrimMemory` / `onLowMemory` 会把历史缓冲池释放掉（上下文、程序与常驻纹理不动）。

## 9. 实现上的几条记录

- **共享程序 ⇒ 共享 uniform**。一个上下文里所有会话用同一批程序对象，uniform 也就只有一份；
  凡是只在 `prepare` / `PeelPressure` 构造时设过一次的值，切换会话时都必须整套重设
  （`ParticleMicroflakeRenderer.applyUniforms`，由 `activate()` 按「上一个用它的是不是我」触发）。
  这是本批最大的正确性风险，用第 1 节的交错对照守住。
- **合成路径把默认帧缓冲的清空交给宿主窗口**：窗口每拍清一次，各会话按创建顺序叠画，
  resolve 输出是预乘 alpha，用 `ONE, ONE_MINUS_SRC_ALPHA` 叠加；目标清成全零时
  `src + 0×(1-a) == src`，与改动前「不开混合直接覆写」逐位相同。离屏对照与预热仍自己清屏。
- **准备与预计算不需要窗口 Surface**：常驻线程上始终绑着一个 1×1 的 pbuffer，
  SurfaceView 的表面还没创建出来时预计算就已经在跑（实测日志里「出现轨迹准备」经常早于
  「粒子 Surface 就绪」）。驱动没有 WINDOW|PBUFFER 组合配置时退回只要 WINDOW + 无表面绑定。
- **粒子 SurfaceView 常驻宿主 DecorView**，首次需要时创建（弹窗关闭请求、出现请求、卡片按下
  三个入口都会提前建），直到 Activity 销毁或配置变化。`ParticleSnapshot` 的遍历要显式跳过它，
  否则它会被当成「窗口下方的独立 Surface」去 PixelCopy，在还没提交过缓冲时反复
  `ERROR_SOURCE_NO_DATA`，把整次捕获拖到超时。
- **`ParticleWindowSurface` 的登记表值必须是弱引用**：它强引用 Activity，直接放进 WeakHashMap
  会让「值经由静态根强引用键」，条目永远回收不掉。
- **1.7 的条件性让出在 GL 侧不再适用**：预计算与播放现在是同一条线程，只能保持 `THREAD_PRIORITY_DISPLAY`。
  材料线程那一条判定（有反馈/播放在跑时让出）保留。
