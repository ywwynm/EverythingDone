## 1 取证：左滑那一拍到底卡在哪

第二批之后只有「提交成功的那些帧」，看不到**没提交的那些拍**。本批加了一条节拍级取证
（`ParticleBeatTrace`，release 恒零开销），把五件事逐条记下来：节拍线程收到的每一次 vsync
（含**没有出拍**的那些）、pump 的进入与准备用时、`needsFrame` 判否时每一层卡在哪条判定上、
合成的等栅栏 / 画 / swap 三段、以及每一帧的驱动呈现时刻。汇总脚本
`analyze_beats.py <序列号> <run 前缀> [场景键…]`。

魅族一轮（`b3mbefore`，三个左滑场景）读出来的结论，逐条对着任务书里的假设：

| 假设 | 实测 | 裁定 |
| --- | --- | --- |
| 节拍漏拍 | 节拍线程每个 vsync 都收到，出拍间隔 88–115 次全是一拍 | **否** |
| `awaitFence` 把提交串成一条链 | 等栅栏 **p50 0.02 / p90 0.03 / max 0.07 ms**（两台一致） | **否** |
| pump 赶不上 | 「目标 → 进入合成」p50 0.9–2.1 ms；准备循环 p50 **0.00 ms** | **否** |
| `wantsFrame` 判否 | 出拍了没画的 20–39 次，**100% 是「相位没变」**（没有一次是阶段 / 可见性 / 渲染器） | 见第 3 节 |
| 手势路径与 ItemTouchHelper 互等 | 没有任何一拍卡在阶段或可见性上 | **否** |
| 节拍与面板相位不对 | **成立，见下** | **是** |

### 1.1 根因：自由计时的节拍相对面板持续漂移

魅族触摸期，节拍线程收到的 vsync 间隔实测 **8.276 ms（120.8 Hz）** 或 **16.53–16.55 ms**
（同一次左滑里两种间隔会交替出现，`tickGap` 直方图 101 : 83）。而第二批之前的节拍是
「起点 + k × **16 666 666** ns」的自由计时——**每拍比真实的两个 vsync 多 0.117 ms**。

逐帧看得非常干净：同一段里「真实呈现时刻 − 本拍目标」每帧**递减 0.11 ms**
（25.54 → 25.47 → … → 13.97），一路减到跨过一个显示周期就跳一档，呈现间隔于是在
**8.3 / 16.6 / 24.8 / 33.1 ms** 之间来回。把参照换成**真实 vsync** 之后更直接：同一批帧的
「呈现时刻 − 本拍 vsync」散在 **1.14 / 2.14 / 3.14 / 3.90 个显示周期**四档上。

三星那一轮是这条根因最好的旁证：它的面板周期是 **8.332 / 16.602 / 16.667 ms**，与我们
写死的 16.6667 几乎相等，**于是几乎不漂**——慢拖的呈现间隔 54/61 都是一拍（88.5%），
而同一时刻魅族只有 43/59（72.9%）。**同一份代码在两台上的差别就是面板周期差的那 0.11 ms。**

### 1.2 修法

`ParticleClock` 改成：

1. **目标就是本次 vsync 的时刻**（不再累加固定间隔），所以永远锚在真实 vsync 上、不积累误差；
2. **出不出拍按「距上一拍够不够久」判**，门限 `16.667 ms − 半个 vsync − 0.5 ms`。
   这条比「按 vsync 计数分频」稳：这条线程收到的 vsync 本身就不规律，按计数分频会跟着乱
   （第一版就是这么写的，实测把左滑「被卡住的帧」占比从 3.9% 推到 12.7%，见第 6 节）。
   门限的语义是「离 60 Hz 最近、且不低于它的那一档」：120 Hz 出 60、144 Hz 出 72、
   90 Hz 出 90、60 Hz 出 60。
3. **「一拍多长」改成量出来的值**（`outputPeriodNanos` = 节拍间隔自己的滑动均值），
   预算截止时间（`ParticleGl.workDeadline`）按它倒推，不再按 16.667 算。

**目标不取系统给的「预期呈现时刻」**：魅族上 `FrameData.preferredFrameTimeline` 给的是
**vsync + 26.0 ms**（入队截止 vsync + 13.7 ms），而我们实际达到的是 vsync + 17.7 ms——
按它写目标等于主动多等一个显示周期。这一项在 API 33+ 用 `postVsyncCallback` 取数据、
API 32 及以下退回 `postFrameCallback`（华为 Android 12 走的就是后者，相位锁定照常工作）。

## 3 「左滑远低于 60 fps」这个前提要修正

三条，按证据强弱排：

1. **「呈现/应有」把停住的那一段也算进了分母。** 左滑三格的注入剖面末尾都有停住段
   （快拖 600 ms、慢拖 300 ms、来回拖最后 400 ms），手指不动时 `wantsFrame` 判否是**对的**，
   屏幕上本来就没有新内容。快拖尤其夸张：甩动只有 180 ms（约 11 拍），实测就出 11 帧，
   **那一段其实是满帧的**，而整格的「呈现/应有」只有 0.31–0.45，差的全是后面那 600 ms。
2. **出拍没画的那些拍，100% 是「相位没变」。** 取证里 20–39 次判否没有一次卡在阶段、
   可见性或渲染器上。相位不变的直接原因是**输入事件的到达节奏**：注入器实测约
   **54–61 Hz**（`MOVE` 间隔 p50 16.6 ms、p90 19–25 ms、max 40 ms），与我们 60 Hz 的节拍
   是两个独立的同频时钟，相位一漂就会有整拍看不到新位置。真手指在 120 Hz 面板上是按面板
   节拍投递的，这一格**有一部分是量法造成的**，但也说明输入流一旦打嗝我们就会丢一拍。
3. **真正剩下的缺陷是节奏不齐，不是帧率低。** 均值接近 60 而间隔在 8.3 / 16.6 / 24.8 / 33.1
   之间跳，看起来就是一直在抖——这正是第 1 节修掉的那一条。

## 6 撤掉的两项（都是被取证证伪的）

**做出来、量过、删掉**，按本专项「没有可测收益就不留」的纪律：

1. **「上一帧的栅栏挪到两拍之间轮询」。** 假设是「在途只留一帧把 CPU 提交、GPU、合成串成
   一条链」。取证直接否掉：`awaitFence` 的实测等待是 **0.02 ms**（两台、三个左滑场景的
   p50/p90/max 全在 0.07 ms 以内）。整段删除。
2. **「呈现时刻下限」**（把 `eglPresentationTimeANDROID` 写成「本拍 vsync + 一个输出周期
   − 4 ms」，想挡住「早到一个显示周期」的那一档）。**魅族上这个下限根本不生效**：下限写在
   vsync + 12.6 ms，实测仍有 **28/69 帧**在 vsync + 8.3 ms 就上屏了。这台的 SurfaceFlinger
   不按 `desiredPresentTime` 推迟我们的缓冲。既然量不出效果、又可能在别的机型上白白多等一个
   周期，整段撤掉。

另有一处**自己写出来又自己查掉**的缺陷，教训值得留：相位锁定的第一版是「按 vsync **计数**
分频」（每 `stride` 个 vsync 出一拍，`stride` 由 vsync 周期的滑动均值推算）。
**这条线程收到的 vsync 本身不规律**（同一次左滑里 8.28 与 16.55 交替，直方图 101 : 83），
推算出来的周期在 8.3 与 16.6 之间摆，于是预算截止时间一会儿 10 ms 一会儿 2 ms，预读被饿死——
实测左滑「被卡住的帧」占比从 3.9% 涨到 **12.7%**。改成「按距上一拍的时长判 + 量节拍间隔本身」
之后恢复。**凡是从一个不稳定的观测量推算出控制参数的地方，都要先问它稳不稳。**

## 7 任务二：两个待用户定夺的 V 级选项（只出图与数字，默认值未改）

受控口径：同一张快照、同一个种子、同一个触点、同一条离屏路径，**只切被测的那一个值**；
切换是**线程局部**的（`ParticlePerfTuning.withOptions`），不会碰到同一时刻常驻 GL 线程上的
创建页提前预算。工具 `ParticleOptionFrames`（debug），驱动 `device_per_frame.py --option-frames`。

对照素材是**附件弹窗的消散**（正向路径同时有现场积分与压力更新，两个选项的代价都体现得出来）：
魅族快照 980×965、华为 651×641——两台在材料的归一空间里都是 **525×517**，
所以**现状的微片尺寸两台相同**。

### 7.1 先把「现状是多大」算清楚

材料在「720 逻辑像素 = 384 dp」的归一空间里建，一个 dp 是 1.875 个单位。这块弹窗上
`max_cells` 那条上限**没有生效**，真正起作用的是 `rules.properties` 里的下限 `cell=1.65`
——也就是**现状的微片是 0.88 dp**，不是方案里写的 2.2 dp（2.2 dp 是整屏那一档的量级）。
所以 E12 在弹窗上的效果比方案预计的大得多：2.2 dp 是 **6.2 倍**的减量。
