# 粒子转场期间触摸波纹冻结：分析与候选方案（2026-10-12）

## 范围与证据边界

**后续进展：**用户已授权“细化方案后，改代码”，并更正具体触发为 Dialog 取消／确认按钮上的波纹被保留在消散粒子中。三星实测源弹窗材料确实含有一块蓝色自绘波纹，真实按钮状态及其窗口图像仍自然淡出；普通页面对照在三星、魅族未复现整段冻结。以下“只分析”是最初阶段记录，不能作为当前未实施的状态。另在 Doing 整页固定场景复现系统波纹停留超过 2.7 秒，正在实施材料过滤位置与有界续帧刷新两处局部修正。

用户反馈上一轮主要问题基本解决，仍能看到点击按钮打开 Dialog 时的 ripple 定格，并询问是否与 DoingActivity 退出残影有关。本轮按要求只分析：未修改实现、编译、发布或操作设备。以下区分源码可以确认的缺口与尚需逐帧复现的实际归因，不将其表述为已经修复。

延续要求：保留 SurfaceView、动态背景、原有控件外观与阴影，保留“添加附件 → 录音”的出现／消散重叠，不通过给所有打开操作增加等待来掩盖问题。

用户随后确认两类入口都明显：旧 Dialog 关闭并打开新 Dialog，以及从页面按钮打开普通 Dialog、原页面仍留在下方。这排除了只处理旧 Dialog 材料即可覆盖全部反馈的判断，但不能据此直接认定两个独立故障。后续应优先选普通页面打开普通 Dialog 的入口，确认该按钮是否经过离屏转移，分辨真实反馈推进停顿、绘制更新缺失与已生成图像未显示；Doing 的续帧缺口不能自动推广成普通 Activity 的根因。静态材料过滤的已知缺口仍需独立验证。

## 三项按优先级排列的假设

### 1. 排除波纹的同步保护没有覆盖实际的异步捕获

这是可以从调用顺序直接确认的实现缺口，但是否覆盖用户观察的全部入口尚未验证。

- `ParticleTouchFeedback.withoutRipple()` 临时设置 `GradientRippleDrawable.omitFromSnapshot`，在 `finally` 中立即恢复。它只负责一次同步调用栈。
- `ParticleDismissController.startContent()` 在这个保护内部调用 `shoot()`；有窗口投影时，`shoot()` 先异步执行 `ParticleDialogShadow.prepare()`，在回调里才捕获内容。
- `ParticleHardwareSnapshot.capture()` 遇到统一方案中的独立 Surface 时，还会先异步执行 `ParticleSurfaceFrames.capture()`，回调后才记录普通 View 内容。
- 因此实际 `view.draw()`／`ParticleViewCaptureTree.record()` 可以发生在保护已经恢复之后。原本为“干净材料”准备的截图仍可能包含当时正在淡出的波纹。
- 此后即使真实 ripple 正常淡出、消散会话等待其结束，之前已经生成的粒子材料也不会随之更新。这种情况视觉上表现为一块旧波纹再次出现或在粒子上保持不变，不能只检查动画器有没有继续运行。
- 当前扫描只识别自绘 `GradientRippleDrawable`，不识别系统 `RippleDrawable`。出现会话不等待背景按钮反馈是有意设计，不能改成全部串行等待。

可证伪检查：在相同触点和种子下，对有／无异步阴影准备、独立 Surface 的材料截图取证；只把过滤移到实际记录调用栈后，静态材料中的波纹残留应消失，而真实按钮波纹时间曲线不变。如果仅背景按钮冻结、粒子材料没有波纹，此项不足以解释该样本。

### 2. Doing 整页捕获丢弃了没有 UI 捕获请求的原生 ripple 续帧

- Android 36 本地 SDK 的 `RippleForeground` 使用硬件属性时可在 RenderThread 上动画；这时属性变化不必每次 `invalidateSelf()`，不能假设每一帧都有宿主 `onPreDraw`。
- `ParticleDoingGlScene` 正常捕获由 `onPreDraw` 请求。消费者会正确及时归还多余图像，但主线程收到图像后有 `!busy` 分支，直接回收没有显式捕获请求的图像。
- 所以“系统已经生成新的波纹帧”与“GL 页面显示了这帧”不是同一件事。单独依赖宿主下一次绘制，可能使波纹只在计时、输入或其它动画触发捕获时才跳到较新状态。
- 是否在目标设备出现这种时序，以及渲染器间共享节点对具体按钮的影响，仍需独立观察；源码缺口不等于已经量出实际停顿时长。

可证伪检查：在 Doing 的静止区域触发系统原生 ripple，分别记录离屏图像序号和最终 GL 显示序号；若前者连续、后者只在显式捕获时更新，即支持本假设。用自绘 ripple 作同页面对照，避免把全部波纹都归到 RenderThread。

### 3. 前景局部捕获对系统 ripple 的绘制与失效假设不完整

- 首页被转移到 GL 的顶栏／FAB 等使用 `ParticleForegroundSurface`。姿态不变且 `source.isDirty == false` 时不再捕获，小块内容通过软件 Canvas 生成、阴影仍硬件绘制。
- 这对 UI 动画器持续失效的自绘波纹与原生硬件波纹不是同一个条件。Android 36 的 `RippleDrawable` 还包含不支持软件 Canvas 的 patterned 分支，不能假设软件记录所有系统波纹都等价。
- 这条只适用于确实经过前景转移的入口，不能据此声称普通 Dialog 的整个 Activity 背景都被截图。源码中 `ParticleLiveBackdrop` 主要用于卡片交接；一般 Dialog 下方的 Activity 仍可走原生窗口绘制。

可证伪检查：同一按钮分别在原生展示、前景 GL 转移、Doing 整页路径观察，并记录 drawable 类型与有效失效信号。只在前景路径失败、而粒子材料干净时才进入这项修正。

## 与旧 DoingActivity 残影的关系

见 [退出回归记录](doing-scene-exit-2026-10-12.md)。旧问题实测为 ripple 自动续帧遇到 ImageReader 消费依赖主线程，主线程又等待共享 RenderThread，造成约 8 秒队列阻塞；另有提前清空整页与调试报告同步解析的问题。

本次视觉冻结可能涉及同一类自动续帧，但不能直接认定旧死锁复发。旧修正的原则仍必须保留：工作线程及时归还多余图像；GPU 使用完成前不释放显示帧；退出先停止生产；窗口分离前不提前清空页面。动态显示与及时丢弃过期帧需要同时满足。

平台文档说明 `acquireLatestImage()` 需要至少两个空余获取名额才能丢弃旧图像，未释放的图像可耗尽队列：[ImageReader](https://developer.android.com/reference/android/media/ImageReader#acquireLatestImage())。这只是队列约束，不构成目标设备画面正确的证据。

## 推荐实施顺序（分析阶段；下文记录实施进度）

1. **把材料捕获与动态展示的波纹策略分开。** 静态粒子材料排除瞬态波纹；背景和前景的持续捕获包含正在播放的波纹。不能把所有捕获统一设为“无波纹”，否则背景反馈会直接消失。
2. **首先修同步保护的作用位置。** 异步阴影／Surface 准备全部完成后，只在真正记录内容及提交对应绘制树的同步区间过滤自绘波纹；退出该区间立即恢复。不能把真实 Drawable 的隐藏状态保持到异步 GPU 读回完成，否则用户会看到真实反馈被提前截断。恢复需保存先前状态并支持嵌套，不用单一布尔默认恢复为 false；处理显示列表失效，确保之后真实帧恢复绘制波纹。
3. **单独补齐整页的自动续帧消费。** 当前场景稳定时，允许原生 ripple 产生的新图像只刷新页面纹理；首帧、卡片首尾切换仍以对应显式提交确认推进，不能把任意迟到图像当作新布局完成。保持有界缓冲、合并旧帧、GPU 释放后归还与窗口退出顺序；不要简单移除 `!busy` 判定，避免旧图像推动错误的交接状态。
4. **按证据处理局部原生波纹。** 先验证已有原生硬件帧能否在正确时间被显示；如局部前景仍缺失，再考虑只为活动按钮保留可持续更新的硬件内容，而不是重录整页或把所有按钮改成另一种自绘 ripple。系统波纹进入静态材料时，需要按实际 background／content／foreground 结构保留底色、选中态、蒙版和裁剪；公共 API 没有提供通用的“保留当前运行波纹、只关闭截图波纹”开关，不能先承诺任意原生控件零成本过滤。

这套方向不要求更换 SurfaceView、改变粒子轨迹或减少粒子数量。第 2 步预计是局部修正；第 3 步涉及生产帧与交接帧的区分，复杂度较高，需要专项回归。无法在未测量前承诺帧率和响应时延完全不变。

## 不作为默认方案的选项

- 所有 Dialog 都等 ripple 结束再打开：会给原本可重叠的流程增加可感知等待，影响交互延迟；不能用固定毫秒值猜测结束。
- `jumpToCurrentState()` 或清除真实 pressed 状态：会跳过原生反馈、可能改变按下行为，而非让它自然播放。[RippleDrawable 文档](https://developer.android.com/reference/android/graphics/drawable/RippleDrawable#jumpToCurrentState())明确其跳过正在运行的状态动画。
- 为 ripple 每帧重建整张页面或重新生成粒子材料：扩大重录／上传成本；材料还参与粒子提取与预计算，替换它不是单纯刷新一个颜色图层。
- 把全部原生 ripple 统一改成自绘、或反射 `setForceSoftware()`：前者需要另验动画外观，后者是隐藏接口；都不适合作为这次局部问题的默认修复。

## 后续验证应检查什么

- 自绘／系统 ripple，页面按钮打开普通 Dialog、Dialog 内点击关闭、“添加附件 → 录音”重叠、Doing 页面按钮与关闭／返回、首页顶栏／FAB 前景交接。
- 快点、连续点、长按后松开；至少正常与较慢动画倍率。波纹应持续扩散并自然淡出，不能被重新显示，也不能使新弹窗等待额外一个完整反馈周期。
- 材料截图不含瞬态波纹；实际屏幕中的源按钮反馈仍连续。逐帧比较颜色、裁剪、按钮内容、阴影，而不是只比较动画器回调。
- 分别测新 Dialog 首个粒子可见延迟、源 Dialog 原有等待时间、粒子呈现帧率；检查取消／异常／返回时没有积压、残影或输入阻塞。
- 继续使用应用内原实现对照与诊断导出，Android 设备回归与卓易通目视结果分开记录。分析阶段尚未开展的测试，后续结果见 [修正与验证](ripple-capture-implementation-2026-10-12.md)。

## 源码定位

- `ParticleTouchFeedback.kt`：77 行的同步过滤、99 行的自绘 ripple 扫描。
- `ParticleDismissController.kt`：236–250 行的异步阴影准备与外层同步过滤；561 行出现路径的反馈收集。
- `ParticleHardwareSnapshot.kt`：83 行独立 Surface 异步准备；190 行开始实际显示树记录。
- `ParticleDoingGlScene.kt`：112–132 行图像接收与 `!busy` 回收；386 行之后退出保护。
- `ParticleForegroundSurface.kt`：322 行失效条件与 351 行软件局部内容记录。
- 本地平台源码：`E:/AndroidSDK/sources/android-36/android/graphics/drawable/RippleForeground.java` 的硬件属性及失效逻辑；同目录 `RippleDrawable.java` 的 patterned 绘制分支与隐藏 `setForceSoftware()`。
