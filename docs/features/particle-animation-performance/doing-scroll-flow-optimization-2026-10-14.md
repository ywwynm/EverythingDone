# 正在做事：滚动与首次流体拖动优化

## 任务与基线

2026-10-14 用户授权继续定位并优化，保留整页 GL 兼容方案，不改变粒子、计时数字动画和 GIF 播放。复测三台授权设备的四种卡片与两种粒子效果。

基线见 [刷新率实测](doing-refresh-rate-2026-10-14.md)：三星上下滚动约 60–64 FPS，OPPO 平板约 82–96 FPS；魅族普通卡片约 118–120 FPS，长清单约 88–100 FPS。魅族视频流体首次可见回调为 823 ms，复测为 591 ms。三台手势期间均已运行于 120 Hz。

## 待验证假设（按优先级）

1. 整页捕获等待旧图像释放，完成时已错过下次遍历：若成立，记录与 GPU 捕获并不昂贵，而图像上传／释放至下一次捕获之间有接近一个刷新周期的空档。
2. 长清单真实绘制记录或 HWUI 同步耗时：若成立，同设备清单的记录／同步耗时会高于文本与图片，缩短排队不能完全消除差距。
3. 首次流体准备或卡片交接阻塞 GL：若成立，首次资源准备或首次帧渲染显著慢于后续，且等待区间可对应 CPU、GPU 初始化或主线程／GL 交接。

先使用既有测量入口增加阶段取证，再单项改变。性能测试不同时录屏；动画与 GIF 的画面验证另行执行。测试卡片仅在内存构建，不新增或完成用户记事。

## 第一轮取证

- 三星文本上下滚动：记录中位 0.192 ms，同步调用 0.283 ms；捕获→图像到达 3.704 ms，栅栏 3.233 ms，切回主线程 1.140 ms，上传与回调 0.941 ms；旧图像释放门槛仅 0.020 ms。总计 9.678 ms，捕获间隔中位 16.647 ms，380 次遍历中 184 次仍忙。
- 魅族视频滚动：总计中位 5.507 ms，捕获间隔 8.300 ms，仅 385 次请求中 11 次忙。
- 因此假设 1 需修正：瓶颈是整条捕获链串行且额外绕回主线程，旧缓冲栅栏门槛并非主要等待；不能直接取消 GPU 读取保护。
- 魅族视频流体首次回调 486 ms；既有分段日志显示管线 197 ms、材料等待 27 ms、材料上传 84 ms、预算与首帧 134 ms。后两次管线 2.6／0.6 ms，上传 13.5／5.2 ms。继续记录首次同步阶段，区分程序建立和历史缓冲初始化。
- 取证文件在 `tmp/doing-scroll-optimization-20261014/trace-baseline/`；本轮开始前保存三机真实记事与计时记录的语义摘要用于结束核对。

## 单变量排程验证

- 不改图像所有权，仅在捕获完成时立即处理忙碌期间已经过 preDraw 的更新，三星文本流体上下滚动升至 118.71／118.08 FPS，捕获间隔中位 8.328 ms。基线 60.62／62.57 FPS；确认主要问题是等待下一次遍历产生的额外空档。
- 保留原生 Ripple 的完整窗口遍历要求：反馈续帧／收尾请求仍等待下一次遍历，只有已完成输入与布局的普通更新可立即消费；所有图像仍等待 GPU 读完再归还。
- OPPO 清单的额外取证：记录中位 0.221 ms、P90 2.201 ms；串行捕获中位 7.050 ms、P90 10.027 ms，371 次遍历中 120 次忙，说明同一排程问题也会放大清单偶发记录开销。
- 魅族首次流体细分：管线约 160 ms，其中倒放积分程序首次建立约 107 ms；材料与初始历史阶段约 330 ms。未进入合并流场分支，排除该分支为本次主要原因。下一步细分真实材料上传、历史建立和第零档初始化。
- 方法采样导致调试运行超时，文件为空，该样本不作帧率证据；改用低开销阶段时间记录，不继续扩大方法跟踪。

## 首次流体初始化

- 程序慢在着色器源码读取／派生，而不只是驱动编译：一次倒放积分源码处理 98.75 ms，对应程序总计 99.79 ms。复用已有后台 GPU 预热的程序，后台上下文与正式 EGL 上下文共享对象；FBO、纹理和会话仍各自所有。完成 GPU 工作后移交程序，正式首用若已建立同配方程序则丢弃预热副本。
- 仅复用程序，管线阶段从约 160–200 ms 降到 19 ms，但整体首次拖动仍有 683 ms，未作为最终通过结果。
- 原材料消失边界和历史范围计算分别曾占 GL 线程约 107 ms 和 109 ms。先移到既有材料工作线程，历史 GPU 建立降至约 2 ms；随后将两个相同的数值循环放入现有 JNI 库，保留原 Kotlin 实现作为不可用时的回退及独立对照。
- JNI 编译继续使用 `-ffp-contract=off -fno-fast-math`，不改变采样数、浮点精度、出生／寿命公式和粒子数量。新增 debug 逐位探针先验证缺失实现失败，再在三台设备各通过 48 组对照，包含 36,270 片和 1／18／36／60 档、边界出生时间与不同释放宽度。
- 滚动调度的正确测试边界是实际 HWUI／GL 队列，普通 JVM 测试不能重现其周期错失。沿用同一设备回归脚本作性能信号；图像门槛、交接状态、材料边界与历史算法的现有 JVM 测试同时通过。

- 后续细分证实剩余首用主要在像素分类：首次模型 165.49 ms，其中分类 132.52 ms；后续模型 44.95／24.92 ms，分类 23.26／3.28 ms。将两次相同下标的整数遍历合并到 JNI：面板色分箱、首次出现位置、通道整数和、透明／白色计数；比例、平滑及颜色公式继续留在 Kotlin。参考路径保留原算法，三机各通过扩展后的 60 组逐位检查。
- 开始候选完整矩阵：三设备 × 四卡型 × 两样式，每组重复三次横滑及两次纵向滚动；关闭详细节拍取证和录屏，以驱动呈现时间戳统计。

## 完整性能矩阵初步结果

24 组均完成，诊断日志无缓冲溢出，无场景失败；这不代表没有未赶上刷新的帧。三星四卡型纵向约 110–120 FPS（此前约 60–64），OPPO 约 106–116 FPS（此前约 82–96），魅族长清单约 107–110 FPS（此前约 88–100）。魅族视频首次流体 340 ms；仍需保留其实际冷启动波动边界。

魅族图片／视频纵向本轮约 112–116 FPS，低于较早基线约 118–120；电池温度由早前 37–38°C 升到本轮 39–40°C，不能据此直接归因为温度。补同条件包间配对，核查是否由调度改动增加负担。

三机的共享预热程序与现场建立程序在 3 个流体相位逐像素对照均最大差 0。粒子相关 JVM 测试 395 项全部通过。静态与动态画面验证另外进行，不将录屏结果作为性能样本。

## 动画、GIF 与数据核验

- 三机各完成 60 组 JNI／Kotlin 逐位对照，覆盖像素分类、面板颜色／权重、材料消失边界和历史范围；各完成 3 相位共享程序／现场程序逐像素检查，最大通道差为 0。
- 三机各通过 792 组计时路径对照，覆盖全部字体、填充／描边、数字插值、尺寸变化及重复绘制；各通过 60 组合成对照，最大通道差为 1/255。现有粒子 JVM 测试共 395 项通过。
- 三机两样式分别核验实际 Doing 视频卡片：计时变化、填充／描边切换、无穷计时、横滑取消／完成、纵向滚动、弹窗返回、布局尺寸变化及后台恢复。前后相同静止计时区域无损截图差为 0；75 帧实际视频 GIF 的运行状态、帧号与画面持续变化。
- 三星、魅族各保存两段约 26 秒录屏。OPPO 系统 `screenrecord` 拒绝输出文件，标准输出尝试无有效视频；改为各 14／15 张无损截图序列（约 0.5 FPS）。平板此项只能验证采样画面及状态，不能据此判断动画连续帧质量；其实际出帧由独立驱动时间戳矩阵验证。
- 方法采样超时、未等到 UI 就开始操作、录屏输出失败及一次被并行仪器启动中断的计时探针均未算通过；已修正测试流程并补齐有效结果。测试之间同一设备不并行运行 instrumentation。
- 三机真实记事及计时记录在测试前后的行数与语义 SHA-256 完全一致。测试仅使用内存卡片；数据库私有副本、用户背景截图与录屏留在本地临时目录，不纳入仓库证据。
