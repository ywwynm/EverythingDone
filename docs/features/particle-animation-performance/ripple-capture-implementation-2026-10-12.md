# 按钮波纹与粒子材料修正（2026-10-12）

## 用户补充与已复现证据

用户已授权细化后改代码，随后明确：主要是点击 Dialog 的取消／确认按钮关闭时，按钮波纹被固定在消散材料内。普通页面打开 Dialog 的背景冻结不再作为已确认故障。保持 SurfaceView、真实按钮反馈、动态背景、重叠转场和原有粒子表现。

三星固定源弹窗的真实触摸对照已复现：`baseline-custom-transition-drift-unified-1791809726/material-1-false.png` 含有蓝色波纹；源按钮实际像素约 391 ms 淡出，但已捕获的消散材料仍保留该颜色。相比之下，三星及魅族的普通页面按钮自然淡出，不能将此问题泛化成全部背景更新停顿。

Doing 页另有独立复现：三星 `baseline2-native-doing-control-drift-unified-1791809921`，原生波纹在页面 GL 输出中的蓝色信号从 192 ms 至 2943 ms 保持 10.13；普通原生页面对照可自然淡出。采样是实际页面输出纹理，最终屏幕仍需结合录屏核验。

原始材料、按钮逐帧像素、屏幕录像和应用报告位于 `tmp/particle-ripple-20261012/`。测试只使用虚构内容；已备份三台设备原 APK 和记事逻辑数据。

## 本轮实施边界

- `ParticleHardwareSnapshot.captureMaterial()` 在异步阴影／独立 Surface 准备后，实际记录显示树及提交绘制的同步区间排除自绘 `GradientRippleDrawable`；随后恢复先前状态。普通 `capture()` 与动态背景仍保留反馈，不跳过真实波纹动画。
- `ParticleDismissController` 的 Dialog 材料调用新入口；软件 Dialog 和旧软件投影路径同样将过滤限定在实际 draw 区间。同步过滤不跨越 GPU 读回等待，支持嵌套恢复。
- 有可见独立 Surface 的关闭路径原本会等待真实反馈结束再捕获；不能声称所有 Surface 弹窗都有同一个异步漏洞。异步过滤修正覆盖实际记录位置，原有等待策略不变。
- `ParticleDoingGlScene` 收到没有显式捕获请求的原生续帧时，仍及时归还图像，只触发下一次受控捕获。不把任意续帧当成卡片交接完成，不撤销既有退出及有界消费保护。
- 调试源集新增 `ParticleRippleProbeActivity`，覆盖 Dialog 关闭、重叠转场、页面按钮和 Doing；诊断页提供无需 ADB 的三个入口及“波纹冻结或残留”观察项，导出包含采样和材料。

编译与三机波纹断言已完成，汇总见下文。通用系统 `RippleDrawable` 的静态材料无损过滤未纳入本次修正；生产取消／确认控件使用自绘波纹，原生 Doing 则走动态更新，不替换系统波纹。

## 迭代中的可证伪检查

第一轮三机 Dialog 材料已不含蓝色波纹；源按钮实际像素仍自然淡出。Doing 只补刷新信号后，魅族与 OPPO 已淡出，三星却保留蓝色信号 8；再保留繁忙期间被丢弃帧的刷新请求后仍残留 3。因此“只补末帧请求即可修复”不成立。

在相同三星样本中，调试探针仅在 1000 ms 对按钮本身调用一次 invalidate，残留立刻归零。说明还需要更新持有原生波纹的按钮显示列表，仅使整页根节点失效不足以清理波纹结束状态。第三轮候选在原生续帧信号到达时只使含 `RippleDrawable` 的控件失效；不变更波纹状态或动画时长，不对所有页面常驻轮询。调试用的延时 invalidate 不进入正式逻辑。

第三轮的三星原生 Doing 两次、魅族和 OPPO 各一次均完全淡出；自绘 Doing 对照也正常。离屏材料与实际窗口分别检查，共 17 项候选断言通过，两个修复前样本按预期失败。三星最终录屏另外暴露原生 Doing 波纹第一帧偏深：修复前相同整页路径已出现，该项未由本轮新增，也未解决，不能据此宣称整页与原生窗口逐帧完全一致。

代码复核同时修正恢复闭包只消费一次：同步记录完成即清空闭包，避免 GPU 读回完成时再次恢复较早状态，破坏嵌套捕获的恢复结果。异常完成也先恢复再回调。

## 验证结果与限制

- 三星／魅族／OPPO 共 25 项波纹断言通过：关闭与重叠弹窗的消散材料无残留蓝色波纹，真实反馈仍淡出；原生与自绘 Doing 波纹最终归零。含 DRIFT／FLOW 和三星按住 450 ms 后松开。两个修复前样本按预期失败。证据见 `diagnostics/ripple-capture-2026-10-12/ripple-audit.json`。
- 21 项其它回归通过：三机各包含两种样式独立 Surface 开关、连续弹窗、Doing 取消与 200 ms 快速完成、关闭按钮与返回键退出。虚构卡片恢复 alpha=1、容器 alpha=0.84；快速完成各回调一次。六次退出后脚本首个有效滚动约 239～378 ms，捕获资源释放和窗口分离均完成。21 份诊断 ZIP 的 CRC 通过。
- 三星与魅族独立 Surface 的 4 份录屏逐帧检查未发现恢复后孤立灰块；OPPO 不支持这条 screenrecord 取证方式，使用截图／缓冲及应用报告，不冒充最终屏幕逐帧验收。
- 真实“添加附件→录音”三星、OPPO通过。魅族首次业务流程完成，但录音出现阶段 `appearance_preparation_aborted`，未计为动画通过；同记事的旧包与最终候选补测均完整播放。保留首次失败，与此前独立 Surface 首帧不稳一并后续排查，不宣称修复。
- JVM 测试 1448 项、失败 0、错误 0、跳过 1。保持 SurfaceView、粒子参数、轨迹和系统动画倍率；软件回退有恢复保护，但本轮高版本 Android 实测不能替代 API 26～28 验证。

### 性能口径

相同 360 dp 卡片、Doing 动态背景，关闭关键图像和录屏；统计粒子可见 150 ms 后的驱动呈现时间戳。时延是激活至首帧回调，并非高速相机测得的触摸至屏幕延迟。完整样本见 `perf-audit.json`。

| 设备／样式 | 修复前 fps | 候选 fps | 激活至首帧回调（前／后，ms） |
| --- | --- | --- | --- |
| 三星 DRIFT | 117.0 | 118.0 | 88.8／78.6 |
| 魅族 DRIFT | 120.6 | 118.5 | 183.4／168.6 |
| OPPO DRIFT | 119.2 | 118.3 | 60.6／61.6 |
| OPPO FLOW | 115.3 | 114.3 | 79.1／94.9 |
| 三星 FLOW，多次对照 | 104.5～113.8 | 101.5～109.6 | 126.3～143.0／111.8～154.0 |
| 魅族 FLOW，多次对照 | 105.5～110.1 | 94.4～114.2 | 168.2～186.5／176.5～194.5 |

FLOW 存在设备与运行顺序波动，不能表述为“性能完全一致”。末轮颠倒顺序后魅族候选 114.2、旧包 107.6 fps；末轮两机滑动报告的原生反馈刷新次数均为 0，新增刷新分支没有在这些样本中执行。不增加常驻刷新定时器，也不据短样本承诺零成本。

三星一次性能运行在导出阶段因缓存 ZIP 消失失败，当时 `/data` 仅剩 623 MB；可能涉及低空间回收，未确认系统原因。仅清理本轮已备份录像与波纹 PNG 后剩余 866 MB，复验导出成功。失败日志保留，不计为成功导出。
