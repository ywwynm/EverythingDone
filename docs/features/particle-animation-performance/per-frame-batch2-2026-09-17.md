## 1 F14：两个上下文分优先级

### 做法

常驻 GL 线程上再建一个**同 share group** 的上下文，用 `EGL_IMG_context_priority` 分档：

| 上下文 | 请求档位 | 跑什么 |
| --- | --- | --- |
| 出帧 | `HIGH` | 现场积分、历史恢复、绘制记录、两遍绘制、resolve、`eglSwapBuffers` |
| 后台 | `LOW` | 出现预计算（`beginReverse`/`stepReverse`）、左滑预读、创建页提前预算 |

四条纪律，逐条落进代码：

1. **优先级必须读回来。** 规范原文把这个属性定义成 hint，实现可以不区分低档、可以按系统
   策略限制高档。`ensureBackgroundContext` 建完立刻 `eglQueryContext` 读两边，**读不到、
   驱动没有这个扩展、或者两档读回来一样，就把第二个上下文销毁、退回单上下文**（= 第一批的
   行为），结论写进日志与观察器产物。
2. **交接写成 fence → flush → wait。** 切到后台之前在出帧上下文 `glFenceSync` + `glFlush`，
   切过去之后 `glWaitSync`（服务端等待，不阻塞 CPU）。`glWaitSync` 没有自带的 flush 位，
   生产侧不冲就可能永远等不到。
3. **切回出帧时不插任何等待。** 让高优先级的一帧去等低优先级上下文里全部在途的工作，
   就是教科书式的优先级反转。反向的可见性由数据那一侧保证：历史采样的「可画档位」只计
   **已经确认完成**的采样（第 2 节），整段预计算的交接在 `endReverse` 处一次性排空。
4. **容器对象不跨上下文共享。** VAO 与累积纹理的 FBO 只有出帧上下文碰：`ensureShared` 里
   真正要建的时候显式切回出帧，绘制路径本来就只在出帧侧。程序对象、uniform、缓冲与纹理
   都是共享的——`advance()` / `PeelPressure.update()` 每次调用都把 SSBO、纹理单元与
   `glUseProgram` 重新绑一遍，所以每上下文各自的绑定状态不构成问题。

**后台放同一条线程、按需 `eglMakeCurrent` 切换**，不另起线程。理由有二：一是同线程切换实测
很便宜（下表）；二是两个上下文共用同一批**程序对象**，而 uniform 是程序对象的状态——
另起线程就要给「切换会话时整套重设 uniform」那条既有机制加锁，风险远大于收益。

### 读回的档位与切换开销

| 设备 | 读回档位（出帧 / 后台） | 建立时标定 32 次切换 | 一整轮矩阵的切换 |
| --- | --- | --- | --- |
| 魅族 20 Infinity（Adreno 740 / Android 15） | **HIGH / LOW** | 0.548 ms（**17 µs/次**） | 270 次 / 9.71 ms |
| 三星 SM-S9180（Adreno 740 / Android 16） | **HIGH / LOW** | 0.319 ms（**10 µs/次**） | 302 次 / 13.13 ms |

两台都真的拿到了 HIGH 与 LOW（`0x3101` / `0x3103`），所以这一项的结论是可归因的。
一整轮九个场景的矩阵里总共只切了 270–302 次、合计 10–13 ms——**切换只发生在真的有后台
工作的那些 pump 里**，切换开销不构成取舍。

## 2 F15：预读不再阻塞 CPU

### 现状与根因

第一批之前，每推进一个采样都要走 `ParticleGpuWork.PreparationQueue.finishBatch`：放栅栏、
`glFlush`、**然后阻塞等上一批算完**。左滑一个采样约 3.9 ms、弹窗 5–7 ms，而一次 pump 的
准备预算是 8 ms——于是一次 pump 里只塞得下两个采样，**这段阻塞正好压在节拍上**。
阶段 0' 量到的「左滑的呈现间隔 p90 恰好是 33.1 ms = 两个 vsync」就是这么来的。

### 做法

`beginReverse(..., async = true)` 之后改成：

- **提交一个采样 → `glFenceSync` + `glFlush` → 立刻返回**，栅栏连同采样号压进一个环形队列；
- `pollReverse()` 用 `glClientWaitSync(sync, 0, 0)`（**非阻塞**，超时 0）把队头已经发信号的
  采样弹出来，`preparedSamples` 只跟着它走；
- 于是**出帧侧永远只画已经确认写完的采样**，后台写、出帧读之间不需要任何 `glWaitSync`；
- 在途上限仍是**两批**（与第一批的 `PreparationQueue` 同深度，留成可调项
  `reverseInFlight`）。改的是「CPU 不再阻塞等它」，不是「往驱动里排更多」——
  排得更深会让弹窗 A 的一帧要等上后台几十毫秒的 compute，而「低优先级一定会被抢占」
  这件事在 Adreno 上没有公开保证（调研第 8 节：抢占点在 bin 边界）。

两处保持同步语义：离屏基准与 `ParticleTrajectoryCheck` 用的 `prepareReverse`（`async=false`，
逐位口径与第一批完全一致），以及关掉 `gestureCreepToFinger` 时出帧路径上的同步补档
（`stepReverse` 在异步模式下退化成「提交 + 排空」）。

**手势的第 0 档留在出帧上下文里**（`beginPrecompute` 显式切回去）：它与识别之后的首帧
在同一条命令流上，次序由 GL 自己保证，直接记成「已完成」，不必再等一次栅栏。

### 档数重定

| 常量 | 第一批 | 第二批 | 依据 |
| --- | --- | --- | --- |
| `GESTURE_PREROLL`（按下阶段先备） | 6 | **12** | 识别那一刻的位移只有一个 touch slop（约 0.6 档），真正吃紧的是**甩动**：材料建好时手指常常已经拖过 20%（36 档里的 7 档）。按下到识别至少一百多毫秒，这段时间屏幕上什么都不画，多备是纯赚 |
| `GESTURE_IDLE_LOOKAHEAD`（手指停住时每拍多备） | 2 | **6** | 「每拍 +2」是为了配合阻塞式补档（一档 4–7 ms，备多了挤掉节拍）。改成异步 + 低优先级之后，手指停住那段是真的空闲 |
| `gestureLookahead(speed)`（在动时预读几档） | 1 或 2 | **`ceil(speed)+1`，上限 6** | 快拖一拍跨三四档，只备一两档时下一拍要画的档位永远还没算出来——阶段 0' 的快拖只出 9 个不同画面就是这么来的 |

## 3 「有会话在出帧时，预算不许跨过下一拍」

一次 pump 的准备预算原来是固定 8 ms，而截止时间**每轮重算一次**就等于没有截止时间
（这是本批自己写出来又自己查掉的一处：`while (… < workDeadline(live))` 必须改成先算一次）。
现在只要有窗口里有会话在逐帧出画，截止时间就压到「下一拍之前还剩 6 ms」，
合成与呈现回调总有地方落脚；没有会话在出帧时（首页空闲预算、弹窗还在预计算）仍用满 8 ms。

## 4 未落地的一项：首帧绕开节拍

调研第 10 节说粒子层是独立 SurfaceView、首帧不必等下一次节拍，最多省一整拍。做出来之后
在魅族上量到的却是**首帧提交早了 6–21 ms，首帧确认上屏反而从 58–68 ms 退到 120–131 ms**，
三个左滑场景一致。单独关掉这一项即恢复（`b2noimm`），单独关掉异步预读则不恢复
（`b2nosync`）——归因很干净。

### 根因：被替掉的那一拍必须真的吃掉

提前出的那一帧会在 `now` 之后的**第一个 vsync** 上屏，而节拍的目标就锚在各个 vsync 上。
只把「已消费的节拍」推到 `now`，紧接着的那一拍（目标 ≈ 同一个 vsync）照样会再提交一帧，
**两张缓冲落在同一个显示周期里，SurfaceFlinger 只 latch 新的那张、把先提交的直接丢掉**。
被丢掉的那一帧永远等不到 `EGL_DISPLAY_PRESENT_TIME`，它卡在待确认队列的**队头**，
后面的帧全部要等到队列溢出（`MAX_PENDING_FRAMES = 6`）才一起放行——观察器里的形态就是
**六个确认时刻挤在 1.7 ms 之内**。把已消费的节拍推到 `now + 一拍`，正好吃掉那一个目标。

### 修好之后仍然默认关闭

改对之后「六个确认挤在一起」的形态消失了，但**收益也量不出来**：这一项的上限本来就只有
一拍（16.7 ms），而第三批的 `beatDuringPreparation` 已经让节拍在准备期间就跑着，实际能省的
更少；魅族三个左滑场景 + 两个弹窗场景的「请求 → 首帧呈现」在开与关之间全落在单轮噪声里
（±20–40 ms）。按本专项「没有可测收益就回退」的纪律**默认关闭**，开关与那条时序教训留在
代码里（`ParticleGl.presentFirstFrames`），换设备或换路径时可以直接开起来复测。

## 6 左滑三格：跟不跟手

新增的滞后曲线：每画一帧记一次「手指要的相位 `wanted`、实际画出的相位 `drawn`、
可画档位、已提交档位、目标档位」（观察器产物里的 `gesture` 行），
`wanted − drawn` 就是**画面落后手指几档**（36 档跨满整张卡片，一档约 36 px）。

| 设备 | 场景 | 移动期不同画面 前→后 | 识别→首个非零画面 前→后 | 滞后 p90 档 前→后 | 滞后 max 档 前→后 |
| --- | --- | --- | --- | --- | --- |
| 魅族 | 快拖 | **7 → 9** | 130.2 → **105.4 ms** | **16.20 → 10.34** | **16.20 → 10.34** |
| 魅族 | 慢拖 | 53 → 53 | 70.5 → 74.8 ms | 0.00 → 0.00 | 0.00 → 0.00 |
| 魅族 | 来回拖 | 74 → 69 | 69.8 → **63.5 ms** | 0.00 → 0.00 | 5.23 → 5.32 |
| 三星 | 快拖 | **7 → 12** | 59.2 → 73.2 ms | 3.88 → 9.01 | 3.88 → 10.65 |
| 三星 | 慢拖 | 55 → 57 | 148.0 → **137.9 ms** | 0.00 → 0.00 | 0.00 → 0.00 |
| 三星 | 来回拖 | 68 → 68 | 57.4 → 59.0 ms | 0.00 → 0.00 | 6.94 → **1.83** |

三条结论：

1. **快拖是本批唯一真正吃到收益的一格**：两台的移动期不同画面都明显上去
   （+29% / +71%），魅族的滞后 p90 降了 36%。三星那一列「滞后变大」是**采样口径**造成的：
   滞后只在真的画出一帧时才记一次，修前整段只画了 7 帧、根本没采到最坏的那几拍，
   修后画了 12 帧才把曲线量全。
2. **慢拖与来回拖根本不是预读的问题**：两台、两种条件下 `wanted − drawn` 的 p90 都是
   **0.00**，也就是画面**逐帧跟着手指**，一档都不落后。滞后只出现在**第一次拖到从没到过的
   深度**那一两帧（max 1.8–6.9 档，占比 3%–7%），因为历史只增不减，越过之后再怎么来回都是
   现成的。**「来回拖不跟手」的成因不在这条链路上。**
3. **来回拖剩下的问题是帧率不是滞后**：移动期 1.81–1.83 s 出 68–74 个不同画面（约 38 fps），
   呈现间隔 p90 33.1–33.3 ms。这一格修前修后一样，而此时预读早就停了
   （`gestureGoal` 很快到 36 档、`needsWork()` 随即为假），所以**不是预算在抢**。
   这条线索记进 followups，下一批单查。

来回拖的注入方式（`device_per_frame.py` 的 `WIGGLE`）：按住不放，
`0.28 → 0.06 → 0.38 → 0.10 → 0.36 → 0.04`（卡片宽度的倍数，向左为正）五次反向，
每段 130–160 ms（约 2.2–2.6 px/ms，即每拍跨过一档以上），最后 600 ms 慢慢回到按下点附近
再停 400 ms 才松手。三条硬约束写在脚本注释里：任何时刻都不能拖到按下点右边
（会被判成反向手势、直接取消会话）、最深处留在 0.38 以内、**松手那一下必须慢**。

## 7 最差的一格：弹窗 A 消散接 B 出现（分析与建议，本批不实施）

阶段 0' 把这一格定成最差的一格，本批之后仍然是：B（录音弹窗）的「请求 → 首帧呈现」
魅族 **1290 → 1230 ms**、三星 **810 → 886 ms**，都远在 500 ms 之上。观察器的分段把它拆开
（相对「请求」的毫秒，魅族修后一轮）：

| 段 | 起 → 止 | 用时 | 说明 |
| --- | --- | --- | --- |
| 弹窗自身起来 | 0 → 359 | **359 ms** | 点「录音」长条行 → Dialog 创建、布局、抓快照、涟漪结算 |
| 建材 + 上传 | 359 → 413 | 54 ms | 10.6 万片 |
| **出现预计算** | 413 → 1177 | **764 ms** | 33 个采样，≈ **23 ms/采样** |
| 首帧提交 + 确认 | 1177 → 1231 | 54 ms | |

**大头只有一个：预计算。** 而离屏基准里同样材料的一个采样只要 5.4–7.7 ms——**贵了三倍多，
就是因为同一时刻 A 正在逐帧现场消散**。本批把它从 869 ms 压到 764 ms（−12%，三星那一轮
反而 436 → 494 ms），也就是说**双上下文分优先级确实缓解了争用，但缓解不了「这 33 个采样
本来就要算」这件事**。

三条可能的下一步，**只建议不实施**：

1. **把 B 的轨迹在 A 的静止期（甚至更早）提前预算，对照创建页的做法。**
   第四批的 `ParticleCreationPrewarm` 已经证明了这条路走得通：**用预测素材算轨迹、播放时
   只把前景贴图换成真实快照**，末帧仍与真实面板逐像素相同（`material.vert` 第 0 遍的采样
   位置与屏幕位置是同一个恒等映射）。录音弹窗在同一台设备上的尺寸与内容是稳定的，
   完全符合这个前提。**代价是一份 30–55 MB 的历史缓冲要提前占着**，且要想清楚缓存键
   （弹窗类型、尺寸、主题色、系统时长缩放），这也正是创建页那条路踩过的坑。
2. **不要指望「边播边算」。** 出现是**倒放**：第一帧要的是 `appearanceStart`（本轮 33），
   而历史是从 0 往上算的——第一帧恰好依赖**最后**算出来的那个采样，所以必须全算完才能起播。
   这条路除非改播放方向的语义，否则不成立，别再评估。
3. **线性地把预计算变短。** 33 个采样 × 10.6 万片是它的全部规模：E12（按 dp 定微片尺寸，
   片数约减半）与 C7/C9（迭代数与网格）都会按比例缩短这一段，且对所有弹窗一起生效。
   本批之后它是这一格唯一能靠「算得更少」拿到的收益。
