  改成 `research-2026-09-18-vendors.md`。
- **检索方法上唯一值得记的一条**：`developer.arm.com` 与 `docs.qualcomm.com` 的网页在本机
  `WebFetch` 取不到正文（前者 JS 渲染、后者域名校验失败，上一轮已记）。这一轮改成
  **把 Arm GPU Best Practices 的 PDF 整份下载后 `pdftotext -layout` 转文本再逐节读**，
  于是第一节里带引号的都是原文而不是搜索摘要。华为的 Maleoon 最佳实践页同样是 JS 渲染，
  仍然只有摘要。
- **最硬的几条结论都来自数代码**，文档只解释了「这些数字为什么重要」：每帧最多约 1370 万次
  3D `texelFetch`（`sample_field` 显式三线性 × 两张纹理 × 两次 `guided_flow` × 4 步 × 10.7 万片）、
  `material.vert` 输出 **14 个 highp varying 分量**（Arm 原文：varying 在片元着色之前要写回主存）、
  `pressure-batched.comp` 用 16 KiB `shared` 载入 32×32 却只输出 16×16。
- **对 Mali 最有杀伤力的一条**：Arm 明写「Arm GPU 没有专用片上 shared，shared 就是经
  load-store cache 的系统内存」且「不要把全局内存抄进 shared」。批处理 Jacobi 的全部前提
  （片上 LDS 便宜、冗余读发生在片上）在 Mali 上都不成立，而**无 shared 的逐次路径已经在代码里**
  （`peel-project.comp`），只差把活动区域接上去——对照几乎零成本。
- **两条被上一轮低估、本轮翻案的**：① Arm 说 `highp` 相对 `mediump`「可以用两倍资源、速度减半」，
  而本管线**一个 `mediump` 都没有**；上一轮按 Godot 的 2–3% 把精度类排到第 10，本轮重排到前列，
  并给了一条能分清「改了没用」与「驱动根本没听」的判据（画面若逐位相同就是后者）。
  ② Arm 的两条 Don't（不要在浮点渲染目标上混合、非必要不用 RGBA16F）正对着我们的全屏
  RGBA16F 累积 + `ONE, ONE_MINUS_SRC_ALPHA`；而混合模式是预乘 over 不是加法累积，
  值域留在 `[0,1]`，**`SRGB8_ALPHA8` 是可用的**——Mali 上是浮点混合变 unorm 混合 + 带宽减半，
  Adreno 上是 bin 数减半。这是唯一一条对两家都是量级级别的候选，也因此排第一且必须看图定夺。
- **天玑不是独立分支**：当前主力天玑用的是 Arm 的 Mali / Immortalis，Mali 分支的规则直接适用，
  差别只在驱动与代际。因此厂商判据一律写成「非 Adreno」而不是判 Maleoon，现有的
  `Shared.adreno()` 恰好就是这个形状。联发科没有公开的 GPU 优化文档，不要引第三方报道当依据。
- **否定项一并记下**（避免以后重查）：索引四边形（Arm 5.2 明文「简单四边形无顶点复用不要用索引」）、
  两遍绘制合一、shared 原子聚合 splat、粒子空间排序、PCG / 多重网格、
  `GLFrontBufferedRenderer` 前缓冲渲染（每帧整屏重画必然撕裂）、`requestUnbufferedDispatch`、
  `glMemoryBarrierByRegion` 用于 compute→compute、framebuffer fetch / PLS 合并累积与 resolve。
- **方案第一步仍是华为上的分段归因**：现有的所有份额数字只在 Adreno 740 上量过，
  而两家在 shared、varying、混合格式、采样器精度四件事上的代价结构根本不同，
  照 Adreno 的份额排序去实施很可能排错。归因新增三条对照（累积格式、批处理 vs 逐次 Jacobi、
  整网格清零），另有一条「`mediump` 是否被驱动接受」的判定。

## 2026-09-17 逐帧成本专项 第二批：两个上下文、异步预读与首帧时序

产出 [per-frame-batch2-2026-09-17.md](per-frame-batch2-2026-09-17.md)。两台真机：
魅族 20 Infinity `392QBFED2226B` 与三星 SM-S9180 `R5CW20BLNKL`。OPPO 与华为本轮仍不在线。

未改任何设备设置、未代授权限。`:app:testDebugUnitTest` 本轮真实执行 1068 项、0 失败、1 跳过。

- **优先级要先读回来才有资格归因。** `EGL_IMG_context_priority` 在规范里明写是 hint；
  两台都真的拿到了 `HIGH` / `LOW`，所以 F14 的数字可以往上算。这条纪律落成了代码：
  读不到、扩展没有、或两档读回来一样，就把第二个上下文销毁、退回单上下文。
- **同线程切上下文很便宜，别为它另起线程。** 实测 10–17 µs/次，一整轮九个场景的矩阵
  总共才切 270–302 次、合计 10–13 ms。而另起线程要给「共享程序对象的 uniform」加锁，
  风险远大于收益——两个上下文共用同一批程序，而 uniform 是程序对象的状态。
- **切回高优先级那一侧时绝不能插 `glWaitSync`。** 那等于让一帧去等低优先级上下文里全部
  在途的工作，是教科书式的优先级反转。正确的做法是把可见性挪到数据那一侧：
  `preparedSamples` 只计**已经确认写完**的采样，出帧侧因此永远不会读到在途的东西。
- **「提前出一帧」必须把它要替掉的那一拍真的吃掉。** 只把已消费的节拍推到「现在」，
  紧接着那一拍会再提交一帧，两张缓冲落进同一个显示周期，SurfaceFlinger 只 latch 新的、
  把先提交的丢掉；被丢掉的那一帧**永远等不到 `EGL_DISPLAY_PRESENT_TIME`**，卡在待确认
  队列的队头，后面的帧要等队列溢出才一起放行。症状看起来只是「首帧上屏晚了 60 ms」，
  真正的指纹是**六个确认时刻挤在 1.7 ms 之内**。
- **归因要一次只动一个开关。** 上面那条是靠两轮各关一个开关（`b2noimm` / `b2nosync`）
  定死的：关掉首帧提前量就恢复、关掉异步预读不恢复。三个左滑场景各一轮，两轮就够。
- **「不跟手」要先量出「差几档」再谈机制。** 新加的滞后曲线（每画一帧记一次
  `wanted − drawn`）直接否掉了「来回拖是预读跟不上」这个假设：慢拖与来回拖两台、
  修前修后四种条件下 p90 全是 0.00 档。剩下的是帧率问题，另记 followups。
- **截止时间只能算一次。** `while (… < workDeadline())` 每轮重算等于给了一个永不到期的
  预算——本批自己写出来又自己查掉的一处。
- **注入的手势要按「真人有多快」定速，慢了什么也测不出来。** 第一版来回拖每段 500–600 ms
  （约 0.5 px/ms、每拍跨不过一档），滞后自然恒为 0；改成 130–160 ms（2.2–2.6 px/ms）
  才量得到第一次深拖那一两帧的滞后。中途快没关系，**松手那一下必须慢**——
  ItemTouchHelper 的完成判定看的是抬手时的速度与位移。

## 2026-09-15 弱设备阶段 A：消散「不播」的根因与修复

完整报告见 [weak-devices-phaseA-2026-09-15.md](weak-devices-phaseA-2026-09-15.md)。
已发布 `202609151437`。

- **先补日志再定位。** 「不播」此前在日志里一条痕迹都没有。补齐「消散受理 / 抓图路径 /
  消散未受理 / 消散未开播 / 消散降级淡出 / 消散未接管」六类具名日志（`BuildConfig.DEBUG`
  之外零开销），一轮就把根因钉死。
- **根因是抓图选路，不是 GPU。** 魅族 20 Infinity（Flyme / Android 15）上「调整颜色」面板
  用**点外部**关闭时，窗口 `PixelCopy` 整个 700 ms 重试窗口都返回 `ERROR_SOURCE_NO_DATA`，
  快照为空、整场不播，修前 2/2 复现；同一面板点取消/确定走离屏硬件抓图 11–53 ms 就拿到图。
  此前只有「有涟漪」（点按钮）才走离屏，返回键与点外部退回窗口 `PixelCopy`。
- **修法**：没有可见独立 Surface 的弹窗一律走离屏硬件抓图；只有确有 `SurfaceView` 时才用
  窗口 `PixelCopy`。加一次单向兜底（离屏失败 → 窗口 `PixelCopy` 再试一次），反方向不做。
  规则抽成 `ParticleCaptureRoute`，6 项 JVM 单测钉住；粒子单测共 103 项全过。

用户的三条与做法、数字见 [per-frame-batch10-ui-2026-09-18.md](per-frame-batch10-ui-2026-09-18.md)，
裁定记在 decisions 的同日条目。三件值得记住的事：

- **「渐变断开」的根因不在颜色，在 bounds。** `BackgroundUtil.applyBackground` 的渐变分支拿的是
  `GradientDrawable`，它按**自己 View 的 bounds** 从头铺到尾；状态栏与顶栏各调一次，就是各跑一整条。
  套一层容器只上一次色就好了。判据也是靠「同一条渐变里相邻两行本来有多少色差」当噪声底立起来的
  ——只报「交界跳了 1 个灰阶」说明不了问题，报「噪声底 0.010、交界 1.061」才是一百倍。
  另外，**随机换色要能碰到真正的竖直渐变**才有说服力：脚本按「顶部一整块最上一行与最下一行的
  色差」判这一次抽到的是不是竖直渐变，抽不到就继续点，魅族点到第 10 次、三星第 14 次。
- **有些对齐是一条恒等式，只能分配。** `AbsSeekBar` 把滑块中心放在内边距上，于是
  「轨道内缩 + 滑块外探 ≡ 滑块半径」。第一版按用户最初的说法把滑块外缘对齐（轨道因此内缩整整
  10 dp），用户随即补充「轨道的视觉对齐同样重要」——这不是改错了，而是这条约束本来就没法两全。
  遇到这种情况要**先把恒等式摆出来**，再谈取哪个点，并且把取值做成一个常量（`SLIDER_EDGE_BALANCE`）。
- **量「右缘对齐」必须把 bounds 与墨迹分开报。** 四项的控件 bounds 本来就都在 16 dp 上，
  看着却不齐：全角 `）` 的墨迹只占左半个全角（白空 11.43 dp）、勾选框的方框在占位里还内缩 2 dp。
  改完之后形状那两项的可见右缘完全重合，文本那两项还差 0.5–1.7 dp——那是字形自带的右侧留白，
  属于排版事实，不是布局取值，如实报数没有继续补偿（补偿会让读数在拖滑杆时左右跳动）。

两台各一轮（魅族 + 三星，**华为按要求全程未连接**）。默认档位 G0 两台全部 0 差异，关键计数
61 / 37 / 33 / 36 / 12 与 `202609180746` 逐项相同。单测 1197 项 0 失败 1 跳过，新增
`ParticlePerFrameBatchTenUiTest` 8 项，另改写了第 5、6、9 批里被本批取代的 3 条断言。

## 2026-09-18 逐帧成本第十一批：切到示例对话框直接显示静止的对话框

用户的这一条与做法、数字见 [per-frame-batch11-ui-2026-09-18.md](per-frame-batch11-ui-2026-09-18.md)，
裁定记在 decisions 的同日条目。三件值得记住的事：

- **多出来的那一步动画往往是某条约束的副产品，先把约束找出来。** 三步开场序列不是随手写的：
  静止态必须可见（否则按钮点不到），而从不可见起步、以可见收尾，出现的次数**必然**比消散多一次。
  照着「少播一遍」去删步数会把静止态删成不可见；真正的解法是改起点——把静止的可见态同时当成
  起点之后，奇偶性自己就配平了，那一帧空白与那一遍多余的动画一起消失。
- **「不许有空白」不是一个判断，是一条链上的每一环。** 这一条落地时要同时堵住四处：切过去那一帧
  的 `visibility`、上一轮原子交接留在对话框身上的 `alpha = 0`、快照没就绪时 `startContent` 的
  「尺寸为 0」拒收（旧代码随即置 `INVISIBLE`）、以及消散压根起不来那一支。漏掉任何一处，症状
  都是同一句「有时候还是会闪一下」。
- **「两个画面是不是同一个」不能用录屏判。** H.264 在大场景切换之后要几帧才收敛，两帧**内容完全
  相同**的静止态之间就能差 p99 = 16–18 个灰阶、8%–11% 的像素差 > 4——与要测的信号同量级。
  先量本底再看信号，本底一旦与信号同量级就必须换通路：把 `input tap` 与 `screencap` 合并成一次
  `adb shell` 落进那 0.6 s 的静止窗口，两张无损 PNG 逐像素比，得到的是干脆的 0
  （魅族 822,000、三星 972,800 像素，差异像素 0）。

两台各一轮（魅族 + 三星，**华为按要求全程未连接**），各录两段（首次切入、切走再切回）：
