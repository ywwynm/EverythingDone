# 记事分享产物与选项规划

承接 [animated-share-evaluation.md](animated-share-evaluation.md)。本文梳理分享
入口下的**全部功能选项**、每项的技术含义与代价，以及动态可见规则。

本 feature 的范围由此从「长截图」扩展到**记事分享产物整体**。

## 硬约束（用户已定，不再讨论）

- **产物与中间产物一律不得使用 GIF。** 动态源全部走原始格式解码：视频走
  `MediaExtractor` + `MediaCodec`，Motion Photo 走内嵌 MP4 的
  `setDataSource(fd, offset, length)`，GIF 附件走自身逐帧解码（那是解码源文件，
  不是派生 GIF）。已有的 `VideoCoverPreviewManager` / `MotionPhotoCoverHelper`
  派生 GIF 管线继续服务卡片与详情页，**不参与分享产物**。
- **并发解码器超限时排队等待，不降级画质。**
- **不以接收方观感设限。** 产物在接收方屏幕上显示多大、看不看得清，是接收方的事——
  他可以双指放大、可以保存后换播放器。凡是从「接收方看着如何」推出的限制一律不作数。
  算约束的只有两类：**生成侧的真实成本**（编不出来、体积、耗时）与**功能性失败**
  （如 IM 把大动图转成静态、动画直接没了）。

## 四个产物入口

| 入口 | 产物 | 说明 |
|------|------|------|
| 分享文字和图片 | 文本 + 原图附件 | 现状，`SendInfoHelper.shareThing`，不动 |
| 长截图 | 静态 JPEG | 现状，`ScreenshotHelper` |
| **长视频** | MP4，画布 = 内容全尺寸，一次性全部呈现 | 新增，受编码器高度上限限制 |
| **滚动视频** | MP4，视口在内容上从上往下滚 | 新增，内容多高都不受限 |
| **附件单独分享** | `ACTION_SEND_MULTIPLE`：长截图 + 选中附件原文件 | 新增 |

现有的 `TwoOptionsDialogFragment`（`DetailActivity.chooseHowToShareThing()`）只能
放两个 action，需要换成一个可承载入口列表 + 参数区的对话框。

## 选项清单

### 组 1 — 附件选择（所有入口可见，附件数 ≥ 2 时）

勾选哪些附件参与分享。缩略图网格 + 勾选态，默认全选。

技术影响：长截图 / 长视频 / 滚动视频需要临时替换 adapter 数据集、重新 layout、
产出后恢复——现有 `updateThingUiBeforeScreenshot` / `updateThingUiAfterScreenshot`
已经是这个模式，可扩展。注意 `spanCount = min(itemCount, mMaxSpanImage)`
（`mMaxSpanImage` 手机 2 / 平板 3，横屏 +2），去掉附件会改变网格列数与 cell 尺寸，
进而改变长图高度——这是预期行为，但会影响长视频入口的 4096 px 可用性判断，需要在
选择变化后实时重算。

附件单独分享则只是过滤 URI 列表，最简单。

### 组 2 — 动态内容（仅当选中附件含视频 / Motion Photo / 动图时可见）

| 选项 | 取值 | 默认 | 说明 |
|------|------|------|------|
| **播放时长** | 3 秒 / 原时长 | 3 秒 | 「3 秒」从各自的 Thing Card Video Frame 起截；「原时长」取所有选中动态附件时长的最大值 |
| **播放编排** | 同时播放 / 逐一播放 | 同时播放 | 直接复用 `DetailAutoplayMode` 的 `ALL_*` 与 `ONE_BY_ONE` 语义。**仅长视频可见**——滚动视频的编排已由「播完再滚」规则定死 |
| **音轨** | 全部不保留 / 全部保留 / 指定保留 | 全部不保留 | 「指定保留」展开为逐附件勾选 |

**「原时长」的代价必须在 UI 上如实呈现。** 按 1080×4400 / 30fps 估算：

| 时长 | 帧数 | 编码耗时 | 体积（H.264） |
|------|------|---------|--------------|
| 3 秒 | 90 | 2–5 秒 | 0.75 MB |
| 10 秒 | 300 | 8–15 秒 | 2.5 MB |
| 30 秒 | 900 | 23–45 秒 | 7.5 MB |
| 60 秒 | 1800 | 45–90 秒 | 15 MB |
| 120 秒 | 3600 | 90–180 秒 | 30 MB |

选「原时长」且记事里有长视频时，应当就地显示预计时长与体积，并把 LoadingDialog
换成带百分比与取消按钮的进度。

**「逐一播放」顺带解决并发上限**：一次只有一路解码器在跑，是产品语义而非降级。

### 组 2b — 是否保留记事布局（仅长视频 / 滚动视频可见）

**这个选项决定的是「内容怎么排」，与「整图画布还是滚动视口」是两个正交的维度：**

| | 保留布局（cell 网格） | 不保留布局（满宽堆叠） |
|---|---|---|
| **长视频**（画布 = 内容全尺寸） | 1080 × 长图高，附件在各自 cell 里播 | 1080 × 堆叠高，附件满宽播 |
| **滚动视频**（视口在内容上滚） | 视口在长图上滚 | 视口在堆叠内容上滚 |

文字部分（标题、正文、清单）两种排法下都原样保留在顶部，不受影响。

**为什么需要这个选项。** 详情附件网格是 `CENTER_CROP`（`attachment_image.xml`、
`ImageAttachmentAdapter:255`），cell 由布局定死。1920×1080 的视频 center crop 进
方形 cell，左右各切 420 px——**43.75% 的画面直接没了**；竖屏视频同理切上下。
对以视频为主的记事，保留布局的代价过高。

**不保留布局 = 满宽垂直堆叠。** 每个附件占满 1080 宽、按原比例、依次向下排，
零裁切：横屏 1920×1080 → 1080×608，竖屏 1080×1920 原样，方形 → 1080×1080。
源显示宽高须先应用 `KEY_ROTATION` 校正——竖屏拍摄的视频物理上存成 1920×1080 加一个
90° 标记，实际显示是 1080×1920。源宽小于 1080 时同样放大到填满。

代价是**内容显著变高**（文字部分按 500 估）：

| 附件构成 | 保留布局 | 不保留布局 |
|---------|---------|-----------|
| 3 个横屏视频 | 1540 | 2324 |
| 1 横 2 竖 | 1540 | **4948** |
| 3 个竖屏视频 | 1540 | **6260** |

#### 长视频的可用性由设备实际编码能力判定

**唯一的限制是编码器实际能力。** 查
`MediaCodecInfo.VideoCapabilities.getSupportedHeightsFor(1080)` 的上限（多数设备
4096），内容高度超过它就是根本编不出来，禁用长视频入口并提示改用滚动视频。
没超就可用，内容多高都不拦。

**不做「降宽度换高度」的规避**——那会把文字一起缩糊，是我们主动损失了画质，
与「编不出来」性质不同。

> **不以接收方观感设限**（2026-07-26 用户裁定）。此处一度还有一条 4000 px 的
> 「文字有效尺寸跌破 12 dp」警告线，已删除：视频在接收方屏幕上显示多大是接收方的事，
> 他可以双指放大、可以保存后用别的播放器看，不构成我们生成什么的约束。凡是从
> 「接收方看着如何」推出的限制一律不作数；只有生成侧的真实成本（编不出来、体积、
> 耗时）和功能性失败（如 IM 把动图转成静态、动画直接没了）才算约束。

因此**不保留布局在内容很高时会撞上编码器上限**，那时改用滚动视频；除此之外两种排法
在长视频里都可用。

#### 滚动视频的视口高度

视口宽度恒为 1080，高度 = **所有附件满宽后的最大高度**，不设下限。

取最大附件高度是为了保证任何附件滚到时都能完整落进视口、不被切掉。比视口矮的附件在
视口内居中、**上下填黑**；文字段滚动时同样按此视口呈现。

后果需知：全横屏素材会得到 1080×608 这样的扁视口，滚动一次只推进 608 px 内容、
总时长相应变长。

**滚动视频的真实价值有两条**：内容高度超过编码器上限时它是唯一选择；以及它提供另一种
呈现节奏（附件依次登场）。**不包括「文字更清楚」**——那是接收方观感，按上文的裁定
不作数。

#### 不需要单独的「轮播」形态

时间上逐个全屏显示附件的效果，滚动视频依次经过各附件时已经覆盖（配合已定的
「播完再滚」规则）。不再单列第三种产物。

### 组 3 — 编码（仅长视频 / 滚动视频可见）

| 选项 | 取值 | 默认 | 说明 |
|------|------|------|------|
| **编码器** | H.264 / HEVC | H.264 | HEVC 同质量体积约省 35%，但编码慢 1.3–1.5 倍，且老设备与部分接收方解不了 |
| **画质** | 三到四档 | 中档 | 见下方「CRF 无法直接暴露」 |
| **输出宽度** | 1080 / 720 / 540 | 1080 | 同时是编码器尺寸超限时的规避手段 |
| **帧率** | 24 / 30 / 60 | 30 | 高级项，可折叠 |

编码器列表须以 `MediaCodecList` 实际查询结果为准：查不到 `video/hevc` 编码器就
隐藏 HEVC 选项，而不是选了才失败。

### 组 4 — 音轨细节（仅当组 2 音轨选「指定保留」时可见）

逐个视频附件勾选是否保留其声音。

## 合成管线：帧率与分辨率怎么消化

源视频的帧率、分辨率、旋转各不相同，但这两件事**都不需要预解码或中间产物**，走
`MediaCodec → SurfaceTexture → GL` 这条路时是顺带解决的。合成阶段是**流式**的：
边解边合边编，零落盘。

### 帧率不同 → 按输出时间轴取最近前向帧

输出定一个固定帧率（默认 30fps），第 i 个输出帧的时间戳是 `t_out = i / fps`。
每个附件各自维护一个「下一帧 PTS」，渲染每个输出帧之前推进各自的解码器：

```
for each attachment a:
    while a.nextFramePtsUs <= t_out:
        a.decoder.releaseOutputBuffer(idx, true)   // 推帧到 SurfaceTexture
        a.surfaceTexture.updateTexImage()
        a.nextFramePtsUs = 下一个已解码帧的 PTS
// 此时每个 a 的 texture 都停在「t_out 时刻应显示的那一帧」，绘制即可
```

这就是 **nearest-previous / frame-hold** 采样，也正是任何视频播放器以 60Hz 刷新率
播 24fps 视频时做的事。源 24fps → 输出 30fps 时部分帧重复一次，源 60fps → 输出
30fps 时每两帧丢一帧，源 30fps 一一对应。不需要插值，不需要「对齐」算法，
只需要比较 PTS。

**「短的播完停在尾帧」天然落在这套逻辑里**（已定）：解码到 EOS 后不再推进，
`updateTexImage()` 不再调用，该 texture 就保持着最后一帧的内容，后续输出帧照常采样它。
零额外代码。

### 分辨率 / 宽高比 / 旋转不同 → 纹理坐标矩阵

附件在长图里的矩形是**布局早就定死的**（cell 尺寸约 500×500），而详情页已有一整套
裁切呈现规则（`MediaCropTransformation` / `MediaCropBitmapRenderer` /
`DetailAttachmentMediaAppearance`）。所以源是 1920×1080 还是 4096×3072 都无所谓：
统一按同一套规则映射到 cell 矩形。

在 GL 里这比在 Bitmap 里更省事——每个附件一张 external texture，配一个 4×4 纹理坐标
变换矩阵：

- `SurfaceTexture.getTransformMatrix()` 给出解码器侧的基础变换，已经把 crop rect 与
  buffer stride padding 处理掉了；
- 在它之上左乘既有裁切规则算出的矩阵，得到最终采样坐标；
- 绘到画布上该附件的 quad。**任意源尺寸 → 任意目标尺寸由纹理采样免费完成**，
  GPU 双线性过滤自带。

只有一件必须记得做：**读旋转元数据**。竖屏拍摄的视频物理上是横向存储 + 90° 旋转标记
（`MediaFormat.KEY_ROTATION` / `METADATA_KEY_VIDEO_ROTATION`），不合进变换矩阵画面会
躺倒。非方形像素（`KEY_PIXEL_ASPECT_RATIO`）极少见，v1 忽略。

### 预解码只在并发超限时才需要

因此「先一个个解码出数据、再做帧对齐」是**可行但不必要**的：帧对齐靠 PTS 比较即可，
不必先落数据。预解码的唯一用途是绕开并发解码器上限（见下方 F3 第二、三层），
与帧率问题正交。常态下走流式，零中间产物。

## 三个必须澄清的技术事实

### F1 — CRF / QP 无法直接暴露

MediaCodec 没有 CRF，那是 x264 / x265 软编的概念。它提供的是
`KEY_BITRATE_MODE`：`BITRATE_MODE_CQ` / `VBR` / `CBR` / `CBR_FD`。只有 CQ 是恒定
质量，配 `KEY_QUALITY`（0–100），但**硬编对 CQ 的支持面很窄**，须先用
`EncoderCapabilities.isBitrateModeSupported(BITRATE_MODE_CQ)` 查询，且各厂商对
`KEY_QUALITY` 的语义并不一致。

因此「画质」给档位而非数字，内部映射：

- 支持 CQ → 设 `BITRATE_MODE_CQ` + 档位对应的 `KEY_QUALITY`；
- 不支持 → 退 `BITRATE_MODE_VBR`，按 `宽 × 高 × 帧率 × 每档 bpp 系数` 算目标码率。

真 CRF 只有引入软编（NDK 版 x264/x265）才能给，但 1080×4400 软编会慢到不可用，
不考虑。若确实想要一个数字入口，可在高级里暴露**目标码率（Mbps）**——那是所有
编码器都支持的。

### F2 — 动态 WebP 逐帧是现存缺口（**已搁置，v1 不做**）

用户 2026-07-26 决定暂不考虑动态 WebP。v1 的动态源只覆盖视频、Motion Photo 与 GIF
附件；动态 WebP 附件在分享产物里停在静态首帧。以下记录留待将来。

禁用派生 GIF 后，「把所有动态源归一化成派生 GIF」这条退路没有了，于是动态 WebP
暴露出真问题：`AnimatedImageDrawable` 没有 seek / 逐帧 API，Glide 4.16 在 API 28+
只把它交还成 Drawable，项目也没有引入任何 WebP 解码依赖（已核对 `app/build.gradle`）。

两条解法：

1. 加 `com.github.zjupure:webpdecoder`（Glide 集成，底层 libwebp，提供逐帧）——推荐；
2. 用 `ImageDecoder` + `AnimatedImageDrawable` 在离屏硬件 Canvas 上按真实时间播放并
   采样——不加依赖，但采样只能实时进行（3 秒就得花 3 秒），且要挂 Handler。

GIF 附件本身不受影响：用 Glide 的 `StandardGifDecoder` 解码**源文件**是正当路径，
与被禁掉的「派生 GIF」是两回事。

### F3 — 排队与「同时播放」在长视频里是矛盾的

长视频输出是**单一时间轴**：输出第 t 帧需要所有正在播放的附件在 t 时刻的画面。
若解码器排队，附件 B 要等 A 解完，但 A 与 B 的第 0 帧必须出现在同一个输出帧里。
所以「超限就排队」不能直接施加在合成阶段。

可行的三层策略，全程无 GIF：

1. **直接并发**。附件上限 9，视频附件通常 1–3 个，而现代设备
   `getMaxSupportedInstances()` 对 AVC 常报 16 以上——绝大多数记事走这层就够。
2. **超限 → 串行预转码**。排队把每个超限附件预转成 cell 尺寸（约 512×512）的高质量
   小 MP4（H.264 高画质档），再并发合成。解码器实例数不变，但每路负载从 1080p 降到
   512×512，实际可并发数远高于标称值。这就是用户要的「放到队列里等待」，代价是一遍
   额外的转码耗时。
3. **仍超限 → 预渲染帧序列落盘**。JPEG q90 帧序列，合成时用 `BitmapFactory` 按帧读，
   **零解码器实例**，无上限。代价是磁盘：512×512 JPEG 约 60 KB，3 秒 / 30fps / 9 附件
   ≈ 48 MB 尚可，但「原时长」下会膨胀到数百 MB——因此这层只在「3 秒」档启用。

另外「逐一播放」档天然只需一路解码器，可作为超限时给用户的建议。

## 动态可见规则

| 选项组 | 出现条件 |
|--------|---------|
| 附件选择 | 附件数 ≥ 2 |
| 保留记事布局 | 产物是长视频或滚动视频 |
| 长视频入口 | 有动态附件，且内容高度 ≤ `getSupportedHeightsFor(1080)` 上限（随附件选择与布局开关实时重算） |
| 滚动视频入口 | 有动态附件 |
| 动态内容组 | 选中附件里有视频 / Motion Photo / 动图 |
| 播放编排 | 上一条成立，**且**产物是长视频 |
| 音轨选项 | 选中附件里有**带音轨**的视频（须探测，Motion Photo 内嵌视频常无音轨） |
| 音轨细节组 | 音轨选「指定保留」 |
| 编码组 | 产物是长视频或滚动视频 |
| HEVC 选项 | `MediaCodecList` 查得到 `video/hevc` 编码器 |
| 帧率 / 目标码率 | 展开「高级」后 |

## 分期建议

**先做长视频 + 保留布局**：它的几何来源（长图 cell 矩形）是现成的，内容高度也最矮、
最不容易撞编码器上限，是验证 EGL + MediaCodec 主干最稳的载体。满宽堆叠与滚动视口都是
在同一套编码骨架上换几何来源，可以后接。

| 期 | 内容 |
|----|------|
| 一 | 主干打通：EGL + MediaCodec input surface + PTS 帧对齐 + 旋转矩阵，走**长视频 + 保留布局**，固定 3 秒 / 同时播放 / 无音轨 / H.264 / 中档画质，帧源直接用原视频，接入 `getSupportedHeightsFor` 判断与入口禁用 |
| 一 · 5 | 加**不保留布局**：几何来源换成满宽垂直堆叠，其余不变 |
| 二 | **滚动视频**：视口高度规则、「播完再滚」时间轴、视口内解码调度（只解视口内附件，天然压低并发） |
| 三 | 选项面板：换掉 `TwoOptionsDialogFragment`，接入附件选择、布局开关、时长、编排、编码器、画质 |
| 四 | 音轨：解码 PCM → 混音防削波 → AAC 编码 → `MediaMuxer`，含采样率 / 声道数重采样。约 200–300 行，独立于前三期 |
| 五 | 附件单独分享（`ACTION_SEND_MULTIPLE`） |
| 六 | 并发超限的第二、三层兜底（预转码 / 帧序列），需真机实测触发频率后再定是否必要 |

## 已定规则（2026-07-26）

- **动态 WebP 不做**，v1 动态源只覆盖视频、Motion Photo、GIF 附件。
- **「原时长」下短视频播完停在尾帧**，不循环、不留黑。实现见上方合成管线一节，
  是 frame-hold 的自然结果，零额外代码。
- **滚动视频采用「播完再滚」**：不是一边滚一边播，而是滚到附件处停下播完再继续。
- **「保留 / 不保留布局」只管内容怎么排**，与「整图画布 / 滚动视口」正交；文字部分两种
  排法都原样留在顶部。
- **长视频高度超过设备编码器上限时直接禁用入口并提示改用滚动视频**，不做降宽度规避。
  这是唯一的高度限制——**不以接收方观感设限**（见上方硬约束），原先那条 4000 px
  可读性警告线已删除。
- **滚动视频视口高度 = 所有附件满宽后的最大高度**，不设下限；矮于视口的附件居中、
  上下填黑。
- **不单列「轮播」形态**——滚动视频经过各附件时已覆盖该效果。

滚动视频的时间轴据此细化为：

1. 从顶部匀速下滚；
2. 某个**附件行**完全进入视口时停止滚动，并发播放该行全部动态附件；
3. 该行最长的那个播完后恢复滚动；
4. 若停顿点上相邻行也已完全可见，合并为一个停顿点，取其中最长者；
5. 滚到底部后再停留固定时长（建议 1 秒）收尾。

总时长 = 滚动时间 + 各停顿时长之和，因此「原时长」档下滚动视频可能相当长，需要与
长视频一样在 UI 上预估并显示。滚动速度本身建议按内容高度定档（而非固定 px/s），
保证短记事不会滚得太慢。
