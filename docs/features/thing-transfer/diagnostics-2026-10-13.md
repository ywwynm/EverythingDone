# 卓易通碰一碰传输诊断

## 当前状态（2026-10-14）

用户决定暂时结束排查并提交。`TapDiagnostics.ENABLE_DIAGNOSTICS` 默认 false，所有诊断入口为 GONE；会话采集、环境及附加 P2P 查询、后台历史读写和文本导出同时关闭，不启动诊断工作线程。重试错误摘要、监听计数和八秒状态快照也随开关关闭，已有保存记录不删除。这里的开关不控制组网兼容策略。

下文保留诊断启用时的使用方式及完整迭代记录。再次采集时将上述常量改为 true 并构建 debug，正式包仍不启用。最新 v7 已证实明确 IPv4 绑定未能消除偶发 TCP 拒绝，见 [TCP 排查记录](tcp-refusal-2026-10-13.md)；不将关闭诊断表述为修复网络问题。

## 现象和边界

用户在华为鸿蒙 7 的卓易通中开启接收，用 Android 设备发送记事或文件夹；碰触后接收方很快提示失败，发送方仍显示连接进度，最终超时失败。本轮不能代做实体碰触，且没有 ADB 授权，因此交付可由用户复现并直接复制的诊断能力。尚未确认失败原因。

源码中 NFC `HELLO` 被接受后，发送方会等待接收方连接 TCP，最长 25 秒；接收方按握手配置调用 `WifiP2pManager.connect`，错误统一落到 `TapFailure.JOIN`。因此，现有两条通用提示不能区分入组服务缺失、系统拒绝、权限／配置异常、广播未到或 TCP 连不上。

## 使用方式

1. 两台设备安装包含本次改动的 debug 版本。
2. 接收方下拉并点击「接收记事」；发送方选择记事或文件夹后打开分享面板。
3. 按原步骤实体碰触，等双方显示失败。
4. 各自点击「查看／复制传输诊断」→「复制全部」，分别提供两份文本，并说明哪台运行在卓易通中。

对话框可在传输期间打开并实时刷新；关闭它仍留在原收发界面。退出后再次下拉可读取最近记录，不必再次进入接收状态。最多保存三次会话，重新打开应用仍可读取；没有隐含的上传动作。

第二版另提供固定入口：**设置 → 碰一碰传输诊断 → 复制全部**（与「碰一碰模拟」相邻）。传输成功、按钮收起或退出收发后均可使用；打开它不创建新的收发会话。覆盖安装第二版后可先复制尚未被淘汰的旧版接收记录，不必为找入口重复传输。

## 采集范围

- 版本、发布编号、Android 运行环境报告的厂商／型号／版本，NFC／HCE／P2P 能力声明，权限与开关，默认网络的 Wi-Fi／移动网络／VPN 类型。
- NFC 发现、IsoDep 连接、SELECT／GET／HELLO 的指令编号、长度与状态字，握手是否完整、总项数和端口。
- P2P 服务／通道初始化、建组／入组请求及回调错误码、连接信息、组丢失、退出清理。
- TCP 连接尝试、主机地址／端口／本地地址、异常类型／原因链／栈位置、协议头、真实字节进度、ACK。
- 文件生成与首页解析／导入的阶段、字节数和导入数。

不记录标题、正文、文件夹名称、附件内容或原始 APDU。诊断中的组名、口令、令牌、接收方随机标识、MAC 和私人文件路径会被隐藏；设备自定义名称不写入报告。

## 实现约束

`TapDiagnosticBuffer` 负责单会话脱敏、有界事件、最近失败和固定环境信息；`TapDiagnostics` 保留三次独立会话并在后台保存。每条事件含相对会话开始的毫秒数，会话头含日期、时间和时区。重试不清除错误，旧传输对象持有原会话，避免新会话接管它的迟到网络日志。

`TapDiagnosticsDialog` 继承现有 `BaseDialogFragment`，不使用粒子开关动画，避免诊断查看依赖额外动画。接收按钮和发送面板的诊断入口仅在 debug 包显示。

保持原 NFC／Wi-Fi Direct／TCP 协议、等待时限和传输失败行为。本次新增的环境查询单独记录平台查询异常；原来没有处理的入组运行时异常在记录后仍抛出。

## 首次两端反馈（2026-10-13 14:10）

两端均为 debug `202610130520`。接收方为卓易通 `HUAWEI VOL-AL00`，报告 Android 16／API 36；发送方为 `OPPO PMA110`，报告 Android 17／API 37。用户提供完整应用内文本，构成本轮可重复的人机配合诊断路径。

- 接收端：IsoDep 发现、连接正常；SELECT／GET／HELLO 全部返回 `9000`。握手长 135 字节，包含 5 个顶层项，端口 39395，SSID 长 32、密码长 8。
- `+5052 ms` 调用 `WifiP2pManager.connect`，`+5058 ms` 回调 `onFailure(0)`；仅 6 ms，尚未进入 TCP。清理时 `requestGroupInfo` 返回空组。
- 发送端：建组成功，组主地址 `192.168.49.1`，端口已监听，约 147 MB 记事文件已就绪；HELLO 被接受后等待 25 秒，没有收到 TCP 连接，最终显示 JOIN 失败。
- 两端 Wi-Fi 和定位开关开启、附近设备权限已授予、精确位置权限未授予；默认网络均为移动网络。能力声明和服务存在不能证明每条底层 P2P 操作已实现。
- 已确认的失败阶段是接收端 P2P 入组请求立即返回通用 `ERROR`；发送方超时是后续结果。尚不能仅凭 `ERROR` 区分平台适配、配置支持或权限兼容问题，不把 NFC、文件大小或广播接收当成本次已发生失败的直接原因。

## 接口核对与反向反馈（2026-10-13）

- [Android 官方接口](https://developer.android.com/reference/android/net/wifi/p2p/WifiP2pConfig.Builder)允许不指定设备地址、按网络名称查找目标；当前组名和密码配置不能仅因未提供 MAC 被判为错误。
- [Android 权限说明](https://developer.android.com/develop/connectivity/wifi/wifip2p)明确针对 Android 13 及以上目标版本的 `connect` 使用附近设备权限；本应用声明 `neverForLocation`，精确位置仅面向 API 32 及以下。两端精确位置未授予不能直接解释这次差异。
- 核对 Android 16 的 `WifiP2pServiceImpl`：包身份／权限检查不通过、底层凭配置入组失败等分支都会返回没有细分类别的 `CONNECT_FAILED`（错误码 0）。这是 Android 参考实现，不能据此断言卓易通内部走了哪个分支。
- 用户补充：反向由卓易通发送、Android 接收时，Android 实际收到记事，但卓易通最终仍提示失败。这证明该环境至少有可工作的建组／传输路径；“卓易通完全不支持 P2P”不能作为结论。
- 反向失败尚缺双方日志，需区分接收端写出 ACK 后立即离组、发送端组丢失先于 ACK 处理，以及其它结束阶段错误；不可把这次反向现象与正向的立即入组拒绝混为同一个原因。

下一次诊断补充 P2P 服务／发现／本机／网络／组状态、只读权限执行状态与异步查询的无回调标记，查询不触发发现、不延迟连接。传输故障和诊断查询异常分别记录，避免平台不支持某条查询覆盖真正的失败。

## 反向发送端日志（2026-10-13 16:16／16:20）

用户提供卓易通两次发送的完整记录，均为 debug `202610130520`，内容约 2.59 MB：

- 16:16：`+7356 ms` 已发完文件、开始等待 ACK，`+22357 ms` 恰在 15 秒读超时后报 `SocketTimeoutException`／TRANSFER。期间组广播仍为自己所建的有效组。用户说 Android 已收到记事，故需继续核对 Android 端 ACK 写出与离组时序。

- 用户反馈接收成功后诊断按钮隐藏，无法方便复制接收端记录。原有下拉／分享入口不足以支持成功之后的排查，需要增加不依赖正在收发的稳定入口。

两种方向的问题继续分开追踪：卓易通接收时的立即入组拒绝，以及卓易通发送时偶发的完成确认超时。本轮不以单边日志宣称 ACK 丢失的具体原因已被证实。

## 第三版：普通 Wi-Fi 兼容接收试验

[Android 的 Wi-Fi Direct 说明](https://developer.android.com/develop/connectivity/wifi/wifi-direct)支持由组主服务普通 Wi-Fi 客户端；[Network Request API](https://developer.android.com/develop/connectivity/wifi/wifi-bootstrap)允许按指定网络凭据发起本地连接，可能弹出系统确认框。由此选择改变接收端连接方式作为下一项对照；这只是可验证的兼容方案，不是已确认的卓易通内部根因。

- 调试版先照常发起 P2P connect，只有明确 ERROR 且新握手提供实际组地址时，才尝试同一组的普通 Wi-Fi 连接；不主动发现，不修改组名或频段，正式包不启用。
- 发送端在现有组就绪后读取实际组主 IPv4，最多额外等待 750 ms；无合法本地地址时仍提供原 P2P 握手，不猜测固定网关。v1 布局末尾增加 `WFIP` 可选字段，无卡片形状时先写零数量；旧读取器在卡片段结束，新读取器兼容无扩展的旧数据。
- `TapWifiNetworkConnection` 申请精确 SSID 的本地网络，使用系统连接确认，接收 Socket 逐个绑定返回的 Network；不调用 `bindProcessToNetwork`。新增的正常权限 `CHANGE_NETWORK_STATE` 仅写入 debug 清单。
- `TapJoinAttempt` 每次实体碰触独立；P2P 迟到成功不能在兼容路径已开始后再次下载，取消／失败后的回调不能重新激活旧尝试。网络请求在失败、退出、恢复等待和成功后释放。
- 兼容连接在写完 ACK 后，等待发送方 TCP 关闭或最多 2 秒再释放网络，避免立即撤销网络申请；这段等待失败仍交付已收齐且写出 ACK 的文件。未改普通 P2P 路径的 ACK 协议或此前反向问题的判断。
- 两端仍沿用 25 秒／22 秒连接期限；看到系统 Wi-Fi 连接提示后应及时确认。若确认流程导致页面停止、系统拒绝或仍无法连 TCP，日志均用于下一轮归因，不无限等待或自动反复请求。

验证包括新旧握手布局、可选地址校验和截断、取消后的迟到回调、重复连接回调，以及本机回环 TCP 的 ACK／关闭顺序。没有与卓易通框架等价的自动化环境，构建和 JVM 测试不能证明兼容方式已在实机成功；不能将这轮发布描述为已修复。

完整 debug 构建与 44 项相关 JVM 测试通过。已发布阿里云 debug `202610130903`，远端元数据与下载 APK 的大小／SHA-256 核验一致；下载包包含新增实现。待用户两台更新后验证系统连接回调、TCP 和结束阶段，成功或失败均保留双方 v3 报告。

## 第四版实现与验证

- `WFWT` 可选尾部声明发送等待 60 秒，旧读取器忽略尾部、新读取器对旧数据沿用 25 秒。接收的 `TapJoinAttempt` 只有在兼容切换时改为碰触后 57 秒；普通 P2P 为 22 秒。接收定时器与 TCP 重试共用本次尝试的绝对期限，取消／重复回调不能续期。允许的输入期限为 25–90 秒，损坏或越界数据在 NFC 解码时拒绝。
