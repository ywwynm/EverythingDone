# 记事传输 决策记录

本文件记录 2026-09-21 grilling 会话逐项确认的决策。每条给出决策本身与理由，
被否决的方案一并记下，避免以后重新讨论。

## 2026-09-21 - 意图：给别人一条记事，不是设备间迁移

这个功能解决的是「当面把一条或几条记事交给另一个人」，一次性、无后续关系。
接收方得到的是他自己的新记事，与发送方那一条此后互不影响。

否决的两个方向：

- **搬到自己的另一台设备**：那是 cloud-sync 的职责，需要保 ID、去重、冲突处理，
  等于把同步协议换个传输通道再实现一遍。
- **两个人协作同一条记事**：需要长期关系与共享身份，远超一次触碰的语义，
  且服务端尚未存在。

## 2026-09-21 - 接收方必须也安装完事儿，用私有格式换取全保真

交换格式是私有的（JSON + 附件，zip 打包）。类型、Thing Background 颜色、
清单层级、提醒规则、习惯周期、卡片与详情外观全部过去。对方没装应用，
拿到的就是一个打不开的文件。

现有的纯文本分享（`SendInfoHelper.shareThing`，产物是拼接文本 + 图片原件）
作为另一条独立的路保留，服务于「接收方不一定装应用」的场景。两条路各管各的，
不合并成一个兼容产物——那样两边都做不好，附件也无处安放。

## 2026-09-21 - 范围：单条 + 多条，不含 Thing Folder

格式顶层是数组，单条是长度为 1 的特例。发送入口挂在详情页分享与
`ThingsActivity` 选择模式两处，后者已有批量导出（`ThingsActivity:12190`），
位置现成。

Thing Folder 暂不支持：需要带嵌套层级、决定导入后落到哪里、处理重名与
Projection Folder 语义，复杂度明显跳一档。

## 2026-09-21 - 附件全部内嵌，可逐个勾选，不设体积上限

附件文件本体进 zip，`Thing.attachment` 里的绝对路径重写为 zip 内相对路径
（`attachments/...`），导入时复制到本地目录再写回绝对路径。

沿用 share-screenshot 组 1 已有的附件勾选交互，默认全选，用户可以只给一部分。
体积只在界面上报数，不做阻挡、不降质——与 share-screenshot 的硬约束
「不以接收方观感设限」一致，且资源成本由用户裁定。

参考量级：带 9 张原图约 30–45 MB，带一分钟视频可能 100–200 MB。通道由用户
在分享面板里现选（互传约 20 MB/s 无所谓，微信有 100 MB 上限），我们不做假设。

## 2026-09-22 - 补回 ACTION_VIEW 文件关联（推翻前一条的一半）

用户指出「对方在文件应用里打开 `.edthing`，不显示能用完事儿打开」。这是真缺口，而且
下面那条决策里放弃文件关联的理由**只对了一半**：

- 对的那半：`content://` URI 的路径通常不含扩展名，`pathPattern` 确实匹配不上。
- 错的那半：「按 MIME 注册会去抢所有 zip 的打开权」——那是针对 `application/zip` 说的。
  而 `.edthing` 的实际判定是 **`application/octet-stream`**（后来实测 MediaStore 得出），
  那是未知类型的兜底，两回事。真机查下来**整台设备上注册
  `VIEW + octet-stream` 的应用只有一个**（三星上是爱奇艺），根本不会把「打开方式」撑乱。

因此补上三条 `ACTION_VIEW` filter：

| filter | 覆盖 |
|---|---|
| `scheme=content` + `mimeType=application/octet-stream` | 主路径：文件管理器传来的 content URI |
| `scheme=file` + `pathPattern=.*\.edthing` | 兜底：少数仍用 file:// 的场景，可精确匹配扩展名 |
| **不注册** `VIEW` + `application/zip` | 那会抢走所有 zip 的打开权，代价不值 |

真机验证（魅族）：系统「打开方式」列表里出现「导入记事 / 完事儿」，与文档查看器、
文件管理并列；选中后预览列表正确列出 2 条记事、各 3 个附件。

**一个测试方法上的坑**：用 `am start` 手工构造 VIEW Intent 时若不加
`--grant-read-uri-permission`，会报 `has no access to content://…`——那是构造的 Intent
缺 flag，不是功能缺陷，真实文件管理器会带上。

## 2026-09-22 - `file://` 读不了是死路，改为引导用户走文件选择器

用户从三星导出、经魅族互传收到文件后，在文件应用里打开，报
`open failed: EACCES (Permission denied)`，路径是 `/sdcard/Download/MzShare/…`。

**这不是代码能绕过去的**：

- 互传落地的文件属于**互传应用自己的 uid**（实测 `-rwxrwx--- u0_a156`），别的应用无权读。
- 完事儿在 Android 13+ 只有 `READ_MEDIA_IMAGES/AUDIO/VIDEO`，而记事文件不是媒体，
  一条都不覆盖；`READ_EXTERNAL_STORAGE` 从 Android 13 起已被拆掉。
- 所以凡是以 `file://` 交过来、又落在别的应用目录里的文件，直接读一定失败。

**但不能因此删掉 `file://` 的 filter**——那样完事儿会从「打开方式」列表里消失，
用户连入口都找不到，比失败更糟。

采用的做法：读失败时**给一条走得通的路**，而不是只报一句权限不足。
`ThingFileReader.Result` 新增 `NoAccess`，导入界面据此把提示换成
「这个文件存放在其他应用的目录里…点下方按钮，在文件选择器里选中它就能导入」，
并把底部按钮变成「去选择这个文件」，点了走 `ACTION_OPEN_DOCUMENT`——
SAF 给的 content URI 是有权限的。

判定靠异常消息里的 `EACCES` / `Permission denied` / `has no access`（逐层查 `cause`），
因为它会被包在 `FileNotFoundException` 之类里，没有专门的异常类型。

## 2026-09-23 - 导入的记事一律落在根目录；附件勾选延后

代码检查发现：导入器把 `folderId` 置空，`ThingManager.create` 却会把空值换成首页当前所在的
文件夹，于是导入的记事落在哪里取决于进程是否还活着、用户上次停在哪个文件夹——可能是私密
文件夹，也可能是回收站里的已删除文件夹。

用户决定：**先统一落根目录**。以后会设计新的导入入口，那时再明确是根目录还是文件夹。
实现上给 `ThingManager.create` 加了 `inheritCurrentFolder` 参数（默认 true，详情页新建不受影响），
导入传 false；并且只有首页正显示「根目录 · 未完成 · 不筛类型 · 不在搜索」时才把导入的记事
直接插进内存列表，其余情况等首页收到 justNotifyAll 后从数据库重读。

同日用户决定：决策「附件可逐个勾选」的界面实现放到缺陷修完之后再做（见 followups.md）。

## 2026-09-23 - 私密鉴权回到调用方；详情页分享不再重复验证

原实现把鉴权写在 `ThingFileSharer` 内部，结果详情页打开私密记事后点「记事文件」会再验证一次，
与本文件「Private Thing 可以传」一节的「详情页访问即信任、鉴权做在调用方」相反。改为：
`ThingFileSharer` 不做鉴权；`ThingsActivity.shareSelectedThingsAsThingFile` 照
`exportSelectedThingsWithPrivacyAuth` 的写法先鉴权，**鉴权通过后才退出选择模式**，取消时选择保留。

## 2026-09-23 - 过期提醒以「已过期」写入，不设闹钟

「过期提醒按应用现有的过期表现走」的具体含义定下来了：照 `AlarmHelper.createAllAlarms`
（开机与恢复时的做法），提醒时刻已过的直接标 `EXPIRED`、不设闹钟。原实现一律按未响写入，
闹钟设在过去的时刻会立即触发，导入那一刻就弹通知（开了「提醒时自动开始」还会直接进入进行中状态）。

## 2026-09-23 - 清单里类型与提醒、习惯不一致时，照应用自己的纠正规则改成 NOTE

提醒类型却没带提醒、习惯类型却没带习惯（或习惯周期解析不了）一律改成 NOTE，与
`RemoteActionHelper.correctIfNoReminder` / `correctIfNoHabit` 相同；NOTE 带着的提醒与习惯丢掉；
不认识的类型（表头、欢迎、通知等）整条跳过。正常导出的文件不会出现这些情况，只防畸形文件——
原样导入的后果是习惯记事点开即崩、笔记上响闹钟。

## 2026-09-22 - 选择模式菜单的文案改成动作式

「记事文件」在分享对话框里与「文本与图片」「长截图」并列，都是产物名，读得通；但在选择
模式菜单里它和「完成所选记事」「移动到文件夹」「导出到 SD 卡」这些**动作**并列，一个光秃秃
的名词读者不知道要干什么。菜单里改用 `act_share_selected_as_thing_file`（「分享为记事文件」），
分享对话框仍用产物名。

## 2026-09-21 - 接收入口：ACTION_SEND 接收 + 应用内导入，不依赖文件类型关联

两条都是确定可靠的机制：

- **ACTION_SEND 接收**（主路径）：manifest 里已有 `text/plain` / `image/*` 的
  接收声明，再加一条我们自己的类型。接收方在文件管理器里选中文件 → 分享 →
  选完事儿。
- **应用内导入**（兜底）：系统文件选择器自己挑。

否决 `ACTION_VIEW` 文件类型关联作为承诺功能。原因是确定的平台行为：跨应用传来的
是 `content://` URI，其路径通常不含文件名与扩展名（可能是
`content://media/external/file/12345`），`intent-filter` 按 `pathPattern` 匹配
扩展名匹配不上；按 MIME 注册则要么无人认得自定义类型，要么注册
`application/zip` 去抢所有 zip 文件的打开权。留作 followup，有真机验证再说。

## 2026-09-21 - 导入语义：忠实复制，提醒会真的响

类型、颜色、内容、附件、外观、完成状态、创建时间、提醒时刻全部原样过去。
传一条「周五 15:00 开会」给同事，他周五真的会响——这正是传它的目的。
过期提醒按应用现有的过期表现走，不猜测地顺延。

确定不过去的字段（无需讨论）：

- `Doing Thing` / `Ongoing Thing` 标记：设备本地状态
- `folderId`：文件夹不传
- `location`：本地列表排序位置，导入时重算到顶部
- `Habit.remindedTimes`：对方已提醒多少次
- `HabitRecord` 全部打卡记录：对方的履历，不是这条习惯的定义。习惯过去的只有
  周期定义与提醒时刻，打卡从零开始

## 2026-09-21 - Private Thing 可以传，但序列化时去掉私密标记

私密编码在标题前缀（ADR-0011），直接写 `thing.title` 会让前缀跟着过去，
接收方导入后那条记事自动就是私密的——「什么都不做」的默认行为不是中立的。
因此要**显式去前缀**。

理由：私密是本设备的展示层保护，不是内容加密（ADR-0012 已明言不承诺密码学
保证）。带着标记过去会让接收方以为这条记事是加密的，与实际保护强度不符；
而且他刚收到就要指纹或密码验证才能看，没有道理。

选中含有效私密记事时，发送前先鉴权一次。这条有现成模式可直接照搬：
`ThingsActivity.exportSelectedThingsWithPrivacyAuth` 用
`ThingPrivacyResolver.isEffectivelyPrivate` 判定、`AuthenticationHelper.authenticate`
鉴权，理由与导出相同（内容会明文离开本机）。项目里 `isEffectivelyPrivate` 已有
37 处调用点，新增的发送路径必须是第 38 处，不能绕开。

注：ADR-0011 要求的集中入口做在**调用方**而非 helper 内部，`SendInfoHelper` 与
`ThingExporter` 自身不含私密判定是正常的。详情页的单条分享与导出无需额外鉴权——
能看到内容说明用户已经通过鉴权（访问即信任）。

## 2026-09-21 - 与 cloud-sync：共用字段映射，不等 P1

cloud-sync plan 的 5.3 字段分域表已经把 Thing 的全部字段列完，`THING` 实体本来
就把 reminder / habit 折叠进同一 payload。序列化照那张表写，两边字段映射从一开始
就是同一份，不会漂移。

不等 cloud-sync 的 P1：

- **uuid 列**：本功能只需要一个「这份文件是哪一份」的标识，导出时现生成即可，
  不需要 DB 迁移。
- **`ed://sha256` 附件引用**：本功能不需要。zip 内走相对路径即可；sha256 是
  cloud-sync 为秒传与跨设备去重才要的。

P1 落地后本格式不用改，只是多了 sha256 可用。

## 2026-09-21 - 导入确认：预览列表 + 逐条勾选 + 重复标注

列出每条的标题、类型、颜色、附件数、提醒时刻，默认全选。与本地内容指纹重复的
标出来并默认不勾选。

事前确认是被既有决策定死的：ADR-0005 已全局移除撤销机制，状态变更统一改为
操作前确认，「先导入、不对再撤销」等于推翻那份 ADR。ADR-0005 留的例外是
「单条直接手势保持即时」，理由是高频核心手势，导入不属于这一类。

去重判据沿用 cloud-sync「首绑定归并」的内容指纹思路。代价是导入那一刻要对本地
记事算一遍指纹，几千条量级可接受，因为导入不是高频操作。

## 2026-09-21 - 发送入口：分享对话框第三项，顺带换掉两选对话框

详情页菜单里 `act_share`「分享」与 `act_export`「导出到 SD 卡」是两个不同动作：
前者走分享面板发出去，后者存在本地。本功能要的是发出去，归前者。

`TwoOptionsDialogFragment` 只能放两项，装不下第三个，正好换成 share-screenshot
plan 里要的那种能放入口列表的对话框；之后长视频、滚动视频、附件单独分享三个
入口直接往里加。

命名定为「**记事文件**」，副文案写明「对方需安装完事儿」。两个选项并列时，用户
需要的信息不是产物形态而是**接收方是谁**，名字里必须带这个信息。候选中
「记事原件」没说清限制，「分享给完事儿用户」说清了但破坏三项并列的结构。

## 2026-09-21 - 不在界面上承诺互传，但应用内碰一碰是单独一期的目标

一期只把文件交给系统分享面板，副文案不提互传——互传能不能用取决于双方设备，
我们判断不了，任何承诺性文案都可能是错的。

真正想要的形态是**双方都打开完事儿，一方在详情页或多选界面、另一方在首页，
碰一下直接触发传输并配动画**。这一条单列为二期，可行性需先在真机上验证。

## 2026-09-21 - 应用内碰一碰的技术形态与硬约束

调研结论：这条路成立，原理与系统碰一碰相同——**NFC 只传握手信息（对方是谁、
走哪个通道、一次性令牌），数据走 Wi-Fi Direct**。开源实现与专利文献都有完整描述。

厂商那条路已查证走不通：小米、OPPO、vivo 开放平台均未对外提供互传 SDK，只有
推送、传包、统一链接；互传联盟 2026-09-16 发布的碰一碰互传标准直接做在系统底层，
应用侧的接入点就是标准的 `ACTION_SEND`。华为 Share Kit 是唯一有应用内碰一碰
API 的，但它是 HarmonyOS NEXT 的 ArkTS 接口，Android 应用用不了。Android 原生的
NFC P2P（Android Beam）Android 10 废弃、Android 14 移除。

`enableReaderMode` 的文档行为带来三条硬约束：

1. **角色必须分配**。读取模式在 Activity 前台时独占 NFC 控制器并禁用本机卡模拟，
   一台设备不能既读又被读。「一方详情页或多选、另一方首页」的分工是必需的，
   不是可选的。代价是两人都在首页时碰了没反应，界面要说清楚。
2. **接收端不能在首页常驻读取状态**。读取模式会暂停系统级 NFC 轮询，常驻意味着
   用户停在首页时公交卡、门禁、系统互传全部失效。必须改成显式且有时限的
   「准备接收」。这一点与最初设想有出入。
3. **发送端卡模拟必须有前台状态门控**。卡模拟是后台服务，不设门控的话任何人拿
   手机碰你都能读走记事。只有在详情页或多选界面且用户明确选了要发时才响应。

已知风险：NFC 天线位置没有厂商标定、可能被默认钱包应用抢占、Wi-Fi Direct 建连
通常 2–10 秒且会失败、部分机型没有 NFC。

## 2026-09-21 - 二期先做真机可行性验证，用独立的最小 APK

碰的那一下必须由用户本人完成，adb 做不出这个动作。

验证程序做成**独立的最小 APK**，两台各装一个，验完卸载。不把卡模拟服务塞进主
应用——那会让完事儿出现在系统设置的「NFC 卡模拟应用」列表里，不该为一次验证
背这个；独立 APK 也编译得快，改一版重装一版代价低。

包名必须独立（不能是 `com.ywwynm.everythingdone`），否则与设备上已安装的完事儿
冲突。代码放 `docs/features/thing-transfer/probe/`，与功能文档同目录；
`settings.gradle` 里 include 并把 `projectDir` 指过去，这样仍能用现有的 wrapper
与 SDK 配置一条命令出包。

## 2026-09-21 - 验证一次验到底，含 Wi-Fi Direct 建连与传文件

不止验 NFC 握手，连 Wi-Fi Direct 建连与实际传文件一起验，这样一轮就能回答
「从碰上到传完要多久」，而不是验通了握手还不知道整体体验如何。

建连采用**发送端提前建组**的做法：发送端先 `createGroup()`，把 SSID 与密码写进
NFC 握手内容，接收端读到后当普通 Wi-Fi 客户端直接连上去，跳过 Wi-Fi Direct 的
发现与 Group Owner 协商——那两步正是 2–10 秒里最慢的部分，系统碰一碰也是这么做的。
代价是 SSID 与密码要塞进 APDU，因此「握手一个来回能装多少字节」是要先量的第一个数。

测试文件三档：1 MB、10 MB、100 MB。附件不设体积上限，大文件的表现必须知道。

## 2026-09-21 - 只验 NFC，二维码不作为备选一起做

二维码能承载完全相同的握手内容（QR 容量约 2900 字节，远大于标准 APDU 的 255），
Wi-Fi Direct 那段代码两条路共用，增量只是一个显示界面加一个扫码界面，且不依赖
NFC 硬件、不会被钱包应用抢占、没有 ROM 差异。

仍然只验 NFC：用户要的是「碰一下」这个动作本身，扫码不是碰，一起做会分散这一轮的
注意力。二维码记入 followups，NFC 若被否决再取用。

## 2026-09-21 - 一期实施期的三处调整

写代码时撞上的三处技术约束，都收窄了原决策：

**其一 · 分享对话框沿用现成的三项版，不造列表式对话框。**
`ThreeOptionsDialogFragment` 已存在（`SettingsActivity` 在用），接口与两项版完全对称，
三项正好放得下。等 share-screenshot 的长视频、滚动视频、附件单独分享真要加进来时
再换成列表式，届时改动更小也更好回退。

**其二 · 导入的记事一律以「未完成」写入，`finishTime` 清零。**
`ThingsCounts.handleCreation` 硬编码 `Thing.UNDERWAY`，带着「已完成」直接建会让计数与
数据库里的 state 对不上；而改走 `ThingManager.updateState` 需要记事在内存列表里的
`position`，那是为 UI 交互设计的路径（操作内存列表、异步执行 DAO），批量导入里用容易
出错。完成状态对接收方的意义远低于类型、颜色、内容、附件、提醒，2026-09-21 用户确认
收窄。其余字段仍然忠实。

**其三 · 「对方需安装完事儿」改用生成后的提示给出。**
分享对话框的三项是等宽单元格、`maxLines=2`，加副文案会让三项高度不齐。名字就叫
「记事文件」，限制信息在产出文件、拉起分享面板时用 Toast 说明。

### 一期实施期定下的三个原未定项

- **格式版本**：清单带 `version` 整数。读到比本机大的版本一律拒绝并提示升级；
  小于等于则接受，不认识的字段直接忽略。
- **部分失败**：逐条独立导入，某条失败不影响其他条，最后报告「已导入 N 件，M 件失败」。
  解析阶段同样逐条独立。
- **扩展名**：`.edthing`。MIME 按实际形态声明为 `application/zip`。

## 2026-09-21 - 分期：一期记事文件先发一版，二期应用内碰一碰接着做

可行性验证通过后定的（7 轮全过，详见 sessions.md）。一期把记事文件格式与导入做完并发一版，
用系统互传就已经能碰；二期再接 NFC 握手与 Wi-Fi Direct。

理由是格式层先在真实使用中跑过一轮，之后出问题时分得清是格式还是传输。反过来一次做完，
格式层的问题要等到最后才暴露，而那时 NFC 那一层也在同时测。

### 验证结论对一期决策的影响

两条原先的估计被实测推翻，但**都不需要回头改决策**：

- **建连不是 2–10 秒，是 0.6–3 秒**（T2 实测 565–2997 ms）。
- **速率不是 3 MB/s，是 43–68 MB/s**（1 MB 测出的 3 MB/s 是 TCP 慢启动的假象）。
  100 MB 的记事碰一下不到 3 秒 —— 「附件内嵌、不设体积上限」这条决策因此更站得住。

新增一条二期实施时必须注意的：**Group Owner 的地址不能写死**。三星当 GO 时是
`192.168.49.1`，魅族当 GO 时是 `192.168.90.70`。

## 2026-09-21 - 验证判据：先定否决线，实测后再定最终标准

**否决线**：碰上到开始传超过 10 秒，或 10 次里成功少于 7 次——这条路直接否掉。

在否决线之上的数据出来再讨论体验可不可接受。不直接对标系统碰一碰的
「3 秒内、10 次 9 成」，因为系统那套有厂商天线标定与底层优先级，第三方应用大概率
追不上，用它当门槛可能误杀一个其实能用的方案。

各阶段耗时要分开记：碰上到握手完成、握手完成到 Wi-Fi 连上、连上到传完。
出问题时才分得清是哪一层。
