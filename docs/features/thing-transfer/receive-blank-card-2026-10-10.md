# 批量接收后滚动出现空白卡片

## 问题与调试范围

用户报告 2026-10-08 在设备 A 一次发送多条记事到设备 B，其中一条包含视频和大量清单项。接收后直接滚动首页，这条记事的位置仍占据空间，但内容完全不可见。

2026-10-10 授权调试三星 `R5CW20BLNKL` 与魅族 `192.168.100.67:42641`，不得影响已有记事。开始时两台均在桌面，应用进程已退出；魅族未见完事儿通知记录，无法直接读取原问题发生时的内存状态。

## 可重复的验证

新增 debug 专用 `TapReceiveVisibilityProbe`：使用生产 `ThingsAdapter`、两列 `StaggeredGridLayoutManager`、默认两项缓存及只在内存中创建的记事／文件夹。测试不调用导入器或 DAO 写入。视频来自既有 debug 测试素材，清单 36 项。固定卡片几何使不同设备都只将第一张长卡片移进缓存，关闭预取以保证验证缓存复用，而不是重新绑定。

顺序：按真实接收设置隐藏 → 绑定卡片 → 滚到屏外并确认进入 `mCachedViews` → 按首页接收回调清除隐藏标记并查找当前 holder → 滚回来。必须证明复用同一视图且未发生重新绑定。

三星未修复版结果（`tmp/tap-visibility-20261010/samsung/before2/result.json`）：

| 场景 | 缓存原视图且无重绑 | 滚回后的状态 |
| --- | --- | --- |
| 普通记事 | 是 | `INVISIBLE`，1380×1290，占位空白 |
| 视频＋36 项清单 | 是 | `INVISIBLE`，1380×1290，占位空白 |
| 文件夹 | 是 | `INVISIBLE`，1380×1290，占位空白 |
| 截图阶段 `alpha=0` | 是 | `VISIBLE` 但 `alpha=0`，仍为空白 |
| 回收后改绑另一项 | 不适用 | 旧 id 的揭示未误显另一项 |

测试前后逐行摘要比较数据库全部表；`things` 仅排除启动时自动重建的系统 header（`type=-1`），其余行和所有其它表均一致。首次夹具将滚动终点取为卡片底边，漏算下外边距，导致仍挂在列表上的卡片未进入缓存而超时；补上下外边距后才得到上述有效复现。

## 排查假设

1. 接收回调只恢复挂在列表上的 holder，遗漏已绑定但暂存在 RecyclerView 缓存的隐藏视图。预测：原视图无重绑返回且仍隐藏；恢复缓存中的接收视图应消除问题。
2. 视频加载或清单绘制失败。预测：去掉复杂内容就不能复现；普通记事的对照可以排除这一条件。
3. 接收动画没有正常结束。预测：明确清除接收隐藏标记后仍有待结束动画；直接调用显示收尾、无动画的最小场景可以排除这一条件。

## 原因

`ThingsActivity.revealTapReceivedThings` 清除 `ThingsAdapter` 的隐藏 id 集合后，只通过 `findViewHolderForAdapterPosition` 恢复当前附着的视图。该查询不覆盖 `RecyclerView.mCachedViews`。缓存中的卡片滚回时可直接复用，不触发 `onBindViewHolder`；因此绑定入口里的可见性／透明度重置没有机会执行。

普通记事、视频清单和文件夹都能复现，且无需运行动画；视频／清单使卡片更高，批量插入与让位更容易将已有隐藏卡片挤进缓存，但不是数据损坏或解码失败的必要条件。

## 修复与复验

- `ThingsAdapter` 用 `WeakHashMap<View, Long>` 记录本次接收实际隐藏过的视图及其 stableId。清除某条记事或文件夹的隐藏标记时，同时恢复对应视图的可见性和透明度，包括暂存在 RecyclerView 缓存中的视图。
- 绑定、真正回收时解除旧归属；已经揭示过的视图也立即解除归属。这样既支持同一 id 短暂对应多个 holder，也不会让晚到的旧回调误显另一条记事或其它动画隐藏的视图。
- `ThingsActivity` 只负责按 stableId 通知适配器恢复，删除只能查找附着 holder 的重复恢复逻辑。不全量刷新、不触发复杂卡片重绑、不改传输数据或粒子动画时序。
- 三星与魅族各 6 项真机回归全部通过：普通记事、视频长清单、文件夹、透明快照阶段、回收改绑保护、同 id 多 holder 与归属释放。前 4 项均确认原 holder 无重绑返回，状态为 `VISIBLE`、`alpha=1`。
- `:app:assembleDebug` 与碰一碰相关 69 项 JVM 测试通过，`git diff --check` 通过。
- 三星 371 条、魅族 180 条现有用户记事及数据库其它表的逐行摘要全部保持一致。未改设备设置或处理通知；测试后回到原桌面，测试视频与设备上的结果 JSON 已清理，本机原始结果保留在 `tmp/tap-visibility-20261010/`。
- 魅族回归本身一次通过；读取结果时发现 Flyme 禁止 `run-as` 读取应用外部私有目录，驱动改为解析 Instrumentation 已返回的同一份 JSON，无需重跑测试。

验证边界：这次复现了与用户描述一致的列表缓存故障，未进行实体 NFC 触碰或复传用户原记事。原始故障现场的应用进程已经退出，无法断言该条原始记事当时的所有运行时状态；网络、导入器和记事内容编码均未改动。
