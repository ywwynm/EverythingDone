## 卓易通接收时建组，Android 碰触后加入并发送

用户已经验证卓易通建组、Android 加入可以传输；卓易通作为接收方时，原 P2P 快速入组立即返回 ERROR，普通 Wi-Fi 兼容方式则需要系统窗口确认。此次按用户要求分离网络角色和记事方向，让卓易通无论发送还是接收都优先负责建组，以便测试碰触后自动连接。

- 新增 `TapReceiverGroupOffer` 和 NFC 接收组协商：SELECT 可选能力位、`0x11` 短 APDU 在一次碰触里交付组凭据和接收标识。旧版仍使用原 HELLO，双方更新才能使用新流程。
- `TapReceiverGroupHost` 提前准备接收组和 TCP 监听。`WifiDirectSenderTransport` 收到协商后释放原发送组，查询确认退出，再加入接收组并主动连接。网络地址从实际连接信息取得；完成后恢复发送组，保留本次分享令牌和已收设备记录。
- `TapReceiverServer` 先校验本次 NFC 的令牌和接收标识，再沿用原文件与 ACK 协议。所有接收路径回 ACK 后均等待发送端关闭 TCP，最多两秒，再释放网络，减少确认尚在本机缓冲时就断网的机会；并不据此宣称已定位此前偶发 ACK 超时的全部原因。
- 调试版对日志中已观察到的 HUAWEI／System 环境默认启用接收建组。诊断窗口增加“接收时由本机建组”开关，下次进入接收时生效。旧发送方或准备失败继续使用原接收路径，保留普通 Wi-Fi 兼容连接作为对照。
- 首页和详情增加接收准备提示，准备完成才接受碰触。诊断升级为 v5，记录协商方向、退出原组、入接收组、主动 TCP、身份确认及清理；保留设置入口、复制和文本文件分享，不记录组密码、令牌或记事内容。

完整 debug 构建及 79 项相关 JVM 测试通过，包括新旧 NFC、短 APDU 上限和损坏输入、真实本机 TCP 传输与 ACK、错误身份、连接方向互斥、取消及超时竞争；修改空白检查通过。没有使用 ADB 或连接设备，没有创建 Git 提交。实际 NFC／Wi-Fi Direct 和系统是否完全不弹确认仍由用户实测。

两台都更新。卓易通进入接收后，等“正在准备接收”消失再碰触；先测试 Android 发往卓易通，再测试卓易通发往 Android，以及连续收发。若异常，从“设置 → 数据 → 碰一碰传输诊断 → 分享文件”提供双方 v5 日志。需要对比旧方式时，仅在卓易通关闭诊断中的接收建组开关，退出并重新进入接收。
