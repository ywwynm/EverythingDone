## 接收附件保留原文件名，重名时追加编号

用户反馈碰一碰传输和更新记事会把附件重命名成应用生成的格式，希望保留原文件名，仅在重名时追加 -1、-2 等后缀。

排查确认发送清单已经包含原文件名，但 ThingFileReader 只在报错时使用它；原导入器固定生成 import_ 加时间戳及序号的名称。现通过 PendingThing.attachmentNames 将清单名称传至共用的 ThingFileAttachmentStore，普通碰一碰接收、文件夹批量接收、更新当前记事及 .edthing 导入统一采用原名。例如照片.jpg 首次接收仍为照片.jpg；目标目录已有同名文件时，依次使用照片-1.jpg、照片-2.jpg。扩展名大小写及无扩展名的情况保持原状。

分配目标文件时使用原子创建，防止并发导入覆盖；文件名中的路径、非法字符、附件分隔符与超长名称按存储要求处理，失败时清理本次新文件。附件内容不变，卡片与详情外观继续映射至对应附件。更新中按内容复用的已有附件保留当前路径、名称、修改时间和有效视频 GIF，不追溯重命名旧附件，也不影响撤销／重做引用。

修复前原名和重名编号两项测试均失败；修复后 170 项相关 JVM 回归全部通过，含 13 项文件存储、10 项真实 TCP 协商和既有外观映射检查。同步修正既有 TCP 拒绝测试在 Windows 写入阶段遭遇连接重置时的预期处理，生产认证逻辑未变。完整 debug APK 构建成功。最终构建保留另一个会话刚发布的 GIF 重播崩溃修复，并复跑其 11 项相关检查。

本轮没有通过 ADB 连接设备；实际碰一碰及更新后的名称显示由用户安装更新后确认。代码和文档保留在工作区，未创建 Git 提交。
