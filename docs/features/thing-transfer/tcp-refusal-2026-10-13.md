# 接收建组后 TCP 偶发拒绝（2026-10-13）

## 实机证据

用户提供两端 debug `202610131115` 的 v5 文本报告：`TapDiagnostics-20261013-202758-5692883679815089803.txt`（卓易通）和 `TapDiagnostics-20261013-202808-7965543032132461783.txt`（OPPO）。本轮只将 20:27 的第三次会话配对；两份报告内较早成功记录的时间和内容不同，不能按会话编号视为同一次传输。

- 卓易通先建组并监听 TCP 42689，NFC 完整成功，双方选中接收方建组流程，开始等待发送方连接。
- OPPO 保留的多次连接均指向 `192.168.49.1:42689`，多数错误中的本地地址是 `192.168.49.4`，返回 `ECONNREFUSED`。接收方没有记录到有效 TCP 连接，最终到达 32 秒连接期限；发送方随后到达 35 秒期限。故障位于 TCP 建连，尚未进入文件或 ACK 阶段。
- 接收方 `Socket closed / accept failed: EINVAL` 出现在超时关闭监听之后，不能当作最初根因。当前 `cancelled` 只看 generation，未包含尝试已经结束，导致清理异常显示成新的传输失败。
- 发送方每约 250 ms 重复记录完整异常，挤掉较早 163 条事件，无法核对最初的组切换及连接过程。最后一次迟到异常使用普通 Wi-Fi 地址，此时接收方已经超时拆组，不能倒推最初路由就是错误的。
- 卓易通另一接收会话成功传输 173,106,537 字节并完成 ACK、TCP 结束、导入，证明该路径有成功实例，不证明稳定性。

## 假设与下一轮判据

按当前证据优先级排列：

1. 卓易通监听端口没有持续暴露在当时的 P2P 网络：预期应用监听仍开放、组和接口地址有效、OPPO 使用对应 P2P 本地地址，但始终没有原始 TCP accept。
2. 发送方入组后的地址或路由尚未稳定：预期失败阶段的组主地址、接口 IPv4 或实际 Socket 本地地址不一致，随后变化；需要保留第一次失败前后的状态。
3. 应用提前关闭或替换了监听：预期在第一轮连接失败前有明确 close 原因、端口变化或监听关闭状态。

无可用的卓易通实体调试环境，普通 JVM 回环连接不能复现兼容层的网络映射。因此不直接改绑定地址、组网顺序、期限或设备识别规则。沿用用户此前授权的可复制诊断方案，补足上述边界；本地自动化只验证诊断保留、限流以及真实 Socket 的生命周期，不据此宣称实机连接故障已经修复。

## 本轮处理范围

保留关键组网事件和第一次连接异常，对重复异常汇总；补充监听地址／开放状态、原始 accept、关闭原因、组接口和本地 IPv4 的只读记录。已结束尝试的关闭异常记为清理事件，避免覆盖最初超时。诊断仍仅在 debug 本地保存，不记录组名、密码、令牌或记事内容。

## 实现与验证

- `TapDiagnosticBuffer` 通过连续 140 次连接异常的回放测试复现关键事件丢失，修复后保留独立的至多 20 条／8,000 字符关键事件；该区和滚动区使用同一脱敏流程。历史读取上限相应增加，仍只保存最近三个会话。
- `TapConnectRetryLog` 在第一次连接失败时保存完整异常，此后每五秒和结束时汇总次数、耗时、外层源地址及底层错误；迟到失败不覆盖已经结束的连接尝试。普通接收主动连接和接收建组时的发送主动连接共用此诊断逻辑，不改变重试间隔或连接期限。
- `TapReceiverServer` 记录绑定地址、关闭状态、accept 调用次数、原始连接计数和关闭原因。接收建组就绪、NFC 完成、等待八秒、超时关闭前均有状态快照；发送方入组后和首次连接失败时查询组状态与接口 IPv4。查询结果不控制传输流程。
- `WifiP2pGroup.getInterface()` 提供组接口名，`ServerSocket.isBound()`／`isClosed()` 仅提供本地对象状态，不能单独证明兼容层已对外暴露端口。公开 API 依据：[组接口](https://developer.android.com/reference/android/net/wifi/p2p/WifiP2pGroup#getInterface())、[监听状态](https://developer.android.com/reference/java/net/ServerSocket#isClosed())。
- 本地完整 debug 构建和 109 项碰一碰相关 JVM 测试通过；新增 4 项覆盖事件保留、容量上限、整段重试的汇总和错误变化，已有真实 Socket 取消测试扩充为验证原始 accept 与仅一次关闭原因。没有连接任何设备，未证明卓易通网络映射故障已修复。

已发布阿里云 debug `202610131257`，远端元数据、发布说明和重新下载 APK 的大小／SHA-256 均与本地发布记录一致，下载包包含 v6 标记。APK 为 30,571,105 字节，SHA-256 `b1182a334c8318b362d84178a1274b72a1719761e0acbbf5864fec7f862c38fc`。测试、发布完整输出分别位于 `memory/tap-tcp-diagnostics-build.txt` 和 `memory/tap-tcp-diagnostics-publish.txt`。

## v6 实机反馈：监听持续开放但没有原始连接

用户提供 21:17 和 21:22 导出的四份 v6 文本，两端均为 debug `202610131257`：

- 21:16 会话的接收端口为 44165；OPPO 确认退出原组后加入目标组，本地 P2P 地址始终为 `192.168.49.4`，对实际组主 `192.168.49.1` 的 110 次连接失败。卓易通的组接口为 `p2p-p2p0-10`、地址为 `192.168.49.1`，中途与超时前均有一个客户端。
- 接收监听从就绪到超时始终 `closed=false`、`closeRequested=false`，32 秒内执行 128 次 accept 等待、`rawConnections=0`；超时后才记录明确关闭原因。现在可排除应用提前关闭或替换该端口这一假设。
- 同批日志中的 21:03 双端记录可以按端口 32977 和 173,106,510 字节内容配对，确认建组、TCP、文件、ACK 成功。21:05 接收 17,520,659 字节也成功，但没有对应发送记录。成功和失败都用 `bind=::`，所以不能宣称 IPv6 通配监听必然不可用。
- OPPO 的 21:02 成功发送使用本地 `192.168.49.4`；不能把 `.4` 与 `.5` 的差别直接当成失败原因。成功与失败同为 5745 MHz，不能归因于本批记录的频段不同。
- 用户明确补充“刚进入接收就碰也会失败”，并给出 21:21 的新一轮双方证据：接收开始约 4 秒内完成 NFC，端口 39061，仍然 128 次 accept、零原始连接，OPPO 的 115 次连接失败。较早失败前等约 24 秒的差别不能作为主要解释，也不要求用户靠改变碰触时机规避。

故障范围进一步收敛为：双方已报告 P2P 加入与正确 IPv4 地址，但连接请求没有到达应用监听。尚无抓包或兼容层内部证据判断拒绝由哪一侧产生，不能把平台端口转发问题当作已证实结论。

下一项只改变接收建组的监听绑定：读取实际组主 IPv4，与组接口上的地址交叉核对后明确绑定该地址；不硬编码网关，不更改发送端路由、连接期限、碰触时序或设备识别。若日志显示明确 IPv4 绑定后仍拒绝，则该改变不足以解决本问题，继续检查平台的组网／端口映射和发送端角色切换后的路由。JVM 测试只能证明绑定与资源生命周期正确，实体结果仍由用户验证。

## v7：明确绑定接收组 IPv4

- `TapReceiverGroupHost` 在准备阶段读取组主地址，要求组已形成、本机为组主，并且该私有 IPv4 实际存在于本次组接口。地址暂未准备好时继续在原有八秒准备期限内查询；缺失、异常、超时或绑定失败按原逻辑清理并回到旧接收方式，不发布未就绪的端口。
- `TapReceiverServer` 构造时必须传入 IPv4 地址，使用 `ServerSocket(0, 50, bindAddress)`；随机端口及身份校验保持原样。该公开构造器支持指定本地监听地址，参考 [Android ServerSocket](https://developer.android.com/reference/java/net/ServerSocket)。这里不声称已知卓易通内部如何处理 IPv4 映射或端口转发。
- 通过原实现未能满足的明确地址绑定测试，再验证修改后的真实 TCP 文件传输、ACK、拒绝错误身份和取消清理；新增地址选择测试覆盖非固定网段、尚未形成的组、非组主、错误接口地址、通配／IPv6／环回／公网地址。113 项相关 JVM 测试及完整 debug 构建通过，修改空白检查通过。
- 诊断升级 v7，增加 `mode=P2P_IPV4`、已核对地址和实际绑定状态。仅改接收建组路径；普通 Android 默认互传、卓易通发送、NFC 协议和完成确认保持原实现。仍未进行实体操作，下一轮以用户的成功率和双方日志评估本次调整。

已发布阿里云 debug `202610131331`。远端元数据、发布说明和重新下载 APK 的大小／SHA-256 与本地一致，下载包检出 v7 和 `mode=P2P_IPV4` 标记。APK 大小 30,571,105 字节，SHA-256 `4421571b6691f1b28ab7a5054441b2f8076215044660d1a660a146922c05e65e`。本地记录为 `memory/tap-ipv4-bind-red.txt`、`memory/tap-ipv4-bind-build.txt`、`memory/tap-ipv4-bind-publish.txt`。

## v7 实机反馈：明确 IPv4 绑定仍然失败

用户继续提供 `TapDiagnostics-20261013-214124-6960320794104226693.txt`（卓易通接收）和 `TapDiagnostics-20261013-214128-5435780449413784518.txt`（OPPO 发送），两端最新会话均为 debug `202610131331`，并要求搜索公开资料。以下只配对最新一次端口 40005 的会话：

- 卓易通在接收开始后 1,157 ms 已监听 `192.168.49.1:40005`，`mode=P2P_IPV4`、`wildcard=false`、`bound=true`、`closed=false`，对应接口 `p2p-p2p0-14`。碰触后等待八秒及 32 秒超时前，组仍有一个客户端，接口仍有效，监听持续开放；最终 128 次 accept 等待、零原始连接。
- OPPO 加入匹配组，接口 `p2p0`、本地地址 `192.168.49.5`。第一次对上述端口连接在约 13 ms 内返回 `ECONNREFUSED`；之后约 111 次仍拒绝。拆组后的最后一次 `ECONNABORTED` 是迟到结果，不能用来覆盖较早的持续拒绝。
- 明确 IPv4 绑定没有消除故障，不能继续把改绑定地址本身作为已有效的修复。当前证据也不支持碰触太晚、接收监听提前关闭、文件过大或 ACK 超时等解释。
- 两端日志仍不能证明 TCP 拒绝由哪个网络栈产生。优先调查卓易通 P2P 接口对应用的可达性，同时保留 OPPO 从组主切为客户端后的路由残留等候选；不把公开相似案例当作本机根因证明。

公开检索找到 DiPlay 的同类环境报告：[Issue #299](https://github.com/shihabal3amri/DiPlay/issues/299)。报告环境为鸿蒙 7／卓易通、Android 16／API 36、`System 104.3.5.001(00GB)`，与本机的 `00HP` 构建接近；报告称 P2P 加入后没有应用 TCP，而外部路由器同一局域网成功。维护者 10 月 11 日将其归为容器网络暴露限制并关闭为 not planned。此项属于其他项目的实测和维护者判断，不是华为或卓易通的官方确认，也没有可直接移植的已验证修复。

### 公开资料对当前判断的影响

- DiPlay 使用 iPhone 对端和 AirPlay，问题记录中有 IPv6 地址绑定失败；本项目则已经明确绑定 IPv4，并由 OPPO 日志确认主动连接收到拒绝。因此只能把它作为提高平台兼容问题优先级的旁证，不能照搬其“应用无法修改”的结论。本项目已有同一路径成功传输，说明并非完全不支持。
- [Android 官方本地网络权限文档](https://developer.android.com/privacy-and-security/local-network-permission?hl=zh-cn) 说明：Android 17 的新权限针对目标 SDK 37 及以上；目标 36 及以下使用 INTERNET 隐式保留访问。项目 `app/build.gradle` 仍为 `targetSdk 36`，已声明 INTERNET；两端诊断中 NEARBY_WIFI_DEVICES 已允许。标准 Android 新权限规则与本次持续拒绝不相符，不应盲目追加权限。此判断不保证鸿蒙兼容层没有独立限制。
- 目前未检索到华为／卓易通官方对这一具体 P2P TCP 故障的确认或修复说明。论坛的泛化解释、其他应用的 VPN 问题及不相同的普通 Android 代码错误，不作为根因依据。

后续应做能区分原因的对照：优先用同一份最小 TCP 逻辑比较普通局域网与 P2P，记录双方监听和连接结果。如果普通局域网稳定而 P2P 失败，则继续聚焦 P2P 接口暴露／角色切换路由；若两者均失败，则不能限定为 P2P。当前碰一碰仍主动建立 P2P，单纯让两台连上同一路由器不等于完成这个对照，需要独立的调试入口。另一个尚未验证的候选是保持卓易通建组、让它主动向 Android 发起 TCP；这还需要可靠交换客户端实际地址，不能写死地址，也不能预先保证自动连接。

需要暂时完成传输时，可沿用用户已确认可用的普通 Wi-Fi 系统确认路径。此次只完成日志核对、公开研究及文档归档，未修改应用代码、未构建或发布，也未操作设备；没有宣称故障已修复。
