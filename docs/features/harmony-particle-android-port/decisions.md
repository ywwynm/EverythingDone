## 2026-10-05：实现层面的几项决定（阶段 A～C）

- **颗粒用 compute 闭式算**（`drift-update.comp`，GLES 3.1），顶点阶段经实例化属性读同一缓冲。plan.md 原写「全在顶点着色器里算」，
  改用 compute 是为了每颗只算一次两倍频湍流（顶点着色器要每个顶点算一遍）；门槛与流体样式相同，不新增设备要求。
- **参考样式库**：`shared/particle-dismiss/drift-styles.json`，由 `export_styles.py` 从桌面复刻的参考输入表生成，十二段，风都朝上
  （63°～141°）。选取：本次方向与参考风向相差 ≤ 22.5°（八方向扇区的一半）才是候选，有候选时以 0.5 的概率从候选里等概率选一段，
  否则随机。选中后：格点值按「归一化位置取样 + 可见范围的最小 / 最大值仿射对齐」套到本次卡片上（化开的先后与起止时刻都跟参考走）；
  风力取参考的，**风向转到本次方向**（与第 1 问的记录一致）；带上参考的颗粒衰减方式（旧钢铁侠只缩小不变淡）与 src-over 下的 alpha 倍数。
  参考的合成方式不带过来，合成方式只看背景（第 3 问）。
- **背景取样**（`ParticleDriftBackground`）：PixelCopy 读 Activity 窗口上快照四周（各向外扩半个快照、去掉快照本身）缩成 32×32，
  求平均相对亮度换算 CIE L*，低于 50 用加光。结果 48 ms 内没回来按深浅色主题。设置页实测 L* = 90。
  **弹窗暗层不计入**：暗层是应用自己挂在 Activity 窗口上的黑色视图（`DialogDimLayer`，0.6），PixelCopy 读得到——首轮真机里确认框消散取到
  L* ≈ 39、误选了加光（起手一团亮白）。现在按取样那一刻的遮盖度把每个通道的**编码值**除以 (1 − a) 还原（界面在编码值上混合），
  修正后同一类弹窗取到 L* = 84、走 src-over。`DialogDimLayer` 为此加了按宿主查询遮盖度的登记。
- **时间轴起点**：从第一处开始变淡的时刻（`startSeconds`）起算，不从源码的 0 起算，去掉开头卡片纹丝不动的那一小段。
- **种子先打散**：`java.util.Random` 对相邻小种子给出几乎相同的第一个数（单测里 64 个连续种子一次也选不到样式），建发生器前过一遍
  SplitMix64（`ParticleDriftModel.seededRandom`）。生产路径的种子本来就是全范围随机数，这一步是给调试探针的固定种子兜底。
- **仅调试包的「钉住样式」键** `debug_drift_force_style`（`particle_tuning` 偏好，值为样式名或 `random`），验收时经 run-as 写入、用完删掉；
  正式包不读。

## 2026-10-05：内容强调与参考样式的湍流换算

- **内容强调**（`ParticleDriftContent` + `drift-update.comp`）：口径照搬流体样式。本体色 = 快照不透明像素 16 级量化的众数，占比 0.24 → 0.60
  平滑给出置信度；内容权重 = 饱和度项 + (与本体色之差 − 饱和度项) × 置信度。强调量 = 置信度 × 权重：有色格子按分布表多出副本颗粒
  （最多两倍，总数上限 7.5 万）、更大（+20%）、更不透明（+25%）、寿命长 30%（不越过整段时长）；本体色颗粒细 26%、透 35%。
  照片类卡片没有明确本体色，置信度为 0，保持源码原样（参考录像的对照因此不受影响）。
- **参考样式的湍流换算**：源码的湍流只取决于颗粒在卡片上的位置。把参考的格点值套到另一尺寸的卡片上时，湍流若仍按本卡片自己的坐标取样，
  卷曲与翻折的形状就不是参考的（用户问「是否完整复刻了旧钢铁侠的卷曲、流动效果」时发现）。现在按「颗粒在卡片上的归一化位置 → 参考卡片上同一处」
  在参考自己的发射区里取样（`lookup = pos0 × scale + shift`），位移仍加在本卡片上；`drift-styles.json` 为此加了参考的扩展画布尺寸。

## 2026-10-05：与桌面实现逐帧一致（用户：「要跟桌面模拟器的效果一模一样」）

逐项对照桌面 `harmony_native.py` 之后，Android 改了这些地方（同一输入下逐帧一致，证据见 sessions.md）：

- **粒子数**改成桌面的 `area_particle_count`：4 万 × 设备像素面积 / 1.3M，按千颗五成双取整，截在 [1 万, 5 万]；「粒子数量」倍率乘在面积上。
  原先按 dp² 算（350 dp 见方 4 万），高密度屏上会比桌面少。颗粒尺寸以设备像素计、不随屏幕密度缩放，按设备像素算密度才与源码画面一致。
- **扩展画布**改成桌面自有界面的口径：(min(画面宽, 2100), min(画面高 × 0.85, 2400))，至少盖住快照；画布与工作面分别取整
  （cvttps2dq(扩展) 与 cvttps2dq(扩展 × 0.5)）。
- **时间**：状态只在设备帧上更新（第 k 帧在 k / 120 秒，取不晚于 T 的最后一帧）；活动时长按宿主的逐帧 deltaT 累计（首帧 0.0167，
  其后相邻两帧整毫秒数之差）；卡片残留也取同一帧的时刻。出生帧先闭式估计、再按桌面的逐帧判据（iTime = k / hz / 2，alpha ≤ 0.9）核对相邻一帧；
  寿命按宿主的 `lifeTime_cfg = (1 − 进度) × (0.5, 0.8)` 再取随机值。
- **点纹理**按桌面的上传方式上下翻转（桌面把 dot01.png 翻转后上传，纹理第 0 行是图片最下面一行）。
- **合成与卡片残留按片元中心换算坐标**：原先用插值出来的坐标，在整数边界上会差一个最小单位，最近邻取样就错到相邻的工作面像素 / 快照像素。
- **内容分析先反预乘**：上传的快照字节是预乘的，半透明处先除以 alpha 还原直通颜色再算权重。

桌面这边补上 Android 的口径（缺省值下与原来逐位相同，三段参考回归确认）：`harmony_native.NativeRenderer.android_extras()` 接湍流换算与偏移、
内容强调（副本分布表、出生时记下强调量、尺寸与不透明度增益、src-over 时 alpha 先截到 1）、任意方向的风。

## 2026-10-06：起播延迟与出帧

- **口径**：两种会话共用调试包里的 `ParticleFramePacing`，每轮打一行：请求 → 第一帧真实上屏、上屏帧数 / 按 60 Hz 应有的帧数、相邻两帧间隔的
  p90 与最大值、没有呈现时刻的帧数。弹窗的请求时刻在触摸分发里同步打下，左滑在开始准备这张卡片时。左滑必须用连续注入
  （`ParticleGestureInput`，约 8 ms 一个 MOVE）：`adb input swipe` 的事件稀疏，跟手只在手指位置变化时出帧，两种样式都会少一半帧。
- **噪声值域只算各格点单元的角点**（`ParticleDriftModel.noiseRange`）：主线程建输入从 23–67 ms 降到 0.2–2.7 ms。全屏快照（新建页
  1440×3088）原来按 8 px 取 69,480 个点，选中参考样式时 `resample` 还要再算两遍。单元内噪声是平滑插值后的双线性函数，样点上的极值必在该单元
  样点子网格的四个角上；14,200 组核对（随机格点、12 段参考及其变体的重采样格点、人造的近平坦格点）里只有近平坦格点的 3 组差 1 ulp，其余逐位相同，
  派生的起止时刻无一变化。Python 移植同步改，设备与 Python 的 1404 组输入逐位相同。
- **确认上屏不再被丢帧压住**（`ParticleWindowSurface.resolvePresented`，两种样式共用）：合成器丢掉的帧一直报 PENDING，原来要等满 250 ms
  超时才放行，排在后面、已经上屏的帧也一起压着。飘散的弹窗出现末段常丢一帧，收尾因此晚 160–194 ms 才交接给真实面板（录屏里末帧停了约 230 ms）。
  现在只要后面已有帧报了真实呈现时刻就放行队首，收尾降到末帧提交后 0.2–7.7 ms。
- **预热**（`ParticleDriftRenderer.warm`）：除着色器外，再读样式表、空跑一次输入、用合成小图跑三次内容分析。进程里第一次飘散的内容分析原来
  55–70 ms（还没编译），热了之后 13–26 ms。
- **准备阶段重排**（`ParticleDriftSession` 的 FOREGROUND）：快照一读回就先传成纹理（`ParticleDriftRenderer.uploadImage`），内容分析交给后台
  单线程（`ParticleDriftContent.analyseAsync`，读快照字节的独立副本），最后才等背景取样定合成方式。原来是「先等背景 → 读回 → 分析 → 上传」串行。
  新建页 GL 侧（首帧 − 截图完成）从中位约 92 ms 降到约 75 ms；分析不再占 GL 线程，同时在跑的其它粒子动画不被它挡住。
- **试过、没采用**：经像素缓冲对象（PBO）上传整屏快照。三星 SM-S9180 上 CPU 一侧反而从 9–17 ms 涨到 18–27 ms，首帧也没变快，已撤回直接上传。
- **剩下的差距**：新建页起播仍比流体慢约 20–40 ms。流体在首页空闲时预算好了轨迹（上传 0 ms），飘散要读回并上传整屏快照（读回 5–13 ms、
  上传 9–17 ms）。再往下要从快照的 HardwareBuffer 直接建纹理（零拷贝），见 followups.md。
- **试过、没采用（用户问「飘散能否也提前计算」之后）**：飘散没有流体那样的轨迹要预算（颗粒位置是闭式公式，输入 3 ms 内算完）。
  流体提前做的是轨迹；真实快照的读回与上传它也是点新建之后才做（「建材」8–15 ms 里）。飘散唯一能提前的是 GPU 资源分配，
  于是试了把整屏快照纹理、工作面帧缓冲、颗粒缓冲留着复用（等价于首页空闲时预先建好）：新建页第 2–6 轮上传 8.7–11.6 ms
  （不复用 8.8–16.7 ms），GL 侧中位仍约 78 ms，没有可测的收益，还要常驻约 28 MB 显存，已撤回。剩下的大头是第一帧从提交到
  上屏的 39–51 ms 与读回 + 上传 13–24 ms，前者两种样式都有，后者只能靠零拷贝去掉。

## 2026-10-06：新建页零拷贝快照（用户：「做吧，做完在手机上测试后发布阿里云」）

- **原来的路**：离屏 `HardwareRenderer` 把新建页画进 ImageReader 的 HardwareBuffer → `Bitmap.copy(ARGB_8888)` 拷回内存（抓图那一步里的
  大头，抓图合计 29–37 ms）→ `copyPixelsToBuffer` 再拷一份字节（4–12 ms）→ `glTexImage2D` 整张上传回 GPU（9–17 ms）。
- **现在**（飘散、新建页、API 31+、页面里没有独立 Surface）：`ParticleHardwareSnapshot.captureKeepingHardware` 把那块缓冲包成硬件位图
  （`Bitmap.wrapHardwareBuffer`）原样交出；会话经 JNI（`particle_hardware_texture.cpp`：`eglGetNativeClientBufferANDROID` +
  `eglCreateImageKHR` + `glEGLImageTargetTexture2DOES`，入口都用 `eglGetProcAddress` 取）把它绑成纹理（`ParticleDriftHardwareImport`）。
  内容分析拆成「取样位置 + 按样本分析」（`ParticleDriftContent.samplePositions` / `analyseSamples`），位置只取决于尺寸；样本由 GPU
  按位置 `texelFetch`（`drift-gather.comp`，整屏 85,760 个、0.34 MB），栅栏到了再读回，在后台线程分析。读字节的老路取同一批位置的样本，
  喂给同一个分析函数。
- **等价性**：真机逐字节核对（调试键 `debug_drift_verify_zero_copy`，`device/zero_copy_check.py --run z2`）三轮：导入的纹理整张读回与老路
  拷回内存的字节 0 个像素不同，GPU 样本 85,760 个 0 个不同；内容分析拆分前后由单测对照原实现（`ParticleDriftContentSamplesTest`）逐位相同。
- **回退**：任何一步不满足或失败（API < 31、扩展入口缺失、EGLImage 绑定或取样出错）都退回老路。预备对象对硬件快照改为惰性
  （`ParticleMicroflakePreparation.startLazily`），只在回退时才把硬件位图拷回内存；没开工时 `isFinished` 算完成，快照照常回收。
- **只用于新建页**：弹窗与卡片的快照小（弹窗 1200×587 上传约 2 ms），而那些路径还要在截图上叠画（圆角遮罩、独立 Surface），没有改。
  首页那一张（新建页打开时垫在后面的背景，`ThingCreationTransition`）同样是拷回内存的，两种样式共用，也没有动。
- **结果**（三星 R5CW20BLNKL）：新建页抓图 29–37 → 5–7 ms；首帧热态中位 205 → 152 ms（q16，141–170；q17 全场景回归里 156，145–183），
  流体 165 ms（q10）。凝聚过程录屏两轮各 31 帧、约 516 ms，相邻帧最大间隔 18 ms，交接到真实页面时没有跳变。

## 2026-10-06：渲染性能与 120 Hz（用户：「可以继续优化下性能，不只是从交互到动画开始播放的延迟，还有本身的渲染性能」）

- **先量开销**：调试包加了 GPU 基准（`DriftParityRender.bench`，`device/gpu_bench.py`）：整段时间轴连画、只在末尾 `glFinish`、
  热身后各条件成对轮换取中位数，逐项去掉 compute / 颗粒绘制 / 叠加 / 卡片残留。三星 SM-S9180 上每帧（含 GPU）：新建页 1.53 ms、
  多选移除 1.07、弹窗 0.87、左滑卡片 0.92；其中 CPU 发命令 0.14–0.17 ms；单独去掉 compute 或颗粒绘制各省一半上下，去掉叠加省 0.28–0.39 ms，卡片残留只在整页的新建页上明显（0.27 ms）。各项份额有重叠，相加超过整套。
  60 Hz 下 GPU 不到一成，渲染开销不是瓶颈，再压它看不出差别。
- **120 Hz**：飘散每帧是设备时刻的闭式函数，任意时刻都能直接画，而动画期间面板本来就在 120 Hz、粒子只隔一个 vsync 出一帧。
  现在窗口里只有飘散会话时节拍切到每个 vsync 一拍（`ParticleClock.setHighRate`，门限按约 8.3 ms 算：120 / 90 / 60 Hz 面板都是
  每个 vsync 一拍，144 Hz 面板为 144 帧），粒子 Surface 投 120 Hz；只要有流体会话（轨迹按 60 Hz 预算）就整体保持 60 Hz。
  开关 `ParticlePerfTuning.driftHighFrameRate`（缺省开，可在 `particle-perf-tuning.json` 里关掉做对照）。首帧提前出帧「吃掉一拍」与出帧统计的
  「应有帧数」都改按当前节拍算；未确认帧上限 6 → 10（120 Hz 下首帧上屏延迟 40 ms 就有 5 帧在途）。
- **粒子 Surface 不再常驻投 60 Hz**：原来建好 Surface 就投 60，SurfaceFlinger 按应用所有图层的投票给整个 uid 设了 60 Hz 的帧率覆盖
  （`dumpsys display` 的 `mFrameRateOverrides=[{uid=10193 frameRateHz=60.000004}]`），面板在 120 Hz 而整个应用一直只有 60 fps——
  首页滚动（2026-09-26 首页滚动分析已指出）与左滑（应用主线程帧间隔中位 16.66 ms）都被它压在 60 Hz。现在空闲不投（覆盖消失）、有流体会话投 60、
  只有飘散投 120；只在状态变化时发一次。
- **试过、没采用**：左滑期间给卡片与列表投 `REQUESTED_FRAME_RATE_CATEGORY_HIGH`。去掉它对照，位置更新与出帧完全一样
  （8.3 ms 一次、102–106 / 121–122 帧），已删除。投票改过之后左滑仍被量成 60 Hz，原因在测试工具：注入器缺省同步注入，节奏被拴在应用帧率上，
  改用异步 240 Hz 注入（`PARTICLE_INPUT_ASYNC=1`，`perf_compare.py --async-input`）后才量到真实情形。
- **结果**（q30，异步输入，热态首帧中位 / 上屏÷应有；括号里是 60 Hz 时的 q17）：弹窗出现 73 ms、428/428（86 ms、208/219）；
  弹窗消散 67 ms、726/727（99 ms、366/358）；左滑 70 ms、417/485（110 ms、205/257）；回位 70 ms、285/285（92 ms、143/143）；
  多选移除的卡片 78 ms、363/360（79 ms、183/182）；新建页 140 ms、283/282（156 ms、140/143）。左滑首帧的提前来自 120 Hz，
  与注入方式无关（同步注入的 q23 / q24 也是 70 ms）。q30 里左滑缺的约 14% 的拍由下一条的补帧解决。录屏（`device/cadence_record.py`）：飘散弹窗消散
  约 950 ms 里屏幕换了 114–115 帧，相邻帧间隔中位 8.24–8.32 ms、最大约 11 ms。流体（q29，异步输入）与改动前（q22）在同一范围：弹窗出现 / 消散 370 / 105 ms（379 / 111）、左滑 203（205）、回位 370（367）、
  多选移除卡片 182（182）；新建页只有一轮热态 155 ms（此前 q10 165、q20 / q21 182–196）。
- **左滑补帧**（`ParticlePerfTuning.lateGestureFrames`，缺省开）：q31 左滑每轮缺 16–20 拍。调试包加了取证（`ParticleGestureProgress.changeSummary`，
  日志「飘散跟手」一行：每次位置变化记它所属的主线程帧、每次出帧记取到的是哪一次变化），q32 三轮的结果：漏掉的 19–21 拍**全部**是
  「这一帧主线程更新了位置，但晚于 GL 线程的读取」，没有一拍是真的没有新位置；主线程在输入阶段写位置，距 vsync 中位 1.5–1.6 ms（p90 2.2–2.4），
  GL 线程按节拍读，距 vsync 中位 1.3–1.5 ms（p90 1.8–2.0）——两条线程在同一个 vsync 之后抢先后，读在写之前的那一拍没有新位置、
  下一拍一次走两步。现在这一拍不跳过：`ParticleSwipeAnimator` 写完位置调 `ParticleGl.gestureMoved()` 唤醒 GL 线程，`lateFrames` 对这一拍还没出过帧、
  离节拍目标不到半个节拍间隔、且有手势会话位置变了（`ParticleLayerSession.wantsLateFrame`，只对**已经出过帧**的飘散左滑成立，各会话的首帧仍按节拍出）
  的窗口按这一拍的目标补画。每个窗口每拍最多一帧；只在高帧率下做，有流体会话时（60 Hz）不唤醒也不补。
  结果（q33 三轮）：出帧 122/121、122/123、122/122（q32 是 102/123、105/124、103/121），漏拍 0 / 1 / 1，p90 间隔 16.7 → 8.3 ms，
  取到的都是本帧的位置（落后 0 拍 365 次、1 拍 1 次）；首帧 54–71 ms 不变。
  考虑过「固定取上一帧的位置」：同样没有漏拍，但 q32 里 90%–96% 的帧本来就取到本帧位置，固定落后一拍等于给左滑加 8.3 ms 延迟，没采用。
