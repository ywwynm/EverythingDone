## FableSol：水位不再一开门就撑满、涨水不再"抽搐"（D174）

针对新录音 `20260722001826.wav` 反馈的两条现象定位并修复。顺带查清了"真机和
Python 打开同一个 wav 表现差很多"的根本原因。

### 1. 为什么真机和回放 wav 差那么多（结论：wav 缺了一段前导）

`AudioRecorder.RecordingThread` 里两件事的门控条件不同：FableSol 分析器从
**录音界面一打开**（`startListening()`）就开始喂，而 raw 文件只有在**按下录音键
之后**（`mIsRecording`）才写。所以分析器听到的音频比 wav 多一段前导，长度等于你在
界面上停留的时间——底噪、归一化中心、七境状态、巨浪 episode 全在那段没被录进去的
音频里就建立好了。

对照实验（同一段音频，只改前导）：无前导时最多出现 0.9 秒 CLIMAX；接 12 秒安静
前导后变成 CLIMAX 3.3 秒、几乎全程满水位。**内容完全一样，只因为分析器之前听过
什么。** 所以拿 wav 回放对比真机本身就不成立。

分析器先于录音运行是有意的（界面一打开水面就该有反应），本版维持现状。

### 2. 水位加"贴地过渡"——不再一开门就撑满

水位走固定绝对刻度，而手机采集档给 250Hz 以下加了 18dB 搁架、又整体 +10.5dB，
房间低频轰鸣的短时响度足以落进满刻度区。此前唯一的拦截是 A 计权静音门——**门一开
水位就直接冲到 ~1.0，中间没有任何过渡**。实测两条时间线在同一时刻电平只差 0.3dB、
底噪差 2.3dB，结果一边判静音（水位 0）、一边水位 156.9dp + 浪高倍率 2.35。

现在按"高出 A 计权底噪多少 dB"做连续折减（14dB 以内平滑渐入）。真正的说话与音乐
远高于这个余量，不受影响；贴着底噪的房间声不再撑满水位。

### 3. 涨水不再"卡一下、抽搐一下"

水位的 33.6dp/s 限速原本是**对输出硬钳位**并把速度改写成 ±限速，下一帧弹簧又从这个
被压低的速度算出更大的位移，于是逐帧在"贴限速"与"弹簧自由"之间来回跳：

```
t=10.42 v=35.07 贴限速   t=10.47 v=23.43   t=10.52 v=35.22 贴限速
```

实测 **33.2% 的帧贴着限速，|加速度| 反复出现 ±350dp/s² 的尖峰（峰值 434）**，正是
"涨到某个高度突然卡一下、抽搐一下，但也没到最高水位"的成因。改用项目已有的软饱和
限幅（C∞，速度与位移始终一致）后，**贴限速的帧从 33.2% 降到 0%**。

### 4. 双端一致性

同一个 wav 在两端各跑一遍完整实时链逐帧比对：PEAK/CLIMAX 档一致 **100%**，
响度/运动/流速相关 **0.999 / 1.000 / 1.000**，水位平均差 **0.48dp**（上一版 3.06dp）。

### 本版需要在真机上看什么

- 安静的房间里水位是否还会自己撑满（应该不会了）。
- 说话/拍手时水位上涨是否平顺，有没有涨到一半"卡一下"的感觉。
- 真正说话时水位是否还够高——贴地折减只作用于贴着底噪的声音，正常说话不该被削。
- 上一版的五项（安静时的水流、退潮速度、浪的圆润度、已显示的浪是否还在原地变形、
  巨浪密度）是否保持。
- 帧率不应有可感变化。
