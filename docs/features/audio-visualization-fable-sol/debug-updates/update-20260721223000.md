## FableSol：退出 ARR 省电平衡投票，并加入能一刀切开成因的 vsync 读数

上一版投票生效了——`hz 120.0/120.0`，物理面板模式回到 120Hz，`skip 0.0%`、`arm 0.4ms`。
但 `vs 16.6`：系统给本应用的 vsync 回调仍是每 16.6ms 一次。面板在 120Hz、应用不丢帧、
回调准时，却只拿到 60 的节拍——这是 Android 的 render rate（面板与应用速率可以不同）。

- **退出 ARR 省电平衡投票**（API 35+，一行）：Android 15 的自适应刷新率默认给窗口投
  「省电平衡」票，会把对话框里的普通 View 压到 NORMAL（约 60Hz）。水面是连续动画，
  现在显式 `window.isFrameRatePowerSavingsBalanced = false`，只作用于本对话框窗口；
- **删掉打空的 `setRequestedFrameRate`**：它调在 `WaveVisualizerFableSolHost`（FrameLayout）
  上，而该偏好既不向子 View 传播，其聚合到的窗口图层又被 `ViewRootImpl` 以
  `FRAME_RATE_SELECTION_STRATEGY_SELF` 禁止下传给 SurfaceView 子图层。GL 图层的票已由
  `Surface.setFrameRate` 直接投，这行是纯噪声，留着会误导后续排查。

### 新增读数——这一版的重点

```
grid 8.3 lead 16.6 dl 12.4 tl 7 work 8.5/9.2 idle 8.0
vs 16.6/8.3 arm 0.4 p95 0.7 skip 0.0%
```

- **`grid`**：`Choreographer.postVsyncCallback` 拿到的 `FrameData` 里，相邻两条 frame
  timeline 的预期呈现时刻之差（API 33+）。**这是 SurfaceFlinger 给本连接的 vsync 周期，
  已把 render rate 除数与 per-uid 覆盖都算进去——唯一能公开读到「系统认为我们该跑多快」
  的数值。**
  - `grid ≈ 16.7` → 系统就是按 60 服务我们，应用侧任何回调结构、线程归属、申请时机的
    改动**全部无效**，只能走设备侧设置或接受 60；
  - `grid ≈ 8.3` → SF 按 120 排栅格，60 是在派发或接收侧丢的，有解；
- **`work` / `idle`**：一次回调从入口到出口的真实占用，以及两次回调之间的空转。
  `work ≈ 8.5、idle ≈ 8.0` 说明我们每帧只被叫醒一次、在干等系统；`work ≈ 16、idle ≈ 0`
  则说明是我们自己占满了两拍，与刷新率无关；
- **`vs` 的 p05**（斜杠后那个）：vsync 周期的下确界。只要系统偶尔给过 8.3，这里就会出现
  8.3；**永远读不到 8.3，才能支持「系统根本不按 120 服务我们」**；
- **`tl`**：frame timeline 条数。若为 1，说明后台 SF 没给 timeline，`grid` 不可用；
- 启动时还会把完整的 `DisplayInfo.toString()` 写进
  `files/debug_logs/fablesol_frame_perf.log`，其中含 `renderFrameRate` 与每个 mode 的
  `fps=/vsync=/synthetic=`——这是绕开 `Display.getRefreshRate()` 版本差异、直接看清系统
  分配的唯一公开通路。

### 一个必须提前说清的前提

即使解锁 120，**当前每帧成本也吃不下**：分段 p50 合计 8.0ms、预算 8.33ms，而
`gl p95 20.7ms`。在 120Hz 下会有可观比例的帧越过截止时刻，观感很可能比稳定 60 更差。
所以顺序必须是：先确认 `grid`，若为 8.3 再把每帧成本压到 **p95 < 8.33ms**，然后才谈
"开到 120"。压成本的手段（纵深行数、渲染列数）已经备好，等这一版读数再动。

全量 209 项 JVM 测试通过。本版**不含任何视觉改动**。
