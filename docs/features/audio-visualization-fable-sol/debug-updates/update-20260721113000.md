## FableSol：定位并修掉 `sample()` 44ms 的真凶（`Math.cbrt`），闪点死算链短路

上一版（`202607210220`）的屏幕仪表在真机上给出了决定性读数：整帧 56.6ms 里
`sample` 独占 **44.0ms**，而 `draw 0.2 / swap 0.1` 说明 GPU 完全空闲——瓶颈 100%
在 CPU，而且和 GPU、面板刷新率、ART 通用税都无关。

- **主因：`Math.cbrt`**。本轮迁移把轨道位移的硬裁剪换成了六阶软饱和
  `value / sqrt(cbrt(1 + ratio⁶))`，调用点是 97 行 × 216 点 × X/Z 两路
  = **每帧 41904 次**。Android 的 `Math.cbrt` 走 libcore 的纯 Java FDLIBM 实现，
  没有 `sin`/`cos` 那样的快速路径，在 debuggable 构建里每次约 1µs——44ms ÷ 41904
  ≈ 1.05µs，完全对得上。桌面 HotSpot 把它当内联函数，代价接近零，所以桌面探针
  对这类问题结构性失明（同一函数桌面只要 0.26ms，相差 170 倍）；
- 改为纯算术实现：位级初值把指数除以 3，再做三次 Halley 迭代（三阶收敛），
  相对误差约 1 ulp。新增测试在 `[1, 1e18)` 上逐点比对 `Math.cbrt`，要求相对误差
  < 1e-14，并锁定 `softLimit` 的零点恒等、单调性与"极值处仍有正导数（无硬平台）"；
- **闪点死算链短路**（逐位等价）：闪点数量总门 `glint_capacity_gain` 默认为 0，
  此时容量恒为 0——取不到锚点、轨迹被清空、一个顶点都不发。但整条计算链照跑：
  每帧 8 层 × 196 列 × 10 模态的微法线采样（**31360 次 sin/cos**）加 1568 次
  exp/pow/sqrt，全是死算。现在在门关闭时整体跳过，输出顶点缓冲逐位不变；调参面板
  拉起该值时成本自然回来。桌面实测 `optics.build` **282µs → 56µs（−80%）**；
- **C2 fairing 的除法换乘倒数**：两个除数（`6.0` 与 `2·step`）都是整行的循环不变量，
  而 ART 只在倒数可精确表示时才把除法降级成乘法，原式每帧要付 **125712 次双精度
  除法**。改为整行只算两次倒数，桌面实测 fairing 三路 **26.7µs → 11.8µs**；
- **修掉性能仪表自伤**：`getThermalHeadroom` 是同步 binder 调用，却被放在 GL 线程的
  逐帧摘要里（这也是上版 `therm` 读数为 0.0 的原因），现按 1s 缓存；分位数改成一次
  排序出 p50/p95/p99（原先对同一份数据排三遍）；HUD 刷新从 8Hz 降到 2Hz。

**仪表增强**：`sample()` 内部现在分四段单独读数——`prep`（串行预备：波包包络、
逐模态标量）、`field`（方向场累加，9 模态 + 波包）、`fair`（层场合成 + 三路 C2
fairing）、`slope`（纵深梯度）。物理段也补了 `bc` / `wave` / `surf` 三项分解。
屏幕 HUD 现在是五行，日志同步记录。

**请重点反馈第四行的 `prep / field / fair / slope`**：桌面与真机对同一段代码的相对
代价可以差两个数量级，这四个数决定下一批砍哪里，不能再靠桌面推断。
