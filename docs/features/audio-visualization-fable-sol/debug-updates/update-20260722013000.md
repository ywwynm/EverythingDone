## FableSol：尖峰归因确认为乘性抖动，补上决定裁窗是否安全的最后一个读数

两张真机对照给出了决定性信息：

| | A（80.4fps） | B（119.6fps） |
|---|---|---|
| `grid` | **16.6** | 8.3 |
| `vs` | 16.6/8.3 | 8.3/8.3 |
| `work` | 5.8/**11.3** | 5.6/**10.3** |
| `steps` | 2.0 | 1.0 |

**A 里 `grid` 变成了 16.6——SurfaceFlinger 把我们的节拍降回了 60。** 这是第三个棘轮，
这次闭合在 SF 的内容检测里：p95 越线 → 漏一帧 → SF 判定我们是 60fps 内容 → 把节拍降到 60
→ `steps` 变 2、开销翻倍 → 出不来。前两个棘轮（应用自己申请太晚、节拍器跟随面板下行）
已经修掉，这个只能靠"不越线"来避免。

各段 p95 与 p50 的比值揭示了尖峰性质：

| 段 | p50 | p95 | 倍数 |
|---|---|---|---|
| `phys` | 1.0 | 1.8~2.0 | ~1.9× |
| `build` | 3.9 | 7.0~8.5 | ~1.9× |
| `sample` | 1.5 | 3.3 | 2.2× |
| `optics` | 0.9 | 1.1~1.9 | ~1.4× |

**尖峰是乘性的（约 1.8~2 倍），不是加性的。** 这排除了 GC、日志写入这类固定开销事件——
它们只会在某一段上加一个固定值。乘性尖峰是 CPU 降频与线程调度抖动的特征：整体被拉慢
一个倍率。上一版消掉的 5.3MB/s 音频垃圾因此不是主因（但仍是净收益，保留）。

**结论：要 p95 < 8.33ms，就得把 p50 从 5.6ms 压到约 4.5ms 以下，即砍掉 1.1~1.5ms。**

- **新增 `rs` 现在合并统计世界空间与投影空间两处单调修复的触发行数**。这是"把 `sample()`
  裁到渲染窗口"是否安全的最后一个未知量：波包按设计先生在画外，而画外正是 orbitX 幅度
  最大处；若该修复真的会触发，裁窗后可见区的行缩放比例就会变，倾斜导致窗口边界跳变时
  还会出现幅度突跳。**若实测长期恒为 0，裁窗在实际参数下不改变任何输出**——那就是一条
  零画质代价、约省 0.6ms 的路（θ≈0、容器 280dp 时，216 个物理点里有约 42% 永远不会被渲染）；
- **`field`、`limit`、`vtx` 也补上 p95**，用于确认乘性抖动是否均匀作用于所有并行阶段。
