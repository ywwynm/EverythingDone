## FableSol：帧节拍改由 GL 线程自驱，消掉每帧一次跨线程唤醒

上一版真机读数确认了两件事：面板**确实在 120Hz**（`hz 120.0`），且上一批优化生效——
分段合计 **8.2 → 6.4ms**（`build 5.9 → 4.7`、`phys 1.4 → 1.1`）。`rs 0.0` 还顺带证明
投影单调修复在真实参数下从不触发。

但由此暴露出真正的矛盾：**work 只有 6.4ms、120Hz 预算 8.33ms，有 30% 余量，帧间隔
却系统性地稳定在 16.5ms（正好两个 vsync）**；而且"开头能满帧、很快掉到 60 就回不来"。
余量够却回不来，说明瓶颈不在算力。

- **成因定位：每帧一次跨线程唤醒**。原先 Choreographer 回调在 UI 线程触发，再
  `handler.post` 把渲染排到 GL 线程，中间要等一次线程唤醒与调度。在大小核调度下这一跳
  可达 1~3ms，叠加 6.4ms 就压过 8.33ms；一旦越线掉到 60fps，物理子步从 1 变 2、
  开销翻倍，形成正反馈把帧率锁死在 60；
- **改法**：GL 线程本来就是 `HandlerThread`、自带 Looper，因此让它持有自己的
  `Choreographer`，vsync 回调**直接落在 GL 线程**，渲染同步完成后再排下一帧。
  UI 线程彻底退出逐帧路径，只保留 250ms 一次的显示状态轮询（HDR headroom 与刷新率
  必须通过 View 拿 Display，只能在 UI 线程做）。原先的 `latestFrameTime` /
  `renderQueued` 合并机制随之整体删除——自驱循环天然不会重入；
- **帧节拍器移到 GL 线程**：`FableSolFramePacer` 现由渲染线程持有，目标帧率仍跟随
  显示模式在 [60, 120] 内，由 UI 侧低频下发。

**仪表**：把热余量 `th` 加回第五行（1.0 表示已到限温）。"开头满帧、很快掉到 60"的
另一个候选成因是 DVFS/温控回落，必须能与算力不足区分开——如果这一版仍掉到 60 且
`th` 明显上升，那就是温控而不是调度。

全量 209 项 JVM 测试通过。本版**不含任何视觉改动**，画面应与上一版逐位一致。
