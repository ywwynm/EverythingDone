## FableSol：单调归约整行折叠 + 顶点循环去冗余，并补上判定 120Hz 是否真的在跑的读数

上一版真机 59.3fps（16.9ms/帧），GL 线程 CPU 合计 8.2ms，而 `draw 0.4 + swap 0.3`
说明 GPU 几乎全闲。围绕"能不能把运算搬到 GPU"做了一轮双端设计审查（Android +
桌面 moderngl 蓝本 + 共享 GLSL），结论见下方。本版先落地其中**纯 CPU、逐位一致、
不碰 GLSL 也不碰蓝本**的一批。

- **两处整行单调归约折叠成一次调用**。`monotoneBlendBound` 在基线步长与比例固定时
  对 `rawStep` 单调不减（≥ floor 恒返回 1；低于 floor 后分母随 rawStep 减小而增大，
  商随之减小），因此 `min_j bound(step_j) ≡ bound(min_j step_j)` 在 IEEE-754 下**逐位成立**。
  世界空间的轨道修复由此从每帧 97 行 × 215 次调用降为 97 次；投影空间的基线步长逐列
  不同、不能提成行常量，改为把 floor 的乘法与整个调用推进到实际发生回折的稀有分支，
  常态帧内层只剩两次减法、一次乘法和一次比较；
- **顶点循环去冗余**（每帧 19012 顶点）：四组节点元素原本各被读两次（一次配 Hermite
  值权重、一次配导数权重），提成元素级局部变量，二维数组的双重解引用与边界检查各省
  一半；顶点分量 6/7 的写入是死存储——滤波后的写回循环会无条件覆盖每一个顶点，改为
  只推进游标；`row / (Z_ROWS − 1)` 与已有的 `z01[row]` 是同一表达式，省掉一次逐顶点除法；
- **新增三个判定用读数**：`hz`（面板运行时**实际**刷新率）、`rs`（投影单调修复实际
  触发的行数 p95）、以及已有的 `drop`。

**为什么 `hz` 这一项是这一版最重要的东西**：`gl 16.9ms` 与分段合计 8.2ms 之间有
8.7ms 无归属，两种解释都与读数自洽——(a) 系统在录音期间把面板压回 60Hz，那么 16.9ms
就是设计节拍、8.2ms 有整整一倍余量，后续所有优化收益为零；(b) 面板确实在 120Hz，
8.2ms 略越 8.33ms 预算，渲染请求的合并把节拍打成每两次 vsync 一帧。**这一版之前无法
区分二者。** 请把第一行的 `hz` 读给我。

### 关于"把运算搬到 GPU"

双端设计审查（42 条候选、逐条对抗复核后成立 9 条）的结论：

- **不成立的部分**：在顶点着色器里解析求值方向场（9 模态 + 波包）会让相位达到
  44~58 弧度，而 GLSL ES 只保证 `sin`/`cos` 在 `[−π, π]` 内的精度，几何会变成
  GPU 厂商相关——正面违反 D40 的"API 26+ 严格像素级一致"。这条路否决；
- **整体搬迁不成立**：银泽坡度滤波是整网格 7 趟可分离算子，需要 CPU 上全部
  97×196 的坡度；而坡度是 worldEta 的 Hermite 导数，等于说 CPU 必须做重建；
  重建做了，坐标也就顺带有了。要打断这个闭环，必须把滤波也搬成独立的离屏 pass；
- **成立的部分**：节点纹理 + 顶点着色器内 Hermite 重建（着色器里没有任何超越函数，
  误差约 1e-4 px，比已接受的 0.035px 低两个数量级），可省 0.7~0.9ms；再加银泽滤波
  上 GPU 另省约 0.8ms。**但这两步都只在 `hz` 确认为 120 时才值得做。**

全量 209 项 JVM 测试通过，验收口径不变（逐位一致，`max|Δ| = 0`）。
