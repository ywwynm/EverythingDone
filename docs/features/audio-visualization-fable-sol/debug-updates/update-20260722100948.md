## 录音采集率改为运行期协商、优先 48kHz（D175）

本版**改变了录音文件的格式**（44.1kHz → 48kHz，文件约大 9%），请重点验证采集本身。
老录音不受影响。

### 为什么改

第三段录音（开录音界面后立刻点录，前导极短）两端仍不一致：Android 一上来就有一道
巨浪、Python 打开同一文件没有。逐条查清后是两个独立问题叠加，其中**留给 Android
的这一个是采样率**——同一段音频按 44.1kHz 分析出 3 道巨浪、按 48kHz 只有 1 道。

选择改 Android 而不是改模拟器，有两条理由：

1. **手机很可能一直在偷偷重采样**。现代 Android 的音频 HAL 原生跑 48kHz，
   `AudioRecord` 请求 44100 会让框架插一层重采样器；而重采样恰好抹平瞬态，偏偏
   FableSol 的巨浪门就是靠 punch / energy_rising 这类瞬态证据判定的。改成 48000
   等于把这层去掉，拿到硬件原始流。
2. **全部调参都是在 48kHz 上做的**。从第一版到现在的每个阈值、以及母带四个已验证的
   巨浪时刻，都是在 Python 模拟器的 48kHz 下标定的。改模拟器等于让工具偏离它自己
   标定出来的参数；改设备才是让真机终于对上工具。

### 怎么改的

没有直接把常量改成 48000——万一某台设备不支持，`getMinBufferSize` 会返回
ERROR_BAD_VALUE，而旧代码遇到这个是直接 return，也就是**静默录不到音**。
现在改为运行期协商：按 `[48000, 44100]` 依次尝试，取第一个真正 INITIALIZED 的，
把实际生效的采样率贯穿三个分析器（FableSol / 原版 / Opus）与 WAV 头。

顺带修掉 Opus 分析器里一个按 44100 写死的 bug：YIN 音高搜索的 tau 上下界写成
`73 // 44100/600` 与 `588 // 44100/75`，在 48kHz 下会把音高范围从 75~600Hz 偏成
82~657Hz；现改为由实际采样率推导。

### 同时修好的（模拟器侧，不影响 App 行为）

模拟器打开文件走的离线路径此前把因果特征降采样到 43Hz（实时链是 93.75Hz），等于
丢掉一半 hop，瞬态证据的峰值被采样漏掉；另外每个渲染帧只把最后一个 hop 喂给动画层，
而 Android 一直是"一帧收到多个 hop 就逐个消费"。两处都已对齐。修完之后离线路径与
实时链在同一采样率下等价，模拟器终于能如实预测真机。

### 验证

48kHz 同源输入下，Android 与模拟器：水位/流速/响度相关 **1.000**，水位平均差
**0.021dp**，巨浪 1 vs 1，PEAK/CLIMAX 档一致 97.7%。

### 本版需要在真机上看什么

**首先确认采集本身正常**（这版动了录音链路）：

- 录音能不能正常开始、能不能存成文件、存下来的音频听起来对不对（不应有变调或变速——
  变调变速说明协商到的采样率和 WAV 头对不上）。
- DEBUG 日志里搜 `AudioRecord source=... rate=...`，确认实际协商到的是 48000 还是
  回退到了 44100。
- 另外两个可视化样式（原版、Opus）有没有异常，尤其是 Opus 的音高相关表现。

**然后再看动画**：上一版那几项（安静时的水流、水位是否会自己撑满、涨水有没有"卡一下"、
浪的圆润度、巨浪密度）是否保持。这一版没有改任何动画参数，只改了送进分析器的音频。

如果录音本身出了问题，直接回滚到上一版即可（`202607220046`）。
