## FableSol：投票与节拍只看「期望」，不再看「当前」——修掉我自己造的第二个自锁环

上一版真机读到 `hz 60.0/60.0`、`vs 16.6`、`skip 34.5%`：**物理显示模式本身掉到了 60Hz**，
系统确实只按 60Hz 派发 vsync，而节拍器还在主动丢掉三分之一的回调。

成因是上一版新加的帧率投票用错了值：投票值取自 `min(当前模式刷新率, 120)`——面板一旦
处于 60Hz，我们就投 60，反而把它牢牢按在 60。**我修掉了一个反馈环，又亲手造了一个同构的。**

- **投票改为「同分辨率下支持的最高刷新率」**（`Display.getSupportedModes()`，API 23），
  上限 120，与面板此刻处于哪个模式**完全无关**。只在相同物理分辨率的模式里挑，避免帧率
  投票顺带触发分辨率切换；
- **API 31+ 改用 `CHANGE_FRAME_RATE_ALWAYS`**。默认的 `ONLY_IF_SEAMLESS` 在无缝切换
  不被允许时会直接忽略投票，无法把面板从 60 拉回 120；
- **节拍器不再跟随显示模式，固定按 120 计**。Choreographer 本来就只在 vsync 触发，
  60Hz 面板上自然只有 60 次回调，节拍器唯一的职责是在 >120Hz 面板上封顶。跟随当前
  模式只会在面板掉档时把自己也锁到低帧率——这正是 `skip 34.5%` 的来源
  （目标被设成 60、而回调按 120 来，于是精确二分频）；
- **`skip` 改为按 HUD 刷新窗口统计**，不再自启动累计。启动瞬间面板模式尚未稳定时的丢帧
  会永久污染累计值，掩盖当前是否真的还在丢。

### 这一版要看的判据

```
fps ???  gl ?  p95 ?  hz A/B
vs ?  arm ?  p95 ?  skip ?%
```

- **`hz A/B` 与 `vs`**：若 B（物理模式）回到 120、`vs` 回到 8.3，说明投票生效，面板被拉回
  高刷。若 B 仍是 60，说明这台设备在当前场景下拒绝切到 120Hz 模式——那是系统的显示策略
  （常见于低电量、省电模式、或系统判定小面积动画不值得高刷），应用侧已无手段，
  60fps 即为该场景下的硬上限；
- **`skip`**：必须为 0%。不为 0 说明节拍器仍在丢帧，是我们自己的问题；
- **`th`**：上一版读到 0.0，说明该接口在这台设备上不可用或恒返回 0，暂时无法用它判断温控。

若 `vs` 回到 8.3 而 `fps` 仍上不去，那才轮到砍 CPU 工作量——当前分段合计 8.8ms
（`build 6.7` 是主项），届时会动纵深行数与渲染列数这两张牌。
