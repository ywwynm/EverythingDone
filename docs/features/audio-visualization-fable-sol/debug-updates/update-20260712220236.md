# 修复 Stage 0 Hann 平滑重复计算造成的性能回归

## 发布说明

### 真机数据结论

恢复帧循环后，用户反馈水面比以前更卡。第二份 `fablesol_frame_perf.log` 显示稳定段
`onDraw` 中位数约 32.8ms，其中 physics 6.5ms、color 11.8ms、submit_optics 13.6ms；
Window 总帧 P50 后段约 59~65ms。GPU P50 只有约 4ms、P95 约 5.4ms，证明瓶颈明确
位于 CPU/UI 线程，而不是 GPU、SYNC 或位图上传。

这些数据也确认 OpenGL ES Stage 1 的必要性：即使完全消除 optics，physics+color
仍超过 60fps 的 16.6ms 预算。下一步将按既定计划把渲染迁到 TextureView + EGL 独立
线程，并把逐顶点配色和光学转入 GLSL。

### 本次回归与修复

Stage 0 将光学 `DoubleArray` 改为 scratch 池时，缓冲版 `smoothSignal()` 在每个采样点、
每个 Hann 核点内重新计算一次 `cos()`。该实现虽然消除了数组分配，却引入大量重复超越
函数，放大了 `submit_optics`，解释了“比迁移前更卡”的新增部分。

现改为在 `FableSolMath` 初始化时一次性缓存半径 3~6 的归一化 Hann 核；每帧平滑仅做
边界夹取和乘加，不再执行 `cos()`，同时继续保持 scratch buffer 零分配。

### 验证

- 新增缓冲 Hann 数值回归：先确认缺少实现时编译失败，再完成实现转绿。
- 半径 3、4、5、6 均与旧 `padEdge + convolveValid` 结果在 `1e-12` 内一致。
- 完整 `:app:testDebugUnitTest`：通过。
- `:app:assembleDebug`：通过。
- 未使用 adb、模拟器或物理设备。

### 真机重点确认
