## FableSol：软饱和快速路 + 把 `field` 22.7ms 拆成可读数字

上一版真机读数 33.8fps（29.6ms/帧），瓶颈已收敛到一点：`sample` 23.0ms 中
**`field` 占 22.7ms**，而 `prep 0.1 / fair 0.1 / slope 0.0`、`optics 5.0 → 0.7`、
`draw 0.1 / swap 0.1`（GPU 仍全空闲）。

但有个数字对不上：`fair` 每次内层迭代约 1.2ns，`field` 约 68ns——两者循环体复杂度
只差一倍，代价却差 57 倍。`fair`/`sheen` 用的是同一套行并行派发且都很快，说明派发机制
没问题，是 `field` 内部另有原因。**这一版先把它拆成可读的数字，不再靠推断。**

- **`sample()` 的分段从四段细化到五段**：把「逐点软饱和 + 单调修复」从方向场累加里
  单独拆出来派发，于是 `field`（9 模态 + 波包的累加）与 `limit`（41904 次软饱和 +
  97 行单调修复）可以分开读数。逐行数学与合在一起时逐位一致；
- **新增 `pkt` 读数**：参与累加的波包数。自然生成上限是 7，但事件注入可以在两次剪枝
  之间叠到 24——若真机读到远大于 7 的值，那么内层迭代数就是我按 7 估算的三倍以上，
  这本身就是答案；
- **新增 `cpu W/N` 读数**：实际参与计算的线程数（常驻 worker + 调用线程）与运行时
  可见核数。若 W 远小于 N，说明行并行在真机上没能吃到多核；
- **软饱和快速路**（浮点误差内）：`ratio⁶ ≤ 1e-3` 时改用 `(1+u)^(-1/6)` 的四项二项
  展开，截断相对误差 < 5.6e-14，避开一次开方与 Halley 迭代里的三次除法。该区间对应
  `|value| ≤ 0.316×limit`，估计命中八成以上调用。阈值刻意不放宽到 1e-2——现有的
  `FableSolCurveFairnessTest` 以 1e-12 绝对容差探测 `value = ±3`，那正好落在快速路内
  （绝对误差 4.8e-14），放宽就失去了这层保护。

**HUD 现在第四、五行是**：

```
prep 0.1 field 22.7 limit 0.0 fair 0.1 slope 0.0
steps 4.0 wave 0.3 surf 0.1 hop 2.0 pkt 7.0 drop 0.0  cpu 4/8
```

麻烦重点看 **`field` / `limit` 的分配**、**`pkt`**、**`cpu W/N`** 这三处。

全量 203 项 JVM 测试通过。
