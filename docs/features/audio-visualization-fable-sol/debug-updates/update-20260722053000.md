## FableSol：撤回 FIXED_SOURCE，并把探针自身开销移出 GL 线程

用户反馈：当前版本进入 120fps 的概率**低于** `202607210718`，且一旦掉到 60 就再也回不来。
复查后确认有两处是我自己引入的退化。

- **撤回 `FRAME_RATE_COMPATIBILITY_FIXED_SOURCE`，改回 `DEFAULT`。**
  FIXED_SOURCE 的语义是「内容帧率固定，系统可自行做 pull-down 匹配」——SurfaceFlinger
  因此完全可以判定「120 的固定源用 60Hz + 2:1 pulldown 也满足要求」并**稳稳停在 60**，
  这正好解释「掉下去回不来」。DEFAULT 表示「按这个速率跑，但可以适配」，是
  `202607210718` 首次跑到 119.8fps 时的配置。上一版把它换成 FIXED_SOURCE 是想让投票
  对内容检测更有粘性，方向错了；
- **摘要与 HUD 的格式化整体搬到监控自己的线程。** 从 `0718` 一路加读数到现在，
  `publishHud` 里已有约 **44 次分位数计算**（每次一趟 240 元素排序），`logGlSummary`
  还要再来约 30 次，全部落在 GL 线程的逐帧关键路径上——这是探针自伤，而且是随着我
  不断加读数而逐版恶化的。现在 GL 线程只剩一次 `post`（复用 Runnable，无分配）。
  窗口的并发读写对调试探针无害：最坏是某次分位数取到半新半旧的样本。

### 顺便回答"这几次优化是不是真的优化"

分成两类，如实对账：

**计算侧优化——全部为真，且量级很大（真机或同进程桌面前后对照）**

| 改动 | 效果 | 验证方式 |
|---|---|---|
| `softLimit` 的 `Math.cbrt` → 纯算术 + 二项展开 | `sample` 44ms → 1.4ms | **真机** |
| 主浪/环境波相位递推（每帧砍 3.1 万次 libm） | `phys` 6.1ms → 1.4ms | **真机** |
| 闪点死算链短路 | `optics` 282 → 56µs | 桌面同进程 |
| 行并行改短自旋 + 挂起 | 空屏障 22.8 → 1.0µs | 桌面同进程 |
| 银泽滤波按行并行 | 68 → 21.8µs | 桌面同进程 |
| fairing 除法换乘倒数 | 26.7 → 11.8µs | 桌面同进程 |
| `sample()` 裁到渲染窗口 | 172 → 97.9µs | 桌面同进程 |

**帧调度侧——有对有错**

| 改动 | 判定 |
|---|---|
| 关闭 ARR 省电平衡投票 | **决定性正确**：60 → 119.8fps |
| `postFrameCallback` 提到渲染之前 | 正确（消除 vsync 栅格量化） |
| 节拍器与投票改用「期望」而非「当前」 | 正确（消除两个自锁环） |
| 帧循环搬到 GL 线程 | 中性：单独并无收益，但结构更清晰、少一次跨线程唤醒 |
| 投票改 `FIXED_SOURCE` | **错误，本版撤回** |
| 探针读数逐版累加 | **负收益，本版移出 GL 线程** |

也就是说：计算侧的优化是实打实的（`sample` 从 44ms 降到 1.4ms、`phys` 从 6.1 降到 1.4），
帧率从最初的 17.7fps 到能跑 119.8fps 主要来自「关闭 ARR 省电平衡投票」这一行；而最近
两版我在追求"稳定 120"时引入了两处退化，现已撤回。

全量 209 项 JVM 测试通过。本版**不含任何视觉改动**。
