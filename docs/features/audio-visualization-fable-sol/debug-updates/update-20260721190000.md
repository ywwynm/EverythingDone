## FableSol：修掉锁死 60fps 的三个成因（主因是上一版自己引入的顺序错误）

上一版把帧节拍搬到 GL 线程后仍是 59.8fps / 16.7ms，`hz 120.0`、分段合计仅 8.0ms。
排查后确认是三个成因叠加，其中主因是上一版改动自身引入的。

- **主因：下一拍 vsync 的申请发生在渲染之后**。`Choreographer.postFrameCallback`
  在回调体内调用时，`doFrame` 已经清掉 `mFrameScheduled`，因此会**当场**向
  SurfaceFlinger 发一次性 vsync 请求，而 SF 给的是「请求时刻之后的第一个唤醒点」。
  上一版把它放在约 8ms 的渲染**之后**，申请时刻（`vsync + 8.2~8.5ms`）已经越过
  `vsync + 8.33ms` 这个唤醒点，只能拿到再下一拍——帧间隔被 vsync 栅格量化成恒定的
  两个周期。这解释了为什么 work 明明只有 8.0ms、预算 8.33ms，间隔却**恰好** 16.7ms
  且几乎无抖动（p95 20.7 正是 16.67 与 25.0 的插值混合，是量化分布而非算力抖动分布）。
  也解释了"开头满帧、掉下去就回不来"：这是个棘轮——120fps 时子步为 1，落下去后
  dt 翻倍、子步变 2，耗时再涨 0.3ms，于是永久越线；掉下去只需 +0.03ms 的噪声，
  爬回来却要 −0.3ms。**修复是把申请提到渲染之前，一行。**
- **成因二：节拍器目标取自会被系统下调的刷新率**。`Display.getRefreshRate()` 的取值
  顺序是 `refreshRateOverride → renderFrameRate → mode.refreshRate`，前两者正是
  "系统认为本应用需要多少帧"的值。拿它当目标，等于让系统的降频决策反过来喂给自己：
  一旦读到 60，节拍器就精确二分频、只按 60 提交，又继续喂给 SurfaceFlinger 的内容
  检测，250ms 轮询永远读不回 120。改为取**物理显示模式**的
  `Display.Mode.getRefreshRate()`（API 23，minSdk 26 无需守卫）；
- **成因三：SurfaceView 图层从未投过帧率票**。GL 出画的是 SurfaceView 自己的子
  SurfaceControl 图层，而现有两处请求都够不到它——Dialog 窗口上的
  `preferredRefreshRate` 只作用于窗口图层；`View.setRequestedFrameRate` 既不向子 View
  传播，其汇总的窗口图层又被 `ViewRootImpl` 以 `FRAME_RATE_SELECTION_STRATEGY_SELF`
  明令禁止下传给子图层。现在直接对 `SurfaceHolder.getSurface()` 调用
  `setFrameRate(target, FRAME_RATE_COMPATIBILITY_DEFAULT)`（API 30+，低版本跳过），
  Surface 重建时重投、销毁前撤票。没有显式票时 SurfaceFlinger 只能按提交节奏做内容
  检测，而结果只会落在显示模式的整数分频上（120/2 = 60）——这正是"一旦被判 60 就是
  精确的 60、且没有恢复通道"的系统侧一半。

**仪表新增一行**，用于验证上述三条是否真的解除：

```
fps 118.7  gl 8.4ms p95 9.1  hz 120.0/120.0
vs 8.3 arm 0.4 p95 1.2 skip 0.0%
```

- `hz A/B`：A 是系统实际下发给本应用的速率，B 是物理显示模式速率。**两者分叉
  （如 60.0/120.0）就说明成因二三仍在起作用**；
- `vs`：相邻 vsync 时间戳之差，等于系统实际派发周期。应为 8.3；若是 16.7，说明系统
  根本没按 120Hz 派发，那是显示侧问题而非我们的问题；
- `arm`：回调相对 vsync 时刻的到达延迟。正常应 < 1ms；持续偏大说明 GL 线程被调度器
  压在小核上；
- `skip`：节拍器主动跳过的帧占比。应为 0%；不为 0 说明目标帧率被设低了。

三者合起来可以一次性区分「系统没按 120Hz 派发」「回调到得太晚」「自己跳了帧」。
