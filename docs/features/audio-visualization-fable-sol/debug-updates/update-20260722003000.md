## FableSol：120fps 达成后转攻 p95 —— 消掉音频线程 5.3MB/s 垃圾，并加尖峰归因读数

上一版把 ARR 的「省电平衡」投票关掉后，真机达到 **119.8fps**：`vs 8.3/8.3`、`grid 8.3`、
`skip 0.0%`、`hz 120.0/120.0`。棘轮随之解开——`steps` 从 2 回到 1，物理与构建连锁下降：
`phys 1.6 → 0.9`、`build 5.4 → 3.7`、`sample 2.1 → 1.3`。

现在的真实数字是 **`work 5.4 / p95 9.2`**，预算 8.33ms。**p50 有 35% 余量，是 p95 的尖峰
在偶尔越线**——这就是"有时 120、有时 60、有时之间"。因此这一版不动任何画质参数，
只针对尖峰。

- **音频分析的缓冲改为定长复用**：`FableSolRealtimeAnalyzer.feed()` 原本每次调用都要
  `concat` 出新数组、末尾再 `copyOfRange` 出新数组；开启采集补偿后 raw 路径再翻一倍，
  即每批 PCM 分配四个大数组，稳态垃圾约 **5.3 MB/s**。GC 会暂停**所有**线程（含 GL 线程），
  直接抬高渲染 p95。改成「按需扩容 + 就地压缩」，稳态零分配；样本值与消费顺序完全不变，
  全部音频链测试原样通过；
- **尖峰归因读数**：`phys`、`build`、`sample`、`optics` 现在都显示 `p50/p95`。
  判据很直接——若某段的 p95 明显高于自身 p50，尖峰就在那一段；**若各段 p95 都贴近各自
  p50，而 `work` 的 p95 仍然高，说明时间花在被测阶段之外**（GC、线程调度、其它进程抢核），
  那就不是靠优化渲染代码能解决的。

### 下一轮看什么

```
work 5.4/9.2 idle 3.0
drain 0.1 phys 0.9/? build 3.7/? draw 0.3 swap 0.2
sample 1.3/? vtx 1.1 sheen 0.2 color 0.0 optics 0.9/?
```

重点是四个斜杠后的数字，以及它们之和与 `work` 的 p95 差多少。差值就是"被测阶段之外"
的开销，也就是这一版试图消掉的那部分。

### 关于"能不能把运算搬进 shader 并行加速"

双端设计审查（49 个 agent、42 条候选、复核后成立 9 条）的结论要分成两半：

- **在顶点着色器里解析求值方向场——不可行。** 相位量级达 44~58 弧度，而 GLSL ES 只保证
  `sin`/`cos` 在 `[−π, π]` 内的精度，超出后是各家 GPU 自由发挥。几何会变成厂商相关，
  正面违反 D40 的「API 26+ 严格像素级一致」。这条路已否决；
- **节点纹理 + 顶点着色器内 Hermite 重建——可行。** 着色器里没有任何超越函数，
  只有乘加与一次除法，误差约 1e-4 px，比 D139 已接受的 0.035px 低两个数量级。
  可省 `vtx` 的约 1.1ms；
- **整体搬迁不成立**：银泽坡度滤波是整网格 7 趟可分离算子，需要 CPU 上全部 97×196 的坡度，
  而坡度是 worldEta 的 Hermite 导数——CPU 必须做重建，重建做了坐标也就顺带有了。
  要打断这个闭环，必须把滤波也做成独立的离屏 pass。

也就是说 GPU 化能拿到的是 `vtx 1.1` + `sheen 0.2` ≈ 1.3ms，代价是跨两个仓库改共享 GLSL、
动 D40 的像素一致合同。**在 p50 只有 5.4ms、瓶颈是尖峰而非算力的当下，性价比不如先削尖峰。**

全量 209 项 JVM 测试通过。本版**不含任何视觉改动**。
