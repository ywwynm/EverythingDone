## FableSol：帧率投票改用 FIXED_SOURCE，让 SurfaceFlinger 不再因偶发漏帧把我们降到 60

上一版读数出现 `hz 120.0/120.0` 但 `grid 16.6`——**面板模式已被我们的投票拉到 120，
但 SurfaceFlinger 给本应用的渲染速率仍被单独降到 60**。这两个是不同的量：投票影响了
模式选择，却没能锁住渲染速率。

原因很可能是投票用的兼容性标志：`FRAME_RATE_COMPATIBILITY_DEFAULT` 的语义是「应用可以
自适应」，SurfaceFlinger 因此仍会按实际提交节奏做内容检测——偶尔漏一帧就判定我们是
60fps 内容，把节拍降下去，而降下去后物理子步从 1 变 2、开销翻倍，就再也回不来。

本版改为 `FRAME_RATE_COMPATIBILITY_FIXED_SOURCE`，声明这是固定帧率内容，让投票对内容
检测更有粘性。**如果奏效，"有时 120、有时 60"会直接消失**——偶发的 p95 越线只会掉一帧，
而不是锁死一段时间。这比继续砍 1~2ms 的性价比高得多。

判据：`grid` 是否稳定在 8.3。若仍会掉到 16.6，说明这条路也不通，只能靠压低耗时。

### 关于上一版读数的说明

上一版（裁窗）在真机上读到 `sample` 2.1ms，比之前的 1.5ms 更高。但**这两次读数不可比**：

| 段 | 上次 60fps 态 | 上一版 60fps 态 | 本轮改过吗 |
|---|---|---|---|
| `vtx` | 1.2 | 1.5 | 否 |
| `phys` | 1.0 | 1.5 | 否 |
| `drain` | 0.1 | 0.2 | 否 |
| `sample` | 1.5 | 2.1 | 是 |

**所有段一致上涨约 35%，包括一行未动的三段**，说明设备当时处在更慢的 DVFS 状态。
裁窗的净效果以桌面探针为准：同一进程内前后对照，`surface2d.sample` **172µs → 97.9µs
（−43%）**，与 42% 的裁剪比例吻合。

### 下一步：`vtx` 的 GPU 化

按当前数字重新评估其收益：`vtx` 1.5ms + `sheen` 0.3ms，GPU 化能拿到约 1.3~1.8ms。
要让 p95 稳在 8.33ms 内需要 p50 ≲ 4.4ms——快状态（p50 5.6）差 1.2ms，GPU 化刚好够但
没有余量；慢状态（p50 8.0）差 3.6ms，GPU 化不够。**它能让快状态站稳，但挡不住设备
进入慢状态**，不是一劳永逸的方案。
