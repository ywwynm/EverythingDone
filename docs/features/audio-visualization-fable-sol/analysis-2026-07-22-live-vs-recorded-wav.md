# 真机实时 ≠ 回放录制的 WAV（2026-07-22）

用户用 `20260722001826.wav` 复现：Android 上"刚上来的声音就立刻触发巨浪、水位几乎
一直是满的、涨到一半还会卡一下"，Python 打开同一个文件却"第一个声音什么都没触发、
全程水位流速都低很多"，并自问"是不是 android 录制时读到的音频跟最终的 wav 不一样？"

**是的，就是这个原因。** 下面是证据链与由此定位到的两个真实缺陷。

## 一、WAV 缺掉了分析器已经消费过的前导

`AudioRecorder.RecordingThread.run()` 里两件事的门控条件不同：

```kotlin
if (mFableSolReceivers.isNotEmpty()) {          // ← 从 startListening() 起就喂
    val (fsFrames, fsEvents) = mFableSolAnalyzer.feed(mono, sampleCount)
}
...
if (mIsRecording) {                              // ← 只有按下录音键之后才写文件
    fos.write(audioBytes, 0, readSize)
}
```

`startListening()` 在录音界面打开时调用，`startRecording()` 才把 `mIsRecording`
置真。所以**分析器听到的音频比 WAV 多一段前导**，长度等于用户在界面上停留的时间。
底噪、归一化中心、七境解码器、巨浪 episode 全部在那段前导里就已经建立。

用同一段音频、只改前导做对照（`scratch/preroll_test.py`，前导取自文件自身）：

| 前导 | 源文件开头 | 全程 |
|---|---|---|
| 无（= Python 打开 WAV） | IDLE 4.6s → CALM，water 0.90 | 最多 CLIMAX 0.9s |
| 12s 安静 | 1.1s → CALM → GROOVE → LIFT → **CLIMAX 3.3s**，water **1.00** | 几乎全程满水位 |
| 12s 有声 | 直接 LIFT 开场 → **PEAK 4.8s** | 几乎全程满水位 |

内容完全相同，**只因为分析器之前听过什么，表现就从"几乎没反应"变成"全程高潮"**。
所以拿 WAV 回放去对比真机是无效的——文件里根本没有决定那次表现的那段音频。

## 二、由此暴露的缺陷 1：水位没有"贴地过渡"

水位走固定绝对刻度 `fixed_loudness01(loud_s_db)`，而采集档 `PHONE_CAPTURE_V1`
给 250Hz 以下加 18dB 搁架、又整体 +10.5dB，房间低频轰鸣的 K 计权短时响度足以落进
−30..−2dB 的满刻度区。此前唯一的拦截是 A 计权静音门——**门一开水位就直接冲到
~1.0，中间没有任何过渡**。于是底噪学得稍低一点，房间声就撑满水位。

实测两条时间线在同一时刻 `loud_db` 只差 0.3dB，`floor_db` 差 2.3dB，结果一边判静音
（water 0）、一边 water 0.983 + wave_scale 2.35 + 水位 156.9dp。

**修复**：给水位加一条连续的贴地衰减，按"高出 A 计权底噪多少 dB"做 smoothstep
折减（`NEAR_FLOOR_SPAN_DB = 14.0`）。真正的说话/音乐远高于 14dB，不受影响；贴着底噪
的内容不再撑满水位。A 计权安全通道始终看原始 PCM，采集调理对它不可见。

（中途试过两条弯路，都已回退并记录：① 把启动窗口的底噪播种改成"取窗口最小值"——
最小值太乐观，反而让门更松；② 给底噪加"学习期快时间常数"——它让底噪更快贴住房间声、
门抬高，把本来该有的反应也门掉了。真正缺的是水位的连续过渡，不是底噪的收敛速度。）

## 三、由此暴露的缺陷 2：水位限速器在抖动

`CriticalSpring` 的 33.6dp/s 限速是**对输出硬钳位**，并把 `velocity` 改写成 ±slew。
下一帧弹簧从这个被压低的速度又算出更大的位移，于是在"贴限速"与"弹簧自由"之间
逐帧来回跳：

```
 t=10.42  v=35.07  SLEW
 t=10.47  v=23.43
 t=10.52  v=35.22  SLEW
 t=10.57  v=35.07  SLEW
 t=10.62  v=23.43
```

实测 **33.2% 的帧贴着限速，|加速度| 反复出现 ±350dp/s² 的尖峰，峰值 434dp/s²**。
这正是用户说的"涨到某个高度突然卡一下、抽搐一下，但也没到最高水位"。

**修复**：改用项目已有的 `soft_limit` / `FableSolCubicResampler.softLimit`（C∞ 软饱和）
限制每步位移，速度与位移始终一致。修复后同一段音频**贴限速的帧从 33.2% 降到 0%**。

## 四、修复后的双端一致性（同一个 WAV，两端 44.1kHz）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 状态完全一致的帧 | 73.0%（初次审计）→ 86.6% | **88.1%** |
| PEAK/CLIMAX 档一致 | 96.8% | **100.0%** |
| `water` / `kinetic` / `flow01` 相关 | 0.96 / 0.97 / 0.98 | **0.999 / 1.000 / 1.000** |
| `level` mean&#124;Δ&#124; | 3.06dp | **0.48dp** |
| 贴限速的帧 | 33.2% | **0%** |

## 五、仍然存在、且属于设计而非缺陷的一点

分析器在录音开始前就在跑，是**有意的**——录音界面一打开水面就该对声音有反应。
因此"回放 WAV" 与"真机实时"永远不会逐帧一致：前者从冷启动开始学底噪，后者带着
已经学好的底噪。修复贴地过渡之后，这个差异的**后果**已经从"全程满水位 vs 几乎没反应"
收敛到"高一档 vs 低一档"，但差异本身不会消失。

如果希望两者严格可比，只有两条路，都属于产品决策：
1. 录音文件把分析器消费过的前导一起写进去（文件会比用户按下录音键的时刻长）；
2. 按下录音键时重置分析器（会带来最长 4.5s 的启动窗口，水面在录音刚开始时发呆）。

目前**两条都没做**，维持"界面一打开就有反应"的现状。
