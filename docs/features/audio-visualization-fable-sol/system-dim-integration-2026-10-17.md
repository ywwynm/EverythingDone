# 卓易通音频弹窗的 C 系统暗层接入

## 已有证据与范围

用户在 debug 202610161648 的 A～I 对照中确认 C 有效：固定 PQ 和生产海浪 PQ 均未报告穿透；轻微偏色与黑角尚未排除。B 无暗层仍穿透，因此本轮采用系统暗层，不能简单归因于应用暗层本身。

仅 `AudioRecordDialogFragment`、`AudioPlayDialogFragment`、`FableSolTuningDialogFragment` 显式启用，基类复用 `FableSolDisplayPolicy.usesPqCompatibility` 的 API 34+／HUAWEI／System 判据。其它弹窗、普通 Android 及图片 HDR 不进入新分支。

## 生命周期

- 第一次显示前设置系统暗层标志，不创建该弹窗的应用暗层。出现按实际粒子进度渐入，稳态 dim=0.6；不开粒子时沿用 220 ms 的暗层淡入量级。
- 同一实例的策略不随 HDR 强度变化。HDR 关闭仍由既有渲染器重建真正的 sRGB SDR 表面；原快照遮盖及目标 EGL 首帧校验保持，背景与圆角不改。
- 粒子在每次动画独占的透明承载窗口显示，位置按屏幕坐标换算，处于原弹窗及其暗层上方。关闭等待承载窗口布局、快照和粒子首帧；创建／捕获失败有有界退出，不能永久残留窗口。
- 粒子接管后，原窗口的 window／decor alpha 同时置零，并明确隐藏独立 Surface；窗口仍为 VISIBLE，继续承载淡出的系统暗层（此前 alpha=1 方案已按本次回归撤回）。归零后等待窗口提交再移除。无粒子时内容与暗层短淡出。重复调用不会恢复已隐藏内容，销毁宿主则立即结束。
- 保留普通设备原有时序，不把全局弹窗改为排队。音频附件在内容退出时暂停，取消录音提前结束服务并标记已处理，防止保留暗层期间继续出声或重复结束新会话；保存与导出依旧在原 `onDismiss` 流程中处理。

## 诊断和验证边界

长按海浪设置的“HDR 高光增强”进入对照页，原 A～I 与模式 1～6 均保留。导出新增 `production_dialog_dim_log`，从 `fablesol_dialog_dim.log` 附带最近 64 KiB，记录弹窗名称、Window 标识、暗层值、应用暗层覆盖、窗口／内容 alpha、出现、粒子接管、暗层归零、提交后移除、承载窗口创建与关闭。仍同时附带 `production_hdr_log`；不保存记事正文、音频或截图，日志尾部可能包含前几个弹窗，排队写入未强制刷新会明确标注。

JVM 新增关闭门闩测试，覆盖首帧／覆盖层任意到达顺序、归零前窗口提交、重复关闭、迟到回调、宿主摘除及两个弹窗独立退出；重跑既有暗层、捕获、Surface 恢复门闩、HDR 关闭与 PQ 强度策略。普通桌面 JVM 无法复现卓易通屏幕合成，故没有能证明“穿透和闪烁已修好”的自动化测试。未连接设备或模拟器。

用户设备复验：分别打开／关闭录音、音频附件和设置；比较粒子关闭、流体、飘散；在设置里往返 HDR 关闭和非零强度，检查白底、圆角、后方内容、背景明暗及窗口残留。快速关闭、连续打开弹窗和取消录音也需检查。若仍异常，导出同一次操作后的日志并描述发生阶段。

构建及 45 项相关测试通过（0 失败／跳过），debug `202610170210` 已发布阿里云。远端元数据与本地一致，APK 回读 SHA-256、大小、原 debug 签名和新增 DEX 标记均核对通过。发布日志为 `debug-updates/update-20261017100956.md`；完整记录与哈希见 `sessions.md`。


## 2026-10-17 实际弹窗回归（用户视频，待修复）

用户反馈 C 接入版打开录音弹窗时，先露出整块背景，再在该背景上播放凝聚；点外部和返回均没有可见的消散；圆角外还有黑色区域。视频 `87001bf225bd76588c504ced6935a07a.mp4`（15.71 秒，1136×1920）逐帧确认：约 2.4 秒面板背景已完整出现，2.52～3.24 秒粒子在其上凝聚；约 14.2 秒面板直接消失，随后只有暗层淡出。黑角在静态录音阶段仍在。此前 45 项 JVM 测试仅验证关闭门闩与策略，未覆盖窗口真实合成，不能作为这些视觉问题已解决的证据。

按顺序排查：① 保留 window alpha=1、仅隐藏 decor 无法覆盖背景／独立 Surface；② 专用粒子承载窗口的布局、抓图、首帧或层级失败；③ View 圆角与底层 Surface 的矩形范围不一致。将原始视频作为视觉复现证据，围绕真实调用链补充可导出的阶段日志；不连接设备，不把本地编译等同于实机修复验证。


### 本轮候选修改

- 出现的兼容窗口在 `DialogFragment.onStart` 显示前建立隐藏租约；恢复 window alpha=0 与 decor alpha=0 共同隐藏。系统暗层仍由原窗口的 `FLAG_DIM_BEHIND` 和 dimAmount 管理，不再为了暗层保留实际窗口像素。
- 粒子关闭接管后同样设置 window alpha=0；去掉交接时追加不可聚焦标志，避免原窗口在独立粒子窗口创建后再改变焦点／排序。新粒子宿主等待布局返回后再添加 Surface；出现／消失均显式保持宿主 Decor 透明。
- 准备失败不再伪造“粒子首帧和覆盖层已就绪”：通过单独回调走内容短淡出。新增可导出的捕获开始／结果／耗时／失败路线、宿主布局、GL 首帧、会话结果、overlay 摘除日志，分清真正播放与回退。
- 黑角另加卓易通专用的原生 Surface 容器圆角候选，按整个 Dialog 轮廓计算 crop；设置页的海浪预览只占上半部，不能把预览自身的底边也裁圆。`SurfaceControl.Transaction.setCornerRadius` 属于非 SDK 能力，只尝试反射调用，不设置可访问豁免；系统拒绝则记录 `native_window_corner_unavailable` 并保留既有 shader／View 裁剪。该候选需要实际导出日志与观感确认，不能声称仅凭 JVM 已解决黑角。
- 普通设备不进入上述兼容分支，海浪 shader、PQ 编码、强度 0 的 SDR 重建与原快照遮盖保持。JVM 只覆盖实际使用的轮廓坐标变换与既有状态门闩，无法模拟卓易通的窗口合成。

### 圆角本轮证据与候选

- AOSP／本地 API 36 `SurfaceView.updateSurface` 会重新提交自身 `mCornerRadius`，只向 SurfaceControl 提交一次圆角既不能更新窗口透明区域的圆角，也可能被后续更新覆盖；没有新日志，暂不判定上一版反射成功与否。
- 旧 C 固定图记录 `previewY=98`、预览高 600、窗口高 2053，仍报告窗口黑角。测试 Surface 未覆盖窗口最上方，故“所有黑角都来自海浪 shader”缺乏依据。旧 D～I 相对于 A 测试且主要记录偏色／穿透，不能冒充 C 下的圆角单项结论。
- 本轮候选将最终清角放在 Decor 的 ViewOverlay 中，以普通 Canvas CLEAR 清除整个窗口圆角之外的像素，同时关闭 Decor 自身的 clipToOutline；原轮廓仍保留供阴影／快照读取，内容根节点裁剪保持。仅三个卓易通音频窗口启用；不改粒子交接、HDR 颜色会话、Surface Z 序或着色器。
- 诊断页新增 J（C＋仅关闭 Decor 裁剪）、K（C＋上述显式清角），C→J→K 分步比较。K 为新候选；窗口四角的 PixelCopy alpha 只用于核对窗口缓冲，不能代表卓易通最终屏幕像素。所有结果仍随原日志导出，不保存图片。
- 桌面无授权设备可执行真实 Window／Surface 合成；没有可证明黑角修复的 JVM seam。本轮采用已有截图／视频和用户逐版复验闭环，保留标记日志；本地回归仅保护已有状态与策略。
