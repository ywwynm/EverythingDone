## 用户反馈

- 第 0 层水体相对正常，其余层偏灰、乳白、浑浊、暗淡；饱和度和局部对比不足。
- 水体、波浪与光线缺少晶莹感、体积感和物理可信度。
- 需要阴影提供立体感，但既有阴影一旦处理不当就会产生灰黑脏感。
- Android 与 Python 必须同步演进，不能各自形成不同的材质语义。

## 结论摘要

当前问题不是“阴影不够重”，而是四项结构性问题叠加：

1. **景深色阶主动消色**：`lighten_far=0.864` 把越远的身份色越多地插值到白色；在 OKLab 中，
   白色的 `a/b` 接近零，因此色度会按 `1-lighten` 近似线性消失。
2. **HDR 银泽覆盖过宽**：连续 HDR sheen 对全部非首层水带都有非零基线，缺少局部太阳反射方向、
   粗糙度分布和归一化能量约束；其近中性白增量会进一步把各层推成银灰/乳白。
3. **光照职责混合**：微法线直接乘主体色，多个反射、透射、光晕和阴影 pass 独立增减最终颜色；
   同一份能量被重复追加或按绘制顺序压暗，容易同时出现脏斑和白膜。
4. **SDR/HDR 不是同一材质基线**：Android 只有 HDR 输出才使用 scene-linear `RGBA16F`；SDR 在
   编码 sRGB `RGBA8` 中合成。水体 shader 内还存在 encode/clamp/decode 往返，因此 HDR 开关不仅
   改变超白峰值，也改变 `0～1` 范围内的混合结果。

所以，应先重构颜色与能量合同，再讨论更强的自阴影。只调高 HDR headroom、闪点数量或阴影增益，
不能修复主体色度和材质分瓣，反而可能继续增加大面积白膜、APL 或暗噪声。

## 代码事实

### 1. 逐层混白必然导致远层低色度

Android `FableSolLayerColorPolicy.kt` 与 Python 对应策略使用：

```text
lighten = depth01 × (lighten_far + moodBright × 0.08 + breath)
layerColor = mixOklab(identityColor, white, lighten)
```

默认 `lighten_far=0.864`。忽略动态增量时，九层混白量和剩余 OKLab 色度约为：

| 层 | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 混白量 | 0 | .108 | .216 | .324 | .432 | .540 | .648 | .756 | .864 |
| 身份色色度剩余 | 100% | 89.2% | 78.4% | 67.6% | 56.8% | 46.0% | 35.2% | 24.4% | 13.6% |

动态 mood/breath 还可能把远层继续推向纯白。`FableSolParams.kt` 中“直接混白不会让 S 塌陷”的注释
与实际 OKLab 插值不符。该结果不是轻微参数偏差，而是现有“水层景深阶梯”的数学定义。

同时，`FableSolMaterialPolicy.kt` 中宏观明暗、微法线、SSS、反射、阴影、闪点和流光的存在度随
景深衰减。远层因此同时发生“身份色色度越来越少”和“形成结构的材质项越来越弱”，最终只剩
越来越白、越来越平的主体。

### 2. 第 0 层与其它层实际走不同材质路径

共享 `water.frag` 对首层 front fill 跳过微法线、SSS、连续 HDR sheen 与连续 HDR transmission；
其余水带会进入这些分支。因此“第 0 层相对正常、其它层共同灰白”的反馈与代码分支高度吻合。

### 3. 连续 HDR sheen 不是受约束的镜面 BRDF

`grazingSheenExcess()` 当前具有以下特征：

- `sunBoost` 存在覆盖全域的 `1.0` 基线；
- `pow(..., 0.70)` 形成很宽的响应；
- 没有微表面法线分布 `D`、几何遮蔽 `G`、明确 `N·L/N·H` 门控或粗糙度归一化；
- 最终以中性近白 excess 直接加到主体，没有和透射/主体共享能量预算。

它更接近“宽域银白膜”，而不是只在正确太阳方向出现的局部镜面反射。连续 sheen、surface band、
glint core 目前还会分别追加反射，没有共享 Fresnel 或剩余能量。

### 4. 微法线与阴影正在污染主体，而不是只塑造表面反射

`water.frag` 的微法线把线性主体色约乘到 `0.82～1.18`，于是高频法线噪声直接变成主体明暗纹理；
这正是阴影/法线稍强就出现脏斑的高风险来源。

当前至少存在三套暗化：顶点 shader 的宏观坡面阴影、optical pass 的 `backShade`、片元 shader 的
微法线乘法。`backShade` 又位于部分反射/透射 pass 之后，导致它按绘制顺序压暗已合成光效；后绘的
glint/veil 则完全不受它影响。这里缺少统一的“直射光可见度”语义。

### 5. 透明、透射和折射的命名与实现不一致

- 九层 alpha 全为 `1.0`；主体按远到近 painter order 覆盖，没有真实背景透过。
- 当前 transmission/SSS/thin glow/veil 主要是 additive 提亮，不是 Beer–Lambert 透射。
- 连续表面是九个深度锚点、每区间若干行组成的 2.5D 高度场，没有介质厚度、背景采样、折射或
  真实自遮挡。

因此，近期应先追求“主体不透明但材质职责符合介电水规律”的低风险升级；是否引入少量真实背景
折射/吸收，需要另行裁决，不能把现有 additive 光效直接称为物理透射。

### 6. 颜色空间与 HDR 合成合同不一致

- Android HDR：scene-linear `RGBA16F`；Android SDR：编码 sRGB `RGBA8`。
- `water.vert` 的层颜色/环境颜色合成和部分正向光照发生在编码 RGB。
- `water.frag` 存在线性化后又编码并裁到 `0～1`、随后再次线性化的链路，基础 SSS 超白信息在中途
  被硬裁掉。
- optical pass 在两种路径都使用相同硬件 alpha blend，但 SDR 目标并非线性 framebuffer。
- 多个 HDR optical pass 叠加后没有统一 headroom budget 或 soft limiter。

正确的 sRGB blending 应先把目标值线性化、在线性空间混合、再编码；Khronos 对 framebuffer sRGB
合成明确描述了这一顺序。当前 HDR 与 SDR 因而不是“相同 SDR 基线 + HDR 局部 excess”。

## Python 固定场景量化

使用现有 ModernGL 离屏路径，固定 seed、时间、Thing 色与波形，并关闭离散 optical effects，只
比较连续水体 shader。初步结果：

- 打开当前连续 HDR sheen 后，第 1～6 层线性亮度中位数相对无 sheen 约增加
  `+.115 / +.093 / +.098 / +.052 / +.030 / +.015`；
- 第 1～5 层约 `90%～100%` 像素至少一个通道超过 reference white；
- HSV 饱和度中位数：第 1 层约 `.897 → .796`，第 2 层 `.831 → .760`，第 3 层
  `.907 → .822`；
- 首层 front fill 的差值严格为零，和用户看到的首层/其它层分化一致；
- 关闭宏观阴影、微法线或 SSS 对逐层色度中位数影响很小；把 `lighten_far` 从 `.864` 降到
  `.60/.36`，第 4～7 层 OKLab 色度则分别约增加
  `+.033/.041/.045/.049` 与 `+.060/.077/.089/.098`。

这些结果只用于定位，不代表直接把 `lighten_far` 改成某个值就是最终方案。它证明当前低色度首先
来自基色阶梯和宽域白色 sheen，而不是缺少更深阴影。

## 任意 Thing 颜色专项审计

用户补充了一个必须进入材质合同的边界：Thing 颜色可以是任意颜色，尤其可能接近白色、浅色、
低色度、接近黑色或位于 sRGB 色域边界。不能再以默认粉色的上下明度余量代表全部输入。

### 当前公式在浅色上的确定性退化

Python 与 Android 的 `depth_scattering_palette()` 使用：

```text
deep       = OKLab(L × 0.70, C × 1.15)
subsurface = OKLab(L × 1.15, C × 0.85)
```

因此，只要输入 `L≥1/1.15≈0.8696`，subsurface 的目标明度就会被钳到 `1.0`；sRGB 色域在白点处
只能容纳零色度，后续 gamut mapping 会把浅黄、浅粉、浅青、浅蓝全部压成纯白。当前不是“浅色
SSS 较弱”，而是多种不同身份色的 SSS 确定性汇聚到同一个 `#FFFFFF`。

固定样本的当前派生结果如下：

| 输入 | OKLab L/C | 第 8 层混白色 | 固定 `ΔL=-.10` 阴影色 | deep | subsurface |
|---|---|---|---|---|---|
| `#FFFFFF` | `1.000/.000` | `#FFFFFF` | `#DEDEDE` | `#9E9E9E` | `#FFFFFF` |
| `#FFF4C2` 浅黄 | `.964/.065` | `#FFFEF7` | `#DED3A2` | `#A39760` | `#FFFFFF` |
| `#F6D8E5` 浅粉 | `.911/.037` | `#FEFAFB` | `#D5B8C5` | `#A0818F` | `#FFFFFF` |
| `#D8F2F2` 浅青 | `.942/.027` | `#FAFDFD` | `#B8D1D1` | `#7C9898` | `#FFFFFF` |
| `#BDD9FF` 浅蓝 | `.877/.061` | `#F6FAFF` | `#9EB9DE` | `#6986AE` | `#FFFFFF` |
| `#15151A` 深色 | `.198/.010` | `#DBDBDC` | `#030305` | `#090909` | `#1C1C1C` |
| `#000000` | `.000/.000` | `#D2D2D2` | `#000000` | `#000000` | `#000000` |

这张表同时证明：

- 对浅色，继续混白与 SSS 都没有可用的向上差异，只剩灰阶暗化承担形体，容易读成脏污；
- 对深色，现有景深阶梯会把黑色远层直接推成浅灰，颜色身份同样失效；
- 对色域边界上的高饱和色，保持原色度时可能既没有向上也没有向下的明度余量，任何明暗变化都
  必须伴随受控的色度压缩；直接逐通道裁切会产生色相/色度断裂。

### 色域边界是硬约束

OKLCH/sRGB 色域在白点和黑点收束到 `C=0`，并且不同色相在同一明度下的最大可用色度不同。
因此不存在一条同时满足“任意输入、固定提亮量、完全保色度、永不越界”的统一曲线。

W3C CSS Color 4 的目标色域映射选择在 OKLCH 中保持色相和明度、压缩色度，并使用 `ΔEOK≈.02`
作为约一个 JND 的局部裁切判断；它也明确指出图像/纹理需要考虑相邻像素关系，不能把每个像素当
作互不相关的离散颜色：
https://www.w3.org/TR/css-color-4/#gamut-mapping

Oklab 作者给出的 sRGB gamut clipping 资料展示了不同恒定色相切片下 `L/C` 边界和 cusp 差异；
投影目标需要随使用情境选择：
https://bottosson.github.io/posts/gamutclipping/

### 推荐的“身份锚点 + 自适应材质响应”

建议不再把 Thing 色理解为“所有层、所有像素都必须等于的填充色”，而拆成两个职责：

1. **身份色锚点**：至少一块稳定、低反射/低曲率区域保持原始 Thing 色，让用户能够识别记事身份；
   渐变 Thing 则保留原始横向渐变关系。
2. **材质响应区**：其它区域允许因环境反射、Fresnel、光程、局部镜面和直射可见度产生明暗，
   但不能把这些结果反向写成逐层统一的新基色。

每个输入色在 CPU 建立 palette 时计算 `L/C/h`、线性亮度 `Y`、恒色相下的 sRGB 上/下余量和
`Cmax(L,h)`。用余量连续地切换主形体线索，不设置突变的“浅色模式/深色模式”：

- **近白/浅色**：没有足够向上余量；主体参考色可在材质响应区有界地下移明度，原色保留在身份
  锚点和最薄/最受光区域。形体主要依靠有亮暗方向结构的环境反射、轮廓与小面积 HDR 镜面；不用
  宽域灰黑阴影。
- **近黑/深色**：没有足够向下余量；主体暗部接近身份色，主要使用亮环境反射、镜面和受限透射。
- **中间色**：上下余量都可用，但仍由同一连续函数分配，避免阈值跳变。
- **低色度/无彩色**：色相接近无定义，不凭空注入固定蓝绿或冷灰；以干净的中性亮度结构和介电
  镜面表达材质。
- **色域边界高饱和色**：保持色相，按需要压缩色度进入目标色域；禁止逐 RGB 通道硬裁。

### 浅色阴影的正确职责

浅色上的“脏”不能仅靠更换阴影色解决。推荐：

```text
final = environmentFill
      + F × environmentReflection
      + visibility × directSunSpecular
      + visibility × directTransmission
      + pathLengthAbsorption
```

- `visibility` 只削弱太阳直射镜面、直射透射/散射，不乘整个主体，也不压暗环境反射；
- 微法线不再产生主体明暗噪声；
- 需要较暗结构时，优先来自环境反射的方向差或受控光程吸收，不使用最后覆盖的灰黑带；
- 对严格纯白、纯黑等极端输入，如果不允许任何非锚点区域偏离原色，SDR 内就不存在双向塑形余量，
  只能依赖轮廓、背景差、折射或 HDR 峰值，无法保证在任意同色背景上仍有充分立体感。

## 九层颜色路径专项调研

### 用户新增约束

保留颜色身份不能把九层都做成与记事原色近似的颜色。目标是同时满足：第 0 层为原色锚点、其余
层仍能辨认为同一 Thing 色系、九层主体具有连续且足够的差异。单独提高远层色度下限并不能完成
这三项职责。

### 当前问题是采样路径指向白点，而不是 OKLab 本身失效

现有 `mixOklab(identity, white, t)` 在 OKLab 中沿直线走向 `(L=1,a=0,b=0)`，因此无论输入色相
为何，`a/b` 和 OKLCH 色度都会近似按 `1-t` 同比消失。OKLab 提供了较均匀的明度、色度和色相
坐标及平滑插值，但它不会自动替应用选择正确终点；算法作者也把三者可独立调整和均匀过渡列为
该空间的设计目标：
https://bottosson.github.io/posts/oklab/

因此应优先更换“白点终点 + 线性层号”的路径合同，而不是先迁移到另一个颜色空间。

### 可行路径：OKLCH 等色相色调轨迹

初步推荐在每个输入色的 OKLCH 等色相切片中构造一条在目标色域内的轨迹：

1. 默认主要改变感知明度 `L`，而不是同时把色度 `C` 拉向零；
2. 用每个 `L/h` 下的 `Cmax` 预先约束轨迹，撞到色域边界时优先换方向或缩短明度范围，其次才
   最小幅降低色度；
3. 对映射后的曲线按 OKLab 累积弧长重新等距采样九层，而不是直接使用 `layer/8`；
4. 浅色上行空间不足时沿较暗方向采样，近黑向亮，低色度输入不凭空指定色相；
5. 最终再检查 8-bit sRGB 量化后的相邻差异，避免纯黑附近多个样本合并。

W3C CSS Color 4 说明 OKLCH 在固定色相切片中具有良好的视觉色相稳定性，`ΔEOK` 可直接使用
OKLab 欧氏距离；其色域映射同样以固定明度和色相、降低色度为主，并给出 `ΔEOK≈0.02` 的一个
JND 参考。该数值只能作为“低于时存在高风险”的告警线；高于它不代表动态九层稳定可分，更不是
九层边界的最终验收目标：
https://www.w3.org/TR/css-color-4/#ok-lab
https://www.w3.org/TR/css-color-4/#gamut-mapping
https://www.w3.org/TR/css-color-4/#color-difference-OK

算法作者给出的 sRGB gamut cusp/交点方法可用于求每个 `L/h` 下的可用色度边界，但“向 cusp
采样”本身不应成为审美目标；cusp 只负责约束轨迹仍在色域内：
https://bottosson.github.io/posts/gamutclipping/

W3C 的 Local-MINDE 适合作为最终安全映射，不应直接充当九层 palette 生成器。规范明确指出这类
算法针对独立颜色；需要保留邻接关系时应整体处理。因此九层应先共同落入可行走廊，或在最终映射
后重新按 `ΔEOK` 分配，避免九层分别压色后再次合并。

### HCT tonal palette 作为对照，而非当前首选

Google Material Color Utilities 的 HCT 使用 CAM16 hue/chroma 与 L* tone，`TonalPalette` 正是
保持请求 hue/chroma、改变 tone 并在色域不足时降低实际 chroma：
https://github.com/material-foundation/material-color-utilities
https://github.com/material-foundation/material-color-utilities/blob/main/java/palettes/TonalPalette.java
https://github.com/material-foundation/material-color-utilities/blob/main/java/hct/Hct.java

它证明“同一色系可以通过 tone 形成明显分级”，但 HCT 主要服务 UI tonal palette，转换和求解也
明显比当前 OKLab 路径复杂。FableSol 两端已经具有 OKLab 变换和恒明度/恒色相的色度二分映射；
在数值对照证明 HCT 明显更优之前，继续扩展 OKLCH 更容易维持 Android/Python 同构。

本地 HCT 对照在 sRGB/ARGB 落地后还出现了相对输入 OKLab hue 的漂移：纯蓝约 `11.2°`、深蓝约
`3.8°`、默认渐变紫端约 `3.0°`，均超过当前最深传播路径约 `2°` 的身份色约束。HCT 可以保留为
离线参考，但没有证据支持为了本轮主体阶梯引入 CAM16/HCT solver 及额外 Python 端口。

### 工程 A/B 起点与边界

- 规范中的 `ΔEOK=0.02` 只表示一次 JND 级别的风险告警。早期提出的相邻
  `0.022～0.028` 过度贴近该告警线，已不再作为清晰分层的推荐起点；当前改为跨颜色验证
  `.032～.040` 级别及近层加权方案，但具体目标不能脱离色域可行性和动态画面自行定稿。
- 对有明确色相的输入，可先试第 8 层保留第 0 层 `65%～80%` 的 OKLCH 色度；不能设全局绝对
  chroma floor，近中性色也不得为了达到比例而人工增色。
- 浅黄/浅青的上方色域边界很窄，应反向压暗；极饱和 cusp 色可能无法同时满足九级总跨度和色度
  保留，需要缩短跨度或最小幅降色度，不能逐 RGB 通道裁切。
- 若渐变两端分别接近白色和黑色，局部采样方向会相反，中间可能出现颜色层差归零；颜色轨迹之外
  仍需一个不制造灰雾的低频层序后备量。
- 极黑输入在连续 OKLab 中等距，不保证量化为 8-bit sRGB 后仍有九个不同码值；必须在最终输出
  精度上做回归。

### `ΔE` 阈值的适用边界与三阶段验收

W3C 的 Local MINDE 色域映射把 `ΔEOK=.02` 作为一次 JND，用途是判断原色与裁切色之间的误差
是否可能不可察觉，不是动态九层水体的稳定层级识别目标：
https://www.w3.org/TR/css-color-4/#binsearch

CIE 明确指出，JND 在标准和科学文献中没有普遍一致的定义，并会随检测概率、观察条件与任务改变；
因此不能把 `.02` 简单乘二或乘三，冒充本产品的合格目标：
https://files.cie.co.at/738_CIE_TN_001-2014.pdf

标准点对点色差主要面对均匀色块。S-CIELAB 原始论文在求图像色差前加入空间视觉滤波，说明波纹、
阴影、高光、背景与空间频率都会改变差异可见性：
https://web.stanford.edu/~jefarrel/Publications/1990s/1997_Zhang_Silverstein_Farrell_Wandell.pdf

近期原始心理物理研究还表明，阈值附近的颜色辨别与阈值以上的差异感知并不共享同一敏感度规律；
九层稳定顺序识别属于后者，不能由 JND 直接推出：
https://www.nature.com/articles/s41598-024-64215-0

因此采用三阶段测量，而不是一个全链路数字：

1. **主体色板**：逐记事色、渐变位置和相邻层记录 `ΔEOK min/P5/median`；低于 `.02` 告警，
   高于它仍需进入动态验收。
2. **SDR 合成后**：在稳定内部和边界法线方向做面积平均或固定空间低通采样，记录
   `full/body` 分离度保留、低于告警线的覆盖面积、层序翻转次数、时间最差值与 P5；不能只看均值。
3. **录音 HDR**：分别检查未录音、约 `360ms` HDR attack、稳定录音与退出。目标峰值、tone mapping
   和显示参考明确时使用 ICtCp/`ΔEITP`；否则只作相对排序。ITU-R BT.2124 的 `ΔEITP=1` 也只是
   最敏感适应条件下“可能一次 JND”的告警参考，达到并不保证稳定识别：
   https://www.itu.int/dms_pubrec/itu-r/rec/bt/R-REC-BT.2124-0-201901-I%21%21PDF-E.pdf
   https://www.w3.org/TR/css-color-hdr-1/#ictcp

验收采用近层词典序优先：先保证 `0↔1`、`1↔2` 在 HDR 进入全过程不坍缩或翻转，再检查
`2↔3`，最后优化中远层。内部稳定目标线最终应由 FableSol 动画中的相邻远近判断/边界标记任务
校准，不虚构文献没有给出的 UI 阈值。建议保留观测量：`adjacentDeltaEOKMin/P05/Median`、
`adjacentDeltaEITPMin/P05`、`separationRetention`、`belowAlarmCoverage`、
`orderingInversionCount`、`temporalWorstFrame` 与 `nearTripletWorstPair`。

### 深蓝完整九层复核

用户指出只看深蓝第 8 层 `#4769BE` 无法判断九层是否真的分明，因此又以 `#1E3A8A` 为锚点，
按最终 8-bit sRGB 量化结果复核全部九层。当前 `lighten_far=.864` 的静态主体阶梯为：

```text
#1E3A8A → #334F98 → #4964A5 → #6079B2 → #778EBF
         → #90A3CB → #A9B8D8 → #C3CDE4 → #DDE3F0
```

其相邻 `ΔEOK` 为 `.0678～.0694`，但第 8 层只保留 `13.7%` 色度；区分主要来自大幅漂白。
固定原始 OKLCH 色相、只在 sRGB 色域迫使时降低色度、再按弧长等距采样后，三档结果为：

| 目标相邻弧长 | 九层最终量化色值 | 实际相邻 `ΔEOK` | 第 8 层色度保留 |
|---|---|---|---|
| `.020` | `#1E3A8A #234090 #284697 #2D4C9D #3251A4 #3757AA #3D5DB1 #4263B7 #4769BE` | `.0185～.0208` | `100.6%` |
| `.024` | `#1E3A8A #244192 #2A4899 #304FA1 #3656A9 #3D5DB1 #4365B9 #4A6CC0 #5073C8` | `.0231～.0257` | `99.7%` |
| `.028` | `#1E3A8A #254293 #2C4A9C #3353A5 #3A5BAE #4263B7 #4A6CC0 #5174CA #597DD3` | `.0271～.0295` | `99.8%` |

因此此前的 `#4769BE` 实际对应最克制的 `.020` 档，不应代表最终推荐强度。`.024` 可作为第一轮
视觉基线，`.028` 用于检验动态水面和局部 HDR 覆盖下是否需要更强层序；是否足够分明仍由完整
阶梯图和最终动态画面裁决，而不是由一个 JND 数值自动决定。

### 近三层优先的非等距复核

用户进一步明确：验收对象是八个相邻边界，且最近三层必须优先保持区分，不能用首尾总差掩盖
近层合并。对深蓝 `#1E3A8A` 追加三组量化后对照：

| 目标间距 | 实际相邻 `ΔEOK` | 第 8 层 | 第 8 层色度保留 |
|---|---|---|---|
| 八段均匀 `.032` | `.0307～.0331` | `#6287DE` | `99.9%` |
| 八段均匀 `.036` | `.0337～.0379` | `#6B91E9` | `100.1%` |
| 前重后轻 `.036,.036,.034,.032,.030,.028,.026,.024` | `.0367,.0351,.0339,.0331,.0299,.0271,.0261,.0249` | `#5F84DA` | `99.2%` |

前重后轻方案的九层最终量化色值为：

```text
#1E3A8A → #274595 → #304FA1 → #3959AC → #4163B7
         → #4A6CC0 → #5174CA → #597CD2 → #5F84DA
```

它的前三个实际间距均值约 `.0352`，只比均匀 `.036` 低 `2.6%`，证明非等距路径可以优先保护
最近三层。不过用户随后明确远层变亮本身没有问题，重点是不能发灰或低饱和；因此把总弧长从
`.288` 降到 `.246`、把最远层从 `#6B91E9` 收到 `#5F84DA` **不再构成方案优势**。均匀 `.036`
在该深蓝样本中同样保留约 `100%` 绝对 OKLCH 色度，并为后五个边界提供更强区分，必须继续保留
为候选，不能仅因第 8 层更亮而淘汰。

这组数值只能作为深蓝对照；`[36,36,34,32,30,28,26,24]` 至多是“近层加权”的待选形状，不是
已确认模板。正式合同应由整条 Thing 的统一极性、明暗余量和色域可行性共同决定八段实际距离，
不能对任意颜色写死八个绝对值：

- 浅色或近白若直接累计 `.246` 向暗，会从约 `L=.96` 降到 `.71`，容易形成过深硬色带；应缩放
  总预算，并用其它低频主体层序量补足不足的边界。
- 高饱和色可能在第一步就撞到色域边界，明度变化和色度下降会共同放大实际 `ΔEOK`；必须限制
  单步实际色差与色度损失，而不是盲目追逐目标值。
- 该权重只负责主体阶梯。录音 HDR 的连续银泽若继续大面积抹白，仍会在动态画面中覆盖近层边界，
  必须由独立的局部光学能量约束解决。

新的比较口径是把三项指标分开：八段相邻 `ΔEOK`、逐层绝对/相对色度保持，以及明度跨度。明度
可以明显增加；只有当继续提亮迫使颜色接近中性轴、从而违反色度合同，才应停止、换向或引入其它
低频层序量。

针对用户要求的“相邻层而非首尾、最近三层最高优先级”，继续测试三组目标步长。当前中间候选为
`[.040,.040,.036,.034,.032,.030,.028,.026]`，总弧长 `.266`；保守组各段约低 `.004`，激进组
各段约高 `.004`。沿固定 OKLCH hue、`C≤C0`、只有色域迫使时单调降低 `C` 的路径采样并量化到
8-bit sRGB 后，中间候选得到：

|---|---|---|---:|---|

合并。相反，深蓝向亮能够保留完整绝对色度。方向应由整条 Thing 的可行性与保色结果选择，而非
按色名硬编码。

又对默认粉和浅黄把全部八段同比缩放为 `.75/.875/1.0`：

- 默认粉向亮的 `C8/C0` 分别为 `.555/.470/.391`，三个预算都不如向暗的 `.759/.707/.651`；
  `.875` 向暗端点为 `#8A0022`，前两段约 `.035`，比完整预算的 `#7B001D` 更克制。
- 浅黄三个向亮预算都会撞到白点；`.875` 向暗端点为 `#B3A979`、`C8/C0≈1.01`，前两段约
  `.036/.033`。
- `.75` 档前两段约 `.030`，仍可能不足；完整 `1.0` 档近层最强，但粉色远端明显更深。

因此下一轮建议裁决的不是一个不可调常量，而是参数化的前重型 profile：保留前三段完整目标
`.040/.040/.036`，只把后五段以默认 `.875` 缩放，得到约
`[.040,.040,.036,.0298,.028,.0263,.0245,.0228]`。后五段强度保留 `.75～1.0` 调节范围；若完整
动画显示远层仍需更强，再提高而不改算法。

这套数值曾提出按“八段走完、量化后不合并、`C8/C0≥.60`”筛选向亮/向暗，再按远层色度保留
择优。用户查看结果后明确否决：它会使默认粉、黄色、青色和绿色等大多数样本越远越暗，与期望的
景深方向不符。该自动方向评分现已撤回，不进入实现。

新的问题定义是：越远越亮属于先验产品语义，色域分析只决定“还能亮到哪里”，不再决定是否把
整条阶梯翻为向暗。当固定 hue、保色的向亮路径耗尽时，应停止继续消色，并用稳定的第二低频层序
量补足余下边界。第二线索必须在未录音 SDR 就可见、不依赖局部闪点、不能是黑色阴影或中性白膜；
其具体职责继续结合代码与物理资料裁决。

因此建议让整条 Thing 渐变以所有横向采样点的最小可用亮弧 `A` 分配颜色路径：先保护
`0↔1/1↔2`；`A≥.080` 时各给 `.040`，不足时各分 `A/2`，避免把浅色仅有的余量全部耗在第一段。
余量再按 `.036/.034/.032/.030/.028/.026` 顺序发放；剩余小于约 `.012` 时停止制造接近不可见的
主体色差，记录每段缺口供第二低频线索使用。当前更稳妥的候选是 `C/C0=.70` 软目标与 `.60` 硬
底线：正常向亮路径到 `.70` 即停；`.70→.60` 只用于补齐 `0↔1/1↔2`，不得为继续拉开远层耗用。
例如默认粉在 `.70` 已能完整满足前三段；高亮黄可从 `.70` 的总弧 `.065` 借到 `.60` 的 `.086`，
把最近两段补到 `.040/.040`；浅黄借到 `.60` 仍只有 `.030`，只能约 `.015/.015`。两档均是待画面
裁决的工程候选，不是文献阈值；`C0<.02` 的近中性色不使用比例判定。

Display-P3 的数值只能小幅延长部分颜色路径：粉色 `A60` 约从 `.183→.229`，绿色约
`.258→.266`，但浅黄仅 `.030→.035`、近白不变。W3C 明确说明 CSS Color 4 的 WCG 空间仍按 SDR
设计；P3 扩展色度三角形，不增加参考白以上的亮度余量，白端仍收束：
https://www.w3.org/TR/css-color-hdr-1/#introduction
https://www.w3.org/TR/css-color-4/#predefined-display-p3

HDR 才能在参考白以上继续提高同一颜色的线性亮度。BT.2100 允许 scene/display-referred 线性 RGB
使用更高动态范围；在线性 RGB 三通道同乘曝光且未碰到实际显示色彩体积时，RGB 比例和 XYZ
chromaticity 保持。BT.2390 同样推荐对 luminance 求尺度后统一乘 RGB，以避免逐通道处理扭曲
saturation/hue：
https://www.itu.int/dms_pubrec/itu-r/rec/bt/R-REC-BT.2100-3-202502-I%21%21PDF-E.pdf
https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2390-12-2025-PDF-E.pdf

但 HDR headroom 受设备峰值、目标色域、系统 tone mapping 和观看环境制约，大面积九层主体不能
长期占用峰值；而且未录音状态没有 HDR。故 HDR 同色曝光只能在录音态增强已存在的向亮层序，不能
承担 SDR 基础边界：
https://www.w3.org/TR/css-color-hdr-1/#defining-dynamic-range

更严格地说，未录音与录音 HDR 应共用同一套 SDR reference-white 主体阶梯，HDR 可用弧不计入
`A`。录音切换只允许局部 Fresnel 肩、透射、crest 与闪点进入 `>1`，主体腹部不乘 exposure；否则
会再次出现第二、第三层点击录音后整层突亮。可先将 body-interior 中位变化 `≤1%`、P90 `≤2%` 和
每层 `>1` 覆盖约 `1%～3%` 作为原型观测档，不先写成最终阈值。

### 色域耗尽后的第二低频线索审计

代码与材质职责对照后，候选优先级如下：

1. **宽肩式、保色的界面响应**：每个 ribbon 沿低频轮廓形成宽软、低幅的当前色亮侧反射肩，并在
   相邻内侧形成更宽更弱的当前色深侧透射/光程肩；两侧近似能量守恒，不混白黑、不成为 1px 描边，
   且 SDR/HDR 常显。浅色亮侧到顶时仍可由折射位移、法线方向差与很弱的保色深侧提供边界。
2. **屏幕空间最小层距**：只给投影后的相邻轮廓距离设下限，作为任意颜色下不依赖材质的硬兜底；
   当前若干约 `4dp` 的间距最容易在运动中丢失。
3. **低频 Fresnel/环境方向差**：按真实视线/反射方向提供晶莹体积感，但不直接混入 horizon 白或暗
   环境色，也不独自承担边界保底。
4. **弱体积吸收**：只辅助透射色密度，不能承担“越远越亮”，近中性色也没有有效色度差。
5. **粗糙度与 alpha**：粗糙度继续由音频和微表面控制；alpha 保持 `1`。两者均不作为层界后备量。

共享 GL 可以在 `water.vert/water.frag` 使用已有 `aDepth01` 与 `uStartLayer` 构造 ribbon 内坐标；
Python ModernGL 已直接解析同一 shader。Android Canvas 的同构落点为 `WaveVisualizerFableSol.kt`，
Python QPainter 为 `ui/canvas.py`。参数和权重分别由 Android `FableSolMaterialPolicy/FableSolParams`
与 Python `params.py/gl_scene.py` 共享同一合同。正式实现前仍需裁决宽肩是否符合外观，防止九层变成
重复描边或交替条纹。

真实 Fresnel 与上述稳定界面肩必须分开命名。PBRT 给出水的 `IOR≈1.333`，介电反射/透射比例由
入射角决定；远处虚拟视线更接近 grazing 时可增强明亮环境反射，但暗环境下不保证变亮，且反射色
来自环境，不能作为任意 Thing 色的边界硬保证：
https://www.pbr-book.org/4ed/Reflection_Models/Specular_Reflection_and_Transmission
https://www.pbr-book.org/4ed/Reflection_Models/Rough_Dielectric_BSDF

同一水材质的九层不得改 IOR；只能改变虚拟视角、法线场、光程、遮挡与反射环境。Microfacet
roughness 会改变反射/透射瓣宽度并遮蔽底纹，直接把远层设得更粗会趋向 frosted/milky，因此不作
层界标量：
https://diglib.eg.org/bitstream/handle/10.2312/EGWR.EGSR07.195-206/195-206.pdf?sequence=1

Beer–Lambert 有色透射只会衰减穿过介质的光，可用于波谷/重叠区但不能解释远层均值上升：
https://pbr-book.org/4ed/Volume_Scattering/Transmittance
https://pbr-book.org/4ed/Volume_Scattering/Volume_Scattering_Processes

因此如果要在任意浅色和 SDR 中硬保证八个边界，就必须承认存在一项受限的感知后备：宽软、低幅、
随当前层色派生的界面肩，或改用屏幕空间最小层距。它不能伪装成九个真实 Fresnel 界面；真实
Fresnel/折射继续负责物理晶莹感，感知后备只填补量化后的相邻分离缺口。

用户已接受 D129 的界面肩方案。正式实现将每对相邻主体色量化后的分离缺口作为权重来源，而不是
给八条边界固定同强度；肩部覆盖低频轮廓的宽区域，亮侧与深侧均从当前位置的层色派生并服从
D126，不新增白/黑边。主体腹部、主体逐层均值和 HDR 录音态切换保持隔离。具体 profile 宽度、
峰值和缺口映射函数继续通过 Android/Python 同构原型调节，不能提前写死为调研中的示意百分比。

随后用户要求停止对个别颜色继续纠结，统一按提亮处理。D130 因此把 bright-only 收口为单一产品
规则：第 1～8 层只沿固定 hue 的感知明度正方向移动，必要时做目标色域映射，不再运行方向评分、
按 hue 分支或向暗回退。前述 `.70/.60`、各代表色容量和 P3 对照保留为实现诊断资料，不再构成
逐色产品逻辑；色域边界处的不足由已接受的界面肩辅助。

### 远层亮度与色度合同复核

针对“远层可以亮，但不能灰或低饱和”，进一步比较了三种固定 hue 提亮路径：

1. **保持绝对 OKLCH `C`**：默认 `Ctarget=C0`，只有目标色域迫使时才降低；最直接地保留原始
   感知色度，也不会把本来克制的 Thing 颜色自动增艳。
2. **保持 `C/Cmax(L,h)`**：会跟随色域切片的非单调外形自动增艳或褪色；深蓝 `#1E3A8A` 的
   第一段就可能达到约 `117.7% C0`，不适合作为任意颜色的主体合同。
3. **相对色度再夹紧到绝对范围**：例如限制在约 `[.75,1.05]C0`，可作为后续 A/B，但目前没有
   比绝对 `C` 合同表现出更稳定的跨颜色优势。

因此推荐先以绝对 `C` 为目标，并用色度保留率限制可用明度路径：工程 A/B 可先把 `C/C0≥.70`
视为首选、`.60～.70` 视为需要视觉复核；D130 已否决低于阈值时换向，向亮余量不足只允许停止
继续推高主体，并把剩余相邻分离缺口交给 D129 的界面肩。若后续确实
需要补偿高明度下的主观饱和感，增艳上限先不超过 `1.05C0`。这些都是待视觉验证的工程起点，
不是规范常量。

固定 hue 下，当前向白进度若仍达到 `t8=.864`，粉色 `#F02A4B`、亮黄 `#FFD600` 与浅黄
`#FFF4C2` 的最远层都只能保留约 `11%～14% C0`，说明事后 gamut-map 无法挽救错误路径；必须在
达到色度下限前停止继续提亮；不得再对浅色反向。深蓝的保色向亮余量较大，因此可以把第 8 层
推得明显更亮，而不必像前一轮判断那样刻意收低 `L8`。

用户已接受 `Cdesired=C0`、主体不自动增艳的默认合同；局部材质响应仍可产生更鲜亮像素。

### 随层保色阴影的代码审计

用户进一步要求所有效果产生的暗部都从当前位置的当前水层色变深，不能直接混黑。这里必须区分
“生成一块暗色”与“真实遮挡移除一项直射光”：前者应派生当前层深色，后者只削弱对应光照分瓣，
两者都不应把最终主体、环境反射和透射总和乘向黑色。

用户已确认“当前水层色”的精确定义：当前层当前横向位置已经完成景深阶梯和 Thing 渐变采样、
但尚未加入反射、透射、次表面散射、高光、闪点与 HDR 的低频主体色。该定义同时确定了绘制顺序：
随层深色只能作为主体/直射光阶段的输入，不能在材质总和完成后以暗色 overlay 补画。

当前 Android/共享 GLSL 与 Python 同构代码初步审计如下：

全链路没有发现仍在生效的显式 `mix(..., black, ...)`、灰黑接触阴影、Multiply/Darken blend 或
固定黑色水体 overlay；当前“脏暗”的风险主要来自功能上等价的主体乘暗、错误暗色目标和事后
source-over 覆盖。

| 路径 | 当前行为 | 与新合同的关系 |
|---|---|---|
| 显式 `backShade` 带 | Android `FableSolShadowColorPolicy.backShade()` 与 Python `_back_shadow_color()` 均从传入的当前层起点色降低 OKLab `L`，再以 source-over 覆盖 | 方向部分正确；但渐变整条带只取起点 hue、现有转换逐 RGB 通道裁切，且暗带会覆盖先画的薄峰透射/SSS，与宏观阴影重复 |
| 宏观坡面阴影 | `FableSolGlRenderer.buildColors()` / Python `_layer_colors()` 先从未应用景深阶梯的原始 Thing 色生成一套 `deepColor`，再由九层共同朝它混合 | 不符合；远层阴影不是从远层当前色变深，而会突然朝第一层身份深色回落 |
| `deepColor` 本身 | `FableSolDepthScatteringPolicy` / Python `depth_scattering_palette()` 使用 `L×.70、C×1.15` | 不符合默认保色合同；既不是当前层色，也会自动增艳 |
| 微法线负向响应 | `water.frag::applyWindCombedMicroNormals()` 把整个 `linearColor` 乘以最低 `.82`；视觉第 1 层 front fill 跳过，第 2/3 层权重接近满值 | 风险最高；微法线应改变对应直射/镜面分瓣，不能把高频法线噪声乘进最终主体体色。Python QPainter 没有该负向乘法，当前双端还不完全同构 |
| Canvas AGSL 深度吸收 | 原 `FableSolAgsl.LAYER_SRC` 在编码 sRGB 中以 `.72～1` 标量乘整个 `c.rgb` | 不符合 D127；已在本轮实现中删除，旧九层 Canvas 填充恢复为纯主体渐变。真实体积吸收待独立介质透射/折射分瓣存在后再实现 |
| 线性宏观阴影混合 | `water.vert` / `FableSolLightColorPolicy` 在 `litLinear` 与上述 `deepLinear` 间插值，并按亮度损失封顶 | 混合空间与强度封顶合理，但目标色来源错误；换成当前位置随层深色后才满足新合同 |
| environment surface band / edge feather | 主题环境色参与 surface band，并在最远层参与 edge feather；暗主题可形成暗 overlay，亮主题可形成乳白 overlay | 不应归类为阴影，但会改变色度与对比；必须按环境反射职责和当前层 Fresnel 预算单独重构，不能继续充当暗部或远层溶解手段 |

因此不能只保留已有 `darkenOklab()` 就宣告阴影已保色。正式重构至少要统一：当前层/当前渐变
位置作为暗部锚点、感知空间恒 hue/近似恒 `C` 的深色派生、只削弱直射分瓣的 visibility，以及
Android GL、Canvas、Python ModernGL/QPainter 的同构输出。

绘制顺序也必须进入验收：当前独立 back-shade 在 body、薄峰透射和连续 HDR 之后以 alpha 覆盖，
因此即使暗色本身来自水层色，仍会把不该受阴影影响的材质分瓣一起压暗。准备态
`presentationAlpha=.16` 把整个场景混向主题背景，属于全局呈现状态而非水体阴影，也应与本合同
分开诊断。

### 体积吸收的独立合同

用户已确认 D127：体积吸收不沿主体恒绝对 chroma 轨迹，也不生成随层阴影色；它只在线性光空间
衰减穿过介质的光。应以 Beer–Lambert 形式 `T=exp(-σₐ·d)` 为物理参照，由身份色关系派生吸收谱，
允许光程增加带来自然的变深、适度增饱和与极小 hue 漂移，同时以最大光学深度、hue 偏移和最低
剩余能量约束艺术范围。主体、环境 Fresnel、镜面、闪点和 HDR excess 必须绕过该衰减。

这意味着旧 Canvas AGSL 在编码 sRGB 中对整个 `c.rgb` 做标量乘法既不满足光空间，也不满足分瓣
职责；正式同步实现需要 Android GL/Canvas 与 Python ModernGL/QPainter 明确相同的透射输入和
近似光程。在真实背景采样尚未存在时，只能把它称为有界介质透射近似，不能宣称完整物理折射。

渐变还暴露出方向选择必须是整条 Thing 级约束：`#FFF4C2→#1E3A8A` 两端各自选择向暗/向亮时，
约在横向 `x=.467` 处，相邻层 `ΔEOK` 中位数仅 `.001`，九层几乎合并；整条渐变统一向暗后，各
位置中位数约 `.0175`。默认 `#F02A4B→#6E62DF` 统一向亮时，各位置约 `.021～.025`。因此不能
按像素或停靠点硬切极性；应在四个身份色停靠点上对整条 Thing 做 maximin 方向选择。纯白到纯黑
等无法由任一单方向覆盖的极端渐变，则必须由另一项低频主体层序量补足。

## 录音启动时第二、第三层突亮的确定性诊断

### 用户观察

- 第 0 层在准备态和录音态都保持记事原色；
- 第 1、2 层原本仍接近记事色，但点击开始录音后会在短时间内明显提亮并趋向乳白；
- 用户怀疑该变化来自最近一次 HDR 优化。

### 反馈环与复现

在 Python ModernGL 中固定身份色 `#F02A4B`、固定非零 speech-like 音频、随机状态、时间与几何，
先稳定运行 240 帧至 `t=4s`，随后冻结同一场景，只把 HDR gain 设为
`0/.25/.50/.75/1.0`，headroom 固定为 `3.6×`。逐层 mask 来自实际网格轮廓，不使用截图手工框选。

| 可见层 | gain=0：中位线性亮度/OKLab 色度 | gain=1：中位线性亮度/OKLab 色度 | 亮度变化 | 色度变化 | 任一通道 `>1` |
|---|---|---|---:|---:|---:|
| 第 0 层 front fill | `.2068/.2275` | `.2068/.2275` | 约 0 | 约 0 | 约 0% |
| 第 1 层，即视觉第二层 | `.2647/.2046` | `.4154/.1510` | `+56.9%` | `-26.2%` | `94.2%` |
| 第 2 层，即视觉第三层 | `.3145/.1797` | `.4198/.1458` | `+33.5%` | `-18.9%` | `72.1%` |

即使把 headroom 限为 `2.0×`，第 1/2 层仍分别提亮 `38.1%/26.5%`、丢失
`17.7%/14.8%` 色度，因此问题不只是把目标上限从 `2.0×` 提到 `3.6×`；更根本的是宽域
continuous sheen 把 headroom 用在了主体面积上。

### 正交消融

关闭全部独立 optical entities 后，gain=1 相对 gain=0 的第 1/2 层中位亮度增量分别约为
`+.1109/+.0881`：

- 只启用 continuous HDR sheen：`+.1099/+.0881`；
- 只启用 continuous HDR transmission：两层中位增量均约为 `0`；
- 恢复离散闪点、表面带等实体：不改变上述中位数结论。

所以，录音启动后的宽域乳白几乎全部由 continuous HDR sheen 独立解释，不是透射、闪点、音频
几何或缺少阴影造成。

### Android 触发链

`AudioRecordDialogFragment.preparedToRecording()` 在同一时刻触发两个 `360ms` 过渡：

1. presentation alpha 从 `.16→1`；
2. `setRecordingHdrActive(true)` 令 `FableSolHdrTransition` 把 HDR gain 从 `0→1`。

音频分析器在点击前已经 `startListening()` 并持续运行；`AudioRecorder.startRecording()` 只开始把同一
PCM 写入文件，不会启动、重置或切换颜色分析。`colorBright/colorEnergy` 的平滑时常约为
`2.0s/1.2s`，mood 约为 `1.5s` 且需要 Section event；它们既没有“开始录音”开关，也明显慢于
`360ms` HDR 过渡。因此麦克风捕获到的点击声最多形成较慢的次要 breath 变化，不能解释这个稳定、
按层选择的启动突亮。

presentation alpha 会影响所有层，其方向还取决于主题 backdrop；在白色 backdrop 的固定实验中，
`.16→1` 反而降低主体亮度并恢复饱和度。它不能解释“第 0 层不变而第 1/2 层乳白提亮”的选择性。

共享 `water.frag` 则明确只对 `vFrontFill==0` 添加 HDR sheen/transmission，第 0 层 front fill 跳过。
第 1/2 水带使用最高的一组连续 sheen 峰值，约跨越 `2.70→2.40` 与 `2.40→2.10`；
`grazingSheenExcess()` 的 `sunBoost` 又有固定 `1.0` 全域基线，最后把约 86% 中性白、14% 身份色
组成的 excess 直接加到主体上。代码结构与用户观察逐项对应。

### 变更历史

- `c03b4f71`：首次建立 HDR Surface、FP16 scene-linear、录音态门控与 `360ms` gain；此时还没有
  continuous water sheen。
- `9f8de815`：加入 `grazingSheenExcess()`，为解决“HDR 看不见”主动把太阳方向从局部门控改成
  全域基线加成；这是宽域银白膜的首次来源。
- `72d9c853` / 阿里云 Debug `202607141022`：headroom 从 `2.0×→3.6×`，并把 continuous sheen
  扩成 `2.70/2.40/2.10/1.80/1.50/1.29/1.08/1/1` 的逐层峰值，最符合用户所说的“上一次
  HDR 优化”。

结论：HDR 能力链和“开始录音后才进入 HDR”的状态关系都不是回归源；录音门控只是把既有问题
显现出来。真正需要替换的是宽域、近中性白、无方向/面积/总能量预算的 continuous sheen。

用户进一步澄清：HDR 不应被限制为只能增强镜面和闪点。局部表面反射、薄峰透射、连续受光结构及
其它有助于晶莹感、立体感和水体质感的响应都可以获得 HDR；约束对象是整层或大面积中性白抬升、
多个效果无预算累加，以及由此造成的层界消失和持续乳白。后续应在保留录音 HDR 状态变化的前提下，
重分配各分瓣的覆盖、方向性和能量，而不是把连续水面 HDR 整体关闭。

## 权威资料支持的物理约束

### 清澈水体应分开处理表面与体积

Unreal Engine 的 Single Layer Water 把 scattering、absorption、reflection、refraction 和 shadowing
作为独立职责；其资料也说明低 scattering 更接近清水，高 scattering 会产生厚、乳白的介质观感：
https://dev.epicgames.com/documentation/en-us/unreal-engine/single-layer-water-shading-model-in-unreal-engine

Google Filament 的 transmission/volume 模型使用路径长度上的吸收：
`color × exp(-absorption × distance)`，并给出水的 IOR 约 `1.33`：
https://google.github.io/filament/main/materials.html

PBRT 的辐射传输与 transmittance 章节给出 extinction、scattering、absorption 和指数透射的基本关系：
https://www.pbr-book.org/4ed/Light_Transport_II_Volume_Rendering/The_Equation_of_Transfer
https://pbr-book.org/4ed/Volume_Scattering/Transmittance

### 反射应由 Fresnel、法线尺度和粗糙度控制

Fresnel 关系决定介电水面正视角反射弱、掠射角反射强；NVIDIA 的水体章节建议用几何波负责大形体、
法线细节负责局部反射，并随距离过滤高频细节：
https://developer.nvidia.com/gpugems/gpugems/part-i-natural-effects/chapter-1-effective-water-simulation-physical-models

Filament 的 specular anti-aliasing 同样以法线方差修正粗糙度，目标是保住高光形状而不是把法线噪声
乘到主体色：
https://google.github.io/filament/main/materials.html#specularanti-aliasing

### 合成应发生在线性空间

Khronos 对 sRGB framebuffer 的说明明确要求：读取目标色后先线性化，在线性空间完成 blending，再
编码回 sRGB：
https://wikis.khronos.org/opengl/Framebuffer#Colorspace

Android 的 mixed SDR/HDR composition 由系统和设备能力共同决定，窗口请求的 desired headroom
不保证全部交付；因此不能用提高请求值替代局部能量控制：
https://source.android.com/docs/core/display/mixed-sdr-hdr
https://developer.android.com/reference/android/view/SurfaceControl.Transaction#setDesiredHdrHeadroom(android.view.SurfaceControl,float)

## 推荐材质合同

以下方向仍需逐项 grilling；其中 C 的产品定义已由 D119 裁决，但具体颜色映射尚未确定：

### A. 所有输出共用同一 scene-linear 基线

- Thing/环境输入只解码一次；水体、阴影和 optical blending 全部在线性空间完成。
- Android HDR/SDR 与 Python ModernGL 共用同一 `0～1` 材质结果。
- SDR 只在 present 末端做输出编码/必要 shoulder；HDR 只开放局部 `>1` excess。
- Python QPainter fallback 保持公式语义同构，不承诺 HDR 像素一致。

### B. 把水材质拆成互不混淆的分瓣

```text
macro normal       → 轮廓、光程、低频形体
filtered micro normal → 环境反射、太阳镜面、可选弱折射
body/volume        → 身份色 + 低散射 + 路径长度吸收
environment Fresnel → 天空/环境反射，阴影不压暗
direct sun specular → 小面积 GGX/近似微表面高光，可进入 HDR
crest transmission → 仅薄、背光、波峰区域
direct visibility → 只削弱太阳镜面与直射散射，不乘最终主体
```

推荐的能量关系是：

```text
final = (1 - F) × volume
      + F × environmentReflection
      + directVisibility × directSunSpecular
      + directVisibility × crestTransmission
```

连续 sheen、surface band、glint 和 halo 不再各自无条件加白；它们应分别表达环境基底、连续镜面尾部、
稀疏高峰和显示光晕，并共享局部 mask、粗糙度与 headroom budget。

### C. 景深只保证层序，不再把“混白”写死为唯一手段

D119 已确认保留“近到远有序、相邻可辨”的产品职责，并取消对单一 `mix to white` 或降低整体
alpha 的绑定。后续候选实现可组合：

- 独立、受限的明度走廊；
- 身份色色度下限；
- 随距离变化的粗糙度和高频细节带限；
- 环境反射占比、低散射和光程的受控变化；
- 必要时仅保留少量艺术化空气透视，而不是把远层推到近白。

`CONTEXT.md` 已同步把 **水层景深阶梯** 改为结果约束。上述候选量仍须经过任意 Thing 颜色的
适配裁决和固定场景验证，不能直接视为实现结论。

### D. HDR 只负责小面积峰值，不负责主体变白

- 保留水的 `IOR≈1.333`、`F0≈0.02037` 和 Schlick Fresnel。
- 用 filtered normal + roughness 控制局部太阳镜面；初始 perceptual roughness 可在近层
  `.09～.16`、中远层 `.12～.22` 内 A/B。
- 以 `RGB>1` 覆盖率和 APL 约束连续高光；最高 `3.6×` 只留给稀疏 glint core，不能让大面积水体
  同时超白。
- 清澈基准先令 scattering 接近零，再少量增加；不要用近白 SSS 补偿体积感。

### E. 阴影先改职责，再考虑增强

- 移除微法线对主体色的负向乘法；微法线只进入镜面/反射/可选弱折射。
- 把 `backShade` 折叠为 `directSunVisibility`，只削弱太阳直射项。
- 宏观曲率暗部若保留，应表达“更长光程导致的身份色吸收”或“直射可见度下降”，不使用灰黑覆盖。
- 在分瓣、线性合成和色度阶梯稳定前，不引入屏幕空间/高度场自阴影；否则更精确的遮挡仍会把错误
  的主体乘法变成更明显的暗噪声。

## 推荐实施顺序

1. 建立固定 seed/time/Thing 色/波形的双端基准与逐层 L/C、线性亮度、APL、`RGB>1` 指标。
2. 统一 scene-linear 颜色与 blending 合同，移除 shader 中途 encode/clamp/decode。
3. 把景深明度与色度解耦，给远层设身份色色度下限。
4. 移除微法线主体乘法，把阴影改为 direct-light visibility。
5. 用粗糙度控制的环境/太阳镜面替换宽域 HDR sheen，并建立统一能量/headroom budget。
6. 引入低散射、受路径长度控制的风格化 absorption/transmission。
7. 单独 A/B 是否需要前 2～3 层的少量 scene-color refraction；最后才评估真实 horizon/self-shadow。

## Android/Python 同步与验收合同

- 继续以 `EverythingDone/shared/fablesol/glsl` 为共享 GLSL 单一权威；Android 打包该目录，Python
  ModernGL 直接加载，仅允许平台版本/precision 适配。
- 参数、逐层数组、pass 顺序、blend 因子、颜色空间 ABI 与能量上限必须同一切片更新；不能只同步
  同名默认值。
- Python 保留 `320dp×420dp`，Android 保留 `280dp×420dp`；比较归一化坐标和逐层材质统计，
  不要求几何逐像素重合。
- 固定回归至少覆盖高饱和红/蓝/绿、浅色、深色、渐变 Thing，静止/人声/onset/tilt、SDR/HDR
  gain/headroom。
- 增加分瓣调试视图：base/volume、Fresnel、environment reflection、direct specular、crest
  transmission、visibility、macro/micro normal、`RGB>1` 与 gamut clipping。
- Python FP16 是数值诊断，不等于真实 HDR 显示；最终 HDR 仍需 Android 实屏验收，且同时检查 SDR
  回退，防止系统 tone mapping 或混合 HDR 把非峰值区域压灰。

## grilling 裁决结果

“水层景深阶梯”的根定义冲突已由 D119 解决：保留九层低频主体的远近顺序和相邻可辨，取消
“必须越远越大量混白、越透明”的手段绑定。D120/D121 曾探索逐色自动方向，但已由 D128/D130
取代：所有颜色统一逐层提亮，不再按输入色、色相、P3/HDR 能力或剩余色域切换为向暗。D122/D117
确认第 0 层低频主体基线承载 **记事身份色锚点**，第 1～8 层只从它派生。

主体颜色路径采用“OKLCH/OKLab 固定色相、感知明度只向亮移动、绝对色度在 sRGB 容纳时保持、
越界时才沿同色相压缩”的 bright-only 色板，取代固定向白混合。相邻 `ΔEOK` 目标、`.70/.60`
色度保留率和 front-load 曲线均是可调验收参数，不是新的逐色分支。量化或色域耗尽留下的层间
分离缺口由 D129 的宽软、低幅、随层保色界面肩补足；D126 同时要求所有显式暗色从当前位置的
当前层色派生。录音仍负责开启 HDR 能力，但 D118 禁止它改变主体基线，只允许局部、有方向和
有预算的反射、透射、受光结构及闪点进入额外 headroom。
