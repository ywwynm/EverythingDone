# 大视频进度与后台恢复排查

## 范围与基线

- 用户报告：饼图接近完成后长时间等待；较长时间处于后台后可能出现进度错误、反复重试或状态混乱。
- 使用指定的 OPPO PLZ110、Samsung SM-S9180、魅族 20 Infinity；所有测试数据在隔离包 `com.ywwynm.everythingdone.covervalidation` 内。
- 沿用 3 秒、25 fps、长边 720 的生成参数，读取 `10f009c3d`、`d4cc84298` 及既有编码器和取帧兼容性取舍后再决定实现。
- 既有验证覆盖短视频、UI 绑定和短暂导航往返，尚不能证明高复杂度媒体的进度准确性及进程被回收后的行为。本轮先记录真实进度与文件完成时间，再验证后台中断。

## 执行记录

- 三台指定设备均已在线。工作区存在通知诊断、空间照片等其他改动，本轮只修改动态封面相关实现和验证材料。
- 夹具为本地生成的 H.264 4K／30 fps／24 秒视频，108,845,923 字节，12 秒处生成 3 秒预览。未修改正式生成实现先测得：OPPO 33.832 秒到 99%，47.613 秒完成；魅族 48.781 秒到 99%，62.773 秒完成。两机都复现约 14 秒的 99% 停留。
- 待验证假设按顺序为：编码器收尾未计入进度；停止后旧生成仍运行并与新任务争用文件；恢复任务读取旧进度；重新绑定时状态／失败记录／完成回调不一致。
- 用户补充不锁屏，采用系统设置与测试应用切换；计划每机 12 次往返及至少 180 秒持续后台，另测明确的进程回收和调度停止。系统设置仅改变焦点，不激活设置项。
- 三星在真实前后台往返中复现同一 WorkRequest 的 `runAttemptCount` 升至 9、进度从 58% 跳至 12%。原始日志显示同一来源的第 41 帧与新一轮第 3、4、6 帧交错处理；旧 Worker 未响应停止，唯一工作并未阻止已经取消的线程继续执行。证据在 `tmp/cover-recovery/samsung-red-live.log` 及各机 JSON 时间线。
- 核对上游 `GCTGifEncoder.cpp`：`encodeFrame` 仅复制并保存像素；`release` 才集中构建全局色表、量化及编码。这不是简单的最后文件重命名耗时。

## 修复决定

- 保留现有高质量全局色表编码器、尺寸与帧率。逐帧阶段结束后进入明确的编码阶段，使用转圈；该库不提供编码百分比，不能伪造时间进度或让 99% 饼图长时间停留。
- Worker 检查停止信号，停止后不能写入进度、发布成功或持久化失败。同一输出串行，临时文件按生成轮次隔离；原生收尾不能中途取消时须等待其释放资源，新轮次不得与之重叠。
- WorkManager 进度附带执行轮次，UI 只接受当前轮次。实际文件就绪优先于过期调度状态；进程重建后重新生成必须从准备开始，不能沿用旧百分比。
- 参考：[WorkManager 停止契约](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/manage-work#stop-worker)、[编码器源码](https://github.com/waynejo/android-ndk-gif/blob/master/library/androidndkgif/jni/GCTGifEncoder.cpp)。
- 第一轮仅修复协作取消和进度，三星已不再交错取帧，但长后台仍被系统以 `EXCESSIVE RESOURCE USAGE / excessive binder traffic during cached` 回收。因取帧持续访问媒体服务，普通 Worker 不能保证进程处于适当的后台执行状态。
- 因此实际生成采用 WorkManager 前台执行：静默低优先级通知，仅含通用生成提示，完成自动移除；Android 15+ 使用 `mediaProcessing`，旧系统使用 `dataSync`。系统禁止从后台提升时退回调度等待，不计入真正生成失败次数。参考 [长时间运行的 Worker](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running)。
- 更换夹具身份后还发现：旧的持久化任务恢复时会重新计算新文件的缓存身份，误替换新来源生成。Worker 现校验入队时的输出身份，过期任务结束；生成期间再次校验源身份，不发布源文件替换前后的混合产物。同源互斥取得后清理此前进程留下的临时文件。
- 加入前台保护后三机的 12 次往返及约 3 分钟后台均完成，未再观察到旧轮次进度混入；魅族的集中编码仍可能被 ROM 暂停，返回后继续，不能保证后台持续运行。
- 进程回收场景虽然最后生成成功，但复核系统退出记录发现三机重启的前台服务都触发 `ForegroundServiceDidNotStopInTimeException`，该轮不能判定通过。项目的 WorkManager 2.9.1 没有 Android 15 前台超时处理；升级到包含对应修复及前台命令竞态修复的 2.10.5，再重新验证。参考 [官方发布说明](https://developer.android.com/jetpack/androidx/releases/work#2.10.5)。后续验收同时检查最终 UI、输出文件、系统退出记录和崩溃日志，不以最终成功掩盖中途崩溃。

- 最后一帧结束应进入集中编码的三项断言，修改实现前均失败；修复后相关状态、旧轮次过滤、取消与同源互斥的 7 项 JVM 检查通过。
- 升级 WorkManager 后完整 JVM 测试：250 个套件、1685 项，0 失败、0 错误、3 项跳过。精简结果见 `checks/background-2026-10-17/jvm-summary.json`。
- 旧 WorkManager 三机中途崩溃的原始栈保留为 `checks/background-2026-10-17/workmanager-291-crash-*.txt`，不计作最终通过。
- 最终复测使用 `wm2105-*` 场景前缀，脚本和复现步骤见 [复测工具说明](tools/background-recovery/README.md)。三机 9 组后台场景及各 72 项基础回归全部完成；最终卡片恢复数量和 GIF 播放，没有新发生的应用崩溃。每个产物均为 720×405、75 个不同画面帧、3 秒。
- ROM 的后台暂停、系统停止或杀进程仍可能发生。恢复语义是重新读取持久化任务、必要时从头生成；原生集中编码没有断点续跑能力。静默前台通知降低被回收的风险，但不是对所有 ROM 持续执行的保证。

## 回归应持续覆盖的边界

- 编码 API 返回不代表文件完成，需要按实际原生实现测量取帧、缓存帧与最终编码三个阶段；短视频或模拟进度不足以证明总进度准确。
- WorkManager 唯一工作保证调度去重，不保证已停止的同步原生调用已退出。回归必须让旧调用阻塞，停止后立即启动同源新任务，确认旧任务不能交付且新任务等待释放。
- 后台恢复必须同时观察任务轮次、真实卡片、文件和系统退出原因；“最后能成功”不能替代中途无崩溃的验证。
