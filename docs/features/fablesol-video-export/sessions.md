## 2026-07-27 — HDR10+ 800 尼特水体颜色偏浅诊断

- 用户反馈 HDR10+、漫反射白 800 尼特、高光起点 90% 的产物中，`#E80859→#671416`
  红色渐变水体比画面预览偏白、偏亮、偏浅；Dolby Vision 8.4、HDR10、HLG 较暗但颜色更准。
- 用 FFmpeg/ffprobe 检查 `phone_videos` 中 DV 8.4 与 HDR10+ 200/500/800 尼特四个样本；
  确认 PQ/HLG、BT.2020、有限范围、Main10、静态亮度元数据与逐帧 ST 2094-40 SEI 均可解出。
- 反解 YUV、PQ/HLG 并按白锚归一化后，三个 HDR10+ 档及 DV 8.4 HLG 基础层的红色通道比例
  中位差约 0.7%～1.2%，排除 P010 矩阵、范围、对齐或 UV 顺序造成显著色偏。
- 800 尼特产物的整帧平均亮度约 452～552 尼特、平均 maxRGB 约 526～603 尼特，峰值约
  7703 尼特；约 48% 帧含超过 2000 尼特目标屏幕的像素。红色水体通常低于 786～1118 尼特
  HDR10+ 膝点，抽查帧最多约 1.6% 红色像素入肩，故 90% 高光起点不是大面积水体变浅的直接原因。
- 结论：码流像素基本正确；主因是 800 尼特绝对白锚将普通画面整体推至高 APL，再叠加
  9.6 倍、约 7680 尼特峰值，触发手机的亮度/色容积映射并改变主观明度。动态统计仍有
  block mean、PQ 域均值和 `fraction_bright_pixels=0` 等质量问题，会增加播放器差异，但
  尚无证据表明它单独导致水体色偏。实时预览还会按当前 `Display.hdrSdrRatio` 限制
  headroom，而导出明确把场景基线 `1.0` 编成 800 尼特，两者本来就不是绝对亮度一比一。完整记录见
  `analysis-2026-07-27-hdr10plus-water-color.md`。未修改实现，未使用 adb。
- 后续评估当前“面板峰值 ÷ 4”自动白锚：它可作为追求明亮观感的粗略档位，但不适合作为
  无条件的保真默认值。约 2000 尼特面板会得到 500 尼特白锚；配合 9.6 倍强度后，母版峰值
  约为 4800 尼特，即面板峰值 2.4 倍，同时仍忽略最大帧平均亮度和饱和色可显示亮度。较稳妥
  的待裁定建议是自动档采用约 `min(面板峰值 ÷ 5～6, 400 尼特)`，并在厂商上报可信时再受
  `desiredMaxAverageLuminance` 约束；峰值 ÷ 4 保留为“明亮”档，800 尼特继续仅供手动高亮创作。

## 2026-07-28 - 三台设备的逐轮定位：验证判据、三轴联动与 EGL config

上一节加入编码器选择之后，OPPO、三星 Z Fold4 与华为平板各暴露出一批问题。本节按设备逐轮
定位，共发布十一个 debug 版本，最终得到的结论几乎都是**验证判据本身不完整**，而不是设备
不支持。

### OPPO：派生结论没有带上全部约束

把编码器钉成 AV1 之后，格式胶囊已经正确地只留下 HDR10 与 HLG，说明文字却仍写着「当前为
HDR10+」——那段文字用的是探测得出的全局 `autoFormat`，即编码器也取自动时的答案。同类问题
还有两处：体积估算按帧率上限计算而非实际可达帧率；能力报告只列第一个落点，因而 HLG 漏掉了
同样成立的 AV1。三处统一改为在当前选择的全部约束下解析（D55）。

### 三星 Z Fold4：从「HDR 落到软件 AV1」查到 EGL config

初始现象是选了 120fps 却输出 60fps 的软件 AV1。逐轮排除：

1. 补齐诊断——此前一种格式只要有任一编码器通过就丢弃其余失败原因，SDR 更是完全没有报告。
2. 修正探测自身：8 位档此前被拿 10 位输入表面验证，与正式导出不是同一条链路。修好后 H.264
   与 HEVC 的 SDR 通路立刻恢复为硬件编码。
3. `CodecException` 的消息常为空，补出厂商诊断串、错误码与瞬时标志。
4. 最终定位到 `EGL_RECORDABLE_ANDROID`：该机共 4 个 10 位窗口 config，带该属性的为 0 个。
   缺少它，缓冲就不带视频编码器用途位，编码器无法消费。此前代码把它当作「给驱动的提示」
   直接降档，判断有误（D56）。改为在 `eglChooseConfig` 落空后自行枚举全部 config 逐项核对；
   该机枚举后结果不变，因此其硬件 HDR 在公开接口上确实不可达（D58）。

### 华为平板：两处判据把可用与不可用同时判反了

- HDR10 被自身校验否决，报错是 `Encoder changed profile 2 to null`。编码器未在输出格式里
  回报 `KEY_PROFILE` 不等于它改掉了 profile，OMX 系尤其常见。改为与色彩键一致处理。
- 全部 HEVC 档位导出成 0 字节文件，只有 H.264 有数据。根因是验证判据只到「拿到输出格式并
  走到流结束」，而 `INFO_OUTPUT_FORMAT_CHANGED` 一到达即可登记轨道并启动封装，此后一个实际
  样本都不产出，收尾依然成功返回。改为以实际写入的视频样本数为硬门禁，并在发布前核对落盘
  大小（D61）。该机的成因同样是 10 位表面缺少 recordable，而 SDR 阶梯的首选档也是

  libplacebo 的策略，不拷贝其表数据或代码（LGPL）。生成后实测低频/高频能量比 0.0003，
  白噪声参照为 0.99——这一步不做谱验证的话，"看起来像噪声"的表也可能根本不是蓝噪声。
- **阈值表存秩不存 8 位值。** 8 位阈值的量化台阶接近一个 10-bit 目标码值，用它做 10-bit
  的无偏舍入等于用比刻度还粗的尺子去量。
- **居中色度相位不能硬套 `f0 = [1/8, 6/8, 1/8]`**：三抽头的对称中心在整数位置上，居中相位
  要用同族的 `[1,3,3,1]/8`。
- **HEVC 的色度位置绕不过完整 SPS 解析**（profile_tier_level、scaling list、short-term
  ref pic set 都在 VUI 之前，且都是可变长）。测试自带一个按 H.265 语法写 SPS 的 writer，
  写进去再读回来——否则这段解析器错了也只表现为半个像素的色边。AV1 反而简单：av1C 记录把
  `chroma_sample_position` 复制到第 3 个字节的低 2 位，不必解 OBU。

## 2026-07-29 - 批次 2 收尾：GPU 接线与"所有 10-bit 优先应用自有 P010"

把 2026-07-28 那半份 CPU 数学接进着色器，并按 D158 把输入通路变成候选轴。批次 2 完成，
全量 411 例单测 0 失败、debug APK 编译通过，未使用 adb。

- **闭环亮度修正要求三趟有严格顺序**：色度先量化写出，亮度趟读**真正写出去的**码值做参考
  上采样再解 Y′。如果亮度趟按"理想色度"求解，修正的就是一件播放端根本不会遇到的事。
- **一条按格式做的粗筛，在通路变了之后就成了错筛。** EGL 的 BT.2020 色彩空间是 **Surface
  输入**的要求；应用自有 P010 画进自己的离屏 framebuffer，那张 1×1 pbuffer 压根没打色彩
  空间属性。原先按格式粗筛会把"能编 P010、没有 EGL 窗口扩展"的设备整格式降到 SDR。判据
  下沉到候选一级后，导出与探测两处同源。
- **相位的时序问题只有缓存能解**：相位必须在第一帧渲染前定下，而码流声明要到编码开始后才
  拿得到。因此短探测把声明存进可行组合表，导出只读**已有**缓存（新增 `cachedMatrix`，绝不
  在导出关键路径上触发探测），取不到就按 Type 0 兼容语义——那正是解码端在 VUI 缺失时的
  解释方式。
- **未定义行为要当成 bug 处理，哪怕分支不会走到。** 蓝噪声资源缺失时也必须给 `usampler2D`
  绑一张完整纹理，于是补了一张 1×1 中性阈值纹理并用 `uNoiseEnabled` 让着色器走固定 0.5，
  正好等于"退回普通四舍五入"。
- **`MediaImage.close()` 在部分 AOSP 版本会 free 底层直接缓冲**，而那正是接下来要写入的
  内存。`getInputImage()` 只用于校正行距与作为"半平面交错"的门禁，用完不关，交给
  `getInputBuffer()` 按契约让它失效。

## 2026-07-29 - 批次 3：SDR 三种成片语义（含首次真机验收）

原生 SDR、稳定映射、动态映射三种语义 + 自动/严格 10-bit/严格 8-bit 位深全部落地；曲线族与
标定插值补为 D171。全量 441 例单测 0 失败，OPPO PLZ110 上四次真实导出逐项核对通过。

- **约束不等于曲线。** D68～D72 给的是"暗部恒等、高亮平滑压缩、只压缩不提亮、两个端点"，
  满足它们的曲线有无穷多条。实现必须补齐这一步并写成决策（D171），否则下一个人改动时既不
  知道当前形状从哪来，也不知道哪些性质是可以动的。
- **把自由度压掉，冲突就不会出现。** 膝点取 `K = 1 - e·(1-W)` 之后，第二段同时满足
  `F(1) = W` 与 `F'(1) = 1/e`；膝点与参考白落点从此不可能互相打架。这比"两个滑杆各调各的、
  再写一堆校验"稳当得多。
- **"够不到就不够"是正确答案。** 动态映射的控制峰值太靠近 1.0 时，要让峰值落到满幅必须用
  凸曲线，那等于在高光段放大对比度——直接违反"只压缩"。宁可让峰值落在 `T < 1`，也不为了
  "用满范围"这个好听的说法破坏更根本的约束。
- **统计的排除理由，往往同样适用于变换。** D73 只说了 padding/画框/投影/描边/时钟不进动态
  统计；但同一条理由——它们是 SDR 图形元素——意味着它们也不该被色调映射压一遍。恰好场景
  纹理就是卡片内容本身，两件事因此共用同一个取样源。
- **运行时降级与候选降级是两回事。** D77/D78 的两条降级里编码档位一切正常，坏的是渲染侧的
  内部质量工具，所以要在**同一个 tier** 上重来，不能消耗降级阶梯。判据都能在首帧之前得出，
  "从第 1 帧重来"因此不浪费渲染。
- **不要把经过有损编码后不可判定的量设成交付门禁。** 8-bit 抖动的频谱在编码器自身的量化面前
  测不出蓝噪声与白噪声的区分度；正确做法是在 JVM 侧钉住阈值表、无偏性、端点与着色器逐行
  对照，而不是对着一段压缩视频反复调参数看能不能"看出来"。
- **真机驱动的两个坑**：音频播放 Dialog 要点**卡片本体**，点播放按钮只会开始播放；
  `uiautomator dump` 只输出屏幕上真的可见的节点，所以在长对话框里找控件必须"滚动 + 重复
  dump"，一次性 dump 找不到不等于控件不存在。

## 2026-07-29 - 批次 4：PQ 母版意图、全片静态统计与 HDR10

静态元数据从"按参数算"改成"按产物测"：编码器 configure 之前多跑一遍全片确定性渲染，读最终
可见合成的线性 BT.2020 画面得到实测 MaxCLL/MaxFALL。452 例单测 0 失败，OPPO 平板实测通过。

- **两条循环就是两份真相。** 预分析要重跑一遍音频驱动、模拟与渲染。各写一份循环，迟早有一
  份被改动而另一份没有，统计描述的就不再是产物那段画面。抽成一个共享的逐帧驱动，编码路径
  只多一个音频回调——这比事后写"两处要保持同步"的注释可靠得多。
- **同一条流水线的另一个出口，好过另一条流水线。** 分析读的是 `export_present.frag` 的
  `uTransfer == 3` 分支，只少套一层 OETF。统计因此不可能与编码输入来自两张不同的画面。
- **"看起来合理的数"比"未知"更危险。** 旧实现把漫反射白（203）写成 MaxFALL，实测下来两台
  设备分别是 164 与 140——旧值一直在高报。规范给了"未提供"这个取值（0），统计不可用时就该
  用它，而不是填一个不会被质疑的数字。
- **同一版 Android 的不同设备，容器写入行为可以不同。** 最低母版亮度这个字段，PLZ110 上被
  MP4 写入器多乘了 10000，OPD2515 上没有。逐字节核对会让前者全军覆没。凡是"我们注入、平台
  转写、再读回来"的链路，核对都要按字段来并容忍已知换算，不能按缓冲区整体比较。
- **核对要读被验证方自己那一份数据。** 探测侧另算一遍描述符，只要漏传一个参数就会稳定地判
  所有设备失败，而那种错误看起来完全像是设备问题。改为直接问编码器要它写下去的那一份。
- **真机脚本不要按本地化文案定位控件。** 平板系统语言是英文，中文 `content-desc` 直接找不到。
  有 `resource-id` 就按 id，没有的（胶囊）才按文案，终态匹配同时接受中英文。

## 2026-07-29 - 批次 5：HDR10+ 精确统计与 Profile B 曲线

统计从 32×32 块平均换成逐像素线性 BT.2020 完整 CFD，曲线从固定二次缓动换成内容密度驱动。
458 例单测 0 失败，OPPO 手机实测载荷逐字段正确。

- **精度损失要算在哪一步。** 从 PQ 反解回线性，FP16 的一个 ulp 在 1000 尼特附近就是 4 尼特，
  而载荷网格是 0.1 尼特。统计源改走 MRT（同一趟呈现多写一个线性附件），比"再画一遍"更安全：
  两遍之间任何一个 uniform 不同，统计描述的就不是编码进去的那张画面，而这种不一致在产物里
  看不出来。
- **`1.0 / 0.00001` 不等于 100000。** 双精度下是 99999.99999999999。凡是"值 ÷ 步长 → 下标"
  的写法都要改成乘以步长的倒数，否则最高那一档永远空着，且没有任何症状。
- **别把充分条件当必要条件。** 门禁要的是绝对斜率 ≤ 1；我先按"差分非增"投影，那是充分但
  过强的条件，直接把解压成唯一形状，内容密度白算了。正确的约束是"每个差分 ≤ 第一个差分"
  ——因为贝塞尔的导数就是差分序列的贝塞尔。
- **没有门禁的时候，回退形状可能一直是错的。** 旧的二次缓入在弱压缩下第二个差分比第一个还
  大，肩部一出膝点就加速到绝对斜率 1.07。加了门禁才发现它从来没满足过约束。
- **时间平滑的采样网格必须钉在绝对量上。** 网格跟着源峰值缩放时，同一个下标在相邻帧代表不同
  的绝对亮度，平滑出来的东西没有物理含义——实测表现是"平滑前后逐位相同"，等于没做。
- **高阶最小二乘必须正则，而且正则强度要与法方程量级相称。** 十阶伯恩斯坦基、8 个自由参数、
  30 个样本，无正则会振荡。加了 1e-3 看起来"加过了"，其实矩阵元约 0.3，等于没加。
- **实现正确不等于功能生效。** D113 用 V8（99.98% 分位）做横轴，而 FableSol 的高光是稀疏
  点缀：MaxCLL 1948 尼特，V8 只有 214 尼特，低于参考显示峰值的下限。于是每一帧都落在 Case 3
  中性曲线上，整套曲线机制对本素材不产生画面影响。这是 D113 明确接受的取舍，不是 bug，
  但必须让用户知道并决定要不要改回 MaxSCL 优先。

## 2026-07-29 - 批次 6：HLG 与杜比视界 8.4

接手时上一轮已写好三个纯数学文件与着色器 HLG 分支，但工程不可编译，且 `hlgPlan` 恒为 `null`
——肩部表为空，高光实际落在着色器末端的逐通道 `clamp` 上，正是 D131 禁止的写法。本轮补完
回环验证、通路接入、设置项、完成态与诊断，492 例单测 0 失败，OPPO PLZ110 三次实测通过。

- **半成品比没做更危险。** 三个文件写得很好、数学也对，唯独没有调用方——从代码上看像是"做完
  了"，运行起来却是硬钳。判断一批工作是否完成，要看**正式通路上有没有真的走到它**，不是看
  文件在不在。
- **请求与产物必须是两套词汇。** `自动增强` 是意图，它的结论只能是"这次真的用上了"或"这次
  停在名义 100%"。把意图当结论写进完成 Dialog，就会把一次未通过的验证说成扩展信号范围。
- **判定门禁的容差必须小于测量步长。** 容差 10、步长 8 时，编码器把某一级钳住，下一级只差 8，
  误差仍落在容差内——安全上限凭空高出一级，而写出去的码值随后被编码器钳掉。这个缺陷是 JVM
  测试逼出来的，肉眼和真机都看不出来。
- **判"有没有塌缩"要比判"误差多大"更有力。** 钳制的误差可以很小（945→940 只差 5），真正的
  判据是整段阶梯有没有全部落到同一个端点上。
- **逐像素 diff 测不出画质改动。** 一旦输入有任何差别，硬件编码器的量化决策就整体发散，
  逐像素差随即被 ±100 量级的对称噪声淹没（本轮实测：更亮 1.535 亿样本、更暗 1.527 亿，
  均值 0.01）。要看系统性改动，必须用对编码噪声稳健的统计量（高分位、阈值以上像素数）。
- **"前 N 帧逐位相同、第 N+1 帧起发散"本身就是证据。** 本轮两条路径在第 124 帧分岔，而那一帧
  正是内容首次越过 `2.0×` 膝点的位置——比任何差值统计都更能说明肩部真的接上了。
- **实现正确仍可能对本素材没效果（第二次遇到）。** 星芒是白的，中性方向按 D134 本就不使用
  super-white；能吃到扩展色容积的是水体的高饱和高光，占比很小，99.99% 分位只高约 1.4 个码值。
  与批次 5 的 Case 3 是同一类结论：要如实说明，不要把"通路跑通了"说成"画质提升了多少"。
- **同一台设备的不同编码通路结论可以相反。** PLZ110 上 HEVC 通路保留了完整的视频数据范围
  （`1019,4,1019,4,1019`），杜比视界通路的阶梯却整段塌缩。D140 不把 super-white 当设备级
  布尔量是对的，缓存签名也必须带上编码器与输入通路。

## 2026-07-29 - 批次 7：离线编码画质策略

只改申请给编码器的那份 `MediaFormat`——码控形态、目标码率、Level/Tier、B 帧、复杂度、
QP 上限。508 例单测 0 失败，OPPO PLZ110 两次实测。

- **"取最高档"是把 Level 当画质档在用。** Level 描述的是**解码**这段码流所需的尺寸、吞吐、
  码率与图像缓存上限；申请更高的档不会让同一 Profile 更清晰，只会让本来放得动它、却只支持
  较低 Level 的设备直接拒收。这类"看起来更保险"的写法要格外警惕：它错在方向上，而不是数值上。
- **解析顺序会倒逼数据模型。** 自动码率要对齐后的宽高与族，Level 又要解析后的码率——两者都
  只在候选生成的那个循环里齐备，因此码率只能成为候选自己的字段，而不是"用的时候再算"。
  凡是"探测算一遍、导出再算一遍"的量，迟早会算出两个数。
- **状态可以编码进"键在不在"。** 码率滑杆的自动/自定义不需要任何新控件：自动就是没保存过
  这个键，于是现有的"恢复默认"（删键）天然把它送回自动值。这也是决策明令不要新增按钮的做法。
- **关闭一个能力 ≠ 请求它的最小值。** 关掉高复杂度要**省略** `KEY_COMPLEXITY`，保留厂商
  默认；下发 `complexityRange.lower` 是另一件事，会把厂商的默认调优也一起关掉。
- **源码契约测试不能按字面搜关键字。** 两条 `assertFalse(contains(...))` 都被自己的解释性
  注释判死了——注释恰恰是在讲为什么不用那个 API。判据要落在**实际的调用形态**上，并把允许
  的用法逐个点名，这样既挡得住回归，也不会逼人删掉记录教训的注释。
- **申请成功不等于生效。** `KEY_MAX_B_FRAMES = 1` 是上限而非强制值：本机接受了这个键，码流
  里却一帧 B 都没有。完成文案因此必须写"已申请"而不是"含有"——这条在决策里写着，实测正好
  撞上，说明那句限定不是多余的。
- **同一台设备验不了所有分支。** PLZ110 的 HEVC 编码器没有公开可用的 CQ 质量区间，也不声明
  `FEATURE_QpBounds`，于是 D146、D167 与 D151 三条在这台机器上根本跑不到。要如实说是"未在
  硬件上验证"，不能因为"导出成功了"就当作全部验过。

## 2026-07-29 - 批次 8：集成验证与交付

不改业务逻辑，只做验证——但验证本身找出三处真问题（两条已作废文案、一条潜伏的裸 `%`、
两处被自己注释判死的源码契约断言）。521 例单测 0 失败。

- **"把规则写成测试"能立刻还本。** 13 套语言的覆盖检查一跑就翻出两条 D141 早该删掉的杜比
  视界 Profile 5/8.1 文案，和三条中文里没标 `formatted="false"` 的裸 `%`。后者尤其阴——
  aapt2 要两个以上才报错，一个能过，于是它一直潜伏到某天这条字符串被送进 `String.format`。
- **源码契约测试第三次栽在同一个地方。** `assertFalse(contains("某个 API 名"))` 会被**解释
  这个 API 为什么不用**的注释判死，而那条注释恰恰是最该留下的东西。判据必须落在实际的调用
  形态上（`setInteger(MediaFormat.KEY_X`、`isFeatureSupported(...FEATURE_Y`），并把允许的
  用法逐个点名——既挡得住回归，也不逼人删注释。
- **"字节不一致"不等于"不确定"。** 同设置连导两次的产物字节不同，但全片预分析的统计值逐位
  复现（对 856 帧每个像素的归约）。再加上"一对前 166 帧逐位相同、另一对从第 1 帧就不同"，
  可以判定发散源在硬件编码器的码控。验收门禁的措辞（"确定性像素控制量"）本来就该这么读。
- **代价要量出来再说。** 画质通路让导出时长增加两到五倍：8-bit Surface 12.1 s，同素材
  HDR10+ 首次 68.2 s；拆开是预分析 21 ms/帧、HDR10+ 统计 20 ms/帧、P010 相对 Surface
  27 ms/帧，P010 峰值内存高约 95 MB。这些数早该在批次 2 就测（plan-review 第五节提过），
  拖到批次 8 才做，好在结论与预估一致。

## 2026-07-29 - HDR10+ 亮度往复变化回归诊断（样片 01_HDR10Plus）

用户报告本轮改动后 HDR10+ 产物亮度频繁变化甚至突变。逐帧解析 853 帧 ST 2094-40 元数据、

帧间 ≤0.15），亮度变化全部来自逐帧动态元数据。只做诊断，未改实现，未使用 adb。

- **根因：Case 3 中性曲线在恒定横轴的接收端上是逐帧全局增益。** 参考显示峰值设为 2000
  尼特 ≥ 全片 V8 峰值 1928 尼特，853 帧全部走 D111 的 `Kx=1、Ky=V8/T`。V8（99.98% 分位）
  随星芒在 201～1928 尼特之间变化，量化后 `ky_raw` 与码流 `dist[99]/2000×4095` 逐帧精确
  相等（corr=1.000），Ky 在 0.100～0.964 之间移动。曲线恒等的前提是接收端按**本帧 V8**
  归一化横轴（D113 的选择）；用户的播放链路显然按恒定基准（母版峰值一类，即 D38 旧语义）
  归一化，于是 Ky 成为整幅画面的乘数：背景约 150 尼特被在约 15～148 尼特之间来回改写，
  0.5 秒内增益可从 0.11 升到 0.59，单帧最大步进 0.043。
- **中性路径完全绕过时间平滑。** `next()` 在 Case 3 分支逐帧 `resetSmoothingTo(null)`，
  0.08/0.80s 的快压慢放从未生效，V8 的每一次不连续（96 对相邻帧跳变 >30 尼特，最大 86
  尼特/帧）原样进入 Ky。
- **旧版稳定的原因。** HEAD 的横轴按母版峰值（逐帧不变），膝点经指数平滑，`Ky/Kx = M/T`
  使膝点以下恒为绝对亮度恒等——在恒定横轴接收端上不存在随帧变化的全局项。压缩路径同样
  受影响：新实现 `fit()` 的 `kneeX = knee/source` 以 V8 为分母，在恒定横轴接收端上膝下
  斜率变成 `S/M`，与中性路径是同一个缺陷，只是本样片没有触发（全片中性）。
- **为何漏网。** 钉住旧膝点语义的 `FableSolExportHdr10PlusCurveTest` 等三个测试本轮删除，
  合并后的 `FableSolExportHdr10PlusTest` 断言的正是 `Kx=1` 的中性形状；批次 5 曾把"全片
  中性"评估为"对画面无影响"，该结论只在 V8 归一化的接收端上成立。单测无法覆盖"接收端如何
  解释载荷"，这一步只能靠目标设备实播验证。
- **待用户裁定的修复方向。** 候选：把曲线横轴退回母版峰值恒定语义（同时修复中性与压缩两条
  路径，且是唯一经用户设备长期实证的解释）；或中性帧恢复 `tone_mapping_flag=0`（只治标）；
  无论哪种，任何可能被接收端解释为全局增益的逐帧量都必须经过时间平滑。次级风险：`S>T`
  素材在中性⇄压缩边界逐次清空平滑状态，边界帧曲线不连续。`fraction_bright_pixels` 在

## 2026-07-29 - HDR10+ 亮度往复变化回归修复（D176）

按上一条诊断的结论实施：曲线横轴从逐帧 V8 退回声明母版峰值恒定，并补上三处被绕过的时间
平滑。524 例单测 0 失败，未使用 adb。

- **发送端换归一化基准，接收端不会知道。** 载荷里的 `Kx`、`Ky` 描述一个函数，而自变量的
  基准由接收端决定。D113 选 V8 优先时同时设了"接收端也按本帧 V8 归一化"这个前提，而那不是
  用户播放链路的行为——于是 `Ky` 成了整幅画面的逐帧乘数。凡是接收端可能解释为全局增益的量，
  都不允许跟着逐帧统计走。
- **"配置级"与"逐帧"是两类判定，混起来用户就无从预期。** `M > 10T` 无解只取决于母版峰值与
  参考显示峰值两个全片常量，过去按逐帧 V8 判，同一套设置会时而成功时而失败，导出前也提示
  不出确定结论。改成配置级之后，构造曲线的那一刻就判掉，设置页的提示也从"部分高亮帧可能"
  变成确定结论加最低可行参考峰值。
- **"必须经过平滑"要按数据流查，不是按名字查。** 除了膝点，还有两个此前没被当成"逐帧量"的
  东西在改载荷：拟合样本取到哪里（帧峰值一跳，肩部从"几乎没有样本"变成"整段被拟合"，单个
  anchor 一帧跳 197/1023），以及"样本少于 10 个就整体退回解析形状"这道阈值开关（跨过阈值
  那一帧跳 184/1023）。前者补上同一套快压慢放，后者直接删掉——正则本就让法方程恒为正定，
  零样本时解精确等于解析形状，中间没有台阶。**凡是能改变输出的分支条件，本身就是一个需要
  连续化的量。**
- **用比较写的门禁遇上 NaN 会全部放行。** `M` 恰好等于 `10T` 时膝点退化为 0，`P1` 的解析式
  变成 `0/0`。NaN 通不过任何比较，于是量化后门禁的每一条判定（单调、斜率、连续）都"通过"，
  量化再把 NaN 变成 0——写出去的是一条把全部亮度映射到零的曲线，画面全黑。可行性判据因此
  收紧到"膝点必须落在 12 位 KneePoint 的第一个非零档上"，`fit()` 另加一道 `isFinite` 拦截。
- **把接收端建模进单测。** 上一条诊断说"单测无法覆盖接收端如何解释载荷"，那只对"照搬现有
  写法"成立：按 `out(L) = F(L/M)·T` 写十行求值，就能让"背景亮度在 V8 跳变下是否恒定"变成
  一条断言。这条测试直接钉住失效模式，比任何形状约束都有力。
- **验收门槛要区分"响应内容"与"往复变化"。** 首批帧里没有高光，肩部跟着内容收紧是动态元
  数据的用途，整段最大最小之比因此必然偏大。判据落在**平滑收敛之后的摆幅**上（实测 1.008），
  以及单帧相对变化的上界（由 τ = 0.08s 与帧率推出）。
