# fablesol-video-export 遗留项

## 验收

- **D15 ① 逐位门禁未建立，且判据本身要改写**（2026-07-26 第四轮修正）。

  原判据"实时与离线逐帧 max|Δ| = 0"**不可能达成**，因为两条路径的初始状态本就不同：

  - 实时分析器从**准备态**就开始吃麦克风数据（`AudioRecorder.RecordingThread` 无条件喂
    分析器，只有 WAV 写入受 `mIsRecording` 门控），开始录音时不重置——这是 README 明写的
    录音预览设计；
  - 水体模拟同样不在开始录音时重置，屏上那一帧带着准备态的历史；
  - 离线导出只有 WAV 里的样本，从零状态起步。

  这三条都是**有意为之**，不该为了对齐判据去改。正确的判据应改成两条：

  1. **离线自比对**（可进 CI）：同一个 WAV 连跑两次，逐帧状态向量 max|Δ| = 0——这测的是
     离线路径本身的确定性，也是真正能自动化的那一条。
  2. **受控初值的双路对照**：给实时侧喂等间隔 1/120 的合成时间戳**并且**把分析器与模拟
     显式复位到零状态，此时才应逐位相同。做不到复位就只能退回事件层（D15 ②）。

  预热门这一项已在代码侧解决：离线路径调 `FableSolRealtimeAnalyzer.skipStartupGate()`，
  因为那道门拦的是麦克风冷启动暂态，读文件没有这回事，而实时侧它早在准备态就放行了。
- **D15 ② 事件层比对未做**：真机录一段、离线导同一份 WAV，比对 onset / 七境转移 / 巨浪触发 /
  段落切换的序列与时刻（容差一个 hop ≈ 10.7ms）。
- **D15 ③ 观感层未做**：构图、配色、时钟位置、圆角、投影、padding 只能人眼验收。
- **播放对话框的字形着墨对齐缺少 Android View 级自动回归**：当前用 33 套真实 JSON 资产的
  纯几何检查覆盖字体/实心/描边组合，并由 JVM 单测与 APK 编译兜底；项目尚未接入 Robolectric
  或截图测试，最终像素对齐仍需真机确认。
- **handle 光学校正、选项胶囊渐变与导出完成 Dialog 缺少 Android Canvas/View 级截图回归**：
  当前以 AOSP `AbsSeekBar` 坐标公式、完整 `ThingBackground` 调用链、布局结构静态检查、
  JVM 单测与 APK 编译兜底；项目没有 Robolectric/截图测试环境，handle 向左越过数字 2dp
  的观感、胶囊换色及完成信息换行与双按钮着色的最终像素结果仍需真机确认。
- **完成通知与新版导出图标缺少系统 UI 级视觉回归**：当前已用共享 `Done` 状态和资源文案
  保证数据同源；图标已改成补全左、上画框的 Material `video_frame_save`。通知在不同厂商
  系统的折叠/展开行数、长路径换行，以及 24dp 图标的边框连续性仍需真机确认。
- **64px 画布与本轮播放界面仍需真机分享/视觉验收**：JVM 已证明 280/310/383dp 三档宽高
  都被扩展为 64px 倍数、左右背景等宽，输出 crop keys 也会被完整画幅校验；但微信聊天与
  朋友圈的真实二次转码是否还会额外裁切，只能用新产物实发确认。按钮文字在 ripple 内的
  光学中心、Material 导出图标的记事渐变着色及 32dp 主播放/暂停图标也需在常用尺寸下复核。

- **HDR 开关与结束态重播仍需目标真机验收**：源码契约覆盖 HDR 120→60 优先于 SDR 的
  尝试顺序、能力缓存与延后后台探测、失败时取消偏好并置灰，以及自然结束后 seek 必须重建
  解码线程；但一帧 `MediaCodec`/10-bit HLG EGL 探测在用户的三星设备上是否正确置灰或
  放行、首次未缓存时设置 Dialog 是否完全无卡顿、放行后实际产物是否标为 HDR，以及
  “播完→拖到中段→点击播放”的声音与进度同步，仍须在该设备实测。

- **华为平板（Kirin / `OMX.hisi.video.encoder.hevc`）的 HDR 是否真的通了未验证**（2026-07-27）。
  已按 D30 把 `eglChooseConfig` 改成四级阶梯，假设失败原因是驱动不给 10-bit config 打
  `EGL_RECORDABLE_ANDROID` 标记。若阶梯全部落空，诊断行「10-bit 表面」会显示"无"——那说明
  这台机器根本没有 10-bit 窗口 config，届时唯一的选项是 8-bit 表面 + 抖动送 Main10 编码器，
  需要先想清楚是否值得（PQ 在 8-bit 下色带很重）。

- ~~**给 HDR10+ 补上色调映射曲线**~~——已由 D38 完成。剩下的是**观感验收**：与无曲线那版对比
  是否出现"高光一来背景让开"，以及背景亮度有没有一跳一跳地呼吸（平滑时间常数不够的征兆）。

- ~~**HDR10+ 字节缓冲通路的产物颜色未经验证**~~——2026-07-27 已用三个白锚样本与 DV 8.4
  HLG 基础层做解码像素对照。反解有限范围 BT.2020 NCL 与 PQ/HLG、按白锚归一化后，红色区域

  UV 顺序未见系统性错误。仍需真人观看确认设备端表现，但 P010 已不再是本轮最高风险。

- **HDR10+ 动态元数据需要同码流 A/B 播放隔离**（2026-07-27）。当前样本证明 800 尼特文件的
  ST 2094-40 SEI 存在，但“HDR 已识别”不能证明厂商按预期采用动态曲线。须保留完全相同的
  HEVC 像素码流，仅移除 ST 2094-40 SEI，在同一设备、同一播放器与亮度下切换，区分高 APL/
  面板色容积限制和厂商 HDR10+ 算法。

- ~~**漫反射白推荐值没有纳入面板平均亮度能力**~~——已由 D45 完成。自动档现取
  `min(面板峰值×1.75÷HDR 强度, 最大帧平均亮度, 400)`，再按 25 尼特向下对齐；默认
  9.6 强度时等价于约 `面板峰值÷5.49`。设置页同步显示结果、母版峰值与公式，手动档不被
  自动策略覆盖。800 尼特继续保留为用户明确选择的高亮创作档。

- **杜比视界 8.4 产物的识别情况未验收**：OPPO 已实测能编出来，但播放端会不会认成杜比视界、

- **四种 HDR 格式的完整播放验收未做**（2026-07-27）。现有样本已确认 HDR10+ 逐帧

  正确解码；仍未确认不同相册/播放器是否实际采用动态元数据、DV 8.4 是否显示为 DV 而非仅

- **三星 S23 Ultra 的 HDR 导出端到端验收未做**（2026-07-27）。D28 修好的是探测被自己的

## HDR 多格式代码审查待修复（2026-07-27）

> **2026-07-27 更新**：下列条目中除"ST 2094-40 分位点统计口径"外，**全部已由 D42 修复**。
> 分位点那条保留，但结论需要修正——见本节末尾。

- **HDR10+ 目标显示峰值的位流单位错误**：
  `targeted_system_display_maximum_luminance` 的单位是 0.0001 尼特，当前却按 1 尼特写入；
  例如 1000 尼特会被播放端解读为 0.1 尼特。须改成乘 10000，并补一个逐字段解码单测，
  不能继续只校验固定头和总长度。
- **正式 HDR10+ 导出没有把 SEI 当作发布门禁**：探测会检查
  `hdr10PlusSeiSeen`，正式导出在 `finish()` 后却直接提交文件。须在发布前验证码流确实带有
  ST 2094-40 元数据，否则该候选失败并继续降级，不能发布一个仅在名称上是 HDR10+ 的文件。
- **P010 字节缓冲与容器色彩范围可能不一致**：着色器固定生成有限范围 P010，但输出格式校验
  沿用了 surface 通路“编码器上报值优先”的规则。若厂商编码器回报 full，样本与信令就会
  冲突；字节缓冲通路应按协商结果生成相同范围，或拒绝改变为 full 的候选。
- **HDR10+ 被无关的 EGL 能力提前否决**：该通路在离屏 framebuffer 内自行做 PQ 与 P010，
  1×1 pbuffer 不使用 PQ/HLG 色彩空间，却仍被 `anyHdrColorSpace`、传递函数列表及 10-bit
  pbuffer config 门控。应只保留 FP16 场景、RGB10_A2 framebuffer、P010 编码与 SEI 的真实
  通路门禁，避免设备实际可编码却不显示 HDR10+。
- **ST 2094-40 统计口径不正确**：当前先把整帧归约为 32×32 个块平均，再对 1024 个块平均值
  取分位点；`average_maxrgb` 还使用“PQ 域先平均、再反解到尼特”，且
  `fraction_bright_pixels` 恒写 0。标准字段要求处理窗口内逐像素 linearized maxRGB 的均值与
  分位点。800 尼特样本中动态元数据的平均 maxRGB 比解码像素线性域实测低约 8%～12%。
  须改为逐像素直方图或等价归约，同时填写真实亮像素比例，避免银丝、星芒等小面积高光被
  块平均抹掉并减少不同播放器的映射差异。
- **P010 的 `slice-height=0` 未处理**：Android 明确允许厂商回报 0；正式编码与独立探测会
  直接把 0 当平面高度，导致 UV 起始偏移和入队长度为 0。至少应把 0 识别为未知并采用经过
  验证的回退布局，无法确认时淘汰该候选。
- **能力探测的诊断状态可能串用旧结果**：新一轮探测开始时没有清空
  `lastSupportedFormats` / `lastCandidateFailures` / `lastFailureReason`；早退或异常后，
  `supportedFormats()` 可能返回上一次的格式列表。须在探测事务开始时原子重置或改为局部结果。
- **设置 Dialog 的 800ms 延后探测约束回退**：当前在创建 HDR 格式块时立即启动编码探测线程，
  与 D24 的“首帧后后台低优先级执行”不一致，首次无缓存打开时可能重新引入卡顿。应恢复延后，
  并在 Dialog 销毁后支持取消尚未开始的探测。
- **HDR10 静态 MaxFALL 仍固定为 203 尼特**：漫反射白已允许 200–800 尼特，固定值不再能
  保证描述真实画面。应由实际帧统计得到 MaxFALL，或采用与当前白锚、画面覆盖率同源的保守值。

### 唯一保留项：分位点口径，且结论要修正（D42）

评审指出"块平均取分位点会抹掉小面积高光"**属实**，但这个数目前承担了**两个用途**，不能一并
处理：

- **我们自己用它定膝点**——这里恰恰**不希望**几个像素的星芒把膝点顶上去，块平均在这个用途上
  是合适的，甚至比逐像素更稳（逐像素会让膝点随星芒抖动，正是"呼吸"的来源）；
- **写进元数据交给播放端**——这里确实失真：p99 与 maxscl 之间会出现一个不合理的大缺口。

所以正确的修法不是简单换成逐像素，而是**把两个用途拆开**：写进码流的分位点走逐像素直方图，
定膝点仍用块级统计（或对逐像素结果另做时间/空间平滑）。逐像素直方图在 GLES 3.0 下可用
"逐像素点图元 + 累加混合写进 1×N 纹理"实现，属于一趟独立渲染，是一件单独的工作。

## 清理

- **屏幕峰值 API 的源码注释不准确**（2026-07-27）：`FableSolExportDisplayLuminance` 称
  `getDesiredMaxLuminance()` 在 API 34 过时；Android 当前文档只把
  `getSupportedHdrTypes()` 标为 API 34 过时，峰值与最大平均亮度接口仍有效。应删除误导说明及
  不需要的 `DEPRECATION` 抑制，并保留“厂商值仍须合理性校验”的实际约束。
- **三条死字符串未清**（2026-07-27）：`fablesol_export_started`（内容仍是已废弃的"水体视频"
  说法）、`fablesol_export_estimate`（被 `estimate_bitrate` / `estimate_quality` 取代）、
  `fablesol_param_export_hdr`（HDR 开关已并入格式选择后失效）。均无引用，不影响用户，
  但对后续阅读与翻译是误导，清理时需同步 13 套语言。

## 标定

- **码率与 CQ 质量档默认值是推测值**（120fps 24 Mbps / 60fps 14.4 Mbps，质量 80%）。
  要用最容易暴露色带的场景实测校准：大面积缓变的深色渐变记事 + 静水。
- **投影与描边参数未经真机确认**：offset 6dp / radius 24dp / alpha 0.28（深）0.40（浅），
  描边 1dp / alpha 0.10（深）0.06（浅）。

## 已知取舍待复核

- ~~**HLG 的超白余量只有约 3.77 倍**~~——已由 D27 处理：PQ 成为默认 HDR 通路（绝对亮度、
  10000 nits 上限，9.6 倍 SDR 白约 1949 nits 完全放得下，无需压缩），HDR10 静态元数据

  开头"）。若掺了挂钟，离线导出的头几秒会与实时不一致，须改成采样驱动。
