## 验收

- **D15 ① 逐位门禁未建立，且判据本身要改写**（2026-07-26 第四轮修正）。

  原判据"实时与离线逐帧 max|Δ| = 0"**不可能达成**，因为两条路径的初始状态本就不同：

  - 实时分析器从**准备态**就开始吃麦克风数据（`AudioRecorder.RecordingThread` 无条件喂
    分析器，只有 WAV 写入受 `mIsRecording` 门控），开始录音时不重置——这是 README 明写的
    录音预览设计；
  - 水体模拟同样不在开始录音时重置，屏上那一帧带着准备态的历史；
  - 离线导出只有 WAV 里的样本，从零状态起步。

  这三条都是**有意为之**，不该为了对齐判据去改。正确的判据应改成两条：

  1. **离线自比对**（可进 CI）：同一个 WAV 连跑两次，逐帧状态向量 max|Δ| = 0——这测的是
     离线路径本身的确定性，也是真正能自动化的那一条。
  2. **受控初值的双路对照**：给实时侧喂等间隔 1/120 的合成时间戳**并且**把分析器与模拟
     显式复位到零状态，此时才应逐位相同。做不到复位就只能退回事件层（D15 ②）。

  预热门这一项已在代码侧解决：离线路径调 `FableSolRealtimeAnalyzer.skipStartupGate()`，
  因为那道门拦的是麦克风冷启动暂态，读文件没有这回事，而实时侧它早在准备态就放行了。
- **D15 ② 事件层比对未做**：真机录一段、离线导同一份 WAV，比对 onset / 七境转移 / 巨浪触发 /
  段落切换的序列与时刻（容差一个 hop ≈ 10.7ms）。
- **D15 ③ 观感层未做**：构图、配色、时钟位置、圆角、投影、padding 只能人眼验收。
- **播放对话框的字形着墨对齐缺少 Android View 级自动回归**：当前用 33 套真实 JSON 资产的
  纯几何检查覆盖字体/实心/描边组合，并由 JVM 单测与 APK 编译兜底；项目尚未接入 Robolectric

## HDR 多格式代码审查待修复（2026-07-27）

> **2026-07-27 更新**：下列条目中除"ST 2094-40 分位点统计口径"外，**全部已由 D42 修复**。
> 分位点那条保留，但结论需要修正——见本节末尾。

- **HDR10+ 目标显示峰值的位流单位错误**：
  `targeted_system_display_maximum_luminance` 的单位是 0.0001 尼特，当前却按 1 尼特写入；
  例如 1000 尼特会被播放端解读为 0.1 尼特。须改成乘 10000，并补一个逐字段解码单测，
  不能继续只校验固定头和总长度。
- **正式 HDR10+ 导出没有把 SEI 当作发布门禁**：探测会检查
  `hdr10PlusSeiSeen`，正式导出在 `finish()` 后却直接提交文件。须在发布前验证码流确实带有
  ST 2094-40 元数据，否则该候选失败并继续降级，不能发布一个仅在名称上是 HDR10+ 的文件。
- **P010 字节缓冲与容器色彩范围可能不一致**：着色器固定生成有限范围 P010，但输出格式校验
  沿用了 surface 通路“编码器上报值优先”的规则。若厂商编码器回报 full，样本与信令就会
  冲突；字节缓冲通路应按协商结果生成相同范围，或拒绝改变为 full 的候选。
- **HDR10+ 被无关的 EGL 能力提前否决**：该通路在离屏 framebuffer 内自行做 PQ 与 P010，
  1×1 pbuffer 不使用 PQ/HLG 色彩空间，却仍被 `anyHdrColorSpace`、传递函数列表及 10-bit
  pbuffer config 门控。应只保留 FP16 场景、RGB10_A2 framebuffer、P010 编码与 SEI 的真实
  通路门禁，避免设备实际可编码却不显示 HDR10+。
- **ST 2094-40 统计口径不正确**：当前先把整帧归约为 32×32 个块平均，再对 1024 个块平均值
  取分位点；`average_maxrgb` 还使用“PQ 域先平均、再反解到尼特”，且
  `fraction_bright_pixels` 恒写 0。标准字段要求处理窗口内逐像素 linearized maxRGB 的均值与
  分位点。800 尼特样本中动态元数据的平均 maxRGB 比解码像素线性域实测低约 8%～12%。
  须改为逐像素直方图或等价归约，同时填写真实亮像素比例，避免银丝、星芒等小面积高光被
  块平均抹掉并减少不同播放器的映射差异。
- **P010 的 `slice-height=0` 未处理**：Android 明确允许厂商回报 0；正式编码与独立探测会
  直接把 0 当平面高度，导致 UV 起始偏移和入队长度为 0。至少应把 0 识别为未知并采用经过
  验证的回退布局，无法确认时淘汰该候选。
- **能力探测的诊断状态可能串用旧结果**：新一轮探测开始时没有清空
  `lastSupportedFormats` / `lastCandidateFailures` / `lastFailureReason`；早退或异常后，
  `supportedFormats()` 可能返回上一次的格式列表。须在探测事务开始时原子重置或改为局部结果。
- **设置 Dialog 的 800ms 延后探测约束回退**：当前在创建 HDR 格式块时立即启动编码探测线程，
  与 D24 的“首帧后后台低优先级执行”不一致，首次无缓存打开时可能重新引入卡顿。应恢复延后，
  并在 Dialog 销毁后支持取消尚未开始的探测。
- **HDR10 静态 MaxFALL 仍固定为 203 尼特**：漫反射白已允许 200–800 尼特，固定值不再能
  保证描述真实画面。应由实际帧统计得到 MaxFALL，或采用与当前白锚、画面覆盖率同源的保守值。

### 唯一保留项：分位点口径，且结论要修正（D42）

评审指出"块平均取分位点会抹掉小面积高光"**属实**，但这个数目前承担了**两个用途**，不能一并
处理：

- **我们自己用它定膝点**——这里恰恰**不希望**几个像素的星芒把膝点顶上去，块平均在这个用途上
  是合适的，甚至比逐像素更稳（逐像素会让膝点随星芒抖动，正是"呼吸"的来源）；
- **写进元数据交给播放端**——这里确实失真：p99 与 maxscl 之间会出现一个不合理的大缺口。

所以正确的修法不是简单换成逐像素，而是**把两个用途拆开**：写进码流的分位点走逐像素直方图，
定膝点仍用块级统计（或对逐像素结果另做时间/空间平滑）。逐像素直方图在 GLES 3.0 下可用
"逐像素点图元 + 累加混合写进 1×N 纹理"实现，属于一趟独立渲染，是一件单独的工作。

  事前提示速度、耗电和发热影响，但尚无可靠的完成时间估算。需要在不同设备上测量真实吞吐量，
  再决定能否提供基于片长、分辨率、帧率和编码器实现的动态剩余时间。
- **10-bit 4:2:2／APV 专业导出另行设计。** Android API 36 新增 P210 10-bit 4:2:2
  ByteBuffer 格式，并公开 APV 422-10、HDR10 与 HDR10+ Profile；现有 Android HEVC Main10
  与 AV1 Main10 Profile 仍明确是 4:2:0，不能仅把 P010 换成 P210 就声称得到同一种格式的
  4:2:2 版本。APV 会新增编码器族、容器／播放兼容性、码率与显式格式选择，不作为本轮普通
  HEVC／AV1／AVC 交付路径的自动候选，后续与 HDR Vivid、Eclipsa Video 等高级格式一并评估。
  依据：
  <https://developer.android.com/reference/android/media/MediaCodecInfo.CodecCapabilities#COLOR_FormatYUVP210>、
  <https://developer.android.com/reference/android/media/MediaCodecInfo.CodecProfileLevel#APVProfile422_10>
- **API 35 ROI/QP offset map 需要独立画质实验。** 支持 `FEATURE_Roi` 的编码器允许按 16×16
  区块或矩形给下一帧设置 QP 偏移，理论上可保护时钟、卡片边缘或水面缓变；但它会引入“哪些
  区域优先”的内容取舍，若简单保护前景可能反而压低 FableSol 核心水体和大面积渐变的质量。
  本轮不把 ROI 并入“高复杂度编码”或“复杂帧质量保护”；后续应在受限 VBR 下用真实厂商编码器
  对全局零偏移、固定区域和内容自适应 map 做同码率 A/B，再决定是否存在无需用户介入的稳健策略。
  依据：
  <https://developer.android.com/reference/android/media/MediaCodecInfo.CodecCapabilities#FEATURE_Roi>、
  <https://developer.android.com/reference/android/media/MediaCodec#PARAMETER_KEY_QP_OFFSET_MAP>
- **可行组合表的探测耗时未实测。** 最坏情况下需要逐 (格式 × 编码器族) 各真实编码一帧，
  高帧率通过时才跳过低帧率那一次。结果按发布号缓存，只在每次 debug 发布后的首次打开付出
  该代价，但具体秒数需要在真机上确认。

## 2026-07-29 三轴可行性语义回归

- 三星 Z Fold4 当前可复现：选择 120 fps，色彩模式与编码器均为“自动”时，派生结论指向
  HDR10、AV1 10-bit，但 HDR10 与 AV1 胶囊均被置灰；实际导出解析为 60 fps HDR10、AV1。

  2. `autoFormat()` 只接收编码器族，不接收当前帧率，可能取到仅在 60 fps 成立的 HDR10；
