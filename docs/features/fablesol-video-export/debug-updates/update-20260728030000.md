# HDR10+ 的元数据是动态的；对我们这个动画它也比杜比视界 8.4 更合适

## 那张表里"静态"那一格是不对的

官方那个页面确实写着 HDR10+ 的元数据是"静态"。这一格要么是笔误，要么是只填了它**也带**的
那一半——HDR10+ 的定义就是在 HDR10 之上再加一层逐场景的动态元数据，没有动态就是 HDR10。

同一家的接口文档说得很清楚：那个逐帧设置元数据的参数，原话是"设置**下一个入队画面**的
HDR10+ 元数据"，格式是 ST 2094-40——ST 2094 整个系列就是动态元数据标准；另一处还写着这份
数据"**每一帧输出都可能不同**"。我们自己在设备上也验过：不逐帧给，码流里就没有那段数据。

准确的说法是**两份都有**：HDR10+ = 静态的母版信息（峰值、最大平均亮度）+ 动态的逐场景信息。
我们的实现正是这样，两份都写。

顺带把界面上一句已经过时的说明改了。之前 HDR10+ 那条写着"动态元数据只能由设备自行生成，
我们既设不了也验不了"——那是画面直送编码器时的实情，换成现在这条通路之后正好相反：那份
数据是**我们逐帧从画面量出来的**。界面上留着一句与实现相反的话，比没有这句话更糟。

## 对这个动画，HDR10+ 更好，而且不是小差距

决定性的不是元数据，是**底层的亮度曲线**。

杜比视界 8.4 的底层是 HLG，在我们这条管线里，普通白之上只剩大约 3.77 倍余量；而 HDR 强度
最高可以拉到 9.6 倍。也就是说强度调过 4 之后，多出来的部分只能被压回去，滑杆基本不起作用了。
HDR10+ 走的是 PQ，9.6 倍换算过来约 1949 尼特，是绝对亮度，放得下且一点不用压。

这对别的内容也许无关紧要，对这个动画却正中要害——**水面上那些细亮的高光和星芒，本来就长在
普通白之上很高的位置**，那正是 HLG 压掉的那一段。

第二点是元数据的可信度。HDR10+ 那份是我们自己从每一帧量出来的，里面装的是什么一清二楚；
杜比视界的那份由设备编码器生成，我们看不见也控制不了，而且它描述的是一个**顶端已经被压掉**
的画面。给一个丢了高光的信号做再好的适配，也换不回丢掉的余量。

第三点是回落表现：HDR10+ 在不支持它的播放端上按 HDR10 播，杜比视界 8.4 则按 HLG 播。两者
都能看，HDR10 的面更广一些。

杜比视界确实有它的长处——在真正支持它的显示设备上，显示端适配更成熟。但它的起点矮一截。

**一句话：这台机器上选 HDR10+。** 自动档本来就是这个顺序，不用手动改。唯一的例外是你把 HDR
强度长期放在 3 以下——那时余量差距基本用不上，两者就接近了。
