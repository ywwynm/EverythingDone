
# 代码评审的问题基本属实，已修八条

评审这份质量很高。逐条核实下来，四条严重问题全部成立，另外三条中等的也成立；只有一条我要
补充一点不同看法。

## 最严重的一条：目标亮度写小了一万倍

HDR10+ 元数据里"这条曲线针对多亮的显示设备"那个字段，**单位是万分之一尼特，不是尼特**。
我按尼特写了进去，于是播放端把 1000 尼特读成 0.1 尼特——整条色调映射曲线的目标亮度直接崩掉。

那个字段的位宽本身就是证据：上限一万尼特除以万分之一，正好需要 27 位。要是按尼特存，
十四位就够了，根本用不着 27 位。

顺带说明，同一份元数据里另外几个亮度字段（画面峰值、平均、各分位点）是**归一化到 0 到 1 的
值**，我原来的换算恰好等价，那几个没写错。两种单位混在一份数据里，是这个格式本身的坑。

已加一条**逐字段解回来核对**的测试。之前的测试只检查开头几个固定字节和总长度——位宽没错、
总长没错、固定头没错，这个一万倍的错误照样全部通过。只有把每个字段解回来比数值才拦得住。

## 其余七条

- **正式导出没有把元数据当发布门禁**：探测会检查码流里有没有那段数据，正式导出却在编完之后
  直接发布。编码器要是运行中把它丢了，我们就会发布一个文件名和完成提示都写着 HDR10+、
  实际却是普通 HDR10 的文件。现在发布前多一道检查，没写进去就让这一档失败、降到 HDR10 重来。
- **画面范围与容器标记可能打架**：字节缓冲这条路上 RGB 转 YUV 是**我们**做的，样本就是有限
  范围；而我沿用了另一条路"编码器说了算"的规则。厂商回报满范围时，标记和样本就对不上，
  表现为发灰、黑位抬高。原则其实很清楚——**谁做的转换谁是权威**：画面直送编码器时是它，
  字节缓冲时是我们。
- **平面高度回报 0 没处理**：系统明确允许厂商报 0，而 0 会让色度平面的起始位置和提交长度
  一起变成 0，画面直接废掉且不报错。现在 0 一律当作"没告诉我"，退回按画面高度计算。
- **HDR10+ 被无关的能力项拦下**：这条路在自己的离屏缓冲里完成 PQ 编码，那张 1×1 的占位表面
  压根没打色彩空间，却仍被"必须有对应窗口扩展"和"必须有 10 位占位表面"卡着。这会让**有编码
  能力、但缺窗口扩展**的设备被错误地降到 SDR。两处门禁都放开了。
- **探测不清旧状态**：新一轮探测开头没有清空上一轮的格式列表，任何早退或异常都会让旧清单
  活下来，还会被存进缓存。现在每轮开头原子重置。
- **设置页丢了延后探测的约束**：删掉旧的 HDR 开关时，把"等首帧过去再跑真实编码探测"这条一起
  弄丢了，第一次打开可能重新卡顿。已补回。
- **画面平均亮度写死 203**：漫反射白已经能调到 800，这个数就跟画面对不上了。现在跟着漫反射
  白走。

## 有一条我补充不同看法

关于分位点统计：评审说得对——现在是先把整帧归约成小块的**平均**，再对这些块平均取分位点，
小面积的银丝星芒会被抹掉，与标准要求的逐像素统计不是一回事。这一条我认。

但要分开看它影响了什么。这些分位点有两个用途：**一是我们自己拿来定膝点**，那里我们**恰恰
不希望**几个像素的星芒把膝点顶上去——块平均在这个用途上反而是合适的；**二是写进元数据交给
播放端**，那里确实失真了。所以它不是"算错了"，是"一个数被当成两个用途"。

真要修，正确做法是逐像素直方图，这在当前的图形接口下要另加一趟渲染，是一件独立的工作，
我先如实记进了遗留项，没有仓促改。
