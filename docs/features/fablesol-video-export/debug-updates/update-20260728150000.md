# 修掉闪退；漫反射白的默认值改由屏幕自己算

## 闪退

崩在录音界面的实时渲染里，跟这几轮做的导出功能无关，是一处一直存在的并发问题。

性能提示会话要拿到几个渲染工作线程的编号才能建立。取这份编号列表时用的写法是**两步**的：
先看列表里有几个、按这个数开一个数组，再逐个填进去。而那些工作线程正在启动、正在往列表里
登记自己。两步之间恰好完成一次登记，就会拿着一个长度为 0 的数组去写第一格——直接崩。

改成先对列表做一次原子快照，再从快照转数组，长度和内容必然对得上。这种并发形态加了单测，
按原来的写法跑同样的压力必然复现。

## 漫反射白改成屏幕自己算

你说得对，写死一个数不合理——现在手机屏幕的 HDR 峰值动辄一两千尼特，屏幕越亮，背景就该
坐得越高。

现在读屏幕自己声明的 HDR 峰值亮度，**取它的四分之一**作为默认漫反射白。一块 1600 尼特的屏幕
得到 400，2600 尼特的得到 650。设置里那根滑杆的初始值就是这个数；一旦你拖过它，就以你的为准，
「恢复默认」会清回自动。

为什么固定取四分之一，而不是按 HDR 强度反推：这两件事得分开。**漫反射白**决定水体和卡片
看起来够不够亮，对标的是这块屏幕能有多亮；**HDR 强度**决定高光比水体亮多少，那是你的意图，
不该被屏幕反过来改写。要是按"让高光正好落在屏幕峰值"去反推，一块 2600 尼特的屏幕反而只能得到
271 尼特——屏幕越好画面越暗，方向就反了。

四分之一的意思是：背景舒服地亮着，高光冲出屏幕上限的那部分交给色调映射曲线去压——那正是
"动态感"的来源。

还有一点：读的是屏幕的**能力**，不是它此刻的亮度设置。后者会让同一段音频在不同亮度下导出成
不同亮度的文件，产物的绝对亮度不该被导出那一刻的屏幕状态挟持。

诊断里多了一行「屏幕 HDR 峰值 · 自动漫反射白」，可以核对这个数是怎么来的——如果那里写的是
"未声明"，说明这台机器没有如实报告峰值，那就退回固定的 400。
