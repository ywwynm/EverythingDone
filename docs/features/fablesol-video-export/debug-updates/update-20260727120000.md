# HDR10+：换一种输入模式到底行不行，这一版去问设备

## 结论先说：另一条路确实存在，而且是官方唯一认可的那条

上一版我说 HDR10+ 做不到，那句话**只对我们目前这条链路成立**，不是对设备成立。两者是
两个命题，我把它们说成了一个。

我们现在是把画面直接送进编码器（叫 surface 模式），而 HDR10+ 那份逐场景动态元数据在这种
模式下系统明确不允许应用提供。但还有一种模式：**先把画面读回来，自己转成编码器要的像素
格式，再一帧一帧地送进去**。那个参数唯一被允许使用的就是这种模式——而且 Android 自己的
兼容性测试套件里，HDR10+ 编码的用例走的正是它。也就是说，凡是声称支持 HDR10+ 编码的设备，
在这条路上都必须真的能编，否则过不了认证。

所以真正该问的是：**三星在这条路上认不认。** 这一版加了一个探测专门去问。

它完全不碰导出流程，只做一件事：按字节缓冲模式配置编码器，喂一帧纯色画面，然后看编码器
回报的格式还是不是 HDR10+。分两次问：

- **裸通路**——只切模式、不带元数据。回答"换个模式是不是就够了"。
- **带元数据**——同时送一份完整的动态元数据。回答"是不是还必须带上它"。

分开问是为了在失败时能分清是这条路走不通，还是我送的元数据写得不对。诊断里会多出一行
「HDR10+ 字节缓冲」，把编码器名字、像素格式支不支持、以及这两问的结果都列出来。

## 顺带更正我上一版的一个说法

我说过"不去伪造元数据"。在 surface 模式下那句话是对的——画面已经交出去了，任何统计量都
只能靠猜。但在字节缓冲模式下**画面在我们手里**：最大亮度、平均亮度、各百分位的分布，全都
是**测得出来的实数**，不是猜的。所以真要建这条管线，元数据不构成道德问题，构成的是工作量
问题。

## 如果三星认，代价是什么

要自己完成两件编码器原本替我们做的事：把渲染结果从显卡读回来并转成 10 位 YUV，以及逐帧
统计画面亮度分布。前者错了会直接表现为颜色不对（好在错得很显眼），后者是纯计算。导出耗时
大概会增加，因为多了读回和转换。

值不值得，等看到探测结果再一起定。先装这一版，开一次设置把那一行发我。
