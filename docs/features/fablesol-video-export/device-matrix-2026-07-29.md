### 实测耗时与峰值内存（7.13 秒音频、856 帧、1152×1472、120 fps）

| 通路 | 耗时 | 峰值 PSS |
|---|---|---|
| HDR10+ 首次（全片预分析 + 逐帧统计 + P010） | 68.2 s | 453 MB |
| HDR10+ 再次（预分析缓存命中） | 50.6 s | — |
| HDR10 首次（全片预分析 + P010） | 52.4 s | 458 MB |
| HDR10 再次（缓存命中） | 33.7 s | 453 MB |
| 原生 SDR · 10-bit 应用 P010 | 35.5 s | 448 MB |
| 原生 SDR · 8-bit 编码器 Surface | 12.1 s | 354 MB |

由此拆出各条内部质量通路在本画布下的实际单价（应用空闲基线约 343 MB）：

- **全片预分析**：约 18 s，合 21 ms/帧。这是 D85 的已知取舍，缓存命中后不再付。
- **HDR10+ 逐帧统计（GLES 3.1 compute + 载荷构造）**：约 17 s，合 20 ms/帧。
- **应用自有 P010（三趟 + 回读）相对 Surface**：约 23 s，合 27 ms/帧；峰值内存高约 95 MB。

三项都远高于 8-bit Surface 那条最短路径（12.1 s），也就是说**画质通路的代价是导出时长增加
两到五倍**。这与 plan-review 第五节的预估一致，属于已定取舍，但值得在产品说明里让用户知道。

### 确定性

同一 WAV、同一设置连续导出，产物**字节不同**（大小相差数万字节），但：

- 全片预分析的统计值逐位复现：`9.593701456980474|0.8043879067632341`。这是对 856 帧
  每个像素做的归约（最大 maxRGB 与逐帧平均的加权最大值），能精确重现，意味着音频驱动、
  模拟、倾斜回放、时钟、渲染、GPU 归约与 CPU 聚合这一整条链路都是确定的。
- 一对产物（一次跑了预分析、一次命中缓存）前 166 帧**逐位相同**，之后才发散；另一对
  （两次都命中缓存）从第 1 帧就不同。同样的渲染条件出现两种结果，说明发散源在硬件编码器
  的码控，不在我们这一侧。

结论：**我们负责的部分是确定的，产物字节不可复现是硬件编码器的性质。** 批次 8 的门禁
措辞正是"相同预分析统计和确定性像素控制量"，不是"字节一致"。

## 二、仍需其它设备或外部平台完成的抽查

以下项目需要 PLZ110 不具备的硬件编码能力、图形能力或外部分享平台。

### 1. 厂商硬件恒定质量（CQ）路径

PLZ110 的 `c2.qti.hevc.encoder` 没有公开可用的 CQ 质量区间，但
`c2.android.av1.encoder` 公开 0～100 的质量区间并声明 QP bounds。2026-07-30 已修复设置页
能力查询遗漏 AV1 的问题，并完成以下验证：

- [x] HDR10／AV1／60 fps 下显示“编码模式”，可选择“恒定质量”与“目标码率”。
- [x] 恒定质量采用编码器公开区间上限 100，完成信息写“恒定质量”。
- [x] AOSP 软件 AV1 HDR 最高质量档的 QP 上限 8 生效；实测 I/P/B 最大 QP 为 8/11/14。
- [x] VBR 的复杂帧质量保护生效；实测 I/P/B 最大 QP 为 40/43/46。

厂商硬件 CQ 仍需一台公开质量区间的设备验证；此前提到的三星或华为设备均可作为候选：

- [ ] 硬件编码器的质量滑杆默认值与“恢复默认”都落在区间上限（D146）。
- [ ] **华为平板专项**：它的 `OMX.hisi.video.encoder.hevc` 属于 configure 必须携带码率键
      的那一类。D167 的同模式兼容阶梯就是为它加的——纯 CQ 应当失败、自动重试 CQ+码率提示
      并成功，用户可见措辞不变。若它反而整个落到 VBR，说明阶梯没生效。

### 2. GLES 3.0 的 HDR10+ 统计后端

PLZ110 取到的是 GLES 3.1，走 compute/SSBO 那条路。需要一台实际 `GL_VERSION` 只到 3.0 的
设备验证 RGBA8 精确打包/回读后端，并确认两个后端的载荷结果**逐项相等**。

- [ ] HDR10+ 导出成功，载荷字段与 3.1 设备一致。
- [ ] 耗时明显高于 3.1 后端属预期，但不应导致导出失败或超时。

### 3. 无硬件 10-bit 通路时的自动落点

**三星 Z Fold4** 已知没有可用的硬件 10-bit 输入通路（D58），默认设置（原生 SDR + 自动位深）
下会落到**软件 HEVC 10-bit P010**。

- [ ] 确认导出能完成（可能显著慢于实时）。
- [ ] 信息栏出现软件编码的速度/耗电/发热说明。
- [ ] 完成信息标注「软件编码」。
- [ ] 若耗时长到不可接受，这是 D53 修订的直接后果，需要产品裁定而不是改代码。

### 4. HLG super-white 的第二台设备

PLZ110 的 HEVC 通路量到了完整的视频数据范围，杜比视界通路则整段塌缩。这两个结论都**只对
这台设备成立**（D140 明确 super-white 不是设备级布尔量）。

- [ ] 另一台设备上导出显式 HLG · 自动增强，看完成信息报「扩展」还是「名义」。
- [ ] 打开设备能力报告，看「HLG 扩展信号范围（已验证的编码通路）」那几行的实测码值。

### 5. 播放与分享的真实表现（本机无法替代）

- [x] OPPO 系统播放器已同帧检查 HDR10、HDR10+、HLG 扩展／名义范围和杜比视界 8.4；
      水体色相连续、星芒高光保留，未见频繁明暗变化。播放器未提供全部格式的可读标识，因此
      格式身份另由 FFprobe 与码流侧数据确认。
- [ ] 微信聊天 / 朋友圈发送后的二次转码结果：画幅有没有被单边裁切、HDR 有没有被压成 SDR。
- [ ] 若要评估 HLG super-white 的画质收益，需要一段**高饱和且明显越过 2.0× 膝点**的素材
      （例如强烈单色光下的水面）；当前代表素材的高光以白色星芒为主，中性方向按设计本就
      不使用 super-white，实测差异只有约 1.4 个码值。
