## 二、必须修正的设计问题

### 1. D131 的一维参数表不能以 q(u) 作查表键（数学错误）

D131 写明"实现使用……一维参数表，以 q(u) 查表"，其前提（D131 原文）是"K、H 和 A 随
颜色方向的标量 q(u) 连续变化"。该前提不成立：**肩部形状还依赖第二个与 q 无关的方向量。**

把肩部方程按 `m̂ = m / q(u)` 归一化后：

- `K̂ = K_D^{1/γ} = 2^{1/1.2} ≈ 1.7818`（整段常数）；
- `Ĥ = H_D^{1/γ}`（整段常数，H_D 为用户 HDR 强度）；
- 方向相关的形状量只剩 `Ĉ(u) = C_S(u) / q(u)`，归一化肩部尺度 `Â = A/q` 满足
  `Â(1−exp(−(Ĥ−K̂)/Â)) = Ĉ−K̂`，即 **Â 只是 Ĉ 的函数**。

而 `Ĉ` 不能由 `q` 确定。在标准范围内 `C_S = C_match = (max(v)/Y_v)^{1/6}`
（`v = rec709ToBt2020(u)`，`Y_v` 为 BT.2020 亮度权重），且
`q = E_ref · max(v)^{5/6} · C_match`——给定 q 后 `max(v)` 与 `C_match` 仍可互相置换。
数值反例：

- 纯红 `q ≈ 0.215` 低于白 `q ≈ 0.265`，但归一化容量 `Ĉ(红) ≈ 5.57` 高于
  `Ĉ(白) ≈ 3.77`——q 与 Ĉ 甚至不同向；
- 红→白路径上 `q ≈ 0.234` 处 `Ĉ ≈ 4.48`；红→品红路径上同样 `q ≈ 0.233` 处
  `Ĉ ≈ 5.04`。同一 q 需要两个不同的 Â，一维 q 表必然给错其中一个：要么让仍有余量的
  颜色提前压缩，要么让容量不足的颜色越过其信号上限后被末端钳制，恰好违反 D129/D133
  "该颜色确实放不下才压"的核心语义。

**修正**：查表键改为 `Ĉ(u)`（或等价的 `C_S(u)/q(u)`），表内容为 `Â = f(Ĉ)`；
shader 中 `C_match = (max(v)/Y_v)^{1/6}` 与 `q` 均为逐像素闭式量，计算代价可忽略。
D129～D134 的其余设计（共同增益、方向相关端点、`W_MAX` 硬门禁）全部不受影响。plan.md
批次 6 的"以 q(u) 查表"表述需同步修正。

**处理结果（2026-07-28，与用户定案）**：已落实——新增 D164（记法 `C_n(u)`，即本节的
`Ĉ(u)`）并直接改写 D131 相应段落，同步 plan.md 决策解析规则与批次 6、execution.md
批次 6 清单。

### 2. D140 的 W_device(u) 连续推导没有给出算法（设计空白）

D140 要求由 Y′、Cb、Cr 三个分量各自的连续安全区间"连续推导每个颜色方向的设备上限
`W_device(u)`"，并禁止离散颜色档与逐通道截断，但没有说明推导方法。该映射
（方向端点 → 量化后 Y′CbCr 是否落入区间）不存在显然的闭式反解，Cb/Cr 沿共同增益方向
也不保证单调。实现前需要定下确定性方案，例如：导出开始时在方向域（`max(u)=1` 的两个
立方体面）上取网格，逐方向二分求最大可用 W，构成二维查表并线性插值，得到的
`Ĉ_actual = min(Ĉ_standard, hlgInverseOetf(W_device)/q)` 仍送入第 1 条的一维 Â 表；
连续性由网格插值保证，并纳入 D133 要求的量化后台阶验证。

**处理结果（2026-07-28，与用户定案）**：已落实——新增 D165，采用方向域（三个立方体面）
网格 + 二分方案，可行性判定按固定 `W` 步长覆盖整段 super-white 区间以保证二分单调性；
D140 原文加入指引，plan.md 批次 6 与 execution.md 清单同步。

## 三、实现前需要定案的冲突与空白

### 3. D91 与 D142 的验收边界字面冲突

D91 第 2、3 条要求"临时 MP4 封装完成后、提交前重新打开产物逐字段核对，不一致则丢弃
候选"；D142 规定"完整编码并成功封装后，不得因附加结构检查推翻结果"。封装完成发生在
提交之前，两条按字面同时适用且互斥。plan.md 已按 D142 收敛（"冲突在短探测阶段淘汰候选；
完整编码和封装成功后附加解析只作诊断"），实现时应明确：**静态元数据的回读核对在短探测
产物（单帧小文件）上执行**，正式产物封装成功后只记录诊断。建议在 decisions.md 给 D91
补一行修订说明，避免 Opus 读到两条相反指令。

连带一个平台事实需要在实现时核对：`MediaMuxer` 把 `KEY_HDR_STATIC_INFO` 落盘为
mdcv/clli box 是较新 Android 才具备的行为（需查 AOSP `MPEG4Writer` 支持起点）；旧系统
上"补入 muxer 轨格式"可能是无效操作，实际承载者是编码器按 configure 时的
`KEY_HDR_STATIC_INFO` 生成的 SEI。因此 configure 时的注入（现有代码已做）必须保留，
不能被"由 muxer 补齐"替代。

**处理结果（2026-07-28，与用户定案）**：按 D142 收敛——新增 D166，改写 D91 第 2、3 条：
回读核对移到短探测产物，正式导出保留注入与真实错误门禁，封装成功后解析只诊断；承载事实
（configure 注入不可替代、核对接受容器 box 或码流 SEI）一并写入，plan.md 两处同步。

### 4. D145 纯 CQ 配置存在设备回归风险

D145 禁止 CQ 模式同时下发 `KEY_BIT_RATE`。现有代码一直同发且在用户设备上工作。风险：
OMX 系编码器（ACodec 路径，如华为平板的 `OMX.hisi.video.encoder.hevc`）在 configure
时要求视频编码器必须携带 bitrate 键，缺失直接失败；若严格照 D145 实施，这类设备的 CQ
候选会整体探测失败并静默落到 VBR——比现状更差，方向与 D145 的意图相反。建议定案为：
短探测先试纯 CQ；失败再试"CQ + 码率提示"作为**同模式**兼容候选并记入诊断；两者都失败
才判该编码器不支持 CQ。这与 D145 的绝对表述有出入，需要用户确认。

**处理结果（2026-07-28，与用户定案）**：采用同模式兼容阶梯——新增 D167（纯 CQ →
CQ+码率提示 → 判不支持；探测与正式同形态；缓存签名与诊断区分形态），D145 原文、
plan.md 批次 7、execution.md 清单与 preferences.md 同步。

### 5. D152 在 CQ 模式下的 Level 码率依据未定义

D152 要求按"当前解析后的码率"选最低充分 Level，但 CQ 模式没有解析码率。若用 VBR
推导值做依据而 CQ 实际码率更高，过低的 Level 提示可能促使部分编码器为守 Level 约束
而限制质量，与"CQ 默认最高质量"抵触。需要补一条规则，例如：CQ 模式下 Level 的码率
分量按该 Level 像素率档位允许的码率上限取，或按 VBR 自动推导值乘保守倍数（如 2～3×）
后夹取。D152 已允许接受编码器回报的更高 Level，这条规则只影响申请值。

**处理结果（2026-07-28，与用户定案）**：新增 D168——CQ 模式 Level 只按尺寸与像素率取
最低充分档、保持 Main Tier，不为未知码率抬档；接受名义超出，编码器回报更高 Level 照
D152 采纳；个别编码器若因此自限质量，按编码器单独处理。D152 原文、plan.md、execution.md
同步。

### 6. D163 的整数秒兼容分支是死条款且自相矛盾

`KEY_I_FRAME_INTERVAL` 自 API 25 起接受 float，本项目 `minSdk 26`，"旧系统不接受
Float"分支永远不会执行；现有代码也已无条件 `setFloat`。且该分支按字面执行会出错：
0.5 秒时"不长于请求的整数秒"只有 0，而 0 表示全帧内编码，与同条"不启用全帧内编码"
矛盾。建议直接删除该段，不要实现。

**处理结果（2026-07-28，与用户定案）**：已从 D163 删除该分支并注明理由；execution.md
的对应验证项改为"Float 下发与跨候选一致性"。

### 7. D112 nearest-rank 与直方图桶粒度需要显式规定

D112 要求逐像素 nearest-rank 精确分位，同时 D104/D124 的两个统计后端都以直方图归约
实现。有限桶宽的直方图给出的是近似分位；若两个后端桶方案不同，"后端一致性测试"会因
桶宽差异而不可判定。建议明确：直方图桶按 DistributionMaxRGB 载荷量化网格（归一化
0.00001 步长，或等价的 PQ 域等步）建桶，使分位结果在载荷精度上精确；MaxSCL 用原值
atomic max 单独维护，不经过桶。两个后端使用同一桶定义。

**处理结果（2026-07-28，与用户定案）**：新增 D169——线性域 100001 桶对齐载荷
`0.00001` 网格，MaxSCL/AverageMaxRGB 不过桶，两个后端同桶定义且一致性测试要求逐项
相等；D112 原文、plan.md 批次 5、execution.md 清单同步。

### 8. AV1 的色度位置声明未覆盖

D154 只讨论了 HEVC 的 SPS/VUI。AV1 10-bit 走应用 P010 时对应物是序列头的
`chroma_sample_position`，短探测与相位匹配规则应同样适用（AV1 默认 CSP_UNKNOWN 时的
兼容语义需一并定义），否则 AV1 P010 路径的相位无据可依。

**处理结果（2026-07-28，与用户定案）**：新增 D170——CSP_COLOCATED→Type 2、
CSP_VERTICAL→Type 0、CSP_UNKNOWN→Type 0 兼容并记诊断，其余约束与 D154 一致；D154
原文、plan.md 批次 2、execution.md 清单同步。

另有两点提示：色度位置探测需要解析短探测码流的 HEVC SPS/VUI（防竞争字节处理等），
是一段真实的解析工作量，建议独立成模块并配已知码流测试向量；GLES 3.1 compute 后端

## 五、成本与风险提示（非设计错误，用户应知情）

- **D85 预分析**使 HDR10/HDR10+ 对同一录音的首次导出渲染量约翻倍；D92 缓存键含实际
  分辨率，而实际分辨率随候选编码器对齐变化，候选失败换档后可能再次预分析。属可接受的
  已定取舍，此处仅确认其后果。
- **自动 SDR 的软件 10-bit 落点**：D53（修订）+ D160 + D158 组合下，无可用硬件 10-bit
  通路的设备（如三星 Z Fold4）在默认设置（原生 SDR + 自动位深）下会落到软件 HEVC
  10-bit P010。约两百万像素 120fps 的软件编码可能比实时慢一到两个数量级，默认档导出
  时长会显著变长。这是已定决策的直接后果，界面警示（D53）必须做实。
- **逐帧 GPU 开销**：应用 P010 路径新增闭环修正（量化色度→参考上采样→Y′ 求解）、
  蓝噪声阈值与全分辨率统计，多趟 pass 叠加后帧成本明显高于现状的三趟；批次 8 要求的
  实际画布耗时/内存记录应尽早做，不要等到集成阶段。
- **蓝噪声资源**：64×64 阈值表需要自行离线生成（如 void-and-cluster）并入 assets。
  引用的 libplacebo 是 LGPL 项目，只参考其策略，不直接拷贝其表数据或代码。
- **CQ 自定义值迁移**（批次 1）依赖"迁移时实际解析的候选签名"，冷启动时能力矩阵可能
