# Android 关闭粒子动画的启动延迟

## 范围与基线

- 用户认可的视觉效果已提交为 `d37b42cb`：修复孤立细缕并保留边缘卷动。
- 本轮只优化关闭动作到首帧的准备链，背景触摸、返回、取消、确认共用同一入口；保留已认可的共同模型、随机输入和触点规则。
- `9018f404` 上真实语言弹窗初轮四条路径：首帧提交分别为 483.5、497.5、434.3、454.8 毫秒。材料构建约 388–451 毫秒，GPU 准备到首帧约 27–41 毫秒。
- 测量脚本 `tuning-0909-gpt6/analysis/measure_dismiss_startup.py`，原始记录位于忽略目录 `analysis/startup-latency/`。确认按钮保持当前语言，不改变应用设置。
- 首次测量的背景触点距窗口太近，落在系统外部触摸容差内，窗口未关闭；已根据实际窗口边界增加距离。这是测试触发问题，不能当成动画失败。

## 诊断顺序

1. 细分材料构建，验证 CPU 数值计算是否为主要瓶颈。
2. 量化 GPU 初始化与首帧提交，避免只优化几十毫秒而留下大段计算。
3. 核对纹理更新和真实窗口移除时序，防止首帧日志早于用户实际看到的画面。

## 验证约束

- 以真实四条关闭路径的启动耗时作为反馈；数值单测不能替代此测量。
- 数值优化必须通过当前材料、随机性、共享场及 GPU 对齐用例，不能重写验收基准来接受视觉变化。
- `R5CW20BLNKL` 当前不在线；不操作其他设备。

## 已验证的瓶颈与第一轮

- 释放场 200–220 毫秒，材料生成/排序约 90–105 毫秒，其他释放梯度、法向、压缩约 90 毫秒。关闭链没有一段人为等待可以简单删掉。
- 为数值循环增加本地批量实现，仍由 Kotlin 共同规则传入参数，保留 Kotlin 参考路径和 JVM 校验。禁用浮点融合与快速数学改写；不减少粒子数量或改变释放、寿命、方向。
- 第一轮在同一真机比较 4 种尺寸 × 5 方向 × 2 种子，共 40 组；材料属性、颜色份额、压缩数组的最大差值均为零。实际启动仍为 200–265 毫秒，因此继续优化剩余梯度计算，不以局部加速宣告完成。
- `measure_dismiss_startup.py --max-first-ms 100` 已在修复前的四条真实关闭路径上失败，保存为启动性能回归回路。
- 本地实现采用批量普通数组访问，避免长时间占用 JNI Critical 区；构建设置 16 KB 段对齐。依据：[Android JNI 指南](https://developer.android.com/ndk/guides/jni-tips)、[NDK CMake 指南](https://developer.android.com/ndk/guides/cmake)、[16 KB 页面支持](https://developer.android.com/guide/practices/page-sizes)。

## 后续优化与复核

- 本地实现继续覆盖梯度与法向计算；四像素向量计算保持每个像素内部原有的双精度累加顺序。深度改为稳定基数排序，等深度仍由原索引确定次序。
- 40 组对照扩展到白面板、丰富颜色与半透明像素，材料属性、颜色份额、压缩数组仍为零差值。另检查 RGBA 上传字节、首帧状态缓冲及原像素不被修改。
- 首帧 GPU 缓冲准备曾占 20–30 毫秒；将颜色转换与初始状态打包改为本地批次，避免临时 FloatArray 和大量托管循环。
- 着色器编译、公共流场上传、屏幕缓冲创建与后台建材重叠。首个弹窗显示时，在不可见的小尺寸缓冲上预热驱动，预热不持有用户画面。
- 预留最大 GPU 缓冲未带来稳定收益，已经去掉，继续按实际材料数量分配。
- 加速后的实际请求到首帧提交约 93–120 毫秒；最初设置的每次均低于 100 毫秒目标尚未稳定通过，不能写成全部通过。最终安装包仍要重新记录完整链路与界面合成时间。
- 一轮测量中 ADB 服务短暂不可达，保留失败日志；恢复连接后重新跑完整样本，不将其计作动画耗时或动画失败。

## 最终本地验证

- 提高准备与 GL 线程优先级后，四条真实关闭路径各两次：请求到首帧提交 86.3–110.3 毫秒，首次 TextureView 界面合成 91.2–119.6 毫秒。这里的起点是关闭请求进入动画控制器，不包含按钮业务回调此前可能执行的工作；界面合成也不等同于外部高速摄像测量。
- 40 组原 Kotlin／本地实现独立对照全部通过，材料最大差值为零，RGBA 和初始状态缓冲逐值一致。
- 旧颜色弹窗 GPU 产物的模型哈希不同，不能混作本轮视觉基准；增加仅限调试验证的 Kotlin 参考开关，在当前模型上重新独立计算材料和上传缓冲，再逐帧比较。
- 完整渲染对照通过：三序列与原 Kotlin 路径的 27 张关键帧，加上钢铁侠／添加附件与认可版本的 18 张关键帧，45 次全画面 RGBA 比较为零差值；材料和三个相位的 GPU 状态也逐值一致。报告为 `analysis/startup-latency/final-visual-parity.json`。
- 19 项 JVM 检查通过（模型 14、时间线 3、着色器 2，无跳过）；新增本地库的 arm64-v8a、armeabi-v7a、x86_64、x86 四种 ELF 加载段均经 readelf 检查为 `0x4000` 对齐。这不是在 16 KB 物理设备上的实测结论。
