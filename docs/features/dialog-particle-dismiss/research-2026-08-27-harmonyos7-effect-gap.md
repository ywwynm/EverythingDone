# Dialog 粒子消散：HarmonyOS 7 参考效果差异分析

日期：2026-08-27
状态：完成参考视频、当前真机效果、桌面模拟器与公开资料的第一轮交叉分析；等待产品取舍后实施

## 一、证据边界

本次结论来自四类证据：

1. 用户提供的 HarmonyOS 7 屏摄视频，重点逐帧检查约 6.45s–7.30s 的清空通知段；
2. 当前真机录屏与 Claude 调试过程留下的对比帧；
3. `ParticleDismissController`、`ParticleDismissRenderer` 与桌面模拟器源码；
4. 华为官方粒子/动效文档、OpenGL ES 规范、Curl Noise 论文，以及 Telegram Android
   同类消散效果的公开实现。

华为未公开该系统动效的实现源码。下文把“视频中可以直接观察到的事实”和“据此提出的
实现推断”分开表述，不声称已经还原其内部算法。屏摄视频还叠加了相机曝光、运动模糊、
屏幕刷新与滚动快门，因此不能把画面中的光晕宽度直接当成系统实际的粒子尺寸。

## 二、参考视频的可观察事实

- 清空动效约在 6.45s 开始，主体约在 7.20s–7.30s 消失，可见主体约 0.8s；这是屏摄
  估算值，不含操作前等待，也不代表所有机型或“动画速度”设置均相同。
- 卡片没有整体同时变成随机点云。最先出现的是若干个局部边缘缺口，缺口继续发展成
  多条弯曲、较厚、粒子密度明显更高的移动锋线。
- 锋线附近的相邻像素在早期仍保持空间连续性，看起来是被掀起的片层；越过锋线后才
  逐步松散为粒子尾流。
- 各条锋线并不完全同步，也不是一个贯穿整个矩形的整齐扫描线。多张通知卡的圆角和
  边界天然提供了多个局部起点，因此画面同时存在几条非连通的浓带。
- 60fps 复核显示，最早可见粒子化出现在画面下方通知卡；其他左侧/较上方局部缺口约在
  随后 6–8 帧（约 100–130ms）内可见。它们不是绝对同帧，但感知上近同时启动；飞行
  向上时，首批起点反而位于运动方向的下游画面位置，即运动坐标中的上游/尾侧。
- 局部粒子会横向摆动，但动画的终端趋势稳定向上，末尾残留也继续上扬；没有随清空
  按钮所在位置整体向下汇聚。
- 观感上的“轻”主要来自大量细小、低透明度粒子形成连续的薄层，以及粒子之间共享的
  低频运动；不是来自少量大粒子、强辉光或大范围随机爆散。

## 三、当前实现的直接差异

| 维度 | 当前实现 | 参考效果 | 后果 |
|---|---|---|---|
| 方向语义 | 主方向由控件中心指向触点 | 本段参考视频稳定向上 | 用户确认完事儿应保留触点方向；这不是差异根因 |
| “帷幔”定义 | `curtain` 只提高初始坐标区段的保留率、副本数、尺寸和激活延迟 | 浓带本身是随时间弯曲、平移的连贯片层 | 当前形成亮块或亮边，不能形成被风带走的布面 |
| 邻域连续性 | 每个粒子有全角度随机早期方向、较大的速度差、独立抖动 | 早期邻近粒子基本同向，后期才解耦 | 当前从第一帧就呈砂砾/点云，而不是薄纱 |
| 白底处理 | 普通区域仅保留约 3%–9%，其余点以极短寿命闪现 | 大量低 alpha 细粒子共同构成半透明层 | 当前出现均匀针孔和骤然露底 |
| 浓带增强 | 三副本重叠、点尺寸翻倍、前段增亮 | 密度、透明度和相干运动共同形成厚度 | 当前容易过曝成白色团块，仍没有形态连续性 |
| 聚拢 | 强 `pinch` 把粒子拉向触点方向轴线，另有外扩 `flare` | 主要是统一方向气流下的折叠与摆动 | 当前出现漏斗、云团或被吸走感 |
| 粒子外观 | `GL_POINTS` 软圆点，最小仍是 1px，部分被内容权重和帷幔再次放大 | 屏摄中更接近细密点/短丝，运动方向连续 | 当前颗粒感明显，速度感和纤维感不足 |
| 时间 | 总预算约 1.345s | 本视频主体约 0.8s | 当前尾部更拖；是否调整需由产品目标决定 |

## 四、根因定位

### 1. 方向跟随不是根因，方向坐标系内的形态不连贯才是根因

初步分析曾把参考视频的上扬误判为产品不变量。用户随后明确：完事儿应保留触点方向，
触点在下方时帷幔向下掀起，触点在左侧时向左掀起。当前从控件中心指向触点的总体方向
因此是正确的交互语义。

需要改写的是该方向坐标系内的运动：揭开锋线、同一帷幔的共享位移和后续尾流应沿同一
主方向自然延续；不能一边跟随触点，一边用全角度独立初速度、强轴向聚拢和多组随机项
破坏片层。参考视频中的“向上”应抽象成可旋转的主方向基向量，而不是写死的屏幕方向。

### 2. 当前“帷幔”是选点掩码，不是运动中的片层

当前 `curtainSeg × curtainBand` 只标记一块初始区域，再以全保留、三副本和大尺寸把它
加亮。标记内的粒子之后仍各自采用随机方向、速度抖动、Curl Noise、聚拢和外扩。这能制造
“这里粒子很多”，但无法制造“这里是一张正在弯折的薄面”。

目标应把帷幔建模为一个运动阶段：同一帷幔 ID 的粒子共享低频位移、切向摆动和上升加速度；
在锋线刚通过时保持邻域相干，随后才逐渐放开个体扰动。

### 3. 随机项过多，而且过早介入

当前粒子在起飞早期就混入全角度随机方向，随后又叠加 0.6–1.5 倍速度差、Curl Noise、
逐粒子正弦抖动、`pinch` 与 `flare`。这些项各自都能增加变化，但同时作用会抹掉局部结构。
Curl Noise 论文证明其适合生成空间连贯、无散度的流场；它并不意味着应再给相邻粒子互不
相关的全角度初速度。目标需要“共享低频场为主、个体噪声为辅，并让个体噪声后置”。

### 4. 用删点和增亮代替了半透明覆盖率

白色区域保留率只有约 3%–9%，被剔除粒子寿命又被压到 0.07 倍。结果是大面积规则网格
迅速打孔，再靠锋线三副本和辉光补亮。参考画面更接近大量低 alpha 粒子的覆盖率渐变：
应优先降低单粒子 alpha 和尺寸，而不是先删掉九成粒子；浓带也应主要由移动锋线的粒子
占用率和寿命窗口形成，而非同一点重复三次造成饱和。

### 5. 当前评价指标测中了“亮度差”，没有测中“帷幔”

历史调试把峰/尾密度比调到约 4–8，但取样区域主要覆盖矩形顶边和右边的亮带。该指标只能
说明“锋线比尾流亮”，不能验证：

- 浓带是否非矩形、非连续整边；
- 浓带是否真的随时间移动和弯折；
- 相邻粒子的速度方向是否一致；
- 末段速度是否仍与本次触点主方向一致；
- 不同随机种子是否仍稳定产生同类形态。

因此指标达标而观感仍不接近，并不矛盾。

## 五、桌面模拟器为何会误导调参

- 主要使用固定随机种子，而 Android 每次消散重新取种子；模拟器只证明一个幸运样本。
- 九宫格以约 0.1 的归一化时间间隔取样，早期决定“片层是否被掀起”的前 100–150ms
  被严重欠采样。
- 静态接触表不能验证速度连续性、加速度和停顿；这些恰好决定“轻盈、灵动”。
- Android Shader 与 Python 内嵌 Shader 是人工复制的两份源码，历史上已经出现参数/逻辑
  不同步；当前脚本还残留旧变量和旧路径。
- 只有固定尺寸、固定背景、固定合成快照，不能暴露宽 Dialog、纯白背景、内容色稀少和
  不同像素密度下的失败模式。

模拟器仍有价值，但应升级为：同一 Shader 源生成 Android 与桌面版本；输出 60fps MP4；
专门输出前 0、33、67、100、150ms；每次展示多种随机种子、宽高比、背景与 density；并
增加方向相干度、末段主方向一致率、锋线曲率/宽度和尾流覆盖率，而不只看峰/尾亮度比。

## 六、推荐的重构模型

保留已经验证可用的 DecorView 快照、全屏透明 TextureView、EGL 线程和 GPU 粒子架构，
替换消散运动模型；不继续在现有参数堆上微调。

### 阶段 A：若干局部边缘起点

1. 在圆角矩形的边缘生成 3–5 个有长度的种子区段，而不是单个触点或完整矩形边；首批
   种子**主要**偏向主运动方向的反向一侧，即帷幔多从上游/尾侧被掀起后顺着主方向飞走。
   “主要”是概率偏置，不是硬裁剪：侧边与少量顺向一侧必须仍能产生起点。
2. 点击位置确定主运动方向：触点在下方时向下，触点在左侧时向左，其他方向同理。所有
   帷幔共享这一本次动画的主方向，但仍允许小幅切向摆动；返回键或代码关闭没有有效触点
   时默认向上。
3. 多个种子在约 0–100ms 的短窗口内近同时激活，而不是先完成一个再扫描到下一个；每个
   粒子分配给最近的种子/帷幔 ID，局部激活延迟由到该种子曲线的各向异性距离与低频噪声
   共同决定，使几条锋线分别推进、交叠。

### 阶段 B：先保持成片，再逐渐解耦

1. 粒子激活后的前 120–200ms 主要服从该帷幔共享的位移：上升、低频横摆、沿锋线切向
   的弯折；相邻粒子只允许很小的个体差。
2. 中后段逐步提高个体扰动和速度差，让片层自然松散为尾流。
3. 删除全角度随机早期方向、触点聚拢和强 `flare`；保留强度显著降低的多尺度 Curl
   Noise，只作为风场纹理，不作为主方向。
4. 使用沿触点主方向的显式加速度或终端速度，确保尾流不会被随机项带离本次交互方向。
   Telegram 的公开同类实现使用持续加速度，说明在 Android GLES 粒子中加入稳定终端力
   的成本很低；只参考其受力思路，不照搬固定向上方向，也不复制其 GPL v2 代码。

### 阶段 C：以覆盖率塑造薄纱

1. 普通区域保留更多粒子，但采用更小尺寸、更低 alpha；不再让九成格子闪一下就死亡。
2. 浓带由 `localAge = time - activationDelay` 的窄时间窗形成：窗口内粒子完整、较密，
   通过后 alpha 与密度平滑衰减。每条帷幔窗口略有不同。
3. 先以细小软点完成第一版；若真机仍显砂砾，再把点扩展为沿速度方向的短四边形，或只
   对粒子层做极弱的前后帧累积。不能直接照抄屏摄光晕，因为录像本身已经增加了拖影。

### 阶段 D：验证与收敛

1. 先在共享模拟器中验证运动结构，固定“方向跟随触点、起点位于运动上游侧、3–5 条局部
   锋线近同时出现、早期邻域相干”四项不变量；其他参数再调。
2. 以至少 12 个随机种子、三种宽高比、纯白/多色内容和两档 density 生成 60fps 视频。
3. 自动检查：末段速度与触点主方向的一致率、邻域速度余弦相似度、锋线连通域数量、锋线
   宽度、尾流覆盖率；人工检查：是否像片层掀起、是否出现矩形边框、漏斗、白团或网格
   针孔。
4. 最后用真机录屏与参考视频并排、按相同时间比例播放。桌面结果只负责筛选，不替代真机
   视觉验收。

## 七、公开资料支持的边界

- 华为官方说明，HarmonyOS 7 将“气体效果”升级为更细腻的“粒子效果”，清空动画刻意
  不做得过快，以保证卡片消散过程自然、连续：
  <https://consumer.huawei.com/cn/support/content/zh-cn16090458/>
- 华为粒子组件把发射器、生命周期、速度/加速度和扰动场分开建模；扰动场通过空间力和
  feather/noise 参数塑造自然轨迹。这支持“结构化发射 + 共享力场”，但不能证明通知中心
  内部正使用该公开组件：
  <https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/arkts-particle-animation>
- 华为动效指南强调物理“力”的秩序感，并把粒子的透明度、大小、速度和加速度视为独立
  维度：
  <https://developer.huawei.com/consumer/cn/doc/HarmonyOS-Guides/arkts-animation-usage-guide>
- Curl Noise 原论文提供空间连贯、无散度且可调幅度的程序化流场依据：
  <https://doi.org/10.1145/1276377.1276435>
- OpenGL ES 3.0 原生支持 Transform Feedback；若后续闭式模型不足以表达持续受力的片层，
  可以在现有 minSdk 能力范围内保留粒子速度/位置状态，但第一版无需立即增加这项复杂度：
  <https://registry.khronos.org/OpenGL/specs/es/3.0/es_spec_3.0.pdf>
- Telegram Android 的公开实现使用 TextureView、OpenGL ES 3、Transform Feedback 和持续
  向上加速度，可作为移动端工程可行性的参照；许可证为 GPL v2，只读其公开思想：
  <https://github.com/DrKLO/Telegram/blob/master/TMessagesProj/src/main/java/org/telegram/ui/Components/ThanosEffect.java>

## 八、当前待确认的产品取舍

1. 出现动画是否也要随本次重做；“消散的严格倒放”会产生向下落回并缝合的语义，未必与
   轻盈出现相符，建议出现与消失使用独立运动模型。
2. 时间目标是忠于本段参考视频的约 0.8s 主体，还是保留当前约 1.345s 的总时长；华为官方
   明确说明清空消散刻意偏慢，因此不能只追求越短越好。
3. 参考视频包含多张通知卡，天然产生多组边界；单个 Dialog 要模拟类似丰富度，需要人为
   生成 3–5 个局部边缘种子，是否接受每次形态有受控随机变化。
