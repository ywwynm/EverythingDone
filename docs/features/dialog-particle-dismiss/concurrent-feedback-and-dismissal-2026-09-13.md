# 触摸反馈并行与真实关闭操作

用户要求出现粒子与 ripple 同时播放，继续解决真实返回键、外部触摸、取消和确认引发的消散卡顿。当前提交 `fa41a6f3` 是对照版本：工具栏重复出现恢复为 35–37 帧，但等待反馈结束，普通关闭仍可见 68–82 ms 起步间隔。

使用 diagnose 流程，保留粒子材质与共同运动模型，分别核对触摸反馈、GL 提交、实际纹理提交及窗口主线程时序。测试限定已授权的 9018f404、R5CW20BLNKL；不录屏、不实际录音、不修改记事。

## 待证伪假设

1. 出现路径的 `awaitPlayback` 显式串行化造成额外等待；移除出现等待后，首帧应早于 ripple 末帧，同时二者实际间隔仍满足预算。
2. 原窗口撤下后的焦点、输入法或布局工作与消散起步重叠；长帧应集中在真实窗口移除而非每次 GPU 绘制。
3. 暗层、全屏透明纹理或 ripple 重绘引入不必要的合成；削减多余图层工作应降低 RenderThread 耗时，同时维持真实颜色和反馈过程。
4. GL 同步或节拍调度使忙帧之后继续丢帧；以提交、窗口消费及 UI 接收三种时刻定位，不能以总提交数替代显示结果。

新回归须通过 Android 输入分发执行关闭动作，保留四类操作的完整输出与失败记录。普通有按钮的诊断选择框只关闭自身，不改变用户数据；添加附件使用真实菜单入口。

## 第一轮实测

- 真实工具栏打开、返回关闭：对照触摸抬起到首个实际纹理提交约 450–459 ms；仅移除出现等待后为 352–373 ms，与 ripple 尾段重叠约 15–49 ms。
- 仅取消等待还不够：六次出现中两次实际帧间隔 P90 超过 30 ms；消散仍有 65–82 ms 长间隔。因此不把这个实验当作完整修复。
- 外部触摸、取消、确认均已复现关闭长间隔，确认不是 `.dismiss()` 直接调用才能触发。第一轮取消的探针曾在外部输入未完成时提前进入下轮；已增加原窗口实际关闭条件，该轮作废，重测结果保留。
- 系统跟踪发现长间隔附近既有窗口移除、重新布局，也有 HWUI 的缓冲等待。其间粒子 GL 仍持续提交；需进一步隔离刷新率切换和全屏纹理消费，不能只优化计算着色器。

参考依据：[AOSP TextureView](https://source.android.com/docs/core/graphics/arch-tv) 说明其内容还需由 UI 工具包合成；[Android 帧同步说明](https://developer.android.com/games/sdk/frame-pacing) 说明仅跟随 Choreographer 不代表缓冲按时显示。此次以实际纹理提交、UI 线程接收和系统跟踪交叉核对。

## 刷新率切换定位

跟踪的 `ActiveModeFps` 确认，取消关闭的 55／65 ms 长间隔和一次出现的 72 ms 起步间隔都覆盖 120→60 Hz 切换。源 Dialog 请求与 Activity 粒子窗口请求不一致，焦点返回后才触发 Activity 的 60 Hz 请求。

第一项隔离实验让宿主保持当前 120 Hz：六次返回的最大间隔降至 34–51 ms，但出现普遍仅 30–32 个实际纹理帧、P90 约 32 ms，不能接受。需要让两个窗口在准备阶段统一请求、避免播放途中切换，同时避免无益的高频重复合成。

## 提交回调和合成开销

- 准备阶段同时登记源 Window 与 Activity，消除了播放中途因焦点转移触发的模式切换；六次返回与三次外部触摸不再出现之前的 65–82 ms 间隔。
- 跟踪另见 `alpha caused saveLayer 2520x1680`：纯黑暗层没有重叠内容，允许直接应用 alpha，省去不必要的全屏离屏合成。浓度和时长不变。这项在此前不同调度版本中未能独立改善卡顿，本轮是在刷新率问题已隔离后的合成减负，不能据此将所有改善归因于它。
- Android 36 SDK 源码中 `ViewRootImpl.performDraw()` 在 View 绘制之前收集 `captureFrameCommitCallbacks()`，而 `TextureView.onSurfaceTextureUpdated()` 在 View 绘制期间触发。原先在 updated 内注册已经晚了一拍；既延后交接，又漏记部分纹理消费。改成 OnPreDraw 登记，提交时读已消费的时间戳，在回调已位于主线程时直接处理，保留 API 29 以下回退。
- 新六轮真实菜单／返回：出现 36–38 帧，P90 18.7–20.4 ms、最大 34.8 ms；关闭 60–61 帧，P90 17.8–19.8 ms、最大 32.3 ms。全部满足当前严格联合预算，末帧吻合。触摸到首帧回调 306–364 ms，ripple 与粒子重叠约 31–99 ms。
- ripple 探针此前只允许一条待提交回调，重复时自身会漏采；改为在实际预绘制中采样主窗口及源 Dialog，和生产交接采用相同的登记时机。旧 ripple 的 P90 不作为最终流畅度结论。
- 暗层实验的一轮返回键未送达窗口（没有对应输入事件），探针超时，保留失败数据；回归现会等出现层释放、真实窗口获得焦点并稳定后再执行关闭。它不代表该轮关闭动画成功。

## 最终共同调度及回归

无 ripple 的首次选择框仍出现过 25 个纹理帧、P90 34 ms。原因是逆向准备只在有反馈时受到 GPU 队列约束；全部正／逆路径改为从准备阶段持有播放优先级后，该反例恢复为 36 帧。此约束只限制在途工作，不减少积分、粒子或改变共同运动模型。

最终测试均通过 Android 实际输入分发。数字是窗口提交回调观测的不同纹理帧和间隔，并非外部仪器测得的面板扫描时间；刷新率切换原因另由系统 trace 佐证。
