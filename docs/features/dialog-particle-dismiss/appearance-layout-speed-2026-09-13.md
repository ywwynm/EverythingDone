# 出现动画速度与布局尺寸交接

## 用户要求

- 出现播放更快，开始前的准备继续压缩；保留下方随机方向与共同消散模型的逆过程。
- 修复更新日志弹窗动画期间与最终尺寸不一致，并覆盖其它会二次布局的弹窗。

## 已复现的问题

真实 `DebugUpdateDialogFragment` 注入固定长、短日志，通过实际动画输入快照与恢复后的 View 比较。未改生产流程时：

- 9018f404 的长日志快照为 840×1557，后续先变为 840×1099，再变为 840×1105；窗口纵坐标也由 105 变为 331。短日志由 700 高变为 699 高。
- R5CW20BLNKL 的长日志同样尺寸不匹配。
- 同时检查固定高度的 `LongTextDialogFragment`，快照和最终画面一致。

代码存在 `scroll.post` 限高、嵌套 `post` 安装分隔线及修改间距的连续布局请求。旧流程首次 pre-draw 后抓图，没有检查待处理的下一次布局。该问题与用户滚动无关；其它异步调整布局的弹窗也可能出现。

验证工具为 `analysis/verify_appearance_colors.py --kinds update long-text --palettes gradient short`；完整尺寸时间线、快照与日志放在忽略跟踪的 `analysis/appearance-layout-speed/`。

## 实现

- 在共用出现捕获入口检查可见子树的布局请求，仅存在待处理布局时重试下一次 pre-draw；仍在整轮 pre-draw 完成后捕获，保留渐变初始化。
- 出现播放目标 0.6 秒；240 Hz 积分、100 次压力迭代与共同粒子规则保持原样，缓存采样匹配实际播放时长。

## 诊断补充

只检查 View 子树仍不足：三星长日志从 1782 变为 1790 时，子树标记已清理，但 `ViewParent.isLayoutRequested` 仍标记窗口根节点需要布局。加入窗口根节点检查后，两台设备的长短日志、长文本、选择框共 12 组快照尺寸一致，整图颜色差为零。不能把首次 pre-draw 当作最终布局。

播放已缩短为 0.6 秒，通常保存 36 个间隔的历史状态。独立正向渲染与逆向还原的 37 个时间点，在两台设备添加附件素材上 RGBA 散列完全一致。继续测量准备阶段耗时，避免将播放缩短误报成启动加速。

准备阶段也试验了提前计算散度与扩大压力工作区。前者收益不稳定，后者在三星上从约 247 ms 退化到 284–296 ms，均已撤回；保持原先验证过的压力计算实现，只保留按播放采样减少历史状态副本。

检查实际绘制依赖后，历史状态由八个 float 收紧为五个：位置 xyz、速度 xy。其余三个分量只用于正向积分；正向解算缓冲仍为八个分量、算法未变。所有保存分量仍为 float32，不进行精度量化。与采样数减少叠加后，预计历史缓冲降到之前约四成，以实际分配日志为准。

## 最终验证与发布

- 22 项粒子相关 JVM 测试通过，全部实际 GLSL 编译通过，无跳过项目。
- 两台设备各检查钢铁侠 225°、添加附件 270°、调整颜色 315° 的 37 个采样，再各检查慢放使用的 61 个采样，共 344 帧逆向还原与独立正向渲染的 RGBA 散列相等。
- 本地五类真实弹窗共 24 组检查通过。发布包再次检查更新日志、颜色信息、选择框、确认框共 16 组，快照与最终 View 尺寸、位置一致，整图像素差为零。
- 发布包播放约 600.5–601.8 ms。钢铁侠、添加附件、调整颜色各导出 1 倍速、0.5 倍速文件；含前后停留的文件长 1.45 / 2.90 秒。预览为 `reverse-appearance.html?v=faster-stable-layout`。
- 历史缓存通常约为此前四成，例如选择框本次约 28 MB。压缩的是状态副本，积分次数及绘制精度保持原样。
