# 出现方向与逆向准备耗时

## 目标与基线

用户要求出现从下方不同位置进入，并继续减少逆向准备等待。当前已发布包 `202609121751` 的真实弹窗渲染请求到首帧：9018f404 约 454–593 ms，三星约 673–850 ms。窗口布局与配色捕获另约几十毫秒；动画本身一秒。

## 诊断闭环

固定素材、方向、种子，使用 Android 的实际共享积分器，分别计时轨迹计算、缓存分配及状态复制；以完整 61 个对应 RGBA 帧与原正向模型相等作为保护。完成后回到真实弹窗测量两台设备的请求到首帧，验证原消散及快速关闭。

优先假设：

1. 完整积分器一直更新已死亡的粒子，但材质和压力采样已经不使用这些粒子。如果跳过它们，GPU 积分时间应下降且可见帧不变。
2. 每个 240 Hz 步骤的调度与中间显存往返增加成本。在同一个压力更新区间合并提交，应降低时间且保留每个原始积分步骤。
3. 压力场的网格求解或轨迹状态复制占主导。如果它们耗时较大，应针对对应部分优化，不能继续凭直觉改主积分器。

项目已有完整 Agent skills 配置，沿用现有领域文档及跟踪方式；本轮不重复初始化配置。

## 已确认的瓶颈与首次验证

逐段强制同步的诊断中，压力场求解约占总耗时三分之二；同步会干扰调度，因此只用来定位主耗时，不作为交付性能。GPU 时间查询在该设备上返回的总量明显小于实际完成耗时，已撤除这项不可信的临时计时。

原逆向准备每次在全部压力网格上执行 100 次迭代，实际多数网格没有有效颗粒。现在先在 GPU 上收集非空网格块，仅对这些块执行完整的八次一批的 Jacobi 求解；空区域的结果仍严格写零。保留第一轮对上一时刻邻域压力的读取，再清空另一个缓冲，避免因清理顺序改变运动。

固定添加附件素材、方向 65°、种子 909602，轨迹准备由上一轮约 413 ms 降至 221.4 ms，61 个对应 RGBA 帧全部相同。这是单次离屏结果，仍需真实弹窗和第二台设备验证。

调度接口依据 Android 的 GLES31 与 Khronos 的内存屏障约定：着色器写间接调度参数后，额外使用 `GL_COMMAND_BARRIER_BIT`；参见 [GLES31](https://developer.android.com/reference/android/opengl/GLES31) 和 [glMemoryBarrier](https://wikis.khronos.org/opengl/GLAPI/glMemoryBarrier)。

## 保留画面一致性的选择

逆向准备从同一份 `step.comp` 派生着色器，仅在粒子寿命结束后跳过不再被材质与压力读取的状态更新；共享源文件和正常消散路径不变。固定添加附件场景的热运行准备为 205.5 ms；三星下方 270° 的首次运行约 345.7 ms，均通过 61 帧像素一致性校验。

试验将四个积分步骤合并到一个计算着色器调用后，实际 GPU 帧散列出现差异，因此撤回，不用微小画面变化换取速度。压力四次一批与八次一批的测量没有明确优势，保留八次一批。诊断过程保留在忽略的 `analysis/appearance-startup` 下，生产代码已去掉临时计时查询。

## 首次准备与真实弹窗

首轮真实弹窗的重复打开，9018f404 请求到首帧为 208–231 ms，三星为 317–347 ms；十二组真实 Chooser／Alert、正反渐变／纯色均完整播放，下方角度正确，动画输入与最终 View 整图像素差为零。首次打开另有约 120–175 ms 的建材／资源／编译准备。

预热原来在首个弹窗的 `onStart` 才开始，与首次动画争用准备阶段。现在在应用首个可见界面的首次绘制后异步触发，同样只使用虚拟材料，且进程内仅一次。出现的计算程序提前编译并与建材重叠；历史缓存共享该程序，避免重复创建与编译。不预计算用户画面，也不预生成整段动画。

目前已通过 21 项粒子相关 JVM 检查（包含所有实际及派生 GLSL 编译）。两台设备三种下方方向、钢铁侠／添加附件／调整颜色的逐帧验证继续使用独立正向输出，不能把旧报告算作本次结果。
