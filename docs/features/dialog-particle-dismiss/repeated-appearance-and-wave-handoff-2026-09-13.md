# 反复出现动画与海浪恢复首帧

用户在已发布版本继续发现：添加附件弹窗反复打开时出现动画经常掉帧；添加附件进入录音后，粒子动画结束处偶发巨大的海浪三角形，随后一帧恢复。

上一轮的重复测试每次重新创建详情页，没有覆盖同一个详情页连续打开的资源生命周期。新回归在一个详情页内连续执行多轮，分开记录 GPU 提交、实际纹理提交和主线程间隔。海浪另用调试专用帧捕获观察冻结画面及解冻首帧，捕获运行不作为性能数字。保留共同粒子模型、轨迹和海浪物理，不以降低粒子数量掩盖调度问题。

测试只使用已授权的 9018f404；不启动实际录音，不改记事。产物位于忽略的 `tuning-0909-gpt6/analysis/repeated-appearance/`。

用户补充：直接 ADB 打开较正常，实际触摸工具栏添加附件更容易掉帧；录音与音频播放关闭仍有单帧闪烁。复现必须通过真实 menu item 的按下／抬起，直接调用 `show()` 仅作消融对照。消失 Surface 交接闪烁重新打开调查，不能沿用上一轮的完成判断。

直接打开的八轮基线仍能捕获 50–81 ms 的纹理提交空档，GPU 大多按 16.7 ms 提交；主线程、GL 绘制完成、窗口帧提交分别记录。海浪首次帧的诊断正在核对延迟数组的初始化线程，避免仅凭恢复后的正常帧作判断。

## 实际触摸复现与调度修正

同一详情页通过真实工具栏 View 的窗口坐标分派 DOWN／UP。基线八轮出现的实际纹理提交数为 34、12、15、29、31、14、14、15，GL 自己仍提交约 35–37 帧。直接 `show()` 不能覆盖这个回归。系统 trace 显示 Activity RenderThread 的 dequeueBuffer 和初始 GPU fence 等待；单独把暗层改为逐帧属性设置没有改善，已撤回。

共同出现入口此前只读取另一弹窗已有的 `ParticleTouchFeedback`，没有登记 Activity 工具栏正在播放的反馈。现在在准备之前就采集宿主反馈，使逆播放历史准备对正在呈现的 ripple 让出 GPU，并等自然结束的窗口帧真正提交。五轮实际触摸初测恢复为 35、35、37、35、37 帧，P90 间隔约 17–20 ms。准备时间、更多重复和复杂弹窗仍需复核，不能据此宣称完全无掉帧。

## 巨大三角形的确定原因

三次真实“附件 → 录音”中，第二次首次冻结帧有 4,704 个顶点位置仍为零，下一张活动帧全部正常。场景 framebuffer 直接读回也出现巨大三角形，证据是 `wave-mesh-baseline/mesh-failure.png`。

`FableSolGlRenderer.buildFrame` 的四个 `lazy(NONE)` 数组此前在并行工作线程内首次读取，会同时分配不同数组，各线程的部分行写入失去。改为在 GL 所属线程统一取得顶点、投影和两组斜率数组，再将局部引用传给行计算，保留延迟分配和全部物理／材质公式。

六轮完整浮点图捕获占用过多测试盘空间，最后一轮写文件遇到 ENOSPC；这组没有完整结果，不计作通过。取回并清理本次诊断文件后改为压缩捕获并限制帧数。生产代码中的三角形修正、冻结首帧初始化，以及消失时的独立 Surface 交接继续分别验证。

压缩捕获的六轮已完成，36 张冻结／恢复图全部通过 GL 错误和零顶点检查，六次首次冻结均为零个未写顶点。初始冻结也以零步长生成水面，首个冻结画面已有完整水体，不再从空白底部突然出现水体。捕获运行不作为帧率结果；正常重力输入和恢复后的物理推进仍会改变水面形状。

## 消失闪烁的独立交接路径

此前只保护 Activity 的粒子层上屏；录音 Dialog 是另一个 Window，SurfaceView 又是其下方独立图层。Surface 退出时原 Window 的洞可能先暴露，下方 Activity 快照不能覆盖还在上方的 Window。现在将同一张最终合成快照也暂存到原根 View 的 overlay，两个 Window 都提交后才移除 Dialog，结束时回收保护层；不隐藏 Surface、不改变布局、不复用旧内容。正在用 Surface 移除前后窗口缓冲做像素回归，尚不将代码推断当作实机无闪烁结论。

最小复现实际移除独立 Surface，保留原 Window：无保护时，海浪测试窗和真实音频播放窗分别有 98.5%／98.3% 的不透明区域像素改变。保留合成图后两者变化超过 2/255 的像素均为零，最大通道误差 1/255。回归脚本包含撤掉保护的对照，不能只以“动画完成”验收闪烁；真实关闭流程还需检查动画层与窗口释放。

## 连续回归与边界

真实工具栏十轮出现均为 35–37 个不同提交帧，P90 为 17–18 ms；出现没有退回到旧版 12–15 帧。严格联合检查仍报关闭阶段的 75 ms 首段空档及个别 P90 超限，不能将其删掉或改阈值当作全部通过。五轮附件→录音的两个出现动画均为 35–37 帧，但重叠时的间隔仍有约 30 ms 的波动。

正在试验有界 GPU 同步队列，让准备的 CPU 提交与上一小批 GPU 运算重叠，最多两批在途，不调整积分或粒子数。同步语义按 [Khronos 同步对象说明](https://wikis.khronos.org/opengl/Sync_Object) 与 [Android GLES30 API](https://developer.android.com/reference/android/opengl/GLES30) 核对；这是排队改进假设，保留与否取决于实测准备耗时、ripple 和实际呈现间隔。

有界队列八轮实际触摸将准备降至 166–196 ms（此前多为 314–359 ms），触摸抬起至出现首帧中位数 491→436 ms；出现 33–37 帧，没有复发十几帧。三轮录音／取消／返回的反馈交接检查通过，ripple 尾段间隔 9–11 ms，但部分关闭仍有 33 ms 派发间隔。

进一步保留窗口提交时刻与主线程接收时刻：两者可能相差约 15–23 ms，测量须区分；本轮的 33 ms 仍见于真实 GL 派发，并非全是测量延迟。`ParticlePlaybackClock` 以前直接丢掉绘制在途时收到的节拍，约 18 ms 的工作会等到 33 ms 才重开。改为最多保留一个最新待绘制节拍，完成本帧立即处理它，不积压历史帧、不改变动画时长，正在复测。

保留最新节拍后，八轮关闭均提交 60–62 帧、窗口取得 58–61 帧，P90 恢复 17–19 ms；八轮出现 35–37 帧，P90 17–19 ms。仍有两个关闭的起步空档为 67／71 ms，因此严格联合预算未全通过，记录保留；出现偶有约 49 ms 合成间隔，也不能宣称每一帧稳定 60 fps。暗层额外试验不透明单层优化未改善这部分，已撤回。

本轮保留的生产改动仅包括宿主 ripple 协调、有界准备队列、最新节拍接力、原窗口 Surface 合成图保护，以及海浪首帧初始化修正。粒子模型、材质、数量、积分及正反轨迹没有更换。26 项方向／逆播放／并行模拟／冻结状态 JVM 检查通过；帧率结论只取未捕获图像的运行。

撤回暗层试验后，最终代码两轮各录音、取消、返回交接检查通过。录音出现实际提交 35／36 帧、关闭 59／60 帧，录音交接主线程最长 39／27 ms，ripple 尾段间隔 9 ms；全部末帧、暗层与释放检查通过。第一附件窗口在这份旧交接工具中直接打开，其 32／37 帧不能替代前述真实工具栏测试。完整结果保留在 `final-transition/`，随后使用发布包复核真实工具栏和海浪。
