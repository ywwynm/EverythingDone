# 弹窗完整呈现连续性

用户对上版提出八项问题：ripple 尾段卡顿、暗层先于粒子出现、海浪窗口消散闪一帧、海浪和双弹窗动画掉帧、外观面板 A 的颜色页错误进入 B 的出现快照、复杂窗口创建停顿、出现准备慢。验收从最终 alpha 和总帧数扩展到实际呈现时序、尾段间隔以及前后帧内容。

已有代码确认暗层在请求出现时立即启动 220 ms 淡入，粒子准备后才播放 600 ms；两者并未共享呈现时钟。既有工作区的功能和其它功能改动保留。本轮大型产物放在忽略的 `tuning-0909-gpt6/analysis/presentation-continuity/`。

## 基线与假设

真实录音交接原窗口 FrameMetrics 最长 106 ms，主线程最长 81 ms；海浪关闭仅 40 次纹理更新。ripple 状态在更新不等于 GPU 已及时绘制。按顺序验证：同步捕获／构造占主线程、独立计时器错过显示节拍、快照早于纹理合成撤下、布局过渡夹带旧页面。

用真实 `panel_thing_card_appearance.xml` 复用执行 A 外观 → A 颜色 → 关闭 → B 外观，输入与最终图不同；输入叠着旧颜色控件与新外观内容。捕获时 `LayoutTransition.isRunning=true`，尺寸完全相同。这是过渡仍绘制已 GONE 子树导致，非快照按记事 ID 的缓存问题。原始证据 `panel-before/input.png`、`final.png`。

## 已定位并修正

- A→颜色页→B 的真实布局复用回归：第一次仅移除 LayoutTransition，仍残留旧布局监听器，动画完成后按钮行偏移 311 px。补充布局完成后的旧过渡取消与重新布局后，输入快照与最终 B 页面整图逐像素相同（2478×1008），证据 `panel-layout-final/`。
- 主线程栈采样定位了 FableSol 模拟/星光初始化、Timely 字体 JSON 解析、反复计算字形边界及静态相同数字的轮廓匹配。海浪重型对象延迟到 GL 使用，当前计时字体在首屏后异步预读，字形包络随字体解析缓存，相同数字跳过形变匹配。
- 快照硬件提交后，GPU 等待、像素读回、渲染器销毁均移到串行后台队列，失败恢复真实内容。
- TextureView 建链先产生 timestamp=0 的空缓冲，不能作为粒子首帧；`onSurfaceTextureUpdated` 通知也早于 RenderThread 实际取缓冲。现在等承载窗口的帧提交回调读取有效时间戳，再隐藏快照、开始暗层。普通快照层与真实窗口的交接也使用帧提交回调。
- EGL 在最后一次 swap 后立即断开会丢弃尚未取走的末帧，先前实际依赖 700 ms 兜底恢复窗口。现在保留连接直到末帧被取走，7 类真实交接测试的末帧时间戳全部匹配，正常结束不再靠超时跳变。
- ripple 的逻辑 alpha 到零之后，还要等原窗口把该帧提交；否则海浪窗口的 PixelCopy 仍可能抓到旧反馈。这项等待属于公共处理，覆盖普通按钮、确认、取消及弹窗连续打开。

## 验证与当前性能

- `final/`：真实详情页记录录音准备、连续普通弹窗、普通关闭、确认、取消、返回、背景关闭 7 类操作。完整 ripple 后才交接，尾段 UI 间隔最大 9 ms；初建录音窗口主线程最长 35 ms（基线 81 ms），原窗口最长帧 54 ms（基线 106 ms）。录音仅打开准备页，不启动录音。
- 优化的压力批处理用于正向实时播放，保持全部 240 Hz 积分和 100 次压力求解。钢铁侠、添加附件、改变颜色各 37 帧：优化正向、逆向缓存分别与原逐步计算的 RGBA 结果 SHA 完全相同，共 111×2 次比较。`gpu-*.json` 保存证据。
- `coverage-final/`：海浪 Surface、真实音频播放窗口（合成静音）、准备中立即关闭、Texture 回退、外观 panel 均完成捕获及退出；`colors-final/`：选择与更新日志两类窗口的动画输入标题、按钮、内容与最终绘制像素相同。
- 出现动画 GPU 提交约 37–38 帧/600 ms，但实际纹理更新及提交会丢帧，录音重叠场景仍只确认 19 个不同纹理帧；消失确认约 56–60 帧/秒，已改善原海浪场景约 40 次更新的情况。不能将 GPU 提交数量当作屏幕帧率，也不能宣称已稳定 60 fps。
- 普通出现轨迹准备约 177–208 ms；录音与前一消失重叠时约 347 ms。已减少 UI 阻塞和重复海浪首帧，仍存在完整逆向轨迹解算及窗口纹理合成开销。120 Hz 提交和额外透明窗口刷新率投票未稳定改善，因此不保留。

图形管线依据：[AOSP TextureView](https://source.android.com/docs/core/graphics/arch-tv) 说明其通过新缓冲触发重绘，并可能丢弃排队缓冲；[SurfaceTexture 时间戳](https://developer.android.com/reference/android/graphics/SurfaceTexture) 对 EGL 生产者使用指定的呈现时间。本轮用独立的提交和取帧时间核对，避免仅凭回调次数判断视觉流畅度。

## 继续定位纹理丢帧

更换真实窗口交接回调后，连续选择框的一次测试仍仅 40 个纹理更新，帧数断言失败，未降低阈值。日志中 GL 已提交 59 帧，因此进一步检验缓冲未完成就连续排入 TextureView 的影响。

`ready-buffer/` 在专用 GL 线程等当前绘制完成后再交换缓冲，四条重复录音／选择框交接通过；录音出现的不同提交帧从 19–20 增至 35，选择框出现从 19–25 增至 35–36。仅对逆向等待的消融 `reverse-ready/` 在第三条录音交接复现掉帧：旧窗口仅 37 次更新、新窗口 24 次，因此采用前后窗口都提交就绪缓冲的共同处理，主线程不等待 GPU。首次冷动画及偶发主线程长帧仍需保留在结果中，不能只报告最快的一次。

连续六条 `buffer-ready-final/` 帧数通过，但重复录音触发后约 350 ms 仍出现 98/116 ms 主线程空档；栈采样 `buffer-stall-profile/` 定位为 HWUI 的 `nSyncAndDrawFrame` 等待，并非再次解析字体或构造录音窗口。代码存在 ripple 释放播放优先级、源粒子到首帧才取得优先级之间的空档，后台逆算可在此时批量排队。

源消散从准备阶段就持有优先级，直到最终交接结束。最终 `priority-continuity/` 连续三轮录音、三轮普通弹窗全部通过：录音主线程最长 43/31/31 ms，普通窗口 26 ms；350 ms 附近不再出现上述长停顿。录音出现实际不同提交帧为 35/37/37，普通下一窗口均 37；源消散为 52–59，下一窗口消失为 58–59。所有动画末帧匹配，暗层首尾同步，ripple 尾段最大间隔 9 ms。回归现另要求实际不同提交帧至少 28/45（出现／消失），非采样模式主线程最长间隔低于 70 ms；未降低既有帧数阈值。

首次录音出现仍需等待 Surface 首帧与完整逆算，按钮抬起到出现开始该组三次约 824/485/550 ms，其中前约 330 ms 原按钮自然完成反馈，期间下一窗口并行准备。可见等待已由源粒子覆盖，不能宣称零准备时间；重叠播放还会丢少量帧。
