# 批量移除与退出选择模式的动画交接

## 需求与视频证据

用户要求修复完成／恢复／删除／彻底删除后的完整动画，并覆盖根目录、文件夹、滚动位置、可见／不可见选择组合。保留 SurfaceView；允许动画期间阻止输入；既有记事不做破坏性操作。

用户补充：两段视频来自另一台 OPPO 手机，不是已连接的 OPPO 平板，也不是卓易通。不能把问题限定为兼容环境。

两段视频为可变帧率：第一段 745 帧／7.2256 秒，第二段 662 帧／7.0586 秒。按解码帧及时间戳核对，第一段约 4.78～4.88 秒出现状态栏图标先变暗、工具栏菜单提前消失、选择工具栏突然退出且状态栏顶部残留色条。约 5.07 秒，剩余文件夹与卡片出现第二次位置跳动。原始文件未改动；逐帧图与时间戳在 `tmp/selection-transition-20261013/`。播放器换算帧号与解码帧号不同，不据此否定用户定位。

## 可证伪的候选原因

1. `ThingListRemovalAnimator.onBodyReleased` 提前派发差分／退出选择，而统一 GL 前景仍持有旧工具栏。若成立，记录应显示选择退出早于粒子／前景彻底释放；移到完整释放后，真实动画应重新可见。
2. `ModeManager.hideContextualToolbar` 立即清空菜单、切系统图标并开启普通阴影。若成立，原实现对照也会出现菜单／系统栏时序问题；保持菜单和旧状态至对应移动阶段后可消除。
3. 剩余卡片绑定直接设置最终颜色／透明度，瀑布流差分后又改变布局锚点或尺寸。若成立，逐帧 View 属性会有无中间值的跳变；动画属性与固定身份／位置记录可分离颜色跳变与布局跳变。

## 反馈回路

使用实际 `ThingsActivity`、`ModeManager`、`ThingsAdapter` 和业务确认入口。为覆盖真实完成／永久删除而不修改用户数据，测试包用独立 applicationId，创建虚构记事／文件夹；探针拒绝在原应用包运行。临时 Gradle init 脚本只改变测试构建包名和 Provider authority，正常发布仍用原配置。每例检查业务结果、动画阶段、逐帧工具栏／卡片属性及录像，不把“回调结束”当成画面通过。原包与数据库保持原样。

初始先建立有代表性的失败样本，再按证据逐项修正；最终矩阵覆盖两种粒子样式、五种来源状态／动作、根目录／文件夹、顶部／中段／底部、可见／混合／全不可见、空列表与部分保留，并补动画关闭和中断路径。

## 已复现与第一轮修正

隔离测试包使用实际 `ThingsActivity`、业务确认按钮和 DAO，在三星复现：选择模式在 2072 ms 退出，而粒子前景直到 2453 ms 才释放，退出／补位被遮挡约 381 ms。魅族文件夹恢复路径还出现未采到可见来源就提前退出的情况，需要核对实际布局与屏幕坐标。

第一轮候选把列表差分移至 `afterRelease`；旧卡片在真实内容交接时隐藏，避免释放前景时闪回。输入封锁覆盖补位与选择退出。工具栏改为按自身高度移动，保留菜单至退场完成；状态栏图标在背景退场后切换，普通阴影随旧阴影移走渐显。记事／文件夹的选择淡化用真实 View 属性连续恢复，不重播媒体加载；批量动作只更新标题计数，不重建未变化的标题布局。尚需逐帧回归，不将构建成功当作画面通过。

进一步回归：魅族差分后的布局准备约 280～300 ms，若动画时钟在发布差分时启动，仍会吞掉动画。将工具栏／颜色恢复的时钟移到布局完成后的 pre-draw，准备期间保持初态；保留记事使用专用 payload，仅更新选择外观。

三星“文件夹／底部／全不可见／彻底删除”发现独立业务失败：`ThingDAO.updateStates` 的写事务内调用 `ThingFolderDAO.touchUpdateTime`，后者另一连接等待同一数据库，约 2.5 秒后抛 `SQLiteDatabaseLockedException` 并回滚。改为删除连接内更新容器时间，两者保持原子性。原失败结果与日志保留，不计入通过。

## 扩展回归中的发现

三台设备各 12 例（共 36 例）已通过真实业务状态核对与逐帧属性检查，覆盖根目录／文件夹、三种滚动位置、可见／混合／全不可见选中项、清空列表、流体／飘散及普通淡出。退出阶段没有仍挂载的粒子覆盖层，工具栏菜单没有提前清空，输入封锁保持至布局与动画稳定，保留项位置和内容透明度存在连续中间值。工具栏退场期间，三星采到 34～35 个中间帧，魅族 16～18 帧，OPPO 平板 17～36 帧；记录的最大帧间隔分别为 20／19／18 ms。这只是此阶段的测量，不代表整个应用或粒子渲染的整体帧率。

三星返回中断通过，已确认的状态操作完成且无输入锁残留。关闭三项系统动画缩放后，批量彻底删除通过；系统原值在 `finally` 中恢复并比对。该例 screenrecord 结束超时，业务 JSON 与截图另行拉回，不能将它记成录像通过。

魅族夜间外观另发现原生卡片颜色异常：模型／GradientDrawable 的浅绿 `#CAD9C2` 在屏幕上为反色深紫，退出颜色动画开始才回到浅绿；旧版对照也有反色。显式对 View 设置 `forceDarkAllowed=false` 的两次对照均未消除，暂不据此改生产深色模式。继续核对 Drawable 缓存与复用路径，防止把错误起始色带入新恢复动画。

进一步用纯软件 Canvas 分离渲染路径，连 `drawColor` 的像素也被改写，排除 GL 和 Drawable 复用。读取该测试机自带的 `framework.jar` 与 `/apex/com.flyme.runtime/javalib/framework-flyme.jar`，确认 `FlymeDarkModeInjectImpl.initNightMode()` 查询 `Application.mzNightModeUseOf()`；返回 `0` 表示应用自行处理、停用 Flyme 二次颜色变换，与标准 `View.forceDarkAllowed` 无关。候选在 `App` 添加保留方法名的同签名回调（标准 SDK 无此成员，不能写 `override`），不调用隐藏 API、不替换渲染后端、不增加设备判断。源码反汇编仅用于本地分析，位于被忽略的临时目录，不随应用或功能文档发布。接下来验证纯色／渐变、浅深外观及其它设备无影响。
