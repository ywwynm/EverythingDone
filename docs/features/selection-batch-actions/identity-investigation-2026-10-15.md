# 完成、恢复、删除后的记事身份排查

## 用户现象与本轮约束

用户报告：在滚动后的列表长按 A 并完成，到已完成恢复 A；回到正在进行时 A 位于 B 前方；长按 A 删除，再永久删除全部已删除记事，最终 A 仍在而 B 消失。B 来自其它设备碰一碰接收。用户不排除误选，要求先复现再修复，不把推测当作已确认缺陷。

本轮授权设备为 `3B1629006YC00000`、`R5CW20BLNKL`、`192.168.100.67:40807`。使用独立测试包及虚构数据执行破坏性操作，逐步比对实际卡片绑定身份、选中集合、动作目标及数据库结果。原应用数据不作为删除夹具。

- 传输文件的字段不含发送端记事 ID；`ThingFileReader` 创建 ID 为 0 的待导入对象，`ThingFileImporter.commit` 在主线程取本机 `headerId`，`ThingManager.create` 使用同一 ID 并推进分配位置。`things.id` 是 SQLite 主键。同名或来源相同不能使两条本地记录共用 ID。
- 三机各一轮连续操作通过：独立包以与 A 相同的源 ID 导出 B，经正式 Writer／Reader／Importer 创建本地新 B；A 完成再恢复后位置为 1、B 为 2，长按 A 删除、普通工具栏永久删除全部回收站记事后，A 不存在、B 仍为正在进行。采样的卡片绑定 ID 与当前位置模型均一致。
- 首轮证据目录：`tmp/selection-transition-20261013/identity-samsung-baseline3-1015/`、`identity-oppo-baseline2-1015/`、`identity-meizu-baseline-1015/`。长按与确认按钮用实际触摸，菜单与状态切换执行正式 UI 回调。初始定位使用真实布局管理器滚到 A，尚需补充手指滚动和其它时序。

## 代码核查

- `ThingFile` 不序列化源记事 ID。导入时在主线程分配本地编号；`ThingDAO.recreateHeader` 以本地最大 ID／排序值加一初始化分配位置。SQLite 的记事 ID 为主键，正常导入不会保留发送端 ID，也不会制造两条共用同一 ID 的本地记事。
- `ThingsAdapter.ThingViewHolder` 的点击／长按回调当场读取 `adapterPosition`，没有捕获绑定时的位置。Activity 据当前位置的 `ThingListEntry` 选择对象；批量动作在确认前复制目标集合，后续执行按对象 ID。
- `ThingListRemovalDiff` 以稳定身份做差分，退场期间冻结旧列表投影，收尾再更新；拖动路径也按稳定身份校验和解析当前位置。
- `getTrashedThingsInScope` 在根目录只取得自身状态为 `DELETED` 的记事，再交给 `deleteThingsForever`；DAO 按 ID 删除。没有发现把正在进行列表中的第二个索引直接拿去永久删除的路径。

## 结论与边界

本轮未复现“选 A 却删 B”，因此没有修改生产业务逻辑。发送端编号碰巧与 A 相同已通过正式序列化和导入做了对照，不支持“碰一碰直接沿用源 ID”这一解释。

测试使用虚构记事及正式文件导入链，没有执行物理碰一碰握手，也没有使用用户的原始 A／B、当时的应用版本、筛选设置或操作时序；六轮通过不能排除尚未覆盖的时序条件，也不能认定用户误操作。后续若再次出现，优先保存从完成到最终列表的连续录屏、版本及动作目标身份，再按已保留的 [隔离脚本](checks/README.md) 扩充复现用例。
